## Cross-Cut Details

### CX-01: Policy Library ↔ Enforcement Ladder

**Relationship**: The ladder resolves (act, rule-version-in-force-at-act-time) → sanction. The policy
library owns the rule text, its version history, its effective dates, and the record of which terms
version each user accepted and when. A rule with no version has no enforceable date, and a sanction
against it is arbitrary by construction.

**Role scoping**:
- **Musician / Producer / Operator / Fan**: read the current rulebook; on a sanction, see the *specific
  version* cited. This is the difference between "you broke the rules" and "you broke rule 4.2 as it
  stood on 12 March, which you accepted on 3 January".
- **Admin/Moderator** *(not a persona — Q-02)*: authors and versions rules; cannot sanction against an
  unpublished draft.

**Synthesis questions answered**:
1. **Shared state conflict**: the library owns rule text; the ladder owns the sanction record, which
   *pins* a rule version by ID. Pinning, not referencing — a later rule edit must not retroactively
   change what a past sanction said.
2. **Trigger chain**: rule publish → taxonomy update (24.01.01) → engine rebuild (24.02.05). If the
   engine rebuild fails, the gate and the rulebook disagree; the correct failure is to keep the old
   engine and alert, not to fail open.
3. **Permission intersection**: rule authorship is the highest-privilege action in the domain — it
   changes what everyone else can do. It needs its own audit trail (Audit Log cross-cut).
4. **Notification fan-out**: a material rule change notifies all users and re-triggers terms acceptance.
5. **State transition conflict**: an act committed under v3, reported under v4, decided under v5. The
   sanction must resolve against v3. Any other answer is retroactive rule-making.

### CX-02: Enforcement Ladder ↔ Statements of Reasons

**Relationship**: The sanction and its SoR are one atomic act. The SoR's statutory field list
(facts relied on, whether automated means were used, the legal or contractual ground, territorial scope,
duration, redress options) is effectively a schema specification for the decision record — which means
the decision record must be structured from the first sanction, not retrofitted once a regulator asks.

**Role scoping**:
- **Musician / Producer / Operator / Fan**: receive the SoR. For Musician and Operator it may describe a
  loss of livelihood, which sets the bar for how specific it must be.
- **Admin/Moderator**: fills the structured decision; the SoR is generated, never typed.

**Synthesis questions answered**:
1. **Shared state conflict**: one record, two projections (the sanction's effect; the user's notice).
   No merge problem by construction — which is the reason to build it this way.
2. **Trigger chain**: decide → persist structured record → apply sanction → emit SoR → (Art 24(5)) submit
   to the Commission's Transparency Database. If SoR emission fails, the sanction must not stand alone;
   the correct compensating action is to roll back the sanction, not to retry silently.
3. **Permission intersection**: none beyond operator scope.
4. **Notification fan-out**: target (SoR), reporter (outcome), and — where the action is on a listing or
   booking — the counterparty, whose transaction just evaporated.
5. **State transition conflict**: a sanction applied while an appeal on the same object is open must not
   double-apply. The object's enforcement state is a state machine, not a set of flags.

### CX-03: Appeals ↔ Enforcement Ladder

**Relationship**: The appeal is the reverse edge. Its existence imposes a design constraint on every
sanction: *sanctions must be undoable, including their side effects*. This is where the constraint gets
expensive — reversal is not un-deletion.

**Role scoping**:
- **Musician**: reversal means their listing, credits, or payout eligibility returns. The listing may
  return to a market where the buyer has already bought elsewhere; the restoration is nominal.
- **Producer**: reversal of a takedown on a mix that has already missed the release date restores a file,
  not the opportunity.
- **Operator**: reversal after the date has passed restores a calendar slot that no longer exists —
  perishable inventory cannot be un-lost (`personas.md`).
- **Fan**: reversal restores account access; usually complete.

**Synthesis questions answered**:
1. **Shared state conflict**: the appeal owns the review; the ladder owns the sanction state. Only the
   appeal outcome may transition a sanction to `reversed`.
2. **Trigger chain**: appeal → human review (never solely automated) → reverse or uphold → restoration
   cascade. **The cascade is the hard part**: reinstate the listing, release the escrow, restore the
   credit, un-strike the repeat-infringer counter, requeue the payout. Each has its own failure mode and
   its own window that may have closed.
3. **Permission intersection**: the appellant must be the sanctioned party — but for an entity sanction,
   *which member* may appeal on the band's behalf is a domain 01 mandate question.
4. **Notification fan-out**: appellant, original reporter, and any counterparty affected by restoration.
5. **State transition conflict**: yes, and it is real — a user can appeal while a second, independent
   sanction lands on the same account. Reversing one must not reverse the other.
