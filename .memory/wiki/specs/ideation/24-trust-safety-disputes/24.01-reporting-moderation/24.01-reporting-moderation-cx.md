## Cross-Cut Details

### CX-01: Report Intake ↔ Queue & Reviewer Ops

**Relationship**: Intake produces a case object (reporter, target, reason, evidence, jurisdiction,
timestamp). The reason code — chosen from the taxonomy bound to
[24.02.04 Policy Library](../24.02-enforcement-appeals-policy/24.02.04-policy-library-versioned-terms.md) —
determines queue, severity, SLA and required reviewer skill. Three reason codes bypass the general
queue entirely: CSAM (→ 24.08.01), self-harm (→ 24.06.03), and factual rights disputes (→ domain 02/09).

**Role scoping**:
- **Musician / Producer / Operator / Fan**: see only their own case ID, status, and the eventual
  reasoned decision. They never see the queue, the severity, or the reviewer.
- **Admin/Moderator** *(not a persona — Q-02)*: the only actor with queue visibility.

**Synthesis questions answered**:
1. **Shared state conflict**: Intake owns the case object; the queue owns the *assignment*. Two reports
   on the same target must dedup into one case with N reporters, or a brigade becomes N enforcement
   signals. Merge strategy: dedup by (target, reason-family), retain each reporter for notification.
2. **Trigger chain**: intake → dedup → route → queue. Sync through routing (the reporter must get a
   case ID immediately); async thereafter. If routing fails, the case must land in an unrouted
   dead-letter queue that is itself SLA'd — a lost report is a statutory breach, not a dropped job.
3. **Permission intersection**: reporting requires no permission (anyone may report anything). Acting
   on it requires operator scope. That asymmetry is the whole design.
4. **Notification fan-out**: intake notifies the reporter (receipt). The *decision* notifies both
   reporter and target — the target's notice is the Statement of Reasons (24.02.03), a different object.
5. **State transition conflict**: the target object can be deleted by its owner while queued. The case
   must survive its target — the evidence snapshot in [24.09](../24.09-case-evidence-locker.md) is what
   makes that possible.

### CX-02: Automated Classification ↔ Queue & Reviewer Ops

**Relationship**: The classifier writes a score and a label onto a queue item. It has no authority to
remove, restrict, or notify. The only exception is exact-hash-matched illegal content (24.08.01),
which is not classification but matching — a categorically different confidence regime.

**Role scoping**:
- **All four personas**: no visibility. They experience only the *latency* of review.
- **Admin/Moderator**: sees the label and score as a sort key, with the classifier's confidence shown
  so it can be distrusted.

**Synthesis questions answered**:
1. **Shared state conflict**: the classifier writes only to its own fields on the case; it never mutates
   the reporter's reason code. A model that overwrote a human's stated reason would destroy the SoR.
2. **Trigger chain**: upload/edit → classify (async) → enrich queue item. Classifier failure degrades to
   an unscored item at default priority — it must never block ingestion or fail closed onto removal.
3. **Permission intersection**: none.
4. **Notification fan-out**: none. A classifier hit notifies nobody, by design (CX-02 evidence).
5. **State transition conflict**: content edited after classification carries a stale score. Re-classify
   on edit, or the score is a lie — and an edited gear listing is exactly the fraud pattern (24.03.03).

### CX-03: Trusted Flagger ↔ Queue & Reviewer Ops

**Relationship**: A trusted-flagger notice enters at elevated priority with a shortened SLA, may arrive
in bulk via API, and carries a legal status ordinary reports do not. The queue must write outcomes back
to the flagger's accuracy record.

**Role scoping**:
- **Musician / Producer**: are the parties bulk label notices land *on*. Their exposure to this lane is
  entirely as a target — which is precisely why the asymmetry is a values question (24.01 index Q-02).
- **Operator / Fan**: not affected.

**Synthesis questions answered**:
1. **Shared state conflict**: the flagger's accuracy ledger is owned here; the flagger *entity* is owned
   by domain 01. Revocation of status is an enforcement action (24.02.01) against an organisation.
2. **Trigger chain**: bulk notice → per-item cases → priority queue → decisions → accuracy write-back →
   threshold breach → status review. Bulk submission failing halfway must be idempotent per item; a
   retried 5,000-item notice must not create 10,000 cases.
3. **Permission intersection**: yes, and it is the point — flagger status *is* a permission that changes
   the SLA of a report. It is granted by the platform and revocable under Art 22(6).
4. **Notification fan-out**: each per-item decision notifies the target (SoR) and the flagger.
5. **State transition conflict**: a bulk notice and a user's own edit can race on one listing. Snapshot
   at case creation (24.09) resolves what was actually claimed against.

## Rejected Pairs

| # | Source | Target | Reason for Rejection |
|---|--------|--------|---------------------|
| R-01 | 24.01.04 Trusted Flagger | 24.01.05 Messaging Safety | Considered because rights-holders would like DM surveillance for leak-hunting. Rejected outright: trusted-flagger status grants queue priority on *reports about public content*; it must never grant reach into private messages. Granting it would make the lane a surveillance instrument aimed at the platform's own users. |
| R-02 | 24.01.02 Automated Classification | 24.01.04 Trusted Flagger | No interaction. A trusted flagger's notice is a human legal assertion; scoring it with a content classifier adds nothing and would let a model silently downgrade a notice with statutory standing. |
| R-03 | 24.01.05 Messaging Safety | 24.01.02 Automated Classification | Considered sharing one classifier across public content and private messages. Rejected: same technique, incompatible governance — different lawful basis, different retention, different escalation, different user expectation. Sharing the model is an implementation detail; sharing the *pipeline* is a privacy incident. |
