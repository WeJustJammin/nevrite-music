## Cross-Cut Details

### CX-01: Off-Platform Income Import ↔ Verified Income Statement

**Relationship**: Import is what makes the ledger complete; verification is what makes it credible. These pull in opposite directions and the tension is the sub-domain's central design problem. Every imported row raises coverage and lowers provable trust. The resolution (D-03) is that trust is a **property of each row**, and the statement renders two totals rather than one.

**Role scoping**:
- **Musician**: feels this hardest — the multi-hyphenate's income is exactly the long tail of small, often cash, often unverifiable payments. Their statement will show a large declared portion.
- **Producer**: mostly session fees and points; a higher proportion is invoice-backed and therefore evidenceable even when off-platform.
- **Operator**: their off-platform income (bar take, door cash) is large and genuinely unverifiable by WeJammin.
- **Fan**: not affected — no access to this sub-domain.

**Synthesis questions answered**:
1. **Shared state conflict**: The ledger row owns `trust_tier`. Import sets it to `declared`; nothing may promote a row to `verified` except the arrival of a platform event or an accepted evidence attachment. Users must never be able to self-promote a tier.
2. **Trigger chain**: Import → row created (`declared`) → statement totals recompute. If a later platform event matches an imported row (CX-04), the row is reconciled rather than duplicated, and the tier may rise to `verified`.
3. **Permission intersection**: A delegated accountant (see the Representation cross-cut in the domain CX) may import on the user's behalf but must not be able to set trust tiers either.
4. **Notification fan-out**: A tier change on a row that a statement has already been generated from should invalidate/re-issue that statement — an artefact already sent to a third party cannot be silently changed.
5. **State transition conflict**: If import and a platform event race for the same economic fact, the platform event wins and the imported row is merged into it.

### CX-02: Income Event Ledger ↔ Multi-Currency Normalization & FX

**Relationship**: The ledger stores native currency and amount; FX supplies the reporting-currency projection. The rate-date rule (transaction date vs receipt date vs period-average) is a **policy** the user's tax jurisdiction largely dictates, not a preference. Changing the policy retroactively restates every historical total, including totals already exported in a tax pack.

**Role scoping**:
- **Musician**: touring and streaming both create cross-border income; hits this immediately.
- **Producer**: remote sessions for overseas clients; same exposure.
- **Operator**: mostly single-currency (their room is in one country) — config only, and often a no-op.
- **Fan**: not affected.

**Synthesis questions answered**:
1. **Shared state conflict**: Native amount is immutable; the reporting projection is derived and recomputable. Never overwrite the native amount with a converted one.
2. **Trigger chain**: Event arrives → rate looked up for the policy date → projection cached. If the rate source is unavailable, the row must remain visible with an unresolved projection rather than being dropped from the ledger.
3. **Permission intersection**: FX policy is account-level config; a delegated accountant is exactly the party who should set it, which is an argument for `⚙️ Config` delegation granularity.
4. **Notification fan-out**: A policy change restates history — the user must be warned that previously exported artefacts no longer match.
5. **State transition conflict**: Rate revisions from the provider vs a locked/exported period. A period exported to an accountant should freeze.

### CX-03: Income Event Ledger ↔ Income-to-Work Linkage

**Relationship**: This is where the domain touches the platform thesis. Provenance (D-18) says the record of who did what must survive; the linkage says the record of **what that work paid** survives with it. The linkage is a read projection joining ledger rows to the credits graph — it stores no money of its own.

**Role scoping**:
- **Musician**: sees lifetime earnings per credit — "this session has paid me £340 across three years."
- **Producer**: sees the same for works they ran, plus their points/backend.
- **Operator**: no linkage — their income attaches to a room and a date, not to a work.
- **Fan**: not affected.

**Synthesis questions answered**:
1. **Shared state conflict**: The credits graph (domain 02) owns the work and the credit; 23.01 owns the money. Neither writes the other. A disputed credit must not silently delete money.
2. **Trigger chain**: Ledger row references `work_id` when the originating domain supplies one. If the credit is later contested or revoked, the linkage must degrade to "unattributed income" — the money is still real.
3. **Permission intersection**: Earnings-per-credit is private. Credit visibility (public) and earnings visibility (private) are different permissions on the same join — a leak here exposes what someone was paid.
4. **Notification fan-out**: Deferred — `[PENDING — /ideate-discover Step 5 deepening]`.
5. **State transition conflict**: A credit revoked while earnings are displayed against it. Money survives; attribution does not.

### CX-04: Off-Platform Income Import ↔ Income Event Ledger

**Relationship**: Imports and platform events describe overlapping reality. The same £500 can arrive as a WeJammin settlement event **and** as a bank credit in a CSV. Without reconciliation the ledger silently doubles the user's income — which then flows into the tax pack (23.02) and the proof-of-earnings artefact (23.01.04), producing a document that is wrong in the user's favour. That is the highest-consequence failure mode in this sub-domain.

**Role scoping**:
- **Musician**: most exposed — the most import sources and the most platform events.
- **Producer**: same mechanism, fewer sources.
- **Operator**: high volume of both; settlement plus bank feed is a routine double-count.
- **Fan**: not affected.

**Synthesis questions answered**:
1. **Shared state conflict**: The platform event is authoritative (D-02). An imported row that matches one is absorbed, not kept alongside.
2. **Trigger chain**: Import → candidate match on amount + date window + counterparty → user confirms merge. Matching must propose, never auto-merge silently; a wrong auto-merge deletes real income.
3. **Permission intersection**: Same as CX-01 — delegates may import, not adjudicate trust.
4. **Notification fan-out**: Unresolved duplicate candidates must block a "final" tax pack export rather than being ignored.
5. **State transition conflict**: A late-arriving platform event matching an already-imported row — the merge must work in both temporal directions.
