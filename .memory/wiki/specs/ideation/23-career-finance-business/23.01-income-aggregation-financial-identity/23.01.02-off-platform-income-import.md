# Feature: Off-Platform Income Import

> **Number**: 23.01.02
> **Parent**: [Income Aggregation & Financial Identity](./23.01-income-aggregation-financial-identity-index.md)
> **Status**: [SURFACE]
> **Last updated**: 2026-07-16

## Overview

WeJammin will never see all of a musician's money — the cash function, the Bandcamp payout, the teaching hour paid by bank transfer, the years of career that happened before signup. Import lets the user complete the picture, at the cost of introducing income the platform cannot prove. The feature's real job is not data entry; it is **holding the line between what is verified and what is merely claimed**, because that line is what makes 23.01.04 worth anything.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Full | The heaviest user: their income is the long tail, and much of it is cash or from platforms WeJammin does not touch. Imports CSVs, adds one-off rows for a cash function, backfills pre-signup history to make a proof-of-earnings artefact usable sooner. |
| Producer | Full | Imports invoice-backed off-platform work (a label session billed directly). Their off-platform income is more evidenceable than a Musician's — an invoice and a bank credit exist — so a higher share can carry an evidence attachment. |
| Operator | Full | Imports door cash, bar take and bookings made by phone or email — the workaround stack in `meta/personas.md`. Genuinely unverifiable by WeJammin and high-volume; the duplicate-collision risk against their own platform bookings is the worst of any persona. |
| Fan | None | Not visible — no income, no professional stake. |

## Behavior

Import creates ledger rows at trust tier `declared`. Nothing the user does can promote a row to `verified`; only a matching platform event (23.01.01) or an accepted evidence attachment can. Every import runs duplicate detection against existing rows before committing, and proposes merges rather than performing them.

### Happy Path

1. Musician uploads a bank CSV (or adds a single cash row manually).
2. System parses rows, proposes a source category and currency per row.
3. System flags 3 rows as probable duplicates of settlements WeJammin already recorded, showing both sides.
4. User confirms the merges and the categories.
5. Rows land as `declared`; the merged 3 stay `verified` and are not double-counted. Totals recompute with declared and verified shown separately.

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Imported row duplicates a platform event | Match proposed on amount + date window + counterparty; user adjudicates | Side-by-side comparison, "same money?" — never a silent auto-merge |
| User imports the same CSV twice | File-level and row-level idempotency; re-import is a no-op for unchanged rows | "N rows already imported, 0 added" |
| A bank credit is a **transfer between the user's own accounts**, not income | Must be classifiable as non-income or the ledger inflates | "Not income" classification available and remembered by rule |
| A bank credit is a **loan or an advance**, not income | Same problem, higher stakes — an advance is a liability, and 23.06.03 must net it, not count it | Routed to advances, not income |
| User inflates declared income to win an advance or a tenancy | Tier segregation contains it — declared income carries no weight where it matters. The anti-persona in `meta/personas.md` inflates credits; the money analogue is identical | Statement shows declared separately; underwriter discounts it |
| CSV format unrecognized (every bank differs) | `[PENDING — /ideate-discover Step 5 deepening]` — column-mapping UI vs per-bank parsers is unresolved | Mapping step |
| Import of pre-signup history | Allowed, always `declared`; cannot be verified retroactively — the platform was not in the room. This is the root cause from problem-statement.md restated as a money problem | Clearly marked historical/declared |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Loading | File parsing | Progress with row count |
| Empty | No imports yet | Explanation of what belongs here (the money WeJammin cannot see) with both entry paths: file and single row |
| Populated | Rows imported | List grouped by import batch, with tier badges |
| Error | Parse failed / unmappable columns | Row-level errors — never reject a whole file for one bad row |
| Partial | Some rows imported, some awaiting duplicate adjudication | Explicit pending-review count blocking "final" downstream exports (23.02.03) |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | Import should aim for maximum coverage — get every penny in | Naive product instinct: completeness = value | ❌ REJECTED: coverage and credibility trade off directly. A ledger of unverifiable self-assertions is exactly the industry failure the platform exists to escape — problem-statement.md's root cause is *asking people to remember*, and an import form is asking people to remember. Coverage is worth having only if segregated. |
| DT-02 | A domain expert (an underwriter) would expect **verified and declared to never be summed** | An advance underwriter or a mortgage assessor discounts self-certified income to near zero. If the two are merged into one total, the whole artefact is discounted rather than just the declared portion — so merging destroys the value of the verified half too. | ✅ CONFIRMED: drove D-03 on the parent index. Two totals, always. |
| DT-03 | Duplicate collision with platform events is a rare edge case | Optimistic framing | ❌ REJECTED: it is the **normal case**. Anyone with both platform income and a bank feed will double-count by default — and the doubled figure flows into the tax pack, overstating income to a tax authority, and into a proof-of-earnings artefact, overstating it to an underwriter. That is the highest-consequence failure mode in the sub-domain, not an edge case. |

## Cross-Cut Notes

- Feeds **23.01.01 Income Event Ledger** — same store, lower tier (see `23.01-income-aggregation-financial-identity-cx.md#CX-04`).
- Constrains **23.01.04 Verified Income Statement** — see `#CX-01`. This is the sub-domain's central tension.
- Touches **23.06 Advances, Commission & Recoupment** — imported "income" that is actually an advance is a liability; misclassification corrupts the recoupment ledger.
- Touches **24 Trust, Safety & Disputes** — systematic income inflation is a fraud signal, not just a data-quality one.
- Depends on the **Representation & Delegated Access** cross-cut — an accountant importing on a client's behalf is the expected workflow, not an edge case.

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | Imported income is always `declared`; users cannot self-promote to `verified` | See DT-02. Self-promotion would make the tier meaningless |
| D-02 | Duplicate detection proposes, never auto-merges | A wrong auto-merge silently deletes real income — worse than a duplicate the user can see |
