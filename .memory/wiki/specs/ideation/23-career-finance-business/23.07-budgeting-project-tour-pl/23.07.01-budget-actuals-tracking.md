# Feature: Budget & Actuals Tracking

> **Number**: 23.07.01
> **Parent**: [Budgeting & Project/Tour P&L](./23.07-budgeting-project-tour-pl-index.md)
> **Status**: [SURFACE]
> **Last updated**: 2026-07-16

## Overview

Set what a tour or a record is supposed to cost, then watch what it actually costs while there is still time to do something about it. The platform's advantage is that most of the costs already flow through it — rehearsal rooms (16), session fees (05), gear (13), plugins (14), production and promo (12, 21) — so actuals accrue on their own rather than depending on someone keeping receipts in a glovebox for six weeks.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Full | For a self-managed act, both halves of this currently do not exist: the budget is a rough number someone said in a pub, the actuals are receipts nobody collected. Sees costs accruing against the plan while the tour is still running. |
| Producer | Full | A recording budget is real, contractual and often **recoupable** (23.06.03) — overspending it has consequences the Musician's rough plan does not. They are also the party who commits most of the spend. |
| Operator | Full | Budgets a show or a room refit. Real but generic small-business budgeting — their meaningful unit is the event (17), not the tour. |
| Fan | None | Not visible — no projects, no professional stake. |

## Behavior

A budget is a set of expected lines scoped to a **project object** (a tour, a record). Actuals are the same expense (23.02.01) and income (23.01.01) rows the platform already holds, tagged with that project. Nothing is captured twice — if a row has no project tag it is invisible here, which makes tagging-at-capture load-bearing (`#CX-01`).

### Happy Path

1. Band plans a 12-date tour; budget lines: van, fuel, accommodation, crew, backline, per-diems.
2. Tour object exists (probably owned by 18 — see parent Q-02); the budget attaches to it.
3. During the tour, costs land tagged to it — rehearsal room booked through 16, van hire captured on a phone at a service station (23.02.01 DT-03).
4. In Leeds the accommodation line is already 40% over; they see it with six dates left, when they can still change hotels.
5. The tour ends; the same rows become its P&L (23.07.02) with nothing new to enter.

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Costs are not tagged to the project | Invisible to budget, actuals and P&L alike — the whole sub-domain silently produces a wrong answer from a missing tag | Tagging must be near-automatic (a tour date implies the tour) or this fails quietly, which is the worst way to fail |
| A member pays personally | A debt of the entity to the member, ranking before profit (`#CX-03`) — not just a cost | Claim recorded, not merely an expense row |
| Budget was never set | Extremely common. Actuals still accrue and are still useful | Actuals-only mode must be first-class; demanding a budget first would lose everyone at step one |
| Shared costs across projects (a van hired for two tours, a laptop) | Apportionment, same problem as 23.02.01's mixed-use | Split across projects; the same rule engine |
| Income lands months after the tour (a settlement, a merch reconciliation) | The P&L cannot close cleanly; distribution (23.07.03) may already have happened | Late income re-opens a closed P&L — the sub-domain's nastiest transition |
| Currency varies across a European tour | 23.01.03's FX policy applies; the budget is in one currency, the spend in four | Native + projection; the FX movement is a real tour cost, not an artefact |
| The tour loses money | The common case, and the one nobody models | Must not be a failure state in the UI. Most tours lose money; a red screen is not information |
| Per-diems paid in cash | Invisible to the platform | Manual, `declared` — the same coverage-vs-credibility trade as 23.01.02 |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Loading | Aggregating | Skeleton |
| Empty | No project or no rows | Explains what a project scope buys; offers actuals-only |
| Populated | Rows tagged | Budget vs actuals by line, with variance |
| Error | Aggregation failed | No variance rather than a wrong one |
| Partial | Some costs untagged / off-platform | Explicit "based on tagged activity" — the honest coverage statement this whole domain keeps needing |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | This is budgeting software scoped to a tour | The obvious framing | ❌ REJECTED: budgeting software requires discipline nobody on a tour has at 2am. The platform's actual advantage is that **the actuals accrue whether or not anyone is being disciplined** — because the rehearsal room, the session fee and the plugin were bought here. That inverts the product: it is not a budgeting tool that needs feeding, it is a spend feed that a budget can optionally be laid over. Which is why actuals-only must be first-class. |
| DT-02 | A domain expert would expect the **project tag to be the whole ballgame**, and to be the thing that silently fails | Anyone who has run a tour: the costs are real, they happen, and they are attributed to the tour only if someone remembers to say so. An untagged cost is not a small error — it is invisible to the budget, the P&L and the distribution, and it makes the tour look more profitable than it was. Since the distribution (23.07.03) pays out on that number, a missing tag transfers money between band members. | ✅ CONFIRMED: tagging must be **derived wherever possible** — a cost incurred on a tour date, at a tour venue, by a tour member, is a tour cost by inference, not by someone's memory. This is the same "capture as a byproduct, never as admin" principle the Producer's persona demands for credits, applied to money. Where inference fails, the untagged rows must be surfaced for sweeping, not left silent. |
| DT-03 | The budget is the primary artefact; the P&L is what it becomes | Sequencing assumption inherited from the feature's name | ⏳ PARTIALLY CONFIRMED: for a Producer with a contractual recording budget, yes — the budget is a real document with legal weight. For the Musician persona (the structural centre), **no**: they have no budget, they have never had a budget, and they will not make one before a tour. Designing budget-first fits the minority persona. The honest design is actuals-first with an optional budget overlay — which also matches the domain's `important` rather than `core` priority and argues this feature is `could`. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | Actuals-first; the budget is an optional overlay | See DT-01 and DT-03 — budget-first fits the minority persona |
| D-02 | Project tagging is derived by inference wherever possible; untagged rows are surfaced, never silent | See DT-02 — a missing tag moves money between band members |
| D-03 | One set of rows, two views; the P&L is not a copy | `#CX-01` — two data sets would guarantee disagreement |
