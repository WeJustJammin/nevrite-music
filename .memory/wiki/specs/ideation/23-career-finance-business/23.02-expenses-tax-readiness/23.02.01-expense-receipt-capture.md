# Feature: Expense & Receipt Capture

> **Number**: 23.02.01
> **Parent**: [Expenses & Tax Readiness](./23.02-expenses-tax-readiness-index.md)
> **Status**: [PARTIAL]
> **Last updated**: 2026-07-23

## Overview

Capture what went out: a receipt photographed at a service station at 1am, a string set, a rehearsal room, a train to a session, a plugin bought through WeJammin itself. The platform's advantage is that a large share of a musician's spend **already happens here** — gear (13), plugins (14), rehearsal rooms (16), session fees paid to contributors (05) — so those rows should never need capturing at all. The feature's real job is the remainder, and to attach spend to the *work* that caused it.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Full | The messiest spend in the product: mileage to a gig, strings, a rehearsal room, a laptop that is 60% work and 40% Netflix. Captures on a phone at a service station, not at a desk — the capture flow is mobile-shaped whether or not a mobile surface exists (`meta/constraints.md` flags this as open). Attaches spend to a tour or a project so 23.07 can compute a real P&L. |
| Producer | Full | Fewer, larger items: outboard, plugins, a hard drive, a room hire, and — importantly — **contributor fees they paid out**, which are their largest deductible and are already platform-native. Capital-vs-expense treatment matters more for them because the amounts cross thresholds. |
| Operator | Full | Rent, PRS/PPL-class licences, staff, backline repair, bar stock. Real and large, but their existing accountant owns the categorization — WeJammin is a feed. Capture is useful; the tax treatment is not this product's job (D-02 on the parent index). |
| Fan | None | Not visible. A fan buying a ticket or merch has a purchase, not an expense — consumer purchase history lives in 19/13/20, not here. Explicit absence: never surface an expense UI to a Fan-context user. |

## Behavior

Expense rows are created three ways: **automatically** from platform purchases (the strongest path — zero effort, perfect evidence), by **file/photo capture** with extraction, or **manually**. Every row carries amount, native currency, date, category (from 23.02.02's jurisdiction vocabulary), evidence, and an optional link to a project/tour.

### Happy Path

1. Musician buys a £320 pedal through WeJammin's gear marketplace (13).
2. An expense row is created automatically: amount, date, vendor, evidence = the platform order itself, category suggested as equipment.
3. It appears in their expense list already categorized and already evidenced — the receipt problem does not exist for this row.
4. Musician links it to no project (general equipment) and moves on.
5. It flows into the tax pack (23.02.03) and, if capital treatment applies, into the asset position rather than the year's costs.

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Purchase is **partly** business (a laptop used 60% for work) | Apportionment percentage on the row; jurisdiction rules constrain what is defensible | Apportionment field with the rule's guidance, not a free-text guess |
| Item is **capital**, not an expense (a £3k guitar) | Must not be expensed in-year; belongs to the asset position with depreciation/capital allowances | Different treatment, surfaced at capture, not discovered by an accountant in January |
| Mileage / per diem | Not a receipt at all — a rate × quantity claim, jurisdiction-specific | Distinct entry path; there is no receipt to photograph |
| Receipt photographed but never categorized | Row is `uncategorized` — a real state, not an error. It is a photo, not a deduction (`#CX-02`) | Counted and surfaced as a pack blocker |
| Expense paid in EUR on tour | Native currency retained; converts via 23.01.03's policy | Native + projection |
| The same spend captured manually **and** auto-created from a platform purchase | Duplicate — the same collision as 23.01.02's, on the outgoing side | Merge proposed, never auto-merged |
| Cash spend with no receipt at all | Allowed, but evidence-less; weaker under audit | Marked as evidence-less; the pack is honest about it |
| Expense belongs to a **Band entity**, not the person | Band expense, band P&L (23.07.03) — must not reduce personal taxable profit | Entity context explicit at capture |
| Receipt extraction misreads the amount | Extraction is a suggestion, never a commitment (D-02). Each extracted field carries a confidence signal; low-confidence fields are flagged for review, and no row is deduction-eligible until the user confirms it (`#CX-02`). The exact confidence thresholds and per-field validation rules are `[PENDING — 23.02.02 category rules / /write-be-spec]` | Extracted values always editable; questionable fields visibly marked "check this", not silently trusted |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Loading | Extraction running | Row created immediately with the image; fields fill in after — never block the capture on the parsing |
| Empty | No expenses yet | Explanation that platform purchases arrive automatically, plus manual/photo paths |
| Populated | Rows exist | List with category and evidence badges; uncategorized surfaced, not buried |
| Error | Extraction failed | Row survives with the image attached; manual entry offered. **Never lose the receipt because parsing failed** |
| Partial | Rows uncategorized or evidence-less | Explicit counts, feeding the pack's blocker list |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | This is a receipt-scanning feature and its quality is extraction quality | Obvious framing — every expense app is an OCR app | ❌ REJECTED: the platform's actual advantage is that **the best rows need no capture**. Gear (13), plugins (14), rehearsal rooms (16) and contributor fees (05) are already platform transactions with perfect evidence. Competing on OCR against Dext/Expensify is a losing fight on a commodity; auto-creating the rows nobody else can see is the differentiated half. Extraction is table stakes for the remainder, not the feature's identity. |
| DT-02 | A domain expert would expect **capital vs expense** to be handled at capture, not discovered later | Any accountant: a £3k guitar is not a cost, it is an asset — and musicians buy assets constantly, which is unusual for a sole trader. Getting this wrong overstates the year's costs, understates profit, and produces a return that is wrong in the user's favour (the dangerous direction). Also: it collides with 15 Gear Registry, which already tracks owned instruments and their value. | ✅ CONFIRMED: capital treatment is a first-class path, surfaced at capture. Strong argument that 15 Gear Registry and the asset position are the same data seen twice — recorded as Q-02. |
| DT-03 | Expense capture is desk work | Convenience assumption inherited from business software | ❌ REJECTED: it is a **service-station-at-1am** activity, exactly like the Operator's "phone at a loading dock" constraint in `meta/personas.md`. If capture requires a browser at a desk it will not happen, and everything downstream (the pack, the P&L) is built on rows that were never created. This sharpens the open mobile-surface question in `meta/constraints.md` from a fan-alerts argument (D-13) into a professional-workflow one. |
