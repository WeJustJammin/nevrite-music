# Feature: Provenance & Session-History Display

> **Number**: 13.03.06
> **Parent**: [Listings & Inventory](./13.03-listings-inventory-index.md)
> **Status**: [PARTIAL] — **Deep Think addition** (not in the sweep's candidate list)
> **Last updated**: 2026-07-17

## Overview

Rendering, on a gear listing, what this specific instrument has *done*: the records it played on, the sessions it appeared in, the chain of people who owned it. "This 1972 Telecaster appears on eleven credited releases" is a price-relevant fact that no gear marketplace on earth can display, because displaying it requires simultaneously owning a credit graph, a serial-keyed instrument registry, and the listing. WeJammin owns all three.

**Why this exists as a node**: the sweep's 28 candidates describe a very good gear marketplace and contain **nothing that Reverb could not build**. This is the one listing feature that is structurally impossible for a point solution — and per the thesis (D-18), the whole reason this domain is inside this platform rather than beside it.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Config | As seller: chooses whether to surface their own credits attached to this unit ("played on my 2019 album"), which is both a value-add and a privacy decision. As buyer: reads the instrument's history — the emotional core of buying used gear. |
| Producer | Config | **The source of this data.** Their sessions (via domain 02) are what create the link between a serial and a release. Consents to whether a session's gear usage is publicly attributable — a session may be under NDA, or the artist may not want their gear known. |
| Operator | Read-only | Sees provenance on gear they're buying; a studio's asset register (domain 15) accrues this history, which is itself a marketing asset ("tracked on these records in this room"). |
| Fan | Read-only | The persona most *moved* by this and least able to verify it. "This guitar played on that record" is precisely the claim a Fan will pay a premium for and cannot check — which is exactly why it must be a verified link, never a seller claim. See DT-02. |

## Behavior

The display reads the join between a **registered unit** (domain 15, serial-keyed) and the **credit graph** (domain 02, keyed by session/release). It renders only **verified** links — a credit recorded at session time by a Producer, against a unit that was registered — and clearly distinguishes them from any seller-asserted history. Consent-gated at both ends.

### Happy Path

1. Seller lists a unit registered in domain 15 with a serial
2. System looks up credited sessions where that unit was recorded as used
3. Verified links (consented, session-captured) render on the listing: "Appears on 11 credited releases"
4. Buyer expands to see releases, roles and dates, each linking to the credit record
5. The unit sells; the history travels to the new owner and keeps accruing

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Unit not registered / no serial | No provenance derivable — most listings at launch | Section absent. **No "no history found"** — that would imply absence of history rather than absence of data |
| Seller claims history the graph doesn't support ("Hendrix owned this") | Seller claims live in the description as claims, never in this panel | Verified panel and seller prose are visually distinct — the whole point |
| Producer/artist hasn't consented to gear attribution | Link exists but is not renderable | Section shows only consented links; count reflects consented only. See Q-01. |
| Credit graph is thin (launch reality) | Feature is inert for most listings | Honest silence. This is why it's a `should`, not a `must` — it cannot carry launch |
| A famous artist's gear becomes identifiable/targetable | Real-world theft risk from publishing "this person owns this valuable instrument" | Consent gating is a **safety** control, not just privacy. See DT-02. |
| Unit was modified since the session (13.02.03) | Provenance is keyed to unit identity (serial), not configuration — the appearance is still factually true, so the link renders. If mod history (13.02.03) records a modification dated *after* a credited session, the expanded link surfaces a neutral "modified since this session" flag. See DT-03. | "Appears on 11 credited releases"; expanded row shows the release + a factual "modified since this session (refret, 2023)" note. Never a judgment ("no longer original") — the buyer draws the conclusion |
| Session was under NDA | Must not leak via gear provenance | Consent at the session level governs; absence must be indistinguishable from no-data |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Loading | Listing render | Panel loads async — never blocks the listing |
| Empty | No registered unit or no links | Section omitted entirely, not "0 records" |
| Populated | Verified links exist | "Appears on N credited releases" + expandable list |
| Error | Graph lookup fails | Section omitted; never an error on a commerce page |
| Partial | Some links consented, some not | Consented links only; **no "N hidden"** — that leaks the existence of hidden links |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | The 28 swept candidates are sufficient for this domain | The sweep was exhaustive (14 lenses, 1,545 concepts) and ratified in D-16 | ❌ REJECTED: the candidate list is a complete description of **Reverb**. Every item on it — catalog, condition, offers, freight, price guide — exists at a competitor today. Under D-18 (provenance is the wedge; consolidation is the platform), a domain containing only copyable features is pure consolidation with nothing that compounds, which the problem statement explicitly names as a failure mode ("consolidation alone is copyable... nothing compounds"). The gear domain's provenance contribution was **entirely absent** from the sweep. This node and 13.06.05 are that contribution. |
| DT-02 | Displaying instrument provenance is straightforwardly good — more information, better prices | It's the obvious framing, and it's the reason to build it | ⚠️ CONFIRMED WITH CONSTRAINT: it is good **only if verified and consented**. Unverified, it is a fabrication engine — "played on Abbey Road" is a claim that adds five figures to a price and cannot be disproved, and a platform panel lends it institutional credibility a seller's prose never would. The Fan persona is the mark. And consent is a **physical safety** matter, not a preference: publishing that a named person owns a $40k instrument, in a domain where the personas doc calls van and venue theft endemic, is targeting information. **Verification and consent are load-bearing, not polish.** |
| DT-03 | A unit modified since a credited session breaks the provenance claim — the guitar that played the record no longer exists in that form, so the link is misleading (resolves Q-03) | The naive fix is to suppress or asterisk provenance on any modified unit; the modding domain (13.02.03) exists precisely because gear changes over time | ❌ REJECTED (suppression) / ✅ RESOLVED as neutral-flag: provenance is keyed to **unit identity (serial)**, not configuration. The unit *did* play on the record — that is a fact modification does not undo, and suppressing it would be the platform asserting a falsehood by omission. The correct behavior is to render the verified link AND surface any 13.02.03 modification dated after the session as a **neutral, factual flag** ("modified since this session — refret, 2023"), never a valuation judgment. This preserves the D-01 verified-only integrity while giving the buyer the one datum that changes what the provenance is worth to them. Configuration-level provenance ("the exact pickups that made that sound") is a deeper axis deferred to `/write-be-spec` — the mod-history join grain is not yet specified. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | Only verified, session-captured links render in the provenance panel | Per DT-02 — an unverified panel is a fraud amplifier with a platform's credibility attached. |
| D-02 | Absent data renders as nothing, never as "no history found" | Absence of data must be indistinguishable from absence of history, or the panel implies a negative it cannot support. |
| D-03 | Consent is required at both the session and owner ends | Per DT-02 — this is a safety control (theft targeting), not only a privacy preference. |
| D-04 | Hidden (non-consented) links are not counted or hinted | "3 hidden credits" leaks exactly what consent was withheld to protect. |
