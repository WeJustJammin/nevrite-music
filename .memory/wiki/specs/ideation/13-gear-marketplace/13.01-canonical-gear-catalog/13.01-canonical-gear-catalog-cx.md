## Cross-Cut Details

### CX-01: Matching ↔ Contribution

**Relationship**: Matching runs on every listing draft. Zero candidates routes the seller into contribution inline; contribution returns a `provisional` model; matching binds the draft to it and the listing publishes without waiting for moderation. This is the loop that lets the catalog grow from the long tail without ever stalling a listing.

**Role scoping**:
- **Musician**: hits this loop on boutique pedals and vintage one-offs; experiences it as a two-field detour, not a gate.
- **Producer**: hits it most often — studio outboard is the thinnest part of any gear catalog.
- **Operator**: hits it at volume during bulk import, where inline prompting does not scale (13.01.04 Q-03 — unresolved).
- **Fan**: never sees it. No listing surface.

**Synthesis questions answered**:
1. **Shared state conflict**: Contribution owns the model record; matching owns the binding. If moderation later merges the provisional into an existing model, the binding re-points — the listing does not break, but its comp set changes underneath it (13.01.04 Q-02).
2. **Trigger chain**: Match failure → contribution (sync, inline). Contribution → provisional publish (immediate) → moderation (async). If moderation rejects, the listing must not vanish — fallback is unmatched-published. `[PENDING — Step 5]`: exact rejection behaviour.
3. **Permission intersection**: Yes — Fan cannot contribute (13.01.02 D-03), and Fan cannot list, so the loop is coherently closed. Moderator standing is category-scoped and earned, so contributing does not confer review rights.
4. **Notification fan-out**: Moderation decisions notify the contributor (CX-M07). Whether they notify *other sellers* whose listings re-pointed is open (13.01.04 Q-02).
5. **State transition conflict**: Two sellers contributing the same missing model concurrently → duplicate provisionals. Dedupe (CX-M17) must catch it at moderation; both listings then re-point to the survivor.

### CX-02: Serial Decoding ↔ Matching

**Relationship**: Decoding produces a model + year hypothesis from a serial; matching consumes it as a ranking signal. This is the only signal that distinguishes a 1962 original from a 1999 reissue when the seller's text says "62 Jazzmaster" for both — the exact case 13.01.04 DT-02 excludes from auto-bind.

**Role scoping**:
- **Musician**: the seller who doesn't know what they inherited — decoding tells them, matching binds it.
- **Producer**: decodes outboard where the year *is* the product identity.
- **Operator**: batch-decodes at fleet intake.
- **Fan**: sees the decoded year as displayed provenance; no entry point.

**Synthesis questions answered**:
1. **Shared state conflict**: Neither owns the other's output. The record stores decoded fields and asserted fields distinctly (13.01.03 D-02), so a dispute can tell who claimed what.
2. **Trigger chain**: Serial entered → decode (sync, inline) → match re-ranks. Decode failure never blocks matching (13.01.03 D-03); matching falls back to text.
3. **Permission intersection**: None. Both are seller-side and identically scoped.
4. **Notification fan-out**: None inside this pair.
5. **State transition conflict**: Decode says 1972–74, seller asserts 1965, matching is asked to bind to a 1965 model. Contradiction is surfaced, not auto-resolved (13.01.03 Edge Cases). The bind follows the *seller's* choice — and the contradiction becomes dispute evidence.

### CX-03: Contribution ↔ Model Records

**Relationship**: The write path into the spine. Contribution creates; moderation merges, unmerges and edits. Every consumer downstream (comps, facets, alerts, registry) reads the result and has no way to detect corruption.

**Role scoping**:
- **All personas** are affected *silently* — this is the defining property. Nobody sees a bad merge; they see a price guide that is subtly wrong.
- **Musician/Producer/Operator**: can contribute; can earn category-scoped review rights.
- **Fan**: no access, by design (13.01.02 D-03).

**Synthesis questions answered**:
1. **Shared state conflict**: Model records are the shared entity. Merge is the conflict operation and it **must be reversible with an audit trail** (13.01.02 Edge Cases) — an irreversible merge is unrecoverable corruption.
2. **Trigger chain**: Contribution → provisional → moderation → canonical | merged | rejected. A merge triggers re-pointing of every bound listing and every registry entry (domain 15) — a fan-out with no natural bound.
3. **Permission intersection**: Category-scoped moderator standing gates the merge operation. Whether that standing reuses CX-M08's reputation substrate is open (13.01.02 Q-02).
4. **Notification fan-out**: Contributor is notified. Downstream listing owners affected by a merge: open (13.01.04 Q-02).
5. **State transition conflict**: A merge landing while a listing is mid-checkout re-points the comp set under a live transaction. Low frequency, high confusion. `[PENDING — Step 5]`.

### CX-04: Model Records ↔ Fitment & Voltage

**Relationship**: Warnings are pure derivations from the per-category attribute schema. If the schema lacks a voltage/market attribute for a category, the warning is not merely missing — it is *underivable*, and nobody knows it should have been there.

**Role scoping**:
- **Fan**: most exposed. Least likely to know voltage is a question; most likely to be harmed by silence.
- **Musician/Producer/Operator**: likelier to catch a missing warning themselves from the spec.

**Synthesis questions answered**:
1. **Shared state conflict**: None — one-way read.
2. **Trigger chain**: Listing/checkout render → derive → warn. Fitment fails silent; voltage fails loud (13.01.05 D-02).
3. **Permission intersection**: None.
4. **Notification fan-out**: None — warnings are render-time, not event-driven.
5. **State transition conflict**: An attribute schema change (adding `voltage` to a category) retroactively makes warnings derivable for existing listings. Backfill behaviour `[PENDING — Step 5]`.

### CX-05: Contribution ↔ Fitment & Voltage

**Relationship**: The dangerous seam. Contribution is open to any non-Fan persona; voltage attributes are a safety input. A contributor who leaves `voltage` blank — or wrong — silently disables a warning that would have prevented a destroyed amp. Medium confidence because the frequency is unknown, but the severity is not in doubt.

**Role scoping**:
- **Fan**: bears the harm without any access to the mechanism that caused it.
- **Musician/Producer/Operator**: cause it, usually accidentally, while doing the platform a favour.

**Synthesis questions deferred** — Medium confidence. Step 5 must resolve whether safety-relevant attributes (voltage, market) require moderation before a model leaves `provisional`, which would partially contradict 13.01.02 D-01 (provisional-publish, never blocking). **This is a real conflict between two confirmed decisions and needs the owner.**
