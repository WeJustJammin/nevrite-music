# Feature: Serial Number Decoding & Dating

> **Number**: 13.01.03
> **Parent**: [Canonical Gear Catalog](./13.01-canonical-gear-catalog-index.md)
> **Status**: [SURFACE]
> **Last updated**: 2026-07-16

## Overview

Given a serial number, tell the user what the instrument probably is and when it was probably made. Every major manufacturer runs its own serial scheme — and has changed it repeatedly, inconsistently, and sometimes reused numbers across factories. Decoding turns a string stamped on a headstock into a model + year hypothesis, which is what makes a listing accurate, a registry entry real, and a comp set correct.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Full | Types the serial off their guitar while listing or registering it; gets a decoded make/model/year with a confidence indication; accepts or overrides. The common case for a seller who inherited or bought used and doesn't know what they have. |
| Producer | Full | Decodes serials on studio outboard and mics — where a year materially changes what the unit *is* (a pre-1970 unit vs a later revision is a different-sounding device, not just an older one). |
| Operator | Full | Decodes serials when building an asset register for a studio or backline fleet; batch-decodes at intake. |
| Fan | Read-only | Sees a decoded year on a listing as displayed provenance. No decode entry point — the persona has no serial to type and no listing to make. |

## Behavior

Decoding is a **hypothesis generator, never an authority**. It returns a decoded result with an explicit confidence and the scheme it matched, and the UI must never present a decode as a verified fact. The output pre-fills a listing or registry entry; the user confirms or overrides, and the record retains which fields were decoded vs asserted.

### Happy Path

1. User enters a serial during listing creation or gear registration
2. System matches the serial against known manufacturer schemes
3. System returns: probable model/variant, probable year (or range), the scheme matched, and a confidence
4. User accepts (fields pre-fill) or overrides with what they know
5. Record stores both the decode and the user's assertion, distinctly

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Serial matches multiple schemes / ambiguous era | Return all candidates with ranges rather than picking one | "Could be 1962–1964 (scheme A) or 1978 (scheme B)" — user disambiguates |
| Manufacturer reused serials across factories | Decode returns a range plus a factory ambiguity note | Ambiguity surfaced, not hidden |
| Serial is fake, re-stamped, or from a counterfeit | Decoding cannot detect this — it is a scheme match, not an authentication | Explicit "decoded, not verified" labelling; escalation path to domain 24 |
| No scheme known for that manufacturer | Graceful null — no guess | "We don't know this maker's serial scheme yet" — contribution CTA |
| Serial belongs to a unit flagged stolen | **Not this feature's job** — screening is 13.03.07, which runs on the same input | Handled at listing gate, not decode |
| Decoded year contradicts the seller's listing claim | Surface the contradiction; do not auto-correct | "You listed 1965; the serial decodes to 1972–74. Which is right?" |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Loading | Serial submitted | Inline decode spinner |
| Empty | No serial entered | Optional field with "why this helps" affordance |
| Populated | Decode succeeded | Decoded model/year + confidence + scheme + "decoded, not verified" label |
| Error | Decode service unavailable | Field stays manual; never blocks listing or registration |
| Partial | Scheme matched but year ambiguous | Range shown with disambiguation picker |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | A decoded date can be presented as a fact | Naive UX instinct — a confident answer looks better than a hedged one | ❌ REJECTED: serial schemes are ambiguous, reused, and re-stamped. A decode presented as fact becomes a listing claim, and a wrong listing claim becomes a dispute in domain 24 with the platform's own UI as the evidence against it. **The confidence and the "decoded, not verified" label are load-bearing legal hygiene, not decoration.** |
| DT-02 | Decoding belongs in domain 15 (Gear Registry), since serials identify units | The registry owns serial-keyed identity, so the serial capability looks like its natural home | ❌ REJECTED: decoding maps serial → **model + year**, using per-manufacturer scheme data, which is *catalog* knowledge (13.01.01's spine). Domain 15 owns the *unit*; it consumes decoding as a service. Putting decoding in 15 would force catalog scheme data into the registry and split the catalog. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | Decode is a hypothesis with explicit confidence, never a verified fact | Per DT-01 — the label is legal hygiene. |
| D-02 | Decoded fields and user-asserted fields are stored distinctly | A dispute needs to know who claimed what. Feeds CX-M19. |
| D-03 | Decode never blocks listing or registration | Service degradation must not stall the listing flow. |
