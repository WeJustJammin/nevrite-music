# Feature: Rental Availability & Reservation

> **Number**: 13.10.02
> **Parent**: [Gear Rental & Backline Hire](./13.10-gear-rental-backline-index.md)
> **Status**: [SURFACE]
> **Last updated**: 2026-07-16

## Overview

Knowing whether the amp is free on Friday and locking it. Rental inventory is a calendar, not a count — the same unit is available, then isn't, then is again — and the reservation has to survive the gap between booking and collection, which may be months for a festival and hours for a session.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Full (both) | Books an amp for Friday's show. As a lender, sees when their gear is out and when it's home. |
| Producer | Full (both) | Books outboard for a tracking week. Needs the dates to be certain — a session is booked around it and everyone is paid to be there. |
| Operator | Full | Runs a fleet calendar, the persona's core competence (the persona doc: "their calendar is the business, and it lives in three incompatible places"). **This is the same pain, applied to gear instead of rooms** — which is the strongest argument that rental belongs with domain 16. |
| Fan | Read-only | Sees availability. No booking. |

## Behavior

Availability is CX-M05's mechanism (sub-domain D-01) applied to a physical unit or a pool. A reservation holds the unit for a date range; the hold has to include buffer for return, inspection and turnaround — a unit returned Monday isn't rentable Monday. Pooled inventory reserves *a* unit; specific inventory reserves *the* unit (13.10.01 DT-01).

### Happy Path

1. Renter picks dates
2. System checks the unit or pool for the range plus turnaround buffer
3. Available; renter reserves with a deposit (13.10.03)
4. Unit is blocked for the range
5. Collection or delivery on the day

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| **Unit doesn't come back on time** | Every downstream booking is now at risk, and someone's show needs that amp tonight | Cascade — the domain's sharpest rental failure. See DT-02. |
| Unit returns damaged and can't go out again | Same cascade, cause differs | 13.10.03 triggers it; forward bookings must be re-sourced |
| Turnaround buffer too short | Back-to-back bookings with no time to inspect | Buffer must be configurable and default conservative |
| Pooled reservation: which unit? | Assign late — at collection, not at booking | Maximises flexibility; incompatible with condition history per unit (13.10.03) |
| Booking months ahead for a festival | Long holds; the deposit sits for months | Same escrow strain as layaway (13.06.03 Q-03) |
| Renter cancels last minute | The slot is perishable — an unsold Friday is gone forever (the persona doc's exact phrase about Operators) | Cancellation terms mirror venue booking, because it's the same economics |
| Double-booked via another channel | Cross-channel again (13.03.03 DT-02), now on a calendar | Worse than a sale oversell — a show has no fallback |
| Unit sold mid-reservation (13.10.01 Q-02) | Forward bookings evaporate | Unresolved |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Loading | Availability check | Calendar loading |
| Empty | Nothing available in range | Alternatives, or "alert me" |
| Populated | Available | Calendar with rates |
| Error | Check fails | Manual enquiry — never a false "available" |
| Partial | Available for some dates | Partial range offered honestly |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | Rental reservation is 13.03.03's inventory claim with dates attached | Both prevent double-allocation of a physical unit, so they look like one mechanism with a parameter | ❌ REJECTED: a sale claim is **instantaneous and terminal** — one arbitration, the unit is gone, done. A rental reservation is a **range that must not overlap another range**, held for months, with turnaround buffers, cascading dependencies and a return that may not happen. The arbitration problem is scheduling, not locking — which is precisely why CX-M05 exists and serves venues, studios, lessons and services. **Rental's reservation has more in common with booking a rehearsal room (domain 16) than with buying an amp (13.03.03)**, and that is the clearest single piece of evidence for the promotion question (sub-domain Q-01). The mechanism this feature needs is already built for a different domain. |
| DT-02 | A late return is an inconvenience handled by a late fee | The standard rental answer; it's what every hire company's terms say | ❌ REJECTED: a late fee compensates the *lender* and does nothing for the **next renter, whose show is tonight**. Rental inventory is a dependency chain — one unit, sequential commitments, each with a fixed unmovable date. A single late return cascades through every downstream booking, and the persona doc is explicit that an Operator's failure mode is "a show that failed on a preventable technical mismatch". **The severity is categorically different from anything in the sales half of this domain**: a late sale delivery disappoints one buyer; a late rental return can cancel a show, and no fee fixes that. This demands proactive re-sourcing (find another unit for the next renter *before* they discover the problem), which is an operational capability, not a payments one — and nothing in domain 13 has that shape. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | Reservation uses CX-M05's scheduling, not 13.03.03's locking | Per DT-01 — different problem shape entirely. |
| D-02 | Turnaround buffer is configurable and defaults conservative | A unit returned Monday is not rentable Monday; ignoring that guarantees the DT-02 cascade. |
| D-03 | Pooled units are assigned at collection, not at booking | Maximises fleet flexibility — but conflicts with per-unit condition history (13.10.03). |
| D-04 | Late returns trigger proactive re-sourcing, not just a fee | Per DT-02 — a fee doesn't put an amp on a stage. |
