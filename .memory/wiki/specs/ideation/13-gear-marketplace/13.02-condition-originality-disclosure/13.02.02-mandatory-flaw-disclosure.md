# Feature: Mandatory Flaw Disclosure

> **Number**: 13.02.02
> **Parent**: [Condition, Originality & Disclosure](./13.02-condition-originality-disclosure-index.md)
> **Status**: [SURFACE]
> **Last updated**: 2026-07-16

## Overview

A structured, category-aware checklist of the specific defects that matter for this kind of gear, which the seller must complete before publishing. Not a free-text "anything else?" box — an enumerated set: neck cracks and headstock repairs for guitars, tube socket and transformer condition for amps, keybed and edge-chip status for cymbals. It exists because "not as described" is the most common gear dispute, and almost all of it is preventable by asking the right question at listing time.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Full (as seller) | Works through a short category-specific flaw checklist while listing. As a buyer, reads the disclosed flaw set as structured data rather than hunting for "some wear" buried in paragraph four. |
| Producer | Full (as seller) | Discloses functional flaws on outboard — noisy pots, drifting calibration, failed channels — which is where the real defects live in studio gear and where cosmetic checklists are useless. |
| Operator | Full (as seller) | Discloses road wear and repair history on ex-rental/backline stock at volume. Needs the checklist to be fast, or bulk listing (13.03.04) becomes unusable. |
| Fan | Read-only | Reads flaws as a buyer. The persona least able to interpret "hairline check in the finish" — plain-language explanations of each flaw's *consequence* matter more here than the flaw name. |

## Behavior

The flaw checklist is **derived from the bound catalog model's category** (13.01.01's per-category attribute schema is the precedent and likely the same mechanism). Each flaw is a structured item with presence, severity and — where material — a required photo. Disclosed flaws constrain the grade (13.02.01) and are pinned into the evidence pack (13.02.04).

### Happy Path

1. Seller reaches the disclosure step; system loads the checklist for that category
2. Seller marks each flaw present/absent, with severity where present
3. System requires a photo for material flaws (structural repairs, cracks)
4. System cross-checks the disclosed set against the chosen grade and challenges contradictions
5. Listing publishes with structured flaws rendered as a scannable list, not prose

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Listing is unmatched to a catalog model (13.01.04) | No category → **no checklist derivable**. A real cost of unmatched listings | Generic fallback checklist; prompt to link a model for a proper one |
| Seller marks "no flaws" on a 60-year-old instrument | Implausible but not impossible — do not block, but a mint-vintage claim raises the evidentiary bar | Soft challenge: "No flaws on a 1962 instrument is unusual — sure?" |
| Flaw exists but isn't on the checklist | Checklist can never be exhaustive; free-text supplements it | "Anything else?" free-text **in addition to**, never instead of, the enum |
| Seller omits a flaw that later surfaces | This is the dispute. Evidence pack (13.02.04) + disclosure record is what adjudicates it | Buyer opens a dispute in domain 24; disclosure record is the baseline |
| Category checklist is wrong/missing for a niche category | Fallback to generic; flag for catalog work | Generic checklist |
| Bulk listing 200 items | Per-item checklists at volume are brutal | `[PENDING — /ideate-discover Step 5 deepening]` — template/default-set behaviour for bulk is unresolved and could sink Operator adoption |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Loading | Category resolved | Checklist skeleton |
| Empty | No category (unmatched listing) | Generic fallback + "link a model" CTA |
| Populated | Checklist complete | Structured flaw list on the listing |
| Error | Checklist service down | Free-text fallback; never stall the listing |
| Partial | Some flaws marked, photos pending | "Photo required for: headstock repair" — publish blocked only on *material* flaw photos |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | A single generic flaw checklist works across all gear | Simplicity instinct | ❌ REJECTED: the same reasoning as 13.01.01 DT-01. "Fret wear" is meaningless on a microphone; "diaphragm condition" is meaningless on a cymbal. A generic checklist asks wrong questions, gets ignored, and therefore discloses nothing. Checklists must be category-derived. |
| DT-02 | Mandatory disclosure primarily protects the buyer | The obvious framing — it's a buyer-protection feature | ⚠️ REFRAMED (partially rejected): its **larger** value is protecting the *honest seller*. A seller who disclosed a repair via a structured field, with a photo, timestamped before sale, is immune to a later "it arrived damaged" claim — the evidence pack (13.02.04) proves the state at dispatch. Framed as buyer protection, sellers experience disclosure as friction and resist it. Framed as seller armour, they complete it willingly. **This reframe should drive the UX copy** — the same insight as the Producer persona's "make the lazy path the correct path". |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | Checklists are category-derived, never generic | Per DT-01. |
| D-02 | Structured enum + free-text supplement, never free-text alone | The enum is what disputes, comps and facets consume; prose serves the human. |
| D-03 | Material flaws require a photo before publish | The only publish-blocking rule in the listing flow — justified because a photographed repair is the cheapest dispute prevention available. |
| D-04 | UX framing is seller-protection, not buyer-protection | Per DT-02 — the framing determines whether it gets completed honestly. |
