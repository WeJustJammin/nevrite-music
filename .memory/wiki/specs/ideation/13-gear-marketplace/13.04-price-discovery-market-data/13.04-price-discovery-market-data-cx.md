## Cross-Cut Details

### CX-01: Confidence ↔ Price Guide

**Relationship**: The guide does not compute a number and then ask how sure it is — confidence decides whether the question is answerable. Above threshold the distribution renders; below it, raw comps appear as examples with no median; at zero, an honest refusal. The inversion matters: the median is the artifact that lies, so at low confidence the median must not exist rather than exist-with-a-caveat.

**Role scoping**:
- **Fan**: the reason for the inversion. Reads any number as a fact; will not read "(low confidence)". Gating is the only protection that works on this persona.
- **Producer**: lives below the threshold (13.04.03 DT-02 — rare outboard is permanently thin). Respects "we can't price this"; would lose trust in the whole surface after one bad number.
- **Musician**: straddles — Stratocasters are confident, a boutique fuzz is not.
- **Operator**: needs the confidence value itself for insurance schedules, where an unconfident valuation is a rejected claim.

**Synthesis questions answered**:
1. **Shared state conflict**: The comp bucket is the shared entity; both read, neither writes. No conflict — but both depend on bucket *integrity*, which 13.01.02 moderation can change underneath them (13.04.01 Edge Cases).
2. **Trigger chain**: Guide requested → assemble comps → compute confidence → gate → render. Confidence failure **fails closed** (13.04.03 D-03) — the domain's only fail-closed rule, and correct here because the alternative is an ungated number.
3. **Permission intersection**: None — all four personas are read-only on both.
4. **Notification fan-out**: None. Both are render-time.
5. **State transition conflict**: A model merge (13.01.02) recomputes buckets and can flip a bucket across the threshold in either direction — a model page that quoted a price yesterday may refuse today. Correct behaviour, confusing UX. `[PENDING — Step 5]`.

### CX-02: Price Guide ↔ Repricing

**Relationship**: The dangerous loop. The guide supplies evidence; repricing turns it into an anchor at the moment of pricing; accepted anchors become the next comps. The guide then measures its own output while its growing sample makes it *look* more authoritative. 13.04.02 D-01 (ranges with visible evidence, never a single number) is the mitigation, and it is a mitigation, not a fix.

**Role scoping**:
- **Musician**: most anchor-susceptible — sells rarely, no market feel, will take the suggestion.
- **Producer**: least affected; mostly below the confidence threshold, so no suggestion is offered.
- **Operator**: the auto-repricing persona; closes the loop *mechanically*, at fleet scale, with no human judgement in the path.
- **Fan**: not a seller. Affected only as a buyer of prices the loop produced.

**Synthesis questions answered**:
1. **Shared state conflict**: Sold listings are the shared entity. Repricing writes *asking* prices; only *sold* prices become comps — which is the loop's one natural brake. An anchored asking price that never sells never becomes evidence.
2. **Trigger chain**: Guide → suggestion → seller accepts → listing → sale → comp → guide. Closed, self-reinforcing, and the cycle time is a sale cycle (weeks to months), so it degrades slowly enough to be invisible until it isn't.
3. **Permission intersection**: Yes — Fan has None on repricing, so the loop is professional-only. Auto-repricing may be entitlement-gated (CX-M24), which would make the loop's tightness a function of who pays.
4. **Notification fan-out**: Stale-listing nudges (CX-M07) are themselves anchoring events at scale — a nudge to 500 sellers of the same model is a coordinated price signal.
5. **State transition conflict**: Two Operators auto-repricing against each other (13.04.02 DT-02). On qty=1 non-fungible units the race has no perfect substitute to converge on — structurally bounded. On counted stock (13.03.05) the goods *are* interchangeable and the bound disappears. **The fungible half of this domain is where the loop bites** (13.04.02 Q-02).

### CX-03: Confidence ↔ Repricing

**Relationship**: Confidence gates repricing exactly as it gates the guide — one mechanism, two consumers. Where the guide's refusal is a UX inconvenience, repricing's refusal is a *protection*: an auto-reprice driven by a two-comp bucket could move a real listing's real price against a fabricated market.

**Role scoping**:
- **Producer**: benefits most from the refusal — their gear is thin, and a suggestion here would be actively wrong.
- **Operator**: auto-repricing must halt in low-confidence buckets, which means a fleet reprice will legitimately skip a chunk of stock. That skip needs explaining or it reads as broken.
- **Musician**: sees "not enough data" instead of a number.
- **Fan**: no access.

**Synthesis questions answered**:
1. **Shared state conflict**: None — repricing reads the gate.
2. **Trigger chain**: Reprice attempt → confidence check → proceed or halt. Halt is silent-safe for suggestions; for **auto-repricing it must be reported**, since an unexplained skip on a fleet run looks like a failure.
3. **Permission intersection**: Repricing is seller-only, so this gate never faces the Fan — unlike CX-01, where the Fan is the whole point.
4. **Notification fan-out**: Auto-reprice halts should batch into the fleet run's report, not fire per-listing (CX-M07).
5. **State transition conflict**: A bucket crossing the threshold mid-run means an auto-reprice fleet job could act on some listings and skip others for the same model within one execution. `[PENDING — Step 5]` — likely needs the confidence snapshot pinned per run.
