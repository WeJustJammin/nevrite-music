# Feature: Work & Recording Identifier Issuance & Reconciliation

> **Number**: 09.06.01
> **Parent**: [Rights Evidence & Public Record](./09.06-rights-evidence-public-record-index.md)
> **Status**: [PARTIAL]
> **Last updated**: 2026-07-23

## Overview

The codes that let the rest of the industry refer to a piece of music unambiguously: **ISRC**
(a recording), **ISWC** (a composition), **UPC** (a release product), **GRid** (a digital release).
Without them, a work is a title and an artist name — and there are four songs called *Waiting Room* by
two bands called *The Colours*.

The feature is **issuance and reconciliation**, not issuance ([09.06 D-03](./09.06-rights-evidence-public-record-index.md)).
WeJammin can genuinely issue ISRCs and UPCs — obtain a registrant code and allocate. It **cannot issue
ISWCs**: those are allocated by a CISAC society when a work is registered, which is
[domain 10](../../10-royalties-collections/)'s surface. For ISWC the platform captures and reconciles a
code assigned elsewhere. Pretending otherwise would promise something undeliverable.

> **Boundary (inherited from the domain index)**: identifier scope is **works and recordings only**. IPI
> is an Interested **Party** identifier and belongs to [domain 01](../../01-identity-profiles-organizations/).

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Full | The owner. Gets an ISRC allocated without buying a registrant code or maintaining a spreadsheet — which is how independents do it today, and why so many recordings ship with a distributor's code the artist does not control. Sees every identifier on their catalogue in one place, and sees which works are missing an ISWC (i.e. not registered with a society, i.e. not collecting). |
| Producer | Config | Triggers allocation at the point a recording is fixed — they are the one who knows when it is final. Config rather than Full: they cause allocation, they do not own the resulting codes, which belong to the recording's owners. |
| Operator | None | Studios do not issue identifiers for other people's recordings. Explicit absence. |
| Fan | None | No access to issuance. Fans *consume* identifiers indirectly via the lookup ([09.06.04](./09.06.04-public-rights-lookup.md)), which resolves them without ever showing a code. |

## Behavior

| Code | Scope | WeJammin's role | Source |
|---|---|---|---|
| **ISRC** | One recording | **Issue** — allocate from a registrant code | Platform (if [09.06 Q-02](./09.06-rights-evidence-public-record-index.md) is yes) |
| **ISWC** | One composition | **Reconcile** — capture the code a society assigns | CISAC society, via [domain 10](../../10-royalties-collections/) |
| **UPC/EAN** | One release product | **Issue** — allocate from a GS1 prefix | Platform or distributor |
| **GRid** | One digital release | **Issue or reconcile** | Platform or distributor |

Allocation rules that are unforgiving: an ISRC is **permanent and never reused**. Every distinct
recording gets its own — a radio edit is a different recording from the album version and needs its own
code. Allocate one to the wrong object and the error propagates into every DSP, society and analytics
system that ever ingests it, and you cannot recall it.

**Reconciliation** is the harder half: a recording often arrives already carrying an ISRC (from a
distributor, a previous release, a label). The platform must capture the existing code rather than
allocate a second — two ISRCs on one recording splits its royalties into two streams that never
reconcile, which is precisely the black-box mechanic this domain exists to fight.

**Canonical resolution (Q-02 resolved).** When two ISRCs are found on one recording, the platform
**does not choose** — it surfaces the evidence and lets the recording's owners decide. The evidence
it presents, in priority order: (1) which code already has DSP/streaming history attached — changing
away from a code that DSPs reference orphans the accumulated stream counts and royalty history, so the
already-circulating code is the default recommendation; (2) which was allocated first; (3) which
registrant issued it. The owners (the rights holders on the work per
[09.01.01](../09.01-rights-registry/09.01.01-work-recording-duality.md)) confirm the canonical code;
the platform records the decision and marks the other as superseded-not-deleted (a permanent code is
never erased, only demoted). Where the conflicting code originates outside WeJammin — a distributor's
or society's allocation — canonicalisation is a **declaration WeJammin records, not an authority it
holds**; the platform's job is to make the conflict visible and the choice evidenced, not to arbitrate
it. Multi-owner recordings with no consensus route to dispute ([domain 24](../../24-trust-safety-disputes/)).

### Happy Path

1. Recording is fixed at session close ([09.01.01](../09.01-rights-registry/09.01.01-work-recording-duality.md)).
2. Platform asks whether it already has an ISRC.
3. It does not, so one is allocated from WeJammin's registrant code and permanently attached.
4. Work is registered with a society ([domain 10](../../10-royalties-collections/)); the society assigns an ISWC.
5. Platform reconciles the ISWC back onto the work.
6. Both codes appear on the work; the lookup can now resolve it by key rather than by guess (CX-01).

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Recording already has an ISRC | Captured, never re-allocated. | "Existing ISRC found — using it." Allocating a second is the error the feature exists to prevent. |
| Two ISRCs discovered on one recording | Real conflict; royalties are already splitting across two streams. Platform surfaces evidence (streaming history, allocation order, registrant) and the owners pick the canonical code; the other is superseded-not-deleted. No-consensus multi-owner cases route to dispute. | "Two ISRCs on this recording — choose the canonical one" with the code that already carries stream history recommended. Which is canonical is not the platform's call alone. |
| Radio edit vs album version | Different recordings → different ISRCs. | "New version — needs its own ISRC." A common and costly mistake. |
| Same recording on multiple releases | One ISRC, many UPCs. The mapping is one-to-many downward, never upward. | Shown as one recording across releases. |
| Allocated ISRC never used (session abandoned) | The code is spent. It must never be recycled. | Nothing user-facing; an operational fact with a permanent obligation attached. |
| ISWC never assigned (work not registered) | Work is not collecting publishing income. | "No ISWC — this work isn't registered with a society" + route to [domain 10](../../10-royalties-collections/). The absence is the actionable signal. |
| Platform ceases to exist with codes allocated | The codes remain in the wild forever, pointing at recordings. | The obligation behind [09.06 Q-02](./09.06-rights-evidence-public-record-index.md); see DT-03. |

| State | Trigger | What User Sees |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | WeJammin should **issue ISWCs** — the candidate list says "Work & Recording Identifier Issuance (ISRC/ISWC/UPC/GRid)", so all four are issuable | The sweep's own framing, taken at face value | ❌ REJECTED — ISWCs are allocated by CISAC societies when a work is registered. No platform can issue one; the authority does not exist to be claimed. WeJammin's real role is **reconciliation**: capture the code the society assigns and attach it. This matters beyond pedantry — a product that promised ISWC issuance would either fail visibly at the first attempt or (worse) mint fake codes that break every downstream system that trusts them. Hence the feature's rename ([09.06 D-03](./09.06-rights-evidence-public-record-index.md)). An honest boundary here is worth more than an impressive-sounding scope. |
| DT-02 | A domain expert would expect **reconciliation** to be the hard half, and the candidate list frames the feature as issuance | Allocating a code is trivial — a counter and a check digit. But recordings arrive from distributors, previous releases and labels **already carrying** ISRCs, and the failure mode is silent: allocate a second and the recording's royalties split into two streams that never reconcile, with each collector believing it has the whole picture. Nobody notices until a statement is short, which is years later, which is exactly the reconstruction failure D-18 targets. | ✅ CONFIRMED — reconciliation is the feature's centre of gravity, and detecting an existing code must precede any allocation. This also reframes what the feature is *for*: not "give my recording a number" but "make sure my recording has exactly one number", which is a different and much more valuable product. |
| DT-03 | Becoming an ISRC registrant is a cheap operational win — buy a code, allocate, done | It is genuinely cheap in money, and it turns WeJammin from a client into infrastructure | ⚠️ PARTIALLY CONFIRMED, with an obligation the candidate list never surfaces. Allocated ISRCs are **permanent and global**: they will sit in DSPs, societies and analytics systems for decades, pointing at recordings, long outliving any commercial decision made here. If WeJammin allocates codes and then pivots, is acquired, or shuts down, those codes do not stop existing — they become orphans whose registrant is unreachable, and the recordings they identify inherit a permanent ambiguity. Taking a registrant code is therefore a **perpetual commitment made by a solo-operated company** (`meta/constraints.md`), and the exit plan needs to exist before the first allocation, not after. Escalated to [09.06 Q-02](./09.06-rights-evidence-public-record-index.md). |
| DT-04 | On a two-ISRC conflict the platform should pick the canonical code automatically — it has the data (allocation dates, stream history) to know which is "right" | Automation is tempting: the platform can see which code DSPs already reference | ❌ REJECTED — canonicalising an identifier reassigns which stream of royalties a recording collects, which is an **ownership-consequential** act, not a data-cleanup one. The platform can *rank* the candidates (streaming history first, because switching away from a circulating code orphans real money), but the choice belongs to the recording's owners; where the rival code came from a distributor or society, the platform is recording a declaration, not exercising authority. Automating it would let WeJammin silently move someone's income between codes — exactly the invisible-reassignment harm the domain exists to prevent. The right product is **evidence + a recommendation + an owner confirmation**, with dissent routed to dispute. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | The platform **issues** ISRC/UPC/GRid and **reconciles** ISWC | ISWC allocation is a CISAC society's authority; claiming it would mint codes that break downstream systems (see DT-01). |
| D-02 | Detection of an existing identifier **precedes** any allocation | Two ISRCs on one recording splits royalties into streams that never reconcile — silent until a statement is short (see DT-02). |
| D-03 | Retry after a failed allocation **never** double-allocates | A duplicate code is worse than a failure; codes are permanent and unrecallable. |
| D-04 | Becoming a registrant is a **perpetual commitment** requiring an exit plan before first allocation | Allocated codes outlive the company; orphaned codes leave permanent ambiguity on real recordings (see DT-03). |
| D-05 | On a two-ISRC conflict the platform **ranks and recommends** (stream history → allocation order → registrant) but the **owners confirm** the canonical code; the other is superseded-not-deleted, no-consensus routes to dispute | Canonicalisation reassigns royalty streams — ownership-consequential, not automatable (see DT-04, resolves Q-02). |
