# Feature: Artist Profile Linking & Disambiguation

> **Number**: 12.03.04
> **Parent**: [DSP Store & Territory Management](./12.03-dsp-store-territory-management-index.md)
> **Status**: [PARTIAL]
> **Last updated**: 2026-07-17

## Overview

Making sure a release lands on the **right artist page**. Every DSP maintains its own artist
entity with its own ID (Spotify URI, Apple Music artist ID), and a delivery that does not name one
explicitly gets matched by name — which routinely attaches a release to a stranger who happens to
share the artist's name, or splinters an artist's catalog across three duplicate pages nobody can
merge without a support ticket.

This is the one place in distribution where the **first mistake is effectively permanent** and where
"delivered successfully" can be the exact opposite of success: a green board and zero streams,
because the work went to someone else's discography. For a platform whose thesis is that the record
it keeps is *true* (D-18), that is the completest possible failure — and it is invisible on every
dashboard unless this feature makes it visible.

> **Deep Think addition** — not in the sweep's candidate list. See DT-01.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Full | Links their WeJammin identity to their existing DSP artist pages once, and it holds for every subsequent release. On a first release, is told plainly that no page exists yet and one will be created — and that this is the moment that decides their page for the rest of their career. Sees which page each store matched, before delivery where possible and after where not. |
| Producer | Read-only | Sees which artist page a record they made was attached to. Read-only, but consequential: a producer with many credits notices a wrong-page match faster than anyone, because they see the pattern across releases. Also relevant to *their own* DSP producer/credit pages, which is arguably a second instance of this problem — see Q-02. |
| Operator | None | Not visible. |
| Fan | None | Not visible — but the **most affected persona by the failure**. A Fan following an artist gets nothing when a release lands on a duplicate page, because their follow is attached to the DSP entity, not the artist. The alert→attendance line personas.md describes as the Fan's success criterion breaks silently, and nobody can see that it broke. |

## Behavior

Each store has its own artist entity. A delivery either **names** the store's artist ID or lets
the store guess from a string. Guessing fails in predictable ways:

| Failure | Consequence |
|---|---|
| Name collides with an existing artist | Release lands on a stranger's page; their followers get it, yours do not |
| Name is slightly different from prior releases | A **duplicate page** is created; catalog and followers split |
| Featured artist unlinked | Feature does not appear on the featured artist's page — a real career cost for session and feature work |
| Band member's solo release matched to the band | Wrong discography |

The fix is to store per-store artist IDs on the WeJammin identity (01) and emit them in the ERN.
Once linked, it holds forever. The problem is the **first release** — no page exists yet, so there
is nothing to link, and whatever the store creates becomes the artist's permanent home. That is
the one irreversible-by-default moment in the domain.

**Recovery is expensive and outside the platform's control.** Merging duplicate DSP pages is a
support-ticket process at each store, measured in weeks, with no guarantee. Prevention is the only
real strategy — which makes this a pre-delivery concern that happens to be tracked post-delivery.

**Per-store linking mechanics (Level 1).** Stores fall into three tiers, and the platform's honesty
about which tier a store is in is itself the feature:

| Tier | Store behavior | What linking can promise |
|---|---|---|
| A — claimable + verifiable | Store offers a claim/auth flow (Spotify for Artists, Apple Music for Artists) that proves control of the page | The stored ID is **verified**; delivery targets it and hijack is not possible |
| B — addressable, not claimable | Store accepts an artist ID in the ERN but has no self-serve claim/verify path | The ID can be emitted and held, but ownership is **asserted, not proven** — see D-05 |
| C — no ID exposed | Store offers no artist-ID surface at all | Nothing to link; name-matching is the only lever and the platform says so plainly |

`[PENDING — /write-be-spec]` — the exhaustive per-store matrix (exact claim endpoints, OAuth scopes,
ID formats, and which live store sits in which tier) is integration detail, not ideation behavior.

### Happy Path

1. Before first delivery, the platform searches each store for existing pages matching the artist.
2. Musician confirms which are theirs, or states this is their first release.
3. Confirmed IDs are stored on the WeJammin identity (01) — not on the release.
4. Every delivery emits the store's artist ID; the store never guesses.
5. Featured artists on the release are linked the same way, using **their** stored IDs.
6. Post-delivery, the platform verifies the release landed on the linked page.

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| First release — no page exists anywhere | Store creates one from the delivery. **Irreversible by default** | "No Spotify page exists yet. This release creates it — check your name is exactly right, because this is permanent." |
| Name collides with an established artist | High risk of landing on a stranger's page | "There's already a Spotify artist called {name} with 40 releases. Is that you?" Blocking question, not a warning |
| Featured artist is not a WeJammin user | No stored ID to emit; the store guesses | "We can't link {feature} — they're not on WeJammin. Their feature may not show on their page." |
| Duplicate page created anyway | Catalog splits; recovery is per-store support | "Spotify made a second page. We've filed a merge request — this takes weeks." |
| Artist has legitimately different names in different contexts (personas.md multi-hyphenate) | **Multiple distinct artist pages by design**, not an error | Each identity/alias links its own set of store IDs |
| Store exposes no artist ID at all | Cannot link; name-matching is all there is | Honest: "{Store} doesn't let us link. We send your name and hope." |
| Release lands on the wrong page | Every status is `Live`; the board is green; the outcome is a disaster | The concrete instance of 12.03.02 DT-03 |
| Linking a **band/entity** identity (permission) | A single member tries to bind the band's Spotify page to the shared identity | Linking an entity identity (01) requires that identity's linking authority; a lone member cannot unilaterally bind it | "Linking {band}'s Spotify page needs a {band} admin — you can propose it, they confirm." |
| Two releases queued before the link is confirmed (concurrency) | First delivery creates the page; a second, near-simultaneous delivery name-matches and can spawn a duplicate | The blocking gate (D-02) holds **all** deliveries for an unlinked identity until first-release linking resolves — deliveries do not race | "Two releases are queued for an unlinked page. We're holding both until you confirm the page." |
| User links to a page they don't control (abuse / hijack) | Someone binds their identity to a famous namesake's real page to ride its followers, or to sever a rival | Linking is a **claim, not proof**; Tier-A links must be verified (D-05), Tier-B unverifiable links are flagged to Trust & Safety (24) and not used for delivery | "We can't verify you own this page. It won't be used for delivery until you claim it." |
| Linked page merged or deleted upstream (staleness) | A stored ID now points at a page the store has merged away or removed | Post-delivery verification (D-03) catches the dangling link before the next release rides it | "Your linked {store} page no longer exists — relink before your next release." |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Unlinked | No store IDs stored | Blocking prompt before first delivery |
| Searching | Looking for existing pages | "Checking for existing pages" |
| Candidates | Possible matches found | "Is this you?" per store, with page evidence (release count, art) |
| Linked | IDs confirmed and stored | Quiet; holds for every future release |
| First-release | No page exists | Explicit warning that this delivery creates the permanent page |
| Held | Deliveries queued against an unlinked identity | "Held until you confirm the page" — nothing races the first-release gate |
| Unverified | A Tier-A link was asserted but not claimed | "Claim this page to use it for delivery" — not emitted until verified |
| Mismatch | Post-delivery check found the wrong page | Alert + recovery path + honest timeline |
| Unlinkable | Store has no ID mechanism | Stated plainly, once |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | The candidate list is missing the most common real distribution disaster | Domain expertise: "my album went to the wrong artist page" and "I have two Spotify pages" are the most-reported artist-facing distribution failures. The sweep's 8 candidates cover message, status, schedule, takedown, Content ID and identifiers — **none covers artist entity resolution** | ✅ CONFIRMED — added as a child. The omission is instructive: the sweep enumerated the *distributor's* machinery (what a distributor does) rather than the *artist's* failures (what goes wrong). A domain built only from the candidate list would deliver flawlessly to the wrong person and report total success. This is also the strongest argument in domain 12 for Deep Think as a step: no amount of drilling into the given candidates would have surfaced it. |
| DT-02 | Store artist IDs belong on the release object | They are used in the ERN, and the ERN is built from the release | ❌ REJECTED — they are properties of the **identity** (01), not of a release. Per-release storage means re-linking every time, which reintroduces the failure on every release, and it cannot express the multi-hyphenate case from personas.md, where one human legitimately holds several artist identities each with its own store pages. Identity owns the links; releases read them. This also makes featured-artist linking work for free, since the feature's IDs live on *their* identity — a small structural payoff from the consolidation thesis. |
| DT-03 | Wrong-page matching is a distribution nuisance | Its natural framing — it is a metadata mismatch, and the release is technically live | ❌ REJECTED — it silently breaks **domain 20 (Fanbase)** and the Fan persona's entire success criterion. A Fan's follow attaches to the *DSP's* artist entity; a release on a duplicate page reaches none of them. The artist sees green status and zero streams and blames the algorithm. Neither party can see the cause. For a platform whose thesis is that the record it keeps is *true* (D-18), delivering an artist's work to a stranger's discography and reporting success is the most complete possible failure of that promise — and it is invisible on every dashboard in the product. |
| DT-04 | Producers hit the same problem on DSP credit/producer pages, so this feature generalises (resolves Q-02) | The identity→N-external-entities pattern is not artist-specific; a producer's credits scatter across duplicate credit pages exactly as a musician's catalog scatters across artist pages, and scattered credits are domain 02's entire thesis | ✅ CONFIRMED — the *mechanism* generalises (store IDs live on the identity, emitted per delivery, verified where claimable), but the *credit-page* instance is owned by **domain 02 (Credits & Attribution)**, not re-scoped into this artist-page feature. This feature stays artist-page; 02 reuses the same linking primitive for producer/writer/performer credit entities. Recording the generalisation here prevents 02 from reinventing it. |
| DT-05 | A stored artist ID is proof the user owns that page | Linking feels like a claim of ownership, so the platform could treat a linked ID as authoritative | ❌ REJECTED — linking is an **assertion, not proof**. Without verification, a user can bind their identity to a namesake's real page to inherit its followers, or point a rival's identity at a dead page. So linking must distinguish **verified** (Tier-A claim/auth completed) from **asserted** (Tier-B, no claim path). Verified IDs deliver; asserted-but-unverifiable IDs are flagged to Trust & Safety (24) and gated. The consolidation payoff (one identity, N store pages) is only trustworthy if the binding is provable — otherwise WeJammin becomes an impersonation vector. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | Store artist IDs live on the **identity** (01), not the release | Re-linking per release reintroduces the failure every time and cannot express multi-hyphenate identities (DT-02) |
| D-02 | Linking is a **blocking** step before first delivery | The first release creates a permanent page; it is the one irreversible-by-default moment in the domain |
| D-03 | Post-delivery verification that the release landed on the linked page | `Live` does not mean *correctly* live (DT-03) |
| D-04 | The platform **owns the merge chase**, it does not hand the artist a support link (resolves Q-03) | Recovery is a per-store support process taking weeks with no guarantee and is outside our control — but the consolidation thesis means WeJammin files and tracks the merge request and reports honest status, rather than dumping the problem back on the artist. It cannot promise a fix; it can own the pursuit. |
| D-05 | Links are typed **verified** (Tier-A claim/auth) vs **asserted** (Tier-B); only verified IDs are emitted for delivery, asserted-but-unverifiable links are flagged to Trust & Safety (24) | Linking is a claim, not proof; without this WeJammin is an impersonation vector (DT-05) |
