# Feature: Per-Store Delivery Status

> **Number**: 12.03.02
> **Parent**: [DSP Store & Territory Management](./12.03-dsp-store-territory-management-index.md)
> **Status**: [SURFACE]
> **Last updated**: 2026-07-16

## Overview

The board that tells an artist the truth about where their release actually is: live on Spotify,
accepted-but-not-live on Apple, rejected by Beatport, overdue at Amazon, blocked in Japan. This is
the destination screen of domain 12 — the one an artist opens repeatedly in release week — and the
one whose honesty determines whether they believe anything else the platform tells them.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Full | Sees one row per store (and per territory where it differs), each with a real state, how long it has been in it, and what is being done. Can act where action exists: retry, chase, fix a rejection (12.03.03), open the live link. Sees "we don't know" where the platform genuinely does not know — which is a state, not an omission. |
| Producer | Read-only | Sees where a record they made ended up. Legitimate interest (often a points position), no authority. Deliberate: giving them controls over another party's commercial distribution would be wrong, but hiding the outcome of their own work would be worse, and it is what every existing tool does. |
| Operator | None | Not visible. |
| Fan | None | Not visible. "Is it out yet?" is answered by 20/21 and the DSP itself — never by this board, which is a professional operations view. |

## Behavior

Status is a per (release × store × territory) object, not a flag. The state vocabulary is
normalised from partner acks (12.02.03) and must never over-claim:

| State | Meaning | Can the artist act? |
|---|---|---|
| Queued | Scheduled, not yet sent | Change schedule (12.04.01) |
| Sent | Handed to the partner | No — wait |
| Received | Partner confirmed receipt | No — wait |
| Accepted | Partner accepted; not yet live | No — wait for the store's own schedule |
| Live | Confirmed live on the store | Open the link |
| Overdue | Response window exceeded | Chase; escalate |
| Rejected | Partner refused | Fix (12.03.03) |
| Taken down | Removed | See 12.05 |
| Unknown | We genuinely cannot tell | Told plainly, with why |

**`Accepted` ≠ `Live`, and the gap between them is where the worst experience in the domain
lives.** A partner can accept a delivery and then simply not publish it — for days, with no signal.
Detecting `Live` requires store-side truth (parent Q-01), not the partner's ack, and that is the
hard part of this feature.

Every state carries **elapsed time and an expectation**. "Pending" is worthless; "Received by
Apple 6 days ago — usually 2" is the entire product. This is the same honesty rule as 12.02.03
D-01, surfaced.

### Happy Path

1. Delivery is scheduled; every selected store shows `Queued` with the target date.
2. At the delivery window, rows move to `Sent`, then `Received` as acks land.
3. Rows move to `Accepted` with the store's expected live date.
4. On release day, rows move to `Live` with a link, confirmed against store-side truth.
5. Board shows all-green; the artist stops checking. That is success.

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Accepted, release date passed, not live | The worst case. Partner ack says fine; reality says no | "Apple accepted this 9 days ago and it still isn't live. We're chasing — here's the reference." |
| Partner reports live, store-side check disagrees | Trust the store, not the ack | "Spotify says it's live but we can't find it. Looking into it." |
| Live in some territories, not others | Per-territory rows | Territory breakdown under the store row |
| Release live on the *wrong artist page* | Technically live — every status is green and the outcome is a disaster | Routes to 12.03.04. **A green board can be a lie**; see DT-03 |
| Reconciliation source unavailable | Status is stale; must say so | "Last checked 3 hours ago" — never a confident stale claim |
| Store has no reconciliation path at all | `Unknown` is the honest terminal state | "{Store} doesn't tell us. We'll show it as delivered, not confirmed." |
| 40 stores × 200 territories | 8,000 status cells; a table is unusable | Summarise by exception — show what is wrong, collapse what is fine |

### States

> The feature's own UI states, distinct from the per-store status vocabulary above.

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Empty | No delivery yet | "Nothing delivered yet" + link to scheduling |
| Loading | Fetching status | Skeleton rows |
| Populated | Statuses known | Exception-first board, healthy rows collapsed |
| Partial | Some stores unreconciled | Mixed board with explicit "unknown" rows |
| Error | Status service down | "Can't refresh — showing last known from {time}" |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | A 40-store × 200-territory status table is the right presentation because per-store status is a first-class object | Following D-02 in the parent index to its literal conclusion | ❌ REJECTED — 8,000 cells is data, not information. Being *correct* about status and *useful* about status are different problems, and the domain's founding insight (status is per-store) solves only the first. The board must be **exception-first**: surface what is wrong or late, collapse what is fine to a count. The rejection matters because the correct data model quietly invites the wrong UI, and this is the screen the product is judged on. |
| DT-02 | The partner's acceptance ack is sufficient to report a release as live | The information the partner gives us; what every distributor uses | ❌ REJECTED — accepted means accepted, not published, and the gap is routinely days. Reporting `Live` off an ack is exactly the over-claiming rejected in 12.02.03 DT-02, and it produces the domain's most infuriating experience: a green dashboard next to an absent release. Confirming `Live` needs store-side truth, which needs an answer to parent Q-01 — and the only method that reliably catches the silent case (checking the public store) is the least respectable one. That tension is real and unresolved. |
| DT-03 | A green board means the release succeeded | The implicit promise of the whole screen | ❌ REJECTED, and this is the most important annotation in the sub-domain. A release can be `Live` on every store and still be a **disaster**: on the wrong artist page (12.03.04), with the wrong (P) line, with splits nobody attested. Green means *delivered*, not *right*. The board must not imply an all-clear it cannot support — and this is precisely why 12.03.04 exists as a Deep Think addition, because the sweep's candidate list had a domain that could report total success while the artist's release was attached to a stranger's discography. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | The board is exception-first; healthy rows collapse | 8,000 correct cells is data, not information (DT-01) |
| D-02 | `Live` requires store-side confirmation, not a partner ack | Accepted ≠ published; over-claiming is the domain's most infuriating failure (DT-02) |
| D-03 | Every state carries elapsed time and an expectation | "Pending" is worthless; "6 days, usually 2" is the product |
| D-04 | `Unknown` is a first-class honest state | Some partners genuinely never tell us |
