# Feature: ERN Message Generation

> **Number**: 12.02.01
> **Parent**: [DDEX Delivery Messaging](./12.02-ddex-delivery-messaging-index.md)
> **Status**: [SURFACE]
> **Last updated**: 2026-07-16

## Overview

Turning the release object into a DDEX ERN — the standard XML message that tells a DSP a release
exists, what is in it, who owns it, where it may be sold and from when. Every delivery, update and
takedown in the domain is an ERN of some kind, so this is the narrow waist the whole distribution
path passes through.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Read-only | Never sees an ERN in the normal path and never should. When a delivery fails, they can see **what was actually sent** — rendered as plain facts ("we told Spotify: release date 14 Aug, 12 tracks, territories worldwide-except-Japan"), not as XML. This exists because "I don't know what my distributor told them" is the defining frustration of the incumbent experience. Raw message download is available but buried. |
| Producer | None | Not visible. Their contribution to the message (credits, ISRC, roles) is authored upstream in 02 and 12.01, never here. |
| Operator | None | Not visible. |
| Fan | None | Not visible. |

## Behavior

An ERN is generated per (release × partner), not once per release — the same release yields
materially different messages for different partners (12.02.02). Generation is a **pure projection**
of already-locked facts: release object (12.01), identifiers (12.07), rights and territory scoping
(12.03.01), credits (02), splits and ownership (09). It authors nothing. Anything the generator
would have to invent is a gap upstream, and must be caught by the gate (12.01.03) rather than
defaulted here — a defaulted ERN field is a fabricated fact delivered to a partner under the
artist's name.

Message types in scope: NewReleaseMessage (initial delivery), the update/supersede form
(12.05.02), and the takedown form (12.05.01). These are variations on one generator, not three.

Every generated message is **retained verbatim** with the version of every input that produced it.
When a partner and an artist disagree about what was delivered, the message is the evidence — and
per the provenance thesis, an unretained message is a fact the platform failed to record.

`[PENDING — /ideate-discover Step 5 deepening]` — field-level mapping from the release object to
ERN elements. It depends on Q-01/Q-02 in the parent index (direct vs aggregator; ERN version) and
writing it now would be fabrication.

### Happy Path

1. Release passes validation (12.01.02) and the readiness gate (12.01.03); delivery is scheduled.
2. For each selected partner, the generator resolves the partner's profile (12.02.02).
3. It projects the release object into an ERN conforming to that profile and version.
4. The message is schema-validated before it leaves; a message that fails our own schema check
   never reaches the partner.
5. Message + asset manifest are handed to the transport (12.02.03).
6. The message is retained verbatim, keyed to the release, the partner and the input versions.

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| A required ERN field has no source value | **Generation fails; nothing is defaulted.** The gap is a bug in the gate, not a message problem | Musician: "We can't deliver to Apple yet — {plain-language gap}." Internally: gate escape recorded |
| Generated message fails our own schema validation | Blocked before send; alerts platform operators | "Delivery to {partner} is held. We're on it." — never a raw schema error |
| Partner's profile requires a field the release model has no concept of | Blocked; needs a model change, not a workaround | `[PENDING — Step 5]` |
| Same release delivered to 40 partners | 40 distinct messages generated, tracked and retained separately | Status per store (12.03.02), not one "delivered" flag |
| Regeneration after a rule-pack update | New message version; supersedes prior via 12.05.02 semantics, never silently overwrites | "We're resending to Apple with a fix." |
| Release date changed after generation, before send | Message regenerated; the queued message is discarded, not amended | Transparent to user |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Pending | Delivery scheduled, not yet generated | "Scheduled for {date}" — no message internals surfaced |
| Generated | Message built + self-validated | Nothing (invisible in the happy path) |
| Sent | Handed to transport | Status moves to 12.02.03's states |
| Blocked | Generation failed | Plain-language reason on the release; platform-side alert |
| Superseded | Regenerated after change | Prior message retained, marked superseded |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | The generator may default missing fields to keep deliveries flowing | Standard distributor pragmatism — a "sensible default" ships releases | ❌ REJECTED, and this is the domain's sharpest collision with the thesis. A defaulted ERN field is a **fabricated fact delivered under the artist's name to a partner**, which is a machine-generated version of the exact reconstruction failure problem-statement.md identifies as the root cause. Defaults are how "P 2024 {artist name}" ends up on a master owned by a band. Generation must fail loudly and route the gap back to the gate. Accepted cost: more blocked deliveries than a competitor, which is the trade D-10 already made. |
| DT-02 | Every generated message must be retained verbatim with its input versions | Provenance thesis (D-18); Audit Log & Provenance Ledger cross-cut; the "my distributor won't tell me what they sent" complaint | ✅ CONFIRMED — cheap to do, and it is the only evidence when a partner and an artist disagree. It also makes the rejection→rule feedback loop (12.01.02 DT-02) analysable after the fact rather than only in the moment. An unretained message is a fact the platform failed to record, which is precisely what the product exists not to do. |
| DT-03 | Takedown and update are separate machinery from initial delivery | Sweep listed "Takedowns & Redelivery" as its own candidate, implying separate mechanics | ❌ REJECTED at the *message* layer — they are ERN variants sharing one generator, one profile resolution and one transport. But ✅ CONFIRMED at the *product* layer: their triggers, permissions and human consequences are genuinely different (a takedown can be involuntary and legally driven). Hence 12.05 exists as a sub-domain while its messages are generated here. This split — shared mechanism, distinct product surface — is the single most important structural call in the domain. |
