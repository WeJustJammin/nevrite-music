# Feature: Per-Partner Profile Conformance

> **Number**: 12.02.02
> **Parent**: [DDEX Delivery Messaging](./12.02-ddex-delivery-messaging-index.md)
> **Status**: [SURFACE]
> **Last updated**: 2026-07-16

## Overview

The per-partner knowledge that makes a standard message actually work: which ERN version a partner
consumes, which profile subset they implement, which optional fields they secretly require, which
extensions they invented, and which technically-valid constructs they reject. DDEX is a standard
in the way HTML is a standard — everyone implements a different dialect, and the gap between the
spec and the partner is where distribution actually lives.

## Behavior

A partner profile is versioned data describing everything WeJammin knows about delivering to one
partner: ERN version, profile subset, required-beyond-spec fields, partner extensions, asset
format and rendition requirements, transport (12.02.03), acknowledgement semantics, territory and
date rules, and the accumulated scar tissue of past rejections.

Profiles are the same artifact class as validation rule packs (12.01.02) and **must share one
source of truth**. The failure mode if they drift is precise and nasty: validation tells the
artist their release is fine for Apple while the generator emits a message Apple rejects. The user
is then told two contradictory things by one product, which destroys trust in both.

This is a **partner-shaped, not code-shaped** feature. Partners change requirements by email, with
no changelog and often after the change is live. Onboarding a partner is largely a commercial and
certification exercise, not an engineering one — which is why parent Q-01 (direct vs aggregator)
dominates this feature's size by an order of magnitude.

### Happy Path

1. Generator (12.02.01) requests the profile for a partner.
2. Profile resolves at its current version, pinned for this delivery.
3. Generator emits a message conforming to that profile.
4. Message passes conformance checks derived from the same profile before transport.
5. The profile version is recorded alongside the retained message, so a later question ("why did
   we send that?") is answerable.

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Partner changes requirements without notice | Rejections arrive (12.03.03) → profile updated → affected releases redelivered | "Apple changed a rule. We've fixed and resent — nothing for you to do." |
| Profile update mid-flight | Version is pinned per delivery; in-flight deliveries complete against the pinned version | Nothing |
| Profile and validation rule pack disagree | **The trust-destroying case.** Must be structurally impossible, not merely monitored | — (must never surface) |
| New partner onboarding | Profile authored + conformance-certified with the partner before any real delivery | Store appears in the picker only once certified |
| Partner deprecates an ERN version | Migration window; all profiles on that version must move | Nothing, if handled ahead of the deadline |
| Partner rejects something the profile says is valid | Profile is wrong; rejection feeds back as a profile correction | Handled by 12.03.03 |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Active | Certified and delivering | Store selectable in 12.03.01 |
| Draft | Being authored | Store not offered |
| Certifying | Conformance testing with the partner | Store not offered |
| Deprecated | Partner sunsetting a version | Internal migration warning |
| Suspended | Partner outage or contract lapse | Store shows as unavailable in 12.03.01 with a reason |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | Profiles (12.02.02) and validation rule packs (12.01.02) are separate concerns — one is about messages, one is about metadata | The natural layering; they sit in different sub-domains | ❌ REJECTED — they are **two projections of one fact**: what this partner accepts. Modelling them separately guarantees drift, and drift produces the worst possible outcome: the product telling the artist "you're ready for Apple" and then failing at Apple. One partner-knowledge store, two read paths. This is the most important structural conclusion in this sub-domain and it crosses a sub-domain boundary, so it is recorded in the domain CX file as well. |
| DT-02 | Partner knowledge is a cost centre — necessary plumbing | Framing it as integration work | ❌ REJECTED — it is the distributor's **actual moat**. DistroKid's value is not its UI; it is fifteen years of knowing what Beatport rejects. WeJammin starts with none of it, which is a real and under-acknowledged cold-start disadvantage that no amount of provenance differentiation offsets. It also strengthens the aggregator option in parent Q-01: buying someone else's accumulated partner knowledge may be strictly correct at launch, even though it looks like ceding the layer. |
| DT-03 | Profile version should be pinned per delivery, not read live | Correctness reasoning about in-flight deliveries | ✅ CONFIRMED — an unpinned profile means a mid-flight update can produce a message that matches neither the old nor the new profile, and makes the retained message (12.02.01 DT-02) unexplainable after the fact. Pinning is what makes "why did we send that?" answerable, which is the whole point of retention. |
