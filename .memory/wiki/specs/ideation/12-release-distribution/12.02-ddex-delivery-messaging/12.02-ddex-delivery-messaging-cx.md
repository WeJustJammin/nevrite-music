## Cross-Cut Details

### CX-01: Profile Conformance ↔ ERN Generation

**Relationship**: The generator is deliberately ignorant. It knows how to project a release object into a message; it knows nothing about Apple. Every partner-specific decision — ERN version, which optional fields are secretly required, which extensions to emit, which valid constructs to avoid — comes from the profile, pinned per delivery (12.02.02 D-02). This keeps partner knowledge in one updatable place instead of smeared through generator branches, which matters because partner rules change by email with no changelog.

**Role scoping**:
- **Musician**: no visibility into either. Experiences the pairing only as "your release went to Apple" or as a plain-language block.
- **Producer / Operator / Fan**: not affected.
- **Platform admin** (`[PENDING]` — not a persona per ideation-index.md Q-02): the real actor. Authors profiles, inspects generated messages, runs conformance tests.

**Synthesis questions answered**:
1. **Shared state conflict**: The **partner-knowledge store** is the shared entity, owned by 12.02.02. The generator is a pure reader. No merge concern — but note this store is also read by 12.01.02 (validation), which is a cross-sub-domain hazard recorded in the domain CX file.
2. **Trigger chain**: Generation requests a profile; a missing or uncertified profile means the partner is not offerable in the first place (12.02.02 D-03), so the failure surfaces at store selection, not at delivery. Failing early is the point.
3. **Permission intersection**: None at persona level — both are platform-internal. The permission question is entirely admin-side.
4. **Notification fan-out**: A profile-caused generation failure alerts platform operators, not the artist. The artist is told only "we can't deliver to Apple yet" with a plain reason — the partner-dialect detail is noise to them.
5. **State transition conflict**: Yes, and it is handled by pinning. A profile updated mid-generation could otherwise produce a message conforming to neither version. Pinning also makes the retained message explainable later (12.02.01 DT-02), which is the whole reason retention has value.

### CX-02: Profile Conformance ↔ Choreography

**Relationship**: Choreography has no transport logic of its own — it executes what the profile describes: which transport, in what order, with what naming, what an ack means, and how long a response should take. The last is the interesting one: the expected-response window that makes `overdue` a real state (12.02.03 D-01) is profile data, not a global timeout — and it resolves **per (partner × message type)**, never per ack stage (12.02.02 D-13).

The window's ratified shape, stated once here so the two files are read together: **observed outranks contractual** — tier 1 is the observed **p95** over **≥30** `signal-complete → first terminal ack` observations in the last **180 days**, rounded up to the next whole partner-business-day with a floor of 1 (`measured`); tier 2 is the partner's stated SLA, used only where that floor is unmet (`stated`); tier 3 is the seeded 5 partner-business-days (`unmeasured`, no artist-facing claim). An **unconditional 10-partner-business-day internal escalation ceiling** runs alongside all three (12.02.02 D-12) and never speaks to an artist.

**Role scoping**:
- **Musician**: sees the *consequence* — "Apple hasn't responded in 6 days, that's longer than usual". "Longer than usual" is only sayable because the profile carries a per-(partner × message type) norm, **and it is a different number from the alarm**: the copy is the observed **p50 at N ≥ 10**, the alarm the **p95 at N ≥ 30**. Below the p50 floor no expectation clause is shown at all — the artist gets elapsed time and an honest "we don't know yet".
- **Producer / Operator / Fan**: not affected.

**Synthesis questions answered**:
1. **Shared state conflict**: None. Profile is read-only to choreography.
2. **Trigger chain**: Profile resolves → transport executes. A suspended profile (expired credentials, contract lapse) holds deliveries rather than failing them — the release is not broken, the partner is unreachable, and those must not look the same to the artist.
3. **Permission intersection**: None at persona level.
4. **Notification fan-out**: Profile suspension must fan out to **every release queued for that partner** at once, not per-release-on-discovery. One partner outage is one event, not forty failures.
5. **State transition conflict**: Yes — a profile suspended while a delivery is in flight. The pinned profile governs the in-flight delivery to completion; the suspension applies to what has not yet started.

### CX-07: Choreography ↔ Per-Store Delivery Status

**Relationship**: A mixed partner result does not fork the release-level status identity. Choreography supplies the original delivery/message correlation for every rejected item; the status record retains it alongside the stable affected-item ID, evidence, and triage state. A corrected item receives a successor-delivery correlation only when redelivered to the rejecting partner. Regenerating an in-flight message remains forbidden.

**State transition**: The parent row projects `Partial acceptance` while evidence is mixed. A new acknowledgement can resolve only the correlated rejected-item detail it confirms; the parent becomes healthy only when full-release evidence supports it. No acknowledgement creates an independent track-status row.

### CX-04: Choreography ↔ Profile Conformance (the learning loop)

**Relationship**: The back-edge, and the one that compounds. Every rejection and every surprising ack is evidence the profile is wrong. Feeding that back turns each artist's rejection into partner knowledge that protects every other artist — the accumulated asset 12.02.02 DT-02 identifies as the distributor's actual moat, and the thing WeJammin most conspicuously lacks at launch.

Note the loop has two heads: it also feeds validation rule packs (12.01.02 DT-02) so the *next* artist is warned before delivery rather than rejected after it. Both must be fed from one store, or the two will drift and the product will contradict itself.

**Role scoping**:
- **Musician**: benefits invisibly and asymmetrically. The artist who hit the rejection pays; every subsequent artist is warned for free. Worth being explicit about — it is a real, if unglamorous, network effect and one of the few in this domain.
- **Producer / Operator / Fan**: not affected.

**Synthesis questions answered**:
1. **Shared state conflict**: Choreography *writes* to the partner-knowledge store (via triage in 12.03.03), which every other feature reads. This is the one write-path into the store from delivery, and it needs review — an automatic rule derived from a one-off partner glitch could block valid deliveries for everyone. Human confirmation before a rejection becomes a rule. `[PENDING — Step 5]` for whether that review is manual, thresholded, or both.
2. **Trigger chain**: Rejection → triage (12.03.03) → proposed profile/rule change → review → profile update → affected releases redelivered (12.05.02). Async, multi-day, spanning three sub-domains.
3. **Permission intersection**: None at persona level; the review step is admin.
4. **Notification fan-out**: When a rule learned from artist A's rejection invalidates artist B's queued release, B must be told before the delivery date, not at it. This is the state-conflict from 12.01 CX-02 arriving from a different direction.
5. **State transition conflict**: Yes. A profile update can invalidate a gate-green release awaiting a scheduled delivery. Since rule packs are versioned data (12.01.02 D-02), this is certain to happen. The release must fall back to blocked with an explanation, never fail silently at the delivery window.

### CX-05: MEAD ↔ Profile Conformance

**Relationship**: MEAD support is partner-optional. The profile declares whether a partner consumes it; unsupported partners are skipped with no failure and no user-visible event. This keeps the "MEAD is never blocking" rule (12.02.04 D-04) structurally true rather than merely intended.

**Role scoping**:
- **Musician**: sees "sent to {N} of {M} stores that use it" — honest about reach without implying a failure.
- **Producer**: contributed descriptors; no visibility into which partners took them.
- **Operator / Fan**: not affected.

**Synthesis questions answered**:
1. **Shared state conflict**: None.
2. **Trigger chain**: Profile says supported → MEAD delivery attempted; unsupported → skipped silently. A skip is not a failure and must never enter the error path.
3. **Permission intersection**: None.
4. **Notification fan-out**: None. A partner not supporting MEAD is not news.
5. **State transition conflict**: A partner *adding* MEAD support later means existing releases could be enriched retroactively — a real, cheap improvement nobody would think to ask for, and a mild argument for retaining enrichment data even where it was never deliverable. `[PENDING — Step 5]`

## Rejected Pairs

| # | Source | Target | Reason for Rejection |
|---|--------|--------|---------------------|
| R-01 | 12.02.01 ERN Generation | 12.02.04 MEAD | Considered because both produce DDEX messages from the same release, and a shared generator looks tempting. Rejected: MEAD's content source is the *session record* (07/02), not the release object, and its delivery is independently sequenced and never blocking. They share the transport (CX-06) and the profile (CX-05) but not a generator. Forcing a shared generator would make a never-blocking enrichment message an input to the blocking delivery path — coupling optional to mandatory, which is exactly backwards. |
| R-02 | 12.02.04 MEAD | 12.02.01 ERN Generation | Same pair, reverse direction. MEAD does not gate, inform or alter ERN generation. Its absence is invisible to the ERN. |
| R-03 | 12.02.03 Choreography | 12.02.01 ERN Generation (retention) | Considered: should choreography own message retention, since it is the last thing to touch the message? Rejected — retention is keyed to *what was generated and why* (message + input versions + profile version), which is generation's knowledge. Transport only knows what it was handed. Putting retention in transport would lose the input provenance that makes retention worth anything (12.02.01 DT-02). |
