## Cross-Cut Details

### CX-01: Composition ↔ Readiness Gate

**Relationship**: Composition (12.01.01) assembles a per-track contributor roll-up by reading credits (02) and rights (09) for each recording. The gate (12.01.03) evaluates that roll-up. The coupling is live, not batch: adding a recording adds its unmet conditions to the gate; removing one clears them. A Musician who cannot get a co-writer to respond can literally drop the track to ship the release — which is a real and probably acceptable escape hatch, but it means the gate's blocking power is bounded by the artist's willingness to cut material.

**Role scoping**:
- **Musician**: sees the gate state change as they compose — the intended feedback loop. The cost of an unresolved contributor is visible while the tracklist is still soft.
- **Producer**: sees their own attestations satisfy conditions across every release a recording appears on, not just this one. Attesting once on a recording pays forward to the album and the compilation.
- **Operator / Fan**: not affected — no visibility into either feature.

**Synthesis questions answered**:
1. **Shared state conflict**: The **recording** is the shared entity, and neither feature owns it — 02/09 do. Both read. Composition owns only the release↔recording membership and order; the gate owns nothing, it is a pure projection. No merge strategy needed, which is the point of the recordings-not-files decision (12.01.01 D-01).
2. **Trigger chain**: Composition change → roll-up recompute → gate re-evaluate. Synchronous and cheap (it is a read over already-authored facts). If the roll-up fetch fails, the gate must show "unknown", never "ready" — failing open here would deliver unattested provenance, the exact failure the domain exists to prevent.
3. **Permission intersection**: Yes, and it is the sharpest one in the sub-domain. Add-eligibility in composition gates on **rights position** (09); the gate's attestation requirement is about **credits** (02). A user can hold a rights position with no credit (a label) or a credit with no rights (a session player). Downstream spec writers must not collapse these into one permission.
4. **Notification fan-out**: Yes — a gate condition arising from a composition change nudges the contributor who must act. Removing a track should *withdraw* any pending nudge; leaving stale "please confirm your credit" requests for a track that no longer exists is a real trust leak.
5. **State transition conflict**: Yes — a contributor can confirm a split at the moment the owner removes the track. Confirmation must be idempotent and attach to the **recording**, not to the release, so a late confirmation is never lost and is still valid when the recording resurfaces on a later release.

### CX-02: Metadata Validation ↔ Readiness Gate

**Relationship**: These are two gates in front of one button and they look the same to the user, which is a design hazard. Validation (12.01.02) is a machine check against a partner rule — the author can always fix it alone, immediately. The gate (12.01.03) is a **social** check — the author usually *cannot* fix it alone, because it needs another person to act. Presenting them in one undifferentiated "problems" list teaches the user that provenance failures are clerical, which is exactly the belief the product exists to break.

**Role scoping**:
- **Musician**: must be able to tell "I have work to do" apart from "I'm waiting on Jamie" — the two have completely different time constants (seconds vs days) and completely different actions.
- **Producer**: mostly appears on the gate side, not the validation side. Their attestation is the product; their typo is not.
- **Operator / Fan**: not affected.

**Synthesis questions answered**:
1. **Shared state conflict**: None. Validation findings are derived from release metadata; gate conditions are derived from 02/09 facts. Disjoint sources, no shared writable state.
2. **Trigger chain**: Sequential by design — validation must be clean before the gate is even presented. Reason: chasing a co-writer for a confirmation on a release that will be rejected for a title-casing rule wastes the one favour the artist gets to ask. Order the human cost, not the machine cost.
3. **Permission intersection**: Yes, and asymmetric. A Producer can clear *validation* items on a release they do not own (recording-level fields they are authoritative for) but cannot deliver it. Their attestation clears *gate* items nobody else can clear. The Producer is a high-power, low-authority actor in this sub-domain, which is an unusual permission shape worth carrying forward.
4. **Notification fan-out**: Validation notifies nobody — it is the author's own problem. The gate notifies broadly. That difference alone justifies separating them in the UI.
5. **State transition conflict**: A rule-pack update (12.01.02 DT-02) can invalidate a release that was previously clean — including one already through the gate and awaiting a scheduled delivery. Rule packs are versioned data, so this **will** happen. The release must fall back to blocked and tell the user why, rather than failing silently at delivery. Unresolved: whether a rule-pack update can invalidate a release *between* gate-green and delivery, and what the user is told. `[PENDING — Step 5]`

### CX-03: Asset Conformance ↔ Readiness Gate

**Relationship**: The gate cannot open until assets are verified, but verification is genuinely slow (spectral analysis over an album of 24-bit/96 kHz masters). This forces the gate to distinguish *unverified* from *failed* — a distinction most builders collapse into a red X, which trains users to distrust the gate and click through it.

**Role scoping**:
- **Producer**: owns the fix. A blocking asset failure is a re-render, which happens in the DAW — per personas.md, the Producer will not tolerate a flow that makes them leave the session. The report must be actionable from a notification, not only from the builder.
- **Musician**: sees pass/fail and cannot act on most audio failures. Telling them "true-peak clipping at 3 points" without a route to the Producer is a dead end.
- **Operator / Fan**: not affected.

**Synthesis questions answered**:
1. **Shared state conflict**: The **master file** is shared with 07 (projects) and the Media Handling cross-cut. Neither this feature nor the gate owns it. Replacing a master post-gate must re-open both the analysis and the gate.
2. **Trigger chain**: Upload → async analysis → conformance result → gate re-evaluate. If analysis fails (not the asset — the *job*), the gate stays closed and retries. Fail closed: an unanalysed master is not a conformant master.
3. **Permission intersection**: Asset upload is Producer-weighted; gate resolution is Musician-and-Producer. A release whose Producer has left the project can become unfixable — nobody with the DAW session is still attached. `[PENDING — Step 5]`
4. **Notification fan-out**: An asset failure must reach the **Producer**, not just the release owner. The release owner is usually not the person who can fix it.
5. **State transition conflict**: Yes — a master replaced while the gate is evaluating. The gate must key on an asset version, not on a boolean, or it will green-light against the analysis of a file that no longer exists.

### CX-05: Metadata Validation ↔ Composition

**Relationship**: Release type is chosen in composition but its rules are owned by validation, and the rules are per-store and contradictory (Apple and Spotify draw the single/EP/album boundary differently). Surfacing the constraint at the moment of the type choice — rather than as a rejection later — is the difference between a rule that teaches and a rule that punishes.

**Role scoping**:
- **Musician**: makes the type choice; must see the consequence (editorial eligibility, chart eligibility) at that moment, not at delivery.
- **Producer / Operator / Fan**: not affected.

**Synthesis questions answered**:
1. **Shared state conflict**: Release type lives on the release object (composition-owned). Validation reads it. No conflict.
2. **Trigger chain**: Type change → re-validate whole release, since type rules cascade to track count, duration and title conventions. Cheap, synchronous.
3. **Permission intersection**: None beyond composition's own — the Producer cannot change type.
4. **Notification fan-out**: None.
5. **State transition conflict**: Type change after gate-green re-opens validation but **not** the gate — provenance facts do not depend on release type. Worth stating explicitly so downstream spec writers do not over-invalidate.

## Rejected Pairs

| # | Source | Target | Reason for Rejection |
|---|--------|--------|---------------------|
| R-01 | 12.01.04 Asset Conformance | 12.01.02 Metadata Validation | Adjacent but genuinely independent: assets are checked by analysis, metadata by rule packs; neither reads the other's state. They meet only at the gate (CX-03), and modelling a direct edge would invent a dependency that does not exist. The one apparent exception — declared duration vs file duration — is a metadata rule that happens to read an asset-derived value, not an interaction between the features. |
| R-02 | 12.01.05 Label Copy | 12.01.04 Asset Conformance | No shared state, no trigger. The (P) line has no bearing on whether a WAV conforms. |
| R-03 | 12.01.01 Composition | 12.01.04 Asset Conformance | Considered because both touch recordings, but the coupling is through the **recording entity** owned by 07/09, not between these features. Composition orders recordings; conformance analyses their files. Neither triggers the other. Modelling an edge here would smuggle in the file-centric release model that 12.01.01 DT-01 explicitly rejects. |
| R-04 | 12.01.05 Label Copy | 12.01.02 Metadata Validation | Tempting — (P) line format *is* a validated field — but that is validation doing its ordinary job over one more field, not an interaction. The interesting edge for label copy is with the **rights record** (09) and with the **gate** (CX-06), and both are already captured. |
