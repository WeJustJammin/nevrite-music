# Feature: Audio & Artwork Asset Conformance

> **Number**: 12.01.04
> **Parent**: [Release Builder & Delivery Readiness](./12.01-release-builder-index.md)
> **Status**: [DEEP]
> **Last updated**: 2026-07-16

## Overview

Checking that the actual media — masters and cover art — meets each delivery target's technical
specification before delivery, and producing the partner-specific renditions each one wants from a
single stored source.

Asset rejections are slower and more expensive than metadata rejections because the fix requires
going back to the engineer or the designer, not editing a text field. A title-casing rejection is
a thirty-second fix by the person already looking at the screen. A "master is not 24-bit" rejection
is an email to a Producer who closed the session three weeks ago, has the project archived on a
drive at the studio, and is currently tracking someone else's record.

**The honest limit of this feature, stated up front**: every check here can pass on the wrong file
(DT-11). Conformance certifies that a file *meets a spec*, never that it is *the right music*. The
only defence against the wrong take is that the file arrived from a WeJammin project (07) rather
than a desktop upload — which is the domain thesis (D-18) reappearing at the asset layer.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Producer | Full | **The authoritative persona here.** Supplies the master (ideally it is already attached to the project in 07 and no upload happens at all), and is the only actor who can fix a real audio failure, because the fix is a re-render in the DAW. Sees the full technical report per track — container/codec, sample rate, bit depth, channel config, integrated loudness (LUFS), true-peak (dBTP), sample-peak, inter-sample clipping count, DC offset, mono-compatibility correlation, head/tail silence, measured duration, spectral cutoff, Atmos/ADM presence — each row scoped to the exact delivery targets it affects. Can replace a master, and sees the replacement's price before committing to it (DT-09). Receives asset failures by notification, actionable without opening the builder (CX-03). |
| Musician | Config | Uploads and replaces artwork; selects opt-in conformance targets (e.g. the Apple Digital Masters badge, DT-04); attests the artwork content checklist (DT-03). Sees audio results as plain-language pass/fail with the technical panel **collapsed by default** — they are not a mastering engineer and the report must be legible without the vocabulary. Can accept an advisory ("yes, I know it's −4 LUFS, that's the record") or route it to the Producer with one action. Cannot fix most audio failures and must never be shown a technical failure without a route to someone who can (CX-03). On a self-produced release they hold the Producer capability too — see DT-18: the lens is per-capability-held, not per-account. |
| Operator | None | Not visible. A studio Operator may have *engineered* the master, but they reach this feature holding the **Producer capability**, not an Operator permission — exactly as the parent index records for the co-owned-master case (which resolves through a domain 09 rights position, not an Operator lens here). Recorded so downstream spec writers do not invent an Operator asset UI. |
| Fan | None | Not visible. The Fan sees the *output* of this feature — the artwork on a pre-save page (12.04.03) and on the DSP — and never the machinery. Note the asymmetry this creates: artwork is the one asset in this feature that is **published to the Fan surface**, which is what makes DT-15 (illegal-imagery scanning) a statutory duty rather than a product preference. |

## Behavior

Two asset classes with different failure economics, different actors, and different fix latencies.

### Scoping rule — asset findings are per-target, never global

Findings are scoped to the delivery targets they affect, mirroring 12.01.02 D-01 (per-store
findings, no global `valid` flag). A finding is **globally blocking only if every selected target
rejects it**. Everything else is blocking *for the targets that reject it*, and the Musician's
established escape — drop the target (12.01.02: "Musician removes a store to dodge a finding") —
applies unchanged. See DT-05; this is what stops an absent Producer from making a release
permanently undeliverable.

Three severities, matching 12.01.02's vocabulary so the builder speaks one language:

| Severity | Meaning | Effect |
|---|---|---|
| **Blocking** | A selected target will reject the asset | Delivery to that target impossible until fixed or the target is dropped |
| **Warning** | Accepted, but degrades the outcome (badge ineligibility, audible artefacts on lossy encodes) | Delivery allowed; the warning is recorded against the release |
| **Advisory** | An observation about an artistic choice or a consequence the artist may not know | Informational; never blocks; never nags twice |

### Audio

**Measured on every master, on every version, exactly once per (asset version × spec version):**

| Property | Check | Default severity |
|---|---|---|
| Container / codec | Content-sniffed, not extension-trusted. Lossless PCM (WAV/AIFF) or FLAC | Blocking where the target's spec pack says so |
| Sample rate | ≥ 44.1 kHz. Higher retained as-is; never pre-emptively resampled (DT-07) | Blocking below the target's floor |
| Bit depth | 16 or 24. 32-bit float accepted as a source, converted in the rendition | Blocking below the target's floor |
| Channel config | Mono or stereo for the standard deliverable. >2 channels is not a stereo master — it is an Atmos deliverable or an error | Blocking |
| Measured duration | Reported. **Not compared to the declared duration here** — that comparison is a metadata rule (DT-06) | n/a — published, not judged |
| Integrated loudness (LUFS) | Reported against each selected target's published normalisation target | **Advisory, always** (DT-01) |
| True-peak (dBTP) | Reported. Above the target's ceiling (typically −1 dBTP for lossy-encode headroom) | Warning |
| Inter-sample clipping | Count of clipped points reported | Warning |
| DC offset | Reported where non-trivial | Advisory |
| Mono compatibility | L/R correlation; a master that substantially cancels in mono | Advisory (DT-14) |
| Head / tail silence | Reported. **Suppressed entirely on continuous-mix releases** (DT-07) | Advisory |
| Spectral cutoff | A sharp cliff consistent with a lossy source | Advisory with appeal — never a verdict (DT-17) |
| Digital silence | A file with no signal at all, or under −60 dBFS throughout | Blocking — this is a broken file, not a choice |
| Spatial (Dolby Atmos ADM BWF) | A separate deliverable with its own spec. Presence detected; absence is never a failure | n/a (Q-02: in scope for v1?) |

**Partner-sourced numbers are data, not code.** Every floor, ceiling and target above lives in a
versioned **asset spec pack** supplied per partner, on the same rails as 12.01.02's metadata rule
packs — because partner asset specs change silently and without changelogs, exactly as metadata
rules do, and because D-02's re-derivation promise is only honourable if a spec change is a data
change. (This is a shared *mechanism*; it is not a dependency on 12.01.02, which reads none of this
feature's state and vice versa — R-01 stands.)

Currently published DSP normalisation targets, for illustration and to make the advisory concrete:
Spotify −14 LUFS, Apple Music ≈ −16 LUFS, YouTube −14, Amazon −14, Tidal −14. These are exactly
the kind of number that will be wrong within a year, which is why they are in the spec pack.

**Loudness is advisory and always will be.** DSPs normalise; an over-compressed master is an
artistic choice the platform does not get to veto (DT-01). What the platform *does* do is price the
choice at the decision, per the domain's own recurring pattern: not "your master is too loud" but
"integrated −4.2 LUFS. Spotify normalises to −14 — this will play about 9.8 dB quieter than you
mastered it, and the quiet passages do not gain that back."

### Artwork

**Mechanically checkable, and cheap — these run in under 3 seconds on upload:**

| Property | Check | Severity |
|---|---|---|
| Dimensions | ≥ 3000 × 3000 px (the universal distributor floor). Ceiling is partner-sourced | Blocking |
| Aspect | Exactly 1:1. **Never auto-cropped** (DT-07) | Blocking |
| Colour space | RGB / sRGB. CMYK rejected | Blocking |
| Format | Content-sniffed. JPEG or PNG; the accepted list is partner-sourced | Blocking |
| Bit depth | 8 bits per channel | Blocking |
| File size | Against the target's ceiling | Blocking for that target |
| Corrupt / truncated / decode failure | Rejected before any further processing | Blocking |

**Not mechanically checkable, and the more common late rejection:** no URLs, no social handles, no
store names or logos, no pricing or promotional text ("out now", "free download"), no third-party
trademarks, no explicit imagery without the corresponding declaration, no visibly low-quality or
pixelated source.

Per DT-03 these are **not** automated blocks and **not** an admin review queue. They are a
**checklist the Musician attests to** at upload — five statements, ticked, recorded with a
timestamp and an actor. This costs the platform nothing, adds one screen, and converts a banner
nobody reads into a fact the record holds. When a store rejects the artwork anyway, the attestation
is what makes the rejection diagnosable instead of mysterious.

### Renditions

The user supplies **one** high-quality source per asset; WeJammin derives what each partner wants
(D-02). Asking a Producer for six encodes is asking them to do the platform's job, and per
personas.md a flow that makes them leave the session will not be used.

**The stored source is immutable.** Renditions may transcode, resample and re-encode because a
partner requires it. Nothing derived may alter the *artistic* content — no loudness normalisation,
no limiting, no silence trimming, no crop, no "helpful" fixes (DT-07). Derived renditions strip
EXIF/ICC and embedded metadata; the source keeps everything.

### Reuse and cache semantics

Analysis attaches to the **recording's asset version**, not to the release. Consequences, all of
which fall out for free:

- A recording delivered as a single and later on the album is analysed **once**. The album does not
  re-verify what the single already proved.
- A partner spec change re-derives results from the stored source — **no re-upload request months
  after the fact** (D-02, and the only model compatible with 12.01.02 DT-02's hot-updatable packs).
- Replacing a master supersedes the asset version, invalidates every result keyed to the old one,
  and re-opens the gate (CX-03: the gate keys on an asset version, not a boolean).

### Happy Path

1. Producer finishes the master inside a WeJammin project (07). The file is already attached to the
   recording — **there is no upload step**. This is the path the whole design optimises for.
2. Analysis starts automatically on the new asset version and runs asynchronously. The builder stays
   fully interactive throughout; nothing about the release is blocked except delivery.
3. Per-track progress appears in the builder; the Producer can close the tab. Completion arrives as
   a notification, not as a reason to sit and watch a bar.
4. The technical report renders per track, each row scoped to the delivery targets it affects.
   Advisories are stated with their consequence priced ("Spotify will play this 9.8 dB quieter").
5. Musician uploads cover art. Dimension / aspect / colour-space / format checks return in under
   3 seconds; the content checklist is presented and attested.
6. Fingerprint match fires against 12.06's reference set at asset availability — the earliest
   possible moment, before any date is announced (DT-08). No match: nothing is shown.
7. Zero blocking findings across the selected targets → assets are marked conformant at their
   current version; the readiness gate (12.01.03) sees them as ready (CX-03).
8. Partner renditions are derived at delivery time from the stored source (12.02.03).

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Master is a lossy source (MP3 decoded and re-wrapped as WAV) | Advisory with an appeal, never a verdict — a dark master, a tape transfer, or a deliberately lo-fi record all trip the same test (DT-17). Blocks nothing; costs the ADM badge target if it is selected | "The spectrum cuts off sharply at 16 kHz, which usually means an MP3 somewhere in the chain. If that's intentional, dismiss this — it won't stop the release. It will cost the Apple Digital Masters badge." |
| Loudness far outside every published normalisation target | **Advisory only, permanently** (DT-01) | "Integrated −4.2 LUFS. Spotify normalises to −14 — about 9.8 dB quieter than you mastered it. That's a choice, not an error." |
| True-peak above the target's ceiling / inter-sample clipping | Warning | "Clipping at 3 points, peaks to +0.4 dBTP. Not blocking. It will be audible on lossy encodes; the fix is 1 dB of headroom." |
| File is digital silence, or under −60 dBFS throughout | Blocking. This is not an artistic choice — it is the wrong file or a broken render | "Track 6 has no audio in it. That's almost certainly the wrong bounce." |
| Artwork below 3000 × 3000 | Blocking on every target — no escape by dropping a store, because they all reject it | "Cover art must be at least 3000 × 3000. Yours is 1400 × 1400. Upscaling won't pass — this needs the original from whoever made it." |
| Artwork is 3000 × 2000 | Blocking. **Never auto-cropped** — choosing what to cut out of a cover is not the platform's decision | "Cover art has to be square. Yours is 3000 × 2000. We won't guess which 1000 pixels to cut." |
| Artwork contains a URL, handle or store logo | Not mechanically detectable with confidence; the attested checklist stands in (DT-03) | Checklist: "No URLs, handles or store logos · No pricing or promo text · No third-party logos · Explicit imagery is declared · This is the original, not an upscale" — ticked, timestamped, recorded |
| Artwork attested clean, store rejects it anyway | Rejection returns via 12.03.03 and becomes an asset rule where it is mechanisable. The attestation makes it diagnosable rather than mysterious | "Apple rejected the artwork for text we don't check for. You attested there was none on {date} — here's their reason." |
| Declared track duration ≠ measured duration | This feature **publishes the measured duration and stops** (DT-06). The declared-vs-measured comparison is a metadata rule and belongs to 12.01.02 (R-01 says so explicitly) | Surfaced by validation, not here — the finding lands on the metadata field that is wrong |
| Explicit flag declared clean, profanity audible in the master | Same boundary: an asset-derived signal is published with a confidence, the rule that compares it to the declared flag is metadata's (DT-06). Advisory at best — transcription is not reliable enough to assert | Surfaced by validation as an advisory on the explicit field |
| Track under 30 seconds | Advisory with the royalty consequence stated — a play under 30 s does not count as a stream on the major DSPs (DT-13) | "Track 2 is 24 seconds. It can be delivered, but it can never earn a stream — the majors don't count a play under 30 seconds." |
| Master substantially cancels in mono | Advisory (DT-14) | "Track 5 loses most of its low end when summed to mono. Clubs and phone speakers are mono. Worth a check with the engineer." |
| Continuous mix / DJ album — no gaps between tracks | Head/tail silence advisories **suppressed entirely** for continuous-mix releases. A silence check that fires on every track of a mix album is noise, and the "fix" would destroy the record (DT-07) | Nothing. The correct output is silence about silence. |
| Producer has left the project; a blocking audio failure remains and nobody has the session | **Not unfixable** — this is what per-target scoping is for (DT-05). Drop the target that rejects it and ship to the rest. Only a globally-rejected failure (e.g. artwork below floor, digital silence) is terminal | "Apple won't take this master and the person who rendered it isn't reachable. You can ship to the other 5 stores now and add Apple later, or get a new render." |
| >2 channels in a file declared as the stereo master | Blocking. This is either an Atmos deliverable in the wrong slot or a render error — both need a human | "Track 3 has 6 channels. If that's the Atmos mix it goes in the spatial slot; if not, something went wrong in the bounce." |
| Atmos supplied for some tracks only | Allowed — partial Atmos delivery is normal and correct | "Atmos on 4 of 10 tracks. Apple takes the other 6 in stereo. Nothing to fix." |
| Master replaced while its analysis is still running | The in-flight job is **superseded**: its result is discarded on completion, never applied. Analysis restarts on the new version. Results are keyed to (asset version × spec version), so a stale result cannot attach | "Replaced. Re-checking track 4." — the old progress bar is gone, not finished |
| Two band members replace the same master within seconds of each other | Both versions are retained; the release points at the later one; neither is silently destroyed. The superseded version stays inspectable and restorable | "Sam replaced this master 20 seconds after you did. Yours is the one attached — Sam's is still here if it was the right one." |
| Master replaced **after** the gate is green | Gate re-opens, analysis re-runs, conformance falls back to unverified. The gate keys on asset version, so it cannot green-light against the analysis of a file that no longer exists (CX-03) | "New master on track 4 — the release is back to checking. Delivery is paused until it clears." |
| Master replaced **after** the release is live | This is a materially different machine from a metadata update: several DSPs require a takedown and a new ISRC for an audio change, which forfeits streams, playlist position and release date (DT-09). Priced at the decision, before the button, per the domain's own pattern | "Replacing live audio isn't like fixing a typo. On {stores} this means taking the track down and re-releasing it under a new ISRC — you lose the stream count, the playlist adds, and the original release date. Here's what survives and what doesn't." |
| Master replaced after Content ID registration | The reference fingerprint is now wrong: the old one keeps claiming UGC that uses audio no longer being sold, and the new audio is unregistered and claims nothing (DT-10). Re-registration is triggered and the interim window is stated, not hidden | "The Content ID fingerprint matches the old master. We're re-registering — until it completes, UGC using the new mix isn't claimed." |
| Fingerprint match at upload against someone else's registered recording | Advisory routed to the gate/rights, **not** an accusation. It fires at upload, before a date is announced, which is the entire point (DT-08). The Musician's named accidental failure is the uncleared sample | "This matches a registered recording by {artist}. That's fine if it's cleared or it's yours — but sort it now, not after you've announced a date." |
| Artwork contains illegal imagery | Statutory obligation, not a product choice — artwork publishes to the Fan surface (D-11/D-13). Detection triggers here; adjudication and every downstream duty belong to 24 (DT-15) | Handled by 24, deliberately not specified as a builder UI |
| Upload is a polyglot / malformed / decompression-bomb file, or a "WAV" that is a zip | Format is determined by **content sniffing, not extension**. Size and decoded-dimension ceilings are enforced *before* any decode. Analysis treats every byte as hostile input | "We can't read this file. It says WAV but it isn't one." |
| Upload exceeds the size ceiling | Rejected at the boundary, before bytes are stored or analysed | "This file is 4.2 GB. The ceiling is {N} GB — if that's an Atmos deliverable it goes in the spatial slot." |
| Network drops mid-upload of a 1.5 GB album from a studio uplink | Uploads are chunked and resumable; closing the tab does not lose progress. And per personas.md this is the wrong path anyway — the DAW bridge is the right one, and the reason it exists | "Upload paused at 62%. It'll pick up where it left off — you don't have to start again." |
| Analysis **job** fails (the job, not the asset) | **Fail closed**: assets stay unverified, delivery blocked, editing unblocked. 3 attempts, exponential backoff at 30 s / 2 min / 8 min, then the file is marked `Unanalysable` with a manual retry. Never silently dropped, never quietly passed. An unanalysed master is not a conformant master (CX-03) | "We couldn't analyse track 2. Retrying (2 of 3)." → "Track 2 won't analyse. Your release isn't blocked from editing — retry, or replace the file." |
| Asset spec pack for a selected target is unavailable | Partial: checked targets report; unchecked ones say so explicitly. Never reported as a pass (the domain's "never claim more than you know" pattern) | "Checked against 4 of 5 stores — Beatport's asset spec is unavailable, so we don't know about it yet." |
| A partner spec change makes an **already-live** release non-conformant | No notification, by design. There is no action available and the release is not at risk; an alert here is anxiety without a lever (DT-16) | Nothing |
| A partner spec change makes an **undelivered** release non-conformant | Re-derivation from the stored source is attempted first (D-02). If it cannot satisfy the new spec, the release falls back to blocked *for that target* and says why — never a silent failure at delivery | "Apple changed their artwork spec. Your cover still passes. Track 7's master doesn't — here's what changed." |
| Musician self-produces: one human holding both capabilities | The lens is per-capability-held, not per-account (DT-18). They see both views; the plain-language layer stays the default and the technical panel is expandable, sticky per user | Plain-language summary, with "show technical detail" — remembered once expanded |
| Ten files uploaded for a ten-track album; mapping is wrong (tracks 4 and 5 swapped) | Only reachable on the **upload** path. Native releases compose from recordings that already carry their master (12.01.01 D-01), so the mapping does not exist to get wrong. On the upload path, mapping is explicit and confirmed — never inferred silently from filenames (DT-12) | "Match these files to the tracklist" — proposed mapping shown, requires confirmation, durations displayed beside each |
| Every check passes on a file that is the wrong take | **Undetectable, and honestly stated.** Conformance certifies a spec, never the music (DT-11). The only real defence is that the file came from the project rather than a desktop | Asset provenance is shown, not hidden: "From the project on {date}" vs "Uploaded from a device" |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Empty | No assets attached | Upload targets for audio + artwork with the spec floor stated **up front, before the upload** — 3000 × 3000 square RGB; lossless ≥ 16-bit/44.1 kHz. Learning the floor after a failed upload is the punish-don't-teach pattern the domain rejects |
| Loading | Analysis running | Per-file progress. The builder stays fully interactive — audio analysis is minutes, not milliseconds, and must never hold the rest of the builder hostage. Closing the tab is safe; completion notifies |
| Populated | All results in | Per-track technical report + per-target pass/fail, advisories priced with their consequence, technical panel collapsed for the Musician lens |
| Partial | Some tracks analysed, or some spec packs unavailable | Mixed report with explicitly pending rows. Pending is rendered as **pending**, never as a red X — CX-03 exists because a gate that shows unverified as failed trains users to click through it |
| Error | Analysis job failed after 3 attempts | Per-file `Unanalysable` with manual retry and the option to replace. Delivery blocked; editing never blocked |
| Superseded | Asset replaced mid-analysis | In-flight result discarded; new version's analysis starts; no stale result can attach |
| Unverified | Asset version has no current result (new upload, or invalidated by a spec change) | "Not checked yet" — distinct from failed, distinct from passed. The gate treats it as closed, and says so |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | Loudness should be a blocking check to protect release quality | Common distributor behaviour and a tempting "we know better" affordance | ❌ REJECTED — loudness is an **artistic decision**, and DSPs normalise anyway. Blocking it makes the platform an unasked-for mastering critic and would be the single fastest way to lose the Producer persona, who will not tolerate tools that second-guess the room. Advise, never block. The line, which governs this whole feature: **block what a partner will reject; advise what a person might regret.** |
| DT-02 | The platform should generate partner renditions rather than ask the user for each format | Producer persona's unique constraint — "any capture flow requiring them to leave the session will not be used" | ✅ CONFIRMED — asking for 6 encodes is asking the Producer to do the platform's job. Store one high-quality source, derive the rest. Also the only model compatible with spec packs changing after delivery (12.01.02 DT-02) — a spec change becomes a re-derivation, not a re-upload request months later, at which point the file is on a drive at a studio and the answer is silence. |
| DT-03 | Artwork content rules (no URLs, no logos) can be automated | Optimism about vision models | ❌ REJECTED — high-confidence detection of "a URL rendered in stylised type across a photo" is not reliable enough to block on, and a false block on cover art is infuriating in a way a false block on a text field is not. **RESOLVED at this depth — it does not become an admin review step either.** An admin queue is an operational cost that scales with volume, a latency tax on every release, and its actor is a persona that does not exist (ideation-index Q-02). The answer is a **five-statement checklist the Musician attests to**, recorded with actor and timestamp. It costs nothing, it makes a later rejection diagnosable instead of mysterious, and it is the thesis applied to artwork: the platform's job is to record who asserted what, not to adjudicate it. Revisit automation only if a pre-check earns trust in production. |
| DT-04 | Failing Apple Digital Masters is a blocking failure | The surface pass wrote it that way | ❌ REJECTED — factual correction. **ADM is an opt-in badge programme, not a delivery requirement.** Apple Music accepts ordinary 16-bit/44.1 kHz masters. Modelling ADM as a store means a lossy-source advisory would block an Apple delivery that Apple would happily accept — a fabricated rejection, which is worse than a missed one because it destroys trust in every other finding. ADM is an **opt-in conformance target** the artist selects; its failures block that target and nothing else. Generalises: targets are not always stores. |
| DT-05 | An asset failure is a property of the release, so it blocks the release | The natural reading of "blocking" | ❌ REJECTED — asset findings are **per-target**, exactly as metadata findings are per-store (12.01.02 D-01). A global asset verdict is the same lie as a global `valid` flag, and it manufactures the unfixable case: CX-03 worries that a release whose Producer has left becomes permanently stuck. It does not. Drop the target that rejects it, ship to the rest, add it back when a new render exists. Only a failure **every** selected target rejects is terminal — artwork below the floor, digital silence, a corrupt file. That is a small set, and it is the correct one. |
| DT-06 | This feature owns declared-vs-measured checks (duration, explicit flag) | Both are audio facts, so they look like audio checks | ❌ REJECTED — and the boundary generalises. **This feature owns measured-vs-partner-spec. 12.01.02 owns measured-vs-declared.** R-01 already reasons exactly this way about duration ("a metadata rule that happens to read an asset-derived value, not an interaction"). The same logic settles the explicit flag, which nobody had placed: the audio is evidence, the declaration is metadata, and the mismatch is a metadata finding. This feature **measures and publishes**; it never adjudicates a human's claim about their own record. Keeps R-01 true rather than eroding it one field at a time. |
| DT-07 | The platform should auto-fix trivial asset failures — trim silence, resample, pad headroom, normalise | The obviously helpful affordance; every "we fixed it for you" product ships this | ❌ REJECTED for anything touching artistic content, with a concrete casualty: **auto-trimming head/tail silence destroys a continuous-mix album**, and DJ mixes and live records are exactly the releases most likely to trip a silence check. The same reasoning kills auto-crop (choosing what to cut out of a cover is not ours) and auto-normalisation (DT-01). ✅ CONFIRMED only for partner-required transcode inside a rendition — resample and re-encode because the partner's spec demands it, report that you did, and **keep the stored source immutable**. The line: *the platform may translate the master for a partner; it may never improve it.* |
| DT-08 | Fingerprint matching belongs at delivery, alongside Content ID registration | Registration happens at release, so matching looks like a release-time concern | ❌ REJECTED — matching must fire at **asset availability**, which is the earliest moment it is possible and long before a date is announced. The Musician anti-persona's named accidental failure is literally "uploads a stem containing an uncleared sample and exposes every collaborator downstream." Discovering that at delivery means discovering it after the artwork is done, the date is public and the pre-save page is live — the same too-late trap the readiness gate exists to escape (12.01.03 DT-01: the gate is a backstop, and the best moment is always the earliest one). 12.06 owns the match; **this feature owns the trigger**, because it is the first thing in the product that holds the audio. |
| DT-09 | Replacing a master post-release is an asset change, i.e. a heavier version of a metadata update | The surface pass's framing | ✅ CONFIRMED, and materially worse than "heavier". Several DSPs will not accept an audio replacement in place at all — the real mechanism is a **takedown plus a new ISRC**, which forfeits the accumulated stream count, playlist placement and the original release date. That is a career-scale cost hiding behind a button that looks like "replace file". Per the domain's own recurring pattern, the price is shown **at the decision**, itemised as what survives and what does not — never after. This is the single most expensive irreversible action in the sub-domain and it currently has the same affordance as changing a title. |
| DT-10 | Content ID keeps working after a master is replaced | Nobody has thought about it, which is the tell | ❌ REJECTED — an unowned failure sitting between two features. The reference fingerprint is derived from the audio, so a replaced master means the **old fingerprint keeps claiming UGC for audio that is no longer for sale, while the new audio is registered nowhere and claims nothing**. Both halves are silent. Nobody designs for this because it requires holding the master, the fingerprint and the release in one system — which almost nothing does. Replacement must trigger re-registration and state the interim window honestly rather than let the artist believe they are covered. |
| DT-11 | A conformant asset is a correct asset | The implicit promise of every green checkmark in every distributor | ❌ REJECTED — and this is the honest limit of the entire feature. Every check here passes on `mix_v2_rough.wav` as readily as on the master, because a rough and a master are both 24-bit/96 kHz stereo WAVs with plausible loudness. Conformance certifies a **spec**, never the music. The only real defence is **provenance**: the file arrived from the project in 07, witnessed, rather than from a desktop upload with a filename its uploader chose.
