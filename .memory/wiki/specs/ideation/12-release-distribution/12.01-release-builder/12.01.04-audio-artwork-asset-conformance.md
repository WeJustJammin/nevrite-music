# Feature: Audio & Artwork Asset Conformance

> **Number**: 12.01.04
> **Parent**: [Release Builder & Delivery Readiness](./12.01-release-builder-index.md)
> **Status**: [SURFACE]
> **Last updated**: 2026-07-16

## Overview

Checking that the actual media — masters and cover art — meets each target store's technical
specification before delivery, and producing the partner-specific renditions each one wants.
Audio and artwork rejections are slower and more expensive than metadata rejections because the
fix requires going back to the engineer or the designer, not editing a text field.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Producer | Full | **The authoritative persona here.** Uploads or attests the master, sees the technical report (sample rate, bit depth, integrated loudness, true-peak, clipping, DC offset, channel config, spatial/ADM presence), and is the one who can actually fix a failure by re-rendering. Sees which specific store each failure affects. |
| Musician | Config | Sees pass/fail and a plain-language summary, uploads artwork, and chooses whether to accept a warning (e.g. loudness outside the recommended window) or send it back. Does not need the DSP-spec vocabulary — the report must be legible without it. On a self-produced release they act with the Producer lens. |
| Operator | None | Not visible. A studio operator may have *engineered* the master, but they reach this feature under the Producer lens, not as an Operator. |
| Fan | None | Not visible. |

## Behavior

Two asset classes with different failure economics:

**Audio.** Store specs diverge (Apple's Digital Masters programme wants 24-bit/96 kHz where
available; most DSPs accept 16-bit/44.1 kHz WAV/FLAC minimum). Checks are objective and
measurable: format, sample rate, bit depth, channel count, integrated loudness and true-peak,
clipping, silence at head/tail, duration against the declared value. Loudness is **advisory**, not
blocking — DSPs normalise, and an over-compressed master is an artistic choice the platform does
not get to veto. Spatial audio (Dolby Atmos ADM BWF) is a separate deliverable with its own
specification, not a property of the stereo master.

**Artwork.** Objectively checkable: dimensions (3000×3000 minimum is the practical floor),
square aspect, colour space, format, file size. Also subject to **content** rules that are not
mechanically checkable — no URLs, no social handles, no store logos, no pricing, no explicit
imagery without the corresponding flag. These produce warnings the human must resolve, and are a
common late rejection.

Renditions per partner are generated by the platform, not asked of the user. The user supplies
one high-quality source; WeJammin derives what each partner wants.

### Happy Path

1. Producer uploads masters (or the recording arrives from a project in 07 with masters attached).
2. Platform analyses each file and produces a technical report per track.
3. Failures show against the specific stores they affect, with the reason in plain language.
4. Musician uploads cover art; dimension/format checks run immediately, content advisories surface.
5. All blocking checks pass → assets are marked conformant; the gate (12.01.03) sees them as ready.
6. Partner renditions are derived at delivery time from the stored source (12.02.03).

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Master is a lossy source (MP3 upscaled to WAV) | Detectable via spectral analysis; blocking for Apple Digital Masters, warning elsewhere | "This looks like it came from an MP3. Apple will reject it; other stores will accept it." |
| Loudness far outside the recommended window | **Advisory only** | "Integrated −4 LUFS. Streaming services will turn this down; that's a choice, not an error." |
| True-peak clipping | Warning | "Clipping at 3 points. Not blocking, but audible on lossy encodes." |
| Artwork contains a URL or social handle | Not mechanically detectable with confidence; advisory | "Store rules ban URLs and handles on artwork. Check yours." |
| Artwork below 3000×3000 | Blocking | "Cover art must be at least 3000×3000. Yours is 1400×1400." |
| Declared track duration ≠ file duration | Blocking (breaks DDEX message integrity) | "Track 4 is 3:42 but the metadata says 3:38." |
| Spatial mix supplied for some tracks only | Allowed — partial Atmos delivery is normal | "Atmos on 4 of 10 tracks. Apple will take the rest in stereo." |
| Analysis job fails | Assets unverified; delivery blocked; editing unblocked | "We couldn't analyse track 2. Retrying." |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Empty | No assets uploaded | Upload targets for audio + artwork with the spec floor stated up front |
| Loading | Analysis running | Per-file progress; large audio analysis is slow and must not block the rest of the builder |
| Populated | Report available | Per-track technical report + per-store pass/fail |
| Partial | Some tracks analysed | Mixed report with pending rows |
| Error | Analysis failed | Per-file retry |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | Loudness should be a blocking check to protect release quality | Common distributor behaviour and a tempting "we know better" affordance | ❌ REJECTED — loudness is an **artistic decision**, and DSPs normalise anyway. Blocking it makes the platform an unasked-for mastering critic and would be the single fastest way to lose the Producer persona, who explicitly will not tolerate tools that second-guess the room. Advise, never block. The line: block what a **partner** will reject; advise what a **person** might regret. |
| DT-02 | The platform should generate partner renditions rather than ask the user for each format | Producer persona's unique constraint — "any capture flow requiring them to leave the session will not be used" | ✅ CONFIRMED — asking for 6 encodes is asking the Producer to do the platform's job. Store one high-quality source, derive the rest. Also the only model compatible with rule packs changing after delivery (12.01.02 DT-02) — a spec change becomes a re-derivation, not a re-upload request months later. |
| DT-03 | Artwork content rules (no URLs, no logos) can be automated | Optimism about vision models | ❌ REJECTED at this depth — high-confidence detection of "a URL rendered in stylised type across a photo" is not reliable enough to block on, and a false block on cover art is infuriating in a way a false block on a text field is not. Advisory + a human check. Revisit if an automated pre-check earns trust. `[PENDING — Step 5]` for whether this becomes an admin review step. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | Block what a partner rejects; advise what a person might regret | Loudness/artistic choices are not the platform's to veto (DT-01) |
| D-02 | One source in, partner renditions derived by the platform | Producer will not do six encodes; also survives spec changes (DT-02) |
| D-03 | Artwork content rules are advisory, not automated blocks | Detection is not reliable enough to block on (DT-03) |
