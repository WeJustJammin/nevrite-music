# Feature: Metadata Validation & Store Conformance

> **Number**: 12.01.02
> **Parent**: [Release Builder & Delivery Readiness](./12.01-release-builder-index.md)
> **Status**: [SURFACE]
> **Last updated**: 2026-07-16

## Overview

The rule engine that checks a release's metadata against both the DDEX schema and each target
store's additional, undocumented and mutually contradictory house rules — before delivery rather
than after rejection. Metadata rejections are the most common distribution failure and the most
demoralising, because they arrive days later, from a partner the artist has no relationship with,
in language nobody outside a distributor understands.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Full | Sees every validation finding inline on the field that caused it, in plain language ("Apple rejects ALL-CAPS titles" — not "ERR_TITLE_CASE_4021"). Fixes and re-validates without leaving the builder. Sees which specific stores each finding affects, so they can choose to drop a store rather than comply. |
| Producer | Config | Can fix the recording-level fields they are authoritative for — version/subtitle ("Radio Edit", "Live at X"), remixer credit, instrumentation, explicit flag. Cannot alter release-level fields (title, artist, date). Rationale: the Producer knows the recording's truth; the Musician owns the product. |
| Operator | None | Not visible. |
| Fan | None | Not visible. The Fan encounters the *consequence* of bad metadata (wrong artist page, missing credits on the DSP) but never the validator. |

## Behavior

Validation runs at three severities, and the distinction matters more than the rules themselves:

| Severity | Meaning | Effect |
|---|---|---|
| **Blocking** | Will be rejected by a selected store, or violates DDEX schema | Delivery impossible until fixed |
| **Warning** | Accepted, but degrades outcome — no editorial eligibility, poor algorithmic placement, likely wrong-artist-page | Delivery allowed; warning recorded |
| **Advisory** | Style/consistency; the release will be fine | Informational |

Rules are **per-store**, not global — a finding is always scoped to the stores it affects. This is
the core design constraint: Apple, Spotify, Beatport and Amazon disagree, and a global "valid"
flag is a lie. Representative real divergences (not exhaustive — `[PENDING — Step 5]` for the
full matrix): title casing, permitted characters in the version field, whether featured artists
must appear in the track title or only in the artist list, explicit-content declaration
requirements, genre taxonomies that do not map onto each other.

Rule packs must be **versionable and updatable without a release of WeJammin** — partner rules
change without notice and with no changelog. A hardcoded ruleset is guaranteed stale.

### Happy Path

1. Musician completes composition (12.01.01); validation runs continuously in the background.
2. Findings appear inline on the offending field, grouped by severity, each tagged with the stores
   it affects.
3. Musician clicks a finding; the builder focuses the field and explains the rule in plain language
   with a concrete example of a compliant value.
4. Musician fixes it; the finding clears live.
5. Zero blocking findings → the release advances to the Delivery Readiness Gate (12.01.03).

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Two selected stores have contradictory rules for one field | Cannot be satisfied simultaneously; requires a per-store metadata variant or dropping a store | "Apple and Beatport want different things here. We can send each its own version, or you can remove Beatport." |
| Rule pack is stale — store rejects something that validated clean | Rejection returns via 12.03.03 and is fed back as a **new rule** | "Apple rejected this for a rule we didn't know about. We've updated our checks — here's the fix." |
| Musician removes a store to dodge a finding | Allowed; finding disappears; recorded | Finding greys out with "no longer applies — Beatport removed" |
| Non-Latin script title with no transliteration | Warning, not blocking — several stores require a transliteration for search | "Add a Latin transliteration or this won't be findable on {stores}" |
| Validation service unavailable | Delivery blocked, editing not blocked | "We can't check against store rules right now. Your work is saved; we'll re-check automatically." |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Loading | Validation running | Inline "checking…" on fields; no blocking spinner over the form |
| Clean | Zero findings | Green summary: "Passes all checks for {N} stores" |
| Populated | Findings exist | Grouped findings panel, blocking first, each scoped to stores |
| Partial | Some store rule packs unavailable | "Checked {N} of {M} stores — {store} rules unavailable" |
| Error | Validation service down | Non-destructive banner + auto-retry |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | Validation can be a single global ruleset with a `valid` boolean | Simplest model | ❌ REJECTED — partner rules genuinely contradict each other. A global boolean forces the union of all rules (over-strict, blocks valid deliveries) or the intersection (under-strict, guarantees rejections). Findings must be per-store scoped, and the delivery decision must be per-store too — which is exactly why 12.03 tracks status per store rather than one `released` flag. |
| DT-02 | Rule packs must be data, versioned and hot-updatable — not code | Partner rules change silently and without changelogs; the rejection feedback loop from 12.03.03 must be able to *write a new rule* | ✅ CONFIRMED — this makes the distributor's hardest-won asset (accumulated rejection knowledge) a first-class product artifact rather than tribal knowledge. It is also a compounding moat: every rejection any WeJammin user hits improves validation for all of them. |
| DT-03 | Error messages can pass through the partner's own text | Cheapest implementation | ❌ REJECTED — DSP rejection text is written for distributors, not artists ("DELIVERY_ERR: invalid PLine format"). Per `specificity-standards.md` and the Musician persona (not a metadata professional), every finding must be translated to plain language with a compliant example. Untranslated partner errors are the reason artists believe distribution is a black box. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | Findings are per-store scoped; no global valid flag | Partner rules contradict (DT-01) |
| D-02 | Rule packs are versioned data, not code | Partner rules change without notice; rejections must write rules (DT-02) |
| D-03 | All partner errors are translated to plain language with a compliant example | Musician is not a metadata professional (DT-03) |
