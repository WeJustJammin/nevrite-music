# Feature: Release Composition & Track Sequencing

> **Number**: 12.01.01
> **Parent**: [Release Builder & Delivery Readiness](./12.01-release-builder-index.md)
> **Status**: [SURFACE]
> **Last updated**: 2026-07-16

## Overview

The release object itself: what type of release this is (single / EP / album / compilation), which
recordings it contains, in what order, on which disc or side, and which project each recording
came from. This is where a finished WeJammin project (domain 07) becomes a commercial product
with a shape a DSP will accept, and where the contributor roll-up that the readiness gate depends
on is assembled.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Full | Creates the release, picks its type, pulls in recordings from their projects (07) or uploads standalone masters, drags to sequence, sets disc/volume grouping, marks a track as the focus/single, and names the primary and featured artists per track. Sees the live contributor roll-up assembled from each recording's credits (02) and the running count of what still blocks delivery. |
| Producer | Config | On a release they do not own: sees the composition read-only but can **correct the recording-level facts they are authoritative for** — which take/master version is the correct one, instrument and role credits for the session they ran, whether a track is an alternate mix vs a distinct recording. Cannot re-order, re-title or change release type. On their own release, they act with the Musician lens. |
| Operator | None | Not visible. A venue/studio operator has no relationship to a release object. A live-album master recorded at their room reaches this feature as a recording contributed by a Musician, not as an Operator action. |
| Fan | None | Not visible. The Fan sees the *result* of composition (tracklist, order, features) only after delivery, via domains 20/21 and the DSP itself. |

## Behavior

A release is a container of **recordings**, not of files. A recording is the canonical entity that
carries the ISRC, the credits (02) and the splits (09) — the same recording can appear on a single,
then an album, then a compilation, without duplicating or forking its provenance. This distinction
is the whole reason the release layer can be thin and the provenance layer can be authoritative.

Release type constrains shape: DSPs enforce their own rules (a "single" is typically ≤3 tracks
and/or ≤30 minutes; an "EP" and an "album" are distinguished differently by Apple and Spotify).
The builder should surface the constraint at the moment of the choice rather than at validation.

### Happy Path

1. Musician creates a release and picks a type (single / EP / album / compilation).
2. Builder offers recordings the Musician has a rights position on — sourced from their completed
   projects (07) — plus a direct upload path for masters made off-platform.
3. Musician adds recordings; the builder assembles the contributor roll-up per track from each
   recording's existing credits (02) and shows the split status for each.
4. Musician sequences the tracklist (drag), sets disc/volume grouping if multi-disc, marks the
   focus track.
5. Musician sets primary artist(s) for the release and per-track featured artists.
6. Builder shows a live readiness summary — what is complete, what blocks delivery (12.01.03).

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Recording already released on an earlier WeJammin release | Allowed — the recording is reused, ISRC is preserved, not reissued. Release-level UPC is new. | Badge: "Previously released on {release} · ISRC reused" |
| Recording has no rights position for this Musician | Cannot be added | "You don't hold a rights position on this recording. Ask {owner} to add it to their release, or resolve ownership in Rights." |
| Track count/duration violates the chosen release type's DSP rules | Blocks at type level, not at delivery | "Spotify classifies 4+ tracks over 30 min as an EP, not a single. Change type or remove a track." |
| Two tracks are the same recording (duplicate add) | Rejected | "This recording is already track 3." |
| Alternate mix added as a separate track | Allowed but flagged — it is a **distinct recording** needing its own ISRC | "Alternate mixes need their own ISRC. We'll assign one at delivery." |
| Compilation with contributors who are not WeJammin users | `[PENDING — /ideate-discover Step 5 deepening]` — depends on Q-02 in the parent index | — |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Empty | New release, no recordings | Empty state: "Add recordings from your projects, or upload masters" + both CTAs |
| Draft | 1+ recordings, not yet valid | Tracklist + live readiness summary with blocking items |
| Loading | Pulling recordings/credits roll-up | Skeleton tracklist rows |
| Ready | All validation and gate checks pass | Tracklist with green readiness state + "Schedule delivery" CTA |
| Locked | Delivered to 1+ stores | Read-only tracklist; edits route to 12.05.02 (update & redelivery) |
| Error | Roll-up fetch failed | Per-row error with retry; release is not blocked from editing |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | A release should contain **recordings**, not audio files — so the same recording can appear on single→album→compilation carrying one ISRC and one provenance chain | Industry standard (ISRC is per recording, UPC per release); D-10 requires WeJammin to own the chain of title end-to-end | ✅ CONFIRMED — a file-centric model forks provenance on every reissue, which is precisely the reconstruction failure in problem-statement.md |
| DT-02 | The builder should let a Musician add **any** recording they have credits on | Naive read of "credits = access" | ❌ REJECTED — a **credit** is not a **rights position**. A session drummer is credited on a master they do not own and cannot distribute. Conflating them would let a contributor release someone else's record. Gate on rights (09), display credits (02). This distinction is invisible in every competitor and is a real source of disputes. |
| DT-03 | Release type is cosmetic metadata | Assumption | ❌ REJECTED — type drives DSP classification, editorial eligibility, and chart eligibility, and DSPs disagree on the boundaries. It must be a validated, constraint-surfacing choice, not a dropdown. |
