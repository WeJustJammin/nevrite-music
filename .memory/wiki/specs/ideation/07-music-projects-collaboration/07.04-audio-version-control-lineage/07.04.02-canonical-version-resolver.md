# Feature: Canonical Version Resolver

> **Number**: 07.04.02
> **Parent**: [Audio Version Control & Lineage](./07.04-audio-version-control-lineage-index.md)
> **Status**: [SURFACE]
> **Last updated**: 2026-07-16

## Overview

The single authoritative answer to "which one is the real one?" — held **per purpose**, not as one "latest" flag.
The canonical rough is v3, the canonical mix is v7, the canonical master is v9; most versions are canonical for
nothing. This is the smallest feature in the sub-domain and arguably the highest-value one in the entire domain:
`Mix_FINAL_v3_ACTUAL.wav` is not a naming problem, it is a **missing pointer** over a set of files that already
exists. Everyone has the files. Nobody has the answer.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Full | **Decides** which version is canonical for each purpose. This is the one place in the sub-domain where the artist outranks the producer, and correctly so — "is this the mix?" is an artistic judgement, not a technical one. Sees at a glance which version everyone should be listening to. |
| Producer | Full | Nominates canonicals (usually the actual doer) and is bound by them: the handoff package (`07.08.01`) builds from the canonical, not from whatever is newest in the folder. Can be restricted to nominate-only where the owner reserves the decision. |
| Operator | None | Not their business. |
| Fan | None | Not visible. The canonical master eventually becomes the released recording via domain 12 — the Fan meets the *output*, never this pointer. |

## Behavior

The resolver holds a small set of named pointers into the timeline (`07.04.01`), one per purpose:
`rough`, `mix`, `master`, and any deliverable variants (`07.07.02`). Nominating a version writes a pointer.
Pointers are mutable — that is the difference between the resolver and the timeline, and the reason they are
separate features.

Three properties do the work:

**"Latest" is deliberately not offered.** Auto-canonical-on-upload would be a one-line feature that recreates
the entire problem: the newest bounce is very often a experiment, an alternate, or a mistake. The pointer moves
only when a human says so. **The friction is the feature.**

**Nomination is loud.** When the canonical mix changes, everyone on the roster is told. Today this information
travels by WhatsApp — "use the new one" — and gets lost, and someone masters the wrong mix. The notification is
one of the most valuable things the product sends.

**Pinned references do not follow the pointer.** A release membership pins a specific version (`07.01.02` D-03).
Re-nominating the canonical master does *not* silently change what an assembled release will ship — it surfaces
the difference and asks.

### Happy Path

1. Producer uploads v7; the roster is notified a new mix exists; **the canonical does not move**
2. Musician A/Bs v6 against v7 (`07.04.06`) and decides v7 is the one
3. Musician nominates v7 as the canonical mix
4. Everyone on the roster is notified: "the mix is now v7"
5. Every unpinned downstream consumer — the handoff package builder, the review link, the stem export target — now resolves to v7 automatically. The mastering engineer cannot master the wrong mix by accident.

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Canonical nominated, then the version fails an integrity check (`07.04.05`) | **Alarm, not silent fallback.** A canonical that has gone bad is a five-alarm event; silently reverting to v6 would hide it. | "The canonical master failed its integrity check" — prominent, to the owner and the producer |
| Two people nominate different versions for the same purpose concurrently | Last write wins with a loud, attributed notice. Silence would recreate exactly the confusion this feature exists to end. | "Alex made v8 canonical 30 seconds after you made v7" |
| No canonical nominated; a downstream consumer asks for "the mix" | Refuses to guess. Guessing is the failure mode. | "No canonical mix has been chosen" with a picker — the handoff builder blocks here |
| Canonical master re-nominated after a release was assembled | Release does **not** move (pin, `07.01.02` D-03); difference surfaced | "This release ships v7. The canonical master is now v9. Update?" |
| Version that is canonical for a purpose is superseded by a newer version | Nothing automatic. The newer version is just a version until someone blesses it. | New version listed; canonical badge unmoved |
| Someone nominates a `rough` as the canonical `master` | Allowed with a confirm — type is advisory, and unusual things happen in real records | "v3 is typed as a rough. Make it the canonical master anyway?" |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Unset | No canonical for a purpose | "No canonical mix yet" — an honest empty state, never a guess |
| Set | Canonical nominated | Badge on the version; resolver panel shows all purposes at a glance |
| Stale | Newer versions exist beyond the canonical | Canonical badge plus "3 newer versions" — informational, never automatic |
| Conflicted | Concurrent nomination | Last write shown with an attributed notice |
| Compromised | Canonical failed integrity | Alarm state; blocked from handoff (parent CX-04) |
| Error | Fetch failed | Error with retry |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | The canonical pointer must be **per purpose**, not a single "latest" or "final" flag | A song simultaneously has a canonical rough (for the label), a canonical mix (for the mastering engineer), and a canonical master (for the release) — and they are three different files, live at the same time, needed by three different people. A single flag forces the exact hack it is meant to prevent: users encode purpose in the *filename*, and `FINAL_v3_ACTUAL` is reborn inside the platform. | ✅ CONFIRMED — per-purpose pointers are the whole design. The failure this feature addresses is not "too many files", it is "no answer to which file". |
| DT-02 | Canonical should update automatically on upload, since the newest bounce is usually the best one | The obvious convenience feature, and it is one line of code | ❌ **REJECTED — and this rejection is the feature.** The newest bounce is very often an experiment, an alternate for comparison, or a mistake. Auto-canonical means the mastering engineer picks up the producer's 3am "what if the drums were louder" test. The pointer must move only by a deliberate human act, and the *friction is the point*: an act with consequences should require an act. This is precisely the discipline the industry lacks and why the disease persists. |
| DT-03 | Because the canonical resolves for everyone, downstream consumers should always resolve live rather than pin | Consistency instinct — one answer, everywhere | ❌ REJECTED — for **releases**, live resolution is catastrophic. A release that silently changes its master because someone re-nominated is the `FINAL_v3` disease with commercial consequences. The rule is a split by consequence: **transient consumers resolve live** (review links, handoff drafts, "what should I be listening to"), **committed artifacts pin** (release memberships, delivered packages, approved sign-offs). Where a pin diverges from the canonical, surface it and ask — never move silently, never leave it hidden. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | Pointers are **per purpose** (`rough`, `mix`, `master`, variants) | Per DT-01 — a single flag forces purpose into filenames and rebuilds the disease inside the product. |
| D-02 | **No auto-canonical on upload.** The pointer moves only by deliberate human act | Per DT-02 — the friction is the feature. |
| D-03 | Transient consumers resolve **live**; committed artifacts **pin** | Per DT-03 — split by consequence, not by consistency preference. |
| D-04 | Canonical changes notify the roster **loudly** | This information currently travels by WhatsApp and gets lost, and someone masters the wrong mix. |
| D-05 | A compromised canonical **alarms**; it never silently falls back | Silent fallback would hide the highest-blast-radius failure in the domain. |
| D-06 | With no canonical set, the system **refuses to guess** | Guessing is the failure mode this feature exists to eliminate. |
