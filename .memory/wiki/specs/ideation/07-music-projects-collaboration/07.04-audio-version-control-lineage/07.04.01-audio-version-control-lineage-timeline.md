# Feature: Audio Version Control, Lineage & Immutable Timeline

> **Number**: 07.04.01
> **Parent**: [Audio Version Control & Lineage](./07.04-audio-version-control-lineage-index.md)
> **Status**: [SURFACE]
> **Last updated**: 2026-07-16

> **Merged from sweep candidates 09 ("Audio Version Control & Lineage") and 11 ("Immutable Version Timeline &
> Change Summary")** per sub-domain D-01 — version control *is* the immutable timeline; the change summary is a
> property of a version, not a separate system.

## Overview

An append-only timeline of every bounce a song accumulates, each version knowing what it came from, who made it,
when, and what changed. It is the direct answer to `Mix_FINAL_v3_ACTUAL.wav` — an industry-wide failure that is a
joke until the wrong master ships. It is deliberately **not Git for audio**: there is no branching, no merging,
no conflict resolution, because audio cannot be merged (sub-domain D-03). What it provides is lineage, identity
and an immutable record.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Read-only | Sees the whole timeline of their song — every mix, who bounced it, when, what changed. Cannot create versions (they come from the DAW) and cannot delete them. This is often the first time an artist has ever seen the actual history of their own record rather than a folder of ambiguously-named files. |
| Producer | Full | Creates versions, usually via the DAW bridge (`07.09`) rather than by uploading. Writes or confirms the change summary. Sets lineage when the system cannot infer it. The heaviest user of this feature by a wide margin. |
| Operator | None | A studio operator has no access to a client's version history. |
| Fan | None | Not visible. The history of a record is professional information — and often unflattering. |

## Behavior

A version is an audio asset plus its lineage (`derived from v6`), its author, its timestamp, its type
(`rough / mix / master / stem set / comp`), and a change summary. Versions are **immutable and append-only**
(D-02): no edit, no delete, no rewrite. That is what makes the timeline a *record* rather than a document, and
what makes it usable as evidence in a dispute (domain 24).

Lineage should be **inferred, not typed**. A producer who must fill in "this came from v6" will not, and the
lineage will be wrong within a week. The DAW bridge (`07.09`) knows the parent because it knows the session that
produced the bounce; where the bridge is absent, the system infers from timing, filename and audio similarity,
and asks only when genuinely uncertain.

The change summary is the honest weak point. "What changed between v6 and v7" is a question the system can only
partially answer — it can detect measurable deltas (length, loudness, a stem appearing) but not *intent*
("brought the vocal up, tamed the 3k"). See DT-02.

### Happy Path

1. Producer bounces a new mix in their DAW into the watched folder (`07.09.01`)
2. System ingests it, infers the parent (v6, same session, same song), computes measurable deltas, creates v7
3. Producer is prompted — non-blockingly — "what changed?"; types "vocal up 1dB, de-essed"
4. Roster is notified that a new mix exists; the canonical pointer does **not** move automatically (`07.04.02`)
5. Anyone can now A/B v6 against v7 (`07.04.06`), and the timeline permanently records who made what, when

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Same file uploaded twice | Detected by checksum; no duplicate version created | "This is identical to v6" |
| Bounce uploaded with no discernible parent (first version, or a mix from another studio) | Version created as a **lineage root**. Roots are legitimate, not errors — work arrives from outside the platform constantly. | Version shows "no parent" without alarm |
| Lineage inferred wrongly | Correctable by the Producer. The correction is itself recorded — you cannot quietly rewrite history. | "Parent changed from v6 to v5 by Producer" in the timeline |
| Version uploaded by someone who then leaves the roster | Version and authorship persist (`07.03.01` D-05) | Author still shown |
| 200 versions on one song | Normal for a heavily-worked record and not a defect. Timeline needs filtering by type and canonical status, not a cap. | Filtered views; canonical versions pinned prominently |
| Storage cost of every version forever (sub-domain Q-02) | `[PENDING — /ideate-discover Step 5 deepening]` — the immutability promise (D-02) and multi-GB stem packs collide directly | — |
| Two producers bounce simultaneously from different sessions | Both land as siblings of the same parent. **This is the correct outcome, not a conflict** — parallel mixes are real. Resolution is by choosing (`07.04.02`), never merging. | Two versions shown as siblings |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Loading | Timeline opened | Version row skeletons |
| Empty | No versions | "No audio yet" + upload/bridge CTA |
| Populated | Versions exist | Timeline with lineage, authors, change summaries, canonical badges |
| Ingesting | Upload/bridge in progress | Progress with an optimistic entry; large stem packs take real time |
| Processing | Uploaded, deltas/waveform being computed | Version exists and is playable; derived metadata fills in behind it |
| Integrity failed | Checksum or media check failed (`07.04.05`) | Version flagged, ineligible for canonical (parent CX-04) |
| Error | Fetch failed | Error with retry |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | Lineage must be **inferred from the DAW bridge**, not entered by hand — hand-entered lineage is wrong within a week | `meta/personas.md` Producer constraint: "any capture flow requiring them to leave the session and go fill in a web form will not be used." Lineage is exactly such a form, and it is the highest-frequency one: it recurs on every bounce, several times a day. Frequency is what makes manual entry fatal here. | ✅ CONFIRMED — this feature is **structurally dependent on `07.09` (DAW Bridge)**. Without the bridge, versions arrive as manual uploads with guessed lineage, and the timeline degrades into a slightly better Dropbox. This is a hard dependency that MoSCoW must respect: shipping this without the bridge delivers much less than it appears to. |
| DT-02 | The system can auto-generate a useful **change summary** by analysing the audio diff | The candidate name ("Change Summary") implies it, and it is technically feasible to compute loudness/spectral/length deltas | ⚠️ **PARTIALLY REJECTED** — the system can detect *measurable* deltas ("2.1 LU louder, 4 s longer, a stem appeared") but not *intent* ("brought the vocal up, tamed the 3k"). Measurable deltas are genuinely useful as a **cheap sanity check on the human's summary** — if the producer says "tiny vocal tweak" and the file is 3 LU louder and 8 seconds shorter, something is wrong and that is worth catching. But it cannot replace the human note, and presenting spectral deltas *as* a changelog would be technically impressive and practically useless. Ship both: machine facts as a check, human note as the summary. |
| DT-03 | Immutability (D-02) is compatible with the platform's storage economics | Assumed when D-02 was made | ❌ **REJECTED as stated** — this is the sub-domain's most serious unresolved tension and it deserves naming rather than hiding. Every version of every stem pack of every song, forever, is a very large bill for a solo-built platform (`meta/problem-statement.md`: "buildable without a platform team"). But D-02 is not decorative — a mutable history is not a record, and the product's promise is that the record survives. The likely resolution is **tiering, not deletion**: the *record* of a version (its existence, lineage, author, checksum, change summary) is immutable and cheap; the *audio bytes* may move to cold storage or, past some horizon, be dropped for non-canonical versions with the record retained as a tombstone. That preserves the provenance claim while bounding cost. Escalated as sub-domain Q-02 — it is a product and pricing decision, not an agent's call. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | Versions are **immutable and append-only** — no edit, no delete | Sub-domain D-02. A mutable history is not a record. Tension with storage cost is real and named in DT-03, not hidden. |
| D-02 | **No branching, no merging** — parallel versions are siblings, resolved by choosing | Sub-domain D-03 and parent rejected-pair R-01. The Git analogy is seductive and wrong. |
| D-03 | Lineage is **inferred**, and only asked for when genuinely ambiguous | Per DT-01 — a prompt on every bounce is a prompt that gets dismissed. |
| D-04 | Change summary = **machine-measured deltas + a human note**, with the deltas used as a sanity check on the note | Per DT-02 — neither alone is sufficient. |
| D-05 | Lineage roots (versions with no parent) are legitimate, not errors | Work arrives from outside the platform constantly; treating roots as broken would insult the majority of real inputs. |
| D-06 | Lineage corrections are **recorded**, never silent | You cannot quietly rewrite history in a system whose value is that history is trustworthy. |
