# Feature: Alternate Version Matrix

> **Number**: 07.07.02
> **Parent**: [Mix & Master Workflow](./07.07-mix-master-workflow-index.md)
> **Status**: [SURFACE]
> **Last updated**: 2026-07-16

## Overview

Every real record needs more than one version of itself: an instrumental (for sync and for live), a clean version
(for radio and for playlists), a radio edit (shorter), a TV mix (vocals down, everything else up), an a cappella,
sometimes a sped-up or extended cut. The matrix is the declaration of which variants a song needs and the record
of which exist. It matters because variants are **cheap during the mix and brutally expensive afterwards** — and
because they are almost always requested afterwards.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Config | Declares which variants they need — partly an artistic call and mostly a commercial one (a sync agent will ask for an instrumental; a playlist will require a clean version). Does not produce them. Sees which exist and which are missing. |
| Producer | Full | Produces the variants and carries the workload the matrix defines. A mixer who knows the matrix up front keeps the session structured for it; one who learns later recalls the session, and the recall may be impossible (`07.06.03` DT-01). |
| Operator | None | Not their business. |
| Fan | None | Not visible here. A fan meets an instrumental as a released track via domain 12/20 — not as a matrix cell. |

## Behavior

The matrix is `song × variant type → version`. Each cell either holds a version (`07.04.01`) or is empty. Variant
types are a fixed music vocabulary (`instrumental`, `clean`, `radio edit`, `TV mix`, `a cappella`, `extended`),
because — exactly as with the stage board (`07.01.03` D-01) — a fixed vocabulary is what lets the system know what
a thing *is* and therefore validate it.

Two properties matter:

**The matrix should be declared in the brief, up front** (parent CX-05). A variant produced during the mix is
nearly free; the same variant nine months later means recalling the session, finding the plugins still work, and
hoping the mix engineer is available and remembers. This is the feature's whole argument.

**Every variant needs a master, treated identically to the primary** (parent CX-02). This is the multiplier and
the most expensive interaction in the sub-domain — the standard industry failure is an instrumental mastered
separately, later, that audibly does not match.

### Happy Path

1. At brief time, the artist declares: instrumental + clean version needed (their distributor requires clean; their sync agent wants instrumentals)
2. Matrix shows two required cells, both empty
3. Mix engineer, knowing this up front, keeps the session structured — vocals on their own busses, no vocal bleed into the master chain
4. At mix-down they bounce all three (primary, instrumental, clean) from the same session in one pass
5. All three go to mastering together and get the identical chain (parent CX-02) — so the instrumental sounds like the record

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Variant requested **after** mastering completes | The expensive case. Triggers a recall (`07.06.04`) and a re-master, and it may be impossible if the environment drifted (`07.06.03` DT-01) | "This needs a session recall — the mix session is from 14 months ago" with the drift warning |
| Clean version needed but the mix has vocal bleed on the master bus | A genuine craft failure that the null test (`07.04.04` DT-01) can detect at stem level | "Vocals appear in the instrumental — the master bus may have vocal processing" |
| Variant exists but was mastered separately | The standard failure (parent CX-02). Detectable by comparing loudness/tonal profile against the primary. | "The instrumental is 1.8 LU quieter than the primary master" |
| Primary master re-done; variants now stale | Lineage marks them stale (`07.04.01`); they must be re-derived | "3 variants are from the previous master" |
| A variant is really a different arrangement (an "acoustic version") | **Not a variant — a different recording.** Belongs in the timeline as its own lineage, possibly its own Song (`07.01.01` Q-01) | "This looks like a new recording, not a variant. Create a version instead?" |
| Sped-up/slowed versions for social platforms | A real 2026 deliverable that would have been absurd five years ago | Supported as a variant type — see DT-03 |
| Instrumental for live playback vs for sync | Different requirements (live wants click and cues; sync wants a clean bed) — the same word means two things | `[PENDING — Q-01, /write-be-spec]` |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Undeclared | No matrix set | "No alternate versions declared" — a valid state; many songs need none |
| Declared | Variants required | Matrix with required cells, empty |
| Partial | Some variants produced | Matrix with filled and empty cells |
| Complete | All declared variants exist and are mastered | Full matrix |
| Stale | Primary master changed | Variants flagged as derived from a superseded master |
| Mismatched | Variant's loudness/profile differs from the primary | Advisory naming the discrepancy |
| Error | Fetch failed | Error with retry |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | The matrix's value is **timing, not tracking** — its job is to move the variant decision earlier | The tracking half is trivial (a grid of which files exist) and worth little. The real cost is temporal: a variant bounced during the mix is a fifteen-minute job; the same variant nine months later means recalling the session (`07.06.04`), hoping the environment still loads (`07.06.03`), finding the engineer, and re-mastering to match (parent CX-02) — days of work and real risk of failure. **Almost every variant is requested late**, because the artist does not know they need an instrumental until a sync opportunity appears. | ✅ CONFIRMED — this reframes the feature from a checklist into a **prompt at brief time** (parent CX-05): "will you ever need an instrumental?" asked once, in week one, is worth more than the entire grid. It is the same principle as `07.06.02` — the value is in asking at the moment it is cheap, and the moment is early. |
| DT-02 | Variants are alternates of the same recording, so the matrix can be a simple grid | The obvious model, implied by the candidate's name | ⚠️ **PARTIALLY REJECTED — the boundary between "variant" and "new recording" is real and the grid hides it.** An instrumental is genuinely the same recording minus a bus. A radio edit is the same recording, shortened. But an "acoustic version" is a *different recording* — different performance, different session, its own credits, its own ISRC — and users will absolutely try to put it in this grid because the word "version" invites it. Getting this wrong pollutes the recording model (`07.01.01` Q-01) at its most sensitive point. **The test is whether it came from the same mix session**: if yes it is a variant, if no it is a recording. The system should apply that test and push back when a user tries to file a new recording as a variant. |
| DT-03 | The variant vocabulary is stable and can be fixed | The parallel to `07.01.03` D-01's fixed stage vocabulary, which was correct there | ⚠️ **PARTIALLY REJECTED — the vocabulary is fixed in *shape* but not in *membership*, and it moves faster than the domain's other vocabularies.** Sped-up and slowed variants for short-form video did not exist as deliverables five years ago and are now routine and commercially material. Whatever platform matters in three years will demand something not on today's list. Stage names are craft and change on a decade scale; variant types are **distribution artifacts** and change on a platform's whim. So: ship a fixed set with a defined extension path, and expect to add rows — unlike the stage board, where extensibility was correctly rejected. Same-looking decision, opposite answer, because the underlying thing changes at a different rate. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | The matrix is **declared at brief time**, and the prompt is the feature | Per DT-01 and parent CX-05 — asking once in week one beats the whole grid. |
| D-02 | Variant types are a **fixed vocabulary with a defined extension path** | Per DT-03 — unlike the stage board, distribution artifacts change on a platform's whim. |
| D-03 | A thing from a **different mix session is a recording, not a variant** — the system applies the test and pushes back | Per DT-02 — the grid invites users to pollute the recording model at its most sensitive point. |
| D-04 | Every variant is mastered **in the same pass, in the same chain** as the primary | Parent CX-02 — the standard industry failure is exactly the opposite. |
| D-05 | Undeclared is a valid state — many songs need no variants | The feature must not imply every song owes a matrix. |
