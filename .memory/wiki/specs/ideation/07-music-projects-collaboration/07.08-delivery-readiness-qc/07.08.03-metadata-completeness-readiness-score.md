# Feature: Song Metadata Completeness & Readiness Score

> **Number**: 07.08.03
> **Parent**: [Delivery, Readiness & QC](./07.08-delivery-readiness-qc-index.md)
> **Status**: [PARTIAL]
> **Last updated**: 2026-07-23

## Overview

The answer to "is this song actually ready?" — asked always against a **specific destination**, never in the
abstract. It is where the domain's **completeness debt** finally becomes visible: every capture prompt anyone
dismissed at `07.01.03` and `07.06.02` shows up here, at the moment it matters, having blocked nobody along the
way. It is the load-bearing counterpart to the domain's non-blocking principle — the reason "never block" does
not mean "never notice".

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Full | "Can I release this?" is their question and this is the feature that answers it. Sees an actionable gap list, not a number — "you need splits from Sam and an ISRC" beats "76%". This is also where they discover that the thing they thought was finished is missing the one fact that will matter in five years. |
| Producer | Full | "Can I hand this off?" is theirs. Sees readiness per destination and is usually the one who can close the gaps. |
| Operator | None | Not their business. |
| Fan | None | Not visible. |

## Behavior

Readiness is computed **against a target** (parent CX-04): ready-for-mix-handoff, ready-for-mastering,
ready-for-DSP-release, ready-for-sync-pitch. Each target has a spec; the score is the gap list against it.

**P-05 (D-07): a target's facts come from whoever owns them.** This is `07.08.01` D-06 applied to targets —
the score's targets and the handoff builder's recipient specs are **one list under two names**, so they take one
ownership rule rather than two:

| Target | Fact source | Status today |
|---|---|---|
| ready-for-mastering | `07.08.01` **authors** (P-04 D-06) | Spec owned here; fact list still to be written |
| ready-for-mix-handoff | `07.08.01` **authors** (P-04 D-06) | Spec owned here; fact list still to be written |
| ready-for-DSP-release | **References domain 12** — `12.01.03`'s condition families, with its severities consumed as this feature's D-02 weights | Available now; the only fully scoreable target |
| ready-for-sync-pitch | **References domain 11** — `11.02.01`'s clearance verdict | Partially available; no pitch-readiness requirement set exists yet |
| archive, engagement-purchased, `live`, `remix` | No target — no owner (`07.08.01` Q-04) | Not offered |

**A target with no owned spec is simply not offerable** — the same treatment `07.08.01` gives an undefined
recipient spec. Nothing blocks, nothing is faked, and no placeholder target is advertised. Readiness therefore
ships **per target as each becomes available**, which is a build-order consequence, not a gate on any user.

**Referenced severities are consumed, never re-derived.** Where an owning domain classifies a fact's consequence,
this feature uses that classification as its weight. Re-deriving one would be a second copy of a third-party
requirement, which `07.07.03` D-04 forbids — and consequence belongs to whoever owns the harm, per domain D-05
("measure and show; never judge").

The inputs span the whole domain: credits captured or not (`07.06.02`), splits agreed or open (`07.06.02` D-03),
sources declared (`07.08.04`, parent CX-02), QC results (parent CX-03), canonical set (`07.04.02`), ISRC/ISWC
present (ISRC/UPC from `12.07`; ISWC captured and reconciled by `09.06.01`, which does not issue it).

Two properties define it:

**Gaps are weighted by consequence, not counted.** An undeclared sample can expose every collaborator
(`meta/personas.md`); a missing BPM inconveniences a search index. Treating them as equal percentage points would
be an act of false precision that misleads exactly when it matters.

**It never blocks** (domain `D-04`, "non-blocking is absolute") — and per Q-01, now resolved, that holds without
exception. Where the consequences are external and irreversible the gate exists but belongs to someone else:
domain 12 may hold a release (D-08 — "12 may gate, 07 may not"), and `07.08.05` D-04 holds a remix publication on
source-declaration verification. Neither is this score.

**Pin vs live, settled (D-08).** This score and the handoff package are not one object with two lifetimes; they
are a **view** and a **record** over one target-spec store:

- The **score is a live view** — it re-evaluates against the current spec version, so a previously-ready song can
  honestly revert (see the edge case below). It is never a stored counter.
- The **package is a pinned record** — per `07.08.01` D-03 it pins its contents, and it additionally pins the
  **spec version** it validated against, so "what was sent, and what it was checked against" is reproducible forever.

One store, one version identity, two projections. Domain 12 resolved this exact shape by dissolving it rather
than arbitrating it (`12.02.02` D-01, `12.01.02` D-07/DT-09: "a store has one version number, so pinning one pins
both"). What 07 does **not** copy is domain 12's authority to hold dispatch — 12 may gate, 07 may not. Here a
moved spec re-evaluates and **names the fact that moved**.

### Happy Path

1. Musician opens their song and selects "ready to release?"
2. Score resolves against the DSP release spec: 4 of 7 requirements met
3. Gap list, ordered by consequence: **splits not agreed** (Sam and Alex have not confirmed); no ISRC; one source undeclared
4. Each gap is a link to the thing that closes it — the split gap opens the capture prompt with the same pre-fill it had at session close (`07.06.02`)
5. Gaps close; readiness flips; the "this song is ready to release" notification is one of the genuinely good ones

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Readiness depends on a fact the viewer cannot see (a split they are not party to) | Says incomplete **without disclosing what** — awkward and necessary (parent CX-04) | "Waiting on information you don't have access to" |
| Musician picks a target whose owning domain has not finished its spec (sync today) | The target is offered only for the parts its owner has published; unpublished requirements are named as pending rather than assumed met (D-07) | "Sync clearance is available; the full pitch checklist isn't defined yet" |
| Split is deliberately open (`07.06.02` D-03) | Counted as a gap for release, **not** as a failure. The openness was itself a legitimate captured fact. | "Split is marked open — agree it before release" |
| Song will never be released (a demo, an exercise) | Score must not nag. Readiness is only computed when a target is chosen. | Nothing shown |
| Contributor never counter-attests (`07.06.02` DT-04) | The claim stays unverified and readiness stalls on a fact the Musician cannot force. **The most frustrating case**, and it is caused by the platform's own attestation model. | "Waiting on Sam to confirm" + nudge — never a way to override |
| Score is high but the important thing is missing | Exactly why weighting exists — a 90% song with an undeclared sample is not 90% ready | Weighted; the sample gap dominates the list |
| Every gap closed but QC fails | Not ready. Audio faults sink readiness like paperwork does (parent CX-03) | QC failure in the gap list |
| Checks still running | Renders honestly as pending — never a falsely high number | "Still checking" |
| Two collaborators close different gaps at once (Producer confirms a credit while Musician declares a source) | Readiness recomputes on either write; last-writer does not clobber the other's gap closure because each gap is closed at its own source, not on the score record. The score is a **view**, never a stored counter to race on. | Gap list shrinks as each closes; no lost update |
| Upstream target spec changes after "ready" (domain 12 revises DSP requirements; parent CX-04) | Readiness re-evaluates against the current spec version — a previously-ready song can revert to incomplete. Better an honest reversion than a stale badge that ships something now non-conformant. A package already sent keeps its pinned spec version and is not retroactively re-judged (D-08). | Ready badge clears; new gap named: "DSP now requires X" |
| Target chosen whose spec nobody owns (`live`, `remix`, archive, engagement-purchased) | Not offerable (D-07) — the picker does not list a target with no owned spec, exactly as `07.08.01` does not list an undefined recipient spec. No placeholder, no empty gap list. | The target simply is not in the picker |
| Referenced owner's fact is temporarily unavailable (domain 12 or 11 unreachable) | The gap is named as pending against its owning domain and weighted as unknown-not-zero; the score never silently treats an unfetched requirement as satisfied. Never blocks. | "Waiting on domain 12's current requirements" |
| Musician re-picks a different target on the same song (mix-handoff → DSP-release) | Score recomputes from scratch against the new spec; gaps that only mattered for the old target vanish, heavier ones appear. No target's gap list bleeds into another's. | Fresh gap list for the newly chosen destination |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| No target | No destination selected | Not computed, not shown |
| Computing | Target selected | Pending, honestly |
| Incomplete | Gaps exist | Ordered, actionable gap list |
| Blocked-on-others | Gap needs someone else | Named, with a nudge; no override |
| Opaque | Gap not visible to this viewer | "Waiting on information you don't have access to" |
| Ready | All met | Ready badge + the good notification |
| Error | Fetch failed | Error with retry |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | A **single completeness percentage** is the right shape | The candidate's name ("Completeness Score") says so, and every product does it — profile completeness, listing completeness | ❌ **REJECTED — twice over.** First, *complete for what?* A song can be entirely ready for a mix handoff and nowhere near ready for a DSP release; one number answers a question nobody asked (parent CX-04). Second, a percentage implies gaps are **fungible**, and they are catastrophically not: an undeclared sample can expose every collaborator downstream (`meta/personas.md`) while a missing BPM inconveniences a search index. "76%" averages a legal landmine with a nice-to-have and calls the result precision. **The output is a weighted, ordered, actionable gap list per target** — and if a number is shown at all, it is a summary of that list, never the product. |
| DT-02 | The score is where the domain's non-blocking principle finally pays off | Tracing the consequence of `07.01.03` D-02 and `07.06.02` D-02 through to their conclusion | ✅ CONFIRMED — **and this feature is what makes "never block" defensible rather than negligent.** The domain repeatedly refuses to stop anyone: the board never blocks, the capture prompt never blocks, QC never blocks, stem naming never blocks. That is correct (coercion loses the room) and it would be irresponsible if the debt vanished. It does not — it accrues silently and surfaces **here**, at the moment the user actually wants something (to ship), when they are motivated to fix it and it is still fixable. **Non-blocking upstream + honest reckoning at the exit is the domain's core interaction design**, and neither half works without the other. This feature is not a nice-to-have dashboard; it is the second half of a principle. |
| DT-03 | The score should nag users toward completeness | The obvious engagement design, and every completeness meter in every product does it | ❌ **REJECTED** — and the reason is structural rather than stylistic. Most songs **never get released**, and that is normal, healthy music-making: demos, exercises, ideas that did not work, sessions that went nowhere. A platform that follows a musician around asking them to complete metadata on a demo they abandoned in March has become homework, and homework gets abandoned. Worse, it would train users to dismiss the completeness signal *as a class* — so when a song they actually care about is genuinely missing its splits, the warning is invisible because it looks like all the others they have learned to ignore. **Readiness is computed only when a target is chosen** — i.e. when the user has declared they want to ship. Motivation must precede measurement, not the other way round. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | Readiness is computed **per target**, never as one global number | Per DT-01 and parent CX-04 — "complete for what?" is the only sensible question. |
| D-02 | The output is a **weighted, ordered, actionable gap list** — a percentage, if shown, summarises it and is never the product | Per DT-01 — gaps are not fungible; averaging a legal landmine with a missing BPM is false precision. |
| D-03 | **No nagging.** Readiness is computed only when the user picks a target | Per DT-03 — most songs are never released, and a nagged signal is a dismissed signal. |
| D-04 | This feature is the **debt ledger** that makes the domain's non-blocking principle honest | Per DT-02 — never block upstream, reckon honestly at the exit. |
| D-05 | Gaps the viewer cannot see are shown as **opaque**, not hidden | Hiding them would make the score inexplicable; disclosing them would leak. |
| D-06 | No override for gaps that need someone else's action | The attestation model means some gaps genuinely are not the Musician's to close — pretending otherwise would let them fake a confirmation. |
| D-07 | **P-05:** a target's facts come from whoever owns them — `07.08.01` authors mastering and mix-handoff; DSP references domain 12; sync references domain 11; an unowned target is **not offerable** | This is `07.08.01` D-06 applied to targets, because the score's targets and the builder's recipient specs are one list under two names. Referenced severities are consumed as this feature's D-02 weights, never re-derived — a second copy would drift (`07.07.03` D-04) and consequence belongs to whoever owns the harm (domain D-05). Readiness ships per target as each becomes available; that is build order, never a gate on a user. |
| D-08 | **P-05:** the score is a **live view** and the package a **pinned record** over one target-spec store | Resolves the pin-vs-live tension with `07.08.01` D-03 by dissolving it, as domain 12 did (`12.02.02` D-01, `12.01.02` D-07/DT-09 — one store, one version identity, two projections). A package pins the spec version it validated against; the score always re-evaluates live and names the fact that moved. 07 does not inherit 12's authority to hold dispatch. |
