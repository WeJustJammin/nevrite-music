> **Number**: 07.08.02
> **Parent**: [Delivery, Readiness & QC](./07.08-delivery-readiness-qc-index.md)
> **Status**: [SURFACE]
> **Last updated**: 2026-07-16

> **Merged** from sweep candidates 29 ("Deliverable Checklist, Spec Validation & Automated Audio QC") and 30
> ("Sample Rate, Bit Depth & Tempo Guardrails") per sub-domain D-01 — one mechanism applied at two moments
> (project config and delivery), not two features.

## Overview

The automated technical checks on audio: does it clip, is the sample rate consistent, is there silence where
there should not be, is the file what it claims to be, does it meet the receiving spec. It catches the class of
error that is objectively wrong and invisible until it is expensive — and it is deliberately narrow, because the
line between "objectively wrong" and "a choice you disagree with" is where automated QC tools go bad.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Read-only | Sees pass/fail on their song's deliverables, in plain language. "This master will distort on Spotify" is a sentence they can act on; "true peak +0.4 dBTP" is not, on its own. |
| Producer | Full | Reads the detail, configures the project's technical spec (48 kHz/24-bit), fixes what fails. The technical detail is for them and should not be dumbed down. |
| Operator | None | Not their business. |
| Fan | None | Not visible. |

## Behavior

Two trigger points, one mechanism (sub-domain D-01):

**At project config** — the project declares its technical spec (sample rate, bit depth, tempo), and uploads that
do not match get flagged at ingest, when the fix is cheap. A stem at 44.1 kHz in a 48 kHz project is a real error
that compounds silently.

**At delivery** — the recipient spec (`07.08.01`) supplies the ruleset (parent CX-01) and the package is checked
against it.

The check set is deliberately narrow and covers only the objective:

| Check | Why it is objective |
|---|---|
| True peak over 0 dBTP | Will audibly clip after lossy encoding, and the artist cannot hear it beforehand (`07.07.03` DT-02) |
| Sample rate / bit depth inconsistency | Something will be silently resampled |
| Digital clipping (consecutive samples at full scale) | An error, not a choice — unless it is (see DT-02) |
| Unintended silence / dropouts | A missing region is a fault |
| Channel count mismatch | A mono file where stereo is expected |
| DC offset | Objectively wrong, invisible, easily fixed |
| Stem sum mismatch (null test) | `07.04.04` DT-01 — the pack is incomplete |

**QC warns; it does not block** (`07.04.04` D-03) — with the single exception of integrity failure
(`07.08.01` D-04), where the blast radius justifies the stop.

### Happy Path

1. Producer builds a mastering handoff (`07.08.01`)
2. QC runs the `mastering` spec's ruleset
3. All checks pass except one: true peak on the alternate is +0.2 dBTP
4. Warning names the file, the value, and the consequence — "this will distort after encoding"
5. Producer re-bounces with a ceiling; the package builds clean

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Clipping that is **intentional** (a distorted mix, a hard-clipped drum bus, an entire genre) | Warned once, dismissible, remembered. Never re-nagged — see DT-02 | "This clips — intentional?" then silence forever after |
| Deliberate silence (a hidden track, an ambient intro) | Same treatment | Dismissible, remembered |
| 44.1 kHz stem in a 48 kHz project | Flagged at ingest, when the fix is cheap | "This is 44.1 — the project is 48" |
| Tempo mismatch against the project's declared tempo | Weakest check in the set — see DT-03 | Advisory at most |
| QC on a 40 GB package | Async; never blocks the build | Progressive results |
| Check itself fails (analysis error) | Reported honestly — **never** silently marked passed | "Couldn't check 2 files" |
| Producer disagrees with a check | They are usually right. Dismissible per file, remembered per project. | Dismissed, gone |
| Master that is quiet, or loud, or dynamic-range-crushed | **Not checked.** Aesthetic choice, out of bounds (`07.07.03` D-01) | No flag |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Pending | Asset ingested | "Checking…" — never a falsely clean result |
| Passed | All checks clean | Quiet pass indicator |
| Warned | Issues found | Ordered by severity, each with its consequence |
| Dismissed | Producer dismissed a warning | Gone, remembered, not re-raised |
| Unverifiable | Analysis impossible | Honest — never a false pass |
| Error | Check failed | Retry |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | The check set must be **narrow and objective** — QC's failure mode is scope creep into taste | The pattern is visible three times already in this domain: `07.07.03` DT-01 (do not prescribe loudness), `07.05.03` DT-02 (do not resolve contradictions), `07.02.02` DT-01 (do not compute splits). Automated QC tools fail the same way every time — they start with true peak and end up telling a producer their mix is "too bright", at which point professionals turn them off entirely **and stop seeing the true-peak warnings too**. The scope creep does not merely add noise; it destroys the credibility of the checks that were worth having. | ✅ CONFIRMED — the check set is a **fixed, defensible list of objectively-wrong-and-invisible faults**. Every proposed addition must pass one test: *is the user unable to perceive this, and is it unambiguously a fault?* Loudness fails (perceivable). Brightness fails (not a fault). True peak passes both. |
| DT-02 | Clipping is always an error | The most obvious check in audio QC, and it is in every tool | ❌ **REJECTED** — clipping is a *technique* in several genres and a deliberate choice in many mixes; hard-clipped drums are a stylistic staple, and some records are clipped end to end on purpose. A tool that flags this on every bounce is a tool that gets muted within a week — taking the useful checks with it (DT-01's failure mode, in miniature). The fix is not to drop the check but to make dismissal **sticky**: warn once per project, remember the answer, never raise it again. **The right to be wrong on purpose is a design requirement in a craft domain**, and a QC system that does not model it will be disabled by exactly the professionals it was built for. |
| DT-03 | Tempo guardrails (from merged candidate 30) are a useful check | Inherited from the sweep's candidate, unexamined | ❌ **REJECTED — and I am removing an inherited check.** What would it even mean? A song with a declared tempo of 120 whose audio measures 119.7 is not wrong — it is played by humans, and that variance is the *point*. A song that changes tempo is not wrong. A song recorded to a click at 120 and later time-stretched is not wrong. There is no failure mode here that a musician cannot perceive better than a detector can, and every flag it raises would be noise against DT-01's credibility budget. The **legitimate** kernel inside candidate 30 is sample rate and bit depth consistency, which is real and retained. Tempo is dropped, and the removal is the honest outcome of examining an inherited assumption rather than implementing it. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | The check set is **narrow, fixed, and objective** — every addition must pass "imperceptible **and** unambiguously a fault" | Per DT-01 — scope creep into taste destroys the credibility of the checks worth having. |
| D-02 | **Dismissal is sticky** — warn once per project, remember, never re-raise | Per DT-02 — the right to be wrong on purpose is a design requirement in a craft domain. |
| D-03 | **Tempo checks are dropped** | Per DT-03 — no perceptible-fault kernel exists; the sample rate/bit depth half of candidate 30 is retained. |
| D-04 | QC **warns**; only integrity blocks | `07.04.04` D-03 and `07.08.01` D-04. |
| D-05 | Failed checks report **the consequence**, not the measurement, to the Musician; full detail to the Producer | "This will distort on Spotify" is actionable; "+0.4 dBTP" is not, for an artist. |
| D-06 | Unverifiable **never** renders as passed | A false clean badge on a delivery is worse than no badge (`07.04.05` D-05). |
