## Overview

Assembling everything a recipient needs, in the form they need it, verified before it goes. A mastering engineer
needs the canonical mix, its loudness targets and the alternate matrix. A mix engineer needs stems, the brief and
the recall sheet. A sync agent needs the instrumental and the clearance status. Today each of these is assembled
by hand into a Dropbox folder, and the difference between a good handoff and a bad one is whether the sender
remembered.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Read-only | Sees that a handoff went out, to whom, and whether it passed its checks. Rarely builds one — this is engineering work. Their real interest is "did the mastering engineer get everything?", which is a yes/no. |
| Producer | Full | Builds packages constantly. This is one of their highest-frequency actions, and — like `07.05.02` — it is a workflow the platform must win or the work leaves the platform and takes the provenance with it. |
| Operator | None | Not their business. |
| Fan | None | Not visible. Public stem release is `07.08.05`, which is a different thing entirely (parent R-02). |

## Behavior

A package is `(recipient spec, resolved contents, validation results)`. The **recipient spec** is the organising
idea and the correction of `07.04.04` DT-03: there is no universal "correct" package, only "does this satisfy the
receiver". Each spec declares what must be present and what checks apply (parent CX-01).

**P-04 (D-06): this feature authors only the specs it owns.** It **originates** `mastering` and `archive`'s
asset half, **references** the specs other domains own, and **defers** the ones that have no owner yet:

| Spec | This feature's role | Authority |
|---|---|---|
| `mastering` | **Originates** | Owned here — `07.08.03` Q-02 states it directly. Contents from `07.07.01` DT-03 (loudness targets), `07.07.02` (alternate matrix), `07.08.04` (source declarations), `07.04.02` (canonical). |
| `mix` (in-project handoff) | **Originates** | Owned here. Contents from `07.04.04` (stems), `07.07.01` (brief), `07.06.04` (recall sheet). |
| `archive` | **Originates the asset half only** | Audio, stems, sessions and manifests in open formats (DT-03). The provenance-graph half is the `Data Portability & Account Export` cross-cut and remains gated on values question Q-02. |
| `sync` | **References domain 11** | `11.02.01` owns the clearance verdict; `07.07.02` D-02 owns the instrumental variant vocabulary. This feature validates presence and surfaces the verdict; it never restates the requirement. |
| DSP delivery | **References domain 12** | `07.07.03` D-04: "Destination specs are owned by domain 12, referenced here. Two copies of third-party requirements would drift, and one would be wrong." See Q-03. |
| mix/mastering bought as an engagement | **References domain 05** | `05.04.02` owns format/LUFS/true-peak/naming; `05.04.04` D-01/D-03 own the artifact set and plugin manifest. |
| `live`, `remix` | **Neither — unowned** | No source defines their contents. Naming them is not specifying them; see Q-04. |

The rule generalises: **where another domain owns a requirement, this feature references and validates against it
and never re-states it.** A second copy of a third-party requirement is a copy that drifts.

Contents resolve from the **canonical** versions (`07.04.02`), not from whatever is newest, and then **pin** —
so a package is an exact, reproducible record of what was sent, forever.

The manifest travels with it (`07.06.03` DT-02): "this session needs Logic 11.2 and these 14 plugins" is the
information that determines whether the recipient can open it at all, and it is the thing a Dropbox folder can
never carry.

> **v1 qualification (D-07, 2026-07-22).** There is **no manifest to travel in v1**, and no missing-media
> check either. Both are produced on the producer's machine by a client `07.09` D-05 does not authorise
> (`07.06.03` D-06, `07.04.05` D-06). For the whole v1 window a session package ships with its bytes, its
> checksums and its pinned contents — and the package must **say** that the environment was not recorded
> rather than let its absence read as "nothing needed". Domain D-06 makes the disclosure obligatory: the
> claim this feature sells is "it will open on the recipient's machine", and in v1 the platform cannot
> check it.

### Happy Path

1. Mix is approved and canonical; Producer builds a handoff for the mastering engineer
2. Selects the `mastering` spec; contents resolve automatically — canonical mix v7, the three alternates (`07.07.02`), the brief's loudness targets (`07.07.01` DT-03), the source declarations (`07.08.04`)
3. Validation runs (parent CX-01): headroom fine, sample rates consistent, all alternates present, integrity verified (`07.04.05`)
4. Package pins its contents and is delivered — as a private link (`07.05.02`) if the recipient is not on the platform
5. Six months later, the record of exactly what was sent is intact and citable

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Canonical not set for a required item | **Warns and asks; does not block.** The builder refuses to *guess* (`07.04.02` D-06) — but per that same decision, refusing to guess "is not refusing to proceed", and domain D-04 makes non-blocking absolute. The build waits on a one-tap pick rather than failing. | "No canonical mix has been chosen" with a picker |
| A referenced spec's own requirement is unavailable (domain 11 clearance verdict, domain 12 destination spec, domain 05 deliverable spec) | Warns and names the owning domain; never blocks and never substitutes a local guess for the absent requirement (D-06) | "Clearance status is unknown — domain 11 has not returned a verdict" |
| Spec has no defined contents (`live`, `remix`) | The name is offered only where a source defines what it means. An undefined spec is not selectable, and the builder says so plainly instead of shipping an empty ruleset (D-06, Q-04) | "No `live` spec exists yet — pick another, or build a custom handoff" |
| Integrity failure on a required asset | **Blocks.** The one hard stop in the sub-domain (parent CX-01, `07.04.05`) — shipping a corrupt master is the largest blast radius in the domain | "This file failed its integrity check and can't be sent" |
| Spec requires something absent (no instrumental for a sync handoff) | Warns and names it; does not block. The producer may have a reason. | "This sync spec expects an instrumental — none exists" |
| Recipient is not on WeJammin | The common case. Delivered by private link (`07.05.02`), watermarked | Link with expiry and terms |
| Package is 40 GB (full session archive) | Real. Resumable transfer both directions; a failed 40 GB download at 90% is worse than the problem being solved | Progress with resume |
| Missing media in a session package | Named specifically (`07.04.05` DT-01) — the number one reason handoffs bounce back. **Post-gate (D-07)**: naming them needs a session parse, and there is none in v1 (`07.09.02` D-09), so v1 reports the references as **unchecked**, never as resolved | "6 referenced files aren't in this package" — v1: "References in this session weren't checked" |
| Recipient's environment lacks the required plugins | Detected from the manifest (`07.06.03` DT-02) and disclosed **before** sending. **Post-gate (D-07)**: no manifest is captured in v1, so this disclosure is unavailable and its absence must be stated, not implied | "The recipient will need 3 plugins they may not have" — v1: "No environment manifest was recorded for this session" |
| Undeclared samples in a package going to a sync agent | Cross-links to `07.08.04`; a sync handoff with unknown clearance status is a commercial trap | "2 sources are undeclared" |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | The **recipient spec** is the organising idea, and shipping opinionated defaults is the value | `07.04.04` DT-03 established there is no universal convention — requirements differ irreconcilably by receiver. The follow-on insight: most producers do not actually know what a mastering engineer wants, and mastering engineers have a written spec on their website that nobody reads. **The knowledge exists and does not travel.** A platform that encodes "here is what a mastering engineer needs" is not building a file-zipper; it is distributing professional knowledge that is currently locked in individual heads and unread web pages. | ✅ CONFIRMED — the defaults **are** the product. A generic "select files, zip them" builder is worthless; anyone can zip. The opinionated spec set is what makes a first-time independent artist hand off like a professional, which is a genuine and rare kind of value. |
| DT-02 | The package should always contain everything, to be safe | The natural instinct — more is safer, and omissions are the visible failure | ❌ **REJECTED** — over-sending is a real harm, not merely inefficiency. Sending the full session to a mastering engineer who needs one stereo file wastes hours of transfer on both sides, and — far worse — it **violates least privilege** (`07.03.03` DT-01) by handing the most sensitive assets in the domain (stems, takes) to someone whose job needs none of them. Every unnecessary copy of a stem pack is an extra place it can leak from, and `07.04.03` DT-03 established that takes are the most personally exposing audio in the product. The mastering engineer's spec deliberately excludes stems **because they should not have them** — the spec is a privacy boundary as much as a convenience. |
| DT-03 | Data portability (the merged candidate 33) is satisfied by this feature | Sub-domain D-02's merge rationale, taken at face value | ⚠️ **PARTIALLY CONFIRMED — and the gap is a values question, not a technical one.** The `archive` spec genuinely gives a user their music: audio, stems, sessions, manifests, in open formats. That is the substantive half of portability and it answers `meta/problem-statement.md` Q-02's "if a user leaves, what do they take?" for the *assets*. But it does **not** export the **provenance graph** — the credits, splits, attestations, session history and version lineage that are the platform's whole differentiator. And that is exactly the tension Q-02 identifies: the graph is the thing users cannot take with them, which is simultaneously what makes the lock-in *earned* (it only exists because the platform captured it) and what would make it *hostile* (if leaving means losing it). The honest position: the graph should be exportable in an **open, portable form** (DDEX RIN is the industry candidate), and if the platform refuses that, the lock-in is hostile and the platform should admit it. Escalated as Q-02 — a values decision for the owner, not an agent's call. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | The platform ships **opinionated recipient specs** — they are the product, not a config surface | Per DT-01 — the knowledge exists in professionals' heads and does not travel; encoding it is the value. |
| D-02 | Packages contain **only what the spec requires** — over-sending is a privacy failure, not a kindness | Per DT-02 — every unnecessary stem copy is another place it can leak from. |
| D-03 | Contents resolve from **canonicals** and then **pin** — together with the **spec version** they were validated against | `07.04.02` D-03/D-06 — a package is an exact, reproducible record of what was sent *and what it was checked against*. Per `07.08.03` D-08 the package is the pinned **record** and readiness the live **view** over one target-spec store; a later spec revision never retroactively re-judges a sent package. |
| D-04 | Integrity failure **blocks**; everything else warns | The domain's only justified hard stop — shipping a corrupt master has the largest blast radius here. Applies without exception: a missing canonical, an unmet spec expectation, and an unavailable referenced requirement all warn (domain D-04, "non-blocking is absolute"). |
| D-05 | The environment manifest travels with the package | `07.06.03` DT-02 — it determines whether the recipient can open it at all. ⚠️ **Held, not overturned, for the v1 window — see D-07**: no manifest is captured in v1, so there is none to travel. |
| D-06 | **P-04:** this feature authors only the specs it owns — `mastering`, `mix`, and `archive`'s asset half — and **references** specs owned elsewhere | Per the Behavior ownership table. `07.07.03` D-04 already locks the principle for destination specs ("two copies of third-party requirements would drift, and one would be wrong"); `07.08.03` Q-02 assigns mastering here and sync to domain 11. Referencing means validating presence and surfacing the owner's verdict, never re-stating the requirement. `live` and `remix` have no source and are not specified by being named — see Q-04. |
| D-07 | **No environment manifest and no missing-media check in v1 — and the package says so.** Both are captured on the producer's machine by a client `07.09` D-05 does not authorise (`07.06.03` D-06, `07.04.05` D-06), so a v1 session package carries bytes, checksums and pinned contents only | Owner ratification DQ-08.2 / DQ-08.4 / DQ-08.5, 2026-07-22. D-05 is held, not overturned — the manifest is still the right payload; there is simply nothing producing it in the v1 window. D-04's integrity block is unaffected: checksums run without a client. What changes is what the package may **claim**: "verified" in v1 means bytes and plausibility, and the unchecked references and absent manifest are disclosed on the package rather than left as silence, per domain D-06 and `07.04.05` D-05's rule against a verification that was not performed. Not re-scoped; `07.09` keeps `Should`, unphased (domain D-10). |
