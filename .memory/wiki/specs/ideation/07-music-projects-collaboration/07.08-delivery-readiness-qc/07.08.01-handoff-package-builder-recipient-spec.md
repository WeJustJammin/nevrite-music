## Overview

Assembling everything a recipient needs, in the form they need it, verified before it goes. A mastering engineer
needs the canonical mix, its loudness targets and the alternate matrix. A mix engineer needs stems, the brief and
the recall sheet. A sync agent needs the instrumental and the clearance status. Today each of these is assembled
by hand into a Dropbox folder, and the difference between a good handoff and a bad one is whether the sender
remembered.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Read-only | Sees that a handoff went out, to whom, and whether it passed its checks. Rarely builds one — this is engineering work. Their real interest is "did the mastering engineer get everything?", which is a yes/no. |
| Producer | Full | Builds packages constantly. This is one of their highest-frequency actions, and — like `07.05.02` — it is a workflow the platform must win or the work leaves the platform and takes the provenance with it. |
| Operator | None | Not their business. |
| Fan | None | Not visible. Public stem release is `07.08.05`, which is a different thing entirely (parent R-02). |

## Behavior

A package is `(recipient spec, resolved contents, validation results)`. The **recipient spec** is the organising
idea and the correction of `07.04.04` DT-03: there is no universal "correct" package, only "does this satisfy the
receiver". The platform ships opinionated defaults — mastering, mix, sync, live, remix, archive — and each spec
declares what must be present and what checks apply (parent CX-01).

Contents resolve from the **canonical** versions (`07.04.02`), not from whatever is newest, and then **pin** —
so a package is an exact, reproducible record of what was sent, forever.

The manifest travels with it (`07.06.03` DT-02): "this session needs Logic 11.2 and these 14 plugins" is the
information that determines whether the recipient can open it at all, and it is the thing a Dropbox folder can
never carry.

### Happy Path

1. Mix is approved and canonical; Producer builds a handoff for the mastering engineer
2. Selects the `mastering` spec; contents resolve automatically — canonical mix v7, the three alternates (`07.07.02`), the brief's loudness targets (`07.07.01` DT-03), the source declarations (`07.08.04`)
3. Validation runs (parent CX-01): headroom fine, sample rates consistent, all alternates present, integrity verified (`07.04.05`)
4. Package pins its contents and is delivered — as a private link (`07.05.02`) if the recipient is not on the platform
5. Six months later, the record of exactly what was sent is intact and citable

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Canonical not set for a required item | **Blocks** — the builder refuses to guess (`07.04.02` D-06). Guessing is the failure mode the domain exists to prevent | "No canonical mix has been chosen" with a picker |
| Integrity failure on a required asset | **Blocks.** The one hard stop in the sub-domain (parent CX-01, `07.04.05`) — shipping a corrupt master is the largest blast radius in the domain | "This file failed its integrity check and can't be sent" |
| Spec requires something absent (no instrumental for a sync handoff) | Warns and names it; does not block. The producer may have a reason. | "This sync spec expects an instrumental — none exists" |
| Recipient is not on WeJammin | The common case. Delivered by private link (`07.05.02`), watermarked | Link with expiry and terms |
| Package is 40 GB (full session archive) | Real. Resumable transfer both directions; a failed 40 GB download at 90% is worse than the problem being solved | Progress with resume |
| Missing media in a session package | Named specifically (`07.04.05` DT-01) — the number one reason handoffs bounce back | "6 referenced files aren't in this package" |
| Recipient's environment lacks the required plugins | Detected from the manifest (`07.06.03` DT-02) and disclosed **before** sending | "The recipient will need 3 plugins they may not have" |
| Undeclared samples in a package going to a sync agent | Cross-links to `07.08.04`; a sync handoff with unknown clearance status is a commercial trap | "2 sources are undeclared" |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Empty | Project has never had a handoff built | Empty state naming the six default specs (mastering, mix, sync, live, remix, archive) with a "Build a handoff" CTA — the first-run teaching surface for DT-01's "distribute professional knowledge" |
| Draft | Building | Spec picker; contents resolving |
| Resolving | Spec selected | Contents assembling from canonicals |
| Validating | Contents resolved | Checks running |
| Blocked | Integrity failure / no canonical | The specific blocker, with the fix |
| Warned | Spec expectations unmet | Named gaps; build available anyway |
| Ready | Validation passed | Package with contents listed; delivery CTA |
| Delivered | Sent | Pinned, immutable record of exactly what went |
| Error | Build failed | Retry |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | The **recipient spec** is the organising idea, and shipping opinionated defaults is the value | `07.04.04` DT-03 established there is no universal convention — requirements differ irreconcilably by receiver. The follow-on insight: most producers do not actually know what a mastering engineer wants, and mastering engineers have a written spec on their website that nobody reads. **The knowledge exists and does not travel.** A platform that encodes "here is what a mastering engineer needs" is not building a file-zipper; it is distributing professional knowledge that is currently locked in individual heads and unread web pages. | ✅ CONFIRMED — the defaults **are** the product. A generic "select files, zip them" builder is worthless; anyone can zip. The opinionated spec set is what makes a first-time independent artist hand off like a professional, which is a genuine and rare kind of value. |
| DT-02 | The package should always contain everything, to be safe | The natural instinct — more is safer, and omissions are the visible failure | ❌ **REJECTED** — over-sending is a real harm, not merely inefficiency. Sending the full session to a mastering engineer who needs one stereo file wastes hours of transfer on both sides, and — far worse — it **violates least privilege** (`07.03.03` DT-01) by handing the most sensitive assets in the domain (stems, takes) to someone whose job needs none of them. Every unnecessary copy of a stem pack is an extra place it can leak from, and `07.04.03` DT-03 established that takes are the most personally exposing audio in the product. The mastering engineer's spec deliberately excludes stems **because they should not have them** — the spec is a privacy boundary as much as a convenience. |
| DT-03 | Data portability (the merged candidate 33) is satisfied by this feature | Sub-domain D-02's merge rationale, taken at face value | ⚠️ **PARTIALLY CONFIRMED — and the gap is a values question, not a technical one.** The `archive` spec genuinely gives a user their music: audio, stems, sessions, manifests, in open formats. That is the substantive half of portability and it answers `meta/problem-statement.md` Q-02's "if a user leaves, what do they take?" for the *assets*. But it does **not** export the **provenance graph** — the credits, splits, attestations, session history and version lineage that are the platform's whole differentiator. And that is exactly the tension Q-02 identifies: the graph is the thing users cannot take with them, which is simultaneously what makes the lock-in *earned* (it only exists because the platform captured it) and what would make it *hostile* (if leaving means losing it). The honest position: the graph should be exportable in an **open, portable form** (DDEX RIN is the industry candidate), and if the platform refuses that, the lock-in is hostile and the platform should admit it. Escalated as Q-02 — a values decision for the owner, not an agent's call. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | The platform ships **opinionated recipient specs** — they are the product, not a config surface | Per DT-01 — the knowledge exists in professionals' heads and does not travel; encoding it is the value. |
| D-02 | Packages contain **only what the spec requires** — over-sending is a privacy failure, not a kindness | Per DT-02 — every unnecessary stem copy is another place it can leak from. |
| D-03 | Contents resolve from **canonicals** and then **pin** | `07.04.02` D-03/D-06 — a package is an exact, reproducible record of what was sent. |
| D-04 | Integrity failure **blocks**; everything else warns | The domain's only justified hard stop — shipping a corrupt master has the largest blast radius here. |
| D-05 | The environment manifest travels with the package | `07.06.03` DT-02 — it determines whether the recipient can open it at all. |
