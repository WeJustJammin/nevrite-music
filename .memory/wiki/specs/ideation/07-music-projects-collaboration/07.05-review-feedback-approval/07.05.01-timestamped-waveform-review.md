# Feature: Timestamped Waveform Review

> **Number**: 07.05.01
> **Parent**: [Review, Feedback & Approval](./07.05-review-feedback-approval-index.md)
> **Status**: [SURFACE]
> **Last updated**: 2026-07-16

## Overview

Comments anchored to a moment in a specific version of a song. Click the waveform at 1:47, say "the vocal
disappears here", and the note lives at 1:47 of v6 forever. Per the domain rationale this is "the highest-value
interaction in music collaboration and table stakes" — it is also the feature most likely to get a producer to
open the platform on day one, before they believe anything about provenance.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Full | Leaves timestamped notes on mixes; replies; marks their own comments resolved. As a band member, sees the other members' notes — which is how a band discovers it disagrees about the chorus before the mix engineer does. |
| Producer | Full | Receives the feedback and works from it; replies; resolves. Their real problem is not reading comments but reconciling contradictory ones, which is why `07.05.03` exists as a separate feature. |
| Operator | None | Not their business. |
| Fan | None | Not visible. A fan never sees an unreleased mix or the argument about it. **Exception**: a non-roster *link recipient* (parent CX-01) can comment without an account — but that is a link, not a Fan account. |

## Behavior

A comment is `(version, position, author, body, created_at)` and optionally a **range** rather than a point —
"the whole second chorus is too dry" is not a moment, it is a region, and forcing it to a point makes it wrong.

Comments anchor to a **version, never to the song** (sub-domain D-02). This is the design decision that makes the
loop honest: a note about v6's vocal balance applied to v9 — where the vocal was already fixed and something else
changed — causes a genuinely wrong fix. Every tool that anchors comments to "the track" has this bug.

The consequence is the feature's hardest problem: when v7 lands, what happens to v6's open comments? See DT-01 —
this is the question the candidate list did not ask and the one that determines whether the feature is useful or
a graveyard.

Entry must be fast and possible while listening. The realistic input context is a producer with headphones on
who does not want to stop playback to type — and, increasingly, a phone.

### Happy Path

1. Musician opens v6 from the timeline and plays it
2. At 1:47 the vocal drops behind the guitars; they click the waveform at that point
3. Type "vox disappears under the gtrs here" — playback continues while typing
4. Comment lands at 1:47 of v6; the Producer is notified
5. Producer opens it, jumps straight to 1:47, hears exactly the moment, fixes it, and bounces v7 with the comment linked to the change

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| New version lands with open comments on the old one | The core problem — see DT-01. Comments **carry forward as unresolved-against-v6**, with a position mapped where lengths allow | "4 open comments from v6" with a mapping caveat if lengths differ |
| Versions differ in length; a mapped position is meaningless | Disclosed, never silently re-anchored — a comment moved to the wrong bar is worse than one that admits it does not know | "v7 is 8 s longer — this position may not match" |
| Comment on a range | Supported natively (not point-only) | Highlighted region |
| Two people comment on the same moment | Both land; clustered by `07.05.03` | Stacked markers |
| Comment left by a non-roster link recipient (parent CX-01) | Lands with **weaker identity**, visibly distinguished | "Sam (via link)" — never rendered identically to an authenticated member |
| Comment author leaves the roster | Comment persists; access to the song is revoked | Comment remains attributed |
| Reply thread becomes a full discussion | Supported, but the argument about the chorus is not what this feature is for; long threads are a signal for `07.05.03` | Threaded replies with collapse |
| Producer disagrees and does not do it | Resolve-with-reason, **not** silent close (parent CX-02) | Author is told, and told why |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Loading | Version opened | Waveform skeleton; comment markers stream in |
| Empty | No comments | Waveform with a hint to click and comment |
| Populated | Comments exist | Markers on the waveform; list alongside; open/resolved filter |
| Composing | Comment started | Inline input; **playback keeps running** |
| Carried forward | Comments inherited from a prior version | Distinct treatment plus the mapping caveat |
| Resolved | Marked resolved | Dimmed; still visible; never deleted |
| Error | Post failed | Local draft retained, retry offered — **never lose a typed comment** |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | **The unsolved problem is comment carry-forward across versions**, and nobody in the sweep noticed it | Version-anchoring (sub-domain D-02) is obviously right — but it creates the hard case immediately. A mix has 12 open comments on v6; the producer fixes 8 and bounces v7. Do the 4 remaining comments appear on v7? If **no**, they are lost and the artist re-types them, and the feature has failed at its job. If **yes**, they must be re-anchored to a version whose timeline may have shifted — and a comment silently moved to the wrong bar is worse than one that was lost, because it produces a confident wrong fix. Every existing tool in this space either drops the comments or lies about their position. | ✅ CONFIRMED as **the** design problem of this feature. Direction: comments carry forward as explicitly *unresolved against the version they were written on*, position-mapped only where lengths allow, and **honestly caveated where they do not**. Refusing to fabricate a position is the trustworthy choice. Escalated as Q-01 — it deserves a real design pass at Step 5, not a paragraph. |
| DT-02 | Text comments are sufficient | Implicit in the candidate | ❌ **REJECTED** — musicians communicate about music badly in text. "More warmth", "make it punchier", "it needs to breathe" are the actual vocabulary, and they are unactionable to anyone who was not in the room. Two additions are worth far more than better text: (a) **reference-linking** a comment to a moment in another track ("like the snare at 0:48 of *this*") — this is how the conversation genuinely happens, and it connects to the mix brief (`07.07.01`); (b) **voice comments**, since a producer with headphones on can say "the 3k is harsh right here" in two seconds and cannot type it in twenty. Voice notes also connect back to the domain's own thesis — capture in the medium the work happens in. |
| DT-03 | This feature is a differentiator | The domain rationale calls it "the highest-value interaction in music collaboration" | ⚠️ **CONFIRMED AS TABLE STAKES, NOT DIFFERENTIATOR** — the rationale itself says "and table stakes", and it is right. Frame.io does this for video; Disco, Filepass, Bandlab and Splice do versions of it for audio; every producer already has a tool. So this feature **wins adoption, not defensibility** — it is the daily hook of D-18's consolidation half, not the moat. Its actual differentiation is structural rather than featural: the comment attaches to a *version in a lineage, with a roster, that produces a credit* — so the review that a competitor treats as the whole product is here just the surface where provenance gets manufactured. That framing matters for MoSCoW: this must be **excellent** because it is the door, and it must not be mistaken for the reason to stay. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | Comments anchor to a **version**, never to the song | Sub-domain D-02 — a comment applied to the wrong version causes a real wrong fix. |
| D-02 | Comments support **ranges**, not only points | "The whole second chorus is too dry" is a region; forcing it to a point misrepresents it. |
| D-03 | Carry-forward is **explicit and honestly caveated** — never a fabricated position | Per DT-01 — a silently re-anchored comment is worse than a lost one. |
| D-04 | Playback **never stops** to compose a comment | The input context is headphones-on, mid-listen. Stopping playback to type loses the thing you were commenting on. |
| D-05 | Resolution is **with reason**, and always visible to the author; comments are never deleted | Parent CX-02 — silence makes the author repeat the note next round. |
| D-06 | Link-recipient comments are **visibly distinguished** from authenticated ones | Parent CX-01 — an anonymous note and a roster member's note must not look equally authoritative. |
