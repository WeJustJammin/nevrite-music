## Cross-Cut Details

### CX-01: Watch-Folder Ingest ↔ Session Parsing

**Relationship**: Ingest sees a file appear. Parsing reads the session that produced it. Separately, each is
weak — a watch folder is Dropbox, and a session parser with no files is a curiosity. Together they produce the
domain's core input: **an artifact with lineage, contributors and context, captured without anyone typing**.

Ingest also tells parsing *when* to run: a new bounce means the session changed, so the parse is worth redoing.

**Role scoping**:
- **Producer**: Full on both. The only active participant.
- **Musician**: Read-only — they see the results (versions appearing, credits pre-filled) and never touch the mechanism. This passivity is the design: the multi-hyphenate benefits without lifting a finger.
- **Operator** / **Fan**: none.

**Synthesis questions answered**:
1. **Shared state conflict**: none — both produce facts, neither mutates the other's.
2. **Trigger chain**: file appears → ingest → locate session → parse → create version with lineage and contributor hints (`07.04.01`). **Parse failure must not block ingest** — a bounce with no parseable session is still a version worth having, just with weaker metadata. Degrading to "a good Dropbox" is acceptable; losing the file is not.
3. **Permission intersection**: the bridge acts as the producer, with the producer's grants. It must never see more than they can.
4. **Notification fan-out**: ingest notifies the roster that a new version exists (`07.04.01`).
5. **State transition conflict**: a bounce lands while the session is still being written (DAW mid-save). Ingest must wait for a settled file — see `07.09.01`.

### CX-02: Session Parsing ↔ In-Session Capture Surface

**Relationship**: **This is the sub-domain's reason to exist.** Parsing turns track names into contributor
guesses ("Sam Drums OH" → probably Sam, probably drums), which turns `07.06.02`'s prompt from a form into a
confirmation. `07.06.02` DT-01 is unambiguous that this difference is the difference between the thesis working
and not working — and this edge is where the pre-fill is actually manufactured.

**Role scoping**:
- **Producer**: Full — sees the guess and confirms or corrects it. Correction is cheap; typing from scratch is not.
- **Musician**: Read-only; they receive the counter-attestation request downstream.
- **Operator** / **Fan**: none.

**Synthesis questions answered**:
1. **Shared state conflict**: none — parsing produces hints; the prompt produces claims; the producer's confirmation is the only writer.
2. **Trigger chain**: parse → hints → prompt pre-filled → confirm → credits to domain 02. A **wrong** hint is worse than no hint if it is confirmed carelessly — an over-confident guess is how false credits enter the graph, which is `07.03.01` DT-02's abuse surface arriving by accident rather than malice.
3. **Permission intersection**: no.
4. **Notification fan-out**: downstream of `07.06.02`, not here.
5. **State transition conflict**: the session changes between parse and prompt (someone renames a track). The prompt should re-parse rather than use stale hints.

### CX-03: Watch-Folder Ingest ↔ In-Session Capture Surface

**Relationship**: A bounce is a candidate prompting moment — work just finished and the producer is at the
machine. Medium confidence deliberately: bounces are **frequent** (a producer may bounce twenty times in a
session), and a prompt on each would be intolerable and would destroy the prompt's credibility everywhere else.
The prompt-worthy moments are probably *session close* (`07.06.02`) and *stage transitions* (`07.01.03`), not
every bounce.

**Synthesis questions**: deferred to Step 5 per the Medium/Low rule. The core question — which moments earn a
prompt — is `07.09.03` Q-01 and matters more than it appears: the prompt's power is entirely a function of its
rarity.

## Rejected Pairs

| # | Source | Target | Reason for Rejection |
|---|--------|--------|---------------------|
| R-01 | In-Session Capture Surface | Take & Comp (`07.04.03`) — **as a comping UI** | Considered surfacing take selection in the bridge, since the bridge is already in the session and the takes are right there. Rejected, consistent with `07.04.03` DT-02 and sub-domain D-03: **the bridge captures, it does not control.** The moment WeJammin renders take lanes it is competing with Pro Tools inside Pro Tools, which it will lose while consuming the domain's entire build. The bridge reads the comp map; it never offers to change it. |
| R-02 | Watch-Folder Ingest | Real-Time Rooms / Audio Transport (D-15 cross-cut) | Considered routing live session audio through the bridge — the bridge is on the machine, so it could be the transport endpoint. Rejected: real-time audio transport is a ratified cross-cut (D-15) with hard latency requirements (~25–30 ms), and file ingest is an asynchronous bulk-transfer problem with none. Same machine, opposite engineering constraints, no shared state. Merging them would subject a bulk uploader to real-time scheduling requirements it does not need. |
| R-03 | Session Parsing | Gear Registry (`15`) | Considered inferring a producer's hardware inventory from session data — outboard sends and I/O routing hint at what is in the rack. Rejected: a session file describes *routing*, not *gear*. "Bus 3 → Insert" implies nothing about what is patched, and guessing would produce a confidently wrong inventory. The legitimate version is the **plugin** manifest (`07.06.03`), which is real data, and the analogue gear belongs on the recall sheet (`07.06.04`) where a human writes it down. |
