## Cross-Cut Details

### CX-01: Song Record ↔ Production Stage Board

**Relationship**: The Song entity holds `current_stage`. The board reads it. Moving a card writes it.
No candidate label becomes a lifecycle contract until P-01's practitioner-validation packet passes and the
product owner approves one immutable shared enum version. That version maps semantic transitions to the
existing capture events: roster seed, take selection, mix-credit confirmation, and split-finality
confirmation. The important direction is the reverse one: an approved semantic transition **fires its
capture prompt**. The board is therefore not decoration — it is the trigger surface for provenance capture.

The mapping must remain one shared vocabulary across all validated workflows. It cannot become a
user-configurable board, production-model-specific stage system, or alternate `current_stage` machine.
P-02 independently resolves catalogue presentation: the board below 60 authorized visible unique Songs and the
table at 60+ remain interchangeable projections over this same field. P-01 validation did not decide that
presentation policy. P-03 re-approval after backward moves remains unresolved.

**Role scoping**:
- **Musician**: sees their songs' stages; can move a song they own; is *prompted* on transitions where they are a listed contributor.
- **Producer**: moves stages for every song in projects they run; is the primary target of transition prompts (they are the capture point per `meta/personas.md`).
- **Operator**: no visibility — the stage of someone's song is not the studio's business.
- **Fan**: no visibility — unreleased work is private by default.

**Synthesis questions answered**:
1. **Shared state conflict**: the Song owns `current_stage` — single writer of record. Board card and table row actions invoke that same write. The selected scope counts unique visible authorized Songs before local filters: board at `0–59`, table at `60+`; a filter cannot change mode. Two people changing the same Song through either presentation remain last-write-wins with the same visible actor-attributed notice. `[PENDING — /ideate-discover Step 5 deepening]` on whether a stage transition needs a lock.
2. **Trigger chain**: approved enum semantic transition → capture prompt → (optionally) credit/split write into domain 02/09. If the prompt is dismissed the transition still commits — **the transition must never be blocked by the prompt**, or users learn to avoid the board. Instead the Song accrues a completeness debt (see `07.08.03`). The approved version maps the existing roster-seed, take-selection, mix-credit, and split-finality semantics; candidate labels cannot silently change those events. This chain is presentation-independent; V1 excludes bulk stage moves.
3. **Permission intersection**: yes — only roster members with a producer-or-owner role can transition a stage through either view (see `07.03.01`). The table never reveals excluded Songs through counts, rows, or ordering.
4. **Notification fan-out**: a transition notifies the roster. `master approved` notifies everyone with a split.
5. **State transition conflict**: a Song demoted through either view after sign-offs were collected marks those approvals superseded (never deleted). **P-03 resolves the re-advance**: they reinstate iff no new version landed in between; otherwise the gate re-collects against its current approver set (`07.05.04` D-07). The predicate is version identity on the append-only timeline, so the outcome is identical from board or table.

### CX-02: Production Stage Board ↔ Release Container

**Relationship**: Release readiness is computed from the board, never typed in. The Release surfaces a
critical-path view against the approved shared enum version's approved-master terminal semantic: "3 of 11
songs are not at the approved-master stage. Earliest realistic date: the slowest one." No candidate label
becomes the gate before P-01 validation and product-owner approval.

**Role scoping**:
- **Musician**: sees the release blocked-by list; this is often the first honest picture they get of their own timeline.
- **Producer**: sees which of their songs is the blocker and is the one who gets chased.
- **Operator**: none.
- **Fan**: none — the release date is not public until the Musician publishes it (domain 12/21).

**Synthesis questions answered**:
1. **Shared state conflict**: the Release owns the tracklist; the Songs own their stages. No contested field — readiness is derived, so there is nothing to merge.
2. **Trigger chain**: the last Song meeting the approved enum version's approved-master terminal semantic flips the Release to `ready to deliver` and hands off to domain 12. A stage write from a table row has the same derived effect for every Release membership of that Song; it does not copy a Song per Release or create a Release-local stage. If domain 12 rejects the package (spec failure), the Release must be able to fall back — `[PENDING — /ideate-discover Step 5 deepening]`. P-02 defines only presentation; P-01 and P-03 boundaries remain unchanged.
3. **Permission intersection**: yes — you can be on the roster of one Song and have no visibility of the Release it sits on (a session player should not see the unannounced album). The table preserves this asymmetry.
4. **Notification fan-out**: readiness flips notify the release owner, not the whole roster.
5. **State transition conflict**: a Song demoted after a Release was marked ready must un-ready the Release. On re-advance, `07.05.04` D-07 decides whether the Song's superseded approvals reinstate or the gate re-collects, and Release readiness recomputes from the resulting stage either way — readiness is derived, so it never needs its own re-approval rule.

### CX-03: Song Record ↔ Release Container

**Relationship**: Membership is many-to-many with per-membership state. The same Song on an album and a
deluxe reissue may point at **different master versions** (album master vs remaster) at different sequence
positions. The membership edge — not the Song — holds the sequence number, the selected master, and any
release-specific edit (radio edit, clean version — see `07.07.02`).

**Role scoping**: `[PENDING — /ideate-discover Step 5 deepening]` — depends on resolving Q-02.

**Synthesis questions answered**: Medium confidence — deferred to Step 5 per the template's rule for Medium/Low entries.
