# Feature: Release Container, Sequencing & Assembly

> **Number**: 07.01.02
> **Parent**: [Song, Release & Production Board](./07.01-song-release-production-board-index.md)
> **Status**: [SURFACE]
> **Last updated**: 2026-07-16

## Overview

The creative assembly of songs into a thing you can release — a single, EP, album, mixtape or deluxe reissue.
It holds the tracklist and its order, the per-track selected master, the gaps and crossfades between tracks,
and the derived readiness picture ("3 songs are not at master; the record cannot ship"). It is deliberately
*not* the DSP delivery pipeline — that is domain 12. This is the part a musician argues about at 2am: what
order do the songs go in.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Full | Creates the release; drags the tracklist into order; picks which master version of each song goes on it; sets inter-track gaps; sees the blocked-by list showing which song is holding the record up. Usually the owner of this decision — sequencing is an artistic call. |
| Producer | Config | Contributes the technical assembly: selects the correct master per track, sets gaps/crossfades and inter-track level relationships, flags songs whose masters are inconsistent in loudness. Does not normally own the running order — they advise. Can be granted Full by the owner. |
| Operator | None | Not their business. A studio has no stake in a client's tracklist. |
| Fan | None | Invisible until domain 12 publishes and domain 21 announces. A tracklist leaking pre-announcement is a real commercial harm — this is why the release container inherits the confidentiality gating of `07.03.03`. |

## Behavior

A Release is a set of memberships, not a folder of copies. Each membership edge holds the sequence position,
the selected master version of that song, and any release-specific variant (radio edit, clean version — see
`07.07.02`). This is what allows one Song to sit on a single, the album and a deluxe reissue at three
positions with three different masters, without duplication.

Readiness is **derived, never declared**. The Release cannot be marked ready; it becomes ready when the last
song on its tracklist reaches `master approved`. This is the anti-lying property: a release date typed into a
box is a wish, whereas a date computed from the stage board is a fact.

Sequencing is a listening activity, not a spreadsheet activity — the running order is judged by playing the
transitions, so the tracklist must be auditionable in order with its real gaps.

### Happy Path

1. Musician creates a Release, picks a type (single / EP / album), names it
2. Adds songs from their catalogue — the picker shows each song's current stage, so an unfinished song can be added deliberately and the consequence is visible immediately
3. Drags them into order; system shows total runtime and the blocked-by list
4. Auditions the sequence — plays the record end to end with real gaps, adjusts gaps at the transitions that feel wrong
5. Songs finish; the board (`07.01.03`) advances; the last `master approved` flips the Release to `ready to deliver`
6. Musician hands off to domain 12 for DSP delivery

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| A song on the tracklist is demoted from `master` back to `mix` | The Release un-readies immediately and names the offender | "No longer ready to deliver — 'Ghost Town' went back to mix" |
| Masters have wildly inconsistent loudness across the tracklist | Detected at assembly, surfaced as an advisory, never a block | "Track 4 is 3.2 LU louder than the record's average" — an advisory the Producer acts on (see `07.07.03`) |
| A song is removed from a release that was already delivered (domain 12) | Refused — a delivered release is frozen; changing it means a new release version | "This release is live. Create a revised version instead." |
| Same song added twice to one tracklist | Allowed (reprises and intros/outros are real) with a confirm | "'Ghost Town' is already at position 3. Add a reprise at position 11?" |
| Contributor on one song opens the Release | Refused — see the permission asymmetry in the parent CX (CX-02) | The song is visible; the release it sits on is not |
| Selected master version is deleted or superseded | The membership pins the *specific version*, not "latest" — it does not silently move | "Track 2 points at v7. A newer master (v9) exists. Update?" |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Loading | Release opened | Tracklist skeleton with runtime placeholder |
| Empty | Release created, no songs | "Add your first song" with a picker showing catalogue + stages |
| Populated | Tracklist has songs | Ordered list, per-track stage badges, running time, blocked-by list |
| Blocked | One or more songs below `master approved` | Ready CTA disabled, with the specific blocking songs named and linked |
| Ready | All songs `master approved` | "Ready to deliver" with the handoff CTA to domain 12 |
| Error | Fetch failed | Error with retry |
| Frozen | Delivered via domain 12 | Read-only tracklist with a "create revised version" affordance |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | Release readiness must be **derived from the stage board**, never a field someone sets | The Operator/Musician failure mode across the industry is a release date agreed before the record is finished, then missed. A derived date cannot be optimistic. It also makes the board load-bearing rather than decorative — people only maintain a board that produces something. | ✅ CONFIRMED — drives the derived-readiness behavior and parent CX-02. |
| DT-02 | Vinyl and cassette impose **side-level** structure (side A / side B, per-side runtime ceilings ~22 min before audio quality degrades) that a flat tracklist cannot express | Physical formats are not a legacy concern — vinyl is a material revenue line for independent artists in 2026, and a sequencer that cannot express sides is unusable for the format that most needs sequencing. Per-side runtime directly affects cut quality. | ✅ CONFIRMED — a flat ordered list is insufficient. The tracklist needs optional side/disc grouping with per-side runtime warnings. Deferred to Step 5 for the runtime thresholds; the structural need is confirmed now. |
| DT-03 | The Release container should also own album art, credits booklet and liner notes | Natural instinct — these ship with the record | ❌ REJECTED — artwork and marketing assets belong to domains 21 (Promotion) and 12 (Release); the credits booklet is a *render* of domain 02's credit graph, not an asset authored here. Pulling them in would make this container the whole product. What it legitimately owns is the tracklist, order, selected masters and gaps. Liner notes being auto-generated from real captured credits is a strong CX to 02 — and a genuine product moment, since today they are retyped from memory. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | Membership edges hold sequence, selected master and variant — the Release does not copy songs | Per parent CX-03: one song on three releases with three different masters is routine. Copying breaks provenance by fragmenting the work. |
| D-02 | Readiness is **derived** from the stage board and cannot be set manually | Per DT-01. |
| D-03 | Selected master is **pinned to a version**, not to "latest" | A release silently changing because someone uploaded a new master is a catastrophic failure mode — this is the `FINAL_v3_ACTUAL` disease with worse consequences. Pinning makes the update an explicit, visible act. |
