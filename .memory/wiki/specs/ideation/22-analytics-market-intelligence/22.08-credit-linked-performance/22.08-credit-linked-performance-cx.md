## Cross-Cut Details

### CX-01: Contribution Catalog ↔ Role-Sliced Attribution

**Relationship**: One rollup, partitioned. The catalog answers "what have I been part of and how is it
doing?"; the role slice answers "how is my *drumming* doing, versus my *mixing*?" Data flows one way —
the slice is a lens, never a second computation. Two computations would eventually disagree, and a
career total that doesn't equal the sum of its role slices is a bug the user will find first.

**Role scoping**:
- **Musician**: the primary case, and the reason the pair exists. personas.md's multi-hyphenate is "a session drummer, occasional mixer, member of two bands" — three careers in one identity, and no existing tool can separate them.
- **Producer**: same mechanics; their slices are production, mixing, engineering, writing.
- **Operator**: none — no credits.
- **Fan**: none.

**Synthesis questions answered**:
1. **Shared state conflict**: none. One rollup, two renderings. The slice never writes.
2. **Trigger chain**: credit graph (domain 02) changes → rollup recomputes → both views update. If a credit is **revoked** (an attestation withdrawn, a dispute upheld), the rollup must shrink — and if 22.08.03 has already exported a proof asserting the larger number, that proof must be invalidated too. Cascading downward through CX-02. This is the sharpest chain in the sub-domain.
3. **Permission intersection**: a contributor sees a record's numbers because they are credited on it. The credit is the permission — which means domain 02's attestation model *is* this sub-domain's access control, and a bug there is a data leak here.
4. **Notification fan-out**: a record the user played on breaking out is genuinely worth telling them ("something you played on is having a moment"). Subject to 22.05.02's noise budget, and to fraud gating (22.06) — the same trap as 22.03.01 DT-03.
5. **State transition conflict**: a credit added while a rollup renders. Snapshot-at-render; low stakes, since the rollup is recomputable and idempotent.

### CX-02: Contribution Catalog ↔ Verified Proof

**Relationship**: The proof is a **public assertion about the rollup**, published onto a service
listing (domain 05) where it does commercial work. Everything the rollup gets wrong, the proof
publishes — with WeJammin's brand attached, which is precisely what makes it worth having and
dangerous to get wrong.

**Role scoping**:
- **Musician**: publishes proof onto their listing — the moment provenance converts into income.
- **Producer**: same; arguably higher-stakes, since their listing *is* their business.
- **Operator**: read-only — they see a proof when evaluating whom to book or hire.
- **Fan**: read-only — a proof on a public listing is visible to anyone, which is the one place a Fan touches this sub-domain at all.

**Synthesis questions answered**:
1. **Shared state conflict**: the proof is derived, but it is **published** — so it has a lifetime independent of the rollup. A snapshot proof that never re-derives will drift from the truth; a live proof changes under the listing without warning. Same fork as 22.05.03 D-01, higher stakes: this one is a commercial claim, not a report. Resolved in 22.08.03 D-02.
2. **Trigger chain**: rollup changes → proof re-derives → listing updates. **A revoked credit must invalidate a published proof.** If it doesn't, WeJammin is publicly asserting a claim it knows to be false — the precise failure D-18 says the platform exists to prevent, committed by the platform itself.
3. **Permission intersection**: the proof is public; the rollup is private. The proof must therefore assert **less** than the rollup knows — a total, not a catalog. Publishing the catalog would leak which records a user played on, and some of those relationships are confidential (ghost production, NDA'd session work). See 22.08.03 DT-02.
4. **Notification fan-out**: does a viewer of a listing get told the proof changed? No — but the owner should know their proof shrank before a client asks about it.
5. **State transition conflict**: proof published, then a source gaps (22.01.03), shrinking the rollup. The proof must degrade honestly rather than silently restate downward. Index D-03.

### CX-03: Role-Sliced Attribution ↔ Verified Proof

**Relationship**: Proof is role-scoped. A drummer's listing asserts drumming credits; a mixing
listing asserts mixing credits. Without the slice, proof is a lifetime total that flatters across
roles — technically true, commercially misleading, and exactly the kind of true-but-misleading claim
that erodes the badge's value for everyone who uses it honestly.

**Role scoping**:
- **Musician**: multiple listings (domain 05) for multiple roles, each with its own proof.
- **Producer**: same.
- **Operator / Fan**: read-only.

**Synthesis questions answered**:
1. **Shared state conflict**: none — the slice is a lens; the proof selects one.
2. **Trigger chain**: role slice → proof scoped to that role. If a credit's **role** is disputed (they were a co-writer, not a producer), the affected role's proof invalidates while others stand.
3. **Permission intersection**: role granularity is domain 02's model. If 02 records "contributor" without a role, this pair is unbuildable — a hard upstream dependency. See 22.08.02 Q-01.
4. **Notification fan-out**: none.
5. **State transition conflict**: none.

Wiring fraud filtering into the proof would put the same filter in a second place, where it can drift. The rule holds here: this sub-domain consumes corrected data and does not re-decide what fraud is. |
