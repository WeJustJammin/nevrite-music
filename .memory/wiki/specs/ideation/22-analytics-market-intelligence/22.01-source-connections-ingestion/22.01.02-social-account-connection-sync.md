# Feature: Social Account Connection & Sync

> **Number**: 22.01.02
> **Parent**: [Source Connections & Ingestion](./22.01-source-connections-ingestion-index.md)
> **Status**: [PARTIAL]
> **Last updated**: 2026-07-17

## Overview

Connecting social accounts (Instagram, TikTok, YouTube, X, Facebook) so that reach and engagement
sit on the same timeline as streams. The point is not vanity metrics — it is the **correlation the
domain index names as its thesis**: a TikTok spike and a streaming spike are only causally legible
when both are on one axis, and no incumbent that lacks the artist's booking data can convert that
correlation into an action.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Full | Connects their own and their bands' social accounts; sees follower/view/engagement series alongside streams; disconnects. The multi-hyphenate case is load-bearing — one human's personal account plus two band accounts, all legitimately theirs, none of them "the" account. |
| Producer | Config | Connects their own professional accounts if they market themselves (many do — a producer's IG *is* their sales funnel, feeding domain 05). Rarely tracks a client's socials; when they do, it is via delegation, not their own grant. |
| Operator | Config | Legitimately present here and nowhere else in 22.01: a venue's own social reach is the venue's marketing asset and feeds domain 21. They connect the venue entity's accounts, not a personal one. |
| Fan | None | Never rendered. A fan's own social accounts are irrelevant to this domain; fan-side social linking, if it exists, is a domain 20 identity concern. |

## Behavior

Mechanically similar to 22.01.01 (OAuth grant → entity selection → backfill → health), but the
physics differ enough to matter, which is why D-01 in the parent index keeps them separate:

- **Retention windows are short and hostile.** Several social APIs expose only a rolling window
  (commonly 28–60 days) of per-post metrics. WeJammin's longitudinal value therefore comes from
  *having been connected*, not from backfilling later. This inverts the usual advice: connecting
  early is worth more than connecting thoroughly, and the UX should say so.
- **Failure is usually transient.** Rate limits dominate; revocation is rarer than on DSPs.
- **Deprecation is permanent and frequent.** Social APIs are withdrawn on short notice with no
  user remedy.
- **Tokens expire on the platform's schedule, not ours.** Meta long-lived tokens last ~60 days;
  others shorter. Re-auth is a routine lifecycle event here, not the exception it is on DSPs — the
  UX must treat "reconnect" as an expected chore, and expiry as `actionable` (it notifies), which
  is the one failure class D-01 does *not* silence.

Disconnect and re-auth are first-class actions, not error recovery: a user disconnects a platform
(history is retained and end-dated per D-02 — the longitudinal record is the value, and it does not
evaporate because the live feed stopped), and re-authorises when a token lapses to resume ingestion
from the gap forward.

### Happy Path

1. User opens Analytics → Connections and picks a social platform.
2. System redirects to the platform's OAuth consent screen, requesting read-only insight scopes.
3. User authorises and selects which pages/profiles/entities to ingest (personal, band, venue).
4. System backfills whatever window the platform permits and states the limit plainly.
5. Series appear on the unified timeline (22.05.01) alongside streams.

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Platform exposes only a 28-day window | Backfill returns 28 days; no more is obtainable at any price | "TikTok only shares the last 28 days. From today, we keep it for you." — stated as a reason to connect now, not as an apology |
| Rate limited (429) | Backoff; health → `degraded`, **no notification** | Nothing. Silence is the correct behavior; alerting on transient failures destroys trust in 22.05.02's alerts |
| Personal account required to read a business page | Grant fails or returns nothing | Platform-specific guidance ("Instagram insights need a Professional account linked to a Page") |
| API deprecated | Health → `terminal`; history retained and end-dated | "X stopped sharing this on 4 June. Your history to that date is kept." |
| Account renamed/handle changed | Entity match may break | Handled by 22.02.03 (match conflict) — the external ID, not the handle, is the join key |
| User connects a social account they don't own (a fan connecting an artist's) | Impossible via OAuth — the grant *is* the ownership proof | N/A — noted because it is the one place where "connection proves ownership" is true here and false in 22.01.01 |
| Access token expires (~60d on Meta, shorter elsewhere) | Ingestion halts at the lapse date; health → `actionable`; **notifies** (this is the one social failure that is not silent, per D-01) | "Reconnect Instagram to keep the data flowing — we've kept everything up to [date]." Reconnect resumes from the gap forward, not from zero |
| Two legitimate owners connect the **same** band/venue entity (multi-hyphenate case) | Connection is keyed on the external entity ID, not the connecting user — the second grant reconciles to the existing connection rather than duplicating the series | Both see the same healthy connection; the second connector is told it is already tracked, by whom is a `[PENDING — Step 5 Must-depth or /write-be-spec]` disclosure/permission question |
| Grant succeeds but platform returns **zero** eligible pages/profiles | Nothing to select; no connection is created | "Authorised, but this account has no pages we can read. Instagram insights require a Professional account linked to a Page." — routes to the same remedy as the wrong-account-type case |
| User disconnects a platform | Live ingestion stops; historical series is retained and end-dated (D-02); no cascade delete | "Disconnected. Your history to [date] stays on your timeline. Reconnect any time to resume." |
| User re-connects after a long lapse | Backfill covers only the platform's rolling window (28–60d); the gap between disconnect and reconnect is unrecoverable at any price (DT-02) | The timeline shows an explicit, labelled gap — never an interpolated line (upholds 22.01.03 D-02: gaps are honest, not hidden) |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Loading | OAuth in flight | Redirect + return spinner |
| Empty | Nothing connected | Empty state framed on correlation: "Connect TikTok to see whether your posts move your streams" |
| Populated | ≥1 healthy connection | Per-platform card with entity, freshness, retention-window note |
| Error | Grant denied / wrong account type | Platform-specific remedy, not a generic error |
| Degraded | Rate limited | Subtle freshness indicator only; no alarm |
| Needs re-auth | Token expired | Reconnect CTA on the platform card; **notifies** — the one actionable social failure (D-01). Existing history stays visible; only the live feed is paused |
| Terminal | API withdrawn | End-dated history, no CTA |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | Social ingestion is a duplicate of DSP ingestion and the two should merge into one connector feature | Sweep listed them as separate candidates; merging is the tidy-looking call | ❌ REJECTED: they share a *shape* but not a *spec*. Retention windows (rolling vs full history), failure classification (transient vs terminal), auth semantics (grant = ownership vs grant ≠ ownership, see 22.01.01 D-01), and cadence all differ. A merged feature would have to spec both branches anyway, and would smuggle the "grant proves ownership" falsehood from socials into DSPs — the exact error 22.01.01 D-01 exists to prevent. |
| DT-02 | A domain expert would expect **short retention windows to be the defining constraint**, and nobody mentioned it | Platform API knowledge; absent from the sweep's candidate description | ✅ CONFIRMED: it inverts the product logic. Because history cannot be bought back, the connection's value accrues from the date of connection — which makes "connect early" the single most valuable onboarding action in the domain, and makes a lapsed connection an unrecoverable loss rather than an inconvenience. This should shape onboarding (domain 01) and the empty state above. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | Transient failures are **silent**; only terminal/actionable failures notify | One noisy rate-limit alert per week trains the user to mute analytics alerts entirely, which breaks 22.05.02 — a `should`-tier feature — to protect a non-event. |
| D-02 | Retention limits are surfaced as a **reason to connect**, not as a disclaimer | Honest and self-serving in the same sentence; the constraint genuinely favours early connection. |
