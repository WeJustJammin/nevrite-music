## Cross-Cut Details

### CX-01: DSP Connection ↔ Ingestion Health

**Relationship**: The connection owns an auth credential with a finite, externally-controlled
lifetime. When it dies, ingestion does not error loudly — it simply stops returning rows, and the
timeline flatlines in a way visually indistinguishable from "your streams stopped". Health is the
feature that distinguishes "we don't know" from "it's zero". Data flows one way: the connection
emits per-attempt outcomes (ok / auth-failed / rate-limited / source-error); health aggregates them
into a per-source freshness state and a named gap range.

**Role scoping**:
- **Musician**: sees the broken connection and the re-auth CTA; is the only one who can fix it for their own identity.
- **Producer**: identical when they hold DSP artist access for their own releases; more often affected as a *consumer* of a gap on someone else's connection (a project's lead artist).
- **Operator**: not affected — no DSP connection of their own.
- **Fan**: no visibility.

**Synthesis questions answered**:
1. **Shared state conflict**: the connection record is owned by 22.01.01/.02; health owns only derived state. No merge conflict — health never writes the connection.
2. **Trigger chain**: an auth failure triggers a health state change → triggers a notification (delivery is a cross-cut, not owned here). If notification fails, health remains correct in-app; the gap is still visible. No rollback needed — health is idempotent and recomputable from attempt history.
3. **Permission intersection**: yes, and it is the sharp edge — a manager/label with delegated read on analytics (domain 01 org scoping) can *see* a broken connection but may not be able to *fix* it, because re-auth requires the DSP-side credential the artist holds. Health must therefore render "broken, and you cannot fix this — ask {identity}".
4. **Notification fan-out**: an auth break notifies the connection owner, and should notify delegated viewers *only* if they depend on it for a scheduled digest (22.05.02) — otherwise it is noise about someone else's password.
5. **State transition conflict**: yes — a re-auth completing while a backfill runs can double-write a date range. Idempotent upsert per (source, entity, metric, date) is the obvious resolution; flagged for `/write-be-spec`.

### CX-02: Social Connection ↔ Ingestion Health

**Relationship**: Same shape as CX-01, different physics. Socials fail by rate limit (transient,
self-healing) and by API deprecation (permanent, unfixable by the user). Health must not scream
"broken" at a transient 429, and must not whisper "retrying" at a permanently dead API. The
classification of a failure as transient-vs-terminal is the actual product decision here.

**Role scoping**:
- **Musician**: primary — their socials are their reach.
- **Producer**: config-level; less likely to track social reach as a career metric.
- **Operator**: config-level — a venue's own social reach matters to them for domain 21, and this is where the Operator legitimately appears in domain 22.
- **Fan**: no visibility.

**Synthesis questions answered**:
1. **Shared state conflict**: none — same one-way derivation as CX-01.
2. **Trigger chain**: rate-limit → backoff → health stays `degraded`, not `broken`. Deprecation → health goes `terminal` and the source is retired from the timeline with its history retained and end-dated.
3. **Permission intersection**: `[PENDING — /ideate-discover Step 5 deepening]` — depends on domain 01's org delegation model.
4. **Notification fan-out**: transient failures must never notify. This is a hard rule; violating it trains users to ignore all analytics alerts, which then breaks 22.05.02.
5. **State transition conflict**: a metric window that shortens (platform reduces retention from 60→28 days) silently truncates history. Health must end-date rather than delete. Flagged for Step 5.

### CX-03: Manual Import ↔ DSP Connection

**Relationship**: Both write the same logical series. When they disagree for the same date, someone
must win, and the losing number must not vanish. Provenance-of-the-number is the design question —
which is thematically the whole product (D-18).

**Role scoping**:
- **Musician**: sees a conflict badge and picks a source of truth, or accepts the default precedence.
- **Producer**: same.
- **Operator / Fan**: no visibility.

**Synthesis questions answered**:
1. **Shared state conflict**: unresolved — `[PENDING — /ideate-discover Step 5 deepening]`. Candidate precedence: live DSP connection > distributor file > manual entry, with the superseded value retained and inspectable rather than overwritten.
2. **Trigger chain**: import → conflict detection → user prompt. Async; a conflict never blocks the import.
3. **Permission intersection**: whoever can import can override — which is a quiet integrity risk if a delegated manager can silently inflate a number the artist then quotes commercially. Flagged.
4. **Notification fan-out**: `[PENDING — Step 5]`.
5. **State transition conflict**: yes — see CX-01 Q5, same idempotency requirement.

### CX-04: Manual Import ↔ Ingestion Health

**Relationship**: Health names a gap; import fills it. This makes the two features a loop rather
than a pair, which is the strongest argument that 22.01 is a genuine sub-domain rather than four
loose files.

**Role scoping**:
- **Musician**: offered "import a file to fill March 2–14" directly from the gap.
- **Producer**: same.
- **Operator / Fan**: no visibility.

**Synthesis questions answered**: `[PENDING — /ideate-discover Step 5 deepening]` — this is a
Medium-confidence pair; synthesis deferred per the CX template's Medium/Low rule.
