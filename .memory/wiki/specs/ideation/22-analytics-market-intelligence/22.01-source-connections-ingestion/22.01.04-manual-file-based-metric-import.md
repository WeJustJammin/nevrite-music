# Feature: Manual & File-Based Metric Import

> **Number**: 22.01.04
> **Parent**: [Source Connections & Ingestion](./22.01-source-connections-ingestion-index.md)
> **Status**: [SURFACE]
> **Last updated**: 2026-07-16

## Overview

Importing performance data from files — a distributor's monthly CSV, a label statement, a DSP's own
export — for the very common case where no live connection is possible or permitted. This is the
fallback that keeps the domain viable if partner-level DSP API access turns out to be unobtainable
(22.01 Q-01), and it is the only route to data for a session musician who played on a record whose
Spotify for Artists account belongs to someone else.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Full | Uploads a distributor or label file; maps its columns once; sees the parsed series land on the same timeline as connected sources; resolves conflicts where a file disagrees with a live connection. For the session player with no DSP access, this is the *only* way their work's numbers ever appear. |
| Producer | Full | Same, plus the client-work case: a producer holding a label statement for a record they produced can import it to complete a project's performance picture without needing the artist's credentials. |
| Operator | None | No file-based performance data exists in a venue's world. Box-office numbers are domain 19's, first-party and native — importing them here would duplicate an authoritative source with a worse copy. |
| Fan | None | Never rendered. |

## Behavior

A file import is a **claim about numbers**, not an observation of them, and the design must never
forget the difference. A connected DSP series is attested by the DSP; an uploaded CSV is attested by
whoever uploaded it. Given the platform's thesis is provenance (D-18), the provenance *of a metric*
is not an afterthought here — an imported number must be visibly distinguishable from a fetched one
everywhere it appears, most sharply when 22.08.03 exports it as commercial proof.

Distributor reporting also lags (commonly 30–60 days) and is **royalty-eligible plays**, not raw
plays — a materially different number from the DSP dashboard's. Presenting them as the same series
would be the exact confident-wrongness 22.01.03 exists to prevent.

### Happy Path

1. User uploads a file (CSV/TSV/XLSX) from a distributor or label.
2. System detects a known format (DistroKid, TuneCore, CD Baby, Symphonic, Believe…) or falls back to manual column mapping.
3. User maps columns to metrics (date, ISRC/UPC, territory, platform, plays) and confirms; mapping is remembered for that source.
4. System matches rows to catalog entities via 22.02.02 (ISRC/UPC), reports what matched and what didn't.
5. User reviews a preview — matched rows, unmatched rows, conflicts with existing data — before anything is committed.
6. User commits; series land, tagged as imported with the file and date as their provenance.

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| File disagrees with a live connection for the same date | Conflict flagged; neither value is destroyed | Side-by-side with the precedence rule applied and the superseded value inspectable. See `22.01-source-connections-ingestion-cx.md#CX-03` |
| Rows reference ISRCs not in the user's catalog | Rows quarantined, not dropped silently | "412 rows reference recordings we can't match to you" + hand-off to 22.02.02/22.02.03 |
| Royalty-eligible plays imported alongside raw DSP plays | Kept as **distinct metrics**, never summed | Labelled distinctly; a chart mixing them without saying so is banned |
| Same file uploaded twice | Idempotent — detected and no-oped | "This file was already imported on 3 June" |
| Overlapping files (Jan–Mar, then Feb–Apr) | Overlap detected; per-date precedence applied | Explicit overlap report, not a silent double-count |
| Unknown/garbled format | Falls back to manual mapping; never guesses | Mapping UI with a data preview |
| A user inflates numbers by hand-editing a CSV | Import succeeds — we cannot detect this | Imported provenance is carried forever and rendered at every export point. See D-02 and Q-02 |
| Currency/territory columns present | `[PENDING — /ideate-discover Step 5 deepening]` — overlaps domain 10's royalty ingestion; boundary unresolved | `[PENDING]` |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Loading | Parsing/matching in flight | Progress with row counts |
| Empty | No imports yet | Empty state naming the two real reasons to use this: no DSP access, or history from before you joined |
| Preview | Parsed, not committed | Matched/unmatched/conflicting breakdown; commit is explicit |
| Populated | Committed | Series on the timeline, provenance-tagged |
| Error | Unparseable file | Row/column-specific error, never "invalid file" |
| Partial | Some rows matched | Committed matched rows + a quarantine the user can work through |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | This duplicates domain 10 (Royalties & Collections), which also ingests distributor statements | Cross-domain overlap reasoning | ⚠️ PARTIALLY CONFIRMED — a real boundary problem, recorded honestly rather than resolved by fiat. The **same file** carries both money (10's concern: what was I paid) and plays (22's concern: how is it performing). Parsing it twice in two domains is a duplicated integration and two chances to disagree. Proposed boundary: **domain 10 owns statement ingestion and parsing; domain 22 subscribes to the play-count series it produces** — one parser, two consumers. But that inverts the dependency (22 would depend on 10 shipping first, which MoSCoW may not honour), so it is escalated rather than assumed. See Q-01 and the domain CX file. |
| DT-02 | A domain expert would expect imported and fetched numbers to be **visibly different forever**, and nobody mentioned it | Provenance reasoning applied reflexively to our own data | ✅ CONFIRMED: an imported number is a self-claim; a fetched number is an attestation. The platform's whole pitch (D-18, and 22.08.03's "verified proof") collapses if a hand-typed figure can be exported wearing the same badge as an API-fetched one. The distinction must survive every rollup, share and export — which makes it a schema-level requirement, not a UI nicety. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | Royalty-eligible plays and raw plays are **distinct metrics**, never summed or silently substituted | They differ by a material margin and by definition. Merging them produces a number that is wrong in a way nobody can later diagnose. |
| D-02 | Import provenance is **permanent and travels to every export** | DT-02. Self-claimed data must never be exportable as verified proof. |
| D-03 | Import is **preview-then-commit**, never fire-and-forget | Imports are bulk, overlapping and hard to reverse; a silent double-count is discovered months later, at exactly the moment the number is being quoted commercially. |
