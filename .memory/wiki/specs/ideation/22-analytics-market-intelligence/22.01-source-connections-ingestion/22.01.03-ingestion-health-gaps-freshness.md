# Feature: Ingestion Health, Gaps & Data Freshness

> **Number**: 22.01.03
> **Parent**: [Source Connections & Ingestion](./22.01-source-connections-ingestion-index.md)
> **Status**: [DEEP]
> **Last updated**: 2026-07-17

## Overview

The feature that makes the platform admit what it doesn't know. Every connected source has a
freshness state and a set of named gaps; every chart, digest and insight downstream is annotated
with the honesty of the data behind it. This exists because the failure mode of an analytics
product is not being wrong — it is being **confidently wrong**: a flatline caused by a dead token
looks exactly like a flatline caused by nobody listening, and the user will act on the difference.

Health is **derived, read-only state**. It never writes to a connection record; it reads the
per-attempt outcome log emitted by 22.01.01/.02/.04 and computes three products: a per-source
**freshness state**, a set of **named gap ranges** per `(source, entity, metric)`, and a
per-rollup **coverage annotation** that decides whether a downstream number may be stated at all.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Full | Sees a per-source health panel and gap markers rendered directly on their charts; acts on the remedy (re-auth, import a file via 22.01.04, or accept that nothing can be done); is the only actor who can repair a connection they own. Multi-hyphenate case: one human sees health for their personal DSP grant, two band-entity grants, and any project sources delegated to them — each with an independent state and its own remedy path. |
| Producer | Full | Same, plus the case that matters more to them: a gap on a *project's* source that corrupts a client deliverable. A producer sending a client a performance report needs to know the report has a hole before the client finds it. When the Musician and Producer are the same human (multi-hyphenate), health is scoped per-identity-context, not merged — a gap on their personal artist grant must not silently degrade a client-project rollup they are viewing as Producer. |
| Operator | Read-only | Sees freshness on the venue-social sources they configured (22.01.02) and on any 22.04 market data they read; cannot repair sources they do not own. Their exposure is small but non-zero — a routing decision made on stale data costs a real booking. |
| Fan | None | Never rendered. A fan seeing public artist stats (domain 01/20) is shown a value or nothing — never a gap explanation. The honesty obligation is to the data's owner, not to the audience. Rationale: a gap explanation exposes which of an artist's sources are broken, which is operational information about the artist that a fan has no standing to receive. |

## Behavior

Health reads attempt outcomes and computes, never mutating source data. The three load-bearing
distinctions:

1. **"zero" vs "unknown"** — these must never render identically. A gap is drawn as a break in
   the series, not as a value of `0` and not as an interpolated line through it. Interpolation is
   banned (D-01): a smoothed line across a gap is a fabricated fact, and this platform's entire
   thesis (D-18) is that fabricated facts are the disease.
2. **transient vs terminal** — decides whether the user is told anything at all (22.01.02 D-01).
   A transient failure (`degraded`) is silent; only user-actionable (`broken`) or permanent
   (`terminal`) failures surface, and each surfaces differently.
3. **attested vs claimed** — a range filled by a live-connection sync is attested; a range filled
   by manual import (22.01.04) is a self-claim. Health carries this provenance forward, and a
   claim-filled range does **not** count as attested coverage in a rollup (see the coverage rule
   below and D-05). This is what stops import from laundering a gap into fake verified proof.

### Freshness state machine (per source, per entity)

Cadence = the source's declared expected sync interval (DSP daily-batch ≈ 24h; social varies by
platform, declared by the connector). Ages are measured from the last successful sync.

| State | Entry condition | Exit condition |
|-------|-----------------|----------------|
| `fresh` | Last successful sync age ≤ 1× cadence | Age crosses 1× cadence, or an attempt fails |
| `stale` | 1× < age ≤ 3× cadence, **no** auth failure recorded | A successful sync → `fresh`; auth failure → `broken`; age > 3× → gap opens, stays `stale` until repaired or reclassified |
| `degraded` | Most recent attempt(s) failed transiently (HTTP 429 or 5xx) and backoff is active | A successful sync → `fresh`; a 401/403 `invalid_grant` → `broken`; connector-withdrawn flag → `terminal` |
| `broken` | An attempt returned auth failure (401/403, `invalid_grant`, `token_revoked`) | User completes re-auth (22.01.01/.02) and next sync succeeds → `fresh` |
| `terminal` | Connector marked API-withdrawn by 22.01.02's deprecation flag | Never automatically — only if the platform restores the API and an operator re-enables the connector |

A **named gap** `[start, end]` for `(source, entity, metric)` opens only when the source is
`broken`, or `stale` past 3× cadence with no successful rows in the window. `degraded` never opens
a gap — the data is late, not missing. `terminal` end-dates history rather than opening a gap —
there is no future data to be missing.

### The Coverage Rule — when a rollup may refuse to state a number (resolves Q-01)

A rollup (chiefly 22.08 Credit-Linked Performance) aggregates one metric across many sources the
user may not individually control. The honesty question — "when is this rollup too incomplete to
state?" — is answered by a **dual gate** computed at query time over the query window:

Let `M` = the set of sources known to have ever contributed to this `(entity, metric)` rollup.
Let `A` ⊆ `M` = sources whose state over the window is `fresh` or `stale` **with no open gap
overlapping the window**, contributing an **attested** value (not import-claimed).
Let **coverage ratio** `c = |A| / |M|`.
Let `dominant-loss` = the largest single-source share of the rollup's total in the last **complete**
prior window, among sources currently in `A`'s complement (i.e. missing/broken/terminal/claim-only).

| Condition | Rollup rendering |
|-----------|------------------|
| `c = 1.0` **and** dominant-loss = 0 | State the number plainly. |
| `0.80 ≤ c < 1.0` **and** dominant-loss < 0.20 | State as a **floor**: "≥ X (N of M sources; {named source} missing {range})". Never a bare headline number. |
| `c < 0.80` **or** dominant-loss ≥ 0.20 | **Refuse to state a single figure.** Render "at least X across N of M sources" with every gap named. A dominant source worth ≥20% of last window's total forces refusal regardless of `c`, because one big dead source makes a high source-count ratio a lie. |

Thresholds (`0.80`, `0.20`, the 3× cadence gap trigger) are **defaults**, tunable **only upward**
(stricter) by the user, never downward — an honesty floor a user can lower is not a floor (DT-04).
The refusal is the honest analogue of interpolation's ban: where D-01 forbids fabricating a value
inside a gap, the coverage rule forbids fabricating a *total* over gaps.

### Happy Path

1. User opens the dashboard; every chart renders with its sources' freshness inline.
2. All sources `fresh`; no gap markers; no interruption. The feature's best day is invisible.
3. User opens the Connections panel and sees per-source "last synced 4 hours ago, next in 8".
4. A rollup on the same screen shows a plain number because `c = 1.0` and dominant-loss = 0.

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Token revoked 11 days ago, unnoticed | Gap named from last-successful-sync; source → `broken`; notification fires once | "Spotify: 11 days missing (3–14 March). This is missing data, not zero streams." + Reconnect |
| Gap on a source feeding a scheduled digest (22.05.02) | Digest still sends, carrying the gap prominently rather than shipping a clean-looking lie | Digest header: "Incomplete — Spotify missing since 3 March" |
| Gap on a source feeding a **shared** report (22.05.03) | Gap travels with the report to its viewer | The label/manager sees the same hole the artist sees — the report cannot be laundered clean by sharing it |
| DSP restates history (revises last week's numbers downward) | Series corrected; restatement recorded and disclosed, not silently applied | "Spotify revised 3–9 March down by 4%." — because a user who screenshotted the old number needs to know why it moved |
| DSP restates a day **to zero** (takedown vs revision) | Distinguished from a gap: an attested zero is a real value, not absence — but a full-catalog restatement-to-zero is flagged as suspicious (possible takedown/dispute), not silently accepted | "Spotify now reports 0 for 3 March (was 4,102). This looks like a takedown, not a normal revision." |
| Rate limit (transient, HTTP 429) | `degraded`; exponential backoff; no notification, no gap (data isn't missing, it's late) | Freshness indicator only |
| Source terminal (API withdrawn) | History end-dated; no gap opened | "Ends 12 May — Deezer no longer shares this" |
| Backfill still running | Not a gap; a boundary marker | "History loading back to 2023-01-01" |
| Every source broken at once | Dashboard renders as unknown, not as zero; rollups refuse (`c = 0`) | Whole-dashboard banner; charts suppressed rather than shown at zero |
| **Concurrency** — re-auth completes while a backfill for the same window runs | Both paths carry the same `(source,entity,metric,date)` rows; identical rows resolve to a single stored value rather than accumulating, so the same day is never counted twice; the gap closes once, not twice (write strategy → `/write-be-spec`) | Gap marker clears; no duplicated spike; "History updated" |
| **Race** — a restatement arrives for a date the user is currently viewing | View is not mutated mid-read; the change is queued and surfaced as a non-destructive banner on next render, with the old value retrievable | "This number changed while you were looking. Refresh to see 3,940 (was 4,102)." |
| **Race** — two adjacent gaps become contiguous (source broken across a boundary) | Gaps merge into one named range rather than rendering two touching breaks | Single "3–21 March missing" not two abutting markers |
| **Partial data** — rollup has 6 of 8 sources fresh, 2 broken, neither dominant | Coverage `c = 0.75` < 0.80 → refuse single figure | "At least 41,200 streams across 6 of 8 sources — 2 missing (see below)" |
| **Partial data** — 7 of 8 sources fresh but the missing one was 55% of last window | `c = 0.875` but dominant-loss = 0.55 ≥ 0.20 → refuse | "Can't total this — your largest source (Spotify) is missing 3–14 March" |
| **Permission** — delegated manager (domain 01 org scope) views a broken source they cannot re-auth | Health renders broken + the identity who *can* fix it; the Reconnect CTA is disabled for the delegate | "Broken — only {artist} can reconnect this. Ask them to re-auth Spotify." |
| **Permission** — delegate depends on the broken source for a scheduled digest | Delegate is notified (they have a stake); a delegate with no dependent digest is **not** notified (it's noise about someone else's password) | Digest-dependent delegate: one alert. Others: nothing. |
| **Malicious input** — a delegated importer fills a real gap with a fabricated CSV to inflate a rollup exported as proof | The import-filled range is provenance-tagged `claimed`, counts as `stale`-equivalent (not attested), and is **excluded from `A`** in the coverage ratio; 22.08.03 export shows the range as unverified | Rollup does not treat the filled range as verified; export badge reads "N days self-reported, not verified" |
| **Malicious input** — repeated forced auth failures on a rival's source to fake `broken` | Not possible cross-account: health reads only the owner's own attempt log; a third party cannot inject attempt outcomes into a source they don't own | N/A — cross-account gap injection is structurally impossible |
| **Network failure** — health cannot read the attempt-outcome log itself (its own dependency down) | Health degrades to "unknown health", never asserts `fresh`; charts show "freshness unavailable" rather than a false green | "Can't confirm how fresh this is right now" — never a stale green tick |
| **Empty** — user has zero connected sources | No health to compute; deferred to 22.01.01/.02 empty states | "Connect a source to see performance" (owned by .01/.02) |
| **Multi-hyphenate in two roles** — same human holds a broken personal-artist grant and views a client project as Producer | Health is scoped per identity-context; the personal grant's `broken` state does not degrade the client-project rollup, and vice versa | Producer-context view unaffected by the personal-artist break; each context shows only its own health |
| Metric-retention window shortens (social platform drops 60→28 days) | History end-dated at the new boundary, not deleted; not a gap (the platform never had it to give) | "TikTok now keeps only 28 days; your older history is preserved by us" |
| Clock skew — a source reports a sync timestamp in the future | Timestamp clamped to server-now for freshness math; anomaly logged; never yields a negative age that would fake `fresh` | Freshness computed from server time, not the source's claimed time |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Loading | Health recomputing after an attempt outcome arrives | Prior freshness shown with a subtle "updating" tick; never blanks to a false state |
| Empty | No sources connected | Deferred to 22.01.01/.02 empty states |
| Populated | ≥1 source with computed health | Per-source freshness + any gap markers inline on charts |
| Error | Health's own attempt-log read fails | "Freshness unavailable" — explicitly not `fresh`, never a false green |
| Partial | Some sources healthy, some in gap/broken | Mixed panel; affected charts carry per-source gap markers; rollups apply the coverage rule |
| Fresh | Last sync within 1× cadence | Quiet timestamp |
| Stale | Sync overdue (1–3× cadence), cause unknown | "Last updated 3 days ago" — surfaced, not alarmed |
| Degraded | Transient failure (429/5xx) in backoff | Freshness timestamp only; deliberately no alarm |
| Broken | Auth failure — user-fixable | Named gap + Reconnect CTA (disabled for non-owners) |
| Terminal | API withdrawn — not user-fixable | End-dated history, no CTA, no nagging |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | Ingestion health is an ops/monitoring concern and belongs on an internal dashboard, not in the product | Node Classification Gate — "NFR wearing a product costume?" | ❌ REJECTED: the *pipeline's* health is ops. The *user's* health is product, because the remedy is exclusively user-side — only the artist holds the credential to re-auth. An ops dashboard cannot fix a revoked token; only a prompted human can. The moment a remedy requires the user, the state is product. |
| DT-02 | What breaks at the intersection with 22.08 (Credit-Linked Performance)? | Cross-domain failure reasoning | ✅ CONFIRMED — and it escalates this feature to `must`. 22.08's headline number ("the records I played on are doing X") is a **rollup across many releases the Musician does not control**, assembled from sources with independent failure states. One dead source silently shrinks a session player's apparent career. Worse, 22.08.03 exports that number as *verified proof* onto a service listing — so a gap makes WeJammin's provenance claim false in a commercial context. Health is what stops the wedge from cutting the wrong way. |
| DT-03 | Users will ignore health warnings the way they ignore every other warning | Behavioral realism | ✅ CONFIRMED, and it changes the design: warnings attach to **the number**, not to a settings panel nobody visits. A gap marker on the chart the user is reading is unignorable; a red dot on a Connections page is not. This is also why interpolation is banned — interpolation is the affordance that lets a user ignore a gap. |
| DT-04 | The coverage threshold should be user-configurable in both directions so power users can loosen it | Reflexive "make it a setting" instinct | ❌ REJECTED asymmetrically: a floor a user can *lower* is not a floor — the first person to lower it is the person about to quote the number commercially, which is exactly who must not. Tunable **upward only** (stricter). Confirmed as D-06. |
| DT-05 | A gap on any broken source should degrade every rollup on the dashboard | Naive "any failure taints everything" reasoning | ❌ REJECTED: gap relevance is per-`(entity, metric)`. A broken TikTok connection must not degrade a *streams* rollup it never fed. Scoping gaps to the metrics they actually contribute to is what keeps the coverage rule from crying wolf and re-triggering DT-03's warning-blindness. Confirmed as D-07. |
| DT-06 | A downward restatement is just a special case of a gap and can share the same rendering | Data-model economy | ❌ REJECTED: a restatement is *attested new truth* (the source affirmatively says "it was less"); a gap is *absence* (the source says nothing). Rendering them identically would tell a user "we lost this data" when the source actually corrected it — a different and more alarming lie. A restatement **to zero**, however, is ambiguous between correction and takedown and must be flagged as suspicious, not accepted silently. Confirmed as D-04's extension and the takedown edge case. |
| DT-07 | Health can assert `fresh` by default when it cannot read the attempt log, since "no failures seen" looks healthy | Fail-open convenience | ❌ REJECTED: absence of evidence is not freshness. If health's own input is unavailable it must render "freshness unavailable", never a green tick — a false `fresh` is the single most dangerous state this feature can emit, because it is confident-wrongness about confidence itself. Fail closed to "unknown". Confirmed as D-08. |

## Cross-Cut Notes

_These feed Step 6 (cross-cut synthesis) — each names a concrete mechanism, not a vague adjacency._

- **Shared entity / one-way derivation** — Touches **22.01.01 / 22.01.02** (attempt-outcome producers). Health consumes their per-attempt outcomes (`ok` / `auth-failed` / `rate-limited` / `source-error`) and never writes back. See `22.01-source-connections-ingestion-cx.md#CX-01` and `#CX-02`. State-race: re-auth-during-backfill must never double-count a date whose rows arrive via both paths — the required-behavior is single-value-per-`(source,entity,metric,date)`; the write mechanism that guarantees it is flagged for `/write-be-spec`.
- **Trigger dependency / remedy loop** — Touches **22.01.04 Manual Import** ([22.01.04](./22.01.04-manual-file-based-metric-import.md)). Import is the remedy this feature offers for a named gap, and import-filled ranges return here tagged `claimed`, which the coverage rule must exclude from attested coverage. See `#CX-04`. This is a two-way loop, not a pointer.
- **Notification fan-out** — Cross-cut mechanism **Notification & Alert Delivery** (domain-CX, platform-wide). This feature decides *what* is worth telling (only `broken`/`terminal`, never `degraded`) and *whom* (owner always; delegates only if they hold a dependent digest). Delivery is the platform mechanism; the fan-out rule is owned here. Feeds Step 6.
- **Permission intersection** — Touches **domain 01 (Identity / org delegation)**. A delegate can *see* a broken source but cannot *fix* it; health must render the fixer's identity and disable the CTA for non-owners. The delegation model that scopes "who can re-auth" is owned by domain 01 and consumed here — genuine upstream dependency.
- **Widest internal dependency** — Touches **22.05 Cross-Source Dashboard & Reporting** ([22.05](../22.05-cross-source-dashboard-reporting/22.05-cross-source-dashboard-reporting-index.md)). Every chart, digest and shared report carries this feature's annotation; the coverage rule gates what 22.05 may display and what 22.05.03 may share.
- **Commercial-proof integrity** — Touches **22.08 Credit-Linked Performance** ([22.08](../22.08-credit-linked-performance/22.08-credit-linked-performance-index.md)). See DT-02. The coverage rule (this file) is the gate that decides whether 22.08.03 may export a number as verified proof or must downgrade it to "self-reported / partial".

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | **Interpolation across gaps is banned** | A smoothed line across missing data is a fabricated fact presented as an observation. D-18 makes fabricated facts the disease this platform treats; drawing one in our own chart would be self-refuting. |
| D-02 | Gaps annotate **the number**, not a settings page | DT-03. Warnings placed where the user isn't are decorative. |
| D-03 | Gaps **travel with shared reports and digests** | Otherwise sharing becomes a laundering mechanism: the artist sees the hole, the label sees a clean chart. |
| D-04 | Restatements are **recorded and disclosed**, not silently applied; a restatement-to-zero is flagged as a suspected takedown | DSPs revise history routinely. A number that changes without explanation is indistinguishable from a bug; a silent drop to zero is indistinguishable from a takedown, and the two demand different user responses. |
| D-05 | Import-filled ranges are tagged `claimed` and **excluded from attested coverage** | Resolves the laundering risk in the malicious-import edge case. A self-claim must never count toward a rollup exported as verified proof. |
| D-06 | The coverage threshold is tunable **upward only** (stricter), never downward | DT-04. A floor a user can lower is not a floor. Defaults: `c ≥ 0.80` and dominant-loss `< 0.20` to state a floored number; below that, refuse. |
| D-07 | Gap relevance is scoped per **`(entity, metric)`**, not per dashboard | DT-05. A broken source degrades only the rollups it actually feeds, so the coverage rule never cries wolf. |
| D-08 | Health **fails closed to "unknown"**, never open to `fresh` | DT-07. A false `fresh` is confident-wrongness about confidence itself — the worst state this feature can emit. |
