# Feature: Ingestion Health, Gaps & Data Freshness

> **Number**: 22.01.03
> **Parent**: [Source Connections & Ingestion](./22.01-source-connections-ingestion-index.md)
> **Status**: [SURFACE]
> **Last updated**: 2026-07-16

## Overview

The feature that makes the platform admit what it doesn't know. Every connected source has a
freshness state and a set of named gaps; every chart, digest and insight downstream is annotated
with the honesty of the data behind it. This exists because the failure mode of an analytics
product is not being wrong — it is being **confidently wrong**: a flatline caused by a dead token
looks exactly like a flatline caused by nobody listening, and the user will act on the difference.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Full | Sees a per-source health panel and gap markers rendered directly on their charts; acts on the remedy (re-auth, import a file, or accept that nothing can be done); is the only one who can fix a connection they own. |
| Producer | Full | Same, plus the case that matters more to them: a gap on a *project's* source that corrupts a client deliverable. A producer sending a client a performance report needs to know the report has a hole before the client finds it. |
| Operator | Read-only | Sees freshness on the venue-social sources they configured (22.01.02) and on any 22.04 market data they read; cannot repair sources they do not own. Their exposure is small but non-zero — a routing decision made on stale data costs a real booking. |
| Fan | None | Never rendered. A fan seeing public artist stats (domain 01/20) is shown a value or nothing — never a gap explanation. The honesty obligation is to the data's owner, not to the audience. |

## Behavior

Health is **derived state** — it never writes to a connection, it reads attempt outcomes and
computes: a per-source freshness (`fresh` / `stale` / `degraded` / `broken` / `terminal`), a set of
named gap ranges per (source, entity, metric), and a per-chart honesty annotation consumed by
22.05.

The load-bearing distinction is **"zero" vs "unknown"**. These must never render identically.
A gap is drawn as a break in the series, not as a value of zero and not as an interpolated line
through it. Interpolation is banned in this domain: a smoothed line across a gap is a fabricated
fact, and this platform's entire thesis (D-18) is that fabricated facts are the disease.

The second distinction is **transient vs terminal**, which decides whether the user is told
anything at all (22.01.02 D-01).

### Happy Path

1. User opens the dashboard; every chart renders with its sources' freshness inline.
2. All sources `fresh`; no gap markers; no interruption. The feature's best day is invisible.
3. User opens the Connections panel and sees per-source "last synced 4 hours ago, next in 8".

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Token revoked 11 days ago, unnoticed | Gap named from last-successful-sync; source → `broken`; notification fires | "Spotify: 11 days missing (3–14 March). This is missing data, not zero streams." + Reconnect |
| Gap on a source feeding a scheduled digest | Digest still sends, but carries the gap prominently rather than shipping a clean-looking lie | Digest header: "Incomplete — Spotify missing since 3 March" |
| Gap on a source feeding a **shared** report (22.05.03) | Gap travels with the report to its viewer | The label/manager sees the same hole the artist sees — the report cannot be laundered clean by sharing it |
| DSP restates history (revises last week's numbers downward) | Series is corrected; the restatement is recorded, not silently applied | "Spotify revised 3–9 March down by 4%." — because a user who screenshotted the old number needs to know why it moved |
| Rate limit (transient) | `degraded`; backoff; no notification, no gap (data isn't missing, it's late) | Freshness indicator only |
| Source terminal (API withdrawn) | History end-dated; no gap opened (there is no future data to be missing) | "Ends 12 May — Deezer no longer shares this" |
| Backfill still running | Not a gap; a boundary | "History loading back to 2023-01-01" |
| Every source broken at once | Dashboard renders as unknown, not as zero | Whole-dashboard banner; charts suppressed rather than shown at zero |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Fresh | Last sync within source's expected cadence | Quiet timestamp |
| Stale | Sync overdue, cause unknown | "Last updated 3 days ago" — surfaced, not alarmed |
| Degraded | Transient failure (rate limit) in backoff | Freshness timestamp only; deliberately no alarm |
| Broken | Auth failure — user-fixable | Named gap + Reconnect CTA |
| Terminal | API withdrawn — not user-fixable | End-dated history, no CTA, no nagging |
| Empty | No sources connected | Deferred to 22.01.01/.02 empty states |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | Ingestion health is an ops/monitoring concern and belongs on an internal dashboard, not in the product | Node Classification Gate — "NFR wearing a product costume?" | ❌ REJECTED: the *pipeline's* health is ops. The *user's* health is product, because the remedy is exclusively user-side — only the artist holds the credential to re-auth. An ops dashboard cannot fix a revoked token; only a prompted human can. The moment a remedy requires the user, the state is product. |
| DT-02 | What breaks at the intersection with 22.08 (Credit-Linked Performance)? | Cross-domain failure reasoning | ✅ CONFIRMED — and it escalates this feature to `must`. 22.08 is proposed `must` because it is the domain's only thesis-aligned node: "the records I played on are doing X." That number is a **rollup across many releases the Musician does not control**, so it is assembled from a patchwork of sources with independent failure states. One dead source silently shrinks a session player's apparent career. Worse, 22.08.03 exports that number as *verified proof* onto a service listing — so a gap doesn't just mislead the user, it makes WeJammin's provenance claim false in a commercial context. Health is what stops the wedge from cutting the wrong way. |
| DT-03 | Users will ignore health warnings the way they ignore every other warning | Behavioral realism | ✅ CONFIRMED, and it changes the design: warnings are attached to **the number**, not to a settings panel nobody visits. A gap marker on the chart the user is currently reading is unignorable; a red dot on a Connections page is not. This is also why interpolation is banned — interpolation is precisely the affordance that lets a user ignore a gap. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | **Interpolation across gaps is banned** | A smoothed line across missing data is a fabricated fact presented as an observation. D-18 makes fabricated facts the disease this platform treats; drawing one in our own chart would be self-refuting. |
| D-02 | Gaps annotate **the number**, not a settings page | DT-03. Warnings placed where the user isn't are decorative. |
| D-03 | Gaps **travel with shared reports and digests** | Otherwise sharing becomes a laundering mechanism: the artist sees the hole, the label sees a clean chart. |
| D-04 | Restatements are **recorded and disclosed**, not silently applied | DSPs revise history routinely. A number that changes without explanation is indistinguishable from a bug, and destroys trust in every other number. |
