# Feature: DSP Account Connection & Sync

> **Number**: 22.01.01
> **Parent**: [Source Connections & Ingestion](./22.01-source-connections-ingestion-index.md)
> **Status**: [DEEP]
> **Last updated**: 2026-07-17

## Overview

The user-facing act of connecting a streaming platform's artist-analytics account (Spotify for
Artists, Apple Music for Artists, YouTube Studio/Music, Amazon Music for Artists, Deezer Backstage)
to a WeJammin identity, and keeping that connection alive as tokens expire and platforms revoke.
This is the supply valve for the entire domain: with no DSP connection, 22.05's dashboard is empty
and 22.08's credit-linked performance — the domain's thesis-aligned reason to exist — cannot be
computed at all.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Full | Connects each DSP artist account they control; sees which of their artist profiles are linked; re-authorises when a token dies; disconnects and chooses whether ingested history is retained or purged. For records they *played on* but do not control, they connect nothing — the data arrives via the release's rights-holder connection (as a delegated reader, D-03) or via manual import (22.01.04), or not at all (see Q-01, and 22.08 Q-01). |
| Producer | Full | Identical mechanics, different motive: connects DSP accounts for releases they own or co-own, and — where a project's artist has delegated it (domain 01 org scoping) — sees the connection health for the project's releases as a **delegated reader** without holding the credential themselves. |
| Operator | None | Venues and studios have no DSP artist account. Not rendered; the analytics surface a venue sees is 22.04 (who is listening near me), which requires no connection of their own. |
| Fan | None | Never rendered. Fans consume public performance stats on an artist profile (a domain 01/20 surface), which are downstream of this feature but never expose the connection itself. |

## Behavior

A connection is an OAuth grant from the DSP scoped to one external artist entity, bound to one
WeJammin identity, with a credential that has an externally-controlled lifetime. The feature owns
three moments: **grant**, **survive**, **revoke** — the middle one being where the real product is,
because a connection nobody re-auths is a dashboard that quietly lies.

Connecting is not the same as matching. The grant proves you can read an artist's numbers; deciding
*which* WeJammin identity and catalog those numbers belong to is 22.02's job. A user who has
connected but not matched has data with nowhere to land.

**Connection identity model (D-03).** The unit of ingestion is the **external artist entity**, not
the user. The first successful grant for external artist `X` establishes the **canonical
connection** for `X`; any later grant by a *different* WeJammin identity for the same `X` attaches
as a **delegated credential/reader** on that one canonical connection, never as a second parallel
pipeline. This makes ingestion exactly-once — a given metric for a given day on a given source is
counted once no matter how many credential-holders exist — makes
re-auth resilient (any authorised credential-holder can revive a broken connection), and keeps
"read access" (many holders) cleanly separate from "ownership" (22.02's single binding).

**Freshness cadence (this feature's emitted expectation).** DSP analytics are daily-batch sources.
A connection reports a per-source `last_successful_sync` timestamp; the classification of that
timestamp into `healthy` / `stale` / `broken` is 22.01.03's job, but this feature's cadence
contract is: a daily source is expected to sync once per 24h, and the concrete thresholds this
feature emits are `healthy` when `last_successful_sync < 26h`, `stale` at `26h–50h`, and it flips
to `broken` on any auth failure regardless of age. Access tokens are short-lived (DSP-typical
~1h) and refreshed silently; only refresh-token death is user-visible.

### Happy Path

1. User opens Analytics → Connections and picks a DSP from the catalog of supported sources.
2. System sends the user to the DSP's own consent screen, where the user sees WeJammin is requesting **read-only analytics access** — no posting, no account changes, no write scope. The attempt stays valid for ~10 minutes.
3. User authorises on the DSP and is returned to WeJammin. The system validates that the return is a genuine, unexpired response to *this* attempt (a forged, replayed, or expired return is rejected here and yields no connection) before establishing the read credential.
4. System lists the artist entities that grant can read (a user may have access to several — their own project, a band, a client's roster).
5. User selects which artist entities to ingest. For each selected entity, system checks whether a canonical connection already exists (D-03): if not, it creates one and binds this identity's credential as primary; if one exists, it attaches this identity as a delegated credential. System hands off to 22.02 for identity matching.
6. System begins a historical backfill and shows progress; the dashboard populates progressively rather than appearing empty then complete.
7. Connection lands in `healthy`; freshness and next-sync time are visible.

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Refresh token revoked (password change, permission review) | Ingestion stops; canonical connection → `broken`; a named gap opens from `last_successful_sync`. Any credential-holder may re-auth to revive it. | "Spotify disconnected on 3 March. Data since then is missing, not zero." + Reconnect CTA |
| Grant returns zero artist entities | No ingestible target; no connection is created | "This account can't read any artist analytics. You may need artist access on Spotify for Artists first." + link to the DSP's claim flow |
| User has access to an artist they do not own (label/manager grant) | Connection allowed; ownership is asserted by 22.02, not by the grant. Connector becomes a delegated reader, not the owner. | Warning that access ≠ ownership; the numbers are attributed to the matched artist entity, not to the connector |
| DSP rate-limits the backfill | Backfill degrades to a slower cadence; already-fetched ranges persist; the read retries automatically at a progressively slower pace until it clears | Progress bar stalls with "Spotify is limiting how fast we can read history — this will finish, slowly" |
| **Same DSP artist connected by two WeJammin identities** (band member + manager) | Second grant does **not** create a parallel connection. It is recognised as an already-connected artist, and the second identity is attached as a **delegated credential** on the existing canonical connection (D-03). Ingestion stays exactly-once. | "This artist is already connected on WeJammin. You now hold a backup credential and can re-authorise it if it breaks." — not an error, an attach |
| **Concurrent first-grant race** (two identities complete OAuth for the same brand-new external entity within the same second) | Exactly one canonical connection is created for the entity; the other grant resolves into an attach on that same connection rather than a second connection or a surfaced failure | Both users land on the same healthy connection; neither sees an error |
| **Re-auth completes while a backfill is running** | No double-count: a given metric-per-day is written exactly once regardless of how many credentials wrote it (CX-01 Q5). The new credential simply supersedes the dead one mid-stream. | Uninterrupted progress bar; freshness advances |
| **Two delegated holders re-auth a broken connection simultaneously** | First valid token exchange wins and flips the connection to `healthy`; the second is a no-op that records its credential as a standby. No duplicate ingestion is scheduled. | Both see "Reconnected"; only one backfill of the gap runs |
| **Network failure mid-OAuth round-trip** (callback never returns, or token exchange times out) | No connection is created; the `state` nonce is left consumable until its 10-min TTL expires so the user can retry the same attempt. Partial state is never persisted. | "We didn't hear back from Spotify. Try connecting again." + retry |
| **Malicious / forged callback** (mismatched or replayed `state`, tampered `redirect_uri`, reused authorization `code`) | Rejected before any token exchange; no connection is created and the attempt is logged for the 24-domain trust surface | "That sign-in link was invalid or expired. Start the connection again." — never a token, never a partial connection |
| **Partial data on backfill** (DSP serves some metrics/date-ranges but 5xx on others) | Connection is `healthy` for the covered ranges; uncovered `(metric, date)` cells are recorded as *unattempted*, not zero, and re-queued. This feeds 22.01.03's gap surface, never a flat line. | Timeline shows an explicit "some history still loading" boundary, not a misleading zero |
| **User revokes WeJammin's app from the DSP side** (not via WeJammin) | Detected on the next sync attempt when the credential is refused; connection → `broken` with a named gap from `last_successful_sync` | Same broken-state UX as an in-app revoke, with "Access was removed on Spotify" phrasing |
| **External entity renamed / handle changed on the DSP** | Tolerated — the immutable external artist id, not the display name, is the join key. Connection stays `healthy`; the new name propagates to 22.02. | Card silently updates the artist name; no break |
| **External entity disappears** (catalog moved to a different DSP id, artist page deleted) | Connection → `broken` (id no longer readable), history end-dated and retained, re-match offered via 22.02 | "Spotify no longer serves this artist page. Your history to 12 May is kept." + re-match CTA |
| **Multi-hyphenate connects the same artist under two of their own roles** (as band-member Musician *and* as co-owner Producer) | One human = one WeJammin identity; roles are lenses, not accounts (personas.md structural fact). A second connect attempt from the same identity for the same entity is a no-op returning the existing canonical connection, regardless of which role lens initiated it. | "Already connected" — the connection is surfaced identically in both role contexts, never duplicated |
| Disconnect by the owner | Ingestion stops; history retention is an explicit choice, constrained by DSP terms (Q-02) | Explicit choice: keep history (read-only, end-dated) or purge |
| Disconnect by a delegated (non-owner) holder | Removes only that holder's credential/delegation; the canonical connection survives as long as ≥1 valid credential remains. A non-owner can never purge history. | "You've removed your access. The connection stays live via {owner}." — no purge option shown |
| DSP deprecates/withdraws API access entirely | Connection → `terminal`; history end-dated, never deleted | "Deezer no longer shares this data. Your history to 12 May is kept." |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Loading | OAuth round-trip in flight (redirect out → callback → token exchange) | Redirect + return spinner |
| Empty | No DSP connected for this identity | Empty state naming the concrete loss: "Connect Spotify to see how the records you played on are doing" + connect CTA |
| Populated | ≥1 `healthy` canonical connection readable by this identity | Per-source card: artist entity, freshness, next sync, credential role (owner vs delegated) |
| Error | Grant denied, `state` mismatch, or token exchange failed | Cause-specific message + retry; never a bare "something went wrong" |
| Partial | Backfill in progress or partially covered | Timeline renders with an explicit "history still loading to {date}" boundary, not a misleading flat line |
| Broken | Refresh token revoked/expired or app access removed DSP-side | Reconnect CTA + named gap range; any credential-holder may act |
| Terminal | DSP API withdrawn entirely | End-dated history, no CTA (nothing the user can do) |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | This is a plumbing feature and belongs in architecture, not the product | Node Classification Gate — "infrastructure wearing a product costume?" | ❌ REJECTED: the OAuth pipeline is architecture, but "connect your Spotify" is a first-class product surface in every comparable product (Chartmetric, Songstats, Soundcharts all lead with it), and the survive/revoke lifecycle produces user-visible states with user-taken actions. The scheduler underneath it *is* routed to `/create-prd-architecture`. |
| DT-02 | Spotify for Artists has a usable public analytics API | Implicit assumption in the domain's premise | ❌ REJECTED as an assumption: there is **no general public S4A analytics API**. Incumbents obtain this via partnership or scraping. This is a load-bearing risk for the whole domain — if access is unobtainable, 22.05 and 22.08 lose their richest source and must fall back on distributor files (22.01.04). Escalated as sub-domain Q-01; this is a `/create-prd-stack` blocker, not a detail. |
| DT-03 | A domain expert would expect **multi-artist grants** — one login reading many artists | Producers/managers routinely hold access to a roster; the naive "one user = one artist" model breaks on contact with them | ✅ CONFIRMED: step 4 of the happy path exists because of this. A one-artist-per-account model would fail the Producer persona immediately and would also fail the multi-hyphenate Musician, who is in three bands (personas.md: "roles are simultaneous, not sequential"). |
| DT-04 | The connection can be modelled per-user (each grant its own pipeline), deferring the multi-holder question | Naive default; also the model the original draft left unresolved (now closed by D-03) | ❌ REJECTED: per-user connections double-ingest the same external artist when a band member *and* a manager both connect it — inflating streams, burning the DSP rate budget twice, and producing two conflicting freshness states for one truth. The only model that survives the band/roster case is **one canonical connection per external entity with delegated credentials** (D-03). Per-user was rejected specifically because the personas guarantee the multi-holder case, not merely permit it. |
| DT-05 | "Grant = ownership" is a safe shortcut, since the person connecting is usually the artist | Convenience assumption; true for socials (22.01.02) | ❌ REJECTED and deliberately inverted: on DSPs, a label or manager legitimately holds read access to an artist they do **not** own. Letting the grant assert ownership would let a manager claim a client's catalog by connecting it — the exact harm D-01 exists to prevent. Ownership is 22.02's single binding; the connection only ever proves *read access*. This is textually the opposite of 22.01.02's model, which is why D-01 in the parent keeps the two features separate. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | Connection is separated from **matching** (22.02) | Conflating them is the common design error: a grant proves *read access*, not *ownership*. A manager with roster access must not be able to claim a client's catalog as their own by connecting it. |
| D-02 | Disconnect offers **retain or purge**, never silent deletion; purge is **owner-only** | History is the asset (D-18: the reason they can't leave). But retention may be forbidden by DSP terms — the choice may not survive `/create-prd-security`. A delegated (non-owner) holder disconnecting removes only their own credential, never the shared history. Recorded as a product intent subject to Q-02. |
| D-03 | **One canonical connection per external artist entity, with delegated credentials/readers** — never one connection per user | Resolves former Q-03 and the two-identity edge case. Per-user connections would double-ingest, double-spend the DSP rate budget, and produce conflicting freshness for one truth when a band member and a manager both connect the same artist — a case the personas guarantee. A second grant for an already-connected entity is recognised as such and attaches as a delegated credential rather than opening a parallel pipeline. Exactly-once ingestion means a given metric-per-day-per-source lands once no matter how many credentials wrote it, and only one canonical connection ever exists per external artist entity. Read-access (many holders) stays separate from ownership (22.02's single binding, D-01). Delegation membership and purge authority are grounded in domain 01 org scoping. |
