## Cross-Cut Details

### CX-01: Geography Map ↔ Routing Insight

**Relationship**: The map produces per-city audience density, trend and engagement depth; routing
consumes it and joins it against things a map cannot know — the artist's booking history (domain 17),
venue supply and capacity fit (domain 16), and travel geometry. The map is descriptive; routing is
the only place it becomes an action.

**Role scoping**:
- **Musician**: sees both fully — their map, their routing options.
- **Producer**: read-only on the map (context for a client), and **no access** to routing. Routing is a live-performance decision; a producer has no standing in it.
- **Operator**: `📊 Reports` on both, and only in aggregate — "artists with a following here", never "this artist has 4,200 listeners here" (D-02).
- **Fan**: no visibility at all. A fan's *contribution* to the map is real but invisible to them, which is worth stating: they generate this data by listening and never see it.

**Synthesis questions answered**:
1. **Shared state conflict**: none — routing derives from the map and never writes it. Single writer.
2. **Trigger chain**: map updates → routing recomputes on read, not on write. Routing is a view, not a job. If the map is stale, routing must inherit and display that staleness rather than silently serving a confident old answer (22.01.03 D-02).
3. **Permission intersection**: **yes, and it is the sharp edge of this sub-domain.** The Operator's aggregate view is computed from artists' private geography. Aggregation is doing real privacy work here and must be specified, not assumed: a "market" with one artist in it is that artist's private data with a hat on. A k-anonymity floor is required, not optional. Flagged to `/create-prd-security` and D-02.
4. **Notification fan-out**: none. Neither is event-driven; both are pull surfaces. Alerting a musician that a city is trending would be a plausible future, and is deliberately not proposed — it would push tour decisions on noise.
5. **State transition conflict**: no race. Both are read-only views over ingested data.

### CX-02: Routing Insight ↔ Show Impact Attribution

**Relationship**: Routing proposes; a show happens (domains 17/18); attribution measures the delta.
The measurement then falsifies or supports the routing model. Without CX-02, routing advice can never
be shown to have worked — it stays permanently unfalsifiable, which is the state most "recommendation"
features live in.

**Role scoping**:
- **Musician**: sees the proposal and the outcome; the only persona for whom the loop closes.
- **Producer**: no access to either.
- **Operator**: `📊 Reports` — a venue legitimately wants to know that shows in their room grow artists, and that is a genuine sales asset for them. But it must be their room's aggregate record, not a specific artist's lift, which is that artist's negotiating position.
- **Fan**: no visibility.

**Synthesis questions answered**:
1. **Shared state conflict**: none. Both derive from the booking record (domain 17), which neither owns.
2. **Trigger chain**: show completes (17) → attribution window opens → lift computed after the window closes. Async by construction — the answer does not exist until weeks after the show. If 17's booking record is wrong or absent, attribution silently measures nothing; it must state that rather than report zero lift (22.01.03 D-01).
3. **Permission intersection**: attribution requires reading the artist's booking history. If a booking was made off-platform, there is no record and no attribution — the loop only closes for shows WeJammin was present for. **This is D-18 in miniature**: being in the room is the precondition for the insight, and the insight is the reason to be in the room.
4. **Notification fan-out**: an attribution result is worth telling the artist ("Manchester is up 40% since you played"). Delivery is a cross-cut.
5. **State transition conflict**: a cancelled or rescheduled show (common) must invalidate an open attribution window rather than measure a show that never happened. Flagged for Step 5.

### CX-03: Show Impact Attribution ↔ Geography Map

**Relationship**: The loop closes. A measured lift in a city is not merely a report — it is a
correction to the map's meaning: this city's audience is *earned and responsive*, not incidental.
An artist with 4,000 listeners in a city they have never played is a different proposition from one
with 4,000 listeners they built by playing there twice, and no map that lacks show history can tell
those apart.

**Role scoping**:
- **Musician**: sees cities annotated with their own history — the map becomes autobiographical.
- **Producer**: read-only.
- **Operator**: `📊 Reports`, aggregate only.
- **Fan**: no visibility.

**Synthesis questions answered**:
1. **Shared state conflict**: attribution annotates the map's rendering; it does not mutate ingested geography. Derived-only.
2. **Trigger chain**: attribution result → map annotation. Idempotent, recomputable, non-critical — if it fails, the map is merely less informative, not wrong. Correct failure direction.
3. **Permission intersection**: inherits CX-01's k-anonymity requirement.
4. **Notification fan-out**: none.
5. **State transition conflict**: none — annotation is recomputable from source at any time.
