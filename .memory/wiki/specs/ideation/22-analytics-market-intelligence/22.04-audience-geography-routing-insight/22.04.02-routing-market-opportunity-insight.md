# Feature: Routing & Market Opportunity Insight

> **Number**: 22.04.02
> **Parent**: [Audience Geography & Tour Routing Insight](./22.04-audience-geography-routing-insight-index.md)
> **Status**: [PARTIAL]
> **Last updated**: 2026-07-17

## Overview

Turning the map into a shortlist: which cities have enough of the right kind of audience to be worth
playing, which are geographically coherent as a run, and which have a room of the right size actually
available. This is the point where analytics produces an action with money attached — and the point
where WeJammin can do something Chartmetric structurally cannot, because it holds the venue supply
(domain 16) and the booking history (domain 17) alongside the audience data.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Full | Sees candidate cities ranked by audience evidence, annotated with venue supply, capacity fit and their own history there; assembles a shortlist; hands it to real booking (domain 17). They decide — the system never books anything. |
| Producer | None | Not rendered. Routing is a live-performance decision and a producer has no standing in it. Explicit absence: a producer with map access (22.04.01) does **not** inherit routing. |
| Operator | Reports | The other side of the same question: aggregate demand in their catchment — "artists in this genre with a following near here" — as a booking prospecting aid. Never an individual artist's numbers (parent D-02). This is the Operator's single most valuable surface in domain 22, and arguably a reason for a venue to be on the platform at all. |
| Fan | None | Never rendered. |

## Behavior

Routing joins things that live in different places and are only jointly available here:

- **Audience evidence** (22.04.01) — weighted toward engagement depth and the owned layer, not raw listener count (22.04.01 D-01, D-02).
- **Venue supply** (domain 16) — is there a room, at the right capacity, that a band at this level can actually get?
- **Booking history** (domain 17) — have they played here, when, what happened?
- **Geographic coherence** — a cluster that a van can plausibly drive.

Output is a **shortlist with reasoning attached**, not a plan (parent D-03). The system does not know
about visas, a drummer's day job, an agent's relationships, or the promoter who still owes them money.
A confident itinerary from a system blind to all of that is worse than no itinerary — it is an
authoritative-looking wrong answer, and the user cannot see which of its inputs was missing.

### Happy Path

1. User opens Routing with a target window and region.
2. System proposes candidate cities with audience evidence, venue supply and their own history in each.
3. Each candidate states its reasoning and its confidence, including what the system could not see.
4. User accepts some, rejects others, adds cities the system missed.
5. Shortlist hands off to domain 17 for actual enquiries — where humans do the booking.

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Strong audience, no suitable venue | Candidate surfaced with the constraint named | "Strong audience, no 200–400 cap room available in your window" — the constraint is the insight |
| Audience is passive (algorithmic listeners) | Down-weighted per 22.04.01 D-01 | "Large but passive audience — few saves or follows. Weak attendance evidence." |
| City never played, no history | Not penalised — it is the opportunity case | Flagged as untested, not as weak. These are the cities routing exists to find |
| City played recently, poorly | History dominates the audience signal | "You played here 4 months ago to 40% capacity" — this outranks any map |
| Geographic outlier with a great audience | Surfaced, coherence cost stated | "Strong audience, 6 hours from your nearest other date" |
| Data too thin to say anything | System declines to rank | "Not enough evidence to route" — an honest refusal beats a confident guess |
| User routes on a bot-inflated city | Excluded upstream by 22.04.01 D-04 | Should never surface; if it does, the failure is in the map's filter |
| Off-platform booking history | Invisible; routing under-informed | Explicit: "we can only see shows booked here" — the loop only closes for shows WeJammin was present for |
| Operator opens the prospecting view and tries to see one artist's numbers | Refused at the boundary — Operator access is `Reports` (aggregate only) per parent D-02 | "Aggregate demand for your catchment" — never a named artist's city listener count, because that count is the artist's guarantee-negotiating position against this exact viewer |
| Producer (with 22.04.01 map access) navigates to Routing | Not rendered — routing access does not inherit from map access | 404 / not-available; a producer has no standing in a live-performance routing decision |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Loading | Computing candidates | Skeleton list |
| Empty | Insufficient audience data | Routes to 22.01/22.04.01 — the missing input is named |
| Populated | Candidates found | Ranked shortlist with reasoning + confidence |
| Partial | Venue/booking data missing for a region | Candidates shown with the gap named, never silently dropped |
| Declined | Evidence too thin to rank | Explicit refusal with the reason |
| Error | Computation failed | Retry |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | This should be a **recommendation engine** that produces an optimal route | The obvious ambition, and the shape the candidate name suggests | ❌ REJECTED: the constraints that actually decide a route are almost all invisible to us — visas, van and crew logistics, agent and promoter relationships, day jobs, a member's childcare, a promoter who still owes money from last time. An optimiser blind to the binding constraints produces confident nonsense, and worse, the user cannot tell *which* input was missing. **Being a well-reasoned input to a human decision is the honest ceiling**, and stating that ceiling is more useful than pretending past it. Hence parent D-03. |
| DT-02 | WeJammin's advantage here is the **venue supply join**, not the audience data | Competitive reasoning against Chartmetric | ✅ CONFIRMED, and it is sharper than the sub-domain index's framing. Chartmetric can rank cities by audience — that is table stakes and they do it well. What they cannot say is *"and there are three rooms at your capacity with availability in that window"*, because they do not hold venue inventory. WeJammin holds domain 16. **The scarce input in routing is not knowing where the audience is — most artists roughly know that — it is finding a room that will actually have you.** That reframes the feature: it is a supply-matching problem wearing an analytics costume, and it makes 22.04.02 dependent on domain 16 having real venue inventory. Without that, this feature degrades to a ranked city list, which is a commodity. |
| DT-03 | What breaks at the intersection with domain 17 (Live Booking)? | Cross-domain failure reasoning | ✅ CONFIRMED, and it is a live incentive risk, not a technical one. Routing surfaces a city; booking (17) monetises the enquiry. That gives the platform a **financial interest in recommending cities that produce bookings**, which is not the same as recommending cities that are good for the artist — the exact structural conflict that makes SubmitHub's pay-to-play problem (22.03.03 DT-03) so corrosive. If venues can ever pay for placement in routing, the feature is dead as an honest instrument and the platform's credibility goes with it, because this is the surface where an artist trusts us with a financially consequential decision. Escalate as a **product values decision**, not an architecture one. |
| DT-04 | Is DSP city-level listener data accurate enough to route a real tour on, or does the feature over-promise on data that cannot support it? | Parent sub-domain Q-02, deferred here to Step 5 | ✅ CONFIRMED as a real limit, and it **reinforces D-01/D-02 rather than undermining the feature**. DSP geography is coarse (city-or-metro granularity, not neighbourhood) and lagged (typically weeks behind), so it cannot bear the weight of a confident itinerary — which is precisely why routing is a shortlist-with-reasoning, not an optimiser. The design already routes around the weakness two ways: booking history (D-03) and prior ticket sales by city (domain 19) **outrank** the DSP signal wherever they exist, because a real result in a room is ground truth where a lagged listener estimate is an inference; and where only DSP data exists, the candidate must **name that its evidence is coarse streaming geography** (D-02). The honest failure mode is the "Declined" state — thin or stale data produces a refusal, not a confident guess. The open residue is whether DSP terms even permit deriving and displaying this geography (domain-level Q-03, `/create-prd-security`), which is a licensing question, not an accuracy one. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | Output is a **shortlist with reasoning**, never a plan or an optimised route | DT-01. The binding constraints are invisible to us; a confident route is authoritative nonsense. |
| D-02 | Candidates always state **what the system could not see** | The user can only correct for a missing input if they know it was missing. |
| D-03 | Booking history **outranks** audience evidence | A real result in a room beats an inferred listener count, always. |
| D-04 | Routing rank is **never purchasable** by venues | DT-03. Paid placement here converts the platform's most trusted instrument into an ad, on the one surface where artists trust us with money-losing decisions. |
