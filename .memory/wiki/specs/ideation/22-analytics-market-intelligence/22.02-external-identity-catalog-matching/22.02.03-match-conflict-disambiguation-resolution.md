# Feature: Match Conflict & Disambiguation Resolution

> **Number**: 22.02.03
> **Parent**: [External Identity & Catalog Matching](./22.02-external-identity-catalog-matching-index.md)
> **Status**: [PARTIAL]
> **Last updated**: 2026-07-17

## Overview

The adjudication surface for matches that cannot be settled by rule: two identities claiming one
Spotify profile, an ISRC that points at two different recordings, a fuzzy match nobody can confirm.
It exists because the alternative — guessing — produces a wrong number wearing a confidence badge,
which is the specific failure this platform was built to end.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Full | Sees their contested and ambiguous matches queued; supplies evidence; accepts or disputes an outcome. The queue is theirs alone — a user only ever sees conflicts touching their own claims. |
| Producer | Full | Same, and is the most common legitimate counterparty: producer and artist both hold a real relationship to one profile, and both are telling the truth about different things. |
| Operator | None | No matches, no conflicts. Not rendered. |
| Fan | None | Never rendered. Fans cannot claim, so they cannot contest. |

## Behavior

Three classes of conflict, and they are not the same problem:

1. **Contested claim** — two WeJammin identities claim one external profile. A *dispute*: there is a
   truth, and someone is wrong (or both are partly right — a band and its frontman).
2. **Ambiguous identifier** — one ISRC, two candidate recordings. A *data-quality defect* in an
   external system. Nobody is lying; the source is broken.
3. **Unconfirmable fuzzy match** — insufficient evidence either way. An *absence*, not a conflict.

Class 1 is adversarial and needs domain 24's dispute machinery. Classes 2 and 3 are not adversarial
and must never be routed through a disputes flow — sending a user to a dispute process for a
distributor's typo is a UX failure that also poisons the disputes queue.

The invariant: **contested state blocks binding, and blocking is loud**. Nothing speculatively binds
while contested, and a cascading invalidation (CX-01) never silently orphans numbers.

### Happy Path

1. System detects a conflict at match time; the match is held, never bound.
2. Affected claimant(s) notified with the conflict class stated plainly.
3. User opens the conflict, sees both candidates and the evidence for each.
4. For class 2/3: user picks or rejects; resolved immediately, no counterparty involved.
5. For class 1: the claim goes to adjudication; both parties see the same state.
6. Outcome binds (or rejects) the match; dependents re-validate.

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Band entity and frontman both claim one profile | This is a representation collision, not evidence adjudication — but it is **not** permission to bind both. Binding remains frozen while domain 01 governance selects whether the external profile represents the band entity or the personal identity. 22 applies that one result. | "Representation pending — domain governance must select one profile subject." No catalog match or analytics binding is released until then. |
| Contested claim, counterparty never responds within the response window | A response window opens on escalation (default duration `[PENDING — Q-01, user decision]`); on expiry the conflict does **not** silently auto-bind — it escalates into domain 24's adjudication with the non-response recorded as evidence. The default *winner* is a product/policy call, not an agent one | Claimant sees "waiting on the other party — N days left"; on expiry, "escalated for review" |
| Serial frivolous contests filed to grief a claimant | Same external profile re-contested repeatedly with no new evidence is rate-limited and, after a threshold, flagged to domain 24 as abuse rather than reopening the queue each time | "This match was recently reviewed — new claims need new evidence"; abuse pattern surfaced to Trust & Safety |
| Both identities in a contested claim resolve to the **same human** (two accounts, one person) | Not a dispute — an account/identity merge. Routed to domain 01, never to adjudication | "These look like the same account — merge or pick a primary identity" |
| Conflict resolved, then contested again by a third party | Reopens; prior evidence retained as precedent | History visible on the match |
| Parent artist match invalidated | Every dependent catalog match invalidates — loudly, never orphaned | "12 recordings unlinked because the artist match was withdrawn" |
| Conflict on a match feeding a live shared report (22.05.03) | Report's affected numbers go to unknown, not to a stale value | Viewer sees the same suspension the owner sees |
| Two claimants, one is provably right via DSP grant | Auto-resolves in favour of the grant; not a human decision | Grant-holder wins; loser notified with the reason |
| Adjudication requires a fact only the DSP knows | WeJammin cannot resolve it | Honest dead-end: "we can't verify this — here's how to claim it on Spotify" + link outward. See Q-01 |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Loading | Queue opening / candidates and evidence being fetched | Skeleton rows; candidate evidence panels shimmer until resolved |
| Empty | No conflicts | Nothing — the healthy default, not a page anyone visits |
| Pending | Conflict detected, awaiting the user | Queued item with class + candidates |
| Contested | Class-1, counterparty involved | Both-party view; binding frozen |
| Governance pending | Band entity / member representation collision | Domain 01 selects one subject; binding remains frozen and is never duplicated |
| Adjudicating | Escalated to domain 24 | Read-only; status from 24 |
| Resolved | Outcome applied | Bound or rejected, with the reason retained |
| Unresolvable | No fact obtainable | Dead-end with an outward remedy — never a spinner forever |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | All three conflict classes are one thing and share one flow | The tidy-looking generalisation | ❌ REJECTED: only class 1 is adversarial. Classes 2 and 3 are data quality and absence. Routing a distributor's mis-keyed ISRC through a *dispute* process would (a) make a trivial correction feel like an accusation, (b) flood domain 24's queue — the queue that also handles real disputes about money — with typos, and (c) require a counterparty that does not exist. Sharing a UI surface is fine; sharing a *process* is not. |
| DT-02 | What would a domain expert expect that nobody mentioned? **Most conflicts have no counterparty to argue with.** | Reasoning about the real distribution of cases | ✅ CONFIRMED, and it re-shapes the feature. The intuition "conflict → dispute → adjudication" imagines class 1, but class 2/3 will dominate by volume — external music metadata is famously dirty, and every dirty row lands here. So this feature is mostly a **data-cleanup queue that occasionally becomes a courtroom**, and should be designed as the former. Building it courtroom-first would produce a heavyweight flow for a lightweight majority, and the queue would go unworked — which silently caps 22.08's coverage. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | Three conflict classes, **two processes** | DT-01. Data-quality defects must not wear a dispute's clothing or clog its queue. |
| D-02 | Contested or governance-pending **blocks binding**; nothing binds speculatively or twice | A speculative or duplicate bind produces a wrong number that gets quoted before the conflict resolves. Unbound is honest; wrongly-bound is not. |
| D-03 | Unresolvable conflicts end in an **honest dead-end with an outward remedy** | WeJammin cannot verify external facts. Pretending otherwise with an eternal "pending" is worse than saying so and pointing at the DSP's own claim flow. |
| D-04 | Designed as a **cleanup queue first**, a courtroom second | DT-02. Volume is class 2/3 by a wide margin. |
