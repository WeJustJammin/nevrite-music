## Overview

The join. Ingestion (22.01) delivers numbers attached to *foreign* identifiers — a Spotify artist
URI, a TikTok handle, an ISRC on a distributor row — and this sub-domain binds them to WeJammin
identities and catalog entities so the numbers have an owner. Nothing downstream in the domain
works without it: an unmatched stream count is a fact about a stranger.

**Why this is a sub-domain (2+ interacting capabilities)**: artist-entity matching, recording/release
catalog matching, and conflict/disambiguation resolution are distinct and interact in a strict
dependency: a recording match is only trustworthy if the artist match beneath it is correct, and a
contested artist match invalidates every catalog match hanging off it. Cascading invalidation is the
interaction, and it is the reason these cannot be three unrelated files.

**Why this is domain 22's and not a cross-cut**: the identifiers matched here (Spotify artist URI,
TikTok handle) exist *only* for analytics purposes and appear nowhere else in the platform. The
**canonical recording/work identifier registry** (ISRC/ISWC/UPC) is a different thing — it serves
02, 09, 10, 11 and 12 as well, and is recorded as a cross-cut, not owned here. This sub-domain
*consumes* that registry; it does not mint it.

| D-02 | This sub-domain **consumes** the canonical identifier registry; it does not own it | ISRC/ISWC/UPC serve 02, 09, 10, 11, 12 and 22. Owning it here would fork the platform's identity of a recording. Routed to the domain CX file as a cross-cut. | Node Classification Gate |
| D-03 | A match is a **claim with evidence**, not a database join | Given D-18 (provenance is the wedge), the assertion "this Spotify artist is me" is exactly the class of self-claim this platform exists to stop taking on trust. Confidence and evidence are first-class. | Agent, Deep Think, 2026-07-16 |
