# Feature: Recording & Release Catalog Matching

> **Number**: 22.02.02
> **Parent**: [External Identity & Catalog Matching](./22.02-external-identity-catalog-matching-index.md)
> **Status**: [SURFACE]
> **Last updated**: 2026-07-16

## Overview

Binding external recordings and releases — identified by ISRC, UPC, or a DSP's own track URI — to
WeJammin catalog entities, so that per-track numbers land on the right record. This is the feature
that makes 22.08 (Credit-Linked Performance) computable: a credit says "I played drums on this
recording", and only a catalog match turns that into "this recording did 4M streams".

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Full | Reviews and confirms which external recordings correspond to records they're credited on; resolves rows that matched nothing. For the session player this is the moment their scattered work becomes a catalog they can actually see — most have never had one. |
| Producer | Full | Same, at project granularity: confirms a project's deliverables map to the released recordings. Frequently holds the most reliable knowledge of what a track actually *is* — they were in the room when it was made (personas.md: "they are the person who knows"). |
| Operator | None | No catalog. Not rendered. |
| Fan | None | Never rendered. |

## Behavior

Matching is scoped by the artist match above it (CX-01) and driven by identifiers, strongest first:

- **ISRC** — the recording identifier. Authoritative *in principle*, unreliable in practice: the same
  recording is routinely issued under multiple ISRCs by successive distributors, and ISRCs are
  re-used and mis-keyed constantly. It is the best key available and it is not a primary key.
- **UPC** — the release identifier. Same caveats, one level up.
- **DSP track URI** — reliable within one DSP, meaningless across DSPs.
- **Fuzzy (title + artist + duration + release date)** — last resort. Proposes; never binds.

The result is deliberately **many-to-many**: one WeJammin recording may legitimately correspond to
several external recordings (an original, a remaster, a territory-specific re-issue), and the
numbers of all of them belong to it.

### Happy Path

1. Artist match confirmed (22.02.01); system enumerates external recordings under that profile.
2. System matches them against WeJammin catalog entities by ISRC, then UPC, then fuzzy.
3. User sees a review list grouped by confidence: auto-matched (ISRC), proposed (fuzzy), unmatched.
4. User confirms the proposals, corrects the wrong ones, and dispositions the unmatched.
5. Per-recording numbers land; 22.08's credit rollup becomes computable.

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Same recording under 2 ISRCs (re-distributed) | Both bind to one catalog entity; numbers **sum** | "2 versions of this recording found — combined" with the components inspectable |
| ISRC re-used for a different recording (a real distributor error) | Match by ISRC alone would be wrong; corroboration (duration, title, date) required before binding | Flagged to 22.02.03 rather than bound |
| Remaster / radio edit / live version | Distinct recordings — **must not** silently merge into the original | Proposed as related, requiring an explicit "same or different?" |
| Compilation appearances | One recording on many releases; UPC-level match multiplies | Release-level rollup keeps them distinct; recording-level does not double-count |
| Track has 6 credited contributors | All 6 legitimately claim the same recording. No division occurs. | Each sees the recording's full numbers; see 22.08 D-01 |
| A recording the user is credited on but the artist match doesn't cover | Common and important — the session player's default case | Unmatched; routed to evidence-based matching via the credit graph rather than via the artist profile |
| Fuzzy match on a covers/tribute act | High collision risk (same title, same duration, different everything) | Never auto-bound; fuzzy proposes only |
| Catalog entity doesn't exist in WeJammin yet | Nothing to bind to | Offer to create it from the external metadata — with imported provenance (22.01.04 D-02) |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Loading | Enumeration/matching in flight | Progress with counts |
| Empty | No external recordings under the profile | "No recordings found for this profile" |
| Populated | Matches proposed | Confidence-grouped review list |
| Partial | Some matched, some not | Matched set live; unmatched queue works down separately |
| Contested | Ambiguous/conflicting identifiers | Frozen; routed to 22.02.03 |
| Error | Matching failed | Retry; manual ISRC entry as fallback |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | ISRC is a reliable primary key and matching is therefore trivial | The naive assumption the sweep's candidate list implicitly makes | ❌ REJECTED: ISRCs are re-issued per distributor, re-used in error, and frequently absent or wrong on older catalog. Any design treating ISRC as a primary key will silently merge distinct recordings and split identical ones. It is the best *hint* available, not a key. This single misconception is the most likely cause of a wrong number in this domain. |
| DT-02 | A domain expert would expect **many-to-many, not one-to-one**, and nobody said so | Catalog knowledge; the candidate list implies a simple join | ✅ CONFIRMED: one WeJammin recording ↔ many external recordings (re-issues, remasters, territory variants) is the normal case, not an exception. A one-to-one model undercounts a career by exactly the amount that matters most — the long-lived catalog that got re-released, which is the work with the most accumulated streams. |
| DT-03 | What breaks at the intersection with 22.08 (Credit-Linked Performance)? | Cross-domain failure reasoning | ✅ CONFIRMED and it is the domain's most consequential coupling. 22.08 rolls up "the records I played on" **across releases the Musician does not own and cannot connect** (22.01 Q-03). So the rollup's coverage is capped by this feature's ability to match recordings via the *credit graph* rather than via an artist profile the user controls. If matching only works downward from a claimed artist profile, 22.08 works only for artists — and fails precisely the session-player persona it exists to serve. **The credit graph must be a first-class matching entry point, not a fallback.** That is a structural requirement discovered here, not in 22.08. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | Matching is **many-to-many** | DT-02. One-to-one undercounts exactly the catalog that matters most. |
| D-02 | ISRC is a hint requiring corroboration, **not a key** | DT-01. Trusting it produces silent, undiagnosable errors in a number users quote commercially. |
| D-03 | Fuzzy matching **proposes only** — it never binds | The covers/tribute collision is unresolvable by heuristic, and a wrong bind is worse than an unmatched row. |
| D-04 | The **credit graph is a first-class matching entry point** | DT-03. Without it, 22.08 serves only artists and fails the session player — inverting the domain's thesis alignment. |
