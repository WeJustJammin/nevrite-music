# Feature: Playlist Placement Tracking

> **Number**: 22.03.01
> **Parent**: [Playlist & Chart Tracking](./22.03-playlist-chart-tracking-index.md)
> **Status**: [PARTIAL]
> **Last updated**: 2026-07-17

## Overview

Tracking where a track sits on playlists across DSPs and — crucially — **when it moved**: added,
re-positioned, removed. Placement is the dominant exogenous driver of a streaming curve, so this is
the feature that turns "my streams tripled last Tuesday" into "you were added to a 400k-follower
playlist last Tuesday" — the difference between a chart and an explanation.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Full | Sees every current and historical placement for their tracks, the add/remove/move events on a timeline against their streams, and the estimated contribution of each placement; sets alerts on adds and (especially) removals. |
| Producer | Read-only | Sees placements for projects they're attached to — useful context when a client asks "why did it stop working?", but they have no lever here and no alerts of their own by default. |
| Operator | None | Not rendered. Playlist placement has no bearing on booking a room. |
| Fan | None | Never rendered. A fan discovering a track via a playlist is a domain 20/21 concern; the placement record itself is professional data. |

## Behavior

Placement is an **event stream, not a list** (D-01). The system records add, position-change and
remove events per (track, playlist), and renders them as annotations against the stream curve so the
two are legible together.

Three playlist classes, deliberately never merged (D-03):
- **Editorial** — a human curator chose you. Losing it is a decision someone made.
- **Algorithmic** (Discover Weekly, Release Radar, Radio) — a system chose you. "Removal" is not
  even a coherent event; these are per-listener and ephemeral. Treating them like editorial
  placements would manufacture drama out of routine machine behavior.
- **User/third-party** — anyone's playlist. The long tail, where most placement volume and nearly
  all playlist fraud live (see 22.06).

The known-hard part: **estimated contribution**. Attributing a stream delta to a specific placement
is inference, not observation. DSPs do not report "streams from playlist X" to artists in any
generally available form. See DT-02.

### Happy Path

1. Track's placements are discovered via the tracking index (Q-01 in the parent index decides how).
2. An add is observed; an event is written with playlist, position, follower count and timestamp.
3. Timeline renders the add against the stream curve; the visual coincidence is the insight.
4. Alert fires (22.05.02): "Added to Fresh Finds — 412k followers".
5. Removal is observed weeks later; a remove event is written and alerted, with the decay visible.

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Added and removed between two polls | The event is invisible — we never sampled it | Nothing. An honest limit of polling; see `#CX-01` synthesis Q5 |
| Playlist follower count changes over time | Follower count is recorded **at event time**, not current | "412k followers when you were added" — a current count would rewrite history |
| Algorithmic playlist "removal" | Not modelled as a removal event | Algorithmic reach shown as a series, not as placements — because it is not one |
| Playlist deleted entirely | Placement ends; distinct from removal | "Playlist deleted" ≠ "you were removed" — different meanings, different responses |
| Track on 3,000 bot playlists | Volume floods the placement list; a fraud signal | Flagged to 22.06; see DT-03 |
| Placement on a playlist we don't index | Invisible | Nothing — a coverage gap, honest per 22.01.03 D-01 |
| Stream lift with no placement change | Attribution finds nothing | "No placement change explains this" — an honest null is a real answer |
| Same track on 2 ISRCs, each placed separately | Placements merge at the catalog entity (22.02.02 D-01) | Combined, with components inspectable |
| Producer detached from a project mid-view | Read access is revoked at the project boundary (Role Lens); the placement view empties for them at next fetch | "You no longer have access to this project's placements" — never a stale cached view |
| Contribution estimate surfaced through Producer read-only | The estimate label (D-03) travels with the number to every persona, not only the owner | "Estimated contribution — inference from timing, not a reported figure", identical wording for Musician and Producer |
| Musician sets a removal alert on an algorithmic playlist | Rejected at alert-creation: algorithmic reach has no removal event to fire on (D-03) | "Removal alerts apply to editorial and user playlists only — algorithmic reach is shown as a series" |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Loading | Placement history fetching | Skeleton timeline |
| Empty | No placements found | "No playlist placements found" + honest note on index coverage |
| Populated | Placements exist | Event timeline against the stream curve |
| Partial | Some DSPs indexed, others not | Explicit per-DSP coverage statement, never silent omission |
| Error | Index unavailable | Retry; existing history stays visible |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | The valuable object is the current placement list ("you are on 14 playlists") | The obvious framing, and what the candidate name implies | ❌ REJECTED: the current list is nearly worthless — it is a vanity count with no action attached. Every actionable question is about a **transition**: what did the add do to my numbers, when did the decay start, what did losing it cost, does this curator's add actually move anything. A list-shaped model cannot answer any of them and cannot be retrofitted, because the events were never recorded. Hence D-01. |
| DT-02 | Per-playlist stream attribution is observable | The assumption behind "estimated contribution" | ❌ REJECTED: DSPs do not generally expose streams-by-playlist to artists. Any contribution number is **inference from coincidence** — a delta following an add. That is defensible as an explanation and indefensible as a fact, so it must be labelled as an estimate everywhere, and must never feed 22.08.03's verified proof. This is the single most likely place for this domain to accidentally fabricate a number, which is why it is named here rather than discovered later. |
| DT-03 | What breaks at the intersection with 22.06 (Fraud Detection)? | Cross-domain failure reasoning | ✅ CONFIRMED: playlist placement is the **primary vector of artificial streaming**. Bot playlists add tracks in bulk, so a sudden fan-out of placements onto low-quality playlists is simultaneously (a) a "win" this feature would naively celebrate with an alert, and (b) the leading indicator of the distributor takedown 22.06 exists to prevent. Celebrating it would be actively harmful — we would congratulate a user on the event that is about to get their catalog removed. Placement events must therefore be classified for quality **before** they are alerted on. That is a hard dependency from 22.03.01 → 22.06, discovered here. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | Placement is an **event stream**; the current list is a derived view | DT-01. Transitions carry all the value, and cannot be reconstructed after the fact. |
| D-02 | Follower counts are recorded **at event time** | A live count silently rewrites the past — "you were added to a 412k playlist" becomes "a 3k playlist" when it decays, which destroys the record of what actually happened. |
| D-03 | Contribution is **always labelled an estimate**, and never feeds verified proof | DT-02. It is inference from coincidence; presenting it as observation is the fabrication this platform exists to end. |
| D-04 | Placement quality is classified **before** alerting | DT-03. Never congratulate a user on the event that is about to get them taken down. |
