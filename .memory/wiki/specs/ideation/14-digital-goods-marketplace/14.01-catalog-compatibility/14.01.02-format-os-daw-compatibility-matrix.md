# Feature: Format, OS/CPU & DAW Host Compatibility Matrix

> **Number**: 14.01.02
> **Parent**: [14.01 Catalog & Compatibility](./14.01-catalog-compatibility-index.md)
> **Status**: [PARTIAL]
> **Last updated**: 2026-07-17

## Overview

The vendor-declared, structured statement of what a digital product runs on: plugin format
(VST3 / AU / AAX / CLAP / standalone), operating system and minimum version, CPU architecture
(x86-64, Apple Silicon native vs Rosetta), and tested DAW hosts with versions. This is the
combinatorial fact that has no analogue in physical gear — a cable either fits or it doesn't,
but a plugin can be "supported on macOS" and still not load in the buyer's specific host.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Read-only as buyer · Config as vendor | As buyer: reads the matrix (usually via the 14.01.04 badge rather than the raw table). As vendor of a sample pack, the matrix is thin — format and DAW are often irrelevant to a WAV pack, so the required fields must collapse by product type or the flow becomes hostile. |
| Producer | Config as vendor · Read-only as buyer | The persona who actually needs the raw table — checks AAX presence for a Pro Tools room, Apple Silicon native vs Rosetta for a modern Mac. As vendor, declares and maintains the matrix per version (14.03.02): a new build can *drop* support, which is a matrix change, not just a version bump. |
| Operator | Read-only | Reads the matrix against the room's DAW and OS, which are frequently *behind* current — studios do not update mid-project. "Supports macOS 15+" is a purchase blocker for a room pinned to macOS 13. Cannot edit. |
| Fan | None | Not on the fan surface. A fan has no DAW, no host, and no reason to see a format column. |

## Behavior

The matrix is structured, per-version, and multi-axis. It is authored by the vendor at submission
(14.08.01), gates listing publish (CX-03), and is consumed by the checker (14.01.04) and by
search faceting. Support is declared per axis-combination rather than per axis independently —
"VST3 on Windows" and "AU on macOS" are separate assertions, and a product may support AAX only
on one platform.

Each host entry carries a support level rather than a boolean: `tested` (vendor ran it),
`supported` (vendor claims it, untested), `known-issue` (works with a caveat), `unsupported`.
Collapsing these into yes/no is what makes existing stores' matrices untrustworthy.

### Happy Path

1. Vendor selects product type; the matrix form renders only the axes that apply to that type.
2. Vendor declares supported formats, then per format: OS + minimum version + CPU architecture.
3. Vendor declares tested DAW hosts with version ranges and a support level per host.
4. System validates for internal contradictions (e.g. AAX declared without a Pro Tools host entry).
5. Vendor publishes; the matrix becomes the basis for badges and facets across the store.
6. On a new version (14.03.02), the vendor is prompted to confirm or amend the matrix — it does not silently carry forward.

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Vendor declares AAX but no Pro Tools host | Validation flags the contradiction at publish | "You declared AAX but listed no Pro Tools version. AAX only loads in Pro Tools." |
| New version drops OS support (e.g. macOS 12 dropped) | Matrix change on a version, not a listing edit; existing owners on that OS must be told and must retain access to the last working build (14.03.02) | Owner: "v3 drops macOS 12. Your v2 remains available in Legacy Versions." |
| Product type is a WAV sample pack — format/DAW axes are meaningless | Axes collapse; matrix reduces to file format + sample rate/bit depth | Vendor: simplified form; buyer: no host badge, no false precision |
| Vendor declares "supported" for a host they never tested, buyer hits a crash | Support level `supported` (untested) was displayed; refund path (14.09) and vendor accuracy signal | Buyer: badge showed "supported — not tested by vendor" rather than a green tick |
| Apple Silicon: native vs Rosetta-only | Distinct values, not one "macOS" row — Rosetta-only is a real performance and stability caveat in a DAW | Buyer: "Intel only — runs under Rosetta" |
| Buyer's host version falls outside the tested range (host tested at Live 11, buyer on Live 12) | Not a match and not a rejection — the checker (14.01.04) returns a partial/amber verdict, not green or red, because host-major upgrades routinely break plugins but often don't | Buyer: "Tested on Ableton Live 11; you're on 12 — vendor hasn't confirmed" |
| Host declared with an open-ended range (`≥ Live 11`) that the vendor cannot have tested against unreleased versions | Range is honoured as a claim, not a test — future host versions inherit `supported` (untested), never `tested`, regardless of the range's upper bound | Buyer on a newer host: amber, not green |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Loading | Listing loads | Matrix section skeleton |
| Empty | Vendor draft, matrix untouched | Required-field prompt; publish gate active |
| Populated | Matrix complete | Structured table + derived badge |
| Error | Validation contradiction | Inline per-row error naming the contradiction |
| Partial | Some axes declared, hosts untested | Table renders with `untested` support levels shown honestly rather than as a green tick |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | The matrix is a per-listing property | The candidate's phrasing, and how most stores model it | ❌ REJECTED — it is a per-**version** property. A v3 build routinely drops an OS or adds a format, and the listing outlives every version. Modelling the matrix on the listing means the moment a vendor ships v3, the store starts lying to everyone still on v2 — and the buyer entitled to v2 (14.03.02 legacy archive) is shown v3's requirements. This forces the matrix to hang off the version entity, which in turn is *why* the legacy archive is not optional. |
| DT-02 | A boolean "supports host X" is sufficient | Simplest model; what most stores publish | ❌ REJECTED — a domain expert would expect a support *level*. Vendors cannot test 14 DAWs × 3 OS versions; they test 3 and claim the rest. A boolean forces them to either lie (claim untested support) or under-declare (lose sales), and both outcomes poison the checker's credibility. `tested` / `supported` / `known-issue` / `unsupported` lets the vendor be honest and lets the badge be trustworthy — which matters because a wrong badge on a non-returnable good (14.09) is a refund, not a shrug. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | Support is declared per axis-*combination*, with a support level, not per axis as booleans | "VST3, macOS, Pro Tools" as three independent checkboxes asserts VST3-in-Pro-Tools, which is false (Pro Tools takes AAX). Independent axes generate impossible combinations and destroy the checker's correctness. |
| D-02 | The matrix hangs off the version, not the listing | Per DT-01. A listing outlives its versions; requirements change per build. |
| D-03 | DAW hosts are a **curated enum** for the checkable set (the ~15 mainstream hosts) plus a free-text "other" that is stored but excluded from facets and the checker | Resolves Q-01. The search cross-cut's facet ("CLAP plugins native on Apple Silicon") and the 14.01.04 checker both require a filterable, machine-comparable host identity — free text alone is unfilterable and uncheckable. A curated enum makes the common case correct; the free-text escape hatch captures the long tail without letting it poison faceting. |
