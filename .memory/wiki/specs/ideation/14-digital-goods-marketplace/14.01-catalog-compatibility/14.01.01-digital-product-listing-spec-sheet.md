# Feature: Digital Product Listing & Spec Sheet

> **Number**: 14.01.01
> **Parent**: [14.01 Catalog & Compatibility](./14.01-catalog-compatibility-index.md)
> **Status**: [SURFACE]
> **Last updated**: 2026-07-16

## Overview

The canonical record of a digital product for sale — what it is, what it costs, what you get in
the box, and what it demands of your machine. Unlike a physical gear listing (13), there is no
condition and no photograph of the actual unit; the listing *is* a spec sheet, and its accuracy
is the entire pre-purchase trust surface because the buyer cannot inspect the good before
committing to a non-returnable download.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Full | Buys plugins/packs from the listing; **also authors listings** for their own sample packs, presets and beats. Enters title, media, audio demos, price, file manifest, and the required compatibility matrix. Sees the compat badge from 14.01.04 before adding to cart. |
| Producer | Full | The heaviest buyer *and* the archetypal vendor (sample packs and presets are producer-made). Reads the file manifest for format/count/size before buying; as vendor, maintains the listing across versions (14.03.02). |
| Operator | Read-only | Buys studio software from the listing but does not author one. Reads seat/licence terms and total download size to plan a room install; cannot edit anything. |
| Fan | None | The professional store is not on the fan surface. A fan buying music from an artist page (domain 20) never sees this listing type — they see a release, and only the delivery layer (14.03) is shared. |

## Behavior

A listing is a structured record, not a rich-text blob. The structure is what makes the store
searchable (14.04.04), checkable (14.01.04), and filterable — and what lets the platform block a
publish that would predictably generate a refund. Required structured fields include: product
type (plugin / sample pack / preset pack / template / beat), file manifest (formats, count,
unpacked size, download size), the compatibility matrix (14.01.02), declared host dependencies
(14.01.03), licence terms reference (14.02.05), and monetisation model (14.07).

### Happy Path

1. Vendor opens the submission flow (14.08.01) and picks a product type — the type determines which structured sections are required.
2. Vendor fills title, description, media, and audio demos; uploads the build/content for QA (14.08.02).
3. Vendor completes the compatibility matrix and declares host dependencies — publish is blocked until both are non-empty.
4. Vendor selects a monetisation model (14.07) and attaches licence terms (14.02.05).
5. System runs QA; on pass, the listing publishes and enters the catalog.
6. A buyer opens the listing; the checker (14.01.04) renders a per-rig verdict badge above the buy button.
7. Buyer adds to cart; checkout is handled by the platform cart/payments cross-cut.

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Vendor publishes with an empty compatibility matrix | Publish blocked at gate (CX-03) | Inline "Add at least one supported format and OS before publishing" on the blocked section |
| Declared download size materially understates actual build size | QA flags mismatch between manifest and uploaded artifact | Vendor: "Manifest says 800 MB; upload is 4.2 GB. Correct the manifest or re-upload." |
| Listing depends on a product the store does not sell (e.g. full Kontakt) | Dependency recorded as external; no add-to-cart offered | Buyer: "Also requires Kontakt 7 (full version) — not sold here" |
| Vendor edits price/terms while the item sits in buyers' carts | `[PENDING — /ideate-discover Step 5 deepening]` — cart price-lock policy is a marketplace cross-cut decision | `[PENDING]` |
| Listing is delisted (vendor exit, 14.08.05; or beat exclusivity, 14.05.02) | Listing leaves the catalog but must remain reachable for existing owners' library entries | Owner: listing in read-only "no longer sold" state, downloads intact |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Loading | Listing requested | Skeleton with media frame and spec-sheet rows |
| Empty | Vendor started a draft | Draft form with required-section checklist and publish gate visible |
| Populated | Listing published | Full listing with compat badge, manifest, demos, buy control |
| Error | Fetch failed | Error with retry; cached spec sheet if previously viewed |
| Partial | Matrix present but rig incomplete | Listing renders; badge shows "Complete your rig profile to check compatibility" instead of a verdict |
| Delisted | Vendor exit or exclusivity sale | Read-only listing, no buy control, "no longer available" notice |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | A digital listing is basically a gear listing (13) minus shipping, so it should reuse the same entity | The obvious consolidation instinct; the merge D-14 already rejected at domain level | ❌ REJECTED — confirms D-14 at feature granularity. A gear listing's price is a function of *condition* on a qty=1 non-fungible unit; a digital listing's price is a function of *licence terms* on infinite stock. There is no condition field, no quantity, no shipping, and no photograph of the actual unit — but there is a matrix, a manifest, a dependency graph, and an EULA that a gear listing has no slot for. Sharing the entity yields the ~40-nullable-column `listing` D-14 predicted. |
| DT-02 | The store's viable day-one inventory is third-party commercial plugins (FabFilter, iZotope, Valhalla) | Reading D-06 ("digital plugins for DAWs") literally | ❌ REJECTED — and this is the most consequential finding in the domain. Commercial plugin vendors have no reason to list on a new store; that requires a business-development motion WeJammin cannot run at launch, and Plugin Boutique/Splice already hold those relationships. But **WeJammin's own users are the vendors** for sample packs, presets, beats and templates — a producer with a folder can list on day one with no BD required. The listing entity must therefore be *excellent* for creator-made content (14.04, 14.05) and merely *adequate* for third-party plugins. This inverts the MoSCoW the candidate order implies. Escalated as a product decision — see domain index Q-02. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | The listing is a structured record with type-conditional required sections, not free text with optional metadata | Free-text specs cannot be checked, filtered, or notified on — which disables 14.01.04, 14.04.04, and CX-01's staleness notification. Structure is the precondition for every other feature in the sub-domain. |
