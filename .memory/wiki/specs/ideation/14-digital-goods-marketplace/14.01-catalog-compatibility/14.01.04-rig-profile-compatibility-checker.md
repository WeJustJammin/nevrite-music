# Feature: Rig Profile & Compatibility Checker

> **Number**: 14.01.04
> **Parent**: [14.01 Catalog & Compatibility](./14.01-catalog-compatibility-index.md)
> **Status**: [SURFACE]
> **Last updated**: 2026-07-16

## Overview

The buyer-side half of compatibility: a saved description of the machines you actually work on
(OS + version, CPU architecture, DAWs + versions, host products you own), and the check that
joins it against a listing's matrix (14.01.02) and dependency graph (14.01.03) to answer the only
question a buyer has — *will this run for me?* Every plugin store publishes a matrix; none of
them answer this, and the gap is why "check the system requirements" is the standard reply to a
support ticket that a store could have prevented at the buy button.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Full | Creates one rig (usually a laptop), sees a green/amber/red badge on every listing. The lowest-effort persona — the profile must be worth completing in under a minute or it stays empty and the badge never renders. |
| Producer | Full | Holds **multiple** rigs — studio Mac, tour laptop, remote render box — and the verdict genuinely differs per rig. Needs a per-rig answer and a rig switcher, not an account-level yes/no. This is the persona that makes the multi-rig model non-optional. |
| Operator | Full | Rigs are **rooms**. "Will it run in Studio B" is the purchase question, and a red verdict in one room out of four drives a partial-seat purchase (14.02.02) rather than a cancelled sale. Room rigs are shared team state, not personal state — a distinction the Musician/Producer model doesn't have. |
| Fan | None | Not on the fan surface. A fan has no rig, and asking for one would be the professional-tool complexity the persona explicitly will not tolerate. |

## Behavior

A rig is a named, self-declared record. The checker evaluates two independent tests against it —
machine capability (matrix) and dependency satisfaction (graph) — and reports them separately,
because the remedies differ. Verdicts are derived at read time and never stored as truth; a matrix
edit or a new purchase must be able to change yesterday's answer.

Verdict values: `will run` · `will run — untested host` · `won't run` (with the failing axis named)
· `needs another product` (with the missing dependency named) · `can't tell` (rig incomplete, or
dependency external per 14.01.03 D-02).

### Happy Path

1. Buyer creates a rig: names it, declares OS + version, CPU architecture, and DAWs + versions.
2. System saves the rig; if the buyer has more than one, one is marked default.
3. Buyer browses the store; every listing renders a badge derived from the default rig.
4. Buyer opens a listing; badge expands to show which axis passed and which failed, per rig.
5. Buyer switches rig in the badge; verdict re-evaluates for that machine.
6. On a `needs another product` verdict, the missing dependency is offered inline (14.01.03).
7. Buyer buys with the verdict shown at the point of commitment — and the verdict is recorded against the order, so a later dispute (14.09.02) can be adjudicated against what the buyer was actually told.

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| No rig declared (the common case) | No verdict is fabricated; badge degrades to a CTA | "Add your setup to check compatibility" — never a green tick by default |
| Rig partially declared (OS but no DAW) | Machine test runs, host test cannot | "Runs on your macOS 14 — add your DAW to check host support" |
| Buyer's declared rig is wrong (says macOS 14, actually on 12) | Verdict was confidently wrong; the good is non-returnable | `[PENDING — /ideate-discover Step 5 deepening]` — whether a wrong self-declaration voids the refund claim is a policy decision, not an agent call. See Q-02. |
| Vendor edits the matrix; a wishlisted item flips to `won't run` | Buyer notified — silent regression is worse than never having badged it (CX-01) | "Serum Bank X no longer supports your macOS 12 as of v3" |
| Buyer's rig has two DAWs, product supports one | Verdict is per-DAW, not per-rig — "runs in your Live, not in your Pro Tools" | Split verdict rather than a single amber |
| Operator room rig edited by one staff member, breaking another's purchase plan | Shared-state write with no ownership model | `[PENDING — /ideate-discover Step 5 deepening]` |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Loading | Verdict being derived | Badge skeleton — never a provisional green |
| Empty | No rig exists | CTA badge: "Add your setup" |
| Populated | Rig + matrix both present | Verdict badge with per-axis expansion |
| Error | Verdict derivation failed | "Couldn't check — showing the vendor's requirements" with the raw matrix as fallback |
| Partial | Rig incomplete or dependency external | `can't tell` with the specific missing input named |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | The rig profile should be auto-detected — that's what makes it accurate and effortless | Native Access / Splice desktop app precedent; the candidate's phrasing ("Saved Rig Profile") implies detection | ❌ REJECTED for this surface, and the rejection is structural rather than a preference. Auto-detection requires a native agent that can enumerate installed DAWs and plugins. The project is **single-surface responsive web** (D-02, confirmed D-12); there is no desktop surface to host such an agent, and inventing one here would contradict a ratified decision. So the rig is **self-declared** — which means it is optional, stale-prone, and wrong sometimes. That materially weakens the feature versus the Splice/Native Access model and is the honest cost of the web-only constraint. Whether the self-declared version clears the value bar at all is escalated as a product decision (sub-domain Q-01), not assumed. |
| DT-02 | A verdict is a property of the account | Simplest model; how a single-machine store would do it | ❌ REJECTED — a verdict is a property of a **(buyer, rig, version)** triple. The Producer persona explicitly holds multiple simultaneous rigs, the Operator's rigs are rooms, and the matrix is per-version (14.01.02 DT-01) rather than per-listing. An account-level verdict is wrong for two of the three buying personas and goes stale on every vendor release. The corollary nobody asks for: the verdict shown at the buy button must be **recorded against the order**, because when a buyer disputes a non-returnable download (14.09.02) the adjudicable question is not "is it compatible" but "what did we tell them it was". |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | Rigs are self-declared, not auto-detected | Per DT-01 — forced by the single-surface web constraint (D-02/D-12). Recorded explicitly so downstream does not silently assume a detection agent exists. |
| D-02 | A buyer may hold multiple named rigs; verdicts are per-rig | Per DT-02 — required by the Producer (multiple machines) and Operator (rooms) personas. |
| D-03 | Machine capability and dependency satisfaction are reported as separate verdicts | Different remedies ("buy another product" vs "upgrade your OS"). A single collapsed badge is unactionable. |
