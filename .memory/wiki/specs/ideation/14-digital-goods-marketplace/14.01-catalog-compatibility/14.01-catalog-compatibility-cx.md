## Cross-Cut Details

### CX-01: Compatibility Matrix ↔ Rig Profile & Checker

**Relationship**: The vendor declares a support matrix (formats, OS versions, CPU architectures,
tested DAW hosts). The buyer declares one or more rigs. The checker evaluates matrix × rig and
emits a per-listing verdict: `will run` / `will not run` / `untested` / `unknown — rig incomplete`.
Data flows one way (matrix → checker ← rig); neither side mutates the other.

**Role scoping**:
- **Musician**: sees a badge on every listing; as a vendor, sees which rigs in the buyer base their matrix excludes.
- **Producer**: usually holds 2+ rigs (studio Mac, laptop, remote box) — the checker must answer per-rig, not per-account, and the answer can differ.
- **Operator**: rigs are rooms. "Will it run in Studio B" is the question, and the answer drives a multi-seat purchase (14.02.02).
- **Fan**: not affected — no visibility into the store.

**Synthesis questions answered**:
1. **Shared state conflict**: No shared entity. Matrix is vendor-owned, rig is buyer-owned; the verdict is derived and never persisted as truth.
2. **Trigger chain**: A vendor editing their matrix must re-evaluate verdicts for anyone with the product in a wishlist/cart. Async. Failure = stale badge, which is the exact defect this exists to prevent — so re-evaluation must be idempotent and re-runnable.
3. **Permission intersection**: Vendors cannot read individual rigs; only aggregate rig distribution. This is a hard privacy line — a rig profile is a fingerprint.
4. **Notification fan-out**: A matrix change that flips a wishlisted item from `will run` to `will not run` must notify the buyer. Silent regression is worse than never having shown a badge.
5. **State transition conflict**: A buyer editing their rig mid-checkout can flip a verdict after the withdrawal-waiver (14.09.01) was shown but before download. `[PENDING — /ideate-discover Step 5 deepening]`

### CX-02: Host-Dependency Graph ↔ Rig Profile & Checker

**Relationship**: The checker's verdict is a conjunction of two independent tests — machine
capability (CX-01) and dependency satisfaction. A product can pass one and fail the other, and
the two failures have different remedies, so they must be reported separately rather than
collapsed into a single red badge.

**Role scoping**:
- **Musician**: the common failure — owns Kontakt Player, buys a full-Kontakt library. Must be told *before* purchase and offered the dependency.
- **Producer**: dependency-heavy by profession; needs "what am I missing across this whole cart" rather than per-listing.
- **Operator**: dependency state is per-room, and a room's licences may be seats rather than owned copies.
- **Fan**: not affected.

**Synthesis questions answered**:
1. **Shared state conflict**: The graph is vendor-declared; owned-product state is owned by 14.03.03. Neither writes to the other.
2. **Trigger chain**: Buying the dependency must re-evaluate the dependent product's verdict. If the dependency purchase is refunded (14.09), the verdict must regress.
3. **Permission intersection**: A dependency satisfied by a *seat* (14.02.02) rather than ownership may not satisfy it in every room — an unresolved case.
4. **Notification fan-out**: Acquiring a dependency should surface "3 products in your wishlist now run" — a real merchandising moment.
5. **State transition conflict**: `[PENDING — /ideate-discover Step 5 deepening]`

### CX-03: Listing ↔ Compatibility Matrix

**Relationship**: The matrix is a required, structured section of the listing rather than free
text in a description. This is the whole point — a matrix in prose cannot be checked, filtered,
or notified on.

**Role scoping**:
- **Musician / Producer (as vendor)**: cannot publish without completing the matrix.
- **Operator**: read-only consumer.
- **Fan**: not affected.

**Synthesis questions answered**:
1. **Shared state conflict**: The matrix is a component of the listing entity; single owner, no conflict.
2. **Trigger chain**: Publish blocks on matrix completeness. Sync gate.
3. **Permission intersection**: Vendor-only edit; platform admin can force-correct a demonstrably false matrix (links to Q-02).
4. **Notification fan-out**: None at publish.
5. **State transition conflict**: None — same entity, same lock.
