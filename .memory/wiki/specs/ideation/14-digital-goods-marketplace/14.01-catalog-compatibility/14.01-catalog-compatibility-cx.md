## Cross-Cut Details

### CX-01: Compatibility Matrix ↔ Rig Profile & Checker

**Relationship**: The vendor declares a support matrix (formats, OS versions, CPU architectures,
tested DAW hosts). The buyer declares one or more rigs. The checker evaluates matrix × rig and
emits a per-listing verdict: `will run` / `will not run` / `untested` / `unknown — rig incomplete`.
Data flows one way (matrix → checker ← rig); neither side mutates the other.

**Role scoping**:
- **Musician**: sees a badge on every listing; as a vendor, sees which rigs in the buyer base their matrix excludes.
- **Producer**: usually holds 2+ rigs (studio Mac, laptop, remote box) — the checker must answer per-rig, not per-account, and the answer can differ.
- **Operator**: rigs are rooms. "Will it run in Studio B" is the question, and the answer drives a multi-seat purchase (14.02.02).
- **Fan**: not affected — no visibility into the store.

**Synthesis questions answered**:
1. **Shared state conflict**: No shared entity. Matrix is vendor-owned, rig is buyer-owned; the verdict is derived and never persisted as truth.
2. **Trigger chain**: A vendor editing their matrix must re-evaluate verdicts for anyone with the product in a wishlist/cart. Async. Failure = stale badge, which is the exact defect this exists to prevent — so re-evaluation must be idempotent and re-runnable.
3. **Permission intersection**: Vendors cannot read individual rigs; only aggregate rig distribution. This is a hard privacy line — a rig profile is a fingerprint.
4. **Notification fan-out**: A matrix change that flips a wishlisted item from `will run` to `will not run` must notify the buyer. Silent regression is worse than never having shown a badge.
5. **State transition conflict**: A buyer editing their rig after commitment can flip a live verdict before the first byte moves — but the flip reaches nothing that has been recorded. The verdict shown at the buy button is snapshotted onto the order (14.01.04 DT-02), and its job is to record *what we told them*, not what is true now; live verdicts are derived at read time and never stored as truth (14.01.04 Behavior). The waiver is not a checkout artifact either — it is captured at **first delivery of a line item**, per entitlement, and gates the bytes (14.09.01 D-01/D-04; 14.03.01 gate 3) — so the window in question is post-commitment and pre-first-byte rather than mid-checkout. Compatibility is not one of delivery's five gates (14.03.01), so a flipped verdict cannot block a download, and a `will run` badge that turns out false refunds the buyer unconditionally whoever's input was wrong (14.09.02 D-02). What remains is presentation, not state: whether a verdict that has flipped since commitment should be **surfaced at the waiver gate** — a compatibility warning on the one screen the buyer is legally required to read, about a right they are about to lose. Deferral re-pointed from the completed `/ideate-discover` Step 5 to `/create-prd` (Owner: User) — it trades conversion against informed consent, and no later stage decides it.

### CX-02: Host-Dependency Graph ↔ Rig Profile & Checker

**Relationship**: The checker's verdict is a conjunction of two independent tests — machine
capability (CX-01) and dependency satisfaction. A product can pass one and fail the other, and
the two failures have different remedies, so they must be reported separately rather than
collapsed into a single red badge.

**Role scoping**:
- **Musician**: the common failure — owns Kontakt Player, buys a full-Kontakt library. Must be told *before* purchase and offered the dependency.
- **Producer**: dependency-heavy by profession; needs "what am I missing across this whole cart" rather than per-listing.
- **Operator**: dependency state is per-room, and a room's licences may be seats rather than owned copies.
- **Fan**: not affected.

**Synthesis questions answered**:
1. **Shared state conflict**: The graph is vendor-declared; owned-product state is owned by 14.03.03. Neither writes to the other.
2. **Trigger chain**: Buying the dependency must re-evaluate the dependent product's verdict. If the dependency purchase is refunded (14.09), the verdict must regress.
3. **Permission intersection**: A dependency satisfied by a *seat* (14.02.02) rather than ownership does **not** satisfy it in every room — settled by 14.01.03 D-03 (closing that feature's Q-02): the graph is evaluated per-rig/per-room, and a seat clears an edge only for the rig it is bound to. The same host product held once as a 1-seat entitlement leaves Studio B unsatisfied.
4. **Notification fan-out**: Acquiring a dependency should surface "3 products in your wishlist now run" — a real merchandising moment.
5. **State transition conflict**: ~~`[PENDING — /ideate-discover Step 5 deepening]`~~ **RESOLVED — none persists.** Edge state is three-valued and re-derived on read (14.01.03 D-02), and verdicts are never stored as truth (14.01.04 Behavior), so buying a dependency, refunding it, or rebinding a seat changes tomorrow's answer without touching yesterday's. The only durable artifact is the verdict recorded against the order (14.01.04 DT-02), immutable by design because it is evidence of what the buyer was told rather than a cache of what is true. And a refunded dependency never reaches the dependent product's entitlement: waiver and refund are per entitlement, never per order (14.09.01 D-04), so the dependent stays delivered and owned while its "also requires" line regresses to unsatisfied.

### CX-03: Listing ↔ Compatibility Matrix

**Relationship**: The matrix is a required, structured section of the listing rather than free
text in a description. This is the whole point — a matrix in prose cannot be checked, filtered,
or notified on.

**Role scoping**:
- **Musician / Producer (as vendor)**: cannot publish without completing the matrix.
- **Operator**: read-only consumer.
- **Fan**: not affected.

**Synthesis questions answered**:
1. **Shared state conflict**: The matrix is a component of the listing entity; single owner, no conflict.
2. **Trigger chain**: Publish blocks on matrix completeness. Sync gate.
3. **Permission intersection**: Vendor-only edit; platform admin can force-correct a demonstrably false matrix (links to Q-02).
4. **Notification fan-out**: None at publish.
5. **State transition conflict**: None — same entity, same lock.

### CX-04: Host-Dependency Graph ↔ Listing

**Relationship**: Medium confidence — the display pattern is industry-standard, but the
owned/not-owned join and the inline add-to-cart for a missing dependency are our proposal and
have not been validated against a real vendor's willingness to point buyers at a competitor's
product (Kontakt is Native Instruments', not ours to sell).

**Role scoping**:
- **Musician**: read-only on both sides (14.01.03 Role Lens). Sees "also requires…" rendered inside the listing with a live owned/not-owned state, and will never open the raw graph — this edge exists so the Kontakt-Player buyer is stopped at the listing rather than at the timeout.
- **Producer**: config as vendor, read-only as buyer. Authors the required product, version range and **edition constraint** (14.01.03 D-01) into the listing's dependency section at submission; as buyer wants the cart-level rollup — "what does this basket require that I don't have" — rather than a per-listing line.
- **Operator**: read-only, and per-room rather than per-account — a seat clears an edge only for the rig it is bound to (14.01.03 D-03), so the same listing renders a different "also requires" state in Studio A and Studio B. They cannot edit any listing field, including on a listing bought for their room (14.01.01 Role Lens).
- **Fan**: not affected — the professional store is not on the fan surface (14.01.01 Role Lens).

**Synthesis questions**: Deferred — Medium confidence entry. The open half is a marketplace-policy call rather than a synthesis gap: whether a vendor accepts an inline add-to-cart pointing at a *competitor's* product, already tracked as 14.01.03 Q-01 (Owner: User → `/create-prd`). Deferral re-pointed there from the completed `/ideate-discover` Step 5. The parenthetical half is settled — a dependency not sold here is external, state `unknown` (14.01.03 D-02), and no add-to-cart is offered.
