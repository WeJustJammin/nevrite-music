# Feature: Host-Dependency & Required-Product Graph

> **Number**: 14.01.03
> **Parent**: [14.01 Catalog & Compatibility](./14.01-catalog-compatibility-index.md)
> **Status**: [PARTIAL]
> **Last updated**: 2026-07-17

## Overview

Many digital music products are not standalone — they are *content for another product*. A
Kontakt library needs Kontakt (and specifically the full version, not the free Player, past a
15-minute timeout). A Serum preset bank needs Serum. A Pro Tools session template needs the
plugins it was built with. This feature models "product requires product" as a declared graph so
the store can tell a buyer what else they need **before** they buy a file that will not open.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Read-only | Sees "also requires…" on a listing with a live owned / not-owned state. This is the persona the feature protects: the classic loss is buying a Kontakt library while owning only Player, discovering the timeout after download, and being told a non-returnable good is non-refundable. |
| Producer | Config as vendor · Read-only as buyer | As vendor of a preset bank or template, declares the required host product and minimum version — the declaration is the product's most important field, since without it the buyer gets an unopenable file. As buyer, wants cart-level rollup: "what does this whole basket require that I don't have?" |
| Operator | Read-only | Evaluates dependencies **per room, not per account** (D-03). A room's host product is typically held as a seat (14.02.02) bound to that room's rig, not owned account-wide. A seat satisfies an edge for the room it is bound to and no other — the same host product owned once as a 1-seat entitlement does not clear the dependency in a second room. This mirrors the checker's already-decided per-rig granularity (CX-01, CX-02). |
| Fan | None | Not on the fan surface. A fan owns no host products and buys no content for them. |

## Behavior

Vendors declare dependencies at submission as structured edges: `requires <product> <version-range>
<edition-constraint>`. Edition constraint is the field that matters and that no store models well —
"Kontakt 7" is not the requirement; "Kontakt 7 **full**, not Player" is. Dependencies may point at
products the store sells (joinable, offerable) or at external products it does not (declared only).

The graph is evaluated against the buyer's owned-product state (14.03.03) to produce
satisfied / unsatisfied per edge. This is a *separate* verdict from machine compatibility
(14.01.02) because the remedy differs — one is "buy another thing", the other is "get another
computer" — and collapsing them into one red badge tells the buyer nothing actionable.

### Happy Path

1. Vendor declares the required host product, version range, and edition constraint at submission.
2. System resolves the declaration against the catalog; if the required product is sold here, the edge becomes joinable.
3. Buyer opens the listing; the graph is evaluated against their library (14.03.03).
4. Satisfied edges render quietly ("Requires Kontakt 7 full — you own this"); unsatisfied edges render loudly with the remedy.
5. If the missing dependency is sold here, an add-to-cart is offered inline.
6. Buyer acquires the dependency; the dependent product's verdict re-evaluates (CX-02).

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Buyer owns Kontakt **Player**, product needs full Kontakt | Edge unsatisfied on edition constraint despite the product name matching | "Requires Kontakt 7 **full version** — you have Kontakt Player. Player will time out after 15 minutes." |
| Required product is not sold on WeJammin (Kontakt, Serum) | Edge declared as external; state is unknown, not unsatisfied — we cannot see a library we don't sell | "Also requires Serum 1.3+ (not sold here) — check you have it" |
| Buyer owns the dependency via a rented/subscription entitlement (14.07.02) that later lapses | Entitlement change re-triggers evaluation (CX-02 trigger chain); the edge flips satisfied → unsatisfied. The dependent product is still owned but its verdict now reads unsatisfied. WeJammin never disables the dependent file — it only reports the requirement no longer holds; whether the file still opens is the host vendor's DRM, not ours. | Buyer: dependent product's badge flips to unsatisfied — "You no longer meet the requirements for this — your Serum subscription lapsed. Re-subscribe to restore." No dunning on the dependent product; the remedy points at the dependency. |
| Dependency refunded (14.09) after the dependent product was bought on the strength of it | Verdict regresses; the dependent product does not | Buyer: dependent product's badge flips to unsatisfied |
| Circular or self-referential declaration | Rejected at submission validation | Vendor: "A product cannot require itself or form a dependency cycle." |
| Vendor of the dependency exits the platform (14.08.05) | The joinable edge degrades to external: existing owners keep the dependency and their edges stay satisfied, but the inline add-to-cart (CX-04) is withdrawn because the target is no longer buyable here. A buyer who does not already own it can no longer satisfy the edge on WeJammin. | New buyer of the dependent product: edge renders unsatisfied with the remedy demoted to advisory — "Requires X (no longer sold here) — you must obtain it elsewhere." Pre-purchase, not post-download. |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Loading | Listing loads | Dependency section skeleton |
| Empty | Product has no dependencies (a standalone plugin, a WAV pack) | Section omitted entirely — not an empty state, an absent one |
| Populated | Dependencies declared and resolved | Per-edge list with owned/not-owned/unknown state and remedies |
| Error | Resolution failed | "Couldn't check what you own — requirements shown without your status" |
| Partial | Some edges internal (joinable), some external (unknown) | Mixed list; external edges honestly marked "can't check" rather than assumed satisfied |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | Product name + version range is a sufficient dependency declaration | The obvious model; how a package manager does it | ❌ REJECTED — **edition** is the axis that actually breaks buyers, and it is invisible in a name+version model. Kontakt Player and Kontakt full report the same product and version; the difference is a licence tier, and it is the single largest source of sample-library returns industry-wide. The same shape recurs elsewhere (Reaktor Player, UVI Workstation, Play vs Opus). Without an edition constraint the graph produces confidently wrong "you're covered" verdicts, which is worse than no graph at all. |
| DT-02 | The store can always tell whether a dependency is satisfied | Implicit in the "owned/not-owned" framing of the candidate | ❌ REJECTED — and this is a boundary worth being honest about. The most commonly required host products (Kontakt, Serum, Omnisphere) are **not sold here** and never will be at launch (DT-02 in 14.01.01). We cannot see a buyer's Native Instruments library. So the graph has three states, not two, and the third — `unknown` — is the *common* case for exactly the dependencies that matter most. Rendering `unknown` as `unsatisfied` cries wolf; rendering it as `satisfied` is the Kontakt-Player defect again. It must be its own state with its own copy. |
| DT-03 | The graph is evaluated once per account — "do you own the required product?" | The simplest evaluation model, and how a wishlist "owned" badge would work | ❌ REJECTED — this resolves Q-02. The Operator's host products are **seats** (14.02.02), and a seat is bound to one room's rig, not to the account. A 1-seat Kontakt entitlement spent in Studio A does not make a Studio-B session template's dependency satisfied — the room that matters has no seat left to bind. An account-level "you own Kontakt → satisfied" verdict would clear the edge for a room that cannot actually run the file, which is the same confidently-wrong failure DT-01 rejects, one layer up. Evaluation must therefore be **per-rig/per-room**, matching the granularity the checker already committed to in CX-01/CX-02. A seat satisfies an edge only for the rig it is bound to. The trade-off — a Producer with the software installed on three machines but only two seats sees the edge unsatisfied on the third rig — is correct, not a defect: the third rig genuinely cannot open the file. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | Dependency edges carry an **edition constraint**, not just name + version range | Per DT-01. Edition mismatch is the dominant real-world failure and is invisible without this field. |
| D-02 | Edge state is three-valued — satisfied / unsatisfied / unknown — not boolean | Per DT-02. External dependencies (the majority of important ones) are unknowable, and both boolean collapses produce a worse outcome than admitting it. |
| D-03 | The graph is evaluated **per-rig/per-room**, not per-account; a seat (14.02.02) satisfies an edge only for the rig it is bound to | Per DT-03, resolving Q-02. Aligns dependency evaluation with the checker's per-rig granularity (CX-01/CX-02) and prevents an account-level "owned" verdict from clearing an edge in a room that has no seat to run the file. |
