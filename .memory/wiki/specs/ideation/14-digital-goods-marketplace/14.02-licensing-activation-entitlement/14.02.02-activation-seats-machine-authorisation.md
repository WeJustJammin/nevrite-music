# Feature: Activation, Seats & Machine Authorisation

> **Number**: 14.02.02
> **Parent**: [14.02 Licensing, Activation & Entitlement](./14.02-licensing-activation-entitlement-index.md)
> **Status**: [SURFACE]
> **Last updated**: 2026-07-16

## Overview

Binding an entitlement to specific physical machines, and bounding how many. This is where a
digital storefront stops being a shop and becomes a **runtime dependency of software it did not
write** — if this feature is down, paid work stops in studios, which is an availability obligation
of a completely different order from "the store is slow today".

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Full | 1–2 machines; rarely thinks about seats until the laptop dies with a seat still bound to it and the replacement won't activate. The persona for whom an unforgiving seat model is pure downside — they have no IT department and no second copy. |
| Producer | Full | Many machines (studio Mac, tour laptop, render box), frequently reinstalled, and works to deadlines. Hits seat exhaustion *legitimately* and constantly. Also the persona who works offline in a studio with no network — see 14.02.03. |
| Operator | Full | **The heaviest user of this feature.** Seats are rooms; a 4-room studio needs 4 seats and needs to know which room holds which. Staff turnover means seats must be reassignable by the business, not by the departed engineer's personal account. Needs an org-level seat map — which sub-domain Q-03 has not resolved. |
| Fan | None | Not on the fan surface. Fan purchases (domain 20) are content, not software; there is nothing to activate and no seat to spend. |

## Behavior

Activation binds a machine fingerprint to an entitlement, spending a seat (CX-01). Deactivation
returns it. Seat allowance comes from the entitlement's monetisation model. The core design
question is not the mechanism but the **failure posture**: what happens when the check cannot be
made. Failing closed protects vendors and stops a session; failing open protects the working
musician and weakens enforcement.

### Happy Path

1. Holder installs the software and requests activation.
2. System computes a machine fingerprint and checks the entitlement's remaining seats.
3. Seat available → fingerprint bound, seat decremented, authorisation returned.
4. Software runs; the holder sees the machine listed in their library (14.03.03).
5. Holder retiring a machine deactivates it; the seat returns immediately.

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Machine dies without deactivation — seat stranded | Self-service seat reclaim, rate-limited. A holder who must email support to use software they bought will not buy again. | "Release all seats" with a cooldown, or per-machine forced release |
| Seats exhausted legitimately (Producer with 4 machines, 2 seats) | Purchase more seats (14.07) or deactivate another machine | "2 of 2 seats in use — release one or add seats" |
| Hardware upgrade changes the fingerprint (new RAM, new drive) | Fingerprint drifts; a strict match deactivates a machine that never moved | `[PENDING — /ideate-discover Step 5 deepening]` — fingerprint tolerance is unresolved; too strict punishes legitimate upgrades, too loose makes seats meaningless |
| Activation server unreachable mid-session | The core question. Fail-open (grace period) keeps the session alive; fail-closed stops paid work over *our* outage. | `[PENDING]` — see D-01 and Q-01 |
| Concurrent activation from two machines against the last seat | Must not both succeed — needs a lock, not read-then-write (CX-01) | Loser: "No seats available" |
| Revocation (14.09.03) races an in-flight activation | Revocation wins; activation rejected | "This licence is no longer active" with reason |
| Studio engineer leaves; seat bound to their personal machine and entitlement | Blocked on Q-03 (org ownership) — today the studio loses its own plugin | `[PENDING — /create-prd-architecture]` |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Loading | Activation requested | "Activating…" |
| Empty | Entitlement held, no machines activated | Seat map with 0 of N used |
| Populated | Machines bound | Per-machine list: name, last seen, release control |
| Error | Activation refused | Reason-specific message (no seats / revoked / blacklisted), never a generic failure |
| Partial | Activated but the check is stale (offline grace) | "Authorised — last verified 3 days ago" |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | Activation should fail closed when the check can't be made — that's what enforcement means | Standard DRM reasoning; the vendor's interest | ❌ REJECTED as a default, on evidence from this project's own personas. The Producer "works inside a DAW, not a browser" and runs sessions in rooms that are frequently offline; the Operator's rooms are sometimes deliberately air-gapped. Fail-closed means **WeJammin's outage stops a paid session with a client in the room** — and the persona's switching trigger is precisely "losing money to a system that failed them". The blast radius of a fail-closed default is a studio that never trusts us again; the blast radius of fail-open is some marginal piracy on a catalog that, per 14.01.01 DT-02, is mostly key-less creator content nobody can enforce anyway. Recommendation: fail **open** with a bounded offline grace window, and let vendors of high-value software opt into stricter posture. Escalated as a product decision (Q-01) — it is a values call about whose risk we absorb, not an implementation detail. |
| DT-02 | Seat exhaustion is a piracy signal | The naive read; how a vendor would frame it | ❌ REJECTED — it is overwhelmingly a **legitimate** signal in this user base, and treating it as suspicion inverts the product. The Producer persona is defined by holding multiple simultaneous machines; the Operator's seats are rooms. The industry's chronic defect here (Waves, older NI) is a seat model built for a single-machine consumer, applied to professionals who are multi-machine by definition — producing the well-known "I bought this and now I can't use it" support pathology. The corollary nobody asks for: **self-service seat reclaim with a cooldown is not a nice-to-have, it is the feature**. Every store that omits it converts a hardware failure into a support ticket and a lost customer. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | Recommend fail-**open** with a bounded offline grace window as the default posture; vendors may opt into stricter | Per DT-01 — the personas make fail-closed a customer-destroying default. Recorded as a recommendation, not a lock: this is a product decision (Q-01). |
