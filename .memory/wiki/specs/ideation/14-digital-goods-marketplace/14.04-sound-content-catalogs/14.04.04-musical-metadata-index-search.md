# Feature: Musical Metadata Index & Key/BPM-Aware Search

> **Number**: 14.04.04
> **Parent**: [14.04 Sound Content Catalogs](./14.04-sound-content-catalogs-index.md)
> **Status**: [PARTIAL]
> **Last updated**: 2026-07-17
> **Origin**: **Deep Think addition** — not in the sweep's 24 candidates.

## Overview

The index that makes sound findable by musical properties rather than words — tempo, key,
instrument, character, target synth — across the store's three content catalogs *and* the buyer's
own asset library (14.03.04). Generic marketplace search finds a *pack*; this finds a **sound at
142 BPM in G minor that fits the track already open**. That is a different query, over different
data, answering a different question, and it is why a sample store is not a shop with audio files.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Read-only | Searches by feel and tempo. Does not author metadata (except as a vendor) and does not think about the index — they think about the sound. Their tags on owned assets (14.03.04) are the one thing they write. |
| Producer | Read-only · Config as vendor | The persona this exists for. Searches against the session in progress: tempo of the track, key of the track, "something dusty". As a vendor, declares the metadata that feeds the index — and their carelessness poisons everyone's results (index Q-03). |
| Operator | None | No column across this entire sub-domain. A studio operator has no reason to search for loops by key. Explicit absence. |
| Fan | None | Not on the fan surface. Musical-property search over a professional catalog is exactly the professional-tool complexity personas.md says the Fan will not tolerate. |

## Behavior

One index, per-type facet schemas (CX-01, CX-02), two scopes. Samples index on BPM, key,
instrument, loop/one-shot, duration; presets on target synth, category, character (no BPM);
templates on DAW, genre, tempo. Forcing a single schema across content types reproduces the
nullable-column defect D-14 rejected at domain level.

Two scopes with a hard boundary: **store** (what I could buy) and **library** (what I own and may
legally use). Per 14.03.04 D-02 these share the index and the vocabulary but are never interleaved
in results — the library scope's answer must be unambiguous.

Musical facets are relational rather than exact: "in key with G minor" includes relative majors
and adjacent keys; "around 142" includes 71 and 284 (half/double time) and ±4 BPM, because that is
what a producer actually means.

### Happy Path

1. Vendor publishes a pack; metadata is declared and cross-checked against extraction (14.04.01 Q-03).
2. Contents index per file, async (CX-01).
3. Buyer searches "142 BPM, G minor, kick" with the store scope.
4. Results include exact matches plus musically-compatible neighbours, ranked, auditionable inline.
5. Buyer switches to the library scope; the same query runs over what they own.
6. Buyer finds nothing owned; the store band appears separately — never interleaved.

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Vendor's key metadata is wrong | Poisons results; buyer blames the search, not the vendor | Extraction cross-check; systematic offenders to QA — see index Q-03 |
| Key is genuinely ambiguous (atonal, percussive, modal) | Key detection is hard and often meaningless — a kick has no key | Metadata must be *nullable and honest*, not force-filled with a wrong value |
| Buyer searches 142 BPM; a 71 BPM loop fits perfectly at double time | An exact-match filter hides the best result | Half/double-time inclusion is a correctness requirement, not a refinement |
| "In key" across relative majors/minors | G minor and B♭ major share a key signature; both fit | Relational facets, not string equality |
| Search returns 40,000 loops | Unusable; the buyer needs 6 | Ranking is the product, not filtering — see Q-02 |
| Buyer's library is empty, store scope is full | Library scope's honest answer is "nothing" | Empty state that offers the store band without interleaving it |
| Pack indexed but audition unavailable | Search results a buyer cannot hear are close to worthless | Degrade honestly; audition is the point (14.04.01 DT-01) |
| Vendor stuffs the popular values (declares "142 BPM, C minor" on everything to appear in every hot query) | The SEO-keyword-stuffing attack ported to a sound catalog — a metadata table with a mandatory key column invites exactly this | Extraction disagreement collapses declared-only confidence (D-04); stuffed listings rank below both-agree matches and route systematic offenders to QA (index Q-03) — `[PENDING — ranking/anti-gaming model, Q-02 → /write-be-spec]` |
| Library scope surfaces a sound whose licence has lapsed/been revoked (subscription-sourced asset, expired grant) | Library scope's contract is "what I own **and may legally use**" — returning an unusable sound as owned is a correctness failure, not a stale cache | Legality is a filter on the library scope, not a warning banner; excluded from results with an honest "no longer in your library" affordance — boundary owned by 14.03.04, `[PENDING — /write-be-spec]` |
| Two buyers hit the same query mid-reindex of a large pack; result counts differ second-to-second | Async per-file indexing (CX-01) means the corpus is a moving target; a stable rank position that jumps under the cursor feels broken | Snapshot the result set per query; new packs land in the next query, not mid-scroll — surfaced via the Partial state, never by silently reshuffling |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Loading | Query submitted | Result skeleton |
| Empty | No matches in scope | Facet-relaxation suggestions ("no 142 in G minor — try ±4, or B♭ major") |
| Populated | Matches found | Ranked, auditionable results with metadata visible |
| Error | Index unavailable | Fall back to browse-by-pack; never a blank page |
| Partial | Indexing in progress on a new pack | "Some new packs are still being indexed" |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | This is the marketplace search cross-cut with extra fields — reuse it and add BPM as a facet | The consolidation instinct, and the reason nobody in the sweep named this as a node: search *is* already a known platform cross-cut serving 05, 13, 14, 16 | ❌ REJECTED — the platform search cross-cut indexes **listings**; this indexes **the contents of listings**, which is a different object at a different granularity. One pack is one listing and 800 indexed files. Worse, the facets are *relational, not equal*: "142 BPM" must match 71 and 284 (half/double time) and ±4; "G minor" must match B♭ major and adjacent keys. No generic faceted search does this, because outside music it is nonsense. And the index's most valuable scope is not the store at all — it is the buyer's own library (14.03.04), which the marketplace search cross-cut has no business touching. So: use the platform cross-cut to find *packs*, and this to find *sounds*. They are not the same feature, which is exactly why the sweep's candidate list mentions "BPM/key metadata" as a throwaway property of candidate 10 and never notices the capability. |
| DT-02 | Metadata should be complete — force vendors to fill every field so the index is reliable | The data-quality intuition; incomplete metadata means missed results | ❌ REJECTED — **forced metadata is worse than absent metadata**, because a wrong value is indistinguishable from a right one and silently poisons every query it touches. Key detection is genuinely hard and frequently meaningless: a kick has no key, a noise sweep has no key, an atonal texture has no key, and a modal loop has several defensible answers. Make the field mandatory and vendors will put *something* there — and now the index confidently returns a "G minor" kick that is nothing of the sort, in a result set the buyer trusts. Nullable-and-honest beats complete-and-wrong. The corollary nobody asks for: the index needs a **confidence** notion, not just values — vendor-declared vs extracted vs both-agree are different epistemic states, and "both agree" is the only one worth ranking highly. That is a materially different index than a metadata table with a key column. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | One index, per-type facet schemas | Per CX-02. A pad has no BPM; a single schema across content types is the nullable-column defect at metadata level. |
| D-02 | Musical facets are relational, not exact — half/double time and key compatibility are correctness requirements | Per DT-01. An exact-match filter hides the results a producer actually wants, which makes the search feel broken for reasons they can't articulate. |
| D-03 | Metadata fields are nullable and honest; no forced completion | Per DT-02. Complete-and-wrong poisons the index invisibly; absent is at least honest. |
| D-04 | The index carries confidence (declared / extracted / agreeing), not just values | Per DT-02's corollary — "both agree" is the only state worth ranking highly, and that cannot be expressed by a value alone. |
