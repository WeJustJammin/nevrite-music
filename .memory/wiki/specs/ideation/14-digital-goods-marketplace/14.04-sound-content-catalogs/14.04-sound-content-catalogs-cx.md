## Cross-Cut Details

### CX-01: Sample Packs ↔ Metadata Index

**Relationship**: A published pack's contents are indexed per file — BPM, key, instrument, loop
vs one-shot, duration. This index serves both the store (browse a pack's 800 loops before buying)
and the buyer's own library after purchase (14.03.04 CX-05). The same extraction runs once and
feeds both.

**Role scoping**:
- **Musician**: searches the store by feel and tempo; never reads a file list.
- **Producer**: searches against the track in progress — "142, G minor, something dusty".
- **Operator**: not affected — no column in this sub-domain.
- **Fan**: not affected.

**Synthesis questions answered**:
1. **Shared state conflict**: Vendor declares metadata; the platform may extract/verify it (index Q-03). On disagreement, whose value wins is unresolved — vendor authority preserves intent, extraction preserves accuracy.
2. **Trigger chain**: Publish → per-file indexing, async. A 5,000-file pack is not indexed synchronously at publish. Failure means the pack is buyable but unsearchable, which is a soft failure worth shipping over.
3. **Permission intersection**: Store scope shows metadata for unowned packs (that's the audition); library scope (14.03.04) requires entitlement.
4. **Notification fan-out**: None.
5. **State transition conflict**: A pack revised (index Q-01) re-indexes; buyer tags on removed assets are orphaned (14.03 CX-06).

---

### CX-02: Presets ↔ Metadata Index

**Relationship**: Presets share the index but not the schema. A preset has a target synth, a
category (bass/pad/lead), and a character — and no BPM. Forcing one schema across content types
produces the nullable-column defect D-14 rejected at domain level, reproduced at metadata level.

**Role scoping**:
- **Producer**: the primary searcher — "Serum, bass, gritty".
- **Musician**: same, lighter.
- **Operator / Fan**: not affected.

**Synthesis questions answered**:
1. **Shared state conflict**: None — per-type facet schemas, one index.
2. **Trigger chain**: Publish → index. Same async path as CX-01.
3. **Permission intersection**: Same as CX-01.
4. **Notification fan-out**: None.
5. **State transition conflict**: None.

### CX-03: Templates ↔ Presets

**Relationship**: A template's manifest enumerates what it needs. Where a dependency is a preset
bank sold here, the manifest can join it — showing owned/not-owned and offering the missing piece.
This is the same graph as 14.01.03; the manifest is a many-edge instance of it.

**Role scoping**:
- **Producer**: as vendor, must declare what their session references — which is tedious and therefore will be skipped unless generated.
- **Musician**: as buyer, needs to know the true cost of a template before buying: the template is £15 and its dependencies are £400.
- **Operator / Fan**: not affected.

**Synthesis questions answered**:
1. **Shared state conflict**: The manifest is vendor-declared; owned-state comes from 14.03.03. No writes across.
2. **Trigger chain**: Buying a dependency re-evaluates the template's readiness (14.01 CX-02).
3. **Permission intersection**: Owning the template does not license its dependencies. This is the trap — see CX-04.
4. **Notification fan-out**: Acquiring a dependency could surface "your template is now complete".
5. **State transition conflict**: A dependency delisted (vendor exit, 14.08.05) leaves a template permanently uncompletable for new buyers.

### CX-04: Templates ↔ Sample Packs

**Relationship**: The hard one. A project template is largely *pointers to other people's
content*. If it bundles the loops it references, the template's vendor is redistributing another
vendor's licensed content — usually forbidden by the very terms (14.02.05) that pack was sold
under. If it doesn't bundle them, the buyer opens a session full of missing files.

**Role scoping**:
- **Producer**: as vendor, faces an unpleasant choice with legal consequences; as buyer, faces a broken session.
- **Musician**: buys a template expecting a working session and gets a dependency shopping list.
- **Operator / Fan**: not affected.

**Synthesis questions answered**:
1. **Shared state conflict**: None structurally — but the *licensing* conflict is real and is the feature's central problem (14.04.03 DT-02).
2. **Trigger chain**: Template purchase does **not** grant its dependencies. Must be stated before purchase, loudly.
3. **Permission intersection**: Direct and adversarial — the template's terms cannot grant rights over a pack the template's vendor merely licensed. 14.02.05 DT-03's "vendors granting rights they don't hold", in its most common form.
4. **Notification fan-out**: None.
5. **State transition conflict**: `[PENDING — /ideate-discover Step 5 deepening]`

### CX-05: Sample Packs ↔ Presets

**Relationship**: Medium confidence. Real products mix types — a drum library ships WAVs *and*

with mixed content or two products bundled (14.07.04) is unresolved.

## Rejected Pairs

| # | Source | Target | Reason for Rejection |
|---|--------|--------|---------------------|
| R-01 | 14.04.02 Presets | 14.04.01 Sample Packs | As a *dependency* relationship: rejected. A preset needs a synth (14.01.03's graph), not a sample pack; a loop needs nothing. They look adjacent because they sit in one store and are made by the same people, but neither requires the other. The genuine overlap is packaging (CX-05), which is a different claim and recorded separately. |
| R-02 | 14.04.04 Metadata Index | 14.04.03 Templates | A template's searchable attributes are genre and tempo — which is 14.04.04's ordinary job via CX-03's manifest and the listing's own fields. There is no template-specific *indexing* concern: the manifest is a dependency artifact, not a metadata one. A direct edge would imply the index must understand session-file internals, which it does not and should not. |
