# Feature: Project Template Catalog & Dependency Manifest

> **Number**: 14.04.03
> **Parent**: [14.04 Sound Content Catalogs](./14.04-sound-content-catalogs-index.md)
> **Status**: [SURFACE]
> **Last updated**: 2026-07-16

## Overview

Selling a DAW session — a mix template, a mastering chain, a genre starter, a finished track with
its stems and routing intact. The product is a session file plus a **dependency manifest**: an
enumeration of every plugin, preset and sample the session references, because a session file is
mostly pointers to other people's content and opening one without its dependencies produces a
screen of missing-plugin errors.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Full | The buyer — usually the learner. Buys a template to see how a record is actually built, which is a teaching transaction wearing a product's clothes (index Q-02). Needs to know the *true* cost before buying: the template is £15 and its dependencies are £400. |
| Producer | Full | The vendor — the teacher. Sells sessions from their own catalog, which is the highest-trust thing they can sell because it exposes their actual method. Also the persona who must declare the manifest, and who will not do it by hand for a 90-track session (DT-01). |
| Operator | None | No column. A studio does not buy project templates; it provides rooms in which sessions are made. Explicit absence. |
| Fan | None | Not on the fan surface. A fan has no DAW to open a session in. |

## Behavior

A template is a listing (14.01.01) of product type `project-template` carrying: target DAW and
version, and a manifest of every referenced dependency — plugins, presets (CX-03), sample packs
(CX-04) — each resolved against the catalog where possible and against the buyer's library
(14.03.03) to show owned/not-owned/unknown.

The manifest is a many-edge instance of the dependency graph (14.01.03). That feature owns the
graph; this feature owns the **missing-dependencies-to-cart flow** and the honest total-cost
display.

The central unsolved problem is CX-04: a session references loops and presets the vendor licensed
but does not own. Bundling them redistributes another vendor's content — usually forbidden by the
very terms it was sold under. Not bundling them ships a broken session.

### Happy Path

1. Vendor uploads a session; the manifest is generated from the session file's references (DT-01).
2. Vendor reviews the generated manifest, declares bundled vs referenced content, and attests rights on anything bundled (14.02.05 DT-03).
3. System resolves manifest edges against the catalog; publishes.
4. Buyer opens the listing; sees the template price **and** the resolved cost of what they're missing.
5. Buyer buys the template and, optionally, the missing dependencies via an inline cart.
6. Buyer opens the session; it loads because the manifest was honest.

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Template references a £300 plugin the buyer lacks | The template is unusable without it; this must be visible before purchase | "You're missing 4 of 11 dependencies — £340 to complete" *above* the buy button |
| Vendor bundles loops licensed from another vendor (CX-04) | Redistribution, usually forbidden by the source pack's terms. 14.02.05 DT-03 in its most common form. | Bundled content requires an explicit attestation; the platform cannot verify it |
| Vendor doesn't bundle, buyer can't get the loops (pack delisted) | Session permanently uncompletable for that buyer | `[PENDING — /ideate-discover Step 5 deepening]` |
| Buyer owns a *different version* of the DAW | Session files are frequently forward-only; a Live 12 set won't open in Live 11 | Target DAW version is a required, gating field |
| Manifest is incomplete (vendor missed a dependency) | Buyer opens to missing-plugin errors and blames the store | Generation over hand-declaration (DT-01) is the only realistic defence |
| Buyer owns the dependency via a lapsed subscription (14.07.02) | Was satisfied at purchase, unsatisfied later — the session degrades over time | 14.01.03 edge case; unresolved |
| Template contains a full finished track | Is this a template or a release? Terms must distinguish "learn from this" from "release this" | Terms (14.02.05) carry the distinction, not the product type |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Loading | Listing fetch | Skeleton with manifest placeholder |
| Empty | No templates match | Empty state with facet suggestions |
| Populated | Template listed | Manifest with per-edge owned state, total completion cost, DAW target |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | The vendor declares the manifest | The candidate's framing ("Dependency Manifest" as a listing field), and how every dependency declaration in this domain works | ❌ REJECTED — **a hand-declared manifest will be wrong, always, and its wrongness is the buyer's problem.** A mix template is 40–90 tracks referencing dozens of plugins, several preset banks, and hundreds of audio files; asking a producer to enumerate that by hand guarantees omissions, and each omission is a buyer opening to missing-plugin errors. The information already exists — a session file *is* a manifest, machine-readable, listing exactly what it references. So the manifest must be **generated from the uploaded session and confirmed by the vendor**, not typed. This is a materially different capability (parse Ableton/Logic/Pro Tools/FL session formats) than a form field, with real per-DAW cost, and it is the difference between a product that works and one that generates refunds. Note the awkward consequence: it puts session-format parsing — proprietary, undocumented, version-drifting formats — on the critical path of a `could`-priority feature (see Q-01). |
| DT-02 | Templates are a product, and they belong in the store | The candidate's placement (candidate 12, in domain 14), which I inherited | ⏳ DEFERRED — escalated to index Q-02, because the classification is genuinely contestable and I should not resolve it alone. "Here is my actual mix session, see how I did it" is **pedagogy with a file attached** — the buyer is a learner, the vendor is a teacher, and the value is the method rather than the asset. Domain 06 (Education, Lessons & Mentorship) owns exactly that transaction. The domain map's own principle for the 14/20 seam was *split by destination* (a producer buying a sample pack is in the store; a fan buying an album is on the artist's page) — apply it here and a template bought while learning belongs in the classroom, while a template bought as a starter belongs in the store. The same file, sold to the same person, lands in two domains depending on why. That is a sign the boundary is drawn on the wrong axis, and it is worth an owner's ruling rather than an agent's guess. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | The manifest is generated from the uploaded session and confirmed by the vendor, not hand-declared | Per DT-01. Hand-declaration is guaranteed-incomplete, and each omission is a broken session for a buyer. |
| D-02 | Total completion cost (template + missing dependencies) is shown before the buy button | A £15 template that needs £400 of plugins is a £415 purchase. Concealing that is the refund generator this product type is prone to. |
| D-03 | Bundled vs referenced content must be explicitly declared, with an attestation on anything bundled | Per CX-04 — the redistribution problem is this feature's defining legal hazard. |
