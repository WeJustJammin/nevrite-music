# Feature: Download Delivery & Resumable Transfer

> **Number**: 14.03.01
> **Parent**: [14.03 Delivery, Versioning & Library](./14.03-delivery-versioning-library-index.md)
> **Status**: [SURFACE]
> **Last updated**: 2026-07-16

## Overview

Moving the bytes the buyer paid for onto their machine, authorised against their entitlement and
survivable across a dropped connection. The scale is what makes this non-trivial: sample libraries
routinely run 40–100 GB, they are re-fetched every time a machine is replaced, and a transfer that
cannot resume is a transfer that never completes on a hotel wifi or a studio's saturated uplink.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Full | Downloads to one machine, usually on domestic broadband. Re-downloads years later on a new laptop and expects it to still be there — the perpetual promise (14.08.05) is meaningless if the bytes aren't fetchable. |
| Producer | Full | Downloads the same product to several machines, repeatedly, often against a deadline. The persona for whom "start again from 0%" after a 60 GB failure is a workday lost. Repeated fetches across machines must not be read as abuse. |
| Operator | Full | Installs per room, sometimes on a locked-down or metered studio network, sometimes air-gapped (in which case a browser download on a connected machine and a manual carry is the real workflow — see Q-02). |
| Fan | Read-only | The shared path. A fan buying an album on an artist page (domain 20) fetches it through this same authorised gate — small files, no versions, no resume drama. They see "download", not a transfer manager. This is the acknowledged reuse the domain index names. |

## Behavior

Every download is authorised per request against a live entitlement check (CX-01) and served
through a short-lived, buyer-scoped URL — never a static link. Transfers support byte-range
resumption and integrity verification on completion. Where the vendor has enabled watermarking
(14.03.05), the stamp is applied in this path, which makes the artifact per-buyer and therefore
uncacheable (CX-04).

Version resolution (CX-02) defaults to the latest the buyer is entitled to; the archive is
reachable by explicit selection.

### Happy Path

1. Buyer opens their library (14.03.03) and requests a download.
2. System checks entitlement state, version entitlement, and withdrawal-waiver capture (14.09.01).
3. All pass → a short-lived buyer-scoped URL is minted.
4. Transfer begins; progress and remaining size are shown honestly for a multi-GB artifact.
5. Connection drops at 60% → transfer resumes from the byte offset, not from zero.
6. On completion, integrity is verified against a published checksum.

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| 60 GB transfer, connection drops repeatedly | Byte-range resume; the URL's short lifetime must not outlive a legitimately slow transfer — a link expiring mid-download is a self-inflicted failure | Progress persists across retries; "resuming from 38 GB" |
| Browser tab closed mid-transfer | **The web-surface wall.** A browser download manager is outside our control; a background, restartable, verified transfer of 100 GB is what a native app exists for (index Q-01). | `[PENDING]` — depends on Q-01 |
| Buyer's disk fills at 90% | Transfer fails late, after hours | Should be pre-empted: unpacked size shown *before* starting, not just download size |
| Entitlement revoked (14.09.03) mid-transfer | In-flight transfer racing revocation (CX-01) | `[PENDING — /ideate-discover Step 5 deepening]` — kill mid-stream or let it complete |
| Same product fetched to 5 machines in a day | Legitimate for a Producer; looks like link-sharing | Must not be rate-limited into uselessness — see Q-03 |
| Download URL shared with a friend | Short-lived + buyer-scoped limits the window, but a live URL is a live URL | Watermarking (14.03.05) is the actual deterrent, not the URL |
| Vendor has exited (14.08.05) | Bytes must still serve — the perpetual promise is a storage obligation | Normal download; buyer sees "no longer sold" but downloads fine |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Loading | Download requested | "Preparing your download…" (URL mint, watermark stamp) |
| Empty | Nothing purchased | Library empty state, no downloads |
| Populated | Entitlement active | Download control with size, version, checksum |
| Error | Auth failed / transfer failed | Reason-specific: revoked / not entitled to this version / network — never a generic failure on a paid good |
| Partial | Transfer interrupted | Resume control with byte offset retained, never a restart-from-zero |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | Resumable multi-GB download is a solved problem — byte-range requests and a CDN | The candidate's phrasing bundles it as a routine capability | ❌ REJECTED — two constraints in this project collide here and neither is negotiable. **First**, the surface: candidate 08 openly names a *Desktop Library Manager*, because Splice, Native Access and Kontakt all ship native apps for exactly this. A browser tab cannot reliably fetch 100 GB in the background, survive a close, install to a user's sample folder, or verify and unpack. But D-02/D-12 ratify single-surface web. So the honest position is that the web can do *adequate* delivery (byte-range, resume within a session) and cannot do what the candidate describes — and I will not invent a desktop surface to close the gap (index Q-01). **Second**, watermarking (CX-04) makes each artifact per-buyer and therefore uncacheable, which removes the CDN the "solved problem" assumes. Both facts must reach `/create-prd-architecture` rather than be discovered there. |
| DT-02 | Delivery cost is a rounding error on a digital sale — no marginal cost, that's the point | The standard intuition about digital goods, and the reason people assume digital margins are ~100% | ❌ REJECTED — this domain has the **worst storage-and-egress profile on the platform**, and it is structurally unbounded. A one-time purchase of a 100 GB library buys a *perpetual* obligation: store it forever, and serve it again on every machine change, for decades (14.08.05 makes this explicit — a vendor exits and we keep storing their catalog for buyers who paid once). Egress is per-fetch, unbounded, and — thanks to CX-04 — uncacheable for watermarked content. Meanwhile the revenue was a single transaction with a marketplace cut. Sample libraries are the pathological case: largest files, most re-downloads, lowest prices. Nobody has costed this (index Q-03) and it is the kind of fact that decides whether a domain is viable, not merely how it is built. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | Downloads are authorised per request via short-lived buyer-scoped URLs, never static links | Per CX-01. A shareable static link makes the entitlement decorative and revocation unenforceable. |
| D-02 | Unpacked size is shown before a transfer starts, not just download size | A 40 GB download that unpacks to 90 GB fails on the buyer's disk after hours. Pre-empting it is trivial; discovering it late is not. |
| D-03 | The web surface delivers *adequate* transfer; the candidate's desktop-manager scope is not built by assumption | Per DT-01. The gap is raised as index Q-01 rather than closed by inventing a surface D-02/D-12 deny. |
