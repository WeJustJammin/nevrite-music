## Cross-Cut Details

### CX-01: Library ↔ Delivery

**Relationship**: Delivery is never open. Each download is authorised against a live entitlement
check (state `active`, version permitted, waiver captured per 14.09.01) and served via a
short-lived, buyer-scoped URL. Revocation (14.09.03) must therefore take effect on the *next*
request, not merely on new purchases.

**Role scoping**:
- **Musician**: re-downloads on a new laptop years later; the check must still pass for a perpetual entitlement, including after vendor exit (14.08.05).
- **Producer**: downloads the same product to many machines routinely — repeated fetches must not look like abuse.
- **Operator**: fetches per room; may be behind a restrictive studio network.
- **Fan**: the shared path — a fan fetching an album bought on an artist page (domain 20) traverses this same gate.

**Synthesis questions answered**:
1. **Shared state conflict**: Entitlement is owned by 14.02.01; delivery reads only, never writes.
2. **Trigger chain**: Request → entitlement check → waiver check → URL mint → transfer. Sync. Any check failing means no URL, not a partial transfer.
3. **Permission intersection**: Yes, and it is the point — 14.02's entitlement state directly gates bytes. A revoked entitlement's in-flight download is an unresolved case (see 14.09.03).
4. **Notification fan-out**: None on normal download. A download from an unexpected location may be a security signal, but treating a touring musician as a threat is the wrong default.
5. **State transition conflict**: Revocation racing an in-flight multi-GB transfer that has hours to run. Killing it mid-stream vs letting it complete is a real decision — see 14.09.03.

### CX-02: Versioning ↔ Delivery

**Relationship**: Delivery serves an artifact identified by (product, version, platform). The
default resolution is "latest the buyer is entitled to"; explicit version selection reaches the
archive. Per 14.01.02 DT-01 the compatibility matrix is versioned too, so the artifact and its
requirements move together.

**Role scoping**:
- **Musician**: wants latest; never thinks about versions until something breaks.
- **Producer**: the persona that needs the archive — reopening an old project demands the build it was mixed with.
- **Operator**: rooms are pinned to known-good builds and updated deliberately, on a maintenance window, not on a vendor's release schedule.
- **Fan**: not affected — no versions in a music purchase.

**Synthesis questions answered**:
1. **Shared state conflict**: Versions are vendor-published and immutable once released; delivery reads.
2. **Trigger chain**: Version selection → artifact resolution → transfer. A `superseded` or `defective` withdrawn version (14.08.04 rollback) still serves prior holders, which means "withdrawn" ≠ "deleted"; a `malicious` withdrawal stops new and in-flight grants but cannot remove an installed copy.
3. **Permission intersection**: Entitlement version range gates which versions resolve (CX-03).
4. **Notification fan-out**: New version publishes → update-available notification to entitled holders. Under a staged rollout (14.08.04) this fans out progressively, not at once.
5. **State transition conflict**: A vendor rolling back a version while a buyer is downloading branches on 14.08.04 D-04's required `withdrawal_reason`: `superseded` or `defective` completes; `malicious` stops the transfer within 30 s and flags the partial unsafe.

### CX-03: Versioning ↔ Library

**Relationship**: The entitlement carries the version range it covers. The library renders it
("you own v1.x — v2 is a paid upgrade") and the archive obeys it. This is the join that makes
14.07.05 (upgrades/crossgrades) possible at all.

**Role scoping**:
- **Musician**: discovers at upgrade time that "lifetime updates" was or wasn't part of the deal — so it must be visible at purchase, not at upgrade.
- **Producer**: as a vendor, chooses the update policy; as a buyer, resents discovering it late.
- **Operator**: needs to know before standardising four rooms on a product.
- **Fan**: not affected.

**Synthesis questions answered**:
1. **Shared state conflict**: The version range is an entitlement property (14.02.01); versioning reads it.
2. **Trigger chain**: New major version → entitled holders get an update, unentitled get an upgrade offer (14.07.05). Async.
3. **Permission intersection**: Direct — the range *is* the permission.
4. **Notification fan-out**: Both populations are notified, with materially different messages. Sending the wrong one is a trust event.
5. **State transition conflict**: A vendor changing the update policy mid-entitlement cannot reach sold entitlements (same principle as 14.02 CX-02).

### CX-04: Delivery ↔ Watermarking

**Relationship**: The watermark is buyer-specific and applied in the delivery path, which means
the artifact is unique per buyer. This collides directly with the caching and CDN strategy that a
multi-GB catalog otherwise demands — you cannot cache what is unique.

**Role scoping**:
- **Musician**: unaware, except that they must be *told* it happens (privacy, and deterrence only works if known).
- **Producer**: as vendor, chooses whether to watermark; as buyer, may object to a personalised file.
- **Operator**: not affected.
- **Fan**: not affected — see 14.03.05 Role Lens.

**Synthesis questions answered**:
1. **Shared state conflict**: The watermark map (buyer ↔ mark) is forensic evidence; it belongs to the platform, not the vendor, or a vendor could deanonymise their buyers.
2. **Trigger chain**: Download request → mark generation → stamp → serve. If stamping fails: serve unmarked, or fail the download? An unmarked file silently defeats the mechanism.
3. **Permission intersection**: Vendor enables it; vendor must **not** read the map (see conflict above).
4. **Notification fan-out**: None per download.
5. **State transition conflict**: Cache invalidation is the whole problem — per-buyer artifacts are uncacheable at the edge, which is a direct hit on the Cloudflare-shaped architecture the constraints lock in. Routed to `/create-prd-architecture`.

### CX-05: Library ↔ Asset Library

**Relationship**: An entitlement to a *pack* grants entitlement to its *contents*. The library
indexes purchases; the asset library indexes sounds. One purchase fans out into hundreds of
addressable, taggable, individually-usable assets — and each asset carries its pack's terms
(14.02.05), which is how a loop's licence reaches a track.

**Role scoping**:
- **Musician**: thinks in sounds, not purchases. "Which kick did I use" is the real question.
- **Producer**: heaviest user; a career of packs is tens of thousands of assets.
- **Operator**: not applicable — a studio doesn't curate a personal loop library.
- **Fan**: not applicable.

**Synthesis questions answered**:
1. **Shared state conflict**: Entitlement is the parent; assets derive. Buyer-added tags are buyer-owned and must survive a pack revision (CX-06).
2. **Trigger chain**: Purchase → asset expansion, async (a 5,000-file pack is not expanded synchronously at checkout).
3. **Permission intersection**: Asset access derives from pack entitlement. A refund (14.09) must remove assets — including ones already tagged and used, which is where it hurts.
4. **Notification fan-out**: None on expansion.
5. **State transition conflict**: See CX-06 — pack revision vs assets already in use.

### CX-06: Asset Library ↔ Versioning

**Relationship**: Medium confidence. Content packs get revised (a loop retuned, a bad file
replaced, a sample pulled for a rights issue). An asset the buyer has already used in a project
must not disappear or silently change underneath them.

**Role scoping**: `[PENDING — /ideate-discover Step 5 deepening]`

**Synthesis questions**: Deferred — Medium confidence. Key open case: a sample pulled for a
**rights** reason is exactly the one that must be withdrawn, and exactly the one already sitting
in someone's released record. That collides with 14.02.05 Q-02 and is unresolved.

## Rejected Pairs

| # | Source | Target | Reason for Rejection |
|---|--------|--------|---------------------|
| R-01 | 14.03.05 Watermarking | 14.03.03 Library | The library shows what you own; the watermark is a property of a delivered *file*, not of an entitlement. Re-downloading may legitimately produce a differently-marked file. Modelling the mark on the library entry would imply one canonical marked artifact per buyer, which is false. |
| R-02 | 14.03.05 Watermarking | 14.03.02 Versioning | Marks are per-buyer, versions are per-vendor-release; they vary on independent axes and never read each other. The delivery path (CX-04) is where both are resolved — coupling them directly would invent a "watermarked version" entity that has no owner and no lifecycle. |
| R-03 | 14.03.04 Asset Library | 14.03.01 Delivery | Tempting, but assets are fetched through the same authorised delivery gate as anything else (CX-01); the asset library is an *index*, not a transfer mechanism. A direct edge would duplicate CX-01 while implying assets bypass the entitlement check — the exact hole CX-01 exists to close. |
