# Feature: Per-Buyer Forensic Watermarking

> **Number**: 14.03.05
> **Parent**: [14.03 Delivery, Versioning & Library](./14.03-delivery-versioning-library-index.md)
> **Status**: [SURFACE]
> **Last updated**: 2026-07-16

## Overview

Stamping a buyer-unique, inaudible mark into audio content as it is delivered, so that a pack
leaked to a warez forum can be traced to the account that bought it. For content with no serial
and no activation check — which is most of this store's realistic inventory (14.02.04 DT-01) —
this is not one anti-piracy tool among several; it is **the only one that exists**.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Read-only · Config as vendor | Must be **told** their download is personally marked — both because deterrence only works when known, and because a personalised file is a privacy fact they are entitled to. As a vendor of their own pack, chooses whether to enable it. |
| Producer | Config as vendor · Read-only as buyer | As vendor, the persona with most to lose from a leaked pack and most likely to want marking. As buyer, the persona most likely to object — a file that identifies them, delivered into a client's session, is a legitimate concern. Both in one human again. |
| Operator | None | Not applicable. Studios buy software (no audio payload to mark) and do not distribute content. |
| Fan | None | Not on the fan surface — but see Q-02: a fan buying an album (domain 20) traverses the same delivery layer, and whether *their* music gets marked is an unresolved question with a very different privacy profile. |

## Behavior

Where a vendor enables it, the delivery path (CX-04) stamps a buyer-unique mark into the audio
before serving. The mark must survive normal creative use — format conversion, time-stretching,
pitch-shifting, layering, light processing — or it is theatre. The map from mark to buyer is
forensic evidence held by the **platform**, not the vendor (CX-04): a vendor able to read the map
could deanonymise every one of their buyers.

Marking makes each delivered artifact unique, which is why it collides head-on with edge caching
(CX-04) and, through it, with the Cloudflare-shaped architecture the constraints lock in.

### Happy Path

1. Vendor enables watermarking on an audio product at submission (14.08.01).
2. Buyer purchases; buyer is told at download that the file is personally marked.
3. Delivery generates a buyer-unique mark and stamps it during transfer (CX-04) — **the only write delivery performs**, since per `14.03.01` D-12 embedded tempo/key/loop metadata is already in the stored master, written at ingest by `14.08.03`. The grant records the seed (`14.03.01` DT-03) and the **per-grant SHA-256** of the stamped bytes, which is what the buyer's client verifies against; the master's hash stays published as the build's identity.
4. Mark ↔ buyer mapping is recorded as platform-held forensic evidence.
5. The pack later appears on a warez site; the platform extracts the mark and identifies the source account.
6. Enforcement runs through domain 24 as an adjudicated case — not a unilateral kill (14.02.04 D-01).

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Stamping fails mid-delivery | ~~Serve unmarked or fail the download?~~ **Resolved — this file's D-03**: *"A stamping failure serves the file unmarked and logs, rather than blocking the download"* — never block a paying customer for an anti-piracy convenience. Per `14.03.01` E-27 the grant must **also record that this artifact is unmarked**, so a file later found leaked is never traced to the seed it *would* have carried. **And per `14.03.01` D-12 a third thing follows**: the served bytes are now the master's bytes, so the grant's per-grant hash is stale and completion must verify against the **master** hash instead. Otherwise a correct fallback fails verification and E-29 fires on a perfect file. | Nothing. Incident logged. |
| Buyer legitimately uses the loop in a released track | **The mark ships inside a commercial record.** This is the normal, intended use — the mark is now in a master on Spotify | Nothing — but it must be inaudible at mastering levels, or the feature has damaged the product it was protecting |
| Mark survives time-stretch/pitch-shift? | If it doesn't, it is defeated by the most routine operation in sample use | Unvalidated — see Q-01 |
| Leaked pack traced to a buyer whose account was compromised | Forensics identify an account, not a person. Treating the mark as proof punishes a victim. | Evidence, not verdict — adjudicated in 24 |
| Buyer objects to a personalised file | Legitimate objection with no clean answer: no mark, no purchase | Disclosed before purchase, not discovered at download |
| Per-buyer artifact vs CDN caching (CX-04) | Every download is a unique object; the edge cache is useless for the largest files in the catalog | Architecture consequence — routed to `/create-prd-architecture` |
| Vendor requests the mark map to chase a leak themselves | Refused — a vendor with the map can deanonymise their buyer base | Vendor gets a case outcome, never the map |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | Watermarking belongs with DRM and anti-piracy — candidate 22 bundles them, so they are one concern | The sweep's candidate 22: "DRM, Anti-Piracy, Watermarking & Serial Blacklisting" | ❌ REJECTED — the bundle conflates a **preventive access control** with a **forensic trace**, and they have nothing in common but a motive. DRM stops use; a watermark does not stop anything — it identifies a leak after the fact. They fire at different moments (activation vs delivery), are owned by different features, apply to disjoint inventory (serials to software, marks to audio), and fail in opposite directions: DRM's failure mode is blocking a legitimate user, watermarking's is embedding a tracker in a commercial master. Splitting candidate 22 (sub-domain D-03) is what let each be modelled honestly. The sharper consequence: per 14.02.04 DT-01, blacklisting is near-useless on this catalog because there is nothing to blacklist — **so this feature carries the entire enforcement load for the store's realistic inventory**, and it inherits the priority the candidate implied for DRM. |
| DT-02 | A watermark's cost is compute at download time | The engineering framing — it's a signal-processing step | ❌ REJECTED — the real costs are architectural and ethical, and both are larger than the compute. **Architecturally**: per-buyer uniqueness means the artifact cannot be cached at the edge (CX-04). That is a direct hit on the locked Cloudflare Pages/Workers constraint, applied to the largest files on the platform (40–100 GB libraries), and it compounds 14.03.01 DT-02's uncosted egress problem — the one content type most needing a CDN is the one that cannot use it. **Ethically**: the mark ships inside the buyer's commercial release. That is the intended, licensed use — so WeJammin is embedding an identifier into a musician's master, distributed to DSPs worldwide, forever. The buyer is not the adversary here; they paid, and the mark rides along regardless. That deserves an explicit disclosure and an owner's decision (Q-02), not an engineering default buried in a delivery pipeline. |

## Cross-Cut Notes

- Touches **14.03.01 Delivery** ([path](./14.03.01-download-delivery-resumable-transfer.md)) — stamped in the delivery path; kills edge caching. See `14.03-delivery-versioning-library-cx.md#CX-04`. **Per that file's D-12, marking is now the sole delivery-time write, and it is the sole reason a second hash exists**: enabling it on a product moves that product from a one-hash contract (published master hash, verified directly, hand-verifiable) to a two-hash one (master published, per-grant verified). It also owns the split in `14.03.01` E-29 — a per-grant mismatch is a stamping or transfer fault on one delivery and must **never** quarantine the vendor's build.
- Touches **14.03.03 Library** ([path](./14.03.03-licence-portal-purchased-library.md)) — **null relationship** (`#R-01`): the mark is a property of a delivered file, not of an entitlement.
- Touches **14.03.02 Versioning** ([path](./14.03.02-versioning-updates-legacy-archive.md)) — **null relationship** (`#R-02`): marks and versions vary on independent axes.
- Touches **14.02.04 Blacklisting** ([path](../14.02-licensing-activation-entitlement/14.02.04-serial-blacklisting-anti-piracy.md)) — per DT-01, this is the enforcement mechanism that works where blacklisting cannot.
- Touches **24 Trust, Safety & Disputes** ([path](../../24-trust-safety-disputes/)) — a traced leak is an adjudicated case; the mark is evidence, never a verdict.
- Touches **20 Fanbase & Direct-to-Fan** ([path](../../20-fanbase-direct-to-fan/)) — shared delivery layer; whether fan purchases are marked is Q-02.
- Routed to `/create-prd-architecture`: per-buyer artifacts vs edge caching. Routed to `/create-prd-security`: the mark map is high-sensitivity forensic data.

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | The mark ↔ buyer map is platform-held; vendors receive case outcomes, never the map | Per CX-04. A vendor with the map can deanonymise their entire buyer base — an unacceptable surveillance capability handed to a user. |
| D-02 | Watermarking is disclosed to the buyer before purchase and again at download | Per DT-02. A personally identifiable file that ends up in their commercial master is not something to discover afterwards; deterrence also requires that it be known. |
| D-03 | A stamping failure serves the file unmarked and logs, rather than blocking the download | Recommendation per the edge-case table: never block a paying customer for an anti-piracy convenience. Flagged for confirmation. |

## Open Questions

| # | Question | Owner | Deferred To |
|---|----------|-------|-------------|
| Q-01 | Does the mark survive the operations sample use *consists of* — time-stretch, pitch-shift, layering, bitcrushing, resampling? If not, the feature is theatre against anyone who chops a loop, i.e. everyone. This is a technology-feasibility question that gates the whole feature. | Agent | `/create-prd-architecture` |
| Q-02 | **[OWNER]** Confirm that embedding a buyer-identifying mark into audio destined for the buyer's commercial release is acceptable (DT-02). And does it extend to fan music purchases via domain 20, where the privacy profile is entirely different? DT-02 states the requirement directly — this *"deserves an explicit disclosure and an owner's decision (Q-02), not an engineering default buried in a delivery pipeline"* — so it is routed to the owner, not to `/create-prd-security`, which can design the mark-map controls but cannot consent on a musician's behalf to an identifier riding into their master. | User | `/create-prd` |
| Q-03 | **[OWNER]** Vendor-enabled or platform-default? Vendor choice fragments the catalog; a platform default marks everything, including products where it is pointless (MIDI, presets, code). **Now also a cost-structure decision, not only a catalog-consistency one**: per `14.03.01` DT-07/DT-08 and its Q-05, watermarking forecloses the CDN, P2P *and* delta patching — the three standard defences against the egress cost DT-02 flags as possibly domain-fatal — which argues for per-product opt-in (cheap on a £15 loop pack, plausibly ruinous on a 100 GB library shipping quarterly updates). Decide with `14.03.01` Q-05, which is routed here. **Third axis added 2026-07-30 by `14.03.01` D-12** (owner ratification of run-3 finding `14-digital-goods-marketplace#001`), which deliberately **did not answer this question** and explicitly left it open: the integrity contract now depends on the answer. Embedded metadata moved to ingest, so the mark is the **only** delivery-time write, and that splits the catalog cleanly in two. An **unmarked** product is delivered byte-identical to its stored master, so its single published SHA-256 is simply correct — and it is hand-verifiable, exactly, by the air-gapped Operator (`14.03.01` D-09). A **marked** product needs the two-hash treatment: master hash published, per-grant hash of the served bytes verified by the client, both shown. So per-product opt-in is now also the decision about **which products keep the simple, corroborable one-hash contract and which take on the stream-hash-and-trailer machinery**. This is weight on the existing question, not a new question and not a lean — the cost evidence (`14.03.01` DT-07/DT-08) and the ethical question (Q-02) are unchanged, and nothing here decides either. | User | `/create-prd` |
