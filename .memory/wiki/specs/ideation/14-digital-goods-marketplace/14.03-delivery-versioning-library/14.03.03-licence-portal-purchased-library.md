# Feature: Licence Portal & Purchased Library

> **Number**: 14.03.03
> **Parent**: [14.03 Delivery, Versioning & Library](./14.03-delivery-versioning-library-index.md)
> **Status**: [SURFACE]
> **Last updated**: 2026-07-16

## Overview

The buyer's permanent answer to "what do I own, and how do I get it again?" — every entitlement
(14.02.01) rendered as something a musician can act on: download it, see which machines hold
seats, check what the licence lets them do, fetch an old version. It is the authorisation gate
for all delivery (CX-01) and the single page a buyer returns to years after the purchase, when
the receipt is long gone and a new laptop needs everything reinstalled.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Full | Their whole purchase history in one place — the consolidation promise (D-18) applied to digital goods. Reinstalls from here after a machine change. Sees seats, versions, terms. As a vendor, their *sales* are a different view (14.08), not this one. |
| Producer | Full | Volume user with hundreds of entitlements across years. Needs to find "that Rhodes library I bought in 2019" — which means the library must be searchable, not a chronological list. Also the persona that reads terms (14.02.05) from here before using a pack on a client record. |
| Operator | Full | **Blocked on 14.02 Q-03.** A studio's library should belong to the studio and be visible to whoever staffs the room tonight. Today, entitlements bind to a person, so the studio's library lives in a departed engineer's account — the exact "proof evaporates when the person moves on" failure the project exists to fix. |
| Fan | Read-only | The shared machinery, deliberately unrecognisable. A fan who bought an album on an artist page (domain 20) sees "my purchases" — a list of music with download links. No seats, no versions, no terms, no store. Per personas.md they will not tolerate professional-tool complexity, so the fan view is a different product wearing the same plumbing. |

## Behavior

The library is a presentation of entitlements, not a second store of truth. Each row renders:
product, monetisation model, entitlement state, seat usage (14.02.02), version entitlement
(CX-03), bound terms (14.02.05), and the download control. Every download authorises through here
(CX-01).

Purchases fan out: buying a pack creates one library row and *hundreds* of assets in the asset
library (CX-05). The two are different objects for different questions — "what did I buy" vs
"which kick did I use".

### Happy Path

1. Buyer opens their library; entitlements load, most-recent first, searchable.
2. Buyer searches for a product bought years ago and finds it.
3. Row shows: active, 1 of 2 seats used, entitled to v1.x, terms "royalty-free, commercial OK".
4. Buyer downloads to a new machine (14.03.01); a seat is spent on activation (14.02.02).
5. Buyer opens Legacy Versions and fetches the build their old project needs (14.03.02).

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Fetch fails transiently | **Must never render "you own nothing"** — a paid buyer seeing an empty library is a panic event and a support ticket | Cached list + retry, explicitly marked stale |
| Entitlement revoked (14.09.03) | Row persists with a revoked state, a reason, and an appeal route — the row does not vanish | "Revoked — refunded on <date>" with appeal link |
| Vendor exited (14.08.05) | Row persists; downloads work; nothing is for sale | "No longer sold — your licence and downloads are unaffected" |
| Hundreds of entitlements | A chronological list is unusable at Producer scale | Search + filter by type, vendor, state |
| Buyer bought the same product twice | Duplicate purchase should have been blocked at checkout (14.02.01) | "You already own this" — resolved before it reaches the library |
| GDPR erasure requested (14.02 Q-02) | Erasing the account erases the library, destroying both the buyer's rights proof and the vendor's sale record | `[PENDING — /create-prd-security]` — genuinely unresolved |
| Studio purchase in an engineer's personal account, engineer leaves | The Operator's blocker; no mechanism today | `[PENDING — /create-prd-architecture]` — 14.02 Q-03 |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Loading | Library fetch | Skeleton rows |
| Empty | Nothing purchased | Empty state with store CTA |
| Populated | Entitlements exist | Searchable rows with state, seats, versions, terms, download |
| Error | Fetch failed | Cached list marked stale + retry — never an empty library |
| Partial | Some rows externally managed (14.02.03) | Bridged rows marked "managed in iLok — refunds and transfers may not apply" |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | The library is an account page — order history with download buttons | The candidate's framing ("Customer Licence Portal"), and how most stores build it | ❌ REJECTED — order history is *transactional* and this is *durational*. An order is a fact about a past moment, closed forever; an entitlement is a live relationship with state that changes for years afterwards without the buyer doing anything — seats fill and free, versions accrue, a vendor exits, a licence is revoked, terms govern a release made in 2029. The tell is the time horizon: nobody opens an order history from 2019, and *everybody* reinstalls a 2019 plugin on a new laptop. Building this as order history produces a page that is correct on day one and useless on day 1,000, which is precisely when this domain's promise (perpetual availability) is actually tested. |
| DT-02 | This library is domain 14's | The domain index's own framing — 14 owns delivery, 20 depends on it | ⏳ DEFERRED — escalated to sub-domain Q-02, and the evidence has grown rather than shrunk during classification. The domain index already concedes 20 (fan music purchases) reuses this machinery. But the same shape recurs across the map: Education (06) delivers lesson materials to enrolled students; Services (05) delivers finished work to a client who paid; Projects (07) delivers stems to collaborators. All four are "an entitled party fetches a versioned file, permanently, gated on a right they hold". One dependant is a seam; **four dependants is a cross-cut wearing a domain costume**. I am not overturning a ratified framing (D-16) on my own authority — but the Node Classification Gate says a mechanism serving many domains is a cross-cut, and by its own test this qualifies. Flagged loudly for the owner rather than quietly reclassified. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | The library is a presentation of entitlements, never a second source of truth | Two stores of "what you own" will diverge, and the divergence surfaces as a buyer being told they don't own something they paid for. |
| D-02 | The library is searchable and filterable from the start, not a chronological list | Per the Producer lens — hundreds of entitlements across years is the normal case, not the extreme one. |
| D-03 | A transient failure renders a stale cached list, never an empty one | Per DT-01's time horizon: this page is load-bearing for people reinstalling a career's worth of tools. "You own nothing" is never an acceptable transient state. |
