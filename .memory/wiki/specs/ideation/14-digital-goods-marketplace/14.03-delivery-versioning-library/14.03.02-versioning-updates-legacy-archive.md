# Feature: Versioning, Updates & Legacy Archive

> **Number**: 14.03.02
> **Parent**: [14.03 Delivery, Versioning & Library](./14.03-delivery-versioning-library-index.md)
> **Status**: [PARTIAL]
> **Last updated**: 2026-07-17

## Overview

Which build of a product a buyer gets, and the permanent availability of every build they are
entitled to. In most software retail "latest" is the only answer anyone needs. In music software
it is frequently the **wrong** answer: a mix from 2021 must be reopened with the 2021 plugin or it
does not sound the same, and a room mid-project does not update because a vendor shipped on Tuesday.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Read-only as buyer · Config as vendor | Wants latest and rarely thinks about versions — until a recall of an old track breaks. As a vendor of a pack, publishes revisions and must be told a revision is not a free action for people already using it. |
| Producer | Full | **The persona that makes the archive load-bearing.** Reopens a client's 2021 mix and needs the exact build it was mixed with; pins versions to projects (domain 07) rather than to an account. Personas.md is explicit that their work lives in a DAW where a plugin version *is* the sound. |
| Operator | Full | Rooms are pinned to known-good builds and updated on a maintenance window, deliberately. An auto-update that lands mid-session is an outage. Needs to hold four rooms on one version and test a fifth. |
| Fan | None | Not on the fan surface. A music purchase (domain 20) has no versions — an album is not rebuilt, and the shared delivery layer carries no version semantics for them. |

## Behavior

A product has a listing (14.01.01) that outlives its versions. Each version is an immutable
published artifact with its **own** compatibility matrix (14.01.02 DT-01) — a v3 that drops macOS
12 is a matrix change, not just a build. The entitlement (14.02.01) defines which version range
the buyer may fetch (CX-03), which is what makes paid upgrades (14.07.05) expressible.

The **legacy archive** is the guarantee that any version a buyer was ever entitled to remains
fetchable. It is not a nice-to-have: it is the mitigation for a vendor's update breaking a
buyer's session, and per 14.01.02 it is also the only honest answer when a new version drops
support for a buyer's OS.

Updates are *offered*, never forced. Withdrawal of a bad version (14.08.04 rollback) stops new
downloads but must not delete the artifact from under buyers who already have it.

### Happy Path

1. Vendor publishes a new version with release notes and a confirmed/amended matrix.
2. System notifies entitled holders that an update is available — offered, not applied.
3. Buyer chooses to update; delivery serves the new artifact (CX-02).
4. Buyer discovers the new build changed a sound; opens Legacy Versions and re-fetches the previous build.
5. Both versions remain permanently available to that buyer.

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| v3 breaks a mix that was built on v2 | Legacy archive is the escape hatch — the entire reason it exists | "Legacy versions" list with dates; v2 fetchable forever |
| v3 drops the buyer's OS (14.01.02) | Buyer is entitled to a product they cannot run; last-supported build must remain | "v3 requires macOS 14. Your last supported build is v2.4." |
| Vendor deletes a version to hide a defect | Withdrawal ≠ deletion (CX-02) — buyers keep what they had | Vendor cannot un-ship a build someone owns |
| Vendor exits (14.08.05) | Every archived version must still serve — perpetual means perpetual | Downloads work; listing marked "no longer sold" |
| Content pack revised, a loop removed for a rights issue | **P-10a (D-04):** a rights takedown is not a revision and does not travel this path. Further delivery of the affected asset stops immediately, but the holder's entitlement row **persists** with its date and reason and never silently disappears — the holder is notified of the rights event as such. Assets already used in released records are unaffected in the record; what stops is onward supply. See `14.04.01` D-08/D-09 and `14.09.03` D-02/D-04. | "This loop was withdrawn following a rights claim on 14 Nov. Your purchase record stays; the file is no longer delivered." |
| Buyer entitled to v1.x only; v2 published | Not an update; an upgrade offer (14.07.05) | "v2 is a paid upgrade — you own v1.4" |
| A pinned project version vs a machine-wide install | A DAW loads one plugin binary; per-project pinning is the DAW's business, not ours | We can serve the build; we cannot make a DAW load two versions — see Q-02 |
| **Permission**: entitlement revoked/refunded, buyer opens Legacy Versions | The archive obeys the live entitlement (CX-03) — a revoked entitlement fetches nothing, legacy included; withdrawal-by-vendor (D-02) and revocation-of-buyer are different events with opposite outcomes | "This licence is no longer active." Legacy list is not a bypass around 14.09.03 |
| **Concurrency**: vendor rolls back v3 while a buyer is mid-download of v3 | The in-flight transfer completes — the artifact is valid, only the *recommendation* changed (CX-02 Q5). v3 becomes Withdrawn for new fetches but the buyer keeps what landed | Download finishes; v3 later appears under "Withdrawn" in their legacy list |
| **Abuse**: buyer scripts a bulk pull of every archived build to mirror the catalog | Legacy fetches are entitlement-scoped and rate-limited like any delivery (CX-01); mass sequential archive pulls are a delivery-abuse signal, not a versioning concern | `[PENDING — /write-be-spec: threshold owned by 14.03.01 delivery + 14.09 abuse]` |
| **Empty by design**: single-version product opened via a stale "Legacy Versions" deep link | No archive exists yet — the UI is absent, not an error; the link resolves to the current build | Current version only; no legacy affordance rendered |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Loading | Version list fetch | Skeleton |
| Empty | Product has one version | No version UI at all — absent, not empty |
| Populated | Multiple versions exist | Current + release notes + Legacy Versions list with dates and matrices |
| Error | Fetch failed | Retry; current version still downloadable from cache of the library row |
| Partial | Entitled to a subset of versions | Newer versions shown as upgrade offers, not as downloads |
| Withdrawn | Vendor rolled back a bad build | Not offered to new downloaders; still fetchable by anyone who had it |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | The legacy archive is a courtesy — a nice-to-have for nostalgic users, cuttable under scope pressure | The candidate lists it last ("Download Delivery, Versioning, Updates & Legacy Archive"), which reads as an afterthought | ❌ REJECTED — it is **load-bearing infrastructure that three other features silently depend on**, and cutting it breaks all of them. (1) 14.01.02 DT-01: the matrix is per-version, so when v3 drops an OS the buyer's *only* remedy is fetching v2 — without the archive we sold them something they cannot run and offer no recourse. (2) 14.08.04: a staged rollout's rollback is meaningless if the previous build isn't retrievable. (3) The Producer persona's defining workflow — reopening old sessions — requires it outright. A plugin version is not a bug-fix level in this industry; **it is the sound**. Cutting the archive doesn't save storage (14.03.01 DT-02: we already store forever), it just removes the escape hatch from a domain full of one-way doors. |
| DT-02 | Buyers want updates; the job is to deliver them promptly | Standard software-retail reasoning; how an app store thinks | ❌ REJECTED — this user base **actively fears updates**, and the product should reflect that rather than fight it. A Producer mid-album and an Operator mid-session have identical incentives: change nothing that works. Auto-update is not a feature here, it is a hazard — the well-known industry pathology is the plugin that updates itself and silently alters a mix in progress. The corollary nobody asks for: the **update notification must state what changed in terms a musician can act on** — "changed the filter curve" is a reason to stay on v2; "fixed a crash on Apple Silicon" is a reason to move. A generic "update available" badge forces a professional to gamble on their own session, so they rationally ignore it forever, and the notification becomes noise. This is why release notes are a required publish field (14.08.01), not vendor courtesy. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | Every version a buyer was entitled to remains permanently fetchable | Per DT-01. Three other features depend on it, and it is the only recourse when a new build drops OS support or changes a sound. |
| D-02 | Updates are offered, never forced; withdrawal is not deletion | Per DT-02. This user base's rational default is "change nothing mid-project", and a vendor must not be able to un-ship a build someone owns. |
| D-03 | Release notes describing *what changed musically* are a required publish field | Per DT-02 — a generic "update available" makes a professional gamble on their session, so they ignore it and the channel dies. |
| D-04 | **P-10a / P-10b:** an **ordinary revision** appends and notifies while every prior entitled version stays fetchable; a **rights takedown** is a distinct legal event that stops onward delivery but **preserves the holder record with its date and reason** | Two paths, never one. P-10b confirms D-01/D-02 rather than choosing among them: replace-in-place contradicts permanent fetchability and "an asset in use must not vanish", and repurchase-per-revision contradicts D-02's "updates are offered" plus the required displayed version range. P-10a confirms the takedown behaviour already written in halves at `14.09.03` D-02/D-04 and `14.04.01` D-08/D-09, whose own section heading states it directly: *"Removal is not deletion, and a rights takedown is not a revision."* Treating a takedown as a revision would reuse a path that does not exist singly; removing the holder record would contradict seven locked decisions and leave put-back after an unopposed counter-notice undefined. Retention duration/cost and preset-pack scope are Q-04. |
| D-05 | **A metadata correction is an ordinary revision, and it changes the master's published SHA-256 — so it appends a version and never edits a build in place** | **New, per `14.03.01` D-12** (owner ratification, 2026-07-30). Embedded tempo/key/loop metadata now lives **in the file**, written at ingest by `14.08.03` D-04. That makes "fix the wrong key on loop 214" a byte-level change to the stored master, not a database edit — new bytes, new hash. D-04's machinery already answers it and needs no new path: this is an **ordinary revision** (P-10b), so it **appends**. The corrected pack publishes as a new version with its own hash; every prior entitled version stays fetchable (D-01); existing holders are notified and offered the fix but never forced onto it (D-02); no held asset is removed (14.04.01 D-09). **What this forbids is the tempting shortcut** — silently re-writing the published build in place. That breaks three things at once: a buyer who recorded the hash finds it no longer matches, `14.03.01` E-19 reads a *correct* older copy as a stored-artifact defect and quarantines a good build, and the air-gapped Operator's hand-verification (`14.03.01` D-09) fails for a reason nobody can explain to them. The append rule is precisely what keeps a published hash immutable for the life of the version it names. Release notes apply as to any revision (D-03) — "corrected the key on 12 loops" is exactly the musically-actionable note D-03 demands, and it is a reason to *stay* on the old build if a session already committed to the wrong label. Reversibility: **Medium** — the alternative (metadata as mutable out-of-band sidecar data) is a real design, but it contradicts 14.04.01 DT-03's entire reason for embedding. |
