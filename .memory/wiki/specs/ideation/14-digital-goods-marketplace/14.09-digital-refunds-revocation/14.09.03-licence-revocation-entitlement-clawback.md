# Feature: Licence Revocation & Entitlement Clawback

> **Number**: 14.09.03
> **Parent**: [14.09 Digital Refunds, Withdrawal & Revocation](./14.09-digital-refunds-revocation-index.md)
> **Status**: [PARTIAL]
> **Last updated**: 2026-07-17

## Overview

Taking back what cannot be taken back. When a refund is granted (CX-02), a used licence transfers
(14.06.02), or hardware is returned with its bundled software (14.06.03), the entitlement must
leave the holder — but the *files* are on their disk, the activation may be cached on a machine
that never comes online again, and under the platform's fail-open posture (14.02.02 D-01) nothing
stops them working. This feature is an honest attempt at recovery, not a guarantee of it.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Read-only | Sees their library row go to revoked, with a reason and — if they dispute it — an appeal route. They never *do* anything here; it is done to them, which is exactly why the reason must be legible. |
| Producer | Read-only | Same. As a vendor, their sale reversing is a payouts event (14.09.02), not a revocation they control. |
| Operator | Read-only | A clawback landing on a room mid-session is the same blast radius as a blacklisting (14.02.04) — and here it can arrive from something as mundane as a refunded duplicate purchase. |
| Fan | None | Not on the fan surface. A fan music purchase (domain 20) has access to remove, not an entitlement with seats and machines to reach. |

## Behavior

Revocation sets an entitlement's state to revoked, which delivery reads (14.03 CX-01) — the
*next* download fails even if the current one cannot be stopped. Activation reads it too
(14.02 CX-03) — but only if the machine ever asks again.

The mechanism is shared by three triggers with the same physics: refund (CX-02), used-licence
transfer stripping the seller (14.06.02 `#R-02` — reuses this, deliberately, rather than inventing
a second stripping path), and hardware return (14.06.03). It is **not** shared with blacklisting
(`#R-01`): identical state change, entirely different due process.

Best-effort is the honest framing. It is not a failure of design; it is the physics of the good.

### Happy Path

1. A refund is granted (14.09.02) — or a transfer settles, or hardware returns.
2. The entitlement's state is set to revoked with a reason and a trigger.
3. Delivery begins refusing new downloads immediately (14.03 CX-01).
4. The holder's library row shows revoked, with the reason and an appeal route.
5. Activated machines lose authorisation on their next check-in — whenever that is, if ever.

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Machine is offline and never checks in | The clawback never lands. Under fail-open (14.02.02 D-01) the software keeps working forever. | Nothing — and this must **not** be reported to the vendor as "revoked". See DT-01 |
| Files already downloaded to three machines | Bytes do not un-download, ever | Recovery of *access rights*, never of the goods |
| Revocation races an in-flight 60 GB download (14.03.01 D-05 / E-05) | Buyer has been refunded and is 60% through the transfer | Transfer is terminated at the next chunk boundary within **30 s**; no grace window applies because the partial fails checksum and cannot be used. This resolves Q-01. |
| Refunded pack's loop is in a released track | Revoking the entitlement does not un-release the record | `[PENDING]` — 14.02.05 Q-02; recommend revoke-future-use / preserve-past-clearance |
| Clawback fails; buyer already refunded | The two are deliberately unconditioned (14.09.02 D-03) — money went back regardless | The store absorbs it. That is what a refund on an unreturnable good *means* |
| Bridged product (14.02.03) | We cannot revoke what PACE controls | Refund policy for bridged products must differ, and be disclosed (14.02.03 Q-02) |
| Buyer's tags and usage history on refunded assets (14.03.04 Q-03) | The buyer's own annotations — tags, folder placement, usage notes — are *their* organisational work, not the vendor's good. Revocation takes the file, not the filing: the row survives (D-04) carrying the buyer's own metadata, tombstoned. Re-purchase later re-attaches to it. | The library row stays where they filed it, marked revoked; their tags and notes are intact but the asset behind them is gone. See DT-03 |
| Same entitlement revoked twice (refund races a transfer strip) | Idempotent — a second revoke on an already-revoked entitlement is a no-op, not an error. The reason/trigger of the *first* to land is authoritative; the second is recorded in history, never overwrites | Nothing new; the row already reads revoked. Internal history shows both triggers |
| Clawback lands mid-session in a studio | The Operator's worst case, triggered by a routine commercial event | See Q-02 — a grace window, as 14.02.04 Q-02 asks for blacklisting |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Loading | State check | Skeleton on the library row |
| Empty | No revocations | Absent, not empty |
| Populated | Entitlement active | Normal library row |
| Error | State check failed | Under fail-open, treated as active — an unreachable check must never read as revoked |
| Revoked | Refund, transfer, or return | Row persists with reason, date, trigger and appeal route. **The row never vanishes** (14.03.03) |
| Unreachable | Revoked centrally, machine still authorised locally | The honest state, and the common one — visible internally, never dressed up as success |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | Revocation removes the buyer's access — that's what it does | The word's plain meaning, and how candidate 21 frames it | ❌ REJECTED — **it removes their access to *future* downloads and, maybe, eventually, their activation. It removes nothing they already hold.** The files are on their disk; the authorisation may be cached on a machine that never contacts us again; and the platform's own fail-open posture (14.02.02 D-01) — chosen deliberately, to protect working musicians from stopped sessions — means an unreachable machine keeps working indefinitely. So there is a genuine, permanent state of **revoked-but-running** that is not a bug: it is the direct, accepted cost of a decision made elsewhere for good reasons. Two consequences worth being explicit about. First, the store must never report a clawback to a *vendor* as "revoked" when it is merely "marked revoked" — that is a lie with money attached. Second, this is why 14.09.02 DT-01's argument holds: since a refund cannot actually recover the goods, refund policy is a **trust decision, not a recovery decision**, and pretending otherwise leads to designing recovery machinery instead of deciding what the store stands for. |
| DT-02 | Revocation and blacklisting (14.02.04) do the same thing, so they should be one feature | The strongest merge argument in the domain — identical state transition, identical enforcement path, identical reach problem. I nearly took it. | ❌ REJECTED — **the state change is identical and the surrounding obligations are opposite.** A refund is a routine commercial event: no accusation, no fault, no defence required, and it should be quiet and instant. A blacklisting is an **allegation of abuse** against a professional, requiring adjudication (14.02.04 D-01), a stated reason, notification and appeal — because a false positive stops someone's livelihood. Merge them and you must pick one set of mechanics for both: either every refund drags an accusation's ceremony behind it (absurd, and it insults an honest buyer), or an accusation ships with a refund's silence (dangerous — a professional's tools die with no reason and no appeal). The tell is the **appeal**: appealing a refund you requested is incoherent; appealing a blacklisting is a right. Same verb, different sentence. This is why the sweep's candidate 22 was split (14.02 D-01) and why revocation moved here (index D-02) — the taxonomy that groups by *mechanism* produces exactly the wrong nodes; grouping by *obligation* produces the right ones. |
| DT-03 | Revocation should wipe the whole library row clean — the buyer no longer owns it, so it should leave as if never bought | Symmetry with the entitlement: no licence, no library presence | ❌ REJECTED — **conflates the vendor's good with the buyer's own work.** Two things live on that row: the *asset* (the vendor's, correctly withdrawn) and the buyer's *annotations* — the tags they applied, the folder they filed it in, the note that says "the kick on the Q3 record" (14.03.04 Q-03). The second is the buyer's labour, not the vendor's property, and a musician who organised 400 packs will not forgive a refund that silently gutted their filing system. So revocation takes the file, not the filing: the row persists as a tombstone (D-04) carrying the buyer's metadata, the asset behind it gone. A later re-purchase re-attaches to the same row — the organisational work was never destroyed, only detached. This is the same principle as D-04 (a vanished row is indistinguishable from a bug), applied one level down: a vanished *tag* is indistinguishable from data loss. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | Clawback is best-effort and is described as such internally and to vendors — never reported as completed recovery | Per DT-01. "Revoked-but-running" is a real, permanent, accepted state; misreporting it to a vendor is a lie with money attached. |
| D-02 | Revocation reaches **delivery** immediately even when it cannot reach the machine | Per 14.03 CX-01. The next download must fail; that is the part we can actually guarantee. |
| D-03 | Revocation and blacklisting remain separate features despite an identical state transition | Per DT-02 — grouping by mechanism produces the wrong nodes; the obligations (accusation, appeal, due process) are opposite. |
| D-04 | A revoked library row persists with reason, trigger and appeal route; it never disappears | Per 14.03.03. A vanished purchase is indistinguishable from a bug and destroys trust in the whole library. |
| D-05 | Revocation removes the asset but preserves the buyer's own annotations (tags, folder placement, notes); a re-purchase re-attaches to the same row | Per DT-03. The buyer's organisational work is their labour, not the vendor's good — wiping it is data loss, not clawback. |
| D-06 | Revocation is idempotent — a second revoke on an already-revoked entitlement is a no-op; the first trigger to land is authoritative, later ones are recorded in history only | Concurrent triggers (refund racing a transfer strip) must not error or overwrite the recorded reason. |
