# Feature: Automated Build QA (malware, code signing, pluginval/auval)

> **Number**: 14.08.02
> **Parent**: [14.08 Vendor Portal, Build Submission & QA](./14.08-vendor-portal-build-qa-index.md)
> **Status**: [SURFACE]
> **Last updated**: 2026-07-16

## Overview

Checking an executable before it reaches a buyer — malware scanning, code-signature and
notarisation verification, and plugin validation (pluginval, `auval`) against the formats the
vendor declared. A plugin is not a file the buyer opens; it is **code that runs unsandboxed inside
a professional's DAW**, with access to their machine, their client's session, and the network. The
gate exists because that fact makes an unscanned publish indefensible.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Read-only | Sees results if they ever ship a binary — most won't (14.01.01 DT-02: the realistic Musician vendor sells WAVs, which route to 14.08.03 instead). Read-only is honest: this gate is not their workflow. |
| Producer | Full | **The persona this is built for** — the only one plausibly shipping executable code. Needs pass/fail with *actionable* reasons: "your VST3 fails auval on Apple Silicon" is fixable; "rejected" is not. |
| Operator | None | No column. Studios buy tools; they do not ship binaries. Explicit absence. |
| Fan | None | Not on the fan surface. |

## Behavior

On submission of an executable (CX-01), the artifact is: scanned for malware; checked for a valid
code signature and platform notarisation (macOS Gatekeeper blocks unnotarised plugins, and the
buyer blames the store); and validated with pluginval/auval against each declared format from the
compatibility matrix (14.01.02) — which is also the natural place to cross-check the vendor's
declaration against the binary's actual formats (14.01.01 Q-01).

The gate is unconditional for code: publish is blocked on a verdict, and a *failure to scan* also
blocks (CX-01 q2). An unscanned binary must never publish.

Per CX-03, field failures from rollout (14.08.04) feed back — QA validates a binary in isolation,
and the failures that matter happen in a 200-track session at 96 kHz that QA cannot simulate.

### Happy Path

1. Vendor uploads a build (14.08.01).
2. Malware scan runs; signature and notarisation are verified.
3. pluginval/auval runs per declared format; the binary's actual formats are cross-checked against the matrix.
4. All pass → verdict recorded → publish allowed → the build enters a release channel (14.08.04).
5. Field telemetry from the rollout feeds back into QA's coverage (CX-03).

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Unsigned or unnotarised macOS build | Gatekeeper blocks it on the buyer's machine; the buyer blames us, not the vendor | Blocked at QA with the fix named — "notarise with Apple and resubmit" |
| Declared AAX but the binary has no AAX component | The matrix lies; buyers with Pro Tools buy something that won't load | Cross-check catches it (14.01.01 Q-01) |
| Scan fails to complete (timeout, 4 GB installer) | Must block, never pass | "Scan didn't finish — resubmit"; an unscanned binary never publishes |
| Malware false positive on a legitimate plugin | Heuristic scanners flag audio DSP code regularly — it does unusual things with memory and timing | Appeal route; a false positive that silently kills a vendor's release is unacceptable (Q-02) |
| Plugin passes QA, then corrupts sessions in the field | QA validated in isolation; the failure needs a real session | CX-03's feedback loop + rollback (14.08.04) — the only real answer |
| Vendor resubmits mid-scan | The later artifact must win | Superseded verdicts must not publish an old build (CX-01 q5) |
| Plugin passes QA and is malicious anyway | Scanning is not proof; a determined actor defeats signature-based detection | See DT-02 — passing QA is an implicit warranty we should be careful about (sub-domain Q-03) |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Loading | Scan in progress | "Checking your build…" with the stage (scan / signature / validation) |
| Empty | No executables submitted | Not shown — content vendors never meet this feature |
| Populated | Verdict recorded | Per-check results with actionable detail |
| Error | Scan couldn't complete | Blocked; resubmit. Failure-to-scan is not a pass |
| Partial | Some formats pass, some fail | Per-format results — VST3 passes, AAX fails; the matrix can be narrowed rather than the build fixed |
| Blocked | Any check failed | Named blocker + the exact remedy |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | QA is a quality gate — it keeps bad products out | The candidate's framing ("Build Submission & QA"), which reads as quality control | ❌ REJECTED — quality is the *smallest* thing it does, and framing it that way misses what makes it non-negotiable. This is a **safety gate on arbitrary code execution inside professionals' machines**. A plugin is not a document the buyer opens in a sandbox; it is a binary loaded into the DAW's process with full access to the filesystem, the network, and a client's unreleased session. A malicious or merely broken plugin can exfiltrate an unreleased record, corrupt a project, or crash a session with a paying client in the room. That is a different category of risk from "the product isn't very good", and it has a different consequence: **it means QA cannot be optional, cannot be vendor-waivable, and cannot fail open** — while every *other* gate in this domain (activation, 14.02.02 D-01; watermarking, 14.03.05 D-03) is deliberately fail-open to protect the working musician. This is the one place the fail-open principle inverts, and knowing *why* is what stops someone applying the domain's general posture here by analogy. |
| DT-02 | If a build passes QA, the store has done its due diligence | The natural conclusion from having a gate at all, and the reason gates feel reassuring | ❌ REJECTED — **passing QA is an implicit warranty, and it is one the platform cannot actually honour.** Signature-based malware scanning does not stop a determined actor; pluginval proves a plugin loads, not that it behaves; notarisation proves Apple saw it, not that it is safe. So a QA pass certifies "we ran some checks", while the buyer reads "WeJammin vetted this" — and that gap is the platform's liability (sub-domain Q-03), sitting right where the store's credibility is. It is worth noticing that this is the same structure as 14.08.01 DT-01's attestation problem, arriving from the code side: in both cases the platform cannot *verify*, only *record*, and the honest product is one that says exactly what it checked rather than implying a guarantee. There is also a real strategic point buried here — the domain's realistic launch inventory is content, not code (14.01.01 DT-02), which means the store can avoid this liability entirely at launch by simply not accepting executables. That is a legitimate answer to sub-domain Q-01 and it makes this feature's whole MoSCoW contingent on a decision nobody has taken yet. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | The QA gate is unconditional for executables — not vendor-waivable, and a failure to scan blocks | Per DT-01. This is the one gate in domain 14 that must fail *closed*; it guards arbitrary code execution in a professional's DAW. |
| D-02 | Verdicts state what was checked, not that the product is safe | Per DT-02 — the gap between "we ran checks" and "we vetted this" is the platform's liability, and honest copy is the cheapest mitigation. |
| D-03 | Failures are reported per-check with an actionable remedy, never as a verdict | "Rejected" generates a support ticket; "your VST3 isn't notarised" generates a fix. |
