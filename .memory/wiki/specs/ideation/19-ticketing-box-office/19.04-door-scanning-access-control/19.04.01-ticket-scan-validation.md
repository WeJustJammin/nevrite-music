# Feature: Ticket Scan & Validation

> **Number**: 19.04.01
> **Parent**: [Door Scanning & Access Control](./19.04-door-scanning-access-control-index.md)
> **Status**: [DEEP]
> **Last updated**: 2026-07-23

## Overview

Point a device at a barcode; get an unambiguous accept or refuse in under a second, in the dark, with a queue behind you and someone's hand shaking. This is the platform's only physical interface — every other surface in 24 domains is a screen someone chose to look at. The door is the one place WeJammin is in the room, at the moment, whether it works or not.

Validation answers four questions: is this a real ticket, is it for **this** show, has it already been used, and is it still live (not refunded, voided or transferred away).

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Reports | Sees, after the fact, how many of the sold tickets actually walked in and which of their guests came. The room-fullness number they read is the derived `admissions_total` (19.05.01 D-09), **not** this feature's gate-only `scanned` — walk-up buyers are admitted at the window and never scan, so a gate-only figure would understate their room. What this feature contributes to that read is the gate component. Never touches a scanner; the door is not theirs. **When the Musician is also the Operator (DIY self-promoted show), they scan through the Operator lens — the two lenses compose on one human and never conflict (see Edge Cases).** |
| Producer | None | Not visible. No box-office surface. |
| Operator | Full | Scans, sees the accept/refuse verdict and its reason, overrides a refusal when they judge it right, reverses an admission when a downstream gate refuses (19.04.04), and looks up a ticket by name when the barcode is unreadable or the fan has no phone. |
| Fan | Read-only | Presents a barcode and is admitted or refused. Their entire experience is a green light and a door. When refused, they must be told *why* in words they can act on — "already scanned at 20:14, main door" is actionable; "invalid" starts an argument. A Fan who is also a gigging Musician still scans purely as a Fan — the door reads the token presented, not the human's platform roles. |

## Behavior

A scan resolves a barcode to a ticket in the local replica (19.04.02), then applies checks in order: exists → belongs to this show → not voided/refunded (as of last sync) → not already scanned (on this device, or on any device that has synced). The verdict is accept, refuse-with-reason, or accept-with-warning.

The barcode is treated as an **opaque token** — matched by exact string equality against the replica, never parsed, interpreted, coerced, or used to construct a query (D-08). Every verdict is recorded locally with a timestamp, device ID and gate, and queued for reconciliation.

### Happy Path

1. Operator opens the scanner for tonight's show; the manifest replica is already downloaded and the scanner states plainly that it is ready.
2. Fan presents a barcode (phone screen, wallet pass, or paper).
3. Scanner reads it and resolves it locally — no network round-trip.
4. Verdict renders in under a second: large, unambiguous, readable in the dark and at arm's length.
5. Accept → the scan is recorded, the scanned count increments, the fan walks in.
6. Verdict is queued for reconciliation; if there is signal it goes now, if not it goes when there is.

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Already scanned | The core refusal | Reason with **specifics**: time, gate, device. Without those the Operator cannot tell fraud from a re-entry, and the fan cannot tell whether their friend used their screenshot |
| Ticket for a different show | Common — fans keep old wallet passes | Refuse naming the show the ticket is actually for (only shown because it is a real WeJammin-issued ticket the presenter holds — see D-08 on why unknown codes get no such detail) |
| Ticket refunded after the replica's last sync | Replica says valid; server says refunded | **Admit** — see DT-02. Reconciliation flags it afterwards |
| Barcode unreadable — cracked screen, low brightness, paper in rain | Very common in practice | Name lookup fallback, always available, never buried. See DT-01 |
| Fan has no phone and no paper | Bought online, arrived with nothing | Name lookup against the manifest; identity check is the Operator's judgement |
| Screenshot passed to a friend; both present the same barcode | First scan admits, second refuses | Refusal reason names the first scan's time and gate; the argument is now about facts, not about the machine |
| Same barcode read twice within 3 s on one device (double-tap, fan holds phone too long) | Debounced — the second read is the same presentation, not a re-scan | Re-shows the same accept verdict; the count does **not** increment again and no refusal fires. See D-09 |
| Rotating/dynamic barcode with no signal on the fan's phone | The pass cannot rotate; a static fallback is required or the ticket is unusable in a basement | See 19.09.02 — this is where anti-fraud and reality collide |
| Unknown / forged / randomly-generated code not in the replica | No exact match | Refuse with a generic "no ticket for this show" — it never reveals whether the code is valid for some other event (D-08, DT-06) |
| Malformed or injection-shaped payload (control chars, SQL-ish text, overlong string) | Matched as an opaque literal against the replica → no match | Refuse "no ticket for this show"; the payload is never interpreted or executed (D-08) |
| Replica holds the ticket ID but is missing the holder name (partial record) | Accept/refuse still resolves — the verdict needs only status, not name | Accept renders "ticket valid — name unavailable"; name lookup degrades but does not fail the door |
| Corrupt / unreadable replica entry for a presented code | Cannot resolve status from that record | Falls back to name lookup + Operator judgement; the corrupt record is flagged for reconciliation, the door keeps moving |
| Manifest has zero tickets (comps-only show, or nothing sold yet) | Scanner is ready but every code refuses | "No tickets issued for this show" — distinct from "not ready", which means no replica at all |
| Comp ticket | Scans identically to a paid ticket | No difference at the door; only the counters differ (19.03.02 D-02) |
| Accessible ticket | Routes to the accessible entrance; the companion scans alongside | See 19.01.05 |
| Scan accepted, then ID check refuses (19.04.04) | The admission is reversed with a linked record; the count reads net | **Scanned-but-refused** is representable and reversible offline on the same device — see D-07, DT-05, and `19.04-door-scanning-access-control-cx.md#CX-03` |
| Operator overrides a refusal | Permitted — sometimes the machine is wrong and the human is not | Override is recorded with who and why; it is attribution, not prevention (same posture as 19.03.03 D-01) |
| Camera / scanner hardware fault, or app crash-restart mid-show | Device reloads the replica from local storage (no re-download) and resumes; scanning input is unavailable while the camera is down | "Camera unavailable — use name lookup"; the name-lookup path stays fully functional so the door never fully stops |
| The performing Musician is also the Operator scanning the door (DIY show) | One human, two lenses — the door surface exposes only Operator capabilities; the Musician "Reports" count is the same data seen afterward | No conflict: role is resolved per-show/per-device by capability, not by the human's identity. Their own comped guest scans as any Fan |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Not ready | Replica not downloaded (no replica at all), or downloaded incomplete | Blocking state before doors — "this scanner is not ready", with the fix stated (get signal, sync now). Only a **missing or incomplete** replica blocks; staleness never does (D-06; rule authored at 19.04.02 D-11) |
| Ready | Replica present and complete, doors not open — **any age** | Scanner idle with the replica's age shown plainly; an amber stale warning may sit on top of ready without blocking it |
| Resolving | Barcode read, lookup in flight | Target is instant (sub-second); a brief spinner appears only if a large replica index pushes resolution past ~500 ms |
| Scanning | Doors open | Camera live; last verdict persists on screen until the next scan |
| Accept | Valid ticket | Large green verdict; ticket holder name if present, "name unavailable" if the record is partial |
| Refuse | Any check failed | Large red verdict + specific reason + the fallback action available |
| Warning | Accepted but notable (comp no-show pattern, re-entry, stale replica) | Amber verdict with the reason |
| Empty | Replica present but contains zero tickets | Ready to scan, but every code refuses "no tickets issued for this show" |
| Partial | Presented ticket's replica record is incomplete or corrupt | Verdict still renders where status is present; name/details show "unavailable" and the record is flagged for reconciliation |
| Error | Camera/hardware fault or app fault | "Camera unavailable — use name lookup"; scanning is degraded to the manual path, not stopped |
| Offline | No network | Stated plainly and *unalarmingly* — scanning works; only reconciliation is deferred. See DT-03 |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | **Name lookup is a first-class path, not a fallback** | Operator persona works "on a phone at a loading dock"; Fan persona has "no professional stake" and will arrive with a cracked screen, 2% battery, a printed page in the rain, or nothing at all | ✅ CONFIRMED — a meaningful fraction of every real door is resolved by typing a name, and every ticketing system treats it as an escape hatch buried behind a menu. It is not an escape hatch; it is the second-most-used feature at the door. It must be one tap from the scanner, work offline against the same replica, and be as fast as scanning. Burying it does not reduce its use — it just makes the queue longer while the Operator hunts for it. |
| DT-02 | When the local replica and the server disagree, the correct default is **admit and reconcile**, not refuse | Reasoning about the cost asymmetry at the door | ✅ CONFIRMED — the two failure modes are not symmetric. Wrongly refusing a legitimate fan is a public humiliation, an argument, a queue, and a person who paid and cannot get in; wrongly admitting someone whose ticket was refunded eleven minutes ago costs one seat in a room that is probably not full. The door should be generous and the ledger should be honest — admit, record, flag at reconciliation, and let the Operator deal with a report instead of a scene. This inverts the instinct that a validation system exists to say no. |
| DT-03 | The scanner should warn prominently when it is offline | Instinct — offline is a degraded state | ❌ REJECTED — and this one matters for adoption. Offline is the *normal* state in the target venues, not the exception. An alarming offline indicator trains the Operator to distrust a system that is working perfectly, and on a night when everything is fine the scanner is screaming at them. What actually matters is **replica age** ("synced 20 minutes ago") and readiness before doors — a stale replica is a real risk; no signal is not. State it calmly, put the alarm on staleness, and let the door work. |
| DT-04 | A stale replica should **block** the door until it re-syncs (resolves Q-03) | Instinct that a validation system must not decide on out-of-date data; the staleness threshold in 19.04.02 | ❌ REJECTED — hard-blocking on staleness strands exactly the venues this sub-domain exists for. Because admit-and-reconcile (DT-02) already absorbs the refund case, a stale replica still produces correct verdicts for the overwhelming majority; its *only* real error is falsely refusing a ticket **issued after** the sync — rare next to the near-certainty that a basement door cannot re-sync on demand. So the threshold governs a **warning**, never a block, and its value, its trigger conditions and its override scope are **authored once in 19.04.02 D-11** — this row deliberately does not restate them, because two independently-authored copies of that rule are what drifted into contradiction (owner decision DQ-16.6, 2026-07-22). Only a **missing or incomplete** replica blocks (D-06). The reframing that falls out of this: staleness' real risk is false-refusal of *new* tickets, not mis-admission of *refunded* ones — so the sync discipline is "sync after the last comp/transfer/sales batch," not "sync as late as physically possible." |
| DT-05 | Undoing a scanned-but-refused admission means **deleting or rolling back** the scan (resolves Q-04) | The naive count-repair instinct — if the person didn't get in, remove the scan | ❌ REJECTED, ✅ replaced — deletion destroys the evidence the whole sub-domain exists to preserve (19.04.02 D-01, evidence-not-repair) and cannot be propagated cleanly once the scan has already gossiped to a peer or the server. The confirmed design: the reversal is an **additive, linked record** carrying reason (age/ID, void, error), time, operator, device and gate, which *supersedes* the original scan for counting while both stay in the log. It applies **locally and instantly with no network**, because the same device that made the scan owns the record it is reversing — the door corrects itself in seconds, offline, before the fan has left the mat. If the original scan already propagated, the reversal propagates the same way and converges; nothing has to be "un-sent." The gate-observed `scanned` counter is therefore read **net**: accepts minus reversals (19.05.01 D-09). It is one *component* of what downstream reads, not the whole of it — the fire officer's capacity number and settlement's admitted number are the derived `admissions_total`, which is this net gate count plus the window `admitted` counter (19.05.01 D-09, DQ-17.2, 2026-07-22). Audit shows "scanned 20:14, reversed 20:14 (age)". |
| DT-06 | An unrecognised code should tell the Operator "this ticket does not exist" | Modelling instinct — say what you found | ❌ REJECTED in that wording — a refusal that distinguishes "no such code anywhere" from "valid code, wrong show" hands a scalper or enumerator a free validity oracle at the door. So the door reveals a ticket's real event **only** when the presented code matches a ticket WeJammin actually issued to that presenter (their own pass for another night), and returns a flat "no ticket for this show" for anything unrecognised. This is a behaviour posture; whether forged codes are additionally defeated by cryptographic signing before any lookup is an architecture/anti-fraud question (Q-03, 19.09.02). |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | Name lookup is a first-class path, one tap from the scanner, offline-capable | It is the second-most-used door feature and every system buries it (DT-01) |
| D-02 | Default posture on replica/server disagreement is admit-and-reconcile | The cost of wrongly refusing a real fan vastly exceeds the cost of wrongly admitting one (DT-02) |
| D-03 | Refusal reasons are specific — time, gate, device — never "invalid" | Specifics turn an argument into a fact; "invalid" starts one |
| D-04 | Offline is stated calmly; the alarm is on replica staleness, not on connectivity | Offline is the normal state in the target venues; alarming on it trains distrust (DT-03) |
| D-05 | Operator override of a refusal is permitted and recorded | Same attribution-not-prevention posture as 19.03.03 D-01 |
| D-06 | **Scan-side consequence only**: staleness never turns a scan into a refusal and never blocks the door — only a **missing or incomplete** replica blocks a scanner from becoming ready. The staleness rule itself, its amber default and its override scope are **authored in 19.04.02 D-11**; this row references it and does not restate it | Hard-blocking on staleness strands basement venues, and admit-and-reconcile already absorbs the refund case; staleness' real risk is false-refusal of newly-issued tickets (DT-04, resolves Q-03). Reduced from a full restatement to a reference because two independently-authored copies of one rule drifted apart — 19.04.02 owns the object being governed (owner decision DQ-16.6, 2026-07-22) |
| D-07 | Scanned-but-refused is an additive, linked **reversal record** (reason, time, operator, device, gate) applied locally and instantly offline; the original scan is never deleted; the gate-observed `scanned` counter is net (accepts − reversals) | Deletion destroys evidence and cannot propagate cleanly; the same device owns the scan it reverses (DT-05, resolves Q-04). "Net" scopes the **gate** count only; the all-bodies total is the derived `admissions_total` (19.05.01 D-09) |
| D-08 | Barcodes are opaque tokens matched by exact equality; input is never parsed or used to build a query, and unrecognised codes refuse with a generic "no ticket for this show" that leaks no cross-event validity | Security-first input handling plus enumeration resistance at the door (DT-06) |
| D-09 | A repeat read of the same code within 3 s of an accept on the same device is the same presentation — re-shows the accept, does not re-increment or refuse | A single fan holding a phone to the camera must not self-refuse or double-count |
