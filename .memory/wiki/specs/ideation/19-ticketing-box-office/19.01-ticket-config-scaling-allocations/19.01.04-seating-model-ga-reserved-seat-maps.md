# Feature: Seating Model — GA, Reserved & Seat Maps

> **Number**: 19.01.04
> **Parent**: [Ticket Configuration, Scaling & Allocations](./19.01-ticket-config-scaling-allocations-index.md)
> **Status**: [PARTIAL]
> **Last updated**: 2026-07-17

## Overview

Determines whether a ticket entitles the holder to *a place in the room* (general admission) or *a specific place* (reserved), and supplies the seat map when it is the latter. This choice changes the granularity of the manifest, the shape of the purchase flow, and the semantics of every hold — so it is a structural decision made before on-sale, not a display preference.

Music venues are the hard case: the same room is standing for a rock show and seated for a folk show, and **mixed** configurations (seated balcony over a standing floor) are routine rather than exotic.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Read-only | Sees the configuration for their show because it sets capacity, and capacity is what their guarantee was negotiated against. Frequently *requests* a configuration ("this is a seated show") as a booking term in domain 17, but does not set it — the room's physical reality belongs to the Operator. |
| Producer | None | Not visible. No box-office surface. |
| Operator | Full | Chooses the model per show, maintains the room's seat maps, marks sections as seated/standing/mixed, and defines sightline and restricted-view attributes. |
| Fan | Read-only | Experiences it as two completely different purchase flows — "pick your seat from a map" vs "choose a tier and quantity". Sees restricted-view warnings where they apply. |

## Behavior

A show's manifest adopts one of three models:

- **GA** — inventory is a decrementing count against a capacity ceiling. Units are fungible; a hold of 20 is any 20.
- **Reserved** — inventory is a set of addressable seat identities, each with a section, row, number, price level, and attributes (restricted view, accessible, companion, aisle).
- **Mixed** — both simultaneously in one manifest, partitioned by section.

Seat maps are a room asset (domain 16) reused across shows; the show selects a *configuration* of the room, and the manifest is instantiated from it.

### Happy Path

1. Operator selects the show's room; system offers the room's saved configurations (e.g. "Standing 350", "All-seated 220", "Seated balcony + standing floor 300").
2. Operator picks a configuration; system instantiates the manifest at the right granularity and derives capacity.
3. For reserved/mixed, Operator reviews the seat map and marks any show-specific kills (camera platform, desk) — these become 19.01.02 kills.
4. Operator assigns price levels to sections or seat sets (19.01.01).
5. System validates capacity against the room's licensed figure and saves the configuration to the show.
6. Fan-facing flow is derived automatically: seat-picker for reserved sections, quantity-picker for GA sections.

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| **Concurrency** — two Fans select the same reserved seat inside the hold window | Seat resolves to a single owner; the second selection must fail before payment, not after | Loser sees "that seat was just taken" the instant it is claimed; the seat re-colours to unavailable on their live map, other seats stay selectable. Race is resolved at seat-claim, using the hold mechanism in 19.01.02 |
| **Permission** — Musician (read-only) attempts to change the model or edit the map | Rejected; the room's physical reality belongs to the Operator (Role Lens). A Musician's "make this a seated show" is a *booking request* in domain 17, not a self-service edit here | Musician sees the configuration but no edit controls; a request path routes through 17, not this surface |
| Configuration changed after on-sale (seated show goes standing) | Resolved by D-03: this is a **reschedule-class event** (19.06.03), not an edit — sold reserved seats that no longer exist cannot be reconciled by editing the manifest | Operator is blocked from silently re-configuring a live show; the action is surfaced as a reschedule, triggering 19.06.03's notify/refund/re-issue flow. Exact re-issue mechanics `[PENDING — /write-be-spec, owned by 19.06.03]` |
| Mixed room where the Fan does not realise the balcony is seated and floor is standing | Buys the wrong thing; a disappointment, and a refund request that policy may not cover | Section descriptions must state standing/seated explicitly on the purchase surface, before seat/quantity selection |
| Restricted-view seat sold without warning | Fan arrives to a pillar; near-certain refund/complaint | Restricted-view attribute must surface at selection, not at checkout — the seat carries a visible marker and a confirm step on the map |
| Seat map missing for a room | Reserved/Mixed models unavailable; only GA can be configured | Operator sees a CTA to build the map (domain 16); the reserved option is disabled with an explanatory tooltip |
| Room's licensed capacity differs between configurations (standing 350 / seated 220) | Correct and expected — the licence is per-configuration (D-02) | Capacity shown per configuration, sourced from domain 16; never a single room number |
| Capacity of the chosen configuration exceeds the room's licensed figure | Blocked at save — a safety and licensing breach, not a warning | Inline blocking error naming the configuration and its licensed ceiling; save disabled until resolved |
| Adjacency broken by scattered singles after hold release | Later buyers cannot sit together | See `19.01-ticket-config-scaling-allocations-cx.md#CX-03`; whether a seat-optimisation pass runs on release is `[PENDING — Q-03, /write-be-spec]` |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Empty | Show has no room or no configuration chosen | Configuration picker, or a prompt to select a room first |
| Draft | Configuration chosen, not on sale | Seat map / capacity editor with kills and price levels |
| Locked | On sale | Map read-mostly; kills still possible, re-configuration blocked |
| Populated (Fan) | Reserved show on sale | Interactive seat map with availability, price level colouring, restricted-view markers |
| Populated (Fan, GA) | GA show on sale | Tier + quantity picker; no map |
| Error | Capacity exceeds the configuration's licensed figure | Inline blocking error |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | **Mixed** is a first-class model, not an edge case to be bolted on later | Operator persona's physically-constrained inventory; the standard UK/EU club-and-theatre layout of a seated balcony over a standing floor | ✅ CONFIRMED — treating mixed as "reserved with some GA sections" is the pragmatic implementation, but modelling GA and reserved as mutually exclusive at the manifest level makes mixed unrepresentable. A domain expert expects mixed on day one; the sweep did not name any seating model at all. |
| DT-02 | Licensed capacity is a property of the room | Reasoning from domain 16 ownership | ❌ REJECTED — it is a property of the **room configuration**. The same room is licensed for 350 standing and 220 seated; a single capacity number on the room record is wrong for one of them, and being wrong here is a safety and licensing breach rather than a data-quality issue. Domain 16 must expose capacity per configuration. This is a constraint on 16, discovered from 19. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | Three models — GA, Reserved, Mixed — with Mixed first-class | Mixed is the routine music-venue layout, not an exotic case (DT-01) |
| D-02 | The show selects a room *configuration*; capacity is a property of the configuration | The same room has different licensed capacities standing vs seated (DT-02) |
| D-03 | Post-on-sale reconfiguration is a reschedule-class event, not an edit | Sold tickets naming seats that no longer exist cannot be resolved by an edit |
