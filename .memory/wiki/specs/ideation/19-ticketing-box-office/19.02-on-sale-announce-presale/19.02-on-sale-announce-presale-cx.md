## Cross-Cut Details

### CX-01: Scheduling ↔ Presale Windows

**Relationship**: The show carries one announce moment and one public on-sale moment. Between them sits an ordered ladder of presale windows, each with a start, an end, and an allocation carved from the manifest. The schedule is the parent clock: moving the public on-sale must move or invalidate every window that would now run past it.

**Role scoping**:
- **Operator**: owns the schedule and the ladder; the only role that can move either.
- **Musician**: negotiates their presale window as a booking term (domain 17) and sees its start/end; cannot move it.
- **Producer**: not affected.
- **Fan**: sees announce and public on-sale times; sees a presale time only if they hold access to it.

**Synthesis questions answered**:
1. **Shared state conflict**: The schedule is owned by the show (Operator). Windows reference it. Single owner, so no merge — but the schedule is frequently a *deal term* from domain 17, and re-keying it here is where divergence starts.
2. **Trigger chain**: Moving public on-sale earlier can orphan windows that now end after it. Must cascade: the system re-validates the whole ladder and blocks rather than silently truncating a window someone has already been told about.
3. **Permission intersection**: Holding a presale window does not confer scheduling rights.
4. **Notification fan-out**: Yes, and it is the sharp edge — codes may already be distributed with a stated time. A schedule change after code distribution must notify every code holder. Fan-out is via the notifications cross-cut.
5. **State transition conflict**: Window-open and window-close events firing near the public on-sale boundary can race. Ordering must be deterministic; a gap where nothing is buyable is a visible failure, an overlap where a presale allocation is still live during public sale is an inventory leak.

### CX-02: Presale Windows ↔ Access Codes

**Relationship**: This is the pair that constitutes the sub-domain's claim to owning the presale *mechanism*. A window defines an allocation and a time box; a code is the key that a specific holder presents to enter it. The binding carries the redemption rules: how many tickets per code, whether the code is single-use or shared, whether it is bound to an account identity, and what happens when the window's allocation is exhausted while valid codes remain unredeemed.

**Role scoping**:
- **Operator**: creates windows and issues codes; sets redemption limits.
- **Fan**: holds a code, redeems it, and experiences the failure when the allocation ran out before their valid code did.
- **Musician**: configures their own window's code policy (their fan-club presale) within limits set by the deal.
- **Producer**: not affected.

**Synthesis questions answered**:
1. **Shared state conflict**: The window owns the allocation; codes are claims against it. Contention is expected, not exceptional — over-issuing codes relative to allocation is standard practice (not every code holder buys), which means "valid code, no inventory" is a designed-for state, not a bug.
2. **Trigger chain**: Redemption decrements the window's allocation via a cart hold (CX-03). If payment fails, the hold must return to the window's allocation, not to public inventory.
3. **Permission intersection**: Yes — a code grants access to *one window's* allocation only. A fan-club code must not unlock the venue window's inventory even if both are open.
4. **Notification fan-out**: Code issuance is a notification event; who receives it is domain 20's decision, not this sub-domain's.
5. **State transition conflict**: Window close and code redemption race at the boundary. A redemption in flight at close must complete or fail cleanly — a half-redeemed code that has consumed allocation but issued no ticket is the worst outcome.

### CX-03: Presale Windows ↔ Queue & Cart Hold

**Relationship**: Cart holds are inventory reserved for a buyer who has not yet paid. Against a presale window's fixed allocation, every cart hold is allocation that no other code holder can reach. Abandoned carts therefore strand window inventory for the hold's duration, and if the hold expiry is long relative to the window, a window can appear sold out while nothing has been sold.

**Role scoping**:
- **Operator**: sets hold duration; sees stranded-cart counts.
- **Fan**: sees a countdown and either completes or loses the hold.
- **Musician**: reports only.
- **Producer**: not affected.

**Synthesis questions answered**:
1. **Shared state conflict**: The window's allocation is the contended resource. Hold-then-pay is the only safe order, but it makes abandonment costly.
2. **Trigger chain**: Hold expiry returns inventory to the window. If the window has closed by then, the inventory must route to public sale rather than vanish — an expiry firing into a closed window is a leak.
3. **Permission intersection**: Not meaningfully.
4. **Notification fan-out**: Hold expiry warns the Fan; no other party is notified.
5. **State transition conflict**: Yes and it matters — hold expiry, window close, and tier advance (19.01.01) can all fire on the same inventory within the same second. `[PENDING — /ideate-discover Step 5 deepening]`

### CX-04: Queue & Cart Hold ↔ Waitlist

**Relationship**: `[PENDING — /ideate-discover Step 5 deepening]`. Confirmed at breadth: the queue's exit point for unsuccessful buyers is the single highest-intent moment for waitlist capture. A fan who queued for forty minutes and reached an empty allocation has demonstrated intent far beyond anything a marketing list can infer. Discarding them at that exact moment — which is the industry default — is the waste this pair exists to name.

**Role scoping**: **Fan** experiences the handoff; **Operator** and **Musician** consume the resulting demand signal.

### CX-05: Access Codes ↔ Waitlist

**Relationship**: `[PENDING — /ideate-discover Step 5 deepening]`. Confirmed at breadth: inventory that reappears (a released hold, a refunded ticket, a cancelled VIP package) needs a fair, fast destination. The waitlist supplies the ordered list of claimants; the code mechanism supplies a time-boxed private claim link so that returned inventory does not simply reopen to the public — and to bots — as a fresh mini-on-sale.

**Role scoping**: **Fan** claims; **Operator** configures the claim window; **Musician** sees the recovery in reports.

## Rejected Pairs

| # | Source | Target | Reason for Rejection |
|---|--------|--------|---------------------|
| R-01 | 19.02.01 Scheduling | 19.02.05 Waitlist | The waitlist is triggered by *inventory exhaustion*, not by a clock. A show can sell out during a presale window, on public on-sale day, or three weeks later — the schedule is irrelevant to it. |
| R-02 | 19.02.01 Scheduling | 19.02.04 Queue | Considered and dismissed: the queue is triggered by concurrent demand, not by the schedule. It is equally applicable to a surprise mid-campaign surge as to an on-sale minute. Coupling it to the schedule would model the common case as the only case. |
| R-03 | 19.02.03 Access Codes | 19.02.04 Queue | Tempting — both gate entry — but they gate different things at different layers. A code answers "may you enter this window"; the queue answers "in what order do the people who may enter get served". They compose without interacting: a queue may exist inside a coded window or on an open public sale. Conflating them produces the incumbent anti-pattern where the queue *is* the fairness mechanism and codes are decorative. |
