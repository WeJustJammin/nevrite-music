# Feature: Presale Windows & Tiered Access

> **Number**: 19.02.02
> **Parent**: [On-Sale, Announce & Presale Access](./19.02-on-sale-announce-presale-index.md)
> **Status**: [PARTIAL]
> **Last updated**: 2026-07-16

## Overview

The ordered ladder of early-access windows that runs between announce and public on-sale — artist presale, fan-club presale, venue/mailing-list presale, local partner presale. Each window has a start, an end, and an **allocation** carved out of the manifest, so that a presale is a genuine reservation of inventory rather than merely an earlier chance at the same pool.

This feature owns the window: its time box, its allocation, and its ordering relative to other windows. It does **not** own who is eligible to enter it — that is domain 20's segment decision (parent D-02).

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Config | Configures **their own** presale window — its allocation (within the limit their deal grants), its code policy, and its timing within the ladder. Sees their window's redemption in reports. Cannot see other parties' windows or allocations, and cannot change the ladder's overall shape. |
| Producer | None | Not visible. No box-office surface. |
| Operator | Full | Builds the ladder, allocates inventory to each window, orders them, sets limits on what each party may allocate, and is the only role that sees the whole ladder at once. |
| Fan | Read-only | Sees a window only if they hold access to it (19.02.03). Never sees the ladder, other windows, or allocations. A window they cannot enter is invisible, not locked — showing a fan a door they cannot open is a support ticket, not a feature. |

## Behavior

Each window carries: an owning party, a start and end datetime (within the schedule from 19.02.01), an allocation (a quantity or seat set from the manifest, per price level), a code policy (19.02.03), and a per-buyer purchase limit.

Windows may run sequentially (artist → fan-club → venue → public) or overlap deliberately. Allocation is the key property: a window's buyers can only reach that window's allocation, so a sold-out fan-club window does not mean the show is sold out.

Unredeemed allocation at window close returns to the next window in the ladder, or to public inventory if none remains.

### Happy Path

1. Operator opens the presale ladder for a scheduled show.
2. Operator adds a window: owning party, start/end, allocation per price level, per-buyer limit.
3. System validates that total allocation across all windows plus public inventory plus holds does not exceed the manifest.
4. Operator repeats for each window and reviews the ladder as a timeline with allocations shown.
5. Musician (or other party) configures their own window's code policy and requests codes; issuance runs via 19.02.03, with recipients selected by domain 20.
6. Windows open and close on schedule. At each close, unredeemed allocation rolls to the next window.
7. Public on-sale opens with whatever remains.

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Total window allocations exceed manifest inventory | Blocked at save — over-allocated presales sell tickets that do not exist | Blocking error naming the overage per price level |
| Window sells its allocation out while public inventory remains | Correct and expected behaviour, universally misread as "the show sold out" | Fan sees "presale allocation exhausted — public on-sale [time]", never "sold out" |
| Fan holds a valid code but the window's allocation is gone | Designed-for state, not a bug — codes are over-issued relative to allocation by standard practice | Honest message naming the public on-sale time, plus a waitlist CTA (19.02.05) |
| Window closes with unredeemed allocation | Rolls to the next window, or to public inventory | Operator sees the roll in the live count; no manual step |
| Overlapping windows both draw from the same allocation | An allocation belongs to exactly one window — overlap in *time* is fine, overlap in *allocation* is not | Blocked at save |
| Musician allocates more than their deal grants | Blocked at the limit the Operator set | Musician sees their cap and their remaining headroom |
| Ladder has a gap where no window is open and public sale has not started | Fans with codes find nothing buyable and assume a fault | Warning at save; gaps are legal but should be deliberate |
| Two code holders race for the last unit of a window's allocation at the same instant | Allocation is money-bearing state — exactly one buyer may win; the manifest decrement is the single serialization point (shared with 19.01.02 holds) | Winner completes checkout; loser sees "allocation exhausted — public on-sale [time]", never a phantom hold or a double-sold seat |
| Public on-sale (from 19.02.01) is rescheduled earlier than a still-open presale window | The ladder's ordering invariant breaks — a presale that was to precede public sale now overlaps or trails it | Blocked at reschedule with a conflict naming the window(s) the new on-sale time collides with; Operator must re-order or close the window first |
| A single buyer exceeds the per-buyer limit by using several accounts | Per-buyer limit is enforced per checkout here; cross-account abuse detection is domain 24's surface, not this feature's | Limit enforced at the visible boundary; systemic scalping abuse is a `[PENDING — 24 Trust & Safety]` cross-cut, not resolved in-window |

### States

> The presale ladder has both a **management lifecycle** (what the Operator/Musician sees while
> building it) and a **fan-facing lifecycle** (what a code holder sees over the window's life).
> The canonical Loading/Empty/Populated/Error states are the management view; the lifecycle rows
> below them are the substates of "Populated" as time advances.

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Loading | Operator opens the ladder for a scheduled show | Timeline skeleton while windows, allocations, and live redemption counts load from the manifest |
| Empty | Scheduled show, no ladder | Operator sees an empty ladder with an "add window" CTA; a show with no presale is entirely normal |
| Populated | One or more windows configured | Full timeline view with per-window allocations, ordering, and validation status (the lifecycle rows below are its time-driven substates) |
| Error | Manifest/schedule unreadable, or a save validation fails | Non-destructive error banner naming the cause (over-allocation, ordering conflict, unreachable manifest); no window state is lost, retry available |
| Draft | Windows configured, before announce | Timeline view with per-window allocations and validation status |
| Pending | Window configured, not yet open | Party sees their window's start time; code holders see a countdown |
| Live | Window start passes | Code holders can enter and buy from the window's allocation |
| Exhausted | Window allocation consumed | Code holders see the honest "allocation exhausted" message, not "sold out" |
| Closed | Window end passes | Unredeemed allocation rolls onward; code holders see the next available entry point |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | A presale must reserve a real **allocation**, not merely grant earlier access to the common pool | Reasoning about what a presale promises vs what incumbents deliver | ✅ CONFIRMED — and this is the feature's central design call. Early-access-without-allocation means a fan-club presale can consume the entire manifest, leaving the public on-sale a fiction, or conversely a well-marketed public on-sale can strand a presale that promised inventory. Allocation makes the promise checkable: "your fan club has 50 of the 300" is a fact the system can enforce and report on, which is exactly the provenance posture (D-18) applied to inventory. |
| DT-02 | "Presale allocation exhausted" and "show sold out" can share a message — the fan's experience is the same either way | UX economy | ❌ REJECTED — and the distinction is commercially material, not cosmetic. A fan told "sold out" during a fan-club presale stops trying and does not return for the public on-sale; the show then under-sells while the fan believes they were too slow. This is a revenue defect produced by a copy decision. The two states must be separate messages, and the exhausted-window message must name the next moment the fan can act. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | A window reserves a real allocation from the manifest | Early-access-without-allocation makes the presale's promise unenforceable and the public on-sale a fiction (DT-01) |
| D-02 | "Allocation exhausted" is a distinct state and message from "sold out" | Conflating them tells fans to stop trying while the show is still selling — a revenue defect caused by copy (DT-02) |
| D-03 | An allocation belongs to exactly one window; windows may overlap in time but not in inventory | Shared allocation across concurrent windows is an unresolvable race on money-bearing state |
| D-04 | A window the Fan cannot enter is invisible, not locked | A visible door with no key generates support load and no value |
