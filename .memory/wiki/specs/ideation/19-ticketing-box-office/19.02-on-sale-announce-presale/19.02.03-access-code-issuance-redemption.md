# Feature: Access Code Issuance & Redemption

> **Number**: 19.02.03
> **Parent**: [On-Sale, Announce & Presale Access](./19.02-on-sale-announce-presale-index.md)
> **Status**: [SURFACE]
> **Last updated**: 2026-07-16

## Overview

The key mechanism: generating codes that unlock a presale window, delivering them to recipients, and enforcing what a code may redeem. A code binds a holder to exactly one window's allocation, with a purchase limit, a use count, and an optional identity binding.

This is the concrete artifact behind the parent domain's boundary claim — **Ticketing owns the code; Fanbase owns the list of who receives it** (parent D-02).

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Config | Sets their own window's code policy (unique-per-fan vs one shared code, tickets per code, identity-bound or not) and triggers issuance. Sees redemption stats for their window — issued, redeemed, unused. Does not select recipients: that is domain 20's segment. |
| Producer | None | Not visible. No box-office surface. |
| Operator | Full | Sets code policy for every window, issues and revokes codes, sees all redemption state, and handles the door-adjacent support case of a fan whose code will not work. |
| Fan | Full | Receives a code, enters it, and gains access to the window it unlocks. Sees whether their code is valid, what it grants, and when its window opens/closes. Never sees other codes or the allocation behind theirs. |

## Behavior

A code carries: the bound window, a use limit (single-use or N uses), a ticket limit per redemption, an optional identity binding (redeemable only by a named account), and a validity period inheriting the window's time box.

Two policies dominate:
- **Unique codes** — one code per recipient, single-use, identity-bindable. Traceable, revocable, leak-resistant. Higher issuance cost.
- **Shared code** — one code for a whole segment. Cheap and simple; leaks to social media within minutes, which for a low-stakes club show is often acceptable and for a high-demand show is fatal.

Redemption validates the code, opens the window's allocation to the buyer, and applies the per-buyer limit. Codes are over-issued relative to allocation by standard practice (19.02.02 Q-02), so "valid code, no inventory" is a designed-for outcome.

### Happy Path

1. Musician or Operator selects a window and sets its code policy.
2. Domain 20 supplies the recipient segment (the *who*).
3. System generates codes per policy and hands them to the notification cross-cut for delivery.
4. Fan receives their code with the window's open time in the venue's local timezone (19.02.01 D-01).
5. At window open, Fan enters the code on the show page.
6. System validates: code exists, window is open, use limit not exhausted, identity matches if bound.
7. Fan is admitted to the window's allocation and buys within the per-buyer limit.
8. Redemption is recorded against the code; the code's use count decrements.

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Valid code, window allocation exhausted | Designed-for state — over-issuance guarantees it | Honest message: allocation exhausted, public on-sale at [time], plus waitlist CTA. Never "invalid code" — blaming the code for an inventory outcome is the failure that generates the support ticket |
| Valid code, window not yet open | Code is fine, timing is not | Countdown to window open in venue local time |
| Code entered after window closed | Expired | Message naming the next entry point (next window or public on-sale) |
| Shared code leaks to social media | Segment gating is defeated; allocation is consumed by non-members | Operator can revoke and re-issue; see DT-02 |
| Fan redeems partially, returns for the rest | Use count and ticket limit must permit resumption or explicitly not | `[PENDING — /ideate-discover Step 5 deepening]` |
| Identity-bound code, fan buys for a friend on their own account | Blocked by design; a common and sympathetic case | Clear explanation, not a generic rejection |
| Code redeemed, payment then fails | Allocation must return to the window and the code's use must be restored — a consumed code with no ticket is the worst outcome | Cart returns; code shows as unused |
| Fan lost the code / never received it | The most common support case in presale | Re-send flow keyed to the account/email, not to the code itself |
| Code revoked after redemption | Ticket already issued — revocation cannot claw it back | Revocation applies to unredeemed codes only |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Not issued | Policy set, issuance not run | Operator/Musician sees the pending issuance and the segment size from domain 20 |
| Issued | Codes generated and delivered | Fan has a code; issuer sees issued count |
| Valid, pending | Code held, window not open | Fan sees a countdown |
| Redeemable | Window open, allocation available | Fan enters code, gains access |
| Exhausted (code) | Use limit consumed | Fan sees that this code has been used, and by which account if identity-bound |
| Exhausted (allocation) | Window allocation gone, code still valid | Fan sees the honest allocation message, not a code error |
| Expired | Window closed | Fan sees the next entry point |
| Revoked | Operator revoked an unredeemed code | Fan sees a plain statement and a support route |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | A failure caused by **inventory** must never be reported as a failure of the **code** | Reasoning about the support surface: "my code doesn't work" is the single highest-volume presale complaint, and it is usually a lie the system told | ✅ CONFIRMED — this is a small copy decision with a large effect and it is the reason to model code-validity and allocation-availability as two separate checks with two separate messages. Incumbents routinely collapse them into "invalid code", which sends a fan who did nothing wrong to a support queue, and hides from the Operator that the real event was an allocation running out. Separating them turns a support ticket into a waitlist signup (`#CX-04`). |
| DT-02 | Shared codes should be removed in favour of unique codes, since shared codes always leak | Security instinct | ❌ REJECTED — the leak is frequently *the point*. At the DIY/club scale that is WeJammin's beachhead, a "shared code posted to our Instagram story" presale is a promotion tactic, not a security failure; the code creates a sense of insidership and costs nothing to run. Removing shared codes would impose high-demand-show discipline on shows that have no demand problem. Both policies stay; the Operator picks per window, and the system should warn — not block — when a shared code is used on a window whose allocation is small relative to the segment. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | Code validity and allocation availability are separate checks with separate messages | Reporting an inventory outcome as a code error blames the fan and hides the real event from the Operator (DT-01) |
| D-02 | Both unique and shared code policies are supported; the Operator chooses per window | Shared-code leakage is a promotion tactic at club scale and a fatal flaw at arena scale — the policy must follow the show (DT-02) |
| D-03 | Failed payment restores both the allocation and the code's use count | A consumed code with no ticket is the worst possible outcome for the fan and unrecoverable without support |
| D-04 | Code re-send is keyed to the account/email, not to the code | A fan who lost their code cannot present it to prove they should get it |
