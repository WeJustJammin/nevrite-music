# Feature: Announce & On-Sale Scheduling

> **Number**: 19.02.01
> **Parent**: [On-Sale, Announce & Presale Access](./19.02-on-sale-announce-presale-index.md)
> **Status**: [DEEP]
> **Last updated**: 2026-07-17

## Overview

Sets the two moments that define a show's public life: **announce** (the show becomes known to exist) and **on-sale** (tickets become buyable by the general public). Between them sits the presale ladder (19.02.02). This feature owns the clock — including the **embargo** before announce, the period when the show exists in the system, the deal is signed (domain 17), the manifest is built (19.01), and nobody outside the parties may know. Its job is to fire the announce and the public on-sale at the exact stored instants, autonomously, with no human required to be present.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Config | Proposes and agrees announce/on-sale timing — it is routinely a booking term (routing conflicts, tour-wide coordination, an embargo tied to a release date in domain 12). Sees the schedule for their show and is notified of changes to it. Cannot move announce or public on-sale unilaterally; may edit only fields the Operator's deal grants them (typically their own presale window, via 19.02.02). A **self-promoting Musician who is their own Operator** holds Full access for that show (highest-privilege-wins, see Edge Cases). |
| Producer | None | Not visible. A Producer's surface is the session and its provenance (credits/splits); a box office has no Producer view and none is synthesised. Listed explicitly so downstream spec writers never add a Producer scheduling surface by default. |
| Operator | Full | Sets the announce and public on-sale datetimes in the venue's local timezone, manages the embargo, and executes or reschedules the on-sale. The only role that can move a public on-sale after presale codes are distributed — and only with explicit confirmation that fans out a notification to every code holder. |
| Fan | Read-only | Sees the announce (the show appears) and the public on-sale time, and can set a reminder for it. Sees **nothing at all** before announce — an embargoed show is invisible, not "coming soon"; the absence of a leak surface is a feature. Cannot see presale windows or codes here. |

> **Access levels**: Full · Config · Read-only · Reports · None

## Behavior

A show carries an **embargo** state until its announce datetime, at which point it becomes publicly visible with an on-sale time attached. At the public on-sale datetime, public inventory becomes buyable. Presale windows (19.02.02) run between the two.

All datetimes are anchored to the **venue's local timezone**, because that is the timezone every human involved is reasoning in — "on sale Friday 10am" means 10am at the room, regardless of where the artist, promoter or fan is. The system **stores the resolved UTC instant** and **speaks the venue's wall clock** in every surface (DT-01). The venue timezone is derived from the venue entity (domain 16), never free-typed here — there is no timezone input to inject into.

The announce and the public on-sale are executed by a **system-scheduled job at the stored instant**, not by an Operator action (DT-03). The Operator need not be awake, online, or present for either to fire.

### Happy Path

1. Operator opens the show's on-sale setup. The manifest (19.01) must be locked first — the system blocks scheduling an on-sale for a show with no sellable inventory (returns `422 MANIFEST_NOT_LOCKED`, routing to 19.01).
2. Operator sets the announce datetime and the public on-sale datetime, entered and displayed in the venue's local timezone. The system resolves each to a UTC instant on save.
3. Operator optionally builds the presale ladder (19.02.02) in the gap between them.
4. System validates ordering: `announce ≤ every presale start ≤ every presale end ≤ public on-sale`. A violation returns `422 SCHEDULE_ORDER_INVALID` naming the offending pair.
5. Operator confirms. The show sits in **embargo**; the schedule is visible to the parties (Operator, and the Musician on the deal) and to nobody else.
6. At the announce instant, the system makes the show public with its on-sale time attached; fans can set reminders (fires the domain 20 fan alert — the Fan persona's core success criterion).
7. At the public on-sale instant, the system opens public inventory. No Operator presence is required; a dead Operator phone does not delay the on-sale.

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| On-sale scheduled with no locked manifest | Blocked — an on-sale over undefined inventory is a money incident, not a validation nicety | `422 MANIFEST_NOT_LOCKED` with `{error, code}`, CTA routing to 19.01 |
| **Manifest partially locked** (some price levels locked, some draft) | Treated as not locked — a partial manifest can still change the number of sellable tickets | `422 MANIFEST_NOT_LOCKED`, banner naming the unlocked price levels |
| Ordering violated (on-sale before announce, presale outside the window) | Blocked at save; the ladder is re-validated as a whole | `422 SCHEDULE_ORDER_INVALID` naming the specific `(earlier, later)` pair that inverted |
| Public on-sale moved **earlier**, orphaning a presale window that now ends after it | Blocked — a window running past public sale leaks presale allocation into the public pool (CX-01); cascade is explicit, never a silent truncation (D-04) | `409 PRESALE_WINDOW_ORPHANED` naming each affected window and its new overrun |
| **Schedule changed after presale codes are distributed** | Change is legal but never quiet — requires explicit Operator confirmation and fans out a notification to every code holder (DT-04, CX-01) | Confirmation dialog naming the exact code-holder count; on confirm, `200` + notification job enqueued to all holders |
| On-sale wall-clock time falls in a **DST spring-forward gap** at the venue (e.g. 2:30am when the venue clock jumps 2:00→3:00) | Blocked at save — a local time inside the gap maps to no instant, and resolving it at on-sale minute is the worst possible time to discover it (DT-05) | `422 SCHEDULE_DST_NONEXISTENT` offering the two nearest valid instants (the moment before the gap and the moment after) |
| On-sale wall-clock time falls in a **DST fall-back overlap** (e.g. 1:30am occurring twice) | Resolved deterministically to the **first** occurrence (earlier UTC instant); not an error | `200`, with an inline note stating the resolved instant so the ambiguity is visible, not hidden |
| **Embargo leaks** before the announce instant (a party publicises the show early) | Not a system state change — the leak is social. The Operator's recovery is an **emergency early announce**: pull the announce datetime to *now*, which the system always permits because announce moving earlier cannot violate `announce ≤ presale ≤ on-sale`. On-sale and presale times are unchanged | Operator sees an "announce now" action; on execute, the show goes public immediately with its unchanged on-sale countdown. Whether a *dedicated* leak-recovery affordance (vs plain "set announce = now") is warranted is a product question — see Q-03 |
| **Two Operators** (or an Operator and a self-promoting Musician-as-Operator) edit the schedule concurrently | Optimistic concurrency — the second save carries a stale version and is rejected rather than silently clobbering the first (D-08) | `409 SCHEDULE_VERSION_CONFLICT` naming which field the other actor changed; the loser re-loads and re-applies |
| **Musician (Config-only) attempts to move the public on-sale** | Permission denied — Config does not confer scheduling rights over announce/public on-sale (CX-01 permission scoping) | `403 SCHEDULE_FORBIDDEN` naming which fields their role may edit (typically only their own presale window) |
| **Multi-hyphenate in two roles**: one human is both the Musician on the deal (Config) and the Operator of the venue (Full) for the same show | Highest-privilege-wins per show — the union grants Full; they are never blocked from moving the on-sale merely because their Musician lens is Config | The full Operator scheduling surface; no self-imposed permission wall |
| **Network failure mid-save** (client drops between submit and ack) | The save is a single transaction — the schedule is either fully written or not at all; a half-written schedule is never persisted. The submit carries an idempotency key so a retry cannot double-apply | On reconnect the client retries; the Operator sees either the saved schedule or the original, never a partial |
| **Malicious past-dated on-sale** (actor sets public on-sale to a past instant to force an immediate open) | Permitted only if it still satisfies ordering and the manifest is locked — a past on-sale simply resolves to "on sale now". It cannot precede announce, so it cannot force-reveal an embargoed show ahead of its announce | If it would invert ordering, `422 SCHEDULE_ORDER_INVALID`; otherwise the show opens per the normal on-sale path |
| **On-sale instant arrives while the Operator is mid-edit** of that same on-sale time | The scheduled job fires at the *stored* instant; an edit landing after the instant has passed cannot un-open a live sale. Pausing a live sale is a distinct action (off-sale, 19.05.04), not a reschedule | The edit save returns `409 SCHEDULE_ALREADY_FIRED`; the Operator is directed to the off-sale control if they need to stop it |
| **Tour-wide on-sale** — 30 dates meant to open at one moment | Today: 30 separate schedules kept in sync by hand; drift is likely the moment one date's venue sits in a different timezone or one leg reschedules. Whether this becomes a first-class object or a batch template is a product/cost decision (parent Q-01/Q-02) — see Q-02 | Per-show schedules; no shared "tour on-sale" object yet |
| Artist and venue disagree on the on-sale time | Not a system failure — a deal dispute. The schedule is a term of domain 17; the divergence surfaces and resolves there, not in the box office | No box-office error; the field reflects whatever domain 17 last agreed |

### States

Interaction/UI states of the scheduling surface itself:

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Loading | Schedule form opened; fetching show, manifest-lock status, and venue timezone | Skeleton of the two datetime fields and the ladder timeline |
| Empty | Show exists, no announce/on-sale set yet | Two empty datetime pickers pre-set to the venue's timezone; Save disabled until the manifest is locked |
| Populated | A valid schedule is saved | Timeline showing announce, presale ladder, and public on-sale, all in venue local time, with the resolved instants available on hover |
| Error | Save rejected (manifest, ordering, DST gap, orphaned window, version conflict) | Inline blocking error on the offending field naming the `code` and the specific offending value |
| Partial | Manifest partially locked, or venue timezone missing from domain 16 | Fields visible but Save disabled; a banner names the exact blocker and links to it |

Schedule **lifecycle** states of the show (the substance this feature manages over time):

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Embargoed | Show created, before the announce instant | Parties (Operator, dealed-in Musician) see the show and its schedule; Fans see nothing at all — the show is not discoverable by any means |
| Announced | Announce instant passes | Fan sees the show with an on-sale countdown and a reminder CTA; presale-code holders see their private countdowns |
| Presale live | A presale window opens (19.02.02) | Fan sees a presale entry point if they hold access; otherwise the public countdown continues unchanged |
| On sale | Public on-sale instant passes | Public inventory is buyable |
| Sold out | Public inventory exhausted | Waitlist CTA (19.02.05) replaces the buy CTA |
| Off sale | Sales closed (door time, or a manual pause) | Show marked off-sale; walk-up may still be available (19.05.04) |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | Schedule datetimes must anchor to **venue local time**, not to the actor's timezone or to UTC in the UI | Operator persona works "on a phone at a loading dock"; artists tour across timezones; the phrase "on sale Friday 10am" is universally understood to mean 10am at the room | ✅ CONFIRMED — and it has teeth beyond display. A touring Musician in another timezone configuring their own presale, and a Fan in a third, must all see the *same* wall-clock moment described the way the industry describes it. Rendering an on-sale in the viewer's local timezone is the technically-correct choice that produces the wrong conversation. **Store the resolved instant; speak the venue's clock.** |
| DT-02 | Announce and on-sale are the same event with a delay — most small shows announce and go on sale simultaneously | Observation that DIY/club shows usually do exactly this | ❌ REJECTED — they are the same *moment* in the common case but not the same *event*, and collapsing them removes the embargo, which is the state that matters most. A show exists in the system from the moment the deal is signed (domain 17), often months before announce, with a manifest, holds and a guarantee attached. That period needs a first-class state where the show is real to the parties and non-existent to everyone else. Simultaneous announce+on-sale is a schedule where the two datetimes are equal — a config, not a separate model. |
| DT-03 | The on-sale must fire on a **system schedule**, autonomously, with no human in the loop | The on-sale instant is chosen for the audience ("Friday 10am"), not for the Operator, who is on a loading dock; a human trigger reintroduces the single point of failure the schedule exists to remove | ✅ CONFIRMED — the stored instant is the trigger and execution is a background job. Requiring an Operator to press "go" guarantees a late on-sale the one time their phone dies, and a late on-sale is publicly visible failure at the exact moment demand peaks. The Operator's presence is required to *schedule*, never to *execute*. |
| DT-04 | A schedule change can silently update every downstream surface | UI economy — one edit, everything reflects it | ❌ REJECTED — once presale codes carrying a stated time are distributed (CX-01/CX-02), that time is a promise made to named holders. A silent change means a fan arrives at a countdown that ends at the wrong moment. Every schedule change **after** code distribution must require explicit Operator confirmation naming the holder count and must fan out a notification to every holder. The change is legal; it is never quiet. |
| DT-05 | A non-existent local wall-clock time (DST spring-forward gap) can be stored verbatim and resolved at runtime | Simpler write path — defer the ambiguity | ❌ REJECTED — a local time inside the gap maps to *no* instant, so "resolve at runtime" means resolving at on-sale minute, the worst possible time to find the schedule is undefined. The gap must be caught at save (`422 SCHEDULE_DST_NONEXISTENT`) with the two nearest valid instants offered. The common 10am on-sale never touches the 1–3am gap, so this guards only the rare deliberate overnight on-sale — but "rare" at on-sale scale is still a public incident, and the fall-back overlap needs a deterministic first-occurrence rule for the same reason. |
| DT-06 | Tour-wide on-sale is adequately served as a **batch operation** over per-show schedules — no first-class "tour on-sale" entity is needed | Batch is cheaper to build; most tours could be hand-synced | ⏳ DEFERRED to product — the reasoning cuts both ways and the choice is a cost/scope call, not an ideation certainty. Hand-kept schedules drift the instant one date sits in a different timezone or one leg reschedules, and a touring artist reasons about "the tour on-sale" as one object; but whether that object is first-class or a batch template is a MoSCoW decision (parent Q-01/Q-02). Recorded as Q-02, owned by the user. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | All schedule datetimes are expressed in the venue's local timezone; the system stores the resolved UTC instant and speaks the venue's wall clock everywhere | It is the timezone the industry speaks in and the only one all parties share (DT-01) |
| D-02 | Embargo is a first-class state, distinct from "not yet announced" | The show is real to the parties for months before it is real to the public (DT-02) |
| D-03 | An on-sale cannot be scheduled against an unlocked or partially-locked manifest | Selling undefined inventory is a money incident, not a validation nicety |
| D-04 | Schedule changes cascade explicitly and block; they never silently truncate a window | A window someone holds a code for is a promise already made (CX-01) |
| D-05 | Announce and public on-sale fire on a system-scheduled job, not on an Operator action | The instant is chosen for the audience, not the Operator; a human trigger is a single point of failure (DT-03) |
| D-06 | A schedule change after presale codes are distributed requires explicit confirmation and fans out a notification to every code holder | A distributed code states a time; changing it silently breaks a promise to named holders (DT-04) |
| D-07 | DST spring-forward (non-existent) local times are rejected at save; DST fall-back (ambiguous) times resolve to the first occurrence, stated explicitly | A gap maps to no instant; deferring resolution to on-sale minute is the worst time to discover it (DT-05) |
| D-08 | Concurrent schedule edits use optimistic concurrency — the stale save is rejected with a version conflict, never silently overwritten | Money-bearing state must not be lost to a last-write-wins race; two Operators (or an Operator and a Musician-as-Operator) can hold the same show, so a concurrent-edit collision is expected, not rare |
| D-09 | When one human holds both Config (Musician) and Full (Operator) on the same show, the union grants Full — highest-privilege-wins per show | The multi-hyphenate must never be blocked by their own weaker lens |
