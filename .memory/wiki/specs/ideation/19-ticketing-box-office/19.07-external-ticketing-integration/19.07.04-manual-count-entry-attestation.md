# Feature: Manual Count Entry & Attestation

> **Number**: 19.07.04
> **Parent**: [External Ticketing Integration & Count Reconciliation](./19.07-external-ticketing-integration-index.md)
> **Status**: [SURFACE]
> **Last updated**: 2026-07-16

## Overview

Someone types the number in. This is not the sad fallback for when the integration fails — for the majority of venues WeJammin is actually targeting, it is **the primary path**, because their ticketing is a WordPress plugin, a Facebook event, a friend with a card reader, or a cash box.

The moment you accept that a human types the number, the problem stops being an integration problem and becomes an **attestation problem**: not *how do we fetch this*, but *who says this is true, and does the counterparty accept it?* That is a question WeJammin is unusually well-placed to answer, because it is the same question the entire platform exists to answer about credits and splits (D-18).

**Deep Think addition** — not in the sweep candidate list (parent D-02).

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Read-only | Sees the number, **who attested it, and when** — and can accept or dispute it. Read-only on the entry itself; the counter-attestation question (Q-01) may make this Full, and the thesis argues it should. Today the equivalent is a text message saying "we did about 200" and no record that it was ever said. |
| Producer | None | Not visible. No box-office surface. |
| Operator | Full | Enters the count, attests it, and answers for it. The attestation is personal — a named human said this, at a time, and that record outlives their memory of it. |
| Fan | None | Never sees this. |

## Behavior

Manual entry writes directly into WeJammin's model — paid, comp, gross, per price level — with source `manual`, an **attesting human**, and a timestamp.

The attestation is the feature. A number without a name on it is a rumour; the same number with "entered and attested by Sarah Okafor, 23:41, 14 March" is a fact about what Sarah said, which is a different and much more durable object. It does not make the number *correct* — nothing can — but it makes it **attributable**, which is what ends arguments.

Counter-attestation by the Musician (Q-01) is what would promote it from "the venue's claim, recorded" to "an agreed fact", which is the thesis applied exactly.

### Happy Path

1. Show has no connector (19.07.01) — the platform is unsupported or there is no platform at all.
2. At close (19.05.05), the Operator is prompted to enter the count as part of ending the night — not as a separate chore afterwards (19.05.05 DT-01).
3. Operator enters paid, comp and gross per price level, reading from whatever their actual system is: a dashboard, a cash box, a clicker, a notebook.
4. System shows what it can check for free: does gross ÷ paid land near the face value? Is paid ≤ capacity? Is paid ≥ scanned, if WeJammin ran the door?
5. Operator attests. Their name and the timestamp bind to the number permanently.
6. The Musician — ideally still in the building — sees the number and its attestation, and accepts or disputes.
7. The attested count feeds the certified statement (19.05.05) and settlement (17).

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Number is simply wrong — an honest mistake at midnight | The most likely failure, and unfixable by any amount of process | Free sanity checks (gross vs face value, paid vs capacity, paid vs scanned) catch the fat-finger cases. They cannot catch a plausible wrong number. See DT-01 |
| Number is deliberately understated | The Operator anti-persona's commercial temptation on a door split | Attestation does not prevent it — it makes it a named, dated, personally-attributed claim, which is a meaningfully different thing to make falsely. Same posture as 19.03.03 |
| Musician has already left | Counter-attestation cannot happen in the room; the same problem as 19.05.05 | The hard case for Q-01. `[PENDING — /ideate-discover Step 5 deepening]` |
| Entered days later from memory | **The exact failure the platform exists to prevent**, reproduced inside the platform | Entry must be part of the close, at the moment. A late entry must be marked as reconstructed, not silently equal to a same-night attestation. See DT-03 |
| Paid < scanned | More people got in than were sold | Caught free; genuine signal (double-scans, counterfeits, or a wrong number) |
| Operator revises after attesting | The number moves after someone put their name to it | Revision is a new attestation, not an edit. The original stands in the record |
| No scanned count either (WeJammin ran no door) | Nothing to check against at all | Single-source and unreconciled; must say so (19.07.03 D-01) |
| Venue has genuinely no idea | Cash box, no clicker, no list | An honest "unknown" beats a fabricated number. `[PENDING]` — is that a supported state? |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Required | Show closing, no connector | Entry is part of the close flow, not a task afterwards |
| Entering | Operator typing | Fields in WeJammin's model; free checks live as they type |
| Warning | A check failed | Stated plainly with the arithmetic, before attestation |
| Attested | Operator confirmed | Number + name + timestamp, immutable |
| Accepted | Musician counter-attested | Two names on the fact |
| Disputed | Musician disagreed | Recorded as part of the record (19.05.05 DT-02) |
| Revised | New attestation supersedes | Both versions in the record; the original is not erased |
| Reconstructed | Entered late, not at the close | **Marked as such** — a memory is not an observation (DT-03) |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | Manual entry is an **attestation** problem, not a data-entry problem — the design target is attribution, not accuracy | Problem statement's root cause — *"no system is present at the moment of creation, so the record is always a reconstruction"*; `personas.md` on the Producer as trust broker — *"their attestation is worth more than a self-claim"* | ✅ CONFIRMED — and it reframes the feature from a compromise into a product. Nothing can make a typed number *correct*; validation can catch a fat finger and nothing more. But WeJammin does not actually need the number to be provably correct — it needs it to be **attributable and accepted**, because that is what settlement runs on and what ends disputes. "Sarah said 214 at 23:41 and the artist accepted it in the room" is a stronger commercial artifact than an API-fetched 214 that nobody looked at, because the disagreement was resolved while both parties were present. The platform's whole thesis is that a fact captured at the moment, with the parties there, beats a reconstruction — and that thesis does not require an API. It requires being in the room, which manual entry is. |
| DT-02 | A manually-entered count is inherently lower-quality than an API-ingested one | Obvious-sounding hierarchy: machines beat humans | ❌ REJECTED, and the inversion is genuinely useful. A **thin** connector (19.07.01's aggregate tier) yields one number with no tier detail, no comp separation, and a mapping that may silently fold comps into paid (19.07.02 Q-01) — nobody has looked at it, nobody has attested it, and its errors are systematic and invisible. A human reading their own dashboard and typing per-tier numbers into *our* model has no mapping layer at all (`#R-02` in the sub-domain CX), produces richer data, and has personally attested it. The API number is more *precise*; the attested number is more *accountable*. For settlement, accountability is worth more — which means manual entry should sit alongside connectors as a legitimate choice, not beneath them as a fallback, and a venue with a thin API might reasonably be *advised* to type it in instead. |
| DT-03 | A count entered three days later is the same fact as one entered at the close | It is the same number about the same night | ❌ REJECTED, and this is the platform's own thesis pointed at itself. `problem-statement.md` says the industry's failure is that *"the facts are reconstructed years later, from memory"* — a count typed in on Tuesday from memory of Saturday is that exact failure, committed inside the system built to prevent it, and if the system records it identically to a same-night attestation then it has laundered a reconstruction into a fact. That is worse than not capturing it, because it looks authoritative. Late entries must be marked **reconstructed**, visibly and permanently, so that downstream consumers — and the artist — can weigh them accordingly. This also creates the right pressure: if entering it at the close produces a stronger record than entering it Tuesday, the close is where it gets entered, which is precisely the lazy-path-is-the-correct-path design law (19.05.05 DT-01). |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | The design target is attribution, not accuracy | Nothing makes a typed number provably correct; attribution is what settlement runs on and what ends disputes (DT-01) |
| D-02 | Manual entry sits alongside connectors as a legitimate path, not beneath them | A thin API is more precise and less accountable than an attested human entry; for settlement, accountability wins (DT-02) |
| D-03 | Entry belongs inside the close flow, at the moment | A count typed on Tuesday from memory of Saturday is the industry's failure reproduced inside the fix |
| D-04 | Late entries are permanently marked **reconstructed** | Recording a memory identically to an observation launders a reconstruction into a fact (DT-03) |
| D-05 | Revision is a new attestation; the original stands in the record | An attestation someone put their name to is not editable |
| D-06 | Free checks (gross vs face value, paid vs capacity, paid vs scanned) run live at entry | They catch fat fingers, which is the most common error; they cannot catch a plausible wrong number and must not pretend to |
