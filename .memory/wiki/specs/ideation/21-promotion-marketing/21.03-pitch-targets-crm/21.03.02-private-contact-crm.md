# Feature: Private Contact CRM & Relationship History

> **Number**: 21.03.02
> **Parent**: [Pitch Targets & Relationship CRM](./21.03-pitch-targets-crm-index.md)
> **Status**: [PARTIAL]
> **Last updated**: 2026-07-17

## Overview

The artist's own record of who they actually know: the contacts they added, the notes only they
have, the history of what happened. This is the spreadsheet the domain index says "walks out the
door when the person leaves" — replaced by something that accumulates. Where the directory
(21.03.01) knows facts about a business, this knows a relationship.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Full | Adds contacts (including people who are in no directory — the promoter's cousin who runs a blog); writes private notes; sees the merged view of public facts plus their own history ("Dave, Outlet X, last pitched 2025-11, replied, asked for a stronger single"); exports everything (21.03.04). This record is theirs and the platform's read access to it is the sharpest privacy boundary in the domain. |
| Producer | None | Not a pitching function; no access to any artist's private relationship record. |
| Operator | None | An Operator's local-press relationships are real and homeless — see Q-03 on the sub-domain index. They are not served by this feature as scoped. |
| Fan | None | No access. Private contact records are personal data about third parties and have no fan-facing surface at all. |

## Behavior

A private contact is either an overlay on a directory target (public facts + my history) or a
standalone entry for someone in no directory at all — which is where the most valuable
relationships usually live, because the contacts that matter are the ones nobody else has.

**The platform must not read the notes.** The directory's aggregation (CX-01) uses *structured
outcomes* — sent, responded, silent, covered — never note content. This distinction has to be
enforced in the schema rather than in policy, because the temptation to mine free-text notes for
directory intelligence will be permanent and each individual instance will look reasonable.

**History survives its referent.** If the directory merges two records, or removes one, or the
journalist moves outlet, the artist's history stays attached to the *person*. The relationship is
theirs; our row is a convenience.

### Happy Path

1. Musician pitches a journalist from the directory (21.02.03).
2. A private contact is created automatically, referencing the target — the artist does not do data entry to get memory.
3. Outcome recorded (21.03.03) and appears on the contact's timeline.
4. Musician adds a private note: "asked for a stronger single next time."
5. Next campaign, a year later, the target surfaces with that history attached — which is the entire point and the thing a spreadsheet has never once done reliably.
6. The note never leaves the artist's account.

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Contact exists only privately, then appears in the directory later | Should reconcile so history unifies rather than fragmenting into two Daves | Suggested link, not an automatic merge — a wrong automatic merge silently corrupts a relationship record |
| Directory target is removed (GDPR erasure) while a private contact references it | The artist's own record of a person they know is *their* data; the directory's record is ours | `[PENDING — /ideate-discover Step 5 deepening]` — genuinely hard: an erasure request against the directory arguably does not reach the artist's private address book, but that argument needs legal review, not my confidence |
| Band entity: member who built the CRM leaves | The fight. Q-04 on the sub-domain index | `[PENDING]` — this is precisely the "walks out the door" problem the domain exists to solve, reproduced inside our own product |
| Contact's data is wrong (artist typo'd the email) | Private data, private error, silent failure — bounces feed back | Bounce surfaced on the contact, not hidden in a send log |
| Artist stores something in notes that is defamatory or is special-category data | Private free text about identifiable third parties is a real exposure surface | `[PENDING — /ideate-discover Step 5 deepening]` — probably a `/create-prd-security` concern; flagged rather than designed |
| Artist has 2,000 contacts from an import | Import quality is unknowable and may be a scraped list | Portability cuts both ways (21.03.04) — an import path is also an ingestion path for lists that should not exist |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Loading | Contact list / timeline being fetched | Skeleton rows; the merged view resolves in two layers (public facts may arrive before the private overlay) — never a flash of public-only data mistaken for the complete record |
| Empty | No contacts | Empty state; the first pitch populates it automatically |
| Populated | Contacts exist | Merged view — public facts + private overlay, with which-is-which legible when it matters |
| Linked | Private contact references a directory target | Both layers shown, distinguishable |
| Standalone | Contact in no directory | Fully private; often the most valuable rows |
| Stale | Directory facts decayed / bounces recorded | Staleness shown on the contact, per 21.03.01 D-01 |
| Orphaned | Referenced directory target removed | History preserved; the reference degrades gracefully, never dangles |
| Error | Contact fetch/save failed | Retry affordance; a save that fails must not silently drop a private note — the artist's typed history is the one thing here that is genuinely unrepeatable, so an unsaved note is held and re-offered, never discarded |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | The CRM must be **populated as a byproduct of pitching**, never by data entry — because a contact database that requires maintenance is the spreadsheet we are replacing, and it will rot identically | Direct application of the platform thesis. `meta/problem-statement.md`: "Because no system is present when the work happens, the facts of the work are never recorded." `meta/personas.md` on the Producer: capture must be "a byproduct of running the session — zero extra admin". The same structural claim applies exactly here — the pitch *is* the moment the relationship fact becomes true | ✅ CONFIRMED — and it is this feature's whole justification. It also explains why 21.03 is a sibling of 21.02 rather than a helper library: the pitch and the memory of it are one event captured once. A CRM the artist has to update is not a product, it is homework, and they will do it for three weeks. |
| DT-02 | The platform should mine private notes to improve the directory — the notes contain exactly the intelligence the directory lacks | Efficiency instinct, and each individual instance would look reasonable ("we're just extracting which genre they prefer") | ❌ REJECTED — and it needs a schema-level boundary, not a policy. The artist's private note is the one thing in this domain that is unambiguously theirs, and the aggregation in CX-01 works fine on structured outcomes alone. Reading notes would also make the export in 21.03.04 a lie by omission: they would be taking a copy of something we had already extracted the value from. `meta/problem-statement.md` Q-02 asks whether the lock-in is earned or hostile; mining private notes is the precise definition of hostile, and it would be discovered eventually. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | Contacts are created automatically from pitching, never by data entry | See DT-01. A CRM requiring maintenance is the spreadsheet, rebuilt. |
| D-02 | The platform never reads note content; aggregation uses structured outcomes only | See DT-02. Enforced in schema, not policy. |
| D-03 | History attaches to the person and survives directory changes | The relationship is the artist's; our directory row is a convenience. |
| D-04 | Directory-to-private linking is suggested, never automatic | A wrong automatic merge silently corrupts a relationship record, and the artist would never know. |
