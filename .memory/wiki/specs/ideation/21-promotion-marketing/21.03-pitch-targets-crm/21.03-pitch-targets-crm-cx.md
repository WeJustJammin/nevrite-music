## Cross-Cut Details

### CX-01: Pitch Tracking → Directory (aggregation)

**Relationship**: Outcomes recorded privately (sent / responded / silent / covered) aggregate
into per-target statistics published in the directory. The flow is strictly upward and strictly
anonymised — the directory learns that a target responds to 4% of pitches, never who pitched them
or what was said.

**Role scoping**:
- **Musician**: contributes without effort (the byproduct of pitching) and consumes the aggregate. The reciprocity is the deal, and it should probably be stated to them rather than assumed.
- **Producer / Operator / Fan**: not affected — not senders.
- **The gatekeeper**: the subject of the statistic, with no seat in the persona model and no consent flow. This is the uncomfortable part (see Q-02, sub-domain index).

**Synthesis questions answered**:
1. **Shared state conflict**: The private outcome is owned by the artist; the aggregate is owned by the platform. Neither mutates the other. An artist deleting their CRM entry should not retroactively rewrite an aggregate — but whether it *may* remain is a GDPR question, not a design preference.
2. **Trigger chain**: Outcome recorded → aggregate recomputed. Async, eventually consistent, no rollback needed. A lost aggregate update is a rounding error, not a failure.
3. **Permission intersection**: Critical and inverted. Write access to a private outcome confers *no* read access to any other artist's outcome, yet all of them are visible in aggregate. The anonymisation is the only thing standing between a useful directory and a leak of every artist's rejection history — and small-n targets make re-identification trivial (if a curator received 3 pitches this month, a 33% response rate identifies a specific artist's outcome to anyone who knows two of them).
4. **Notification fan-out**: None. Aggregation is silent.
5. **State transition conflict**: An outcome can be corrected after the fact ("actually they did reply, late"), which must recompute the aggregate. Late-arriving corrections to a statistic others have already acted on are a known-acceptable inconsistency here.

### CX-02: Directory ↔ Private CRM

**Relationship**: The private contact holds a reference to the directory target plus the artist's
own overlay. When the directory's facts change — the journalist moved outlet, the submission
address changed — the private contact's reference must notice, without the platform ever reading
the artist's private notes.

**Role scoping**:
- **Musician**: sees one merged view (public facts + private history) and should not have to care which half is which — until it matters, at which point the distinction must be legible.
- **Producer / Operator / Fan**: no access.

**Synthesis questions answered**:
1. **Shared state conflict**: No conflict by construction (D-02). The directory owns public facts; the CRM owns private overlay. The merged view is a render, not a stored entity.
2. **Trigger chain**: Directory fact change → notify contacts referencing it ("Dave moved to a different outlet — your history stays with Dave, not the outlet"). This is a genuinely valuable event and it is one a spreadsheet can never fire.
3. **Permission intersection**: The platform must never read private notes to improve the directory. The aggregation in CX-01 uses *outcomes*, which are structured events, never note content. This line has to be explicit in the schema, not merely in policy — because the temptation to mine the notes will be permanent.
4. **Notification fan-out**: Directory changes fan out to every artist holding a private reference. Target opt-out (21.02.06) must fan out the same way and override everything.
5. **State transition conflict**: A directory target can be deleted or merged (duplicate entries reconciled) while private contacts reference it. Private history must survive its public referent — the relationship is the artist's, not the directory's.

### CX-03: Private CRM ↔ Portability

**Relationship**: Portability is answerable only because D-02 separated the entities. The artist
takes their CRM — every contact they added, every note, every outcome. They do not take the
directory, which they did not create. The line is clean precisely because the objects were never
merged.

**Role scoping**:
- **Musician**: exports their own record, in full, in a form that is actually usable elsewhere.
- **Producer / Operator / Fan**: no access.

**Synthesis questions answered**:
1. **Shared state conflict**: A contact the artist *added* to the directory is the hard case — they created the data, and it is now in the commons. See 21.03.04 DT-02.
2. **Trigger chain**: Export → assemble → deliver. No downstream effects. Export must not be a signal that triggers retention behaviour, which is precisely how "earned lock-in" turns hostile.
3. **Permission intersection**: A band entity's CRM versus a member's personal CRM (Q-04, sub-domain index). When a member leaves, this is the fight.
4. **Notification fan-out**: None — and deliberately. Notifying anyone that a user exported their data is a retention dark pattern.
5. **State transition conflict**: Export races ongoing writes. A snapshot is fine; the artist does not need a transactionally perfect export, they need their contacts.
