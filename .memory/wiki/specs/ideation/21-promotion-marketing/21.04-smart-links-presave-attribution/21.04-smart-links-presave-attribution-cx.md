## Cross-Cut Details

### CX-01: Pre-Save ↔ Smart Link (the mutation)

**Relationship**: One URL, two meanings, separated by a moment. Before release it collects
authorisations; at release it becomes a routing link to the live track. Everyone who shared it —
the artist, the fans who reposted it, a journalist who embedded it in a premiere — shared it in
the first state and it must not break in the second.

**Role scoping**:
- **Musician**: creates it once and expects it to survive the transition without their intervention. If they must swap links at release, the product has failed at its single most important moment while they are busiest.
- **Producer**: no involvement.
- **Operator**: no involvement.
- **Fan**: experiences both states, possibly the same fan twice. A fan who pre-saved and returns on release day should not be asked to pre-save something already in their library.

**Synthesis questions answered**:
1. **Shared state conflict**: One link object, one owner, a state field. Modelling them as separate entities would force a URL swap at release, which is the failure mode this design exists to avoid.
2. **Trigger chain**: Release moment → link mutates **and** the queued pre-saves fire. If the pre-save fan-out partially fails, the link has still mutated — these are independent. Coupling them would mean a token failure blocks the link, which is strictly worse.
3. **Permission intersection**: The fan's authorisation grants library-write to *them*, scoped to this release. It confers nothing on the link and expires with the action.
4. **Notification fan-out**: Release day is the largest fan-out in the domain — every pre-saver gets the track. It is also the moment most likely to fail at scale (see 21.04.02).
5. **State transition conflict**: The sharp one. If the release date moves (21.01.04), the link is in pre-release state with authorisations attached against a stated date. The mutation must follow the *release event*, not the originally-stated date — otherwise a delayed release mutates a link to a track that does not exist.

### CX-02: Lifecycle ↔ Smart Link / Pre-Save

**Relationship**: Lifecycle owns the phases: created → pre-release → released → in-window →
out-of-window → retired. It is the mechanism by which the domain index's Fanbase boundary is real
rather than rhetorical: these objects have a lifespan by construction.

**Role scoping**:
- **Musician**: sees which links are live, which are dead, and which are quietly rotting (pointing at a delisted DSP release).
- **Fan**: encounters retired links — and what a retired link *does* is a real product decision, because the fan clicked in good faith.
- **Producer / Operator**: no involvement.

**Synthesis questions answered**:
1. **Shared state conflict**: Lifecycle owns the phase; the link owns its content and routing. No contention.
2. **Trigger chain**: Release event → mutation. Window close → attribution stops counting. Retirement → the link's behaviour changes for every fan who ever shared it. Retirement is the irreversible-feeling one and needs the most care.
3. **Permission intersection**: None significant.
4. **Notification fan-out**: A link about to retire while still receiving meaningful traffic should tell the artist before it dies, not after.
5. **State transition conflict**: A retired link that still has inbound traffic is evidence the retirement policy is wrong. The system should notice its own error rather than silently 404 an audience.

### CX-03: Attribution ↔ the instruments

**Relationship**: The click and the authorisation are the only first-party events this sub-domain
owns. Everything downstream — the stream, the save, the purchase — happens inside a DSP that
reports nothing back at click resolution. Attribution is therefore honest only up to the click,
and every claim past it is inference.

**Role scoping**:
- **Musician**: must not be shown a causal story. They will make real spending decisions on it.
- **Fan**: not a participant — and their click being tracked at all is a privacy fact, not a neutral one.
- **Producer / Operator**: no involvement.

**Synthesis questions answered**:
1. **Shared state conflict**: Attribution reads click/auth events; it writes nothing back. Clean.
2. **Trigger chain**: Click → event → attributed to a campaign if inside a window. No failure path worth designing; a lost click is a rounding error, and pretending otherwise invites the precision theatre 21.04.03 rejects.
3. **Permission intersection**: None.
4. **Notification fan-out**: None.
5. **State transition conflict**: A click arriving after the window closes must not be silently dropped *or* silently counted — see CX-04.
