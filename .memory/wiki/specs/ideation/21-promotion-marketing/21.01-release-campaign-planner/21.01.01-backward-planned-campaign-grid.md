# Feature: Backward-Planned Campaign Grid

> **Number**: 21.01.01
> **Parent**: [Release Campaign Planner](./21.01-release-campaign-planner-index.md)
> **Status**: [PARTIAL]
> **Last updated**: 2026-07-17

## Overview

Enter a release date; the platform derives every deadline that hangs off it — master final,
artwork locked, metadata final, distributor delivery, DSP editorial pitch, press embargo lift,
announce, on-sale, release day, post-release push. The deadlines are computed from channel rules
the platform knows, not typed by the user, which is the entire difference between this and a
blank Trello board.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Full | Sets the release date and campaign type; sees the full derived grid; overrides individual deadlines with a reason; assigns owners to rows; moves the anchor (triggering 21.01.04). Sees the one row that matters most rendered as a hard stop: the DSP editorial pitch window and how many days remain before it is unrecoverable. |
| Producer | Read-only | Sees **only** the rows that bind them — "final master due R−35", "stems + alt mixes due R−35", "any recall of a delivered master must be flagged by R−28". Delivered into the session context they already live in (domain 07), not as a marketing dashboard they must visit. Cannot see the marketing rows, the pitch plan, or the budget. |
| Operator | None | Release-cycle planning is not a venue/studio function. A studio's *own* deliverable deadline reaches them through the Producer lens if they are engineering the session. Event marketing timelines live in 21.08 where the Operator is a full participant. |
| Fan | None | The grid is invisible. Fans see its outputs — an announce, a pre-save link, a release — never the plan. Leakage of an unannounced release date to a follower is a confidentiality failure, not a feature. |

## Behavior

The grid is derived, not authored. A **campaign template** (release type: single / EP / album /
video) supplies a set of **rule-generated rows**, each with an offset or a hard constraint from a
channel's published requirements. The user's inputs are the anchor date, the campaign type, and
the channels in play. Everything else falls out.

Rows carry: label, derived date, source of the rule (so the user can see *why* R−28), owner,
readiness state (from 21.01.02), and whether the deadline is **hard** (missing it forfeits
something unrecoverable) or **soft** (missing it costs momentum).

The hard/soft distinction is the feature's spine. Most campaign deadlines are soft — a late
Instagram post is a shrug. A small number are hard and irreversible, and the product exists to
make those unmissable.

### Happy Path

1. Musician creates a campaign against a release in domain 12 and enters the target release date.
2. Picks campaign type (single / EP / album) and toggles channels in play (DSP editorial, press, radio, playlists, paid).
3. System derives the grid — every dated row, each annotated with the rule it came from and hard/soft status.
4. Musician reviews; assigns owners to rows (Producer gets the master row; self or manager gets the rest).
5. Musician overrides two dates with a stated reason (grid records the override and the divergence from the rule).
6. Grid is saved and becomes the campaign's spine — the calendar (21.01.03), the gate (21.01.02) and the pitch queues (21.02) all read from it.
7. Hard-deadline rows begin emitting escalating reminders as they approach.

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Release date entered is already inside a hard window (e.g. release in 5 days, DSP pitch minimum not met) | Grid computes anyway but marks the unmeetable rows **forfeit**, not "overdue" — the distinction is that no action recovers them | "This release date forfeits DSP editorial pitching. Moving to [earliest viable date] recovers it. Continue anyway?" with both paths live |
| Release date entered is in the past | Rejected at input | Inline validation before the grid is ever computed |
| Channel rule is stale — the platform's stored window no longer matches the DSP's current rule | **Unmodelled.** This is the sub-domain's core liability: we told the user R−28 and they missed a real R−35 | `[PENDING — /ideate-discover Step 5 deepening]` — see Q-01 on the sub-domain index. Rule provenance and staleness display must be designed, not bolted on |
| User overrides a hard deadline to a date past the real window | Override permitted (it is their product) but the row keeps its forfeit marker and the reason is recorded | Warning that this specific override is not recoverable, unlike a soft override |
| Campaign created with no release attached (domain 12 entity does not exist yet) | Grid computes in a provisional state; distributor-dependent rows are unresolvable | Rows dependent on a real release show as blocked with a link to create the release first |
| Two campaigns target the same release | `[PENDING — /ideate-discover Step 5 deepening]` — likely rejected (one campaign per release) but a label running a territory-split campaign is a real counter-case | — |
| Owner assigned to a row is not (or is no longer) a collaborator on the release — e.g. the Producer is removed from the domain-07 project after being given the master row | Row's assignment is preserved but flagged unresolved; reminders fall back to the campaign owner (the Musician) rather than silently dying | Row shows the owner struck through with "no longer on this project — reassign", and the reminder chain reverts to the campaign owner so a hard deadline is never left un-nudged |
| Producer lens surfaces a marketing row (permission leak) | Must never happen — the Producer sees only their bound deliverable rows (master/stems/recall). Any marketing, pitch, or budget row leaking into the Producer surface is a confidentiality failure, not a display bug | Producer sees only their own rows; a leak is treated as a Sev-class defect, not a soft warning. Enforced server-side, not by hiding columns client-side |
| Concurrent edit — Musician and their manager both editing the grid (owners, overrides) at once | Last-write-wins is unacceptable on a grid whose whole value is a correct hard-deadline date; edits are scoped per-row and a stale-row write is rejected | The second writer sees "this row was updated by [name] a moment ago — reload to see it" on the affected row only; unaffected rows save normally |
| Anchor moved after the grid is saved (release date slips) | Recompute is owned by 21.01.04 — every derived row shifts, overrides are re-evaluated against the new anchor, and rows that were forfeit may become recoverable (or vice-versa) | Musician sees a diff of what moved and which hard windows changed status before confirming; the grid is not silently rewritten under them |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Empty | No campaign exists for this release | Empty state: "Set a release date and we'll build the grid" with the single date input |
| Deriving | Anchor + type submitted | Brief computation state; the grid is derived server-side from rule data, not guessed client-side |
| Populated | Grid computed | Full dated grid, hard rows visually distinct from soft, each row showing its rule source |
| Partial | Some channels toggled off, or release entity incomplete | Grid renders with unresolvable rows explicitly blocked rather than silently omitted |
| At-risk | A hard row's dependent asset is red near its deadline | The row escalates; the campaign header carries the risk summary |
| Forfeit | A hard window has passed unmet | Row marked forfeit and frozen — no retry affordance, because there is no retry. Post-mortem note captured for 22 |
| Error | Rule data unavailable | Grid does not render half-computed. A wrong date is worse than no date — this is the one place where failing closed is correct |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | The valuable deadline is not "post on Instagram" but the DSP editorial pitch window, because it is the only one in the campaign whose miss is **unrecoverable at any price** | Domain index rationale ("missing the DSP editorial pitch window forfeits Release Radar for the cycle"); mirrors the problem-statement's core claim that unrepeatable data is what matters | ✅ CONFIRMED — and it sets the design principle: hard/soft is a first-class field, not styling. A planner that treats all deadlines as equal has no thesis. Parallels `meta/problem-statement.md`: "A split captured on the day costs one signature; reconstructed three years later may be unobtainable at any price." Same shape, different artefact. |
| DT-02 | The pitch deadline is not really a marketing deadline — it is **downstream of distribution, which is downstream of the master**. You cannot pitch a track Spotify does not yet have | Reasoning about the actual dependency chain: Spotify for Artists can only pitch an unreleased track already delivered by the distributor and present in Spotify's system | ✅ CONFIRMED — this is why the grid must reach into domain 12 and domain 07 rather than being a self-contained marketing artefact. It also explains why marketing plans fail: the artist controls the pitch date but not the two upstream deliveries it depends on. The grid's real job is making that chain visible. |
| DT-03 | Users will want to author their own deadlines, so the grid should be a flexible task board with templates | Standard product instinct; every competitor does this | ❌ REJECTED — if the user types the deadlines, the platform has contributed nothing and the product is a to-do app with a music skin. The derivation *is* the value. Overrides are supported (D-01 does not make it a prison) but authoring is not the primary path. A user who wants a blank board wants Notion, and should use Notion. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | Hard vs soft deadline is a **first-class field**, not a visual treatment | The product's justification is preventing unrecoverable loss. If the DSP pitch row looks like the "post a teaser" row, we have built decoration. |
| D-02 | Rule provenance is displayed on every derived row | The user must be able to see *why* a date is what it is, both to trust it and to catch us being wrong. It also limits our liability when a rule goes stale — a visible source is auditable. |
| D-03 | The grid fails closed when rule data is unavailable | A confidently wrong deadline causes the exact loss the feature exists to prevent. Rendering nothing is recoverable; rendering R−28 when the truth is R−35 is not. |
