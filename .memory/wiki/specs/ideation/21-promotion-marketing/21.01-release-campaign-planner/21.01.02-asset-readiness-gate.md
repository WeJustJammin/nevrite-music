# Feature: Asset Readiness Gate

> **Number**: 21.01.02
> **Parent**: [Release Campaign Planner](./21.01-release-campaign-planner-index.md)
> **Status**: [PARTIAL]
> **Last updated**: 2026-07-17

## Overview

Every deadline on the grid depends on an artefact existing and being final — the master, the
artwork at spec, the metadata, the credits, the press kit, the video. This feature tracks whether
each one is actually ready, who owns it, and what is blocked while it is not. It converts a
calendar of dates into a calendar of *risks*.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Full | Sees every asset row, its owner, its state, and what deadline it blocks. Chases the ones that are red. Marks their own assets (artwork, bio, photos) ready. Sees the campaign-level risk roll-up: "2 assets red, 1 blocking a hard deadline in 6 days." |
| Producer | Config | Owns and marks state on **their** rows only — master final, stems delivered, alternate/instrumental mixes, ISRC-ready file spec. Can flag a recall on an asset they previously marked final. Cannot see, and is not shown, what marketing deadline their master unblocks — they see "due 2026-09-04", not "the Spotify pitch depends on you". |
| Operator | None | Not an asset owner in a release cycle. A studio that is *also* delivering the master does so through the Producer lens — the row belongs to the person, not the room. |
| Fan | None | No visibility. Asset states are pre-announcement information about unreleased work. |

## Behavior

Asset rows are generated by the grid (each derived deadline declares its dependencies), not
created by hand. Each row has an owner, a state, and a spec — "artwork ready" is not an opinion,
it is 3000×3000 RGB JPEG under the distributor's constraints, and the gate should be able to tell
the difference where the spec is machine-checkable.

The gate's non-obvious job is modelling **un-finalisation**. Assets are marked final and then
revised — a master gets recalled, artwork gets a legal note, a credit is disputed. Because
downstream actions (distributor delivery, pitch sends) may already have fired on the first
"final" signal, the gate must model "was final, no longer is" as a distinct and loud state.

### Happy Path

1. Grid derives deadlines; each declares its asset dependencies; gate rows appear with owners defaulted from the project (domain 07) roles.
2. Musician confirms owners and adjusts.
3. Producer receives their rows in session context — "final master due 2026-09-04".
4. Producer uploads/links the master and marks it final; the gate validates what it can against spec.
5. Gate flips the row green; the dependent grid row clears its blocker; distributor delivery in domain 12 is now unblocked and notifies whoever it blocks.
6. Campaign risk roll-up updates.

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Asset marked final, then recalled after downstream delivery already fired | Row enters **was-final** state; every downstream action that consumed it is flagged for review, not silently re-run | High-severity alert naming the specific downstream actions already taken: "Distributor delivery sent 2026-09-05 used the recalled master." Recovery is a human decision, not an automation |
| Asset uploaded but fails machine-checkable spec (wrong dimensions, wrong sample rate) | Row does not go green; failure is specific | "Artwork is 1400×1400 — distributor requires 3000×3000 minimum" |
| Asset owner is a Producer who has left the project | Row is orphaned; ownership must be reassigned | Orphaned-owner state with reassign action, surfaced in the risk roll-up |
| Asset has no machine-checkable spec (a bio, a press quote) | Gate falls back to human attestation — someone asserts it is ready | Explicit "marked ready by [person] on [date]" rather than a false green implying validation |
| Credits not yet confirmed but press kit needs them | Blocked — the EPK (21.09) cannot claim credits the credit graph has not confirmed | Blocked state linking to domain 02 |
| Two people touch the same row concurrently — Musician reassigns the owner while the outgoing owner is uploading and marking it final | Last-writer-does-not-win silently; the reassignment and the mark-final are different facts on the same row and both are retained. The delivered file is attached to the row regardless of who now owns it; ownership and delivery are separate fields | Musician sees "delivered by [prior owner] before reassignment — confirm the new owner accepts this asset" rather than a lost upload or a clobbered owner |
| Producer attempts to mark a row that belongs to a different owner as final | Rejected — the Producer owns and marks state on **their** rows only (Role Lens). No cross-owner write | Row is not editable for them; it shows the real owner and state read-only, no false affordance |
| Fan or unauthenticated visitor reaches an asset-gate URL for an unreleased campaign | Denied — asset states are pre-announcement information about unreleased work (Role Lens: Fan = None) | Not-found / no-access response that does not confirm the campaign or release exists |
| Asset final but rights not cleared (uncleared sample in the master) | `[PENDING — /ideate-discover Step 5 Must-depth or /write-be-spec]` — the gate probably must not go green on rights grounds, but clearance state lives in domain 09 and the boundary is unresolved (Q-01) | — |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Loading | Gate opened, rows/validation results still resolving | Skeleton rows with owner and due date visible first; state chips resolve as validation returns — a slow spec check never blocks the whole grid from rendering |
| Empty | No grid yet | No gate — the gate has nothing to attach to without deadlines |
| Not started | Row derived, nothing delivered | Grey row with owner and due date |
| In progress | Owner has claimed/started | Neutral state; no false comfort |
| Ready | Delivered + validated (or attested where unvalidatable) | Green, with how it was verified (machine-checked vs attested) shown, not hidden |
| Was-final | Recalled after being marked ready | Loud distinct state — **not** a reversion to "in progress", because downstream consumers already acted |
| At risk | Red or not-started within N days of a hard deadline | Escalated in the roll-up and to the Musician |
| Blocked | Depends on another domain's unmet state (credits, clearance) | Blocked with a link to the blocking artefact, not a generic error |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | A readiness gate needs an **un-final** state, because assets get recalled after downstream systems have already consumed them | Reasoning about failure modes at the 21↔12 intersection: distributor delivery is a one-way door that fires on "master final". A boolean `is_ready` silently loses the fact that a delivery already went out against the old file | ✅ CONFIRMED — this is the difference between a checklist and a gate. `meta/personas.md` names the Producer's worst accidental behaviour as closing a project without capturing what matters; the was-final state is the same class of problem — the system must remember that a fact *changed*, not just what it currently is. |
| DT-02 | "Ready" should be machine-validated wherever the spec is machine-checkable, and honestly labelled as attestation where it is not | Reasoning about what a green tick means. A green tick that means "someone clicked a button" and a green tick that means "the file was validated against the distributor's spec" are different facts, and conflating them means the artist finds out at delivery | ✅ CONFIRMED — show the verification method on the row. This is a small instance of the platform's whole thesis: a verified fact and a claimed fact are not the same object and must not render identically. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | Gate rows are **derived from grid dependencies**, not hand-created | Same principle as the grid itself: if the user has to list what the campaign needs, we have not encoded any knowledge. |
| D-02 | Verification method is displayed, never hidden behind a uniform green tick | An attested "ready" and a validated "ready" carry different risk. Rendering them identically transfers our uncertainty to the artist without telling them. |
| D-03 | The Producer's rows are surfaced in project context, not in the marketing UI | `meta/personas.md`: the Producer's unique constraint is that their work happens in a DAW and any flow requiring them to leave the session will not be used. A marketing dashboard is the definition of leaving the session. |
