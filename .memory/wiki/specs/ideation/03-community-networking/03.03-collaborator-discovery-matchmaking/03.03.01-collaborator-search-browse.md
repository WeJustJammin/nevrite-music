# Feature: Collaborator Search & Browse

> **Number**: 03.03.01
> **Parent**: [Collaborator Discovery & Matchmaking](./03.03-collaborator-discovery-matchmaking-index.md)
> **Status**: [SURFACE]
> **Last updated**: 2026-07-16

## Overview

The pull surface: "I need a pedal steel player who has actually recorded pedal steel, within driving
distance, who is open to a split-based track." Search over people is only worth building because the
platform can answer that query with **evidence** — the credit graph (domain 02) proves the pedal steel
claim, geography and the D-15 latency ceiling bound the distance, and the open-to signal (03.03.03)
answers the appetite half. A search that reads only self-declared tags is a directory, and music
directories fail because everyone claims everything.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Full | Searches for collaborators by instrument/role, genre, geography and appetite. Per personas.md they are also the searched-*for* — and their multi-hyphenate identity means they must be findable under three different queries (as a drummer, as a mixer, as a band member) without maintaining three profiles. |
| Producer | Full | Searches to fill a session seat — "who can play upright bass on Thursday in this city". Per personas.md they are the trust broker and their searches carry the highest downstream value, because the person they find gets a credit that becomes that person's evidence for the next job. |
| Operator | Read-only | Can browse people (an engineer for a room, a dep for a house band) but their real discovery need is *acts to book*, which is domain 04/17. Read-only here reflects that this surface is not built for them; forcing it to serve them would blur it into a booking tool. |
| Fan | None | No access (parent D-05). Per personas.md the Fan has no professional stake; a searchable index of musicians exposed to a consumer population is a contact-scraping and harassment surface with no product justification. Fans discover artists through 03.06 (scenes) and domain 20, which are built for that. |

> **Access levels**: Full · Config · Read-only · Reports · None

## Behavior

Search accepts a need and returns ranked people. The axes that are defensible from what we know:
instrument/role (evidenced by credits, not claimed), genre (evidenced by credit context), geography
(hard-bounded by D-15's latency ceiling for real-time work; softer for asynchronous), appetite
(03.03.03), and graph proximity (03.04.01 — "2 hops from you via your bassist" is a stronger result
than a stranger with better tags).

Ranking is 03.03.02's job; this feature owns the query surface, the result presentation, and the
saved-search/re-findability problem (see the CX-03 note about non-repeatable result sets).

`[PENDING — /ideate-discover Step 5 deepening]` — the axis set cannot be finalised until the skill/role
vocabulary owner is resolved (parent Q-03) and the credit graph's shape is known (domain 02 drilling).

### Happy Path

1. User expresses a need — role, genre, geography, appetite
2. System resolves candidates from the credit graph and open-to signals, respecting blocks and reachability
3. Results render ranked, each showing **why** it matched — the evidence, the path, the distance
4. User opens a profile or initiates contact through the reachability path (03.04.04)

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Thin scene — no candidates within the radius | The domain's stated cold-start reality (200 in a city vs 20,000 scattered) | Widen radius / relax appetite, with an honest statement that the scene is thin rather than a fabricated result list. Padding with bad matches is how a market loses trust in one query |
| Candidate has the skill but no credits evidencing it (a genuine beginner, or new to the platform) | Evidence-first ranking structurally buries newcomers — the cold-start problem applied to people | See DT-02: this is a real fairness defect in the evidence-first design and needs an explicit answer |
| Result is unreachable (inbound policy or block) | A visible dead end is worse than an absence | Filtered out before render, not shown-and-failed |
| Stale open-to signal produces a ghost | Contact goes nowhere; the demand side stops trusting results after two dead leads | Decay handling in 03.03.03 |
| Query names a person, not a need ("find Rob") | This is identity lookup (domain 01), not matchmaking | Should route to global search, not be answered here |
| Searcher games the axes to enumerate the user base (scraping) | An indexed directory of working musicians is commercially valuable to poach | Rate limits; routes to domain 24. Flagged in Q-03 |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Loading | Query submitted | Skeleton results; per CX-03, per-candidate graph traversal makes this genuinely slow at scale |
| Empty | No candidates match | Honest empty state with relaxation CTAs — never padded with poor matches |
| Populated | Candidates found | Ranked list with per-result evidence and path |
| Error | Query failed | Retry; last successful results preserved |
| Partial | Graph traversal timed out; tag-only results available | Degraded results **labelled as such** — an unlabelled degraded result set is a lie about evidence, which is the one thing this product cannot be caught doing |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | Collaborator search is a search problem | The obvious framing | ❌ REJECTED: it is a *trust* problem wearing a search costume. Every point solution already offers filters over self-declared tags; none can answer "has this person actually done this, and would someone I trust vouch for them". The differentiator is not the query surface, it is that the index is built from evidence (D-03) and the graph (03.04.01). Building this as a better search box would reproduce the failed pattern with nicer UI. |
| DT-02 | A domain expert would immediately ask: **what happens to people with no credits yet?** | Adversarial reasoning against the evidence-first design; the cold-start lens | ✅ CONFIRMED as a genuine structural defect, not an edge case. Evidence-first ranking is a rich-get-richer machine: the drummer with 200 credits outranks the excellent 19-year-old with none, forever, because you need credits to get hired and hiring is what produces credits. This is the platform's own thesis turned against its newest users, and it compounds with R-03's rejection of collaborative filtering (same failure). It needs an explicit answer — a newcomer lane, a first-credit accelerator, or an admission that this surface serves established professionals and beginners enter via scenes (03.06). Recorded as Q-01; an agent should not pick. |
| DT-03 | Geography can be a simple radius filter | Naive assumption | ❌ REJECTED: per D-15 the ~25–30 ms desync ceiling makes real-time collaboration physically impossible beyond a few hundred miles — so distance is a *hard constraint* for real-time work and nearly irrelevant for asynchronous work. One radius control cannot express both. The query must know which kind of collaboration is intended before distance means anything, which makes "remote OK / in the room" a primary axis rather than a checkbox. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | Results are ranked on evidence, not self-declared tags | DT-01 — the only thing that differentiates this from every failed music directory. |
| D-02 | Every result states why it matched | Evidence that is not shown is indistinguishable from a guess, and this product's whole claim is that it is not guessing. |
| D-03 | Degraded (tag-only) results must be labelled as degraded | An unlabelled fallback silently converts an evidence claim into a tag search — the one lie this product cannot afford. |
| D-04 | "Remote / in the room" is a primary query axis, not a filter | DT-03 — distance means something entirely different for each, per D-15. |
