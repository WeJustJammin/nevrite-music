# Feature: Breakeven & What-If Modelling

> **Number**: 17.03.02
> **Parent**: [Deal Structures & Economics](./17.03-deal-structures-economics-index.md)
> **Status**: [SURFACE]
> **Last updated**: 2026-07-16

## Overview

The calculator that answers "what does this deal actually pay if 300 people come?" before anyone
agrees to it. It evaluates the same expression the settlement engine will evaluate later
(17.09.01) — which is what makes it trustworthy, and what makes a deal's outcome knowable on the day
it is offered rather than discovered in a back office months afterwards.

**Merged** from sweep candidates 03 and 15, which described the same calculator twice (index D-01).

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Full | Models what an offer pays them at realistic attendance **before approving it** (17.02.03). This is the direct countermeasure to the persona's documented worst accidental behaviour — signing terms they don't understand. Their model uses their own cost assumptions (crew, transport, commission), which the promoter never sees. |
| Producer | None | No role. |
| Operator | Full | Models the room's own breakeven before offering — at what attendance does this deal stop making money for the venue. Their model uses their cost assumptions (staffing, security, marketing spend), which the artist never sees. |
| Fan | None | Never visible. |

## Behavior

The modeller evaluates a deal expression (17.03.01) across a range of attendance levels and shows the
outcome for **both** sides at each level, using each side's own private cost assumptions.

The critical property: **the modeller and the settlement engine are the same evaluator.** If they
differ by even an edge case, the product has told someone a number it will not honour — which is
worse than not modelling at all, because they believed it.

Modelling is private and speculative. Nothing is notified, nothing is stored on the deal, and — per
the sub-domain's rejected pair R-01 — a model can never mint a new deal type.

### Happy Path

1. Operator parameterises a deal structure (17.03.01) while composing an offer.
2. Operator adds their private cost assumptions — staffing, security, marketing.
3. Modeller renders outcomes across an attendance range: at 150 the room loses money, at 280 it
   breaks even, at 400 the versus clause flips and the artist takes the percentage.
4. Operator adjusts the guarantee and watches the breakeven move.
5. Offer is sent (17.02.01) rendering the outcomes so the artist reads the same consequences the
   Operator modelled — even though each side's private cost assumptions remain their own.

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Deal contains a free-text term outside the grammar | The model **silently omits it** and the number is wrong. The silence is the danger (CX-01) | `[PENDING — /ideate-discover Step 5 deepening]` — should be a visible "this deal has unmodellable terms" flag |
| Deal is part of a cross-collateralized run | Per-show breakeven is **meaningless** — the modeller must switch to run basis or it lies confidently (CX-03) | Basis must be labelled; per-show numbers marked provisional |
| Modeller and settlement engine disagree | The product told someone a number it will not honour | Must not be reachable — one evaluator, not two (D-01) |
| Attendance assumption has no basis | The user guesses; the guess drives the deal | Draw history (17.11.01) should seed the range rather than a blank field |
| Artist models with no cost assumptions | Sees gross-looking numbers and thinks they're take-home; commission and crew come off later | `[PENDING — Step 5]` — a model that flatters is worse than no model |
| Both sides model the same deal and get different answers | Correct and expected — different private costs, same deal | Each side sees only their own; neither is "wrong" |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Empty | No deal parameterised yet | Prompt to select a deal structure first |
| Modelled | Expression + assumptions present | Outcome curve across attendance; breakeven marked |
| Provisional | Deal is in a cross-collateralized run | Run-basis outcomes; per-show numbers explicitly labelled provisional |
| Degraded | Deal contains unmodellable free-text terms | `[PENDING — Step 5]` — outcome shown with an explicit incompleteness warning |
| Seeded | Draw history available for this artist × market | Attendance range pre-populated from 17.11.01 with its confidence |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | The modeller is a convenience calculator | Feature-priority instinct — it looks like a spreadsheet replacement | ❌ REJECTED: it is the **comprehension layer on an information asymmetry**. The domain index states settlement asymmetry "runs one direction" — the promoter knows the room's economics and the artist does not. Modelling before agreeing is what lets the artist in `meta/personas.md` stop signing things they don't understand. It is a fairness mechanism wearing a calculator's clothes. |
| DT-02 | Modeller and settlement engine can be separate implementations | Natural separation — one is interactive, one is a batch computation | ❌ REJECTED, emphatically. If they diverge by any edge case, the product has quoted a number it will not honour, and the user believed it. **Two evaluators is a trust bug, not a performance optimisation.** One evaluator, two call sites. |
| DT-03 | A modeller with no attendance data is still useful | The obvious build order — ship the calculator, add data later | ⏳ DEFERRED, leaning negative. A blank attendance field asks the user to guess, and the guess drives the deal — the modeller then launders a guess into a confident-looking curve. Draw history (17.11.01) is what makes the range honest, and it is a settlement byproduct that will not exist at cold start. **The modeller may be weaker than it looks until the settlement corpus exists** — which has MoSCoW consequences the owner should see (Q-03). |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | One evaluator serves both modelling and settlement | Divergence means quoting a number the product will not honour — a trust bug, not an optimisation (DT-02). |
| D-02 | Each side's cost assumptions are private; the deal expression is shared | This mirrors reality — neither side opens their books — while still letting both read the same deal terms. |
| D-03 | Modelling never writes to the deal | A speculative what-if must not mint a deal type or create a run (sub-domain R-01, R-02). |
