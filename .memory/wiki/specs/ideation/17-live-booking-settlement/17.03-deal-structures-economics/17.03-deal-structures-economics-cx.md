## Cross-Cut Details

### CX-01: Deal Term Grammar ↔ Breakeven & What-If Modelling

**Relationship**: The modeller evaluates expressions built from the grammar. This is a hard
containment, not a convenience: **anything the grammar cannot express, the modeller cannot model and
the settlement engine cannot compute.** The three share one vocabulary by construction, which is why
the grammar's closed-vs-open question (index Q-01) sets the ceiling on the entire domain's
automation.

**Role scoping**:
- **Operator**: models the room's breakeven from the same terms they will offer.
- **Musician**: models what the offer actually pays them at realistic attendance before approving it
  — directly answering the `meta/personas.md` failure of signing terms they don't understand.
- **Producer**: not affected.
- **Fan**: not affected.

**Synthesis questions answered**:
1. **Shared state conflict**: None — the grammar is platform-owned read-only vocabulary. Neither
   side mutates it, so there is nothing to merge.
2. **Trigger chain**: Grammar → expression → model. If a term is free text (17.02.01 DT-03), the
   model silently omits it and understates or overstates the outcome. **The failure is silent, which
   is the dangerous part.**
3. **Permission intersection**: Both sides model the same expression; neither sees the other's
   assumptions (expenses, comp policy) — which is precisely the information asymmetry the domain
   index says runs one direction at settlement.
4. **Notification fan-out**: None — modelling is private and speculative by design.
5. **State transition conflict**: None; the modeller is a pure evaluator with no state.

### CX-02: Deal Term Grammar ↔ Multi-Show Deals & Cross-Collateralization

**Relationship**: A multi-show deal is not a collection of single-show deals. It introduces terms
whose **scope is the run**, not the date — "guarantee against 85% of the aggregate net across 12
dates". These terms have no per-show meaning at all, so the grammar must carry a scope dimension
rather than assuming every term resolves within one show.

**Role scoping**:
- **Operator**: a promoter buying a run negotiates run-level terms; a single room in someone else's
  run may not even know it is cross-collateralized.
- **Musician**: bound across every date; the artist's exposure is the run, not the night.
- **Producer** / **Fan**: not affected.

**Synthesis questions answered**:
1. **Shared state conflict**: The run is an entity above the shows. Ownership is genuinely unclear
   when a run spans multiple independent Operators — `[PENDING — /ideate-discover Step 5 deepening]`.
2. **Trigger chain**: Run terms → per-show allocation → aggregate settlement. If one show cancels,
   every other show's settlement changes retroactively. This is the mechanic's whole point and its
   whole difficulty.
3. **Permission intersection**: An Operator of one date in a cross-collateralized run may be
   contractually entitled to see aggregate performance they have no commercial right to see. Real
   and unresolved.
4. **Notification fan-out**: A cancelled or under-performing date must notify the run, not just the
   date.
5. **State transition conflict**: Yes, severely — a show cannot reach final settlement while the run
   is open (CX-03). Per-show settlement finality and run-level truth are in direct conflict.

### CX-03: Multi-Show Deals & Cross-Collateralization ↔ Breakeven & What-If Modelling

**Relationship**: Cross-collateralization makes per-show breakeven **meaningless**. Show 3 of 12 has
no independent breakeven when losses pool across the run — a sold-out Wednesday can pay for a dead
Monday, and the Wednesday's own settlement number is a fiction until the Monday is known. The
modeller must switch basis or it produces confidently wrong answers, which is worse than refusing.

**Role scoping**:
- **Musician**: sees run-level economics; per-date numbers are provisional and must be labelled so.
- **Operator**: the run's promoter models the run; a single-date Operator inside someone else's run
  models their own date normally and is unaffected.
- **Producer** / **Fan**: not affected.

**Synthesis questions answered**:
1. **Shared state conflict**: Provisional per-show numbers vs final run numbers coexist for the
   whole run. Both must be visible and clearly distinguished, or someone will bank a provisional.
2. **Trigger chain**: Any show's actuals → recompute run → every other show's provisional number
   moves. Async fan-out across dates that may be months apart.
3. **Permission intersection**: See CX-02 — aggregate visibility across independent Operators is
   unresolved.
4. **Notification fan-out**: Recomputation moves numbers the artist may already have seen and
   believed. Silent recomputation is a trust failure.
5. **State transition conflict**: Direct. **A show cannot be finally settled while the run is open**
   — which contradicts 17.09's per-show settlement finality. This is the sharpest unresolved
   structural conflict in the domain and is flagged as an Open Question at domain level.

## Rejected Pairs

| # | Source | Target | Reason for Rejection |
|---|--------|--------|---------------------|
| R-01 | Breakeven & What-If Modelling | Deal Term Grammar (write direction) | Rejected. Modelling **reads** the grammar and never writes it. A tempting product move is "save this model as a new deal type", which would let users mint grammar — but that converts a closed vocabulary into an open expression language by the back door and silently destroys settlement automation (index Q-01). The write direction must not exist unless Q-01 is answered "open", and then it is a different design entirely. |
| R-02 | Breakeven & What-If Modelling | Multi-Show Deals (creation direction) | Rejected as an interaction. Modelling a run does not create one — a run is created by a negotiated multi-show offer (17.02), not by someone exploring numbers in a calculator. The real edge runs the other way (CX-03): an existing run changes how modelling must work. Modelling → creation would let a speculative what-if bind an artist across 12 dates. |
