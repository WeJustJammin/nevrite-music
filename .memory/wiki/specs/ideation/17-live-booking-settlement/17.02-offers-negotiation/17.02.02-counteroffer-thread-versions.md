# Feature: Counteroffer Thread & Version History

> **Number**: 17.02.02
> **Parent**: [Offers & Negotiation](./17.02-offers-negotiation-index.md)
> **Status**: [SURFACE]
> **Last updated**: 2026-07-16

## Overview

The negotiation itself — an ordered thread of complete offer versions, where each counter is a whole
new document rather than a field edit, and every version is preserved. The version history is not an
audit convenience: it is the evidentiary record of what was actually agreed, which is the exact class
of fact that `meta/problem-statement.md` says currently gets reconstructed from memory years later at
the moment it becomes contested.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Full | Counters via their agent, or directly when self-booking. Sees every version side-by-side with what changed and — critically — **what was traded for what**. Their real question is never "which fields changed" but "did we give up the merch cut to get the guarantee up, and was that worth it?" |
| Producer | None | No role. |
| Operator | Full | Counters, compares versions, sees the whole thread. Uses version history to remember why a term is where it is — three weeks and forty offers later, nobody remembers why this room gave up its merch cut. |
| Fan | None | Never visible. |

## Behavior

Each counter produces a **complete new version**, not a diff applied to a mutable object. This is
deliberate and non-obvious: live deals are traded as bundles — a promoter drops the guarantee by £500
and simultaneously gives back the merch cut. Field-level mutation would present that as two unrelated
edits and destroy the trade's meaning (CX-01).

Versions are compared as whole documents with the *trade* surfaced, not just the deltas.

Drafts are private per side (index Q-03); the thread is shared. Both sides may compose a counter
simultaneously, producing sibling versions — the product must not pretend one is authoritative.

Every version is immutable and permanent. The thread survives the deal.

### Happy Path

1. Musician's agent receives v1 (from 17.02.01) and opens it against the artist's targets.
2. Agent composes a counter — raises the guarantee, concedes the merch cut — producing v2.
3. System renders v2 against v1 showing the trade as a trade, not as two field changes.
4. Operator counters with v3; the thread continues.
5. A version is accepted (gated by 17.02.03). Every prior version remains permanently readable.

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Both sides counter simultaneously | Server-assigned version ordering; both survive as **siblings**, neither overwrites | Both versions shown as concurrent; the parties must resolve which they're negotiating from |
| Counter arrives after an approval was granted on an earlier version | Prior approval is invalidated (CX-02) — the v2/v4 failure this design exists to prevent | Approvers notified that their approval no longer applies, naming the version |
| Trivial counter (typo fix) invalidates full board approval | Punitive — but auto-judging triviality is how the v2/v4 bug returns | `[PENDING — /ideate-discover Step 5 deepening]` — genuinely unresolved (Q-01) |
| Negotiation moves to a phone call and returns with "agreed" | The thread has a hole exactly where the decision happened | `[PENDING — Step 5]` — see DT-03 |
| Counter offered after the offer expired | Refused; expiry killed the thread (17.02.04) | "This offer expired on {date}. Ask for a new one." |
| Thread abandoned with no accept or reject | Common; deals die silently | `[PENDING — Step 5]` — whether threads auto-close is undecided |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Open | v1 sent | Latest version + full history; whose turn it is |
| Countered | New version | Diff against parent with the trade surfaced |
| Forked | Simultaneous counters | Two sibling versions, neither authoritative |
| Pending approval | Version sent for entity approval | Version locked from further countering by that side |
| Accepted | Approved version accepted | Thread closed; deal record created; history frozen |
| Dead | Expired, withdrawn, or rejected | Read-only history retained permanently |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | A counteroffer is an edit to the offer | Naive CRUD modelling | ❌ REJECTED: it is a new document. Deals are traded as bundles — guarantee down, merch cut back — and field-level mutation renders that as two unrelated edits, destroying the negotiation's meaning (CX-01). It also destroys the evidence: "what did we actually agree" needs the document, not a change log. |
| DT-02 | Version history is an audit nicety | Feature-priority instinct | ✅ CONFIRMED as **thesis-critical**, not a nicety. `meta/problem-statement.md`: the defining failure is that facts get reconstructed from memory at the moment they become contested. A live deal's terms are exactly such a fact, and the version thread is provenance-at-source applied to booking. This is why the feature is `must` despite looking like table stakes. |
| DT-03 | The thread captures the negotiation | Optimistic modelling | ❌ REJECTED: **the decisive moves happen on the phone.** An agent and a promoter agree the real deal in a two-minute call and the thread receives only the ratified outcome. The system therefore captures the *result* and not the *reasoning* — and a version with no visible antecedent is exactly where a later dispute lives. A domain expert would expect this hole. The honest options are to accept it, or to make logging a verbal agreement cheap enough that it happens. Unresolved (Q-02). |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | Every counter is a complete new version, never a field mutation | Deals are traded as bundles; mutation destroys the trade's meaning and the evidentiary record (DT-01). |
| D-02 | Versions are immutable and permanent; the thread outlives the deal | The thread is the provenance artefact for the deal's terms (DT-02) — the same argument that makes split capture the platform's wedge. |
| D-03 | Simultaneous counters produce siblings, not an overwrite | Neither side's counter is authoritative; pretending otherwise silently discards a real negotiating position. |
| D-04 | Drafts are private per side; only sent versions enter the thread | Private drafting is universal practice; a shared-draft model would be a fantasy nobody would use. |
