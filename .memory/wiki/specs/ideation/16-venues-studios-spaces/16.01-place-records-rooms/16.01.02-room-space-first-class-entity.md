# Feature: Room / Space as First-Class Child Entity

> **Number**: 16.01.02
> **Parent**: [Place Records & Rooms](./16.01-place-records-rooms-index.md)
> **Status**: [SURFACE]
> **Last updated**: 2026-07-16

## Overview

The bookable, spec-carrying unit inside a place. A venue is not one thing — it is a 400-cap main
room and a 80-cap basement with different stages, different curfews and different deals. A studio
is Live Room A, the vocal booth, and the mix suite. **The room, not the place, is what has a
spec, an availability calendar, and a rate.**

This is the structural spine of the domain. Getting it wrong collapses everything downstream:
if the spec hangs off the place, a band books "the venue" and arrives to the wrong room; if the
calendar hangs off the place, a studio cannot sell its mix suite while a band is tracking.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Operator | Full | Creates and names rooms, attaches each room's spec (16.02/16.03), sets per-room availability, rates and booking posture. Declares which rooms are **mutually exclusive** (booking the live room blocks the control room). |
| Musician | Read-only + suggest | Browses and books a specific room, not a place. Compares rooms within a place ("is the basement big enough?"). Can suggest edits to room specs. |
| Producer | Read-only + suggest | The heaviest reader — the room choice IS the creative decision. Reads acoustics, signal chain, and which rooms can run simultaneously. Highest-authority editor on studio room specs. |
| Fan | Read-only | Sees the room name on a ticket ("Main Room" vs "Basement") and its accessibility profile. Does not see specs, rates, or availability. |

## Behavior

A room belongs to exactly one place record and carries: name, type (live room / control room /
booth / stage / rehearsal room / lockout), the spec sheet appropriate to its type, capacity
(16.02.01), photos (16.01.03), accessibility (16.01.04), a rate card (16.06.07) and an
availability calendar (16.06.01).

**Rooms interlock.** The critical modelling fact is that rooms are not independent resources: a
control room and its live room are usually one booking; a venue's main room and its bar may share
a PA; two rehearsal rooms may share a load-in corridor with one lift. Room-to-room exclusion and
dependency rules are what make compound booking (16.06.05) and conflict prevention (16.06.01)
correct rather than merely plausible.

### Happy Path

1. Operator claims a place, is prompted "how many bookable rooms?"
2. Operator adds Room A: name, type, capacity; system attaches the spec sheet for that room type
3. Operator adds Room B; system asks whether A and B can be booked at the same time
4. Operator declares A+B mutually exclusive (shared control room)
5. Each room gets its own calendar; booking A now blocks B automatically (16.06.01)

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Place has exactly one room (most rehearsal rooms, most small venues) | A default room is auto-created and the room layer is hidden in the UI — the Operator never learns the word "room" | Place-level booking; room is invisible plumbing |
| Room is reconfigurable (seated 200 / standing 400) | Configuration is a property of capacity (16.02.01), not a separate room — same physical space, same calendar | One room, capacity varies by config |
| Two rooms share a PA — both bookable, but not both loud | `[PENDING — Step 5]` — exclusion is currently binary (can/cannot co-book). A "can co-book but degraded" state may be needed | — |
| Operator deletes a room with future bookings | Blocked. Room can be retired (no new bookings) but not removed while bookings exist | "3 bookings use this room — retire it instead?" |
| Room is subdivided or merged (studio knocks through) | `[PENDING — Step 5]` — likely retire + create, but the gig/session history attribution is unresolved | — |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Draft | Room created, spec incomplete | Not bookable; Operator sees a spec-completeness meter |
| Live | Spec meets the minimum bar, posture set | Bookable/enquirable per 16.06.06 |
| Blocked | Co-booked exclusive sibling room is reserved | Calendar shows unavailable with reason ("Live Room is booked") |
| Retired | Operator retires the room | Historical bookings intact; no new bookings; hidden from search |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | Rooms are independent bookable resources | The obvious model — each room gets a calendar, done | ❌ REJECTED: rooms interlock physically. A live room and its control room are one booking. Independent calendars produce a double-booking of a shared resource — which is precisely the Operator's stated switching trigger ("a costly double-booking"). Room exclusion/dependency rules are mandatory, not an enhancement. |
| DT-02 | The room layer will confuse single-room Operators | A rehearsal room owner does not think "I have one room" — they think "I have a room" | ✅ CONFIRMED: the abstraction must be invisible at N=1. Auto-create a default room and never surface the concept. The Operator persona works "on a phone at a loading dock" — hierarchy they didn't ask for is a defection trigger. |
| DT-03 | Reconfigurable capacity needs separate room records | Seated vs standing feel like different products (different capacity, different ticket map) | ❌ REJECTED: same physical space, same calendar, same load-in, same curfew. Only capacity and the ticket map change. Modelling it as two rooms would let both be booked at once — a physical impossibility the data model would happily allow. Configuration belongs to capacity (16.02.01). |
| DT-04 | Room specs are what 19 Ticketing needs for a seat map | Ticketing needs to know where people stand/sit | ⏳ DEFERRED: the room carries capacity and configuration; whether it carries a **geometric seat map** is a 19 question. Flagged as a cross-domain touchpoint — 16 should not grow a seating-chart editor without 19 confirming it owns it. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | The **room** is the spec-carrying, calendar-carrying, bookable unit | A place is a container; everything transactable is per-room |
| D-02 | Rooms carry explicit exclusion/dependency rules | Rooms interlock physically; independent calendars produce real double-bookings (DT-01) |
| D-03 | The room layer is invisible when a place has one room | Do not tax the single-room Operator with an abstraction they didn't ask for (DT-02) |
| D-04 | Reconfiguration is a capacity property, not a second room | One physical space cannot be booked twice (DT-03) |
