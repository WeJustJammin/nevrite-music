# Feature: Place Record & Type Taxonomy

> **Number**: 16.01.01
> **Parent**: [Place Records & Rooms](./16.01-place-records-rooms-index.md)
> **Status**: [SURFACE]
> **Last updated**: 2026-07-16

## Overview

The canonical record for a physical music place — a venue, a recording studio, a rehearsal
facility, or a trade/facility (luthier, rental house, pressing plant) — and the taxonomy that
decides which technical spec sheet a record carries. A place record exists independently of
whether anyone has claimed it: most records are born unclaimed and seeded from public data
(16.05.01), which is what gives the registry coverage before it has a single transaction.

The type is not cosmetic. `type=venue` attaches the venue spec (16.02), `type=studio` attaches
the studio spec (16.03) — and the platform's most common real-world record is a place that is
**two types at once** (a venue with a tracking room upstairs, a studio that hosts small shows).

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Operator | Full | Owns the record once claimed (16.05.02). Sets name, type(s), address, contact, description, opening posture. Can dispute a community edit to any field. Cannot delete a record — only mark it closed (16.01.05), because the record carries other people's gig history. |
| Musician | Read-only + suggest | Reads the record to decide whether to enquire. Can suggest edits (16.05.03) to any field and can create a place record that does not yet exist (a rehearsal room they use). Cannot set the commercial fields — those are Operator-only even on an unclaimed record. |
| Producer | Read-only + suggest | Same as Musician. Additionally the highest-value editor on studio-type records — they are in the room and know the record is wrong. |
| Fan | Read-only | Sees venue-type records only, as a show-discovery surface (where is this gig, how do I get there, is it accessible). Studio, rehearsal and trade records are not surfaced to Fans — there is nothing there they can act on. |

## Behavior

A place record is an **entity**, not a listing. It has: identity (name, aliases, former names),
location (address, geo point, what3words-grade precision for load-in), type set, one or more
rooms (16.01.02), a claim state (unclaimed / claimed / contested), and per-field provenance
(16.05.03). Every field carries where it came from and when it was last verified.

Type is a **set, not an enum** — the record's type set determines which spec sub-documents exist.
A place typed `[venue, studio]` carries both 16.02 and 16.03 spec sheets against its rooms.

### Happy Path

1. Musician searches for a room; the place does not exist in the registry
2. Musician creates a record: name, address, type — 3 fields, no spec required
3. System geocodes, runs duplicate detection (16.05.07), and shows near-matches before accepting
4. Record is created `unclaimed`, provenance `user-contributed`, freshness clock starts
5. Record is publicly visible and indexable; the Operator later discovers and claims it (16.05.02)

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Place already exists under a former name ("The Boileroom" → "The Bunker") | Duplicate detection (16.05.07) matches on geo + alias, offers merge instead of create | "A place at this address already exists — is this it?" with the existing record |
| Venue moves address, keeps name | New location is a **new record**, old record marked relocated and linked — gig history stays attached to the building where it happened | Both records visible, cross-linked "moved to / moved from" |
| Two types, one address, different owners (studio subleases a room inside a venue) | `[PENDING — /ideate-discover Step 5 deepening]` — likely two records with a containment link, but the claim model for a contained record is unresolved | — |
| Home studio at a residential address | Address precision is reduced to area-level until booking is confirmed | "Exact address shared after booking" |
| Place is a pop-up / non-permanent (warehouse show, festival site) | `[PENDING — Step 5]` — the record model assumes permanence; temporary places may not belong here at all | — |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Unclaimed | Seeded or user-created, no verified owner | Public record + "Do you run this place? Claim it" banner |
| Claimed | Ownership verified (16.05.02) | Verified badge, Operator-controlled fields locked to suggestions |
| Contested | 2+ claims, or an owner disputes a community edit | Record stays live; disputed fields show last-agreed value + a dispute marker |
| Closed | Marked closed (16.01.05) | Read-only historical record; not bookable, still linked from past gigs |
| Merged | Resolved as a duplicate | Redirects to the surviving record |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | Type should be an enum — a place is a venue OR a studio | Simplest data model; matches how the candidate list was written | ❌ REJECTED: the multi-hyphenate fact (`personas.md`) is not only true of humans. Rooms are multi-hyphenate too — a venue with a tracking room, a studio that does Sunday shows, a rehearsal facility with a live room. An enum forces the Operator to create two records for one building, which splits their calendar — the exact failure the Operator persona is escaping. Type is a set. |
| DT-02 | "Studio Records" (candidate 02) is a distinct thing from a venue record | Sweep candidate list | ❌ REJECTED: a studio record is a place record with `type=studio`. Identity, address, claim, provenance, decay and rooms are identical. Only the **spec sheet** differs — so only the spec sheet is modelled separately (16.03). Folded the record half into this feature. |
| DT-03 | Deleting a record must be impossible for a claimed Operator | Anti-persona: Operator "misrepresents the room's specs"; and a hostile Operator could delete a record carrying bad reviews or a gig history that contradicts them | ✅ CONFIRMED: the record carries third-party facts (who played here, 16.05.06 harvested data). Deletion is a data-integrity attack surface. Closure, not deletion — and closure is reversible. |
| DT-04 | A relocated venue keeps one record | Naive continuity — "it's the same business" | ❌ REJECTED: the entire value of this domain is that the record describes a **physical room** — load-in, capacity, acoustics, curfew. None of that survives a move. A record is a building, not a business. The business continuity is a link, and the org lives in domain 01. |

## Cross-Cut Notes

- Touches **01 Identity, Profiles & Organizations** ([../../01-identity-profiles-organizations/](../../01-identity-profiles-organizations/)) — a claimed place is owned by an **org**, not a person. Multi-site operators (a 4-room group) are one org with N place records.
- Touches **16.05 Curation & Data Integrity** ([../16.05-curation-provenance-data-integrity/](../16.05-curation-provenance-data-integrity/)) — every field on this record is subject to seeding, claim, suggested edits, provenance and decay.
- Touches **16.01.02 Room as First-Class Entity** ([./16.01.02-room-space-first-class-entity.md](./16.01.02-room-space-first-class-entity.md)) — composition; specs and bookings hang off rooms, not places.
- Consumed by **17 Live Booking**, **18 Show Production**, **19 Ticketing** — all three resolve a show to a place record.

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | Type is a **set**, not an enum | A building can be a venue and a studio; forcing two records splits the Operator's calendar (DT-01) |
| D-02 | Candidate 02's "Studio Records" folded into this feature | A studio record is a place record with `type=studio` — only the spec sheet is studio-specific (DT-02) |
| D-03 | No hard delete; closure only | The record carries third-party gig history and harvested facts (DT-03) |
| D-04 | A record is a building, not a business | Relocation creates a new record with a link — nothing physical survives a move (DT-04) |
