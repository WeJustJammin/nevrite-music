# Feature: Place Data Seeding & Ingestion

> **Number**: 16.05.01
> **Parent**: [Curation, Provenance & Data Integrity](./16.05-curation-provenance-data-integrity-index.md)
> **Status**: [SURFACE]
> **Last updated**: 2026-07-16

## Overview

Populating the registry from public sources before a single Operator has signed up — OpenStreetMap,
Wikidata, MusicBrainz, licensing registers, PRO registers — so that a musician searching for a room
in Leeds on day one finds rooms in Leeds rather than an empty page.

This is the domain's answer to the cold-start problem, and the domain index names it as one of the
six capabilities justifying domain status: **the unit of value is coverage and accuracy at zero
transactions.** An empty directory has no users, and users are what make it non-empty. Seeding is
the only way out of that loop.

It is also the feature with the most dangerous non-obvious constraint: **source licences**.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Operator | Read-only (indirect) | Never sees this feature. Experiences its output: they discover a record for their own venue that they did not create, seeded from public data, waiting to be claimed (16.05.02). That discovery is the domain's primary acquisition path. |
| Musician | Read-only (indirect) | Experiences it as a registry that is not empty. Sees seeded records marked as unverified — a seeded record must never masquerade as a curated one. |
| Producer | Read-only (indirect) | Same. Studio seeding is thinner than venue seeding — public datasets know where venues are and mostly do not know where studios are. |
| Fan | Read-only (indirect) | Sees seeded venue records on show pages. Same unverified marking. |

## Behavior

Ingestion runs per source, mapping external records to place records (16.01.01) with **per-field
provenance** — every seeded field carries which dataset it came from, when, and under what licence.
Records land unclaimed, with freshness clocks that start already running (16.05.05) and duplicate
detection (16.05.07) applied both within and across sources.

Source classes, with sharply different licence profiles:
- **OpenStreetMap** — the best geographic coverage of venues that exists. **ODbL: share-alike.**
- **Wikidata** — CC0, no obligations, decent coverage of notable venues, poor on small rooms
- **MusicBrainz** — CC0 for core data; carries venue/place entities linked to release data
- **Licensing / PRO registers** — public records, patchy machine access, variable terms per territory

The ODbL question is not a detail. Share-alike may create obligations on a derived database, and the
answer determines whether the best venue dataset in the world is usable at all. **That analysis is a
legal/architecture decision and is routed out of the product to `/create-prd` — it is not this
feature's to answer, only to flag loudly.**

`[PENDING — /ideate-discover Step 5 deepening]` — per-source field mapping, refresh cadence, and
whether sources are re-ingested (and if so, how re-ingestion interacts with community edits made
since).

### Happy Path

1. Ingestion pulls venues in a target city from a compatible source
2. Each record maps to a place record: name, address, geo, type — nothing more, because nothing more is reliable
3. Duplicate detection (16.05.07) runs within the source and against existing records
4. Records land unclaimed, provenance-tagged, freshness clock already running
5. An Operator searches for their own venue, finds it, and claims it (16.05.02) — the acquisition loop

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Source licence is share-alike (ODbL) | **Blocked pending a legal decision routed to `/create-prd`.** Not this feature's call | — |
| Source record is a venue that closed in 2019 | Lands unclaimed, never verified, decays to the floor (16.05.05); presented as unverified, never as open (16.01.05 DT-03) | "Never verified — may no longer exist" |
| Source has a pub with occasional live music tagged as a venue | Over-inclusion. Precision vs recall is a real trade-off and OSM's `amenity=pub` is not a music venue | `[PENDING — Step 5]` |
| Same venue in three sources with three spellings and two addresses | Cross-source duplicate detection (16.05.07) — the load-bearing dependency; without it, seeding produces garbage | Merge candidates |
| Community edits a seeded field, then the source is re-ingested | **Re-ingestion must never overwrite a human edit.** Provenance ranking exists precisely for this | `[PENDING — Step 5]` |
| Source data is wrong (bad geocode, 200m off) | Seeded facts are claims with a weak provenance class, correctable by anyone (16.05.03) | Low-confidence marker |
| A venue does not want to be listed | `[PENDING]` — an unclaimed record for a real business created without their involvement. Delisting rights are a genuine question, not a hypothetical | — |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Seeded | Ingested, unclaimed, unverified | Record + "unverified, from public data" + claim CTA |
| Enriched | Community added fields to a seeded record | Mixed provenance visible per field |
| Claimed | Operator claimed it (16.05.02) | Provenance history retained; record now owner-controlled |
| Merged | Duplicate resolved (16.05.07) | Redirects to survivor |
| Rejected | Ingested then judged not a music place | Suppressed; the rejection is remembered so re-ingestion does not resurrect it |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | Seeding is a data-loading task — architecture, not product | It looks like an ETL job, and the classification gate asks exactly this | ⚠️ SPLIT, deliberately. The **pipeline** (scheduling, fetching, mapping, retries) is architecture and is routed out. What stays is genuinely product: *which* sources, *what a seeded record looks like to a user*, whether a seeded record can masquerade as verified (no), what happens when a human edit meets a re-ingest (the human wins), and the delisting question. Those are product decisions with user-visible consequences, and none of them are ETL. |
| DT-02 | Seeding is a growth hack | It fills the directory before there are users | ❌ REJECTED as a framing — it is the **acquisition mechanism itself**. The Operator does not sign up and create a record; they *discover a record for their own venue that already exists* and claim it (16.05.02). Seeding and claiming are one loop, and the loop is the domain's entire cold-start answer. Calling it a hack understates it: the domain index says the unit of value is coverage at zero transactions. |
| DT-03 | Any public dataset can be ingested | It is public data | ❌ **REJECTED — the most dangerous assumption in this domain.** ODbL (OpenStreetMap) is share-alike, and OSM is simultaneously the best venue geodata that exists and the source with the heaviest obligations. Whether share-alike reaches a derived database that mixes OSM geo with community-contributed specs is a real legal question with a real answer, and getting it wrong contaminates the platform's core dataset. Routed to `/create-prd` as a **not-product legal/architecture decision** — flagged loudly rather than assumed away. |
| DT-04 | Re-ingestion keeps the data fresh | Sources update; pull the updates | ❌ REJECTED as stated: re-ingestion that overwrites human edits destroys the exact value the domain creates. A community-corrected load-in beats OSM's guess in every case. Provenance ranking must make source data the **weakest** class, never the winner. Re-ingestion may add new records and fill empty fields; it may never overwrite a human. |
| DT-05 | Studios can be seeded like venues | Same mechanism, different type | ❌ REJECTED: public datasets know where venues are (they are public-facing businesses with licences and addresses) and largely do not know where studios are (many are residential, unlisted, and deliberately private). Studio supply must be acquired, not ingested — which means the cold-start answer is **venue-shaped only**, and 16.03's supply has no seeding story at all. That asymmetry is a real strategic finding, not a data gap. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | Seeding + claiming is **one acquisition loop**, not a growth hack | The Operator discovers their own record rather than creating one — the domain's cold-start answer (DT-02) |
| D-02 | Re-ingestion may add and fill; it may **never** overwrite a human edit | Source data is the weakest provenance class; a corrected load-in beats OSM's guess always (DT-04) |
| D-03 | A seeded record must never present as verified | It is an unverified claim from a third-party dataset, and much of it is years stale (16.01.05 DT-03) |
| D-04 | ODbL share-alike analysis routed to `/create-prd` as a legal/architecture decision | The best venue dataset carries the heaviest obligations; not a product call to make here (DT-03) |
| D-05 | Studios cannot be seeded — supply must be acquired | Public data knows venues; it does not know studios. The cold-start answer is venue-shaped only (DT-05) |
