# Feature: Compound / Multi-Resource Booking

> **Number**: 16.06.05
> **Parent**: [Space Booking & Reservations](./16.06-space-booking-reservations-index.md)
> **Status**: [PARTIAL]
> **Last updated**: 2026-07-17

## Overview

Booking a room and everything the session needs, atomically: **room + engineer + backline**, or live
room + control room + assistant, or a venue + in-house sound + a backline hire. Several resources,
several calendars, one transaction that either succeeds entirely or does not happen.

The domain index names compound booking as one of the six capabilities justifying domain status, and
it is right to: a studio booking is *never* only a room. It is a room, and a person, and the gear
that must be in it. Every one of those has its own availability, and a booking system that reserves
the room and hopes about the rest is not booking a session.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Operator | ⚙️ Config | Defines what can be compounded with what, which combinations are mandatory (a mandatory assistant, 16.03.03), and which rooms cannot co-exist (16.01.02 D-02). Manages resources with very different scarcity — usually the person, not the room, is the binding constraint. |
| Producer | Full | **The persona this feature exists for.** Books live room + control room + assistant as one act. Experiences the atomicity — "the room is free but the engineer isn't" means no booking, which is correct and needs explaining. |
| Musician | Full | Books a rehearsal room + backline hire, or a venue + in-house sound. Simpler compounds, same mechanics. |
| Fan | ❌ None | No visibility. |

## Behavior

A compound is a set of resource reservations that succeed or fail together. Resource types: rooms
(with exclusion rules), people (engineers, with their own calendars and possibly their own 05
listings), and gear (backline, hire items from the inventory, 16.03.02).

The mechanics that make it hard:
- **Atomicity** — hold all, or release all. A partial hold that persists is the Operator's named anti-persona failure ("forgets to release a hold") arriving by machine instead of by forgetfulness.
- **Exclusion** — booking the live room blocks the control room (16.01.02 D-02). Exclusion and compounding are the same graph read in two directions.
- **Asymmetric scarcity** — the room is usually available and the engineer usually is not. The UI must say which half failed, or the client concludes the calendar is broken.
- **Mandatory members** — a mandatory assistant is not an add-on; it is part of the compound and must be priced and reserved as such.

The unresolved and most interesting case: a **cross-domain compound** — a dry-hire room here plus a
freelance engineer from 05. Nobody owns it, and it is the platform's clearest structural cross-sell
(16.03.03 DT-03).

### The resource graph (Level 1 model)

A compound is a set of edges over a **shared availability graph**. Nodes are scarce resources of three
kinds, each carrying its own calendar:

- **Rooms** (16.01.02) — first-class entities that also carry *exclusion* edges (16.01.02 D-02).
- **People** (engineers, assistants) — each with a calendar, and possibly their own 05 listing.
- **Gear** (backline / hire items, 16.03.02) — each an inventory unit with its own bookings.

Composing a compound selects a node set. Confirming it writes a **hold edge to every member's calendar
under one shared TTL** — the hold TTL is inherited from 16.06.01, not reinvented here. Exclusion edges
are read as *forced co-members*: selecting the live room pulls its exclusive sibling into the node set
automatically (DT-03), so the two can never be sold apart. The hold either lands on every calendar or is
rolled back from all of them — there is no persisted state in which some members are held and others are
not (D-02).

Two forks remain genuinely open and are deferred, not fabricated: whether reserving a hire item is this
domain's job or 15's (Q-02), and the authority/permission model when a member is a named 05 provider
(Q-04). Neither blocks the Level-1 behavior above; both change *whose calendar the edge is written to*,
not *that the edge is written atomically*.

### Happy Path

1. Producer selects Live Room A, Tuesday
2. System shows what compounds: control room (mandatory — exclusive sibling), assistant (mandatory per 16.03.03), Rhodes (hire extra, 16.03.02)
3. Producer adds the assistant and the Rhodes
4. System holds all four resources atomically and prices the compound
5. All four confirm or none do; the reservation (16.06.03) covers the whole compound

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Room free, engineer booked | The compound fails. Correct, and surprising — the UI must name the failing half or the calendar looks broken | "Room available — engineer unavailable on this date" |
| Partial hold left behind by a failed compound | The failure mode that would make the platform cause the Operator's anti-persona failure automatically. Atomicity is mandatory | Never visible if correct |
| Engineer is a named 05 provider | Whose calendar is authoritative and whose permission grants the booking? Unresolved (16.03.03 Q-03) | `[PENDING — Step 5]` |
| Hire item is also listed in 13 / registered in 15 | Is reserving the Rhodes this domain's job or 15's? Same fork as 16.03.02 DT-03 | `[PENDING — Step 5]` |
| Client wants the room without the mandatory assistant | Not offerable — a booking rule, not an upsell (16.03.03 DT-04) | "Assistant required for this room" |
| Compound cancelled | Do all members refund on one ladder, or does the engineer have their own cancellation terms? | `[PENDING — Step 5]` |
| Cross-domain compound (dry hire + 05 engineer) | Nobody's feature. The platform's clearest structural cross-sell, unowned | `[PENDING — Step 5]` |
| Two clients compose overlapping compounds at once (both want the same engineer) | The atomic hold is a race: first to confirm wins all members; the second's confirm finds the engineer already held and the whole compound fails, cleanly, with nothing partially reserved | "The engineer was just booked — your reservation was not made" |
| Hold TTL expires mid-composition (client adds members slowly) | The shared TTL (16.06.01) lapses; all held members release together on one clock, never member-by-member. Re-composing re-checks live availability | "Your hold expired — re-checking availability" |
| Client holds many compounds to block a rival's slot, never confirms | Abuse of atomic holds to deny inventory (the Operator's anti-persona failure, weaponised). Hold caps / confirm-rate limits enforced at the 16.06.01 hold layer, not re-solved here | Held compounds beyond the cap are refused |
| A member is removed from inventory (engineer quits, gear sold) while a hold is live | The live hold is honoured to its TTL or confirmation; the resource is withdrawn from *new* composition only. A confirmed compound is a reservation (16.06.03) and is not silently voided | Existing hold/booking unaffected; member no longer selectable |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Composing | Client selecting members | Live availability per member |
| Held (atomic) | All members held | One TTL across the compound |
| Partially unavailable | One member cannot be held | Which member failed, explicitly |
| Confirmed | All members confirmed | One reservation (16.06.03) |
| Expired | Shared TTL lapses before confirm | All members drop on one clock; prompt to re-check availability |
| Released | Any member released | All members released together |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | A compound is a booking with add-ons | Book the room, then tick some extras — the e-commerce pattern | ❌ REJECTED: an add-on has no independent availability. An engineer has a **calendar**; a Rhodes can be at another session. These are reservations against separate scarce resources, and treating them as line items means the system cheerfully sells a session with an engineer who is already booked. The compound is a set of reservations, not a cart. |
| DT-02 | Non-atomic is acceptable — reserve the room and sort the rest out | The room is the main thing | ❌ REJECTED twice over. Without atomicity: (a) the client gets a room they cannot use because the engineer never confirmed; (b) failed compounds leave orphaned holds, which is the Operator's stated anti-persona failure — "forgets to release a hold, blocking a slot they'd happily have sold" — now **automated by the platform**. Atomicity is not a refinement; it is what stops the feature from actively harming the persona it serves. |
| DT-03 | Exclusion (16.01.02) and compounding are different features | One blocks, one bundles | ❌ REJECTED — **they are one graph read in two directions.** "Booking the live room blocks the control room" and "booking the live room includes the control room" describe the same physical relationship: those two rooms move together. Modelling them separately guarantees they will disagree, and the disagreement will present as a double-booking. |
| DT-04 | The room is the scarce resource | It is the expensive thing with the calendar | ❌ REJECTED: **the person is usually the binding constraint.** Rooms sit empty far more often than good engineers are free. This inverts the UX priority — the compound should be composed around the person's availability, not the room's, and the failure message a client sees most is "the engineer isn't free", not "the room isn't". |
| DT-05 | Cross-domain compounds (room here + engineer from 05) are out of scope | Domain boundaries are boundaries | ⚠️ FLAGGED, not rejected. It is the platform's clearest structural cross-sell: no competitor can offer "this dry-hire room plus this freelance engineer, both reserved, one transaction" because none of them holds both sides. That is consolidation as D-18 defines it, instantiated in one booking. It is currently **nobody's feature** — 16.03.03 Q-02 raises it, 05 does not know it exists, and it will fall down the gap between them unless someone claims it. |
