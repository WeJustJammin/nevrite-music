# Feature: Spec Conformance Check (Rider ↔ Room)

> **Number**: 16.07
> **Parent**: [Venues, Studios & Spaces](./venues-studios-spaces-index.md)
> **Status**: [PARTIAL]
> **Last updated**: 2026-07-23
> **Origin**: Deep Think addition — asserted in the domain index's rationale, absent from the sweep's 22 candidates

## Overview

Comparing what an act **needs** against what a room **has**, and surfacing the mismatches before the
day. The band's rider says 6 monitor mixes; the room has 4. The rider asks for a shower; there isn't
one. The production needs 3-phase power; the room has 13-amp sockets and an optimistic attitude.

The domain index states this outright as the domain's justification — *"structured specs make
rider-vs-venue conflict detection possible for the first time"* — and then the sweep's 22 candidates
do not contain it. **An asserted capability that nobody owns does not get built**, which is why it
exists as a node rather than as an implication of 16.02.

It is also the answer to "why structure the spec at all?" Without conformance checking, the spec is a
prettier PDF.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Full | Runs the check before agreeing to a show and sees, in seconds, whether the room can run their production. Today this is an email thread, a phone call, and a surprise at soundcheck. |
| Producer | Full | Runs it for a session — does this room have the chain the project needs — and for live recording, where the check spans both spec sheets. |
| Operator | 📊 Reports | Sees conflicts flagged against their room at advance, not at 6pm on the day. Also sees which *unstated* fields cause failed matches — the strongest incentive the domain has for filling the spec. |
| Fan | ❌ None | No visibility. Utterly irrelevant to a ticket buyer. |

## Behavior

Two structured documents, one comparison. The **room spec** is 16.02 (venue) or 16.03 (studio). The
**rider / tech pack** belongs to **18 Show Production & Touring** — it is a property of the act, not
the room (16.02.04 DT-02).

Output is a three-way classification, not a pass/fail:
- **Conflict** — the room cannot meet the requirement (4 mixes vs 6 needed)
- **Unknown** — the room has not stated it, so nothing can be concluded. **This is the most common result** and it must not be dyed green.
- **Match** — the room states it and it satisfies the requirement, with the field's freshness attached (16.05.05)

The check's honesty is its entire value. A confident green tick derived from a stale or unstated
field is worse than no check, because it transfers the band's risk onto a claim nobody verified. A
match must carry its confidence: "6 mixes — verified 3 months ago" is a different statement from "6
mixes — never verified".

**Matching semantics per field type.** The classification a field receives depends on how that field
is modelled in the room spec (16.02 / 16.03) — which is why this feature's reach rests on 16.02 Q-01.
At Level 1 the matcher runs four comparison behaviours, chosen by field type, and every one of them
can also return **unknown**:

| Rider requirement type | Comparison behaviour | Match / Conflict / Unknown |
|------------------------|----------------------|----------------------------|
| **Numeric ≥ threshold** (monitor mixes, amps, ceiling height, capacity) | Stated value vs required value | Match if stated ≥ required; Conflict if stated < required; Unknown if unstated |
| **Presence / boolean** (shower, 3-phase power, in-house PA, load-in ramp) | Does the room state it has the thing | Match if stated present; Conflict if stated absent; Unknown if the field was never filled |
| **Enum / set membership** (power connector ∈ {13A, 16A, 32A, 3-phase}, stage-box channel count) | Required value ∈ room's stated set | Match if required is in the set; Conflict if the set is stated and excludes it; Unknown if the set is empty/unstated |
| **Free text** ("a decent PA", "a vibey room") | None possible — a prose requirement or a prose spec field cannot be compared | Always **Unknown**, tagged "needs a human read". Never Match, never Conflict |

A rider requirement can only reach a decisive Match or Conflict when **both** sides are structured:
the room field is an enum/number/boolean (16.02 Q-01 resolves toward structure) **and** the rider
line is machine-readable (18's concern). When either side is prose, the honest result is Unknown, not
a guess. This keeps the free-text reality (most riders are prose today) from ever masquerading as a
pass or a fail — the feature degrades to "here are the fields we could not check", which is still
useful and still honest.

`[PENDING — Step 5 Must-depth or /write-be-spec]` — the exact tolerance rules inside a type (does "6
mixes needed, 6 stated" match when one is a stereo pair; does a 16A requirement match a stated 32A
socket via a known adapter). This long-tail per-field detail is deferred; the four-way behaviour above
is complete for Level 1.

### Happy Path

1. Band is offered a show; opens the venue's room and runs the check against their rider (18)
2. Output: 3 matches (verified), 4 unknowns, 1 conflict — "6 monitor mixes required, room states 4"
3. Band raises the one conflict at advance instead of discovering it at soundcheck
4. Operator confirms 4 is right; band brings 2 extra wedges or drops to 4 mixes — decided in advance, calmly
5. The 4 unknowns prompt the Operator to fill those fields — a failed match is the domain's best nudge

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Room has not stated the field | "Unknown" — never a pass. The commonest outcome at cold start and the honest one | "Not stated — ask the venue" |
| **The field is not modelled in this record's regime** (16.01.06 D-05 — the profile declares no such statutory slot) | Also `unknown`, but for a **different reason**, and the distinction matters downstream: it is not a gap the Operator can close, so it must **not** feed D-06's lost-enquiry nudge. Nudging an Operator to fill a slot their regime does not have is blaming them for a jurisdiction | "Not applicable here" to the Operator; "Not stated" to the reader. Never counted against the room |
| Field is stated but stale (16.05.05) | Match with a caveat, or drops out of confident matching entirely (16.05.05 D-03) | "Matches — but last verified 2 years ago" |
| Rider is free text ("a decent PA") | Falls to the free-text branch — classified **Unknown, "needs a human read"**, never Match/Conflict. Most riders are prose, and no amount of spec structuring on our side fixes the other half | "Couldn't auto-check — read this line yourself" |
| Spec is free text (16.02 Q-01 resolves that way) | The check is impossible. **This feature's existence depends on a decision in 16.02** | — |
| Conflict is negotiable (6 mixes vs 4 — the band can cope) | A conflict is information, not a verdict. It must never block a booking | Flagged, not blocked |
| Everything matches, and the room is still wrong | The check is only as good as the spec, which is only as good as the harvest (16.05.06). **False confidence is the failure mode to fear** | Confidence shown per field |
| Rider changes mid-tour, or the spec decays between check and show | Level-1 default: the check is a **point-in-time snapshot, re-run on demand** — no auto-resubscribe. Whether it should watch and re-alert is a user scope decision (Q-03) | "Checked on {date} — re-run to refresh" |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Not run (Empty) | No rider selected / default | CTA to pick a rider and check it against the room |
| Running (Loading) | Check invoked | Skeleton of the result rows filling in; "Checking rider against room…" |
| Complete (Populated) | Comparison done | Conflicts / unknowns / matches, grouped, with confidence per field |
| Mostly unknown | Room's spec is thin | "This room hasn't stated enough to check" — honest, and a nudge to the Operator |
| Stale | Matched against decayed fields | Match + prominent age ("verified 2 years ago") |
| Error | No comparable rider (prose-only), or room spec unavailable/failed to load | "We couldn't run this check — the rider isn't structured / the room's spec didn't load", with retry and a manual-read fallback. Never a silent green |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | Conflict detection is implied by having a structured spec | The domain index asserts the capability; 16.02 provides the data | ❌ REJECTED — **and this is why the feature exists as a node.** The spec is one half; the rider (18) is the other; the matcher is neither. An asserted capability with no owner falls into the gap between two domains and does not get built. Creating it explicitly forces the 16↔18 dependency to be visible now rather than discovered during `/write-architecture-spec`. |
| DT-02 | The result is pass/fail | The band wants to know: can we play here? | ❌ REJECTED: **"unknown" is the most common result** and collapsing it into either bucket is a lie. Unknown-as-pass transfers the band's risk onto a claim nobody made. Unknown-as-fail deletes every honest room that has not finished its spec — which at cold start is nearly all of them. Three states, and the middle one is the majority. |
| DT-03 | This belongs in 18 with the rider | 18 owns the advance, and the check happens at advance | ⚠️ PARTIALLY REJECTED — genuinely arguable, and worth stating the reasoning. The check is anchored **here** because the spec's schema defines what is comparable: whatever 16.02 structures is what can be checked, and nothing else. The matcher must live where the schema lives or it will drift. But the *moment* of use is 18's advance, so 18 owns the workflow and 16 owns the comparison. Flagged as a high-confidence cross-domain touchpoint — this needs confirming with 18, not asserting. |
| DT-04 | The check makes the spec worth maintaining | It gives the structured data a use | ✅ CONFIRMED, and it closes the domain's incentive loop. 16.02.02 DT-02 worries Operators will not fill a long form. The answer is not persuasion — it is **consequence**: an unstated field produces "unknown", unknowns lose enquiries, and the Operator sees which fields cost them work. The check is what converts spec-filling from admin into self-interest, and it is the mechanism the venue-spec sub-domain has been assuming without naming. |
| DT-05 | A green tick is a good outcome | Users want reassurance | ❌ REJECTED — **false confidence is this feature's worst failure mode.** A match against a stale or never-verified field looks identical to a match against a fact a band confirmed last week, and the band acts on it: they leave the wedges at home. The check must carry per-field confidence (16.05.05) and stale fields must drop out of confident matching. A check that is confidently wrong is worse than no check, because it moves risk onto the platform's claim. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | Created as an explicit node despite absence from the sweep | The domain index asserts the capability; an asserted capability with no owner falls between 16 and 18 and never gets built (DT-01) |
| D-02 | Three-way output — conflict / **unknown** / match. Never pass/fail | Unknown is the majority result; collapsing it either way is a lie that costs a band or an honest room (DT-02) |
| D-03 | Matches carry **per-field confidence**; stale fields drop out of confident matching | A confidently wrong check moves risk onto the platform's claim, and the band leaves the wedges at home (DT-05) |
| D-04 | 16 owns the comparison (the schema defines what is comparable); 18 owns the rider and the advance workflow | The matcher must live where the schema lives or it drifts (DT-03) |
| D-05 | A conflict is **information, never a block** | The band decides whether 4 mixes is workable; the platform does not get a vote |
| D-06 | This feature is the venue spec's **incentive loop** — but only over fields the Operator can actually fill. An `unknown` caused by a **regime capability the record does not have** (16.01.06 D-05) is excluded from the lost-enquiry nudge | Unknowns lose enquiries; the Operator sees which unstated fields cost them work (DT-04). Nudging on a slot their regime does not declare would make the loop dishonest in exactly the way D-02 and DT-05 exist to prevent — the same `unknown` output, two causes, and only one of them is anybody's fault |
