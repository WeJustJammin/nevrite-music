## Cross-Cut Details

### CX-01: QC ↔ Delivery & Acceptance

**Relationship**: QC is not a step inside delivery — it is delivery's **precondition**. A file that fails the agreed spec has not been delivered; it has been rejected back to the seller, invisibly to the buyer.

The reason this ordering is load-bearing is the auto-accept clock. If QC ran at acceptance instead, a 44.1k master would publish to a buyer who agreed 48k, their window would start, and a buyer on tour could auto-accept — paying for and taking ownership of a file that failed the spec they themselves specified. The platform would have executed a copyright assignment over a defective deliverable and called it consent.

This is precisely the same principle as the requirements gate (05.03.01), from the other side of the engagement, and the symmetry is strong enough to state as a domain principle: **no clock runs against a party until the counterparty has actually done their bit.** The requirements gate holds the seller's clock until the buyer's material is complete; QC holds the buyer's clock until the seller's file is valid.

**Role scoping**:
- **Musician**: seller side — sees failures before their client does, which is the whole point. Buyer side — never sees a broken delivery at all.
- **Producer**: same, with the highest exposure because their deliverables feed somebody else's stage (mastering, DSP delivery in domain 12), so a spec failure here propagates downstream.
- **Operator**: none — attendance has no spec.
- **Fan**: none.

**Synthesis questions answered**:
1. **Shared state conflict**: The delivery artifact. QC owns validity; delivery owns publication. No ownership conflict, but a strict ordering — and the `Overridden` state is the deliberate seam where the seller's judgement beats the machine's, recorded and shown to the buyer.
2. **Trigger chain**: Upload → QC → pass → publish → clock starts. If QC fails, nothing publishes and nothing rolls back (nothing had committed). If the QC **engine** is unavailable, 05.04.02 D-05 says fail *open* with a visible flag — the file publishes unchecked and flagged, because a silent pass would make the badge a lie.
3. **Permission intersection**: Only the seller sees QC results pre-publication. That asymmetry is deliberate: a buyer who saw their engineer's failed exports would draw conclusions the data does not support.
4. **Notification fan-out**: A QC failure notifies only the seller. The buyer is not told their delivery was late because of a failed export — that is between the seller and their DAW.
5. **State transition conflict**: A QC run still in progress when the seller retracts the delivery (05.04.01 D-05). The retraction must win and the QC result be discarded.

### CX-04: QC ↔ Watermarking

**Relationship**: Two features, one engine, fixed order, and — importantly — **opposite failure postures**.

Order: QC must run on the **clean** file. Watermarking is applied after. Reversing them would have QC measuring loudness and true-peak on audio that has had a forensic mark embedded in it, which is measuring the wrong artifact and could itself trip a true-peak check.

Failure posture: when the engine is unavailable, QC **fails open** (publish unchecked, visibly flagged) while watermarking **fails closed** (fall back to streaming-only, never publish unwatermarked). This asymmetry looks inconsistent and is deliberate. An unchecked file is a *known unknown* — flagged, visible, and the buyer can still evaluate it. An unwatermarked download is a *silent* loss of the seller's only protection: nobody would notice, and by the time it mattered the file would be gone. Fail toward the state where the failure is visible.

Both features sit on the same **stack collision**. `meta/constraints.md` locks Cloudflare Workers as compute, and the domain map already routes heavy audio transcode/waveform/DSP to not-product as a hard constraint. Loudness/spectral analysis over a 40 GB stem set and forensic watermark embedding are both squarely outside what a Worker can do in-request. Neither feature can proceed without a DSP service that is not in the locked stack.

**Role scoping**:
- **Musician / Producer**: both experience this as latency at delivery — the most impatient moment in the engagement, when the work is done and the seller wants it gone.
- **Operator / Fan**: none.

**Synthesis questions answered**:
1. **Shared state conflict**: The audio asset exists in at least two versions (clean, protected). The clean one is canonical for QC, provenance and post-acceptance release; the protected one is transient. Only the clean version should be what acceptance transfers.
2. **Trigger chain**: Upload → QC (clean) → pass → watermark → publish. Two engine calls per delivery, and every revision redelivery repeats both (05.04.03 cross-cut note) — so the DSP cost is per-round, not per-engagement, which materially changes the sizing.
3. **Permission intersection**: None between the two.
4. **Notification fan-out**: Neither should notify the buyer of its internal states. The buyer sees "delivered" or nothing.
5. **State transition conflict**: If watermarking fails after QC passed, the delivery must not publish unprotected. It falls back to streaming-only, which is a *different product* from what the seller elected — so the seller must be told, not silently downgraded.

### CX-02 / CX-05: Artifact Set ↔ Delivery, and ↔ Watermarking

**Relationship**: The artifact set is the answer to "what changes hands", and it turns out to govern both of its neighbours. Against **delivery**, it defines the payload and makes explicit that acceptance does two orthogonal things at once — transfers rights (05.06) and hands over artifacts (this) — which 05.04.04 DT-03 identifies as the domain's most seductive conflation. Against **watermarking**, it determines whether protection is even possible: a stereo mix can be marked, a DAW session cannot be marked at all, and stems can be but probably should not (05.04.03 DT-03 — 24× the DSP, worse artefact exposure on solo material, and pointless because the buyer is going to import and process them anyway).

The consequence neither feature states alone: **protection posture is per-artifact-type, not per-engagement.** An engagement delivering a mix + stems + session needs three different answers in one delivery.

**Role scoping**:
- **Musician**: as a seller, the practical effect is that "protect my drafts" is not one switch.
- **Producer**: most exposed, because their engagements deliver the widest artifact sets.
- **Operator / Fan**: none.

**Synthesis questions answered**:
1. **Shared state conflict**: The artifact set is agreed on the quote and frozen there (scope of record). Neither delivery nor watermarking may add to it.
2. **Trigger chain**: Acceptance → clean artifacts released per the agreed set. If the set includes a session, the transfer is large and slow, and acceptance should not block on it.
3. **Permission intersection**: Yes, and it is the counter-intuitive one — a buyer may hold a full work-for-hire assignment (owns the master absolutely) and still have no entitlement to the session. Rights permissions do not imply artifact permissions.
4. **Notification fan-out**: `Session Withheld` should be stated plainly at delivery, not discovered later. This is a case where redundant clarity is worth the noise, because the assumption is near-universal.
5. **State transition conflict**: None significant.
