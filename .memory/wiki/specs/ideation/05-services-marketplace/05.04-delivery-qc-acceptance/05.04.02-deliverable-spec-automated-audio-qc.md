# Feature: Deliverable Technical Spec & Automated Audio QC

> **Number**: 05.04.02
> **Parent**: [Delivery, QC & Acceptance](./05.04-delivery-qc-acceptance-index.md)
> **Status**: [SURFACE]
> **Last updated**: 2026-07-16

## Overview

The technical contract for what comes out: format, sample rate, bit depth, loudness target, true-peak ceiling, headroom, naming convention, file count — declared on the listing, agreed on the quote, and checked automatically before the file reaches the buyer. Half the "the mix is wrong" arguments in music are not about the mix; they are about a 44.1k file arriving where a 48k one was needed, or a master printed 3 dB hotter than the DSP will accept.

Automated QC checks a spec. It does not check whether the music is good, and it must never be described as if it does.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Full | As a seller, sees their file checked before it goes out — catching the 44.1k export they made at 3am, before their client does. As a buyer, states a spec once instead of discovering the mismatch at mastering. For a session player delivering stems, the naming convention check alone removes the most common cause of a redelivery. |
| Producer | Full | The persona who owns the spec, because they are the one who knows what mastering, the DSP or the sync licensor will require. Sets demanding specs as a buyer; meets them as a seller. Their mixes are the input to somebody else's stage, so a spec failure here propagates downstream into domain 12. |
| Operator | None | Not visible. Attendance has no technical spec. |
| Fan | None | Not visible. |

> **Access levels**: Full · Config · Read-only · Reports · None

## Behavior

The spec is declared on the listing (05.01.01), agreed on the quote (05.02.01), and enforced at delivery (05.04.01). QC runs **before** the delivery is published to the buyer — a failing file is rejected back to the seller and the buyer never sees it, so their auto-accept clock never starts on a file that was never valid.

What QC can honestly check:

| Check | Example |
|---|---|
| Container/format | WAV, AIFF, not MP3 |
| Sample rate / bit depth | 48 kHz / 24-bit as agreed |
| Loudness | integrated LUFS within a stated tolerance |
| True peak | no sample exceeding the agreed dBTP ceiling |
| Clipping / DC offset | consecutive samples at full scale; non-zero DC |
| Duration | matches the agreed programme length — also the per-minute pricing input (05.01.03 DT-03) |
| Silence | leading/trailing silence, or a stem that is silent throughout (the classic export failure) |
| File count & naming | 24 stems, named to the convention |
| Channel config | stereo where stereo was agreed; mono stems not accidentally dual-mono |

What QC cannot check, and must not imply it can: whether the mix is any good, whether the stems came from the right session, whether the vocal is the comped take, whether the performance is human (05.06.05).

### Happy Path

1. Seller declares a spec per listing tier, from a per-craft template (mastering for streaming, stems for mixing, film/TV delivery)
2. Buyer agrees or amends it on the quote
3. Seller uploads deliverables
4. QC runs; results shown to the **seller** first
5. Pass → delivery publishes to the buyer; auto-accept clock starts
6. Fail → rejected to the seller with the specific failures; no buyer visibility, no clock

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Loudness fails by 0.2 LUFS | Hard-failing a trivial tolerance breach is worse than the breach | Tolerance bands, and a warn-vs-fail distinction per check |
| Seller believes QC is wrong | It sometimes will be — a deliberately clipped master is a real aesthetic choice | Override with a reason, recorded and shown to the buyer. Never a silent bypass. |
| A stem is silent | Almost always a real export error; occasionally intentional (a muted alt take) | Warn, not fail |
| Spec not stated | Nothing to check | Per-craft default spec, clearly shown as a default rather than an agreement |
| Buyer's stated spec is wrong for their own purpose (asks for 44.1k, needs 48k for the sync) | The platform knows the downstream requirement better than the buyer does | Advisory: "Sync delivery usually needs 48k. Sure?" — advice, not a block |
| Multi-GB stem set | QC over tens of GB is not a quick check | See DT-03 — the stack collision |
| On-location engagement | No file | Feature absent |
| QC passes but the material is wrong (stems from the wrong session) | QC cannot see this. The seller catches it at the *requirements* gate (05.03.01 DT-02); the buyer catches it at review. | This limit must be stated plainly, not papered over |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Spec Declared | Listing/quote | The checklist both parties agreed |
| Checking | Upload complete | Progress — honest, because this is slow on large sets |
| Passed | All checks pass | Delivery publishes |
| Warned | Non-fatal issues | Seller decides: fix or proceed with the warning recorded |
| Failed | Fatal breach | Seller-only; specific failures; no buyer visibility |
| Overridden | Seller overrides with a reason | Buyer sees the override and the reason at delivery |
| Unavailable | QC cannot run (size/format/engine) | **Must fail open with a visible flag, not silently pass** |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | QC can meaningfully assess deliverable quality | The candidate list's phrasing ("Automated Audio QC") invites this reading | ❌ REJECTED, and the rejection needs to be loud. QC checks a **spec**, not a mix. It can prove a file is 48k/24-bit, sits at -14 LUFS integrated, never exceeds -1 dBTP and contains 24 correctly-named non-silent stems. It cannot tell you the mix is any good, and it must never be presented in a way that implies it did — because the moment a buyer reads a green "QC Passed" badge as a quality warrant, the platform has taken on an implicit assurance it cannot honour, and the first taste dispute will cite it. The naming matters: this is a **spec check**, and calling it that everywhere in the UI is a design requirement, not a copy preference. |
| DT-02 | **QC must gate delivery, not acceptance** | Reasoning about the auto-accept clock's start condition | ✅ CONFIRMED — and it mirrors 05.01.06 DT-01 exactly, from the other side of the engagement. The requirements gate stops the seller's clock until the buyer's material is complete; QC stops the buyer's clock until the seller's file is valid. Both are the same principle: **no clock runs against a party until the other party has actually done their bit.** If QC ran at acceptance, a broken file would publish, the auto-accept window would start, and a buyer on tour could end up auto-accepting a 44.1k master they never opened — paying for and taking ownership of a file that failed the spec they agreed. The symmetry is elegant enough to be worth stating as a domain principle rather than two local rules. |
| DT-03 | **The QC engine is infrastructure and collides with the locked stack — but the QC rules are product** | Node Classification Gate + `meta/constraints.md` (Astro/Cloudflare Workers/Supabase locked) + the domain map's stated stack collisions | ✅ CONFIRMED, and it produces a clean split rather than a node deletion. *What a deliverable must satisfy* is product content with real commercial consequences (a spec template that gets streaming loudness wrong sends every master out at the wrong level). *Executing loudness and spectral analysis over full-length multitrack WAV sets* is heavy DSP — the domain map already routes "heavy audio transcode/waveform/DSP (Media Handling)" to not-product as a **hard constraint** against the Cloudflare Workers CPU/time limits, and a 40 GB stem set is exactly the case those limits were never meant to serve. So: rules here, engine in the Media Handling cross-cut, and the execution constraint routed to `/create-prd`. The `Unavailable` state exists because of this: when the engine cannot run, the honest behaviour is to **fail open with a visible flag** — silently passing unchecked files would make the badge a lie, which DT-01 says is the one thing this feature must never be. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | This is a **spec check**, never a quality assessment, and the UI must say so everywhere | A green badge read as a quality warrant becomes an implicit assurance the platform cannot honour. See DT-01. |
| D-02 | QC gates delivery, not acceptance | Mirror of the requirements gate. No clock runs against a party until the other has done their bit. See DT-02. |
| D-03 | Checks are warn-or-fail, with tolerances — not binary | Hard-failing a 0.2 LUFS breach is worse than the breach. |
| D-04 | A seller may override with a recorded reason, visible to the buyer | Deliberately clipped masters are a real aesthetic choice. A silent bypass would be worse than no QC. |
| D-05 | When the engine is unavailable, **fail open with a visible flag** | Silently passing unchecked files makes the badge a lie. |
| D-06 | The rules are product-owned; the DSP engine belongs to Media Handling and is routed to `/create-prd` | Stack collision with the locked Workers constraint. See DT-03. |
