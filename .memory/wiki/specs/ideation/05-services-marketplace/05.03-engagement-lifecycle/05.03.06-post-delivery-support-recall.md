# Feature: Post-Delivery Support Window & Recall

> **Number**: 05.03.06
> **Parent**: [Engagement Lifecycle](./05.03-engagement-lifecycle-index.md)
> **Status**: [SURFACE]
> **Last updated**: 2026-07-16

## Overview

The tail after acceptance: a bounded window in which a buyer can come back for the small, legitimate things that only surface downstream. In music this has a name and an etiquette — the **recall**. Mastering reveals a hi-hat that spits, the vinyl cut needs a different low end, the sync licensor needs an instrumental that was never asked for. None of these are revisions; the engagement is closed, the money released, the rights transferred.

## Behavior

A support window opens at acceptance and runs for a declared period. Inside it, the buyer may request a **recall** — a bounded, small change to delivered work — or an **artifact request** (a file that existed within scope but was not delivered: an instrumental, a TV mix, a different format).

The structural problem is that acceptance already did three things (05.06.03): released escrow, transferred rights, emitted credits. A recall must reopen the *work* without unwinding any of those. It is not a return to `In Revision`, because that state implies unreleased money and untransferred rights.

The line against a change order is scale. A recall is "the vocal is 0.5 dB hot". A recall is not "the label wants a different mix".

### Happy Path

1. Engagement accepted; rights transferred; escrow released; support window opens
2. Buyer takes the mix to mastering; mastering flags a problem
3. Buyer raises a recall inside the window, citing the specific issue
4. Seller accepts it as in-window; makes the change; redelivers
5. No new escrow, no new rights transfer, no new credit — the same work, corrected
6. Window expires; engagement fully closes

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Recall request is really a new mix | Seller declines as out-of-window-scope; it is a new engagement | "That's a new job — want me to quote it?" |
| Window expired, request legitimate | No obligation; goodwill or a new engagement | "This engagement closed on {date}." |
| Recall requested but the seller has moved on / lost the session | The realistic failure. Sessions get archived, drives die, the seller changed DAW. | Ties directly to 05.04.04 (session handover) and to the retention question — see Q-01 |
| Buyer uses recalls as free revisions | The abuse mode. Bounded count + scale test. | "Recall 2 of 2 used." |
| Recall on a work-for-hire deliverable the buyer now owns | The buyer owns it; they are asking the seller to work on the buyer's property | Fine, but it is worth noting the rights and the labour have separated |
| Seller refuses a legitimate recall | Not a contractual breach if the window terms are met — but it is a reputational fact | `[PENDING — /ideate-discover Step 5 deepening]` — see Q-02 |
| Recall reveals the original delivery failed QC | That is not a recall, it is a defect — the original acceptance was on a bad file | `[PENDING — /ideate-discover Step 5 deepening]` — defect vs recall boundary; see Q-03 |
| Points-based engagement (05.06.02) | The seller has an ongoing royalty interest, so their incentive to recall is permanent | Interesting inversion: points-holders will *want* to recall |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | **A recall must reopen closed, paid, rights-transferred work without unwinding any of those three things — which means it cannot reuse the revision state** | Adversarial: trace a recall through the acceptance transaction (05.06.03) and see what breaks. | ✅ CONFIRMED, and it is the reason this is a feature rather than a variant of 05.03.03. Acceptance is atomic and does three things at once: releases escrow, executes the rights transfer, emits the credit. A recall touches none of them — the buyer still owns the work, the seller has still been paid, the credit still stands — and yet the *work* must reopen. Returning the engagement to `In Revision` would model it as though money were unreleased and rights unvested, which is false and would make every downstream reader of the engagement's state wrong. A recall is therefore a **post-terminal** state: the engagement is closed and something is nonetheless happening. That is unusual enough that it must be modelled deliberately rather than emerging as a bug. |
| DT-02 | **The realistic failure is not refusal, it is that the seller no longer has the session** | Domain expertise: what actually goes wrong here? | ✅ CONFIRMED — and it connects two features that otherwise look unrelated. A recall is only possible if the session still exists: the project file, the plugin versions, the licences, the drive. Three months later the seller may have moved DAW, lost a licence for a discontinued plugin, or archived to a drive that has since died. Nobody's fault, and the recall is simply impossible. This makes the support window a **retention obligation on the seller** as much as a service promise, and it gives 05.04.04 (source file & session handover) a second, non-obvious justification: a buyer who holds the session can have someone else do the recall. It also means the window's length is not a free parameter — a 12-month recall window is a promise most sellers cannot physically keep, so a short honest window beats a long fictional one. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | A recall is a **post-terminal** state — the engagement stays closed, rights stay transferred, escrow stays released | See DT-01. Reusing `In Revision` would make every downstream reader of the state wrong. |
| D-02 | Framed as the music-industry recall, not as generic warranty/support | The etiquette already exists in the industry; importing SaaS support semantics would model the wrong thing. |
| D-03 | The window is bounded in both duration and count | Otherwise it is unlimited revisions with extra steps (05.03.03 DT-01). |
| D-04 | The window is a retention obligation on the seller, so its length must be one sellers can actually honour | A 12-month window is a promise the drive will not keep. See DT-02. |
