# Feature: Statement Parsing & Format Adapters

> **Number**: 10.02.02
> **Parent**: [Statement Ingestion & Normalization](./10.02-statement-ingestion-normalization-index.md)
> **Status**: [SURFACE]
> **Last updated**: 2026-07-16

## Overview

Turning **each source's file into royalty lines**: DDEX DSR from DSPs, per-society CSVs that share no column names, distributor exports, label statements as spreadsheets, and — routinely — PDFs designed for a human to read and nobody to parse. Every source has its own adapter, and there is no standard that covers even a majority of them.

The feature's real product is not the parse; it is the **honest report of what the platform did and did not understand**. A parser that silently drops the lines it could not read is worse than no parser, because it produces a total that looks complete.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Read-only | Sees what was understood, what wasn't, and — the number that matters — whether the parsed lines sum to the total printed on their statement. They cannot fix a parser and should never be asked to map columns; that is the platform's job and the ask would be indistinguishable from failure. |
| Producer | Read-only | Same, at volume. A producer ingesting label statements hits the widest format spread and finds the adapters' edges first. |
| Operator | None | No surface. |
| Fan | None | No surface. |

## Behavior

Per source, an adapter defines the mapping from that source's file to normalized lines: (usage period, territory, right type, source identifier for the work/recording, usage quantity, gross, deductions, net, currency). The output is *lines*, not conclusions — matching them to a catalogue is `10.02.03`'s job and must stay separate, because a parse error and a match error feel identical to a user and have completely different fixes.

The control that makes the whole sub-domain trustworthy is **reconciliation to the stated total**. Every statement prints a number the source says it paid. If the parsed lines do not sum to it, the parse is wrong — and this is checkable, locally, with certainty, for every statement, without any external cooperation. It is the only hard oracle available anywhere in domain 10, and it should be treated as the feature's primary output rather than a validation nicety.

Adapters are **data with versions**, not code paths. Sources change their formats without notice and without a migration; a format change must be a new adapter version applied to statements from that date, with old statements still parseable by the version they arrived under — otherwise re-running an old ingest silently produces a different answer than the one already paid out.

### Happy Path

1. Statement arrives from a known source (`10.02.01`)
2. Adapter for that source + format version parses it into lines
3. Lines are summed and reconciled against the total the statement itself states
4. Reconciliation matches; lines are handed to `10.02.03` for matching
5. What was parsed is reportable in the source's own terms — the user can look at their statement and at the platform side by side

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Parsed lines don't sum to the stated total | **The parse is wrong.** The one certain, local check in the domain | Explicit discrepancy — never a rounded-off "close enough" |
| Source changed its format | Adapter breaks, usually mid-batch, always without notice | Fails loudly; a partial parse must not proceed as if complete |
| PDF statement designed for humans | Common with older labels and some societies | `[PENDING — /ideate-discover Step 5 deepening]` — extraction feasibility per source is unknown |
| Negative lines (returns, adjustments) | Real and routine. A parser that assumes positive money is wrong on its first restatement | Must round-trip negatives faithfully → `10.03.04` |
| Deductions itemised vs netted | Some sources show gross and deductions; some show only net. The second makes explainability structurally impossible | Disclosed as net-only, never reverse-engineered (`10.01.07` D-03) |
| A line with no identifier at all | Just a title string. Very common on older statements | Parsed as a line; matching is `10.02.03`'s problem — do not drop it |
| Multi-currency in one statement | Real for aggregated foreign income | Per-line currency → `10.02.04` |
| Rounding at the source | Sub-cent per line, material across a million lines | `[PENDING — Step 5]` — see `10.03.01` |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Unparsed | Received, queued | Waiting |
| Parsed | Adapter succeeded, total reconciles | Line count and total, matching the statement |
| Reconciliation failed | Lines ≠ stated total | **Blocked.** The parse is not trusted; nothing proceeds to matching |
| No adapter | Unknown source or format | Honest gap: the file is retained (`10.02.01` D-03), the platform cannot read it, and it says so |
| Partial | Some lines unreadable | Named, quantified, and **not** silently dropped |
| Superseded | Adapter version corrected | Re-parse produces a new interpretation; the old one is retained, because money may already have moved on it |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | Parsing and matching are one step — you read the file and attach the money to the work | The natural framing, and how a first implementation would be written | ❌ **REJECTED, and keeping them apart is what makes the sub-domain debuggable.** They fail identically from the user's side ("my money isn't showing up") and have nothing else in common. A parse failure is the platform's fault, is fixed by an engineer, and is **locally detectable with certainty** via the stated-total check. A match failure is a catalogue/identifier problem, is fixed by the user or by domain 09, and is **never locally certain** — you cannot prove a line belongs to a work. Merging them means a mismatched line and a misparsed line land in the same bucket with the same message, and the stated-total oracle — the only hard check in the domain — becomes unusable, because you can no longer tell whether the sum is wrong or the attribution is. |
| DT-02 | The platform can ask the user to map unknown columns | Standard import-wizard UX; it works fine for CSV contact imports | ❌ **REJECTED.** A royalty statement's columns are not self-describing to their own recipients — "Adj. Net Rec." is not a question a working drummer can answer, and a wrong answer produces a confidently wrong payment rather than a visible error. Worse, per-user mappings mean the same source parses differently for different users, and the platform can never reason about a source's format again. **Adapters are the platform's job, per source, once.** The honest failure mode is "we don't support this source yet" — which is at least true, and is a queue the platform can work through. |
| DT-03 | Reconciliation to the stated total is a validation check | It looks like one — sum the lines, compare, warn | ✅ **CONFIRMED, and promoted to the feature's primary output.** Domain 10 is characterised by facts nobody can verify: registration state is inferred (`10.01.04` D-03), matching is probabilistic (`10.02.03`), society behaviour is opaque, at-source deductions are unknowable (`10.01.07` D-03). The stated total is **the only hard oracle in the entire domain** — a number the counterparty itself published, checkable locally, for free, on every statement, with no relationship required. A domain this full of inference should build its trust story on the one thing it can actually prove. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | Parsing and matching are **separate features** | DT-01. Different fault owners, different fixes, and merging them destroys the stated-total oracle. |
| D-02 | **Reconciliation to the stated total gates everything downstream** | DT-03. The only hard oracle in domain 10. A failed reconciliation stops the pipeline; it does not warn. |
| D-03 | Adapters are the platform's job, per source. **The user never maps columns** | DT-02. Users cannot answer the question, and a wrong answer becomes a wrong payment. |
| D-04 | Adapters are **versioned data**, applied by statement date | Sources change formats silently; re-parsing an old statement under a new adapter would change a number that has already been paid. |
| D-05 | Unparseable lines are **named and counted**, never dropped | A silently short parse produces a total that looks complete. This is the mechanism by which a platform becomes its own black box (parent domain D-09). |
