# Feature: Registration Status, Acknowledgement & Rejection Loop

> **Number**: 10.01.04
> **Parent**: [Society Registration & Delivery](./10.01-society-registration-delivery-index.md)
> **Status**: [PARTIAL]
> **Last updated**: 2026-07-23
> **Origin**: Deep Think addition — not a sweep candidate

## Overview

The **per-work, per-society, per-territory registration state** and the loop that maintains it: reading acknowledgements, interpreting rejections, detecting silence, and driving the fix back to whoever can make it. The parent domain's own Overview names this as the hard part — *"the rejection loop nobody notices for a year"* — and no sweep candidate covered it. The sweep named delivery; this is the feature that decides whether delivery worked.

The asymmetry that justifies it: sending a registration is one act, but **being registered is a state that decays**. A society rejects, a conflicting claim appears, a co-writer's PRO disputes, an acknowledgement never comes — and none of those produce an error the user ever sees. The money simply doesn't arrive, and the absence is unnoticeable because there was never a promise of a specific amount on a specific date.

## Behavior

Registration state is **inferred, never read** — a consequence of `10.01.03` D-01/DT-01: the transport is batch and offers no per-work status call. The platform's model of "registered at PRS" is therefore always a belief derived from the last acknowledgement that mentioned the work, and the feature's integrity depends on treating it as a belief with an age.

Three signals arrive, and they are not symmetric:

- **Acknowledgement** — the society accepted the work. Often carries back an ISWC the platform did not have, which flows to domain 09's identifier record. Cheap, unambiguous, and the only signal that means anything positive.
- **Rejection** — the society refused, with a code. Codes are terse, society-specific, and frequently point at a party who is not the reader ("writer not found", "conflicting claim", "invalid publisher chain"). Translating a code into *an action by a named person* is the whole value of this feature.
- **Silence** — nothing came back. **This is the failure the domain exists to solve and it produces no event at all.** It must be manufactured into an event by the expected-by alarm (`10.01.03` D-03), because nothing else will.

The distinction that must survive downstream: **rejected is better than silent**. A rejection is a fact with a reason and a next step. Silence is a year of accumulating black-box money that `10.05.01` will later "discover" for the same user, from the same platform, that failed to register it. The product must not be proud of finding money it lost.

Conflicts deserve separate treatment from rejections. A conflicting claim means *someone else told the society they own this*, which is not a data-quality problem — it is domain 09's dispute, discovered by domain 10, at a society that will hold the money until it resolves.

### Happy Path

1. Acknowledgement returns via `10.01.03` and is parsed per work
2. Work's state for that society + territory becomes **registered**, with the acknowledgement as evidence
3. Any ISWC returned is written back to the work's identifier record (domain 09)
4. Registration state unblocks downstream expectation: this work should now earn from that body, on that body's distribution calendar (`10.09`)
5. Statements later arrive naming it (`10.02`), closing the loop from split to money

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Silence past expected-by | Manufactured alarm. **The domain's headline failure mode** | Overdue, escalated, with the society and the batch named — never a spinner |
| Rejection: "writer not found" | The named writer's IPI is wrong or unaffiliated (`10.01.01`). The fix is another person's | The person and the action, not the society's code |
| Rejection: conflicting claim | Someone else claims this work at this society. Not a data error — a rights dispute discovered by the collections system | Routed to domain 09; money held at the society meanwhile |
| Rejection reason is unintelligible | Common. Society codes are terse and assume institutional literacy | Translation is a per-society knowledge asset, and where it is absent the platform must **say so** rather than paraphrase a guess |
| Registered at one society, silent at another | Normal and invisible. One territory pays, another doesn't, and nobody notices which | State is per society **and** per territory — never one flag |
| Acknowledged, then later un-registered | Societies do reverse. The platform's belief was true and is now stale | Belief has an age; a stale ack is not proof |
| Batch rejected for format (`10.01.03`) | Every work stalls for a technical reason that is the platform's fault | Must not be shown as a user problem |
| Registered against the wrong party | A typo'd IPI (`10.01.01`) registers a stranger. The ack is *positive* — the system believes it succeeded | The worst case in the domain: a confident, wrong, green tick. Subsumed by this file's Q-03 — the detection path is a reconciliation between this feature's registration state, `10.09`'s expectation and `10.02`'s observed statements. `[PENDING — /create-prd-architecture]` |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Unregistered | Never submitted | Honest absence, with the reason (blocked, or never attempted) |
| In flight | Delivered, within expected-by | Expected-by date, always |
| Registered | Acknowledgement received | Registered at that body/territory, dated, with evidence |
| Rejected | Rejection code returned | Reason translated to an action and a named owner |
| Conflicted | Society reports a competing claim | Routed to 09; money held at source |
| Overdue | Expected-by breached, silence | **Alarm.** The feature's reason to exist |
| Stale | Registered, but splits since changed (`10.01.02`) | Re-registration needed; the society holds a wrong record |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | This is a status field on the work, not a feature | The sweep's implicit position — it produced no candidate for it, folding "rejection handling" into a bullet under delivery | ❌ **REJECTED, and the omission is instructive.** A status field is *read*; this state is **inferred from an absence**, decays, is per-society *and* per-territory, and its most important value (`overdue`) is produced by a clock rather than by any counterparty. The parent domain's Overview independently identifies this loop as the hard part while the candidate list omits it — a sweep tuned for coverage named the visible act (delivery) and missed the failure mode that decides whether the act worked. That is a general lesson for the remaining drills, not just this one. |
| DT-02 | Silence should be modelled as pending until something arrives | The default in every integration ever built | ❌ **REJECTED — categorically, and this is the domain's central design claim.** A pending state that never resolves is *precisely* the mechanism by which a year of royalties becomes black-box money. Nobody notices, because nothing is red. The platform must synthesise the event the counterparty never sent: expected-by, breach, alarm. **The uncomfortable corollary**: `10.05.01` black-box recovery is marketed as the strongest activation event in the corpus ("we found you £800") — but if this feature works, WeJammin is the reason its own users have less black-box money to find. **The activation event and the core competence are in tension**, and that should be said out loud rather than discovered in a roadmap meeting. |
| DT-03 | A rejection is a bad outcome | Plain reading — the registration failed | ❌ **REJECTED, and inverting it is the honest product framing.** Rejected is *better* than silent: a rejection is a dated fact with a reason and an owner. Silence is a slow, invisible loss. If this feature's success metric were "rejection rate", it would optimise toward submitting less — the exact wrong behaviour. The metric is **time-to-known-outcome**, and a fast rejection beats a hopeful pending every time. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | Registration state is **per work × per society × per territory** — never one flag on a work | Registered at PRS is not registered at GEMA. A single flag makes territorial leakage undetectable. |
| D-02 | Silence is **synthesised into an event** via expected-by; indefinite pending is forbidden | DT-02. It is the exact mechanism that produces black-box money. |
| D-03 | Registration state is a **belief with an age**, not a fact | The transport offers no status call (`10.01.03` DT-01). Every read is an inference from the last mention. |
| D-04 | Rejection reasons are translated into **an action and a named owner**, or the platform says it cannot translate | A paraphrased guess at a society code is worse than an honest "we don't know what this means". |
| D-05 | The success metric is **time-to-known-outcome**, not rejection rate | DT-03. Optimising rejection rate optimises toward not submitting. |
| D-06 | Conflicts route to domain 09; they are not rejections | A competing claim is a rights dispute, not a data-quality failure. |
