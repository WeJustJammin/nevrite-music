# Feature: CWR & Society File Exchange

> **Number**: 10.01.03
> **Parent**: [Society Registration & Delivery](./10.01-society-registration-delivery-index.md)
> **Status**: [SURFACE]
> **Last updated**: 2026-07-23

## Overview

The **transport**: emitting CWR (Common Works Registration) files in the version a given society accepts, delivering them by whatever channel that society actually uses, and receiving the acknowledgement files that come back. CWR is a fixed-width, record-typed format from the pre-web era, versioned (2.1, 2.2, 3.0) with uneven adoption, and each society layers its own quirks on top of the standard.

This is deliberately a thin, boring feature with a hard boundary: it moves bytes and knows nothing about royalties. The interesting things live on either side of it — the payload (`10.01.02`) and the acknowledgement's meaning (`10.01.04`).

## Behavior

Per society, the platform holds a **delivery profile**: CWR version, dialect quirks, channel (SFTP drop, portal upload, in some cases a human emailing a file), batch cadence, file naming and sequencing rules, and the shape of the acknowledgement that returns.

Two properties of this format make it unlike any modern integration and must not be designed away:

- **It is batch, not request/response.** You send a file containing many works and get an acknowledgement file back — hours or weeks later, sometimes partially, sometimes for a subset. There is no per-work status call. The registration state of a work is therefore always *inferred from the last file that mentioned it*, which is why `10.01.04` is a real feature rather than a status field.
- **Sequencing is stateful.** Files carry sender/submission sequence numbers; societies reject out-of-order or duplicate submissions. A retry is not idempotent in the way an HTTP retry is, and a naive resend can produce a duplicate registration — which becomes a conflict, which is worse than the failure it was trying to fix.

The platform must also accept that **the channel is sometimes a person**. Several societies still take submissions by portal or email. Modelling delivery as "always automated" produces a system that silently stalls for the societies where it isn't.

### Happy Path

1. Works reach registration-ready (`10.01.02`) and accumulate for a society's next batch
2. System emits a CWR file in that society's version and dialect, with correct sequencing
3. File is delivered via that society's channel
4. Acknowledgement file returns — possibly days later, possibly partial
5. Acknowledgement is parsed and handed to `10.01.04`, which decides what it means per work

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Society uses CWR 2.1, platform emits 2.2 | Whole file rejected — not one work, the batch | Batch-level failure; every work in it stalls together |
| Acknowledgement never arrives | The most dangerous failure, because nothing is *wrong* on screen. This is the parent domain's "rejection loop nobody notices for a year" | Must be a **timeout with a real alarm**, not an indefinite pending state. See `10.01.04` |
| Partial acknowledgement | Some works ack'd, some silent. Silence is not rejection and not acceptance | Per-work, never per-batch, resolution |
| Retry after ambiguous delivery | Sequence collision or duplicate registration | Retries must be sequence-aware; a blind resend is worse than waiting |
| Channel is a human portal | No automation exists at any price | Modelled as a manual delivery task, not hidden behind a spinner |
| Character encoding / non-Latin names | Fixed-width + legacy encodings mangle names outside ASCII. Real, and it disproportionately breaks non-Anglophone writers | Charset is a **per-society profile field** (D-02 — the profile is data, not code); what the emitter does with a character that profile cannot carry is a payload-shape question, same family as `10.01.06` Q-04. Precedent to follow — established for DDEX, **not yet ratified for this domain** — is `12.01.02` D-04: per-target derived rendering, canonical value never altered, both retained. `[PENDING — /write-be-spec]` |
| Society changes its dialect | Silent breakage of a working integration | Per-society profile is data, not code — see D-02 |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Accumulating | Works ready, batch not due | Next delivery window |
| Delivered | File transmitted | Sent, with a timestamp |
| Awaiting acknowledgement | Delivered, nothing back | Waiting — **with an expected-by date**, never open-ended |
| Acknowledged | Ack file parsed | Handed to `10.01.04` |
| Batch rejected | Format/sequence failure | Every work in the batch stalls; the reason is technical and must not be shown as the user's fault |
| Overdue | Expected-by passed | Escalated as a finding, not left pending |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | This is integration plumbing — architecture in a product costume, and should be routed to `/create-prd` rather than existing as a node | Node Classification Gate, "not-product" test. The candidate names a file format, which is exactly what an architecture concern looks like | ❌ **REJECTED, narrowly.** The generic machinery — retries, credentials, scheduling, webhooks — *is* a cross-cut (global `CX-M22`) and is routed there. But two things here are irreducibly product: **batch-with-no-status-call** means a work's registration state is inferred rather than read, which forces `10.01.04` to exist as a feature; and **the channel is sometimes a human**, which forces a manual-delivery task into the product. Both change what the user sees. A pure architecture routing would have deleted the reason `10.01.04` exists. |
| DT-02 | CWR is the format, so the platform should build a CWR emitter | The candidate's own framing ("CWR & Society File Exchange") | ❌ **REJECTED as too narrow.** CWR covers musical works and publishing. It does not carry neighbouring rights (`10.01.06` — SoundExchange and PPL use their own formats entirely), and it does not carry the MLC's ingestion (`10.01.05`). Naming the feature after CWR risks an architecture that models one format as *the* format, then bolts the others on as exceptions. The feature is **per-society delivery profiles**, of which CWR is the largest family. |
| DT-03 | An unacknowledged submission is a pending state | The obvious modelling; it has been sent, nothing came back, so it is in progress | ❌ **REJECTED — this is the single most expensive default in the domain.** An indefinite "pending" is exactly how a registration silently fails for a year while the user believes they are registered and the money accumulates in a society's black box (which `10.05.01` then sells back to them as a discovery). Every submission must carry an **expected-by date derived from that society's known turnaround**, and breaching it is an alarm, not a longer wait. The parent domain's Overview names this failure; the fix is refusing to model silence as progress. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | The feature is **per-society delivery profiles**, not "a CWR emitter" | DT-02. CWR does not cover neighbouring rights or the MLC; naming the feature after one format would make the others exceptions. |
| D-02 | A society profile (version, dialect, channel, cadence, turnaround) is **data, not code** | Societies change dialects without notice; a code-shaped profile means a deploy per society quirk, and there are dozens of societies. |
| D-03 | Every submission carries an **expected-by date**; silence past it is an alarm | DT-03. Indefinite pending is how a year of royalties disappears. |
| D-04 | Retries are sequence-aware; blind resend is forbidden | A duplicate registration becomes a society conflict, which is more expensive than the original failure. |
| D-05 | Manual/human delivery channels are **modelled explicitly** as tasks | Several societies have no automated intake. Hiding this behind an automated-looking UI produces silent stalls. |
