## Cross-Cut Details

### CX-01: Stage Plot Builder → Input List & Patch

**Relationship**: Every source on the plot (a mic'd amp, a DI'd keyboard, a vocal position)
generates one or more input list rows. This is a derivation, not a sync: the plot is upstream and
the list has no independent existence. It is the single design decision that eliminates the "plot
shows three vocal mics, input list has two" error class — not by checking for it, but by making it
unrepresentable.

**Role scoping**:
- **Producer**: authors the plot, refines the derived rows (mic choice, phantom, substitutability).
- **Musician**: places their gear on the plot and their sources appear on the list without them thinking about it.
- **Operator**: consumes the list, writes the patch column. Never sees the derivation.
- **Fan**: no visibility.

**Synthesis questions answered**:
1. **Shared state conflict**: The plot owns source existence; the list owns per-source detail. A row cannot be created without a plot item, and deleting a plot item must not silently discard the row's mic preferences and patch — it should orphan them visibly.
2. **Trigger chain**: Plot item added → row generated → channel count changes → diff re-runs (18.03.02) → possibly a new shortfall. Synchronous within the authoring session. If the diff fails, the row still exists — the derivation must not depend on the diff.
3. **Permission intersection**: A Musician placing their own gear on the plot creates input rows the Producer must then detail. Config-level plot access implies row *creation* — a permission in one feature creates work in another. This needs to be visible to the Producer, not silent.
4. **Notification fan-out**: If the plot changes after the venue patched, the venue must be re-notified (CX-04). Within the act, plot changes should notify whoever owns the input list detail.
5. **State transition conflict**: Two members editing the plot simultaneously generate rows concurrently. Row identity must be stable and derived from the plot item's identity, not from position in the list — or the patch column corrupts on re-order.

### CX-02: Input List & Patch → Monitor & IEM

**Relationship**: A mix is literally a subset of the input list plus levels. Remove a channel and
every mix referencing it is now wrong. This is the tightest coupling in the sub-domain and the
reason 18.05.03 cannot live in the rider: there is no channel to reference there.

**Role scoping**:
- **Producer**: sees which mixes break when a source changes.
- **Musician**: sets their own mix contents from the available channels — a UI that must not offer channels that don't exist.
- **Operator**: sees the resolved mix count and contents; not the editing.
- **Fan**: no visibility.

**Synthesis questions answered**:
1. **Shared state conflict**: The list owns channels; mixes hold references. A mix must never hold a copy of a channel — a copy would let the mix drift from the list, reproducing the exact error CX-01 exists to prevent one level down.
2. **Trigger chain**: Channel removed → mixes referencing it flag as broken, not auto-repair. Silent removal from a mix is how a performer loses their vocal in the wedge and finds out on stage.
3. **Permission intersection**: A member has Config on their own mix but only Config on *their own* inputs. They can reference a channel they cannot edit — read-reference across an ownership boundary, which is correct here.
4. **Notification fan-out**: A source change should notify anyone whose mix contained it. This is a real fan-out: one channel deletion can touch every member.
5. **State transition conflict**: Person-level mix defaults (18.05.03 D-03) reference channels from a *different act's* list. Resolution must be by role/instrument semantics, not channel index — 18.05.03 edge case 5.

### CX-03: Stage Plot Builder ↔ Monitor & IEM

**Relationship**: Bidirectional and easy to miss. A mix is sent to a *position* — so the plot
supplies the destination. But the reverse also holds: a wedge is a physical object that appears on
the plot *because* a mix needs it. Add a fifth mix on a wedge and the plot gains an item, the
backline manifest may gain a rental, and the stage footprint changes.

**Role scoping**:
- **Producer**: sees that adding a mix has physical consequences on stage.
- **Musician**: places themselves; their mix follows their position automatically.
- **Operator**: reads both to set the stage — wedge count and placement come from here.
- **Fan**: no visibility.

**Synthesis questions answered**:
1. **Shared state conflict**: Wedges are the shared object. Are they plot items that mixes reference, or mix outputs that render onto the plot? Provisional answer: the mix is authoritative (a wedge exists because a mix needs it), the plot positions it. Not yet settled — see Open Questions.
2. **Trigger chain**: Mix added on a wedge → plot item appears → footprint changes → stage-dimension diff may newly fail. A monitor decision can therefore make the act not fit the stage, which is a non-obvious chain worth specifying.
3. **Permission intersection**: A Musician moving their position on the plot moves their mix's destination without touching the monitor spec. Correct, but it means plot Config implicitly edits monitor routing.
4. **Notification fan-out**: Wedge count changes are venue-relevant (they supply them) — must reach the advance.
5. **State transition conflict**: If a member is deleted from the plot, their mix and wedge should not silently vanish — the mix may be reassigned rather than removed.

### CX-04: Input List & Patch → Stage Plot Builder (reverse invalidation)

**Relationship**: Medium confidence — a consequence rather than a designed flow. Once a venue has
filled the patch column, the act's plot is no longer freely editable in practice: changing sources
invalidates work someone else did. This is the same class of problem as the advance freeze
(18.03.05) appearing inside a document.

**Role scoping**:
- **Producer**: must see that editing the plot costs the venue rework.
- **Operator**: must be told, or they set the stage to a stale patch.
- **Musician**: unaffected directly, affected on the night.
- **Fan**: no visibility.

**Synthesis questions answered** _(Medium confidence — remainder deferred to Step 5)_:
2. **Trigger chain**: Plot source changed post-patch → affected patch rows invalidate → venue re-notified. Unchanged rows must keep their patch — invalidating the whole sheet for one added mic would guarantee it gets ignored.
5. **State transition conflict**: If the advance is frozen, this is a change-control event (18.03.05), not a document edit. The document-level and pack-level freezes must not disagree about what's editable.

| R-01 | 18.05.03 Monitor & IEM | 18.05.02 Input List & Patch (patch column) | Considered: does the monitor spec constrain the venue's patch assignment? | R-02 | 18.05.01 Stage Plot Builder | 18.05.02 Input List & Patch (as peers) | Considered whether these are peer documents that sync bidirectionally. Rejected — CX-01 establishes strict derivation. A bidirectional sync between a plot and a list is the incumbent model and is exactly why they contradict each other. The reverse edge that *does* exist (CX-04) is invalidation, not authorship. |

> **Notes for agents:**
> - CX-03's ownership question (are wedges plot items or mix outputs?) is the one genuinely unresolved modelling decision in this sub-domain. It is small but it determines whether adding a mix can make an act not fit a stage.
> - The R-02 rejection is the sub-domain's core discipline restated: derivation, not sync. Any future agent tempted to make the input list independently editable is reintroducing 18.05.02 DT-01's failure.
