# Feature: Day Sheet Generation & Distribution

> **Number**: 18.10
> **Parent**: [Show Production & Touring](./show-production-touring-index.md)
> **Status**: [PARTIAL]
> **Last updated**: 2026-07-17

## Overview

The single page every person on the tour reads each morning: where you are, what time the bus
leaves, when you're on, where you sleep. It is not a document anyone should *author* — it is a
render of the schedule (18.07), travel (18.12), crew calls (18.08) and venue facts (16) for one
date, scoped to what each recipient is allowed to see.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Read-only (own) | Receives their day sheet each morning — lobby call, travel, soundcheck, set time, curfew, hotel, wifi, weather. Sees per diem amount but no other person's pay. Cannot edit; can flag "this is wrong". |
| Producer | Full | Generates, previews per recipient, and distributes. Overrides any auto-derived line, adds free-text notes ("no catering — buyout"), and controls which sections each role receives. |
| Operator | Read-only (venue-scoped) | Receives the venue-relevant slice — load-in, crew calls, set times, curfew — with no travel, hotel, per diem or personnel detail. Often the day sheet is how the venue learns the final schedule. |
| Fan | None | Never receives a day sheet. Public day-of information (doors, set time) is published through domain 19/21, generated from the same schedule but a different artifact with a different trust boundary. |

## Behavior

One event date resolves into N role-scoped renders. The generation is deterministic from source
objects, so a schedule change makes the distributed sheet stale — which is the central design
problem. Distribution is push (notification + in-app) plus an exportable PDF for the reality that
half of touring runs on a printed page taped to a flight case.

### Happy Path

1. Producer opens tomorrow's date; the day sheet is already assembled from live data.
2. Producer reviews per-role previews (band / crew / venue) and adds a free-text note.
3. Producer hits distribute; each recipient gets their scoped version by push and email.
4. Recipients open it on a phone; it renders offline once cached.
5. A schedule change re-generates it and re-notifies only the roles whose slice changed.

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Schedule changes after distribution | Sheet is versioned; affected recipients re-notified with a changed-lines diff | "Day sheet v3 — soundcheck moved 16:00 → 17:30" |
| Recipient has no signal at the venue | Last cached version renders with a staleness stamp | "Cached 08:14 — may be out of date" |
| Source data incomplete (no hotel booked) | Line renders as a visible gap, never silently omitted | "Hotel: NOT BOOKED" in amber, not a blank |
| Someone works off a printed copy | Printed sheet carries a version stamp and short URL/QR for the live one | "v2 · wejamm.in/d/xy4z" in the footer |
| Crew member added after distribution | New member auto-receives the current version | "You've been added to [date] — here's your day sheet" |
| Operator opens their scoped link, sees no travel/pay | Scoping is enforced at render, not hidden client-side — the venue slice is a distinct rendered object that never contains per diem, rooming or personnel pay | Load-in, crew calls, set times, curfew only — no "hidden" section exists to inspect |
| Musician forwards their scoped link to a non-recipient | Link resolves to the forwarding recipient's own scope only; a viewer who is not a recipient of that date gets an access-denied, not a wider sheet | "This day sheet isn't shared with you" |
| Producer edits a note while a schedule change re-generates | Free-text overrides are annotations keyed to a line, not the document body, so a regen preserves them and bumps the version; last-write-wins on the same note with an edit stamp | "Note kept · sheet regenerated to v4" |
| Recipient flags "this is wrong" on a line | Flag routes to the Producer as an alert against that specific line + version; does not alter the sheet | Producer: "Musician flagged 'set time' on v3" |
| Distribution partially fails (bad email, unsubscribed push) | Per-recipient delivery status tracked; failed recipients retriable without re-sending to the whole list | "Couldn't send to 2 of 9 — retry" |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Loading | Date opened | Section skeletons |
| Empty | Date confirmed, nothing scheduled | "Nothing to render yet — add a schedule" |
| Populated | Sources resolve | Full sheet with per-role preview switcher |
| Error | Render/distribution failed | "Couldn't send to 2 of 9 recipients — retry" |
| Partial | Some sources missing | Sheet renders with explicit gap markers and a completeness count |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | The day sheet should be an editable document | Incumbent behaviour (Master Tour, Word templates) | ❌ REJECTED — the reason day sheets are wrong today is that they are hand-typed copies of data that has since changed. Render-only from live sources is the whole value. An override is an annotation on a line, not a fork of the document. |
| DT-02 | Staleness is the hard problem, not layout | Domain expert lens | ✅ CONFIRMED — a distributed PDF is a snapshot the moment it leaves. Versioning + changed-line diffs + re-notify of only affected roles is the minimum viable answer; a printed copy needs a version stamp because paper cannot be recalled. |
| DT-03 | Missing data should be omitted for a clean sheet | Design instinct | ❌ REJECTED — an omitted hotel line reads as "no hotel needed"; an amber "NOT BOOKED" reads as "someone forgot". Gaps must be loud. This is a safety property on driver-hour and load-in lines. |
| DT-04 | One sheet for everyone is simpler | Naive modelling | ❌ REJECTED — the venue must not see per diems or rooming; the band must not see crew pay. Role-scoping is not a nicety, it is the reason a single shared sheet can exist at all. |
| DT-05 | The renderer is generic across artifacts (advance sheet, tour book, itinerary) | Cross-cut lens | ✅ CONFIRMED — same mechanism, different projection. Recorded as the **Document Generation & Distribution** cross-cut rather than duplicated per artifact. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | Day sheet is a render, never an authored document | The industry's failure mode is hand-copied data that has since changed |
| D-02 | Kept as a domain-level feature, not placed in a sub-domain | It renders across five sub-domains and belongs to none of them |
| D-03 | Missing source data renders as an explicit gap, never an omission | An omitted line is indistinguishable from "not needed" |
