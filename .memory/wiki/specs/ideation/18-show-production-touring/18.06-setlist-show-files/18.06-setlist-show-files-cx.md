## Cross-Cut Details

### CX-01: Setlist Builder → Show File Custody

**Relationship**: The export manifest is derived from the setlist's order. This is the same
derivation discipline as the plot→input-list edge (18.05-cx CX-01): today a human keeps a paper
setlist and a numbered folder in sync by renaming files, and the failure — playing to the wrong
stems — is common and unrecoverable mid-song. Deriving the manifest makes the desync
unrepresentable.

**Role scoping**:
- **Producer**: re-orders the set and the export follows; sees which files are stale on the rig.
- **Musician**: re-orders the set without thinking about playback at all — that's the point.
- **Operator**: sees durations only; no file access.
- **Fan**: no visibility.

**Synthesis questions answered**:
1. **Shared state conflict**: The setlist owns order; files own content and version. A song with no file is fine; a file with no song is an orphan and must be visible (18.06.03 edge case 3), not silently dropped from the manifest.
2. **Trigger chain**: Set re-ordered → manifest re-ordered → **the rig is now stale**. The chain stops at the platform's boundary (18.06.03 D-01) — the export is a human act. This is the one place the derivation cannot complete itself, and the manifest+checksum exists precisely because of that gap.
3. **Permission intersection**: A Musician with Full access to the setlist can re-order it, which invalidates a rig export the Producer made. A permission in one feature silently invalidates another's work — the Producer must be notified, not surprised at soundcheck.
4. **Notification fan-out**: Any setlist change after an export must notify whoever owns the rig. This is the highest-value notification in the sub-domain.
5. **State transition conflict**: Two people re-ordering concurrently produce two manifests. Order must be resolved before export, and an export should record which setlist version it came from.

### CX-02: Setlist Builder → Stage-Ready Output

**Relationship**: A pure render, but with a hard constraint the source doesn't have: the output goes
to paper and to offline devices, so it cannot be silently corrected. Once tonight's setlist is on
the floor, editing the builder does not edit the floor. Version stamping is the only mitigation and
it is a partial one.

**Role scoping**:
- **Musician**: consumes their own view; edits the source freely up to print.
- **Producer**: generates and knows who is on which version.
- **Operator**: no access to either.
- **Fan**: no visibility.

**Synthesis questions answered**:
1. **Shared state conflict**: The builder is authoritative; the output is derived and non-authoritative. When the floor sheet and the platform disagree, **the floor sheet wins** — because that's what the band is looking at. This inverts the usual rule and is worth stating explicitly.
2. **Trigger chain**: Setlist change → re-render → re-issue → the previous version is loose in the world on paper. Unrecallable by design.
3. **Permission intersection**: Any band member can change the set; everyone's view changes. On a shared document with Full access for all members, a 17:00 re-order affects four people's stage sheets.
4. **Notification fan-out**: A late change must reach every performer, and acknowledgement matters — the same pattern as advance change control (18.03.05 D-04), at a much shorter time scale.
5. **State transition conflict**: A change made while someone's device is offline never reaches them. The version stamp is the only cue that they're on a stale sheet, which is why it must be visible in the view, not buried.

### CX-03: Setlist Builder ↔ Performed Setlist Capture

**Relationship**: Bidirectional and the sub-domain's most valuable edge. Forward: the plan pre-fills
the performed setlist, which is the *only* reason capture takes seconds and therefore the only
reason it will happen (18.06.04 D-05). Backward: measured durations from what was actually played
flow into the plan, so a tour's set timings get more accurate every night — and the curfew margin
downstream stops being a guess (18.06 D-04).

**Role scoping**:
- **Musician**: confirms the pre-filled list; their performance history accrues.
- **Producer**: corrects deviations and personnel; counter-attests.
- **Operator**: read-only on the performed setlist for their room; no access to the plan.
- **Fan**: sees the performed setlist only if published — the only Fan surface in this domain.

**Synthesis questions answered**:
1. **Shared state conflict**: **They must never merge.** The plan is intent and stays mutable; the performance is fact and freezes on confirmation (18.06 D-01). An uncaptured show has a plan but no fact, and must be shown as such — not as a performance (18.06.04 D-04).
2. **Trigger chain**: Show `performed` → capture offered pre-filled → confirmations → performance becomes an attested fact → feeds 02/10/01. Backward: confirmed durations → the plan's estimates improve. The backward flow must not rewrite a *frozen* performance — it only updates the mutable plan.
3. **Permission intersection**: The sharpest one in the sub-domain. Anyone can edit the plan; **nobody can unilaterally assert the fact**. Counter-attestation (18.06.04 D-03) means the permission model here is fundamentally different from every other document in the domain — it's the credits model, not the production model.
4. **Notification fan-out**: Capture requests every performer's confirmation, including deps who may not be tour members and may not have accounts. A guest performer's credit needs a person who isn't on the tour.
5. **State transition conflict**: Late capture (days later) races with memory. The reconstruction marker (18.06.04 edge case 3) is the honest answer — and it is the thesis in miniature: a fact captured on the night and a fact reconstructed on day six are not the same evidence, and the system must not pretend they are.

### CX-04: Stage-Ready Output ↔ Performed Setlist Capture

**Relationship**: Medium confidence, and a genuine design opportunity. The performer view is open,
in someone's hand, at the exact moment a song is dropped. It is the only surface present when the
deviation happens. If capture can piggyback on it — a tap on the song that didn't get played — the
"capture must take seconds" requirement is satisfied by a surface that already exists. But 18.06.02
D-02 says the view must require *zero* interaction during performance, so any capture must be after
the set, not during.

**Role scoping**:
- **Musician**: the person who knows what was skipped, holding the device that shows the plan.
- **Producer**: confirms afterward.
- **Operator**: no access.
- **Fan**: no visibility.

**Synthesis questions answered** _(Medium confidence — remainder deferred to Step 5)_:
2. **Trigger chain**: Set ends → the view offers "what actually happened?" → capture pre-filled from the sheet in hand. The tension with 18.06.02 D-02 resolves cleanly if capture is offered *after* the set, never during.
5. **State transition conflict**: The view is offline-first (18.06.02 D-03); capture made offline must queue and sync, and a queued capture is not yet an attested fact.

### CX-05: Show File Custody ↔ Stage-Ready Output

**Relationship**: Medium confidence, and possibly not a real edge. Cues on a performer's view often
correspond to playback events (a track starts, a click counts in), so the two documents describe the
same moments from different sides. But the platform is not in the playback path (18.06.03 D-01), so
it cannot know what the rig is doing in real time — which caps how tightly these can couple.

**Role scoping**:
- **Musician**: sees a cue; the rig fires a track. Nothing connects them but the setlist.
- **Producer**: authors both and keeps them consistent by hand.
- **Operator**: no access.
- **Fan**: no visibility.

**Synthesis questions answered** _(Medium confidence — deferred to Step 5)_:
2. **Trigger chain**: None at runtime, by design. Any real coupling (auto-advance by timecode) requires an integration D-01 rules out — see 18.06.02 Q-02. Both documents derive from the setlist, so their consistency comes from CX-01 and CX-02, not from each other.
