# Feature: Backing Tracks, Click, Timecode & Show File Custody

> **Number**: 18.06.03
> **Parent**: [Setlist & Show Files](./18.06-setlist-show-files-index.md)
> **Status**: [SURFACE]
> **Last updated**: 2026-07-16

## Overview

Custody and versioning of the files a modern show runs on: backing track stems, click, timecode
maps, and the session that plays them. **WeJammin does not play them** — that is Ableton's job on a
dedicated machine on stage. What WeJammin owns is knowing *which file is current*, which is the
actual unsolved problem: the folder is called `FINAL_v3_ACTUAL` and nobody is certain.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Config | Uploads their own stems or parts, sees which version tonight's show runs on, and knows whether the track they re-recorded made it to the rig. |
| Producer | Full | Owns the show files: versions them, maps them to setlist songs, and is the person who discovers at soundcheck that the rig has last month's version. The MD/playback lens. |
| Operator | Read-only (durations only) | Sees only that tracks exist and their durations, because that affects set timing and their curfew. Never has access to the act's audio — it is unreleased master material. |
| Fan | None | Never. These are unreleased masters and the most commercially sensitive files in the domain. |

## Behavior

Files attach to setlist songs, so the setlist's running order *is* the show file order — re-order
the set and the playback order follows, without anyone renaming a folder. Versions are immutable
with one marked current per date. The export is a manifest and a file set the playback rig ingests;
the platform's boundary is the moment the files leave for the stage machine.

### Happy Path

1. Producer uploads the tour's stems and click, attaching each to a setlist song.
2. Files are versioned; one version is marked current for the tour.
3. Setlist re-orders for tonight; the export manifest re-orders automatically.
4. Producer exports to the playback rig before the show; the manifest states versions.
5. A stem is re-recorded mid-tour; a new version is marked current and the rig is re-exported.

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Rig has a different version than the platform says | The core failure; the manifest and a checksum are the only defence | "Rig exported 4 Mar — 2 files changed since" |
| Files are enormous (multitrack stems, hours of audio) | Storage and transfer at scale — a real constraint on the tour bus | "3.2 GB — export over wifi before you leave" |
| Song not in the setlist but its files exist | Orphan files are visible, not hidden | "2 files not in tonight's set" |
| Timecode drives lighting/video cues | Files are inputs to systems outside the platform entirely | "Timecode map exported — verify against the LD's rig" |
| Uncleared sample in a backing track | Rights exposure travels with the file — links to 09 | `[PENDING — /ideate-discover Step 5 deepening]` |
| No signal at the venue to fetch the current version | Export must happen before travel; the rig cannot depend on connectivity | "Not synced — export before you lose signal" |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | **No playback engine.** The platform's boundary is the export to the rig | Hard-real-time audio on stage is a different product and nobody would trust a browser platform with it |
| D-02 | The setlist's order is the export manifest's order | Eliminates the human folder-renaming sync that causes wrong-stem failures |
| D-03 | Versions are immutable; one is current per date; a manifest + checksum enables verification | The platform cannot know what's on the rig — it can only let a human check |
