# Feature: Event Record & Lifecycle States

> **Number**: 18.01
> **Parent**: [Show Production & Touring](./show-production-touring-index.md)
> **Status**: [SURFACE]
> **Last updated**: 2026-07-16

## Overview

The single event record every other object in this domain hangs off — one show, one date, one
venue, one bill. It carries the lifecycle state machine (`enquiry → hold → confirmed → advancing →
advanced → day-of → performed → settled → archived`) that gates which production objects may be
created, edited, or frozen. Domain 17 owns the commercial deal; this record is the operational
twin that the deal creates on confirmation.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Full | Creates a one-off show or adds a date to a tour; sees the date's state on their calendar; for a DIY act they *are* the TM and drive the record from confirmed to settled. Cannot move the record to `settled` — that is 17's state. |
| Producer | Full | The production/TM lens: owns the record through `advancing → advanced → day-of`. Triggers the advance, freezes it, marks the show performed, opens the post-show report. |
| Operator | Config | Sees only their own dates. Confirms the date exists in their calendar, sets venue-side facts (doors, curfew, load-in windows), and accepts/declines the advance. Cannot change the artist's bill or lifecycle beyond their side of the handshake. |
| Fan | None | The event record itself is internal. Fans see a *derived public listing* (date, doors, set time, on-sale) owned by domains 19/21 — never the operational record. |

## Behavior

The record is created by a confirmed booking in domain 17 (or manually, for shows booked
off-platform). State is the domain's central gate: riders can be edited freely in `confirmed`,
enter change-control at `advanced`, and become read-only history at `performed`. Cancellation and
postponement are first-class states, not deletions — a cancelled show still has costs, deposits
and a settlement tail.

### Happy Path

1. Domain 17 marks a deal confirmed → an event record is auto-created and linked to the deal.
2. Producer opens the record; venue (domain 16), date, and bill are pre-filled from the deal.
3. Producer advances the state to `advancing`, which unlocks the advance workflow (18.03).
4. On completion of the advance the record moves to `advanced` and the production pack freezes.
5. On the day the record moves to `day-of`; after the show, to `performed`, which opens the
   post-show report (18.18) and hands settlement back to 17.

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Show booked off-platform | Record created manually; venue may be an unclaimed stub in 16 | "This venue isn't on WeJammin — capability diff unavailable" with an invite CTA |
| Date moves (postponement) | Record keeps identity and history; new date written; advance re-opens with a diff against the old date's venue facts | Banner: "Date changed — 6 advance items need re-confirmation" |
| Show cancelled after advance | State → `cancelled`; production objects preserved read-only; deposits/costs handed to 17 | Cancellation reason picker; "Costs already incurred: 3 items" |
| Venue delisted/closed between confirm and show | Capability data goes stale; diff degrades to unverified | "Venue data unverified — advance manually" |
| Two records created for the same date+venue+artist | Duplicate detection on (artist, date, venue) | Merge prompt showing both records' objects |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Loading | Record opened | Skeleton of the production pack tiles |
| Empty | Confirmed but nothing advanced | "Nothing advanced yet" with "Start advance" CTA |
| Populated | Objects attached | Production pack dashboard with per-object completion |
| Error | Linked deal or venue unresolvable | "Can't load the linked booking — retry / unlink" |
| Partial | Some production objects missing at `day-of` | Amber banner listing what never got done |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | The event record is the same object as domain 17's booking/deal and should not exist twice | Sweep boundary between 17 and 18 | ❌ REJECTED — different lifecycles, actors and lifespans. The deal is done when signed; the operational record's life *starts* there and runs weeks later with different people (crew, venue production) who must never see deal terms. One object would force fee visibility onto crew. |
| DT-02 | Cancellation is a terminal delete | Naive modelling | ❌ REJECTED — a cancelled show has a financial tail (deposits, non-refundable travel, incurred costs) and a reputational one. Cancellation is a state with its own workflow, not an absence. |
| DT-03 | A festival slot, a support slot and a headline show are the same record type | Domain expert lens | ✅ CONFIRMED — same record, different `role_on_bill` and a different set of objects the artist owns vs consumes. A festival slot advances against the *promoter's* production, not a venue's. |
| DT-04 | Postponement can be modelled as cancel + new record | Naive modelling | ❌ REJECTED — it destroys the advance history and the ticket link (domain 19 must roll tickets over, which requires record identity to survive the date change). |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | Event record is distinct from the booking/deal record (17) | Different actors, lifespans, and confidentiality — crew must never see the fee |
| D-02 | Cancellation and postponement are states, not deletions | Both have financial and ticketing tails that require record identity to survive |
