## Cross-Cut Details

### CX-01: Tour Container ↔ Routing Feasibility

**Relationship**: The container holds the sequence; the check tells you whether the sequence is
possible. Critically, this runs on **holds as well as confirmed dates** (18.11 D-03) — which is
what makes it useful rather than retrospective. An agent holding six dates wants to know which four
route before deciding what to confirm, and that is a question no existing tool answers.

**Role scoping**:
- **Producer**: sequences and checks in one loop; uses the check to argue for a travel day.
- **Musician**: sees the human consequence — "nine-hour drive after a 01:00 load-out".
- **Operator**: **no access to either** — the route is not theirs to see.
- **Fan**: no visibility.

**Synthesis questions answered**:
1. **Shared state conflict**: The container owns the sequence; the check owns nothing and writes nothing. It's a pure function of the sequence plus data from 16 (addresses, load-in windows), 18.07 (load-out times), 18.12.03 (driver rules) and 17 (radius clauses). Five sources, no writes — the same honest-checker structure as the curfew check (18.07-cx CX-01).
2. **Trigger chain**: Date added/moved/removed → affected legs re-check → verdicts update. **A failing check never blocks the sequence** — an agent must be able to hold an impossible route and then fix it. Same reasoning as the curfew checker and the advance freeze: a blocking gate gets bypassed by not using the tool.
3. **Permission intersection**: The check reads contract terms from 17 (radius clauses) that the Producer may not be entitled to see in full. It may need to report "this date violates a contract term" without exposing the contract — a real scoping problem, since the TM is often not the party to the agent's agreement.
4. **Notification fan-out**: A hold dropping in 17 can silently make the rest of the route infeasible (18.11.01 edge case 1). That must notify, because the consequence is two cities away and nobody is looking.
5. **State transition conflict**: Legs involving holds are speculative. When a hold confirms, the leg's verdict doesn't change — but its *consequence* does, because now you're committed. The verdict should probably re-surface at confirmation rather than assume it was read when it was provisional.

### CX-02: Tour Container → Itinerary & Tour Book

**Relationship**: The book is the container rendered. Same relationship as schedule→day sheet
(18.10) one scope up, and the same unsolvable problem: a compiled artifact in a van, on paper,
cannot be recalled. The book's job is to be correct *and* to be honest about when it isn't.

**Role scoping**:
- **Producer**: generates and re-issues, scoped per role.
- **Musician**: carries it, reads it in transit, needs it offline.
- **Operator**: **not a recipient** — the book would show them the whole route.
- **Fan**: no visibility.

**Synthesis questions answered**:
1. **Shared state conflict**: The container is authoritative; the book is derived and non-authoritative. But the printed copy in someone's hand is what they'll act on — the same inversion as the setlist floor sheet (18.06-cx CX-02). When they disagree, the human acts on paper.
2. **Trigger chain**: Route change → book re-compiles → re-issue → changed-pages summary → previous versions loose in the world. Every distributed copy stales instantly.
3. **Permission intersection**: **The scoping is doing heavy lifting.** One container renders a band book (no crew pay), a crew book (no deal terms), and nothing for the Operator. A scoping bug here leaks fees or personal data into the wrong hands — and per 18.11.03 DT-04 this is the domain's highest-PII artifact.
4. **Notification fan-out**: Only roles whose pages changed need re-notification; a blanket re-issue trains people to ignore it.
5. **State transition conflict**: A book compiled while dates are holds is largely fiction, and re-compiles as they confirm. The provisional marker (18.11.03 edge case 4) must be prominent, or people plan their lives around speculative dates.

### CX-03: Routing Feasibility → Tour Container (reverse mutation)

**Relationship**: Medium confidence — a decision-support flow rather than a data flow. An infeasible
leg doesn't change anything by itself; it presents the Producer with three options (add a travel
day, drop the hold, accept an illegal drive) and they mutate the container. The check's value is
that the options are visible *before* the dates are confirmed, which is the only time they're cheap.

**Role scoping**:
- **Producer**: the decision-maker; the only role that acts on this.
- **Musician**: lives with the outcome.
- **Operator**: no access.
- **Fan**: no visibility.

**Synthesis questions answered** _(Medium confidence — remainder deferred to Step 5)_:
2. **Trigger chain**: Infeasible leg → human decides → container mutates → re-check. Explicitly **not** automatic: the system does not insert travel days or drop dates, for the same reason it does not optimise routes (18.11.02 D-01) or make the weather call (18.17 D-01) — the trade-offs are commercial and human, and the platform can't see them.
5. **State transition conflict**: Adding a travel day changes per diems (18.13.01), hotel nights (18.12.01) and the budget (18.13.02). A routing fix cascades into three finance objects, and the Producer should see that cost before committing — otherwise the fix for one problem silently creates another.

## Rejected Pairs

| # | Source | Target | Reason for Rejection |
|---|--------|--------|---------------------|
| R-01 | 18.11.02 Routing Feasibility | 18.11.03 Itinerary & Tour Book | No direct interaction. Feasibility verdicts do not belong in the tour book — the book is a reference for people *living* the route, not a planning artifact, and "this leg is tight" is not something a band member in a van can act on. The feasibility check informs the sequence (CX-03); the sequence informs the book (CX-02). Transitive, not direct. |
| R-02 | 18.11.03 Itinerary & Tour Book | 18.11.01 Tour Container (as a writable view) | Considered: should editing the book edit the tour? Rejected — that would make a *render* authoritative, which is the exact failure the day sheet's D-01 rejects (18.10). The book is downstream; edits belong upstream. |

> **Notes for agents:**
> - CX-01's synthesis question 3 (reading 17's contract terms without exposing them) is a real permission problem this pass has not solved.
> - CX-03's synthesis question 5 is the most under-appreciated coupling in this sub-domain: **a routing fix is a finance change**. Adding a travel day to fix a drive costs per diems, a hotel night, and a day of not earning — and nothing currently shows that to the person making the call.
