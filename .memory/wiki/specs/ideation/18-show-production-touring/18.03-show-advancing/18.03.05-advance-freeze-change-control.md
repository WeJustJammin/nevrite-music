# Feature: Advance Freeze & Late-Change Control

> **Number**: 18.03.05
> **Parent**: [Show Advancing](./18.03-show-advancing-index.md)
> **Status**: [PARTIAL]
> **Last updated**: 2026-07-17

## Overview

The moment the advance stops being a conversation and becomes **the plan** — and the controlled
path for the changes that inevitably come after it. Without a freeze, "advanced" is a feeling and
every sheet is an untracked draft; with one, there is a single dated, versioned pack that everyone
provably worked from, and every later change is an event with an author, a reason, a blast radius,
and a notification. This feature is the object the other four advancing features hang off — the
checklist, the diff, and the sheet all describe an *open-ended conversation* until a freeze turns
them into a versioned artifact.

> **Deep Think addition** — not in the sweep's candidate list. See DT-01.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Producer | Full | Declares the freeze (with override + reason if hard items remain), and is the sole approver for every post-freeze change. Sees the change log, each change's blast radius, and per-recipient acknowledgement status. This is their accountability record when something goes wrong on the night. |
| Operator | Config (can request) | Requests a post-freeze change ("local support needs 20 minutes") as a **proposal**, never a unilateral edit to the artist's pack. Sees the frozen pack as the authoritative version for their room that night, and is notified of changes that touch their load-in, curfew, or backline. |
| Musician | Read-only | Sees that the show is advanced and a plain-language summary of what changed since freeze. Gets pushed only the changes that affect *them* ("soundcheck moved 90 minutes to 17:30") — not the full change log, which is the Producer's tool, not theirs. |
| Fan | None | Internal production feature. A late change with public consequence (doors moving, set time) reaches fans through domain 19/21's own notification path, never this one — this pack is production-confidential. |

## Behavior

Freeze converts the working advance into an **immutable, versioned pack**: rider as-agreed,
accepted redlines, schedule, contacts, backline, crew calls. Freeze requires zero *hard*-outstanding
items (18.03.01) by default, but can be overridden with a stated reason so real shows are never
driven out of the tool (see DT-04, D-03). Once frozen (`v1`), the pack is distributed and every
subsequent change is a **change-control event** with a four-step lifecycle: **proposed → approved →
applied → notified**. Each event carries a **blast-radius preview** naming who is affected and which
artifacts (day sheet, advance sheet, run of show, crew calls) go stale, and each new applied change
issues the next version (`v2`, `v3`, …) re-notifying only the affected roles with a changed-lines
summary.

**Critical vs routine classification** (resolves Q-01): a change is **critical** — and therefore
requires per-recipient *acknowledgement*, not just delivery — when ANY of:
- it lands inside the show-day window (**T-24h or later**), OR
- it moves a **time** a person must physically act on (soundcheck, load-in, doors, set time, curfew), OR
- it changes **who** is expected (crew call added/removed, contact swapped).
Everything else (a note edit, a corrected phone number that isn't the day-of contact, a backline
spec that both sides already verbally aligned) is **routine**: delivered and logged, no
acknowledgement required. Critical changes that go unacknowledged escalate (see States → Populated,
edge cases).

### Happy Path

1. Producer opens the freeze view at T-5d, sees zero hard-outstanding, and freezes the advance.
2. The pack is versioned `v1` and distributed; Producer, Operator, and each Musician work from it.
3. At T-1d the venue requests a load-in time change; it arrives to the Producer as a **proposal**, not an applied edit.
4. Producer sees the blast radius — 2 crew calls, the day sheet, the run of show — and approves.
5. `v2` is issued; only the affected roles are re-notified with a changed-lines summary; because the change moves a day-of time, it is flagged **critical** and acknowledgement is tracked per recipient.

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Show day arrives, advance never frozen | System auto-freezes at `day-of` (T-0) with open items recorded as unresolved, so a versioned pack always exists | "Auto-frozen with 4 items unresolved — recorded" |
| Hard item still open but Producer wants to freeze | Freeze allowed with an explicit override + mandatory reason; the override is stamped into the pack | "Freezing with 2 hard items open — state a reason" |
| Change needed with no time to approve (T-2h) | Emergency path: apply-and-notify in one step, author recorded, still versioned and critical | "Applied immediately by [name] — 9 people notified" |
| Change proposed by someone who left the tour | Proposal rejected at authorship check; only current participants can author | "You're no longer on this date" |
| Operator tries to edit the artist's frozen pack directly | Blocked — Operators can only *propose*; the edit is converted to a proposal awaiting Producer approval | "Sent as a request — the tour manager approves changes" |
| Cascade: a late setlist change alters run of show and curfew margin | Blast radius spans sub-domains, not just this pack; the margin breach is surfaced before approval | "This change breaks the curfew margin by 6 min" |
| Critical `v2` change unacknowledged near show time | Unacknowledged critical changes escalate from a passive notification to a direct nudge on the individual | "3 people haven't seen the 17:30 soundcheck change" |
| Two people approve conflicting changes at once (concurrency) | Version issue is serialized; the second approval re-bases on the new current version and re-shows its blast radius before committing | "The pack moved to v3 while you were reviewing — re-confirm" |
| Freeze on a show with an empty/never-started advance | Freeze is unavailable; nothing to version | "Nothing to freeze — start the advance first" |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | The sweep's advancing model is incomplete without a freeze | Deep Think — domain expert lens | ✅ CONFIRMED, node created — the candidate list had a checklist, a diff, and a sheet, all describing advancing as an *open-ended conversation*. Every real advance has a moment where it becomes the plan, and everything bad in live production happens **after** it: the change nobody was told about. Without a freeze there is no "the plan", so a change is a change to nothing and the sheets have no meaningful version. This is the object the other four hang off. |
| DT-02 | Change control means blocking changes | Naming instinct | ❌ REJECTED — changes are normal and constant in live production; blocking them makes the system something people work around, worse than the email chain. The goal is that a change is **authored, notified, and blast-radius-visible** — never that it's prevented. |
| DT-03 | Notification is enough | Naive modelling | ❌ REJECTED — a notification nobody opened equals no notification, and at 17:00 the difference is a crew member at the wrong door. Acknowledgement tracking on *critical* changes, with escalation, is the difference between a record and an outcome. |
| DT-04 | Freeze is a hard gate requiring zero open items | Process instinct | ❌ REJECTED — real shows freeze with things unresolved constantly. A gate that can't be overridden gets bypassed by not using the system. Override-with-a-stated-reason keeps the record honest *and* keeps people inside the tool — the same "make the lazy path the correct path" principle the Producer persona's anti-pattern demands. |
| DT-05 | "Critical" can be left to the author's judgement | Simplicity instinct | ❌ REJECTED — leaving criticality to the person making the change means the tired TM at T-2h under-flags exactly the change that matters most. A deterministic rule (day-of window OR a time-a-person-acts-on OR who-is-expected) removes the judgement call and makes acknowledgement predictable. Author may *escalate* routine→critical, never *demote* critical→routine. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | The freeze exists — advance completion is a state, not a percentage | Without "the plan", a change isn't a change to anything and versions are meaningless |
| D-02 | Change control authors and notifies changes; it never blocks them | A blocking gate gets bypassed by not using the system |
| D-03 | Freeze can be overridden with a stated reason | Real shows freeze with open items; an unoverridable gate drives people out of the tool |
| D-04 | Critical changes track acknowledgement, not just delivery | An unopened notification at 17:00 is a crew member at the wrong door |
| D-05 | "Critical" is classified by a deterministic rule (day-of window OR time-a-person-acts-on OR who-is-expected), not author judgement | Author under-flagging at T-2h is exactly when acknowledgement matters most (resolves Q-01) |
