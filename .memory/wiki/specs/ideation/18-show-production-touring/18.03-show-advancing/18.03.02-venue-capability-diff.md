# Feature: Venue Capability Diff & Requirement Reconciliation

> **Number**: 18.03.02
> **Parent**: [Show Advancing](./18.03-show-advancing-index.md)
> **Status**: [SURFACE]
> **Last updated**: 2026-07-16

## Overview

The engine that compares the act's structured requirements (rider, input list, stage plot,
backline) against the venue's structured technical truth (domain 16) and reports exactly three
things: what matches, what the room can't provide, and what nobody has enough data to know. This
is the single feature that justifies the domain's claim to be a wedge — no incumbent can compute
it, because none of them holds both sides.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Read-only | Sees the plain-language consequence: "this room has no bass rig — you're bringing yours or renting". Doesn't care about channel counts; cares whether their show works. |
| Producer | Full | The primary consumer. Reads the full diff, decides per shortfall whether to bring, rent, substitute or redline, and re-runs it as either side's data changes. |
| Operator | Config (supplies the truth) | Doesn't run the diff — *feeds* it. Their listing in 16 is one of the two inputs, so diff quality is a direct function of their listing quality. Sees the shortfalls raised against their room and can correct their data or accept the gap. |
| Fan | None | No visibility, no derived artifact. |

## Behavior

Both sides must be structured for the diff to exist — this is why 18.04's structured rider matters
and why an unclaimed venue stub degrades the feature to nothing. Every comparison resolves to
`match`, `shortfall`, or `unknown`, and **`unknown` is a first-class outcome that must never be
silently rendered as a match**. Shortfalls become advance items (18.03.01) and can trigger rental
sourcing (18.09.02).

### Happy Path

1. Advance opens; the diff runs across rider, input list, plot and backline vs the venue's spec.
2. Producer sees 31 matches, 4 shortfalls, 6 unknowns.
3. Producer resolves each shortfall — rent a bass rig, substitute the console, redline the towels.
4. Unknowns become questions on the checklist for the Operator to answer.
5. Operator answers; the diff re-runs; unknowns fall to zero and the advance can freeze.

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Venue not on WeJammin / unclaimed stub | Diff cannot run; degrades to a manual checklist, loudly | "No venue data — this is a manual advance. Invite the venue?" |
| Venue data is stale (listed console sold last year) | Diff is confidently wrong — the worst outcome; mitigated by post-show corrections (18.18) and data-age display | "Venue spec last updated 14 months ago" |
| Equivalence, not identity (Midas M32 vs Behringer X32) | Requires an equivalence model, not string matching; near-matches surface as a distinct outcome | "Console: near-match — X32 vs requested M32. Accept?" |
| Rider says "or similar" | Unstructurable intent; flagged as a judgement item, not auto-matched | "'Or similar' — needs a human call" |
| Requirement has no counterpart field in the venue schema | `unknown`, never `match` | "No data on 3-phase power at this venue" |
| Venue overstates capability to win the booking | Diff passes; failure surfaces on the night; post-show report corrects the record | Handled by the 18.18 → 16 truth loop |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Loading | Diff running | "Comparing 41 requirements against [venue]" |
| Empty | No structured rider yet | "Build a rider first — there's nothing to compare" |
| Populated | Diff complete | Three-band result: matches (collapsed), shortfalls, unknowns |
| Error | Venue spec unresolvable | "Couldn't read venue data — manual advance" |
| Partial | Diff ran with data gaps | Result with a coverage bar: "31 compared, 6 unknown, 4 uncomparable" |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | This is the domain's wedge and everything else supports it | Domain rationale + D-18 thesis | ✅ CONFIRMED — and the corollary matters more: the diff is **worthless without domain 16's supply**. This domain's value is entirely gated on venue-side data density. That is a sequencing fact the MoSCoW and the beachhead question (problem-statement Q-03) must absorb: 18 cannot be a beachhead ahead of 16. |
| DT-02 | String/spec matching is sufficient | Naive implementation | ❌ REJECTED — the interesting cases are all *equivalence*: an X32 is a fine substitute for an M32 for most acts and unacceptable for some; a 32-channel desk meets a 28-input list. Without an equivalence model the diff is either uselessly strict or dangerously loose. This is a real product problem, not an implementation detail. |
| DT-03 | Unknown can be treated as fine-until-proven-otherwise | Design instinct | ❌ REJECTED — a silent `unknown→match` is how a band arrives to a room with no 3-phase power. `unknown` must be visually and structurally distinct from `match`, and must block the freeze if the requirement is hard. The whole point is to eliminate the assumption. |
| DT-04 | Venue data quality is the venue's problem | Boundary lens | ❌ REJECTED — a confidently wrong diff is worse than no diff, because it removes the TM's instinct to check. Data age must be visible, and the post-show correction loop (18.18) is a load-bearing dependency, not a nice-to-have. |
| DT-05 | The requirement↔capability diff is specific to venues | Cross-cut lens | ⚠️ PARTIALLY REJECTED — the *mechanism* (structured requirement set vs structured capability set → match/shortfall/unknown with equivalence) recurs in casting (04: role needs vs musician skills), services (05: brief vs provider capability), and gear (13/15). Recorded as a cross-cut candidate at medium confidence; the *venue* diff and its equivalence model stay domain-owned. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | `unknown` is a first-class outcome, never rendered as a match | Silent unknown→match is how a band arrives to a room that can't run the show |
| D-02 | An equivalence model is required, not string matching | The interesting cases are all substitutions; strict matching is useless, loose matching is dangerous |
| D-03 | Venue data age is displayed on every diff | A confidently wrong diff is worse than none — it removes the TM's instinct to check |
