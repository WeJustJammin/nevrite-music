## Cross-Cut Details

### CX-01: External Import ↔ Claim Inbox

**Relationship**: Import creates credits about people who are not users, which become shells, which become the inbox's supply. The relationship is not simply "more import, more inbox" — it is non-monotonic. Below a matching-precision floor, additional import volume *reduces* inbox value, because a user shown other people's credits concludes the graph does not know who anyone is (`02.03.02` DT-03), and that judgement is about the whole product, formed in the first thirty seconds.

So the two features pull against each other: import wants density (`02.03.01` DT-01), the inbox wants precision. Import's throttle (`02.03.01` D-04) exists because of this pair, not because of any ingestion limit.

**Role scoping**:
- **Musician**: the beneficiary when precision holds; the casualty when it doesn't.
- **Producer**: their import creates other people's shells at the highest volume — one Producer's catalog can seed dozens.
- **Operator**: room-name chaos in external sources makes room shells especially duplicate-prone.
- **Fan**: neither feature exists for them.

**Synthesis questions answered**:
1. **Shared state conflict**: Import writes shells; the inbox reads them. Two imports naming the same non-user must converge on one shell, not two — otherwise the same human gets two inboxes and neither is complete. That convergence is `02.01.04`'s job, triggered here.
2. **Trigger chain**: Import → shell creation → match scoring → suggestion. A failed match is silence, not an error — the shell simply waits, possibly forever (`02.03.02` Unclaimed state).
3. **Permission intersection**: Yes, and it is uncomfortable: a Producer's import decision creates public-ish shells about third parties who never consented (`02.03.02` Q-02). One user's convenience is another person's exposure.
4. **Notification fan-out**: **The critical gap.** Shells have no notification channel (`02.03.02` DT-01). Import can create ten thousand shells and notify nobody. The loop only closes through a human telling another human.
5. **State transition conflict**: A shell being claimed while a new import adds credits to it — the claim must absorb the late arrivals rather than fixing the shell's contents at claim time.

### CX-03: External Import ↔ Claim Adjudication

**Relationship**: The sub-domain's most consequential internal fact. Import creates credits whose origin is a stranger's database entry; when two people claim one, **there is no corroborator inside the platform** because nobody here was there. Session-captured credits have a Producer who knows; imported credits have nobody (`02.03.03` D-01).

This makes the unresolvable case the *majority* case, since import outnumbers capture for years. It is not a process gap — it is sub-domain D-01 (import is reconstruction) surfacing as an operational consequence. Any attempt to fix it with a better adjudication process is `02.03.03` DT-01's rejected path: a fabrication with a case number.

**Role scoping**:
- **Musician**: may be permanently unable to claim a credit that is genuinely theirs, if they share a name (`02.03.03` Q-03).
- **Producer**: cannot corroborate a session they did not run and was never captured.
- **Operator**: same.
- **Fan**: absent.

**Synthesis questions answered**:
1. **Shared state conflict**: The contested credit is held unattached — neither claimant owns it. State belongs to adjudication; import is upstream and inert.
2. **Trigger chain**: Import → shell → two claims → contest → routed to a corroborator → **none exists** → permanently unresolvable. The chain terminates without a resolution, which most workflows do not allow for and this one must.
3. **Permission intersection**: Nobody has the permission that matters, because the knowledge does not exist on the platform. This is a knowledge gap wearing a permissions costume.
4. **Notification fan-out**: Both claimants are told it is unresolvable. That message must explain *why* (imported, not captured) or it reads as the platform being arbitrary — and it is in fact the platform's thesis being honest about its own limits.
5. **State transition conflict**: An unresolvable contest could later become resolvable if the session's Producer joins and captures the work retroactively. Whether contests re-open on new evidence is undecided. `[PENDING — Step 5]`

| R-01 | 02.03.02 Claim Inbox | 02.03.01 External Import (as a *feedback* edge) | Tempting: rejected suggestions should improve import matching. Feeding rejections back into import scoring would teach it that correct data is wrong. The negative assertion belongs to `02.01.04`'s resolution model, not to import. |
