# Feature: Identifier Resolution & Duplicate Merge

> **Number**: 02.01.04
> **Parent**: [Credit Graph & Discography](./02.01-credit-graph-discography-index.md)
> **Status**: [SURFACE]
> **Last updated**: 2026-07-16

## Overview

The plumbing that decides whether two credits refer to the same human, the same work, or the same room — and anchors each of them to the identifiers the rest of the industry uses (ISRC for recordings, ISWC for compositions, IPI/ISNI for people, plus the platform's own). Without this the graph fragments into thousands of near-duplicate nodes and cannot emit valid DDEX RIN (`02.08`), which means it cannot leave the building.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Config | Confirms or rejects merge proposals about **themselves** ("are these two you?") and links their own external identifiers (IPI, ISNI, PRO membership). Never merges other people. Sees the union of both discographies on accept. |
| Producer | Config | Confirms merges about **works** they created ("are these two recordings the same master?") — they are the only party who actually knows whether `MixV3_FINAL` and the released master are one recording. Also confirms room and party merges within their own sessions. |
| Operator | Config | Confirms merges about **their room** — studios are duplicated relentlessly by imports ("Abbey Road" / "Abbey Road Studios" / "Abbey Rd. Studio Two"). Nobody else can adjudicate this. |
| Fan | None | Never sees a merge. Post-merge they see a redirect from the old discography URL and a page with more credits on it. Explicit absence: merge is a destructive graph operation and fan-scale participation would be a vandalism surface. |

## Behavior

Two distinct jobs that are easy to conflate and must not be:

- **Anchoring** — binding a node to an external identifier. Deterministic when the identifier exists (an ISRC is an ISRC).
- **Resolution** — deciding two nodes are the same thing when no identifier says so. Probabilistic, and therefore never fully automatic for people.

The asymmetry that governs the design: **work merges are recoverable, person merges are not.** Merging two recordings wrongly annoys people. Merging two humans wrongly attributes one person's career to another — it moves reputation, and it may move money downstream via neighbouring rights (domain 10). So person merges require the affected human's confirmation; work merges can be proposed with higher automation.

This feature exists almost entirely because of `02.03.01` (external import). A pure capture-at-source graph has little duplication — everyone in the room is a resolved identity. The moment MusicBrainz, Discogs and PRO data land, duplication becomes the dominant data-quality problem.

### Happy Path

1. Import or capture creates a node that resembles an existing one (name, co-contributors, era, identifiers)
2. System scores the match and, above a confidence floor, raises a merge proposal — it does not merge
3. Proposal is routed to the party who can actually adjudicate (the human for people, the Producer for works, the Operator for rooms)
4. On confirm, nodes collapse: credits union, identifiers union, old URLs redirect, history retains both originals
5. On reject, a permanent negative assertion is written so the same proposal is never raised again

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Two genuinely different players, same name | Reject writes a "these are not the same" edge; both nodes carry disambiguators thereafter | "John Smith (drums, Leeds)" / "John Smith (keys, Bristol)" |
| One human, two identities, one is unclaimed | The claim flow (`02.03.02`) and the merge flow are the same act from the user's side and must not feel like two chores | One prompt: "these credits look like you" |
| Merge proposal about a party who never joins | Sits unresolved. **Never auto-merged** — an unattended merge of two humans is exactly the irreversible harm | Both nodes persist; discography split across them |
| Wrong merge confirmed | Unmerge must exist and must restore both nodes' credits intact | `[PENDING — /ideate-discover Step 5 deepening]` |
| Node has conflicting identifiers (two ISRCs) | Not a merge candidate — it is a data error. Held for correction (`02.01.06`) | "Conflicting identifiers" flag |
| Merging parties have contradictory credits on the same work (both credited as sole producer) | Merge surfaces the contradiction rather than silently unioning it | Contradiction shown pre-confirm |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Unanchored | Node has no external identifier | Soft prompt to link IPI/ISNI/ISRC; no blocking |
| Proposed | Match scored above floor | Merge proposal in the adjudicator's inbox |
| Confirmed | Adjudicator accepted | Collapsed node; redirect from the loser's URL |
| Rejected | Adjudicator declined | Permanent negative assertion; disambiguators applied |
| Unresolved | Nobody can adjudicate (unclaimed party) | Duplicate nodes persist, marked |
| Conflicted | Contradictory identifiers or credits | Held; routed to amendment |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | Person merges can be automated above a high enough confidence threshold, like every other entity-resolution system | Standard ER practice; the volume argument (imports will create tens of thousands of candidates) | ❌ **REJECTED** — a false-positive person merge silently transfers one musician's career to another, and downstream it can misroute neighbouring-rights income (domain 10). Its cost is not symmetric with its benefit at any threshold, and the victim may not notice for years. The volume problem is real but the answer is better routing of proposals, not auto-merge. Works and rooms are different — their false positives are annoying, not career-altering. |
| DT-02 | Identifier anchoring is optional polish; the platform's own IDs are enough | Walled-garden reflex — we own the graph, why care about ISWC | ❌ **REJECTED** — without ISRC/ISWC/IPI anchoring, `02.08` cannot emit valid DDEX RIN, domain 10 cannot register neighbouring rights, and the user's data cannot leave. That last point makes anchoring the concrete answer to the open question of whether the lock-in is **earned or hostile** (`problem-statement.md` Q-02). Anchoring is what makes it earned. |
| DT-03 | A rejected merge only needs to suppress that one proposal | Naive implementation | ✅ **CONFIRMED as insufficient** — rejection must write a durable *negative assertion*, not dismiss a notification. Import runs repeatedly; without a persisted "not the same", every re-import re-raises the same proposal and the user is asked forever. This is the difference between a system that learns and one that nags. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | Person merges are **never** automatic, at any confidence | DT-01. Asymmetric, potentially irreversible, financially consequential harm. |
| D-02 | Merge proposals route to the party with actual knowledge, not to an admin queue | The Producer knows if two masters are the same recording; an admin is guessing. Routing by knowledge is what makes the confirmation meaningful rather than a rubber stamp. |
| D-03 | Rejection writes a permanent negative assertion | DT-03. |
