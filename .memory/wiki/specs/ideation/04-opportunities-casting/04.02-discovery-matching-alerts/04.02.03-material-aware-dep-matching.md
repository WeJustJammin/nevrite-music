# Feature: Material-Aware Dep Matching

> **Number**: 04.02.03
> **Parent**: [Discovery, Matching & Alerts](./04.02-discovery-matching-alerts-index.md)
> **Status**: [SURFACE]
> **Last updated**: 2026-07-16

## Overview

Matching a dep or sub not on "is a drummer near London" but on "can play *this* set, on *this* date,
with *this* much time to learn it". The question a bandleader actually asks at 9pm when their
drummer drops out is whether the replacement already knows the 25 songs — and the answer is a fact
about material, not about instruments. This is the domain's clearest differentiation and the single
thing a Facebook dep group structurally cannot do: a group can broadcast the ask, but it cannot know
that the person reading it played that exact set twice last year.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Full | Both sides. As the MD/bandleader posting: sees candidates ranked by material confidence with the evidence stated ("played this set twice, 2025"), not a bare score. As the dep: receives an alert whose urgency is justified by that confidence (CX-05), and sees exactly what they'd need to learn and by when. |
| Producer | Read-only | Benefits indirectly — when depping a session player they inherit the same mechanic, but they rarely post dep calls and their material is a rough, not a setlist. Sees material confidence when a session player is proposed to them. |
| Operator | Read-only | Sees only the outcome: their Friday slot has a full band again. The Operator does not care who the drummer is, only that the show happens — which is precisely why this feature protects their revenue without their involvement. |
| Fan | None | Never sees dep matching. A Fan learning that the drummer they're watching is a last-minute sub is not information the band wants published, and the platform should not be the one to publish it. |

## Behavior

Material confidence is assembled from facts the platform holds because the work happened here:

| Signal | Source | Strength |
|--------|--------|----------|
| Played this exact set before | 18 Show Production (setlists) + 02 Credits | Strongest — a fact, not an inference |
| Played ≥N of these songs before, in any context | 18 + 02 | Strong |
| Recorded on these songs | 02 Credits | Strong, and a different kind — knowing the record ≠ knowing the live arrangement |
| Charts/stems available and time to learn | 07 Projects / 18 | Enabling condition, not confidence |
| Plays this repertoire/genre | 01 Profile (self-claimed) | Weak — this is what everyone else already does |

### Happy Path

1. Dep call raised from context (04.01.01 D-02) — the show already knows date, venue, setlist and fee.
2. Base match narrows to available + reachable (CX-04).
3. Material scoring runs on the survivors only — never on people who cannot be there.
4. Pool ranks by material confidence, evidence stated.
5. Cascade fires in confidence order (04.04.04), alert urgency justified by confidence (CX-05).

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| **No setlist exists** — the dominant real case at launch | Degrades to 04.02.02 base matching. The differentiator silently disappears. | Poster: "No setlist on this show — matching on availability and location only. Add a setlist?" |
| Setlist exists but no charts/stems | Confidence is computable; learnability is not. A dep who's never played the set has no path to learning it in 4 hours. | "Sam's free and local but doesn't know this set — no charts attached." |
| Setlist changes after matching | Score invalidated. Setlists change constantly, often on the day. | Re-score, or accept staleness? See Q-05 — the answer is bounded but not settled: `04.01.02` fixes already-invited positions as immutable, so whatever re-scoring does, it can only ever touch the **un-reached tail**. |
| Dep played the *recorded* version, never the live arrangement | Confidence overstates. The live version may be in a different key, half the length, with a different ending. | `[PENDING]` — needs 18 to distinguish arrangement versions. See Q-02. |
| Dep's credit history is private | Material knowledge derived from private credits (CX-04 synthesis Q3). Cannot be used to rank without exposing it. | `[PENDING]` |
| The set is covers, played by everyone | "Played this set" is near-meaningless for a function band doing the same 40 standards as every other function band | Confidence should discount ubiquity — an unmodelled and genuinely hard problem. See Q-03. |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| No material | Show has no setlist | Honest degradation to base matching, with the fix offered |
| Scoring | Setlist present, pool resolved | "Checking who knows this set…" |
| Ranked | Confidence computed | Pool with evidence stated per candidate |
| Stale | Setlist changed post-scoring | See Q-05 — whether this state re-scores the un-reached tail or is presentational only is open |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | Material scoring runs **only on the available+reachable survivors** | Ordering is a cost decision: scoring is expensive and worthless for someone who cannot be there. |
| D-02 | Confidence is **stated as evidence**, never as a bare score | "Played this set twice, 2025" is checkable by a bandleader; "87% match" is not, and this is a feature whose entire value is being believed. |
| D-03 | **Degrade honestly** when no setlist exists — say so, offer the fix | Silently falling back to a geo filter while branded as material-aware is the failure mode that destroys trust in the differentiator. |
| D-04 | Proposed `could` in MoSCoW despite being the domain's best feature | Its dependencies (02, 18) do not exist at launch (DT-02). Sequencing, not value. |
