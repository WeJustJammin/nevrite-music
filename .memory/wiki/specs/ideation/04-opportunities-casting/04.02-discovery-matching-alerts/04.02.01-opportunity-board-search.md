# Feature: Opportunity Board & Search

> **Number**: 04.02.01
> **Parent**: [Discovery, Matching & Alerts](./04.02-discovery-matching-alerts-index.md)
> **Status**: [SURFACE]
> **Last updated**: 2026-07-16

## Overview

The pull surface — browse, search, filter and save an intent across every published opportunity the
viewer is entitled to see. It is the thing the sweep called a "gig & job board", and it is the
product that Facebook groups and WhatsApp threads currently are: the parent domain names the dep
circuit, the function-band scene and the crew network as "the clearest displacement target in the
corpus". Its defining requirement is that the default view is not "everything" but "things I could
actually do".

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Full | The primary consumer surface. Browses ranked by fit, filters by paid-only / instrument / date / radius, saves intents that double as alert subscriptions (CX-01). The multi-hyphenate reality means they hold several intents at once — "bass, London, weekends" and "mixing, remote, any" are both live, and a UI making them pick one identity fails them per `personas.md`. |
| Producer | Full | Browses briefs, topline calls and session work. Less date-driven, more scope-driven — filters on deliverable type and format rather than on a calendar. Their board is quieter and they check it deliberately rather than reflexively. |
| Operator | Full | Inverted use: browses acts seeking support slots and crew seeking work, to fill *their* gaps. Their board is a supply board viewed from the demand side, which is why the same object serves them at all. |
| Fan | Read-only | Sees public postings only (04.01.02 open rung) — member-wanted ads and open calls read as ambient scene activity. No contact detail, no compensation, no requirement checklists, no targeted or invite-only posts. This lens exists because the board may be public for cold-start reasons (Q-01), and if it is, a consumer audience will land on it. |

## Behavior

### Happy Path

1. User opens the board. Default view is match-ranked (CX-02) — availability and radius applied before they ask.
2. User narrows by filter. "Paid only" is the filter that makes the board usable at all and is a direct consequence of the 04.01.03 compensation gate producing honest data to filter on.
3. User saves the intent. The save is not a bookmark — it becomes a standing alert subscription (CX-01).
4. User opens a post, sees the requirement checklist pre-evaluated against their profile (04.01.04), and submits (04.03.01).

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Cold start — board is nearly empty | The two-sided market's founding problem. An empty board teaches the user the product is dead and they don't return. | `[PENDING — /ideate-discover Step 5 deepening]` — seeding strategy is a product decision, not an agent call. See Q-02. |
| Matching unavailable | Degrades to an unranked but populated board — never to an empty one (CX-02) | Chronological listing, no "why this matched" |
| Filters exclude everything | Named loosening suggestion rather than a bare empty state | "0 results. Dropping 'within 10 miles' → 23." |
| Post fills while user is reading it | State change mid-view; for dep calls this is the *normal* case, not an edge one — minutes matter | "Just filled." Kept visible rather than vanishing under the tap. |
| Fan lands on a public dep call | Sees the headline, not the phone number. Contact gating is 04.01.02's escalation rule. | Public-safe rendering |
| Board scraped in bulk | Not a product behaviour — routed to `/create-prd-security`. Job boards are scraped aggressively and the whole value of a two-sided market is the pool. | — |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Loading | Board opened | Skeleton listing |
| Empty (cold start) | No posts exist | See Q-02 — the hardest state in the domain |
| Empty (over-filtered) | Filters exclude all | Loosening suggestion with the specific filter named |
| Populated | Posts matched | Ranked list with match reasons shown |
| Unranked | Matching degraded | Chronological, no match reasons |
| Saved-intent | Intent saved | Confirmation that it is now also an alert (CX-01) — the dual nature must be explicit or users will save intents and wonder why nothing arrives |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | The board's hardest problem is not search — it is **cold start**, and a board is the one feature whose value is entirely other people's supply | Reasoning about the two-sided market; the sweep's candidate 01 treats it as a listings UI | ✅ CONFIRMED as the dominant risk. ❌ REJECTED as solvable inside this feature — seeding is a go-to-market decision (import from where? partner with whom? fake it?) that belongs to the owner, not to a spec. Logged as Q-02. Noting it honestly beats specifying a search UI as though the pool exists. |
| DT-02 | A domain expert would expect the board to show **why** something matched, not just that it did — "you've played this set", "you're free", "2 miles away" — because an unexplained ranking in *hiring* reads as a black box deciding your income | Reasoning from the ranking-fairness hazard raised in the parent index Q-02 | ✅ CONFIRMED — match reasons are a transparency requirement, not a nicety, and they double as the honest surface for the fit-vs-quality question. If the board can't state the reason in a sentence a musician accepts, the ranking is probably doing something the product shouldn't do. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | The default board view is **match-ranked, not chronological** | "Everything" is a listings page; "things I could do" is a product. Chronological is the degraded state, not the default. |
| D-02 | Match reasons are **shown, always** | An unexplained ranking that decides who gets offered paid work is a black box in the wrong place (DT-02). |
| D-03 | Saving an intent **creates an alert subscription**, and says so | Per CX-01. Silent duality means users save intents, receive nothing, and conclude alerts are broken. |
