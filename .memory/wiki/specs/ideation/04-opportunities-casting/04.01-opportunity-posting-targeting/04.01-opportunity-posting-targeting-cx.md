## Cross-Cut Details

### CX-01: Compensation Gate ↔ Opportunity Post

**Relationship**: The compensation declaration is not a field on the post — it is a precondition of
the post's `published` state. A poster may draft freely, but the transition `draft → published`
evaluates the declaration and refuses on a missing or prohibited value (e.g. a submission fee
charged to applicants). This is the single mechanism that encodes the parent domain's stated
anti-Sonicbids position into behaviour rather than copy.

**Role scoping**:
- **Musician**: as poster, blocked until they state the fee or explicitly mark the post as an
  unpaid category the taxonomy permits. As applicant, they see the declaration as a first-class
  badge, not fine print.
- **Producer**: binds hardest here — "do a quick test mix and we'll see" is the canonical abuse and
  the gate names it.
- **Operator**: declares door split / guarantee / day rate. Door-split-only shows as such rather
  than masquerading as paid.
- **Fan**: not affected — cannot post.

**Synthesis questions answered**:
1. **Shared state conflict**: The post owns its state; the gate is a validator, not a co-owner. No
   merge conflict — the gate has no persisted state of its own beyond the declaration on the post.
2. **Trigger chain**: `publish` → gate evaluates → pass publishes, fail returns the post to `draft`
   with the specific unmet condition. Synchronous — an async gate would leak an unvetted post into
   the board.
3. **Permission intersection**: `[PENDING — /ideate-discover Step 5 deepening]` — whether a
   platform admin can override the gate for a vetted institutional poster is unresolved and is a
   Trust & Safety (24) boundary.
4. **Notification fan-out**: Gate failure notifies only the poster. Gate *pass* is what releases the
   post to the alert fan-out in 04.02 — so the gate is upstream of every alert.
5. **State transition conflict**: Editing compensation on an already-published post is the race —
   a bait-and-switch vector (publish paid, silently change to unpaid). Requires re-gating and
   probably applicant notification. Flagged in 04.01.03 Open Questions.

### CX-02: Type Taxonomy ↔ Eligibility Criteria

**Relationship**: Type is the key that selects the eligibility vocabulary. This is precisely why the
Crew and Camp candidates did not survive as separate nodes — a crew job differs from a dep call in
*which criteria are offered and required*, not in what the object is or how it flows. Type also
selects criteria that are legally rather than musically shaped (right-to-work, insurance, rigging
certification), which is why the vocabulary cannot be one flat list.

**Role scoping**:
- **Musician**: sees musical criteria (instrument, doubling, reading, transport, travel radius).
- **Producer**: sees skill/gear/DAW/delivery-format criteria.
- **Operator**: sees the legal and physical set — certs, insurance, load-in capability, right-to-work.
- **Fan**: no access.

**Synthesis questions answered**:
1. **Shared state conflict**: Taxonomy owns the type definitions; criteria attach to the post. Type
   change on a draft orphans criteria that the new type does not recognise — needs an explicit
   discard-or-map step, not a silent drop.
2. **Trigger chain**: Selecting type → criteria vocabulary loads. Sync, local, no failure path
   beyond an unknown type.
3. **Permission intersection**: Some criteria are *assertions about the applicant that the platform
   can verify* (a verified credit, a registered gear item) and some are self-claimed (right-to-work).
   The distinction matters and is unresolved — see 04.01.04.
4. **Notification fan-out**: None directly.
5. **State transition conflict**: Type is effectively immutable once published — changing a live
   post from "dep call" to "crew job" invalidates every submission against it.

### CX-03: Targeting ↔ Eligibility Criteria

**Relationship**: Two independent narrowing layers that posters routinely conflate. Targeting
answers "who is this shown to"; eligibility answers "who may submit". The contradiction case is
real and common: a poster hand-picks five trusted deps as an invite-only target list, then sets a
requirement (say, reads notation) that two of the five fail. The system must decide whether
targeting overrides eligibility (the poster explicitly chose these humans) or eligibility overrides
targeting (the requirement is real).

**Role scoping**:
- **Musician**: most exposed — the dep circuit runs on hand-picked lists where the poster's personal
  knowledge of the player outranks any criterion the system holds.
- **Producer**: same, for prior collaborators.
- **Operator**: less exposed — Operator targeting is usually pool-shaped (local, verified), not
  hand-picked, so eligibility doing the narrowing is the expected behaviour.
- **Fan**: no access.

**Synthesis questions answered**:
1. **Shared state conflict**: Both are attributes of the post; no separate owner. The conflict is
   semantic, not concurrent.
2. **Trigger chain**: Evaluated together at match time (04.02) and at submit time (04.03). A
   divergence between those two evaluations is a bug class worth naming now.
3. **Permission intersection**: **This is the crux** — an explicit invite is a permission grant.
   Recommendation to carry into Step 5: an explicit invite should *waive* eligibility with the
   failure shown to the poster, not silently exclude a human they deliberately named.
4. **Notification fan-out**: If eligibility silently suppresses an invited person, they are never
   notified — a silent failure with a real-world cost (the dep never knew they were asked).
5. **State transition conflict**: Tightening eligibility on a live post can retroactively invalidate
   already-submitted applications. Unresolved — see 04.01.04 Q-02.

### CX-04: Compensation Gate ↔ Type Taxonomy

**Relationship**: "Unpaid" is not uniformly abusive, and a gate that treats it that way will block
legitimate posts. Joining a band is unpaid and always has been; a rehearsal tryout is unpaid and
legitimate; an open-mic slot is unpaid and legitimate. A free test mix, a spec topline, and a
"paid in exposure" function gig are not. The type discriminator is what tells them apart, so the
gate's rule set is type-scoped rather than global.

**Role scoping**:
- **Musician**: the beneficiary of the nuance — member-wanted ads must remain postable.
- **Producer**: the constrained party — the unpaid types available to them are far narrower.
- **Operator**: door-split and open-mic types need honest categories rather than a binary.
- **Fan**: no access.

**Synthesis questions answered**:
1. **Shared state conflict**: None — the gate reads type, does not write it.
2. **Trigger chain**: Type → rule set selection → gate evaluation. A missing rule set for a new type
   must fail closed (block publication), not open.
3. **Permission intersection**: None.
4. **Notification fan-out**: None.
5. **State transition conflict**: Adding a type to the taxonomy without a compensation rule set is
   the deployment race. Fail-closed handles it.
