# Feature: Blind Review Mode

> **Number**: 04.03.04
> **Parent**: [Submission & Audition](./04.03-submission-audition-index.md)
> **Status**: [SURFACE]
> **Last updated**: 2026-07-16

## Overview

Anonymised assessment — the orchestral screen, rendered in software. Submissions are judged without
the reviewer knowing who made them, which is the standard remedy for the bias that casting is
notorious for. It carries the "blind/anonymised review" half of sweep candidate 04, and it is the
feature that sits in direct opposition to the domain's own differentiator: everything
04.03.02 does to make an application credible is exactly what blind mode must destroy.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Full | Submits anonymised, and pays a real cost for it — a player whose case is "I've done this twice" is reduced to whoever they are on the day. That reduction *is* blind review working as designed, and it is why the feature is not universally welcome among the people it protects. Sees clearly whether a post is blind before deciding to spend the effort. |
| Producer | Config | Enables it as poster. As a reviewer they are also the hardest to blind *from* — a Producer who knows the scene recognises a player in two bars and cannot un-know it. As attestor, their attestations are the de-anonymising payload (CX-01). |
| Operator | Config | Enables it for house auditions — orchestral, pit, house-band contexts where blind screening is already the professional norm and the expectation pre-exists the software. |
| Fan | None | Never reviews, never submits, never sees blind media. |

## Behavior

What must be stripped, and what cannot be:

| Layer | Strippable? | Notes |
|-------|-------------|-------|
| Name, photo, profile link | ✅ Yes | Trivial |
| Verified credits (04.03.02) | ✅ Yes — but this is the contradiction (CX-01) | Stripping them removes the application's entire evidentiary basis |
| Media metadata — filename, EXIF, DAW session name, render path | ✅ Yes, and **must** be | Every one is a real leak vector; DAW-rendered files carry all of them by default |
| Location, availability | ⚠️ Partially | A radius narrows the pool to a knowable set |
| **The audio itself** | ❌ **No** | A voice is a fingerprint; a player has a signature; a room has a sound. This is physics, not a gap. |
| Writing style in free-text answers | ❌ Not reliably | — |

### Happy Path

1. Poster enables blind mode at composition (04.01.01), for a type where it is coherent.
2. Applicants see the post is blind before investing effort.
3. Submissions capture with identity stripped — **at capture, not at render** (CX-01 synthesis Q2).
4. Reviewer assesses an anonymised set in the queue (04.04.01).
5. Un-blinding at shortlist: the normal real-world flow is blind first round, named final — which reopens the storage question (CX-01 synthesis Q5).

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Reviewer recognises the player in two bars | Unpreventable. Blind mode reduces bias; it does not eliminate identification, and claiming otherwise is a false promise. | — |
| Evidence stripped, application now has no basis | **The contradiction (CX-01).** A blind application is a take and nothing else. | See Q-01 — unresolved |
| Un-blinding at shortlist | Evidence must have survived the blind stage *somewhere*, so it was stored un-stripped and hidden at render — which is the design CX-01 says will leak | `[PENDING]` — see Q-02 |
| Small pool | Anonymity is statistical. In a pool of four bassists in one city, blind mode is theatre. | Warn the poster |
| DAW render leaks the session name | Stripped — but only if the strip actually covers every container and codec's metadata surface | Routed to `/create-prd-security` |
| Poster enables blind mode on a dep call | Incoherent — the whole point of a dep call is *who you are* and whether you know the set. Should not be offerable for that type. | Type-scoped availability |
| Blind post's notifications name the applicant | Classic side-channel leak (CX-01 synthesis Q4) | Routed to `/create-prd-security` |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | **Blind review and the platform's differentiator are mutually destructive**, and the sweep listed blind review as a neutral feature without noticing | Reasoning about candidate 04 against D-18 and 04.03.02 | ✅ CONFIRMED and **retained unresolved** (sub-domain D-03). A verified credit graph is the most de-anonymising data the platform holds — "bass on that record, 2024" identifies one human. Resolving this by quietly dropping blind mode would remove a real fairness instrument; resolving it by dropping evidence in blind posts makes blind applications evidentially empty. Both are real losses. It is a product-values decision, not an agent call. Logged as sub-domain Q-01. |
| DT-02 | A domain expert would say **the audio is unanonymisable and the software is not the screen**. The orchestral screen works because a curtain is physical and a violin is relatively anonymous. A vocalist cannot be blinded at all; a drummer's signature is audible to anyone who knows them | Domain reasoning about what blind review actually achieves in music | ✅ CONFIRMED — which bounds the feature honestly. Blind mode **reduces bias at the paperwork layer** (name, photo, CV, credits, school, who-you-know) and that is genuinely most of the bias in casting. It does not anonymise performance. The product must claim the former and never imply the latter, or it makes a promise about someone's livelihood that it cannot keep. |
| DT-03 | **Storing evidence un-stripped and hiding it at render is the naive design, and it will leak** — via notifications, via an API response, via a shortlist un-blind, via an admin view | Reasoning from CX-01 synthesis questions 1, 4 and 5 | ✅ CONFIRMED as the likely implementation trap. Stripping **at capture** is safer and genuinely lossier — you cannot un-blind for the final round, which is the flow most posters actually want. That trade-off is unresolved (Q-02) and it is an architecture decision with a security dimension, routed onward rather than guessed at here. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | The evidence contradiction is **retained and escalated, not resolved** | Both features are legitimate; silently dropping either is a decision disguised as an omission (sub-domain D-03). |
| D-02 | Blind mode is **type-scoped** | Incoherent for dep calls (the point is who you are and whether you know the set); coherent for auditions and house/orchestral work. |
| D-03 | The product claims **paperwork-layer bias reduction only**, never performance anonymity | The audio is unanonymisable (DT-02). Over-claiming makes an unkeepable promise about someone's income. |
| D-04 | Small-pool warning | Anonymity is statistical; four bassists in one city is theatre. |
