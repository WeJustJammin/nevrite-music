# Feature: Lesson Delivery & Session Record

> **Number**: 06.01.04
> **Parent**: [Lesson Booking, Packages & Delivery](./06.01-lesson-booking-packages-delivery-index.md)
> **Status**: [SURFACE]
> **Last updated**: 2026-07-16

## Overview

The lesson itself, and the artifact it leaves behind. The live room is consumed wholesale from the
`Real-Time Rooms, Presence & Audio Transport` cross-cut — this feature does not own transport. What
it owns is everything *around* the room that makes a lesson a lesson: the safeguarding gate that
must pass before anyone joins, the attendance evidence that settles a no-show, the recording under a
chaperone policy, and the **session record** — what we covered, what to practise, what to fix — which
is the seam where a delivered lesson becomes an assignment (06.03) and the credit becomes earned.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Full | **As Teacher**: joins the room, shares audio/screen/score, records if policy permits, writes the session record during or immediately after (the capture moment — see DT-01), assigns practice from inside the lesson, marks attendance. **As Student**: joins, plays, receives the record and the assignment, re-watches the recording, sees what to practise before leaving the room. |
| Producer | None | Not visible. A Producer running a paid remote session uses Services (05) + Real-Time Rooms directly; a lesson is not a session and the two must not share a room type — the safeguarding gate is the reason. |
| Operator | Read-only | As an academy or studio: sees room occupancy and attendance for rooms they own — never lesson content, never the recording, never the session record. Enough to run a building and a register; nothing more. This boundary is deliberate and is a safeguarding requirement, not a courtesy. |
| Fan | None | Not visible — no fan-facing entry point. |

## Behavior

Delivery is gated, then run, then recorded — in that order, and the gate is not skippable. Before a
join is permitted for any lesson involving a minor, the Safeguarding cross-cut must have satisfied:
teacher vetting current, guardian consent on file for this pairing, and the recording/chaperone norm
for 1:1 established. Only then does the room open.

The room itself is the cross-cut's. Layered on it: attendance/join evidence (which 06.01.03 needs to
settle no-shows), optional recording under policy, and the session record. The session record is the
highest-value artifact in the domain and the one most likely not to get written — which is a design
problem, not a discipline problem (DT-01).

`[PENDING — /ideate-discover Step 5]`: the in-person delivery path. If Q-03 on the parent index
resolves to "yes, in-person lessons are in scope", this feature needs a second delivery mode with no
room, no join log, and a materially heavier safeguarding surface (a physical meeting between an adult
and a minor). That is not a variant — it is a second implementation, and it is not written here
because the scope question is genuinely open.

### Happy Path

1. Occurrence's start time approaches; both parties get a join prompt
2. Safeguarding gate evaluates (vetting current, consent on file, policy set) — passes
3. Both join; presence and join times are recorded; recording starts if policy permits
4. Teacher teaches, shares audio/screen, marks up what needs work
5. Teacher writes the session record and assigns practice **inside the room**, before leaving
6. Lesson ends; credit is consumed (06.01.02); student receives record + assignment + recording

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Teacher's vetting expired this morning | Gate **fails closed** — the room does not open, no exception path | Both: "This lesson can't start — {teacher}'s check needs renewing." Teacher: renewal flow. Credit is **not** consumed and this is not a student no-show |
| Guardian consent not on file for a minor | Gate fails closed; booking should have caught this earlier, so this is a defence-in-depth failure | Guardian: consent request. Lesson postponed, credit intact |
| Student joins, teacher never does | Join log evidences it; 06.01.03 resolves in the student's favour automatically | Student: "{Teacher} didn't join — credit returned" |
| Network dies mid-lesson | Real-Time Rooms cross-cut owns reconnection; partial delivery is recorded | Both: reconnect banner; if unrecoverable, `[PENDING — Step 5]` on partial-credit treatment |
| Teacher records without consent | Blocked — recording requires the policy set at booking and (for a minor) guardian consent; there is no ad-hoc record button | Teacher: "Recording isn't enabled for this student" |
| Lesson runs long | `[PENDING — Step 5]` — does it burn a second credit, or is over-run free? Real teachers over-run constantly |
| Teacher writes no session record | Lesson completes and the credit still consumes — the record must not be a payment gate — but the student gets nothing durable and the domain's whole value proposition quietly fails (DT-01) | Teacher: prompt, escalating over time. `[PENDING — Step 5]` on whether it hardens further |
| Recording contains a copyrighted backing track | Domain 24 / DMCA surface — a lesson recording is UGC audio like any other | `[PENDING — /create-prd-security]` |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Loading | Room joining | "Connecting…" with device check |
| Empty | No session record written yet | Student: "No notes from this lesson yet". Teacher: the prompt |
| Populated | Lesson delivered, record written | Session record + recording + assignment, all on one card |
| Error | Room failed | Cross-cut's failure UI + "your credit hasn't been used" reassurance |
| Partial | Lesson ended early / one party dropped | Record flagged partial; credit treatment `[PENDING — Step 5]` |
| Gated | Safeguarding gate failed | Explicit reason + the specific action that clears it. Never a generic "unavailable" |
| Live | Both joined | In-room UI (cross-cut owned) + teacher's record/assign panel |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | The session record will not get written unless it is captured **in the room, while the lesson is happening** — and this is structurally the same problem as the Producer's split capture | `meta/personas.md` (Producer's "worst accidental": closes a project without capturing splits — "the design must make the lazy path the correct path"); `meta/problem-statement.md` root cause: "no system is present at the moment of creation, so the record is always a reconstruction" | ✅ CONFIRMED — and it is the reason this feature exists as more than a link to a video room. The teacher who writes notes "later that evening" writes them never; a lesson reconstructed from memory a week on is as lossy as a split reconstructed after three years. **The platform's thesis applies to teaching without modification**, which is a genuinely useful finding: the same in-the-room capture discipline that domain 07 uses for splits is what makes 06.03's practice tracking have anything to track. |
| DT-02 | A delivered lesson should generate a **verified credit** in domain 02, since the platform is already in the room and credits are the wedge | Thesis (D-18) — provenance is the wedge; the temptation to apply it everywhere is strong | ❌ REJECTED — a credit is proof you played on a *record*. "Took 40 piano lessons" is not a credit; it is a progress history, and it belongs in 06.03. Minting credits for lesson attendance would debase the credit graph, which is the platform's single most valuable asset, in exchange for a vanity metric. Logging this rejection explicitly because the pull toward it is strong and a later reader will re-propose it. **Where the wedge legitimately applies to teaching is the opposite direction**: verified credits earned elsewhere are what credential the teacher (06.02.02). |
| DT-03 | A lesson room is just the Real-Time Rooms cross-cut with a different label | The cross-cut list explicitly names "Education's live lesson room" as a caller | ❌ REJECTED — the transport is identical, but a lesson room has a **precondition no other caller has**: the Safeguarding gate. A Services remote session between two adults opens on click; a lesson may be an adult alone with a child, and must not open until vetting and consent are proven current. The cross-cut owns the pipe; this feature owns the lock on the door. |
| DT-04 | Recording is a nice-to-have convenience for students who want to re-watch | Naive product read — re-watching is the obvious student benefit | ❌ REJECTED as the primary driver. Recording's first function is **safeguarding** — the cross-cut lists "chaperone/recording norms for 1:1 lessons" as a control, i.e. the recording is the chaperone when no third adult is present. That inverts the design: recording defaults and consent flows are set by policy for child protection, and student convenience is the secondary benefit. It also means "let me turn recording off" is not a preference toggle — it is a safeguarding decision. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | The session record and next assignment are captured **in the room**, not afterwards | Per DT-01 — the platform's own thesis, applied to teaching. Capture-at-source or the record is a reconstruction. |
| D-02 | The safeguarding gate **fails closed** with a specific, actionable reason | Per DT-03. An education product that opens an adult↔minor room on a stale check is an existential failure, not a bug (the cross-cut's own framing). A generic "unavailable" is a support ticket and a angry parent. |
| D-03 | A lesson does **not** mint a verified credit in domain 02 | Per DT-02 — it would debase the credit graph, the platform's most valuable asset. |
| D-04 | Failure to write a session record does **not** block credit consumption | The teacher taught; withholding their pay over paperwork is hostile and would push lessons off-platform. The fix for an unwritten record is capture design (D-01), not a payment gate. |
