# Feature: Cue Mix Recall & Portable Monitoring Profile

> **Number**: 08.04.03
> **Parent**: [Talkback & Cue Mixes](./08.04-talkback-cue-mixes-index.md)
> **Status**: [SURFACE]
> **Last updated**: 2026-07-16

## Overview

Your headphone preferences follow you. A drummer who always wants the click loud, themselves louder, and
minimal talkback ducking should say so once — not rebuild it in every room, every session, forever. This
is the consolidation thesis applied to something small enough that nobody has bothered: the platform
already knows, so it should not ask again.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Full | Owns their monitoring profile — instrument-relative preferences ("my own input +4", "click prominent", "light talkback ducking"), saved once and recalled into every room. Sees what mapped and what did not when joining. Can keep several profiles for different contexts (tracking drums vs singing a guide vocal are genuinely different jobs). |
| Producer | Read-only | Sees that a performer recalled a profile — useful context for a mix they did not build, and it explains why a performer arrived already comfortable. Cannot read or edit the stored preferences themselves; those are private. Can still seed a starting mix (08.04.02), which the profile then overrides. |
| Operator | None | Not visible. Per parent D-03 the profile belongs to the person, not the room; a room-level default would compete with the person-level profile for the same slot and the person must win. An Operator's room capabilities are declared in 08.04.02, not here. |
| Fan | None | Not visible. No fan path into a jam room. |

## Behavior

The design problem is **mapping**, and it is the whole feature.

A stored preference is about *sources* ("less guitar"). A room provides *its* sources. These do not line
up: last session's guitar is not this session's guitar, this room has two of them, and the click the
profile wants may not exist. A naive recall that matches on source names produces confidently wrong
mixes — which is worse than no recall, because the performer trusts it and only discovers the error by
ear, mid-take.

So the profile must store preferences in terms that survive the trip:

| Stores well | Why |
|-------------|-----|
| Self level ("my own input +4") | Always exists, always means the same thing |
| Click prominence | Exists or does not — binary, unambiguous |
| Talkback ducking depth | Property of the person, not the room |
| Role-relative preferences ("rhythm section prominent") | Maps onto whatever fills the role |
| Overall headphone level | Universal |

| Stores badly | Why |
|--------------|-----|
| Named-source levels ("guitar −3") | The referent changes between rooms |
| Absolute source positions | Meaningless in a different room |

**Unmapped preferences are shown as unmapped, never silently approximated.** Per CX-02, the performer
must be told what could not be applied.

**Nothing auto-saves.** One weird room should not permanently corrupt someone's default.

### Happy Path

1. Musician sets up a cue mix they like and saves it as a profile, naming it for the context ("drums, loud click").
2. Later, they join a different room.
3. System recalls the profile and maps what it can onto the room's sources.
4. Musician sees their mix already close to right, plus a note on anything that could not be mapped.
5. They adjust what remains and play — having spent seconds, not minutes.

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Room lacks sources the profile references | Mapped parts apply; unmapped parts are flagged. Never silently approximated. | "Some of your saved settings don't apply here: {list}." |
| Room has sources the profile has never seen | They arrive at a neutral default, flagged as new. | New sources marked. |
| Profile fetch fails | Mix starts at a neutral default and says so. Must never start at a previous performer's mix — an obvious bug with an unpleasant failure. | "Couldn't load your profile — starting neutral." |
| Musician has multiple profiles | They pick, or the system suggests based on declared instrument. Suggestion, never silent selection. | Profile picker on join. |
| Musician's role differs from last time (drummer today, singing next week) | The reason multiple profiles exist. A single profile would be wrong half the time. | Picker. |
| Profile drifts stale as habits change | No auto-save means the profile only changes deliberately — which is the point, and also means it can quietly rot. | Explicit save prompt when the session's mix diverges materially. |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Empty | No profile saved | Neutral mix + "save this as your default?" after they have built one. |
| Recalled (clean) | Profile mapped fully | Their mix, ready. |
| Recalled (partial) | Some preferences unmappable | Their mix + explicit list of what did not apply. |
| Diverged | Session mix differs from profile | Unsaved-change indicator; explicit save available. |
| Error | Profile unavailable | Neutral default + honest explanation. Never someone else's mix. |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | The profile must store **role- and self-relative** preferences, not named-source levels — because the source names do not survive the trip between rooms and a name-matched recall produces confidently wrong mixes. | Domain reasoning: "guitar −3" is meaningless in a room with two guitars or none. "My own input +4" and "rhythm section prominent" survive anywhere. This is the difference between a recall that works and one that looks like it works. | ✅ CONFIRMED — and it is what makes the feature non-trivial. A naive implementation stores a dictionary of channel levels and is wrong the first time it is used in a different room. |
| DT-02 | This is the **consolidation thesis at small scale** — the platform is already in the room, already knows who you are and what you play, so asking you to rebuild your headphone mix every session is exactly the fragmentation the product exists to end. | `meta/problem-statement.md` (D-18): consolidation is what puts WeJammin in the room; being in the room is what makes capture possible. This is a tiny instance of the same logic — the value is not the mixer, it is that your preferences accumulate to your identity like everything else here. | ✅ CONFIRMED — and it is the honest reason this is a feature rather than a settings panel. It is also small: worth building only if the rooms exist at all (parent D-04). |
| DT-03 | The profile should auto-save at session end, since performers will not remember to. | Convenience framing, and superficially consistent with "make the lazy path the correct path" from `meta/personas.md`. | ❌ REJECTED — the persona instruction applies to *capturing facts that would otherwise be lost* (splits, credits), not to *overwriting a stated preference*. Auto-save means one unusual room (a weird foldback, a broken source, a one-off arrangement) silently becomes your permanent default, and you discover it three sessions later wondering why your click is wrong. The lazy path here is "keep what you told us", and that is already the correct one. Explicit save, with a prompt on material divergence. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | Preferences are stored role- and self-relative, never as named-source levels | Names do not survive the trip between rooms. See DT-01. |
| D-02 | Nothing auto-saves; save is explicit with a prompt on material divergence | One weird room must not become your permanent default. See DT-03. |
| D-03 | Unmapped preferences are shown, never approximated | A confidently wrong recall is worse than no recall, because it is trusted. |
| D-04 | The profile belongs to the person and lives at identity level | Multiple profiles per person, because the multi-hyphenate plays several roles. |
| D-05 | A failed recall starts neutral, never at another performer's mix | Obvious, and exactly the bug a room-scoped implementation produces. |
