# Feature: Session Pre-Flight & Rig Readiness Check

> **Number**: 08.06
> **Parent**: [Real-Time Jamming & Remote Sessions](./realtime-jamming-remote-sessions-index.md)
> **Status**: [SURFACE]
> **Last updated**: 2026-07-16

> **Deep Think addition** — not in the sweep's candidate list. Added because the entire category's
> support burden is "it doesn't connect", and a paid session that dies on a rig problem is a dispute,
> not an inconvenience.

## Overview

Proves everyone's rig works *before* the clock starts. Reachability, interface, buffer, bandwidth, disk
headroom, permissions — every one of these fails silently until the moment it matters, which is with a
client waiting and a session booked. This feature turns "it should work" into a green light somebody can
be held to, and turns a failed session from an argument into a known fact recorded in advance.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Full | Runs pre-flight before a session — ideally days before, when a problem is fixable rather than fatal. Sees a plain checklist of what is wrong with their rig and what to do about it. Can share their result with the Producer so they are not diagnosing over a phone call. |
| Producer | Full | Sees pre-flight status for **every** participant before the session starts. This is the persona whose client is paying by the hour while someone hunts for a driver. Can require pre-flight before a booked session and can see which participant is the risk. |
| Operator | Config | Runs pre-flight for their **room** as an endpoint and publishes the result as a saleable fact — "this room passes, here is its measured reach." Per `meta/personas.md`, their worst accidental behaviour is publishing a stale gear list so a band arrives to a room that cannot run their show. A dated pre-flight result is the direct antidote. |
| Fan | None | Not visible. No fan path into this domain. |

## Behavior

Pre-flight checks the things that fail silently and expensively:

| Check | The failure it prevents |
|-------|------------------------|
| Reachability (NAT/firewall traversal) | "It just says connecting" — the category's #1 support call |
| Audio interface present and claimable | Another app has the device; discovered at minute zero |
| Buffer / driver configuration | Latency blamed on the network for the whole session |
| Uplink/downlink headroom | The monitor stream degrades under a contract it cannot hold (08.03.01) |
| Local disk headroom | Capture dies mid-take (08.05.01) — the worst one, because it destroys the asset |
| Microphone / device permissions | Talkback silently dead |
| Measured latency to the counterpart | The verdict (08.01.02) is stale or absent |

**Pre-flight is a scheduled activity, not a launch gate.** Its value is being run *early* — a
reachability problem found three days out is a fixed router setting; found at the session start it is a
cancelled booking. A check that only runs at launch is a check that finds problems at the exact moment
they cannot be fixed.

**A recorded pre-flight result is commercial evidence.** When a paid remote session (booked via domain
05) fails on technical grounds, "whose fault" is a real dispute with real money attached. A dated,
per-participant pre-flight record turns that from memory-versus-memory into a fact — the same move the
thesis makes for credits, applied to blame.

**Pre-flight must not become a gate that blocks people from trying.** Consistent with 08.01.02 D-02: it
informs, records, and lets the user proceed.

### Happy Path

1. A session is booked (or a Musician plans a jam).
2. Each participant is prompted to run pre-flight, well ahead of the session.
3. System checks each item and reports pass/fail in plain language, not error codes.
4. Failures come with the specific fix — "another app is using your interface: close it" — not "device unavailable".
5. Producer sees all participants green before the session, or knows exactly who is the risk.

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Pre-flight passes, session fails anyway | Will happen — conditions change and a check is a snapshot. Pre-flight must not over-promise, or its one failure destroys trust in every pass. | Result carries its timestamp and conditions. "Passed at 14:02 Tuesday" is a fact; "you're ready" is a promise we cannot keep. |
| Participant never runs it | Common. Producer needs to know it was skipped, not assume pass. | Explicitly "not run" — never a neutral or blank state that reads as fine. |
| Passes days early; rig changes | Result goes stale. Staleness must be visible. | Age-labelled; re-run prompt near session time. |
| Fails on something unfixable (ISP-level) | Honest dead end for real-time — but not for the domain. Routes to Overdub Mode (08.07). | "Your connection can't do live sessions. Overdub works on any connection." |
| Disk headroom passes then fails (something else fills the disk) | Realistic. The check is a snapshot; capture needs its own live guard (08.05.01). | Re-checked at capture start. |
| Participant fakes/skips and blames the platform | Why the record matters. | Dated per-participant record, referenced by 05/24. |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Not run | Never attempted | Explicit "not run" — never blank. |
| Running | Checks in progress | Per-check progress. |
| Passed | All green | Timestamped result + conditions. Not a promise. |
| Failed | One or more red | Named failures + specific fixes, ranked by what blocks the session. |
| Stale | Aged since the run | Age label + re-run prompt. |
| Unfixable | Structural failure | Honest dead end + Overdub route. |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | A domain expert expects a **pre-flight check**, because the entire category's support burden is "it doesn't connect" — NAT traversal, device claiming, driver config — and none of those fail gracefully. The sweep's candidate list omitted it entirely, which is a coverage gap rather than a judgment call. | Domain reasoning + category evidence: Source-Connect's support and documentation are dominated by connectivity diagnosis; every network-audio tool ships some form of connection test. It is table stakes that reads as unglamorous, which is exactly why a sweep tuned for product concepts missed it. | ✅ CONFIRMED — added as a domain-level feature. Its absence would be discovered in the first week of real use, at maximum cost. |
| DT-02 | Pre-flight's value is **temporal** — it must run early, not at launch. A check at session start finds problems at the exact moment they cannot be fixed, which makes it a diagnosis of a disaster rather than a prevention of one. | Reasoning: a router/firewall fix takes days (or an ISP call). Finding it at minute zero of a booked session converts a fixable problem into a cancelled booking and a refund argument. | ✅ CONFIRMED — pre-flight is scheduled and prompted ahead of the session, not a launch gate. This inverts the obvious design (a "test connection" button next to "join") and is the difference between the feature working and merely existing. |
| DT-03 | This is infrastructure diagnostics and therefore not-product — it should be routed to `/create-prd` with the rest of the media infrastructure. | Adversarial: NAT traversal and device enumeration are plainly architecture. | ❌ REJECTED — **partially, and the split is real.** The *mechanisms* (STUN/TURN traversal, device enumeration) are architecture and are routed. What is product: the scheduling (DT-02 — when it runs is the whole value), the plain-language remediation, the shareable per-participant status the Producer acts on, the routing to Overdub Mode on unfixable failure, and **the dated record as commercial evidence** in a 05/24 dispute. Strip the product half and you have a "test connection" button that finds problems too late to fix — which is what the category already ships and why it does not work. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | Pre-flight is scheduled ahead of the session, not a launch-time gate | Its entire value is finding problems while they are still fixable. See DT-02. |
| D-02 | A result is a timestamped fact, never a promise of readiness | One over-promised pass that fails destroys trust in every subsequent one. |
| D-03 | "Not run" is an explicit state, never blank | A blank reads as fine, and the Producer needs to know it was skipped. |
| D-04 | Failures name the specific fix, not the error | "Another app is using your interface: close it" beats "device unavailable". |
| D-05 | Pre-flight informs and records; it does not block | Consistent with 08.01.02 D-02. |
| D-06 | The per-participant result is retained as commercial evidence | Turns "whose fault" from memory-versus-memory into a fact. |
