# Feature: Route-Aware Radius Correction

> **Number**: 08.02.02
> **Parent**: [Playable Radius & Peer Matching](./08.02-playable-radius-peer-matching-index.md)
> **Status**: [SURFACE]
> **Last updated**: 2026-07-16

## Overview

The learning loop that turns a plausible map into a trustworthy one. A predicted radius is arithmetic
on coordinates; a measured radius is what actually happened across accumulated probe history. This
feature owns the arbitration between them — deciding when enough real evidence exists to overrule the
prediction, and being honest with the user when the correction is bad news about their own connection.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Read-only | Sees their radius move over time and, crucially, *why* — "we estimated 340 miles; your last 14 sessions show 210, because your ISP routes you the long way round." Cannot edit it. Can trigger a fresh measurement (via 08.01.01) but cannot argue with the result. |
| Producer | Read-only | Sees corrected radii for people they might staff onto a live session, with the confidence attached. Cares about the confidence more than the number, because a shortlist built on one lucky probe is a session that fails with a client in the room. |
| Operator | Read-only | Sees their room's corrected reach. This is the number that determines what they can honestly advertise — and it is read-only precisely because it is the number they have the most incentive to inflate (`meta/personas.md`: worst intentional behaviour is misrepresenting the room's specs). |
| Fan | None | Not visible. No fan surface in this domain. |

## Behavior

`[PARTIAL]` — the arbitration rule is the substance of this feature and it is genuinely undecided.
What is confidently known:

**The correction must be confidence-weighted, not last-value-wins.** A single bad probe during a
transient network event must not permanently shrink someone's radius, and a single lucky probe must not
inflate it. The output is a radius *plus* a confidence, and the confidence is what downstream consumers
(the map, the predicate) need in order to present the number honestly.

**The correction is asymmetric in its consequences.** Shrinking someone's radius makes them less
discoverable and is bad news they did not ask for. Growing it is free. This asymmetry means the
threshold for shrinking should probably be higher than for growing — but that is a product judgment
about false positives vs false negatives, and it is the owner's call, not the agent's.

**The correction data is per-pair, not per-person.** Person A's radius is a summary over their pairwise
history; the underlying truth is always pairwise. The summary exists for the map's benefit.

`[PENDING — /ideate-discover Step 5 deepening]`: the actual confidence model, the sample thresholds,
the decay rate on old probes, and whether corrections are per-route or per-peer.

### Happy Path

1. A real session or probe completes; its measured latency is recorded against the pair.
2. System updates the pairwise history and recomputes the pair's measured radius contribution.
3. If accumulated evidence crosses the confidence threshold, the measured value supersedes the prediction for that pair.
4. The person's summary radius is recomputed and the map (08.02.01) and predicate (08.02.03) both move.
5. If the change is material, the user is shown what changed and why — with the cause named, not just the number.

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Cold start — no probe history anywhere | The prediction stands and the map says so. This is the normal state at launch and possibly forever if rooms are cut (parent Q-03). | Soft boundary + "estimated". |
| One anomalous probe (someone's housemate started a download) | Must not move the radius. This is the primary failure mode a naive implementation gets wrong. | Nothing — the outlier is absorbed. |
| User changes ISP or moves house | History is now about a network that no longer exists. Needs invalidation, and detecting the change is not trivial. | `[PENDING — Step 5]` |
| Correction shrinks the radius materially | Bad news the user did not ask for. Whether to notify is a real product question — see parent CX-01. | `[PENDING — Step 5]` |
| Probe history is sparse and contradictory | Confidence stays low; the map keeps the soft boundary rather than committing to a wrong hard one. | Soft boundary + "still learning". |
| Correction is used to infer a peer's network conditions | A privacy side channel: repeated probing reveals facts about someone's home connection. | `[PENDING — /create-prd-security]` |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Predicted | No usable history | Estimate, soft boundary, explicitly labelled. |
| Learning | Some history, below confidence threshold | Estimate + "refining based on N sessions". |
| Measured | Confidence threshold met | Hard boundary + sample count + last-updated. |
| Invalidated | Network context changed | Reverts to predicted; explains why history was dropped. |
| Error | Correction pipeline failed | Falls back to prediction, labelled. Never a silent stale value. |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | A domain expert expects **geographic distance to be a weak proxy** and the measured route to be the truth — so a product that ships only the prediction will be visibly wrong to exactly the users who matter most (dense-city users with bad peering, who are the highest-density collaborator pools). | Domain reasoning: internet routes follow peering economics, not geography. Cross-ISP and cross-border hops routinely add more latency than hundreds of miles of backbone. | ✅ CONFIRMED — this is why the correction is a feature rather than a tuning detail. Without it the map is arithmetic on coordinates wearing a lab coat. |
| DT-02 | The correction should be **confidence-weighted with an asymmetric threshold** — harder to shrink a radius than to grow one, because shrinking removes someone from other people's discovery on evidence they cannot contest. | Reasoning: the cost of a false shrink (someone loses work invisibly) exceeds the cost of a false grow (a session is attempted and fails, which is recoverable and produces a probe). | ✅ CONFIRMED as the right *shape* — but the actual asymmetry is a product judgment about which error the owner prefers. Logged as Q-01. |
| DT-03 | The correction loop can bootstrap from measurement probes alone, without needing real sessions to ship first. | Optimistic framing that would rescue this feature from the MoSCoW cliff. | ❌ REJECTED — partially. A probe measures the network path, which is genuine data, so *some* bootstrapping is possible without rooms. But the thing being predicted is whether people can *play*, and only a real session validates that a given ms figure was musically workable for a given instrument pair. Probes calibrate the network model; they cannot calibrate the musical threshold (08.01.02 Q-01). So this feature is not fully rescued from the room dependency, and parent Q-03 stands. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | The output is a radius *and* a confidence, never a bare number | Downstream consumers cannot present the number honestly without knowing how much to trust it. |
| D-02 | Confidence-weighted, never last-value-wins | A single anomalous probe permanently shrinking a radius is the naive implementation's defining bug. |
| D-03 | The underlying truth is pairwise; the personal radius is a derived summary | Prevents the incoherent "whose radius wins" question. Consistent with 08.02.01 D-03. |
| D-04 | Corrections are explained by cause, not just shown as a number | "Your radius shrank" is alarming; "your ISP routes you the long way round" is actionable. |
