# Feature: Overdub Mode (Latency-Independent Tracking)

> **Number**: 08.07
> **Parent**: [Real-Time Jamming & Remote Sessions](./realtime-jamming-remote-sessions-index.md)
> **Status**: [SURFACE]
> **Last updated**: 2026-07-16

> **Deep Think addition** — not in the sweep's candidate list, and the most consequential omission in it.
> **Most "remote session" work never needed low latency at all.** This is the mode that does the actual
> job, runs on the locked stack, and needs none of the media infrastructure the rest of the domain demands.

## Overview

A remote player tracks against locally-buffered playback, records locally at full quality, and their take
is aligned server-side afterward. **Network latency is irrelevant** — the player is not playing *with*
anyone in real time; they are playing *to* something already downloaded. A guitarist overdubbing onto a
finished bed, a vocalist doing a comp, a session drummer replacing a programmed part: none of these need
sub-30 ms, and all of them are what people mean when they say "remote session."

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Full | Receives a bed (the existing arrangement) and a brief, plays to it locally with zero network latency and full monitoring quality, records locally, uploads takes. Can do multiple takes and choose. Works on any connection, from anywhere — the playable radius (08.02) does not apply. Per `meta/personas.md`, this persona lives on a portfolio of small income streams; this is the mode that makes remote session work actually accessible to them. |
| Producer | Full | Sends the bed and the brief, receives aligned takes, comps them into the project. Can attend live via the monitor stream (08.03) if they want — but crucially does not need to, which means the session no longer requires two calendars to intersect. Per `meta/personas.md`, they are the capture point; the attendance record (08.05.04) fires here identically. |
| Operator | Config | Largely peripheral — a studio can host an overdub as a room, but overdub's whole point is that it needs no special room. An Operator's endpoint is one option among many, and this is the one feature in domain 08 where their rig is not an advantage. Honest to say so. |
| Fan | None | Not visible. No fan path into this domain. |

## Behavior

**The reframe**: domain 08 is built around a physics problem (the ~25–30 ms ensemble ceiling) that caps
the playable radius at a few hundred miles. Overdub Mode sidesteps the physics entirely, because a
player tracking to local playback experiences **zero** network latency in their monitoring. Their own
input is local; the bed is already on their disk. There is nothing to be late.

What is required, and it is all cheap:

| Requirement | Where it lives |
|-------------|---------------|
| Deliver the bed to the player | File transfer. Storage + CDN. |
| Player monitors bed + own input | Local. Their machine, their interface, no round trip. |
| Record locally at full quality | 08.05.01 — already the design |
| Align the take to the project timeline | 08.05.02 — trivial here: the bed *is* the reference |
| Bind the take to the human | 08.05.04 — identical certainty |

**Alignment is dramatically easier in overdub than in a jam.** The player recorded against a known,
identical bed, so the bed is the alignment reference. There is no clock-drift-between-peers problem
because there are no peers — one recorder, one reference. The hardest part of 08.05.02 largely
evaporates.

**This is the one feature in domain 08 that runs on the locked stack.** Per `meta/constraints.md`
(Astro/Cloudflare/Supabase) and the domain index's own admission that real-time jamming "will not run on
Cloudflare Workers + Supabase and needs dedicated media infrastructure" — overdub needs file storage,
background processing, and no media infrastructure at all.

**And the provenance still lands.** The attendance record (08.05.04) is identical: one identity, one
track, observed with certainty, confirmed at session end. The thesis half of domain 08 survives intact
without a single millisecond of real-time transport.

### Happy Path

1. Producer creates an overdub request — the bed, the brief, what they want, by when.
2. Musician accepts; the bed downloads to their machine.
3. Musician plays to the bed locally, monitoring with zero network latency at their interface's real quality.
4. They record takes locally; take as many as they like; the network is doing nothing.
5. Takes upload; alignment (08.05.02) places them against the bed; attendance record (08.05.04) binds them to the human.
6. Producer receives aligned takes in the project (07), with the credit evidence already attached.

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Bed changes after the player started | Their take is against a stale reference — a real and common problem when a mix keeps moving. | `[PENDING — /ideate-discover Step 5 deepening]` — likely: bed versioning, with a warning. |
| Player's sample rate differs from the bed | Take needs resampling; risks drift if handled naively. | System handles; must be verified, not assumed. |
| Player's monitoring latency (their own interface) is bad | Their problem, not the network's — but it still ruins their timing, and they will blame the platform. | Pre-flight (08.06) covers it. |
| Player uploads nothing | Same leverage dynamic as 08.05.01 Q-02, minus the room. | `[PENDING — Step 5]` |
| Producer wants to attend live | Optional via 08.03 monitor stream. The point is that it is optional. | Available, not required. |
| Take arrives out of time despite alignment | Alignment placed the file correctly; the player played badly. Different problem, and the product must not conflate them — telling a musician the machine says they rushed is a fight. | `[PENDING — Step 5]` |
| Player is on a phone/tablet | Realistic given `meta/constraints.md`'s open mobile question — and overdub is the one mode where it is plausible. | `[PENDING — Step 5]` |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Requested | Producer sent the request | Brief + bed + deadline. |
| Downloading | Bed transferring | Progress; must complete before playing. |
| Ready | Bed local | Play. No network dependency from here. |
| Recording | Take underway | Local recording indicator. Network state irrelevant and shown as such. |
| Uploading | Take finished | Resumable progress. |
| Aligned | Processing done | Take placed against the bed. |
| Delivered | Producer has it | Take in the project; credit evidence attached. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | Overdub is a first-class mode, not a fallback | Most remote session work is this. See DT-01. The domain's name misled the sweep. |
| D-02 | The bed is the alignment reference | Removes the peer-clock-drift problem entirely — the hardest part of 08.05.02 evaporates. |
| D-03 | Playable radius does not apply | No physics constraint. Works from anywhere, on any connection. |
| D-04 | Provenance capture is identical to a live session | The thesis does not depend on real-time transport. This is the key MoSCoW fact for the whole domain. |
| D-05 | Producer attendance is optional | Removes the calendar-intersection requirement, which is a real constraint on remote session work. |
