## Cross-Cut Details

### CX-01: Membership ↔ Mandate Scope

**Relationship**: Every membership edge carries a mandate, explicit or default. The default case dominates — most bands will never open the mandate surface — which is why the default governs the real behaviour of this intersection for almost every user. **01.03.03 Q-01 is now RESOLVED** (D-07..D-10): a band's confirmed `permanent` edges are seeded with all seven activities up to USD 1,000 and escalate above it; `touring`/`staff`/`honorary` edges carry presence and no authority; no other org type is seeded at all.

**Role scoping**:
- **Musician**: in a band, their mandate is the seeded default until someone changes it — full authority up to the ceiling if they are a permanent member, none at all if they are touring.
- **Producer**: configures staff mandates deliberately (a business), and depends on band mandates being real at the capture moment.
- **Operator**: configures venue staff mandates; reads the counterparty's.
- **Fan**: no memberships, therefore no mandates.

**Synthesis questions answered**:
1. **Shared state conflict**: The edge owns the mandate. One writer per edge, guarded by whoever holds administer authority. No merge case.
2. **Trigger chain**: Membership ends → mandate terminates with it, atomically. They are one record, so there is no window in which a former member retains authority. This is the reason for modelling mandate as an edge attribute rather than a separate grant.
3. **Permission intersection**: Yes, and recursively — changing someone's mandate requires an administer mandate. The bootstrap is 01.02.02 (creator gets the first one). **Widened by 01.03.03 D-07**: in a band, `administer` is seeded on every confirmed permanent edge, so the recursion is peer-to-peer rather than creator-down — any permanent member may alter any other's mandate. Outside a band, D-10 leaves the bootstrap exactly as it was.
4. **Notification fan-out**: Mandate changes must notify the affected member — silently gaining or losing authority is disorienting, and silently *gaining* it is a security event. **Load-bearing under the seed**: confirming a membership *is* a gain of authority, so the invitation and the acceptance screen must both state what is being received (01.03.01 Happy Path step 4), or the seed becomes the silent gain this rule forbids.
5. **State transition conflict**: Two administrators editing one member's mandate concurrently — last-write-wins is acceptable here; both writers already hold full authority, so neither outcome is an escalation.

### CX-02: Representation ↔ Mandate Scope

**Relationship**: Representation scope is a mandate with two extra bounds (term, territory). This identity is the evidence for the sub-domain merge: if membership authority and representation authority were modelled separately, a manager and a band member with identical signing power would be authorised through two code paths, and the two would drift until one of them had a hole.

**Role scoping**:
- **Musician**: grants scoped authority to a manager; reads it in the same plain language as a bandmate's.
- **Producer**: represented, and represents (a studio booking out its engineers).
- **Operator**: the counterparty — needs certainty that the agent can bind the artist.
- **Fan**: absent.

**Synthesis questions answered**:
1. **Shared state conflict**: The representation edge owns its mandate; both parties can read it, only the granting party can widen it. Narrowing/revoking by the grantor is unilateral by design.
2. **Trigger chain**: Term expires → mandate lapses → context vanishes (01.01.03 D-01). No sweep. But see CX-04: nothing announces it.
3. **Permission intersection**: Yes — 01.03.03 D-03 (no mandate exceeds the granter's own) is what stops an agent sub-delegating recording scope they never held.
4. **Notification fan-out**: Grant and revocation notify both parties. Expiry is where it fails today (CX-04).
5. **State transition conflict**: Two agents claiming exclusive scope — detected on-platform (01.03.02 Edge Cases), invisible off-platform.

### CX-03: Membership ↔ Representation

**Relationship**: One graph, two edge types. A party's authority set is the union of what arrives via membership and what arrives via representation, and the enforcement cross-cut must not care which route it came by. The UI must care a great deal — "in the band" and "manages the band" are socially very different — but the authority model must not fork.

**Role scoping**: All three professional personas traverse both edge types daily. Fan traverses neither.

**Synthesis questions answered**:
1. **Shared state conflict**: Distinct edges, same party pair possible — a manager who is *also* a band member is real (the multi-hyphenate again). Their authority is the union; nothing needs merging.
2. **Trigger chain**: Independent lifecycles. Leaving the band does not end managing it.
3. **Permission intersection**: Union of both edges' mandates. The union is deliberately not additive beyond the ceiling — the higher of two value ceilings applies, not their sum. `[PENDING — Step 5: confirm]`
4. **Notification fan-out**: Independent.
5. **State transition conflict**: A person who both manages and is a member, leaving the band while retaining management, must not lose the org context. Falls out correctly because contexts are derived from the union.

### CX-04: Mandate Scope ↔ Representation (expiry)

**Relationship**: Derived contexts make expiry clean — authority simply stops. But "clean" is not the same as "good": nobody is told. An agent mid-negotiation on the last day of a term finds their context gone, with a live deal in it. The derivation solved the security problem and created a UX one.

**Role scoping**: Musician (their agent goes quiet), Producer, Operator (their counterparty evaporates mid-advance). Fan absent.

**Synthesis questions answered**: Medium — 1, 5 deferred. (2) Expiry → context removed, no compensating action exists today. (3) Yes — authority ends at expiry. (4) **Gap**: expiry should warn ahead of time and on lapse; currently unspecified. Flagged for Step 5.

### CX-05: Representation ↔ Membership (accepting on behalf of a band)

**Relationship**: A band appointing a manager is a band *decision*, not an individual one. So accepting a representation request for a band requires signing authority — and possibly a governance vote (01.04.01). The recursion is real: the mandate graph guards changes to the mandate graph.

**Role scoping**: Musician primarily. Producer where a studio appoints representation. Operator rarely. Fan absent.

**Synthesis questions answered**:
1. **Shared state conflict**: The band is the represented party; one member acts for it. If two members respond differently to the same request, the first authorised response wins and the second sees it resolved — the outcome is correct but may be socially explosive. `[PENDING — Step 5]`
2. **Trigger chain**: Request → mandate check → possible governance gate (01.04.01) → accept → edge exists.
3. **Permission intersection**: Yes — the defining case. Without a signing mandate, no appointment.
4. **Notification fan-out**: All members should see that their band gained a manager. This is not optional; it is how the worst-intentional case gets caught.
5. **State transition conflict**: Concurrent accept/decline by two members — see 1.

| R-01 | 01.03.01 Membership | 01.03.02 Representation (as a shared consent flow) | Both need invite→accept, so unifying the flow is tempting. Rejected: joining a band is social and permanent-ish; appointing an agent is commercial, scoped and term-bounded. One flow would either burden the band with commercial fields or strip the agent of the terms that define the relationship. They share a shape, not a flow. |
| R-02 | 01.03.01 Membership capacity | 01.03.03 Mandate activity | **AMENDED (DQ-02.6) — the rejection stands for *derivation* and is lifted for a *rebuttable default*.** Still rejected: **deriving** mandate from capacity ("drummers can't sign"). Capacity describes what you *do musically*; mandate describes what you may do *commercially*; the band's drummer is frequently the one who handles the money, and deriving one from the other encodes a false stereotype into the authority model. Now permitted: a **default** keyed to capacity, which is not a derivation because it is rebuttable in one act by anyone holding `administer`. 01.03.03 D-09 uses exactly this — the peer seed attaches to `permanent` only, and `touring`/`staff`/`honorary` start with nothing until the band grants it. The line is: capacity may *seed* authority, and may never *cap* it. Without this amendment D-09 would contradict a ratified item, so it is recorded here rather than left implicit. |
