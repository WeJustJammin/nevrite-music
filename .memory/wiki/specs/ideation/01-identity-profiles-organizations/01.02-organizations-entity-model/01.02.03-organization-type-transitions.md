# Feature: Organization Type Transitions & Multi-Type Entities

> **Number**: 01.02.03
> **Parent**: [Organizations & Entity Model](./01.02-organizations-entity-model-index.md)
> **Status**: [PARTIAL]
> **Last updated**: 2026-07-17

## Overview

Entities at the indie end of music refuse to hold still. A rehearsal room starts putting on gigs and becomes a venue. A band starts a label to release its own records. A studio opens a shop to sell the outboard it no longer uses. This feature covers an entity holding several types at once and moving between them **without losing what it accumulated** — the bookings, reviews, credits, followers and identifiers earned under the previous shape.

> **Deep Think addition** — no candidate in the sweep's list covers this. It surfaced by asking what an indie venue operator does in year two.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Full | Adds `label` to their band when they self-release. The band keeps its followers, its credits and its page; it gains release surfaces (12). They do not create "Band Records Ltd" as a second entity and start from zero. |
| Producer | Full | Adds `venue` to their studio when it starts hosting sessions-as-events, or `shop` when it sells gear. Their studio's reviews and credit history — the thing that took ten years — carry across. |
| Operator | Full | The archetype for this feature. The rehearsal-room-becomes-venue transition is the indie norm, and the entity's booking history is precisely what makes it credible as a venue. Losing it to a type change would be the platform destroying the asset it exists to accumulate. |
| Fan | None | Cannot transition entities. Sees the outcome: a page that gained a gig listing. The transition should be invisible to them — a fan who followed the rehearsal room keeps following the venue. |

> **Access levels**: Full · Config · Read-only · Reports · None

## Behavior

Type is a **set**, not a value (D-02 on the parent index). Adding a type is additive: the entity gains that type's attribute set (01.02.01) and its surfaces, and keeps everything it had. Removing a type is the risky direction, because the removed type's accumulated data — a venue's past shows, a shop's sold listings — must persist even though the surfaces that displayed them are gone.

The invariant: **transitions never fork the party identity**. Followers, reviews, credits, identifiers and bookings are attached to the party, not to the type, so they survive by construction rather than by migration.

Who may trigger a transition is a **membership-role** question, not a persona one: changing an entity's capability set is an owner/admin action within the org's membership model (01.03), not something any linked member can do. The three professional personas all show as Full in the Role Lens because any of them can *be* the org admin — the gate is the role they hold on this specific entity, not which persona lens they view it through.

### Happy Path

1. Operator's entity is a `studio`, two years of bookings and reviews behind it.
2. They start hosting gigs and hit "list a show" (domain 17).
3. System detects the entity has no `venue` type and offers to add it inline — not to create a new entity.
4. They confirm. The entity gains venue attributes (capacity, curfew, stage) and venue surfaces.
5. Same page, same URL, same followers, same reviews, two types. The studio's ten-year reputation is now the venue's reputation, which is exactly right.

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Type removed while its data is live (removing `venue` with shows booked) | Blocked, same rule as closure (01.02.02) | "You have upcoming shows as a venue. Resolve them before removing this capability." |
| Type removed with only historic data (past shows, no future ones) | Type removed; surfaces gone; history persists and remains citable | "Your past shows stay on your record. You just won't appear in venue search." |
| Entity accumulates many types (studio + venue + shop + label) | Allowed. The page gets busy — a composition problem for 01.06.01, not a validity problem | Multi-capability page |
| The band-starts-a-label case where the label really *is* a separate legal entity | Genuine ambiguity: on-platform they are one party; legally two. Modelling both would collide with the registered-details attribute | `[PENDING — /ideate-discover Step 5 deepening]` — see Q-01 |
| Reviews earned as a studio surface on the venue side | Correct by construction (attached to the party) — but is it *fair*? A great studio is not necessarily a good venue | `[PENDING — Step 5]` — see Q-02; also see domain CX-07 |
| Transition changes trader status obligations (adding `shop`) | Trader classification (01.08) is re-evaluated. Legal consequences follow the capability, not the type name | Trader disclosure flow triggers |
| A linked member who is not an owner/admin hits an action implying a missing type | The transition offer is not shown; the action is blocked at the point of use, not after they fill a wizard | "Only an owner or admin of this entity can add a capability. Ask them to enable venue listings." |
| Two admins add the same type concurrently (both hit "list a show" within seconds) | Idempotent — the type set is a set, so the second add is a no-op, not a duplicate or a conflict. No half-added type either way | Both see the entity with the venue capability once; no error, no double section |
| An admin adds several types with no intent to use them (squatting a type's search surface to look bigger, or to occupy a category) | An added type surfaces in that type's search only once its required attributes are populated and it has activity — an empty capability is present but not discoverable (see Partial state). Repeat abuse is a Trust & Safety signal (24), not a validity block | Type shows on the page but returns nothing in venue/shop search until it is real |
| Adding a type that was previously removed (re-adding `venue` after a season closed it) | Allowed and cheap — the historic data was never deleted (D-04), so re-adding the type re-lights the old surfaces over the same accumulated record | Past shows reappear under the re-enabled capability; no re-entry |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Loading | Type set fetch | Skeleton |
| Empty | Single type — the common case | No transition UI; the offer appears only when an action implies a missing type |
| Populated | 2+ types | Capability sections on the org page; each type's surfaces live |
| Error | Type add failed | Error with retry; no half-added type |
| Partial | Type added, its attributes not yet filled | Type's surfaces present but not yet discoverable (a venue with no capacity cannot be searched by capacity) |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | An entity has exactly one type, set at creation | The default assumption in the sweep's candidate list, which named "Organizations & Entity Model (band, label, studio, venue, agency, shop)" as if the parenthesis were an enum | ❌ REJECTED — it collides with the same physical address being a rehearsal room, a studio and a 120-cap venue, which is the indie norm, not an exotic case. One type per entity forces three entities, which fragments exactly the history that makes each of them credible. Type must be a set. This is a cheap decision now and an unaffordable migration later. |
| DT-02 | Type transitions are a settings screen | Naive framing | ❌ REJECTED — nobody navigates to a settings page to declare an identity change. The transition is discovered at the moment of the action that needs it ("list a show" → "you're not a venue yet, add it?"). Same pattern as facet addition in 01.01.01 — assertion happens at the point of use, not in a wizard. |
| DT-03 | What accumulates must attach to the party, not the type — otherwise every transition is a migration | Reasoning from the thesis: `problem-statement.md` says the platform's value is that facts accrete to an identity | ✅ CONFIRMED, and it is the whole feature. If followers/reviews/credits hang off the type, then a rehearsal room becoming a venue starts at zero — the platform would be *causing* the evaporation it exists to prevent. Attaching to the party makes survival the default and needs no migration code. |
| DT-04 | Any linked member can add a type, because the transition is offered at the point of an action they were already allowed to take | Naive read of D-02 (offer-at-point-of-use) | ❌ REJECTED — the point-of-use trigger governs *when the offer appears*, not *who may accept it*. Changing an entity's capability set alters its legal exposure (adding `shop` re-triggers trader obligations, 01.08) and its search presence; that is an owner/admin action under the membership model (01.03), not a member one. Otherwise a session player linked to a studio could unilaterally make it a shop. The gate is the org role, decoupled from the persona lens. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | Type is a set; entities may hold several at once | DT-01 — the indie reality, and unaffordable to retrofit |
| D-02 | Transitions are offered at the point of the action that needs them | DT-02 — matches how the assertion actually arises |
| D-03 | Followers, reviews, credits and identifiers attach to the party, never to the type | DT-03 — makes transition survival free and prevents platform-caused evaporation |
| D-04 | Removing a type removes surfaces, never history | Consistent with 01.02.02 D-03 (no deletion) |
| D-05 | Adding or removing a type is an owner/admin action under the membership model (01.03), gated on org role not persona | DT-04 — capability changes carry legal and search-visibility consequences a non-admin member must not trigger unilaterally |
| D-06 | Type add is idempotent and empty capabilities are non-discoverable until populated | Concurrency safety (set semantics) plus abuse resistance — a squatted type surfaces nowhere until it is real |
