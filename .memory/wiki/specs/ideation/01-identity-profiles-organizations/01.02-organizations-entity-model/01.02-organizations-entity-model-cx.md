## Cross-Cut Details

### CX-01: Types & Attributes ↔ Type Transitions

**Relationship**: Because type is a set, attribute sets must compose without collision. Two types that both define "capacity" (a venue's audience capacity, a rehearsal room's occupancy limit) would collide on a naive union. This is a real constraint on how 01.02.01 defines the taxonomy — it cannot assume its types are mutually exclusive.

**Role scoping**:
- **Musician**: band + label — attribute sets barely overlap; composition is trivial.
- **Producer**: studio + shop — overlap on address and opening hours; the union must not duplicate them.
- **Operator**: studio + venue + rehearsal — the worst case, and the most common one. Multiple near-synonymous capacity/space concepts.
- **Fan**: sees only the composed public page.

**Synthesis questions answered**:
1. **Shared state conflict**: The party owns the attribute values; types declare which attributes apply. Where two types declare the same attribute, it is one value on the party, not two — the entity has one address regardless of how many things it is.
2. **Trigger chain**: Type added → attribute set expands → previously-invisible fields appear unfilled. No rollback needed; unfilled attributes are a normal state (01.02.01 Partial).
3. **Permission intersection**: No. Mandate to edit the org (01.03.03) covers all its types uniformly `[PENDING — Step 5: could a member be mandated for only the shop and not the venue?]`.
4. **Notification fan-out**: Type addition notifies members (their org gained a capability) `[PENDING — Step 5]`.
5. **State transition conflict**: Two members adding different types concurrently is safe — set union is commutative. Genuine benefit of modelling type as a set.

### CX-02: Creation & Lifecycle ↔ Type Transitions

**Relationship**: The most valuable interaction in the sub-domain. Duplicate detection at creation exists to stop a split identity — and the single most common cause of a split identity is *not* two people naming the same band. It is one person whose entity already exists in a different shape ("I have a studio, now I need a venue, so I'll create one"). Detection that only matches names would let this through, because the user genuinely is creating a differently-named thing. It must recognise the *capability* intent.

**Role scoping**:
- **Operator**: the primary case — studio owner starting to host gigs.
- **Producer**: studio owner starting to sell gear.
- **Musician**: band starting a label.
- **Fan**: cannot create; unaffected.

**Synthesis questions answered**:
1. **Shared state conflict**: One party either way. The question is whether a *second* party gets created, which is precisely what this interaction prevents.
2. **Trigger chain**: Create attempt → detection → offer "add capability to your existing entity" instead. If the user refuses and insists on a new entity, that is allowed (they may be right — a genuinely separate business), and the Canonical Data cross-cut inherits the cleanup.
3. **Permission intersection**: Adding a type to an existing entity requires an owning mandate on it; creating a new entity requires nothing. This asymmetry is a perverse incentive — the *correct* action is harder than the wrong one. Flagged for Step 5.
4. **Notification fan-out**: Adding a capability notifies co-members; creating a second entity notifies nobody — which is how split identities go unnoticed.
5. **State transition conflict**: None.

### CX-03: Types & Attributes ↔ Creation & Lifecycle

**Relationship**: Lifecycle terminal states are type-specific. `dissolved` is meaningful for a band and meaningless for a shop; `closed` is meaningful for a shop and wrong for a band. A multi-type entity therefore has no single terminal state — a band+label that stops being a band still has a catalogue to administer.

**Role scoping**: Musician — dissolution (01.04.04). Producer/Operator — closure and dormancy. Fan — sees the resulting page state only.

**Synthesis questions answered**:
1. **Shared state conflict**: Lifecycle state is on the party; type is a set on the party. A multi-type entity with divergent terminal states per type is unmodelled — `[PENDING — Step 5]`, and it is the sharpest open question in the sub-domain.
2. **Trigger chain**: Closure blocked by live obligations (01.02.02 Edge Cases). Dissolution routes to 01.04.04's governance flow.
3. **Permission intersection**: Terminating an org requires an owning mandate; dissolving a band additionally requires whatever 01.04.01's decision rules say.
4. **Notification fan-out**: Yes — members, counterparties with live bookings, and (for `closed`/`dissolved`) followers, who see it on the public page.
5. **State transition conflict**: Dormant→active races are harmless. Closure vs an incoming booking is a real race and resolves at 17's booking gate.

### CX-04: Creation & Lifecycle ↔ Types & Attributes

**Relationship**: Progressive attribute filling means an org's data completeness tracks its usage, not its age. A venue created two years ago that has never been booked through the platform has an empty tech spec — and looks identical to a brand-new one. Freshness (01.02.01 D-03) and completeness are therefore both usage-derived, which is worth knowing before anyone builds a "profile completeness" nag.

**Role scoping**: Operator most affected (the richest attribute set, therefore the emptiest at rest).

**Synthesis questions answered**: Medium confidence — 1, 3, 5 deferred to Step 5. (2) Action needing an attribute → prompt at that moment. (4) No fan-out.
