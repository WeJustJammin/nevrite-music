# Feature: Organization Types & Type-Specific Attributes

> **Number**: 01.02.01
> **Parent**: [Organizations & Entity Model](./01.02-organizations-entity-model-index.md)
> **Status**: [SURFACE]
> **Last updated**: 2026-07-16

## Overview

The taxonomy of non-human parties and what each type actually carries. A band has a lineup and a catalogue; a venue has a capacity, a load-in and a curfew; a studio has rooms and gear; a label has an imprint and a release schedule; an agency has a roster; a shop has a returns policy and a trader status. The shared spine is small — every org is a party with a name, a profile and members — and everything else is type-specific, which is why this is a taxonomy and not a table of nullable columns.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Full | Creates and edits a band. Fills band-specific attributes: lineup, genre, home city, catalogue, the alias(es) it releases under. Does not see venue capacity or studio gear fields — they are not fields on their entity, not hidden fields. |
| Producer | Full | Creates and edits a studio: rooms, gear inventory, hourly/day rates, acoustic detail, remote-session capability. This is the entity that appears in 05 and 16, and the one they invoice from. |
| Operator | Full | The heaviest user of this feature. Venue attributes are the product: capacity, stage dimensions, PA/backline, load-in access, curfew, licence, age policy, accessibility. `personas.md` is explicit that a stale gear list means a band arrives to a room that cannot run their show — so these attributes are the safety-critical part of the taxonomy. |
| Fan | Read-only | Sees the public face of an org: a band's page, a venue's capacity and accessibility, a shop's returns policy. Never sees operational internals (rates, contact routing, staff). The Fan reads a venue page to decide whether to go, not to book it. |

> **Access levels**: Full · Config · Read-only · Reports · None

## Behavior

Every org shares a thin common spine: party identity, display name and trading name, profile surface (01.06), members (01.03.01), and optionally party identifiers (01.09). Beyond that, attributes are type-specific and owned by the domain the type serves — a venue's stage plot is specified in 16, not here. **This feature owns the taxonomy and the spine; it does not own the contents of each type's attribute set.**

That seam matters: if this file tried to specify venue capacity semantics it would duplicate domain 16, and the two would drift.

An entity may hold more than one type (D-02 on the parent index), in which case it carries the union of those types' attributes.

### Happy Path

1. Musician creates a band from their profile.
2. System asks only for what every org needs: name, and who else is in it.
3. Band exists immediately with a page, a member list and an actable context (01.01.03).
4. Band-specific attributes are filled progressively, from the surfaces that need them — a gig booking asks for the tech spec, not a wizard at creation time.
5. Attributes accumulate as a byproduct of use rather than as an onboarding tax.

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Org attributes go stale (venue's backline changed, band's lineup changed) | Staleness is a first-class state, not a silent lie. Attributes that other people rely on to show up in a physical room carry a last-confirmed date | "Confirmed 14 months ago" on the gear list; a prompt to reconfirm before advancing a show |
| An entity is genuinely two types (rehearsal room + venue) | Union of both attribute sets — D-02. Not two entities | One page, both capability sets |
| A type's attributes are needed by a domain that is not yet built | Attribute set is defined by the owning domain; absent domain = absent attributes. The spine still works | Org exists with the spine only |
| Someone creates a band that is really a solo alias | Allowed, and common. The distinction (Q-01 on 01.01.02) is not enforceable at creation | Both exist; no policing |
| Free-text vs structured attributes (genre, gear) | `[PENDING — /ideate-discover Step 5 deepening]` — structure enables matching in 04/05/17; free text is how musicians actually write. The tension is unresolved here and in 01.01.01 Q-02 | `[PENDING]` |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Loading | Org fetch | Skeleton org header |
| Empty | Org created, spine only | Page renders with name + members; progressive prompts for what the next action needs |
| Populated | Type attributes filled | Full org page per type |
| Error | Fetch failed | Error with retry |
| Partial | Some type attributes filled, some stale | Attribute groups show confirmation age; stale operational attributes are flagged, not hidden |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | One `organization` table with a type enum and every type's attributes as nullable columns | The obvious model — and exactly the anti-pattern D-14 already rejected for marketplaces ("a `listing` entity with ~40 nullable columns") | ❌ REJECTED — the same argument holds. A venue's curfew and a label's release schedule have nothing in common. This file therefore owns a thin spine plus a taxonomy, and defers each type's attribute contents to the domain that uses them (16 for venues, 12 for labels). Ratified reasoning, applied to a second case. |
| DT-02 | Org attributes are inert data | Naive framing | ❌ REJECTED — for Operators they are safety-critical and perishable. `personas.md` names the exact accidental failure: "publishes a stale gear list, so a band arrives to a room that can't run their show." An attribute someone will physically rely on needs a confirmation age, which makes staleness a modelled state rather than an accident. Nobody in the sweep named this. |
| DT-03 | The band is the org type that justifies the whole taxonomy | `personas.md`: "bands, labels, studios, venues and agencies are first-class entities... The Band is modelled as an **entity** (domain 01)" | ✅ CONFIRMED, with a sharper reason than the sweep gave. The band is the type where entity-ness is *least* legible to users (nobody thinks of their band as an org) and *most* consequential — it signs, it is paid, it owns a catalogue, and it outlives its lineup. Every platform that modelled "user has a profile" failed here first. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | Thin shared spine + type-specific attribute sets owned by the consuming domain | DT-01 — avoids the nullable-column entity D-14 already rejected once |
| D-02 | Attributes are filled progressively from the flows that need them, not at creation | An org that takes 20 minutes to create does not get created; the band exists in the world already |
| D-03 | Operationally-relied-upon attributes carry a confirmation age | DT-02 — staleness is a modelled state because someone drives to it |
