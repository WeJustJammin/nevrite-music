# Feature: Organization Types & Type-Specific Attributes

> **Number**: 01.02.01
> **Parent**: [Organizations & Entity Model](./01.02-organizations-entity-model-index.md)
> **Status**: [DEEP]
> **Last updated**: 2026-07-23

## Overview

The taxonomy of non-human parties and what each type actually carries. A band has a catalogue and the alias it releases under; a venue has a licensed capacity, a load-in and a curfew; a studio has rooms, gear and rates; a label has an imprint and a release schedule; an agency has a roster; a shop has stock and a returns policy. The shared spine is small — every org is a party with a name, a profile and members — and everything else is type-specific, which is why this is a taxonomy and not a table of nullable columns.

This feature owns **the spine, the type set, and the contract every attribute must satisfy**. It does not own the attributes themselves — a venue's stage plot is specified in 16, a label's release schedule in 12. The contract is the deliverable: five declared properties (§ Behavior) that the owning domain must state for every attribute it defines. Without that contract the seam is a hand-wave, and the union of two types' attributes is undefined behaviour on the most-used data in the platform.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Full | Creates and edits a band. Fills band-specific attributes: genre, home city, catalogue, the alias(es) it releases under, whether it is available to book. Does **not** fill "lineup" — the current lineup is a derived view over active memberships (01.03.01), never a stored attribute (DT-07). Does not see venue capacity or studio gear fields — they are not fields on their entity, not hidden fields. |
| Producer | Full | Creates and edits a studio: rooms, gear inventory, hourly/day rates, acoustic detail, remote-session capability. This is the entity that appears in 05 and 16, and the one they invoice from. Their gear inventory is `perishable` and their rates are `type`-scoped — so when they also hold `venue`, their studio hourly rate and their venue hire fee coexist rather than collide (DT-04). |
| Operator | Full | The heaviest user of this feature and the one it is designed around. Venue attributes are the product: occupancy ceiling, seated/standing configuration capacity, stage dimensions, PA/backline, load-in access, curfew, statutory records (16.01.06 D-06), age policy, accessibility. `personas.md` names the exact accidental failure — "publishes a stale gear list, so a band arrives to a room that can't run their show" — so these attributes are the safety-critical part of the taxonomy. **Whether any of them are `constrained` is profile-declared, not universal**: where the record's regime profile declares an instrument that imposes the condition (16.01.06 D-05/D-06), those fields are not preferences at all and the Operator cannot lawfully negotiate them away (DT-08). **Where the profile declares none — as the US launch profile does for the operating conditions — the same fields resolve to `preference`**, are the Operator's own claims labelled as claims, and are theirs to set and to lift (16.02.03 D-01/D-13, 16.06.03 D-25). |
| Fan | Read-only | Sees the public face of an org: a band's page, a venue's capacity, age policy and accessibility, a shop's returns policy. Never sees operational internals (rates, contact routing, staff, load-in). The Fan reads a venue page to decide whether to go, not to book it — but the accessibility and age-policy attributes are load-bearing for that decision, so staleness is visible to them too. Cannot confirm or edit any attribute. |

> **Access levels**: Full · Config · Read-only · Reports · None

## Behavior

Every org shares a thin common spine: party identity, display name and trading name, profile surface (01.06), members (01.03.01), and party identifiers (01.09). Beyond the spine, attributes are type-specific and owned by the domain the type serves.

**Type is a capability declaration, not an attribute bundle.** Adding a type lights up that type's surfaces; the attribute set is a consequence of the surfaces, not the definition of the type. This ordering matters — it is what lets `agency` be a real type with a near-empty attribute set (DT-09), and it is why a type with unfilled attributes is a normal state rather than a broken one.

The type set may be empty. A party with a name and members and no type is a **collective** — a loose group that is not yet a band, or an org whose last type was removed (01.02.03 D-04). It has a page, members and history, and no capability surfaces. Creation asks for a type because it is the cheapest signal for routing surfaces (01.02.02), but nothing requires the set to stay non-empty, and no arbitrary "you must keep one type" rule is needed.

An entity may hold more than one type (D-02 on the parent index), in which case it carries the **union** of those types' attributes — see the scope property below for how the union is made well-defined.

### The attribute declaration contract

This feature does not decide what a venue's capacity means. It decides that domain 16 cannot define `capacity` without stating these five properties. Each property exists to resolve a specific failure, cited:

| Property | Values | What it decides | Resolves |
|---|---|---|---|
| **Scope** | `party` · `type` | Whether the value is one-per-entity (address, legal name, contact routing) or one-per-type (rates, capacity, hours). Union collisions are only possible on `party` scope, and on `party` scope they are correct — the entity has one address regardless of how many things it is | DT-04; corrects parent CX-01 Q1 |
| **Authority** | `preference` · `constrained` · `floored` | Whether the org may set the value freely, is bounded by an external instrument, or may only improve on a statutory minimum (a trader's returns policy). **`constrained` is not a fixed property of a field — it is resolved per record**: the value is bounded only where the record's regime profile declares an instrument filling the relevant **slot** (16.01.06 D-05/D-06 — occupancy ceiling, liability cover, electrical/fire-safety record, performing-rights licence status, hirer requirements). Where the profile declares none, the field resolves to `preference` and the bound has no input (16.02.03 D-01/D-13) | DT-08, DT-10 |
| **Freshness** | `static` · `slow` · `perishable` · `live` | How fast the value rots and therefore what the system does about it (below) | Q-02, DT-02 |
| **Gate** | the capability it unlocks, or `none` | What is unavailable while it is unfilled. This is what makes progressive filling safe: the system knows what is blocked by what and prompts at the moment of the block, never as a completeness nag | DT-06; CX-04 |
| **Use** | `matched` · `displayed` | Whether the value feeds matching/search in 04/05/16/17 (and therefore needs a controlled vocabulary behind it) or is only rendered to humans (and therefore should be free text) | Q-01, DT-05 |

### Freshness classes — what the system does

| Class | Cadence | System behaviour | Example |
|---|---|---|---|
| `static` | never | No confirmation age. Never prompted | Founding year, legal name |
| `slow` | 365 days | Confirmation age shown past 182 days; flagged past 365 | Address, accessibility, licensed capacity |
| `perishable` | 180 days **plus confirm-on-use** | Age shown past 90 days; flagged past 180. **Additionally**: any flow in 16/17/18 that relies on the value prompts for reconfirmation when its age exceeds 30 days, at the moment of reliance | Backline/PA, rates, load-in access, curfew |
| `live` | n/a | Not confirmation-aged. Owned by the domain's availability surface, not by this taxonomy | Calendar availability, stock on hand |

180 days for `perishable` because a room's backline turns over on a scale of months, and twice-yearly is the lightest calendar cadence that catches a change before a season of bookings is taken against it. 30 days at the reliance gate because within a month the room is almost certainly as listed, and beyond that a show being advanced has earned a fresh check. **Confirm-on-use is the primary mechanism; the calendar cadence is only the backstop** for values being read in search but not yet acted on.

**Stale attributes are flagged, never hidden.** Hiding a stale venue from search would remove the Operator's bookings for a data-hygiene reason they would never see explained, which punishes the accidental failure `personas.md` describes rather than fixing it.

### Happy Path

1. Musician creates a band from their profile.
2. System asks only for what every org needs: name, and who else is in it.
3. Band exists immediately with a page, a member list and an actable context (01.01.03).
4. Band-specific attributes are filled progressively, from the surfaces that need them — a gig booking asks for the tech spec, not a wizard at creation time. Each prompt names the gate: "Add your capacity so promoters can find you by room size", not "your profile is 40% complete".
5. Attributes accumulate as a byproduct of use rather than as an onboarding tax.

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Org attributes go stale (venue's backline changed, band's lineup changed) | Staleness is a first-class state, not a silent lie. Every `perishable` and `slow` attribute carries a last-confirmed date and is flagged past its cadence | "Confirmed 14 months ago" on the gear list; a prompt to reconfirm before advancing a show |
| An entity is genuinely two types (rehearsal room + venue) | Union of both attribute sets — D-02. Not two entities | One page, both capability sets |
| Two types declare the same attribute name with different meanings (studio hourly rate vs venue hire fee; venue capacity vs rehearsal-room occupancy) | No collision. Both are `type`-scoped, so both values exist, each qualified by the type that declares it. The naive union collides only because under-qualified attributes look identical (DT-04) | Rates and capacities shown per capability, labelled by capability |
| Two types declare the same `party`-scoped attribute (studio + shop, both declaring address) | One value on the party. This is correct, not a collision — the entity has one address regardless of how many things it is. The second declaration is satisfied by the existing value, not asked again | Address asked once, ever |
| A type's attributes are needed by a domain that is not yet built | Attribute set is defined by the owning domain; absent domain = absent attributes. The spine still works | Org exists with the spine only |
| Someone creates a band that is really a solo alias | Allowed, and common. The distinction (Q-01 on 01.01.02) is not enforceable at creation | Both exist; no policing |
| Free-text vs structured attributes (genre, gear) | Resolved by the `use` property (D-04). `matched` attributes accept free text and map it to a controlled vocabulary; `displayed` attributes are free text and stay free text. **The user is never shown a dropdown that does not contain them** | Types "doom-jazz"; sees "doom-jazz" on their page; is found under jazz and metal in search |
| A `matched` value maps to nothing in the vocabulary | Value is kept and displayed verbatim; the org is matchable on its other attributes only; the unmapped term is queued for vocabulary review. Never rejected, never coerced to "Other" | "doom-jazz" shows on the page; a quiet note that it isn't a search term yet |
| Self-asserted capacity exceeds the recorded occupancy ceiling | **Reachable where the record's regime profile declares the occupancy-ceiling slot** (16.01.06 D-05/D-06). There, rejected at write: the ceiling is `constrained` authority and the platform will not publish a working capacity above the instrument that bounds it. **Where the profile does not declare the slot, there is no ceiling to exceed** — the figure publishes as an unverified Operator claim (16.02.01 `Claimed` state) | "Your occupancy ceiling is recorded as 250. A working capacity of 400 can't be published — update the statutory record if this is wrong." · In a profile with no such slot: "Capacity not verified against a statutory record" |
| Venue sets a curfew later than a statutory operating-hours condition | **Only reachable where the record's regime profile declares an instrument that imposes operating hours** (16.01.06 D-05). There, rejected at write, same rule: the distinction between "our curfew is 23:00 because we like to go home" (`preference`) and "because a statutory condition says so" (`constrained`) is modelled, because 17's booking flow may negotiate the first and must never negotiate the second (DT-08). **Where the profile declares none — as the US launch profile does — this rejection has no input**: the curfew is the Operator's own claim, theirs to set and theirs to lift, and the field resolves to `preference` (16.02.03 D-01/D-13; 16.06.03 D-25) | Where a condition exists: "23:00 is a condition of your {profile-declared operating-hours record}, not a preference. It can't be moved here." · In a profile that declares none: "Curfew 23:00 — stated by you, not verified against a statutory record." |
| A trader's shop publishes a returns policy below the statutory minimum ("no returns, ever") | Rejected at write **wherever a floor is known**. `floored` authority: the statutory floor for the buyer's jurisdiction is rendered as non-editable platform text; the shop's own field may only add terms more generous than the floor (DT-10). **No floor is stated anywhere yet** — it is a property of the *buyer's* jurisdiction rather than the record's address, so it does not resolve against the place-record regime profile D-14 uses, and Q-03 records that no source supplies one. So this row names no window: a hardcoded figure here would be the EU/UK default arriving through user-facing copy, which is exactly what D-14 and `01.07` D-06 refuse for instruments (`01.08` Q-02, same seam from the seller side) | "Buyers have a {profile-declared cancellation right} you can't remove. Add your own terms below that." The window is filled by the resolved floor, never by a literal in this spec |
| Malicious or absurd attribute value (capacity 100,000; gear list naming equipment that does not exist) | Not blocked where no instrument bounds it — self-assertion is the model (01.01.01 D-02). Cost is borne at the reliance gate: the counterparty confirmation (D-06) is where the lie meets someone standing in the room. Repeat divergence routes to 24 | Value publishes; unconfirmed; diverging counterparty confirmations surface on the page |
| The multi-hyphenate confirms their own attribute from both sides — a Producer who owns the studio *and* is in the band booking it, answering the advance-gate reconfirmation | The counterparty confirmation is **not satisfied**. When acting context (01.01.03) resolves both sides of the gate to the same human, the prompt is recorded as a self-assertion, not a counter-attestation, and the gate asks another member of the counterparty | "You're on both sides of this booking — someone else from {band} needs to confirm the backline." |
| Attribute write races a type removal (member A fills venue capacity; member B removes the `venue` type concurrently) | The write is rejected — its attribute set no longer applies. The **value is retained**, per 01.02.03 D-04 (removing a type removes surfaces, never history), so re-adding the type restores it. Add+remove is *not* commutative, unlike the add+add case parent CX-01 records as safe | "{Org} is no longer a venue — someone removed that capability while you were editing. Your entry is saved if it's added back." |
| Two members edit the same attribute concurrently | Last write wins on `preference` authority, and the loser is told rather than silently overwritten. `constrained` and `floored` values re-run their bound on every write, so a race cannot land an unlawful value | "{Member} changed the curfew to 23:00 while you were editing." |
| Member holds a mandate for one type but not another (mandated for the shop, not the venue) | `[Not modelled]` — mandate (01.03.03) covers the org uniformly. Attribute-level mandate scoping would need per-type mandates, which 01.03.03 does not define. Recorded as Q-04 rather than invented here | Full edit access to all types they can administer |
| Type added; its attributes not yet filled | Normal state, not an error. The type's surfaces exist; capabilities behind unfilled gates are unavailable and say which attribute unlocks them | "Add capacity to appear in promoter searches by room size" |
| Last type removed | Type set is empty. Valid — the org is a collective: page, members, history, no capability surfaces. No "you must keep one type" rule | Page renders with members and history only |
| Fan encounters a stale accessibility or age-policy attribute | Flagged to the Fan too, not just to professionals. These two attributes are load-bearing for a Fan's decision to travel to a venue, which makes them the only operational attributes with Fan-visible freshness | "Accessibility info last confirmed 18 months ago" |
| Org fetch fails | Error with retry. The page never renders as attribute-less on failure — an empty gear list and a failed gear list must not look alike | Error state, explicit; no false emptiness |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Loading | Org fetch | Skeleton org header |
| Empty | Org created, spine only; or type set empty (collective) | Page renders with name + members; progressive prompts for what the next action needs, each naming its gate |
| Populated | Type attributes filled and within cadence | Full org page per type; capabilities live |
| Error | Fetch failed | Error with retry; never rendered as false emptiness |
| Partial | Some type attributes filled, some unfilled, some past cadence | Attribute groups show confirmation age; stale operational attributes are flagged, not hidden; gated capabilities name the attribute that unlocks them |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | One `organization` table with a type enum and every type's attributes as nullable columns | The obvious model — and exactly the anti-pattern D-14 already rejected for marketplaces ("a `listing` entity with ~40 nullable columns") | ❌ REJECTED — the same argument holds. A venue's curfew and a label's release schedule have nothing in common. This file therefore owns a thin spine plus a taxonomy, and defers each type's attribute contents to the domain that uses them (16 for venues, 12 for labels). Ratified reasoning, applied to a second case. |
| DT-02 | Org attributes are inert data | Naive framing | ❌ REJECTED — for Operators they are safety-critical and perishable. `personas.md` names the exact accidental failure: "publishes a stale gear list, so a band arrives to a room that can't run their show." An attribute someone will physically rely on needs a confirmation age, which makes staleness a modelled state rather than an accident. Nobody in the sweep named this. |
| DT-03 | The band is the org type that justifies the whole taxonomy | `personas.md`: "bands, labels, studios, venues and agencies are first-class entities... The Band is modelled as an **entity** (domain 01)" | ✅ CONFIRMED, with a sharper reason than the sweep gave. The band is the type where entity-ness is *least* legible to users (nobody thinks of their band as an org) and *most* consequential — it signs, it is paid, it owns a catalogue, and it outlives its lineup. Every platform that modelled "user has a profile" failed here first. |
| DT-04 | The multi-type union collides on shared attribute names, and needs a collision rule | Parent CX-01 states the problem: "Two types that both define 'capacity' (a venue's audience capacity, a rehearsal room's occupancy limit) would collide on a naive union" | ✅ CONFIRMED as a problem, ❌ REJECTED as framed — **the collision is a symptom of under-qualified attributes, not a naming clash**, so a collision *rule* is the wrong fix. A venue's standing capacity and a rehearsal room's occupancy limit are not two values of one attribute; they are two attributes that a thin model let share a word. Qualify by scope (`party` vs `type`) and the collision cannot arise: `type`-scoped values coexist by construction, `party`-scoped values are genuinely one value. **This corrects parent CX-01's synthesis answer 1**, which asserts one-value-on-the-party *universally* — true for address, false for rates and capacity. A studio's hourly rate and a venue's hire fee at the same address are both correct and must both exist. |
| DT-05 | Structured vs free text is a binary choice — one of them wins | The framing of Q-01, inherited from 01.01.01 Q-02 | ❌ REJECTED — the industry has already run this experiment and the answer is neither. Discogs pairs a closed 15-genre taxonomy with ~600 open styles and free-text notes; Reverb pairs a structured make/model catalogue with free-text condition. The working pattern is **free text as the input, structure as the derivation**: the user types "doom-jazz", the system matches it to {jazz, metal} for search, and the page still says "doom-jazz". The failure mode of pure structure is not that it is restrictive — it is that it manufactures "Other", and everyone in "Other" is unmatchable, which defeats the only reason structure was wanted. The failure of pure free text is that 04/05/16/17 cannot match at all. The `use` property makes this per-attribute rather than a platform-wide religion: gear condition is `displayed`, genre is `matched`. |
| DT-06 | Progressive filling (D-02) implies a profile-completeness score to nudge people | The obvious way to make progressive filling converge, and what parent CX-04 anticipates someone building | ❌ REJECTED — and CX-04 already contains the reason: completeness tracks *usage*, not age, so a completeness score measures how much a user has used the platform and then nags them for the result. It also has no idea which missing attribute matters; 90% complete with no capacity is worse than 40% complete with one. The `gate` property replaces the score: never nag for completeness, prompt at the block, and name the capability being unlocked. 01.02.03's Partial state ("a venue with no capacity cannot be searched by capacity") already discovered this — the gate property is that observation formalised into the contract. |
| DT-07 | A band's `lineup` is a band-type attribute | This file's own prior Role Lens said so — an error caught by reading 01.03.01's boundary | ❌ REJECTED, and it was a live bug in this file. A band's **members** (01.03.01 — party edges carrying mandate and payability) and its **lineup** (who is on stage tonight — deps, subs, touring players who are not in the partnership) are different facts about different people. Storing lineup as an attribute lets the band page and the mandate graph drift, and the drift is expensive in both directions: a dep who appears in the lineup can end up holding signing authority, and a touring member who is not "a member" loses the credit for the show they played. Resolution: **current lineup is a derived view over active memberships, never stored**; historical lineup is derived from membership history plus per-performance facts owned by 17/18 and per-recording facts owned by 02. A domain expert would flag this before anything else on the page — it is the oldest entity-modelling failure in music. |
| DT-08 | Every org attribute is something the org gets to decide | Implicit everywhere; nobody has said otherwise | ❌ REJECTED — a venue's curfew, licensed capacity and age policy are **licence conditions**, not preferences. Breaching them loses the licence, which ends the business. "Our curfew is 23:00 because we like to go home" and "because the premises licence says so" are the same string and different facts, and 17's booking flow may negotiate the first while asking for the second is asking the Operator to commit an offence. A platform that lets a promoter negotiate a statutory constraint, or that publishes a working capacity above the licensed figure, is generating the liability. Hence the `authority` property. Nobody in the sweep, the parent index or either sibling named this, and it is the failure mode nobody designs for — because it only bites once, catastrophically. **⚠️ Refined (owner ratification, DQ-14.1/14.4 → 16.01.06 D-05/D-06, 16.02.03 D-13, 16.06.03 D-25):** this annotation named the **UK premises licence** as *the* instrument and asserted the constraint as universally live. It is one instrument in one (now unauthored) regime profile, not the model. The `authority` property is confirmed and regime-independent; what is profile-declared is **whether an instrument exists to impose the condition at all**, and which **slot** it fills (16.01.06 D-05/D-06). Where one exists, this rejection stands unchanged. Where none does — as the **US launch profile** declares for the operating conditions — curfew and dB limits resolve to `preference`, are Operator claims labelled as claims (16.02.03 D-01), and the rule has **no input** rather than a silently unenforced one (16.06.03 D-25). The capacity half is gated the same way: the ceiling constrains only where the record's profile declares the occupancy-ceiling slot. |
| DT-09 | `agency` does not earn a type because it has no attributes of its own — it is purely a representation relationship (01.03.02) with a roster view | Parent index Q-03, verbatim | ❌ REJECTED — the question assumes type *is* an attribute bundle, and it isn't (§ Behavior). Type is a **capability declaration**; the attribute set is downstream of the surfaces. `agency` lights up real surfaces — a roster, the authority to assert representation, appearance in agency search — and therefore earns a type on a near-empty attribute set. It is not attribute-empty in any case: territory is a genuine org-level fact (a UK indie agency and a global one are different products to a booking musician) and is `matched`, since 04/17 need to filter on it. Commission belongs to the representation edge (01.03.02), not the org, because it is per-deal. **This answers parent index Q-03** — reconcile at Step 6; not edited here. |
| DT-10 | `shop` is not a type — it is the `trader` classification (01.08) applied to any org | Parent index Q-01, verbatim | ❌ REJECTED — they are orthogonal, and the clearest proof is that **trader applies to parties that are not orgs at all**: a musician flipping gear at volume is classified a trader (01.08) and is not a shop. `shop` is a capability declaration on an org (listing surfaces in 13/14, stock, a returns policy); `trader` is a statutory classification on *any* party, derived from selling behaviour, that forces publication of legal identity (domain CX-08). An org can be both (the normal case), a person can be a trader without being a shop, and the two are assessed by different authorities — one by the org, one by the law. Adding `shop` is strong evidence for trader classification and re-triggers 01.08's assessment (01.02.03 already records this), which is a *dependency*, not an identity. The consequence lands in the contract: a trader's returns policy is `floored` authority, so the statutory minimum is platform text and the shop may only improve on it. **This answers parent index Q-01** — reconcile at Step 6; not edited here. |
| DT-11 | Org attributes should be counter-attestable by the counterparty who just relied on them, exactly as credits are counter-attested in 02 | Reasoning from the thesis. `personas.md` makes the Producer valuable precisely because "their attestation is worth more than a self-claim, which is precisely what makes counter-attestation valuable" — and D-18 makes provenance the wedge | ✅ CONFIRMED, and it is the largest finding here. Every org attribute today is a **self-claim by the party with the strongest incentive to inflate it** — `personas.md` lists the Operator's worst intentional behaviour as "misrepresents the room's specs or capacity to win bookings". A self-asserted confirmation date (D-03) fixes the *accidental* stale-gear-list failure and does exactly nothing for the intentional one, because the liar will happily click "still accurate". The band that just loaded into the room has verified the backline with their hands and has no incentive to lie about it. Applying the platform's own counter-attestation mechanism to rooms rather than only to recordings is the same wedge on a second surface, and it needs no new mechanism — 02 already is one. This file's scope is the *declaration* (an attribute can carry counterparty confirmations alongside the org's own); the mechanism is 02's and the prompt placement is 16/17's. |
| DT-12 | Type-specific attributes should be inheritable down an org hierarchy (sublabel inherits the label's registered details; a studio chain's rooms inherit the chain's policies) | The natural extension once orgs can relate to orgs | ❌ REJECTED — parent index D-03 already folded org↔org hierarchy into 01.03.02 as a party↔party relationship, on the grounds that it is real (Universal → Def Jam) but far from this platform's indie users. Attribute inheritance would resurrect hierarchy as a structural feature through the back door, and would do it in the worst way: an inherited value has no clear owner, so its confirmation age and its `constrained` bounds become ambiguous exactly where they matter most. If a sublabel needs the parent's registered details, that is a relationship read, not an inheritance. |

## Cross-Cut Notes

- Touches **16 Venues, Studios & Spaces** ([../../16-venues-studios-spaces/](../../16-venues-studios-spaces/)) — **shared entity + contract dependency**. Owns venue/studio attribute *contents*; this file owns that the type exists, that it carries them, and the five properties each must declare. 16 must classify every attribute it defines, and must place the `perishable` reconfirmation prompt in the advance flow. The occupancy-ceiling and curfew `constrained` bounds (DT-08) are 16's to source from the **statutory record where the record's regime profile declares an instrument that fills the slot** (16.01.06 D-05/D-06); where it declares none — as the US launch profile does for the operating conditions — there is nothing to source, the fields resolve to `preference`, and 16 renders them as Operator claims labelled as claims (16.02.03 D-01/D-13; 16.06.03 D-25). **This file never names the instrument** — only the slot (D-14).
- Touches **17 Live Booking & Settlement** ([../../17-live-booking-settlement/](../../17-live-booking-settlement/)) — **trigger dependency**. The advance gate is where confirm-on-use fires, and where the same-human-both-sides case (01.01.03) must fail the counterparty confirmation. 17's negotiation flow must respect `authority`: negotiable against `preference`, refused against `constrained`.
- Touches **02 Credits & Attribution** ([../../02-credits-attribution/](../../02-credits-attribution/)) — **mechanism reuse (DT-11)**. Counter-attestation of org attributes is the same mechanism 02 runs for credits, pointed at rooms. This file declares that attributes carry counterparty confirmations; 02 owns how attestation works. Also: no lifecycle or type change may remove a credit.
- Touches **12 Release & Distribution** ([../../12-release-distribution/](../../12-release-distribution/)) — **gate dependency**. Label type attributes. A label's identifiers (LC, DDEX party ID) are not optional decoration — they `gate` delivery, which is the clearest instance of the `gate` property outside 16.
- Touches **01.09 Party Identifier Resolution** ([../01.09-party-identifier-resolution.md](../01.09-party-identifier-resolution.md)) — **type-determined applicability**. Which identifiers apply is a function of type (LC and DPID are label-only; ISNI/IPI attach to artist parties per domain CX-05). 01.09 owns identifier contents and resolution; the taxonomy owns which type admits which.
- Touches **01.03.01 Membership Records** ([../01.03-membership-representation-mandate/01.03.01-membership-records-lifecycle.md](../01.03-membership-representation-mandate/01.03.01-membership-records-lifecycle.md)) — **shared entity, corrected boundary (DT-07)**. Members are the spine; lineup is a derived view over active memberships and is explicitly not an attribute of this feature. See domain CX-03.
- Touches **01.03.03 Mandate Scope** ([../01.03-membership-representation-mandate/01.03.03-mandate-scope-delegated-authority.md](../01.03-membership-representation-mandate/01.03.03-mandate-scope-delegated-authority.md)) — **permission**. Mandate covers the org uniformly, so a member mandated for the shop can also edit the venue. Parent CX-01 flagged this for Step 5; it needs per-type mandates that 01.03.03 does not define. Q-04.
- Touches **01.06 Portfolio, Media Reel & EPK** ([../01.06-portfolio-media-epk/](../01.06-portfolio-media-epk/)) — **composition**. Orgs have profile surfaces; a venue page and a band page are both composed there. A multi-type entity's composed page is 01.06.01's problem (01.02.03 records this) — and freshness flags must survive that composition rather than being styled away.
- Touches **01.08 Trader Status** ([../01.08-trader-status-classification.md](../01.08-trader-status-classification.md)) — **orthogonal classification, not a type (DT-10)**. Adding `shop` re-triggers 01.08's assessment. Trader status makes the returns policy `floored` and forces legal-identity publication (domain CX-08).
- Touches **01.02.03 Type Transitions** ([./01.02.03-organization-type-transitions.md](./01.02.03-organization-type-transitions.md)) — **shared entity + state race**. Union composability (CX-01); the add/remove race on an in-flight attribute write is *not* commutative, unlike the add/add case CX-01 records as safe.
- Touches **01.02.02 Creation & Lifecycle** ([./01.02.02-organization-creation-lifecycle.md](./01.02.02-organization-creation-lifecycle.md)) — **trigger dependency**. Creation captures the spine only; attributes accrue from use (CX-04). An empty type set is a valid post-creation state.
- Touches **04 Opportunities & Casting** ([../../04-opportunities-casting/](../../04-opportunities-casting/)) and **05 Services Marketplace** ([../../05-services-marketplace/](../../05-services-marketplace/)) — **matching dependency**. These are the consumers that justify `matched` attributes existing at all; the controlled vocabulary behind them is shared, which is why its governance is Q-01.
- Touches **13 Gear Marketplace** ([../../13-gear-marketplace/](../../13-gear-marketplace/)) / **14 Digital Goods** ([../../14-digital-goods-marketplace/](../../14-digital-goods-marketplace/)) — **gate + statutory floor**. `shop` type lights up their listing surfaces; the returns-policy floor (DT-10) is enforced against their sales flows.
- Touches **24 Trust, Safety & Disputes** ([../../24-trust-safety-disputes/](../../24-trust-safety-disputes/)) — **notification/escalation**. Repeated divergence between an org's self-asserted attribute and counterparty confirmations (DT-11) is the signal for the Operator's worst intentional behaviour, and routes here.
- Touches **Canonical Data / Entity Merge** (cross-cut) — duplicate org records (two "The Lexington") must redirect, not rewrite. On merge, `type` scope decides the arithmetic: `party`-scoped attributes must reconcile to one value; `type`-scoped ones survive per type.

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | Thin shared spine + type-specific attribute sets owned by the consuming domain | DT-01 — avoids the nullable-column entity D-14 already rejected once |
| D-02 | Attributes are filled progressively from the flows that need them, not at creation | An org that takes 20 minutes to create does not get created; the band exists in the world already |
| D-03 | Operationally-relied-upon attributes carry a confirmation age | DT-02 — staleness is a modelled state because someone drives to it |
| D-04 | Every attribute an owning domain defines must declare five properties: **scope, authority, freshness, gate, use** | The deliverable of this feature. Each property resolves a named failure (DT-04, DT-08, DT-02, DT-06, DT-05). Without the contract the seam between this file and 16/12 is a hand-wave and the union is undefined behaviour |
| D-05 | Type is a **capability declaration**, not an attribute bundle; the attribute set is downstream of the surfaces | DT-09 — this is what lets `agency` be a real type on a near-empty attribute set, and why unfilled attributes are a normal state |
| D-06 | An attribute may carry **counterparty confirmations** alongside the org's own assertion | DT-11 — the org is the party with the strongest incentive to inflate; the band standing in the room is not. The platform's own wedge, applied to rooms |
| D-07 | Freshness is enforced primarily by **confirm-on-use at the moment of reliance**; calendar cadence is the backstop | Matches the sub-domain's established pattern — 01.02.03 D-02 offers transitions at the point of the action, 01.01.01 adds facets at the point of use. Nobody visits a settings page to refresh a gear list |
| D-08 | Stale attributes are **flagged, never hidden** | Hiding removes the Operator's bookings for a reason they never see, punishing the accidental failure rather than fixing it |
| D-09 | `matched` attributes accept free-text input mapped to a controlled vocabulary; unmapped values are kept and displayed, never coerced to "Other" | DT-05 — resolves Q-01 for org attributes. Scoped to org attributes; 01.01.01 Q-02 is the same shape for person facets and is not this file's to close |
| D-10 | `shop` stays a type; `trader` is an orthogonal classification on any party | DT-10 — answers parent index Q-01 |
| D-11 | `agency` earns a type | DT-09 — answers parent index Q-03 |
| D-12 | Current lineup is a derived view over active memberships, never a stored band attribute | DT-07 — corrects an error in this file's own prior Role Lens |
| D-13 | The type set may be empty; a typeless org is a collective | Cheap, consistent with D-02, and it removes the need for an arbitrary "keep one type" rule on the last removal |
| D-14 | **`constrained` authority is resolved per record against a regime profile, never asserted as a fixed property of a field, and this file names the *slot* and never the instrument.** Where the record's profile declares an instrument filling the slot (16.01.06 D-05/D-06), the bound is live and the value is not the org's to set. Where it declares none — including every unauthored profile — the field resolves to `preference`, is an Operator claim labelled as a claim, and the bound has **no input** rather than being silently unenforced | Owner decision (DQ-14.1/14.4), refining DT-08. DT-08 named the **UK premises licence** as *the* instrument and asserted the constraint universally; the argument for the `authority` property survives intact and its universality does not. The **US launch profile declares no operating-hours instrument**, so curfew and dB limits are `preference` at launch (16.02.03 D-01/D-13) and 16.06.03 D-22's overrun ceiling has no input (16.06.03 D-25). The **US instrument names are a live `[PENDING]` on 16.01.06 D-06**, deferred to `/create-prd-security` — this file must not supply one. Consistent with 01.07 D-06, which applies the same rule to credential types |
