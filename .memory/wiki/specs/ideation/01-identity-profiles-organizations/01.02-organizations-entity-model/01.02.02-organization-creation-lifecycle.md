# Feature: Organization Creation & Lifecycle

> **Number**: 01.02.02
> **Parent**: [Organizations & Entity Model](./01.02-organizations-entity-model-index.md)
> **Status**: [DEEP]
> **Last updated**: 2026-07-16

## Overview

How an entity comes into existence and how it stops — creation, duplicate detection at the moment of creation, dormancy, and closure. The lifecycle matters because an org accumulates the things the platform exists to protect (credits, bookings, reviews, royalty lines), so no lifecycle state may ever destroy them. An org is never deleted; it becomes dormant, closed, or dissolved, and its record of work survives all three.

Two facts shape every rule below. First, per `problem-statement.md`, the platform's value is that facts accrete to an identity — so any creation flow that costs more than the moment it interrupts will not be used, and any lifecycle state that drops an accreted fact is the platform committing the failure it exists to prevent. Second, creating an org is an **assertion**, not a proof (D-01) — which is why creation is cheap, weak, and non-binding, and why every consequence that matters (money, bookability, ranking) hangs off claiming (01.05), not off creation.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Full | Creates a band in under 30 seconds from their profile — or, more often, from inside another flow: naming the band on a credit (02), a lineup (01.03.01), or a gig offer (17). Later marks it `dormant` when it stops gigging — which must not read as failure, and must not remove the catalogue, the credits, or the fans following it. Their hardest case is the name collision: their band shares a name with three others and they must still be able to create it (DT-04). |
| Producer | Full | Creates a studio org, and — at the capture moment — creates *other people's* orgs by reference: the band tracking tonight that has no page. Their lifecycle risk is different: a studio that closes still holds the credits for everything tracked there, and those credits are other people's careers. Closure never cascades. They also need the closure rule to not trap them: an unsettled invoice a client will not sign off must not hold their studio open forever (D-09). |
| Operator | Full | Creates a venue — commonly by **claiming** a seeded one (01.05) rather than creating from scratch, because their venue is likely already listed. Seasonal dormancy is normal (a festival site, a winter closure) and must not look like closure to bookers. The heaviest user of duplicate detection: their entity is unique-by-address, so a name match in the same locality is almost always the same room (D-05), and their most common "creation" is really a type addition to an entity they already own (CX-02). |
| Fan | None | Cannot create orgs. Sees only the *consequences*: a band's page marked inactive, a venue marked permanently closed, a follower notice when an org they follow closes or reopens (D-15). Explicit absence — a fan creating a venue page is how directories get polluted. **Enforcement caveat**: per `personas.md`, personas are lenses, not account types, so this row means *the fan surface offers no creation entry point*, not that a role check denies it. The act of creating an org is itself the act of behaving as a Musician. The real defence is D-14, not a persona flag — see DT-09. |

> **Access levels**: Full · Config · Read-only · Reports · None

## Behavior

Creation is deliberately cheap: name + type + (for a band) who else is in it. The expensive parts (attributes, verification, payability) accrue later from the flows that need them (01.02.01 D-02).

Creation is also **invocable inline from any flow that needs to name a party** (D-13) — the credit flow (02), an invitation (01.03.01), a booking (17), a lineup. It is never only a destination reached from a profile. A creation flow that requires leaving the session is a creation flow that does not run at the capture moment, which is the one moment `problem-statement.md` says the platform exists for.

### Three creation modes

The creator's asserted relationship to the org determines what they get. This resolves the old Q-02 (can a non-member create?) — yes, and it is not an exception to "creator becomes owner"; it is a **different mode** (D-07).

| Mode | Creator asserts | What they get | Ownership status |
|------|----------------|---------------|------------------|
| **For myself** | "I'm in this band" / "I run this studio" | Membership edge (01.03.01) + **owning mandate** (01.03.03) | `owned` |
| **For a party I represent** | "I manage this band" | Representation edge (01.03.02) + **custodial mandate** | `unclaimed` |
| **By reference** | Nothing — they named it because a flow needed it (a credit, a booking, a lineup) | Creator attribution only. No edge, no mandate | `unclaimed` |

**Custodial mandate** is derived, not invented: 01.03.03's rule 1 says a mandate cannot exceed the granting party's own authority. An unclaimed org has granted nothing. Therefore a creator-asserted mandate on an org nobody has claimed **cannot include binding authority** — the custodian may edit the record, add attributes and invite, but cannot accept money, sign, accept a booking, or list for sale. Those unlock on claim (01.05.02).

Mode 3 is shadow-org creation and is governed by 01.05.01 — including its rule that creation-by-reference happens *only* as a side effect of a flow that needed the party, never as a standalone action.

**The first owning mandate always lands on a human, never on an acting-context org** (D-12). If a Musician creates a studio while acting as their band (01.01.03), the human holds the mandate and the band↔studio link is recorded as a party↔party affiliation (01.03.02), per the parent index's D-03 that org↔org hierarchy is not modelled here.

### Duplicate detection

Detection runs **before commit** and is the cheapest possible moment to prevent a split identity — after creation it becomes a merge, and domain CX-02 records what merges cost. It resolves the old Q-01 with three rules:

**1. Aggressiveness is per-type, because uniqueness is per-type (D-05, DT-04).**

| Type class | Types | Uniqueness fact | Detection behavior |
|---|---|---|---|
| **Unique-by-address** | venue, studio, rehearsal, shop | One room, one address. Two "The Lexington" in Islington is a data error, not two venues | Normalized name match **within the same locality** ⇒ treat as the same entity. Claim/join is the **primary** action. "It's a different one" is available but requires naming the distinguishing detail, which is recorded and rendered on both pages |
| **Not unique at all** | band, label, agency | Band names collide constantly and legitimately — different scenes, different countries, sometimes a lawsuit. The industry's own answer is territorial disambiguation, never uniqueness | Name match alone is a **weak** signal and never the same-entity default. It becomes strong only with ≥1 corroborating signal (see rule 2). With name only: candidates shown as a list, **create stays the primary action** |

**2. Signals, in priority order.** Detection matches on more than the current display name:

| # | Signal | Why |
|---|--------|-----|
| S1 | **Creator already holds an owning mandate on an entity that could take this type** | CX-02's case, and the highest-value hit. Fires regardless of name: "Add `venue` to The Old Dairy?" |
| S2 | Normalized name match — NFKC, case-folded, punctuation/diacritics stripped, leading "The" and legal suffixes (Ltd, LLC, Records) ignored | The common honest collision |
| S3 | Name match against **name history and release aliases**, not just current display name (D-06, DT-05) | Bands rename constantly. D-03 guarantees the history still exists to match against |
| S4 | Locality match (same postcode/city) | Decisive for unique-by-address types; corroborating for others |
| S5 | Member overlap ≥1 person with an existing party's member set | The two-bandmates case — the strongest band signal |
| S6 | Target is an existing shadow/seeded party (01.05.01) | Routes to claim, not to a second entity |

**3. Detection never blocks — it interrupts.** Ceiling: one screen, always dismissible, always with a create path. The false-positive cost is a few seconds of friction; the false-negative cost is a merge. So detection biases toward **recall** (show more candidates) and never toward denial. A hard block would hand a band name to whoever typed it first — the exact land-grab DT-02 rejected.

**Why S1 is ranked first**: domain CX-03 and sub-domain CX-02 both flag a perverse incentive — creating a new entity requires nothing, while adding a capability to an existing one requires a mandate, so the *correct* action is harder than the wrong one. The asymmetry cannot be fixed with permissions (there is no entity to hold a mandate on yet). It is fixed here, at the UX layer where it actually lives: when S1 fires, the correct path is the default path.

**Detection is bounded, and the creation always wins.** If detection cannot answer within its bound, the org is created and the offer is surfaced post-commit as a follow-up. Losing a creation to a slow lookup is the worst available outcome — it loses the fact at the capture moment. Target: P95 < 500 ms, hard bound 2 s (exact budget → `/create-prd-compile`; see Q-03).

### Lifecycle

Lifecycle state and ownership status are **orthogonal axes** (D-08). An unclaimed venue can be seasonally dormant; a claimed band can be dormant. Collapsing them into one enum is the bug this decision prevents.

**Ownership axis**: `unclaimed` → `owned` → `ownerless` (involuntary loss only — see D-16) → `owned`.

**Lifecycle axis**:

| From | To | Guard | Effect |
|------|----|-------|--------|
| `active` | `dormant` | Owning mandate. No other guard | Removed from supply-side (booking/hire) search. Page renders with an explicit dormancy note. Reversible in one action |
| `dormant` | `active` | Owning mandate | Relisted. No notice to anyone — pausing is not an event |
| `active`/`dormant` | `closing` | Owning mandate | **Intent state.** Stops new obligations accruing: no new bookings, delisted from supply search, listings withdrawn. Existing obligations run out. Reversible |
| `closing` | `closed` | **Zero live obligations.** Auto-transitions the moment the last one clears | Public terminal signal. Followers notified (20) |
| `active`/`dormant` | `closed` | Zero live obligations at the moment of the request | Direct close, for the org that has nothing outstanding |
| `closed` | `active` | Owning mandate | Reopen. Followers notified — they were told it closed, so they are told it did not (D-15) |
| `active`/`dormant` | `dissolved` | Band type only, and only if `band` is the party's **sole** live type. Governance rules per 01.04.01 | Executed by 01.04.04. Terminal via this file |
| `dissolved` | — | — | Not reversible through this file's controls. Reversal requires the governance that produced it → 01.04.04 |

**Live obligation** — the definition that gates closure. An obligation blocks only if it is **finite and resolvable**:

| Blocks closure | Never blocks closure |
|---|---|
| A confirmed future booking (17) | An open royalty stream (10) — perpetual by nature |
| An unsettled balance in either direction (17, 23) | Held credits (02) — permanent by design |
| An undelivered paid service or order (05, 13, 14) | A catalogue and its rights positions (09) |
| A pending payout | Followers (20) |
| An open dispute (24) | Reviews, history, identifiers |
| A live listing carrying a bid or offer | Past bookings, past shows |

This split is load-bearing (D-10, DT-06). If perpetual entitlements blocked closure, **no label could ever close** — its royalty streams outlive it by decades. The rule is that closure ends the party's capacity to take on new obligations; it never touches what the party is owed or what it proved.

**A multi-type entity has one lifecycle state, on the party** (D-17, DT-15) — resolving the sub-domain CX file's sharpest open question. Ending one capability of a band+label is a **type removal** (01.02.03), not a lifecycle transition. Terminal states are only available when they are terminal for the whole party. This preserves 01.02.03 D-03's invariant that transitions never fork the party identity.

### Nobody declares dormancy

The real-world default is that nothing is ever marked — 01.04.04 says it plainly: "the band just quietly stopped… nobody initiates anything." A lifecycle model that depends on a declaration will be wrong most of the time.

The resolution (D-11, DT-08): **infer quietness (a fact), never infer intent (a state)**.

| Elapsed with zero org activity | System does | Public sees |
|---|---|---|
| 12 months | Private prompt to owning mandate holders: "Still going?" One tap for `active` / `dormant` | Nothing |
| 18 months, and 2 prompts unanswered | Suppressed from **supply-side search only** (booking/hire results). Still findable by name, still linked from every credit | Nothing. No badge, no state change |
| Ever | — | **Never** a published inferred terminal state |

A declaration always beats an inference and resets the clock. A festival site that declares `dormant` every October is never inferred-quiet.

### Anti-abuse

Creation must stay cheap (D-02, DT-10), so abuse is handled by making the spam **worthless**, not by making creation **hard** (D-14):

1. **Unclaimed orgs are inert**: cannot take money, cannot be booked, cannot be listed for sale, do not rank in search, are not indexed. A spam org buys the spammer nothing.
2. **Creator attribution is permanent** — every org knows who created it. This is 01.05.01's accountability mechanism, and it is what makes an easy creation surface survivable.
3. **Rate as friction, not denial**: >3 orgs created per account per rolling 24 h, or >10 lifetime, triggers a verification step — not a block. Basis: a working musician plausibly creates 1–3 orgs across a career (their band(s), maybe a label); 5 in a day is not a musician behavior. Exact numbers are tunable — see Q-01.

### Happy Path

1. Musician taps "Create a band" from their profile (or names a band inline from a credit flow — same flow, same rules).
2. System asks for the name, and asks the relationship: *are you in this band, do you represent it, or are you just naming it?* They pick "I'm in it".
3. Detection runs before anything is committed. It checks S1–S6: the creator holds no entity that could take `band` (S1 no); the name matches two existing bands (S2/S3); neither shares a member or a home city (S5/S4 no).
4. Type is `band` — not unique by nature — and the only signal is a bare name match. So **create stays the primary action**, with the two matches shown beneath it: "There are 2 other bands called Wolves. Yours? [Join] · or carry on creating."
5. Musician carries on. Band is committed; the creator becomes the first member with an owning mandate; ownership status is `owned`, lifecycle is `active`.
6. Band is immediately usable: it has a page, an actable context (01.01.03), and can be invited to a gig.
7. Attributes fill in later, from the flows that need them (01.02.01 D-02) — the tech spec is asked for by the booking, not by a wizard.
8. Two years later the band stops gigging. One tap sets `dormant`: it leaves booking search, the page says so plainly, the catalogue, credits and followers are untouched, and one tap brings it back.

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Creating an org that already exists (seeded venue, or another member already made the band) | Detection intercepts before commit. Highest-leverage moment on the platform to prevent a split identity — after creation it is a merge, and merge is expensive (domain CX-02) | "The Lexington already exists — is this yours? [Claim it] [It's a different one]" — claim routes to 01.05, never to a second entity |
| Two band members each create the band on the same day | Detection catches the second on S5 (member overlap). The second person is offered to *join*, not create | "Someone already created {band}. Ask to join?" |
| **True race**: two members commit within the detection window, so neither saw the other | Detection re-runs against committed state at commit. The loser is **not** given an error — it converts to the join offer with their typed input carried into the join request. Two orgs are never both committed for the same detected match | "{Name} just created this band. Your details were carried over — ask to join?" |
| Genuinely new band with a common name (three other bands called Wolves) | Created. `band` is a not-unique type, so a bare name match never blocks (D-05). All four coexist; disambiguation is territorial/contextual, as in the industry | Create is the primary action; the other three are listed, not enforced |
| Creator already owns an entity that could take the requested type (studio owner "creating" a venue) | S1 fires and is the **primary** action — add the capability to the existing entity (01.02.03), do not create a second party. Fixes the CX-02 perverse incentive at the point where it bites | "You already run The Old Dairy. Add `venue` to it? [Add capability] [No, this is a separate business]" |
| Creator insists it *is* a separate business | Allowed — they may be right. A second party is created, the refusal is recorded, and the Canonical Data cross-cut inherits any cleanup | Second entity created; no scolding |
| Name uses homoglyphs / zero-width chars / RTL overrides to evade detection ("Тhe Lexington", Cyrillic Т) | Normalization for matching folds Unicode confusables and strips zero-width and directional-override characters, so the evasion does not defeat S2. The name **displays** as typed; only matching is normalized | Detection fires normally. Deliberate evasion + impersonation routes to 24 |
| Name is a trademark someone else holds | Creation never adjudicates trademark — the platform cannot, and enforcing name uniqueness would hand the name to whoever typed it first (DT-13). The page exists; the dispute is a 24 / 01.05.03 matter | Created. Rights-holder has a report/contest route |
| Creating an org for a party you are not in and do not represent | Not an exception — it is mode 3, shadow-org creation (01.05.01), and only from a flow that needed the party. Creator gets attribution, no mandate; org is `unclaimed` and inert | "This band will be added unclaimed. {Band} can claim it." |
| Custodian of an unclaimed org tries to accept a booking / take money / sign | Blocked by derivation, not by policy: the org granted no authority, so no binding mandate exists (01.03.03 rule 1) | "You can hold this record for them, but only {org} can accept bookings. Invite them to claim it." |
| Someone claims an unclaimed org while the custodian is mid-edit | Claim wins; custodial edits in flight are preserved as the claimant's inbox item, not discarded. The custodian's mandate downgrades to whatever the new owner grants | Custodian: "{Name} claimed {org}. Your changes were sent to them." |
| Creator leaves the band they created (voluntary) | Ownership must transfer before or on departure. An org with no owning member is unadministrable | Blocked until a successor mandate exists (01.03.03) — see domain CX-06 |
| Sole owning mandate holder **dies** | Death does not ask permission, so the "always one owner" invariant is violable by mortality. It binds on *voluntary* departure only. The org enters `ownerless`; succession routes via 01.10 (estate) and 01.05.03 (transfer). It is **not** frozen — other people's bookings depend on it | Co-members: "{Org} has no administrator. Here's how to establish one." Public page unchanged |
| Sole owner's account terminated by 24 | Same as death: `ownerless` + succession route. A person's suspension **never cascades** into the org — that would punish its other members and counterparties, the same non-cascade principle as D-03 | Org keeps trading via succession; no public state change |
| Org is closed while it has live obligations | Closure blocked, never cascaded. `closing` is offered as the alternative | "You have 2 confirmed bookings and an unsettled show. Resolve these, or start closing — you'll take no new work while they clear." |
| **Counterparty holds closure hostage** — refuses to settle so the org can never close | The reason `closing` exists (D-09). `closing` stops new obligations immediately, without the counterparty's cooperation. The stuck obligation escalates to 24's dispute path on its own clock; closure completes automatically when it clears | "Closing. You're taking no new bookings. 1 item is waiting on {counterparty} — we've opened a dispute route." |
| A label closes but its royalty streams run for 40 more years | Perpetual entitlements never block (D-10). If they did, no label could ever close | Closes normally; royalties keep paying to whoever 09/10 says owns them |
| Org is closed but its credits are load-bearing for other people | Closure never removes credits. The org page persists read-only | "Closed" state; credits intact and still citable |
| Closed org reopens (a shop that shut in the recession) | `closed` is reversible by an owning mandate holder. Followers were told it closed, so they are told it reopened | Follower notice: "{Org} is open again." Page returns to `active` |
| Someone tries to un-dissolve a band through the org's own controls | Refused here. `dissolved` was produced by governance, so only that governance can reverse it | "Dissolution was a band decision. Reversing it is too — {route to 01.04.04}." |
| Multi-type band+label wants to stop being a band but keep the label | Not a lifecycle transition. Remove the `band` type (01.02.03); the party stays `active` as a label. `dissolved` is unavailable while another type is live (D-17) | "You're also a label. Remove the band capability instead — your catalogue keeps running." |
| Nobody ever declares dormancy — the actual common case | Quietness is inferred as a **fact**; intent is never inferred. Prompt at 12 months; supply-search suppression at 18 months + 2 unanswered prompts; no public state change, ever | Owner: "Still going?" Public: nothing |
| Festival site is quiet 11 months a year by design | A declaration always beats an inference and resets the clock. A declared-`dormant` org is never inferred-quiet | Nothing — this is what D-04 makes normal |
| Dormant org receives a booking request anyway (someone has the link) | Not rejected — dormancy is not a wall. The request is delivered with its context, and offers reactivation in the same action | "You're marked dormant. {Venue} wants you on the 14th. [Reactivate & reply] [Decline]" |
| Fan-created spam orgs / vanity venue pages | The fan surface offers no creation entry point, but the enforcement is D-14, not a role check (DT-09): the org would be `unclaimed` ⇒ inert, unranked, unindexed, and permanently attributed to its creator. Spam buys nothing | Report path → 24 |
| Bulk org creation (11 orgs in an hour) | Rate is friction, not denial: >3/24 h or >10 lifetime triggers a verification step. Creation is never hard-blocked — that would break the Producer's capture moment | "Quick check before we add this one." |
| Creation submitted while the creator's account is suspended/limited (24) | Blocked. A suspended account cannot create parties — but note the asymmetry: suspension blocks *new* creation and never cascades into orgs the account already owns (see the termination row) | "Your account is limited. You can't add organizations right now." |
| Network drops mid-submit — did it create? | A retry of the same creation from the same client must resolve to the same org, never a second one. Non-negotiable: the retry path is exactly the path a nervous user takes | Retry lands on the created org, not a duplicate |
| User abandons the flow after detection, before commit | Nothing is committed. No partial org exists at any point, and the detection result is not cached against them | Nothing created |
| Empty name / whitespace-only / absurd length | Rejected at the field, on blur, before detection runs. A party's name is its public identity; it is never optional and never blank | Inline error on blur: "Give it a name." |
| Band's name is identical to a person's name (a solo alias — "Sam Fender") | Allowed. 01.02.01 already accepts that band-vs-solo-alias is unenforceable at creation. Detection surfaces the person as a candidate but never blocks — a person and a band are different party kinds | "There's a musician with this name. Is this their solo project, or a band? [It's my project] [It's a band]" — both create |
| Detection returns 200 candidates (a very common name) | The interrupt has a ceiling: one screen, top matches by signal strength, create always reachable without scrolling. Detection biases to recall in *what it searches*, not in *what it shows* | Top matches + "None of these — create {name}" |
| Multi-hyphenate: the creator is both the band's drummer and the studio's owner, creating the band at their own studio | Two distinct parties, both legitimate, no conflict. The mandate lands on the human either way (D-12); the band↔studio link is an affiliation (01.03.02), not ownership | Both orgs exist independently; neither owns the other |
| Musician creates a studio while acting as their band (01.01.03) | The **human** takes the owning mandate, never the acting-context org — org↔org hierarchy is out of scope here (parent D-03). The band↔studio relationship is recorded as an affiliation | "You'll be the administrator. {Band} will be linked to it." |
| Org created and never used — the majority outcome | Persists. Inert if unclaimed, quiet if owned. This is fine: an unused record costs nothing and the cost of *not* having it at the moment someone needs to name it is the entire thesis | Nothing |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Loading | Creation submitted / org fetch | Progress. Detection runs before commit, bounded (P95 < 500 ms, hard bound 2 s); past the bound, creation proceeds and the duplicate offer arrives post-commit rather than the creation being lost |
| Empty | Org exists with the spine only — name + custodian, no members. **The unclaimed case** (mode 2/3) | Page renders name + "unclaimed", an invitation to claim, and nothing actable. Note: the previous claim that an org never exists without a member is false under D-07 — shadow orgs have a custodian and no members |
| Populated | `active`, `owned` | Normal org page |
| Error | Creation failed (network, validation, rate check) | Error with retry; **no partial org is ever committed**, and retrying never yields a second org |
| Partial | `dormant` — or `closing`, or inferred-quiet | `dormant`: page renders with an explicit dormancy note, absent from booking search, one-tap reactivate. `closing`: owner sees the itemised blockers and what they are waiting on; public sees nothing but the absence of availability. Inferred-quiet: public sees **nothing at all** (D-11) |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | Duplicate detection belongs to the Canonical Data / Entity Merge cross-cut, so this file should not mention it | The boundary narrowing recorded in the domain overview did move entity merge out | ⏳ SPLIT — merge (reconciling two records that already exist) is the cross-cut's. **Prevention at the creation moment is a product flow that lives here**, and it is worth far more: the entity-merge cross-cut is the expensive cleanup for the case this step prevents. Handing the whole problem to the cross-cut would delete the cheap fix and keep only the dear one. |
| DT-02 | Creating an org proves you own it | Implicit in every "create your band" flow | ❌ REJECTED — and the distinction is load-bearing. Creation is an assertion; claiming (01.05) is a proof. Conflating them means whoever types the name first owns the venue, which is a land-grab surface. It also means the seeded-venue case (01.05.01) has no home. Creation must be cheap *and* weak. |
| DT-03 | An org can be deleted | Standard CRUD assumption | ❌ REJECTED — an org accumulates other people's careers. Deleting a studio would evaporate the credits of everyone who ever tracked there, which is the precise failure in `problem-statement.md` ("the proof of it evaporates"), delivered by the platform itself. Lifecycle terminates in states, never in deletion. |
| DT-04 | Band names are unique enough to enforce, so one global duplicate threshold serves every org type | The default in every "name is taken" flow ever built | ✅ CONFIRMED as **false for bands, true for venues** — which is the finding. A domain expert would say this immediately: band names collide constantly and legitimately (the UK Nirvana and the Seattle one; Charlatans/Charlatans UK; Suede/The London Suede; Bush/Bush X), and the industry's own remedy is territorial disambiguation, never uniqueness. A venue, by contrast, is one room at one address — two "The Lexington" in Islington is a data error. So **aggressiveness is per-type because uniqueness is per-type** (D-05). A global threshold is not merely annoying; it is wrong on the domain. Resolves the old Q-01. |
| DT-05 | Detection matching current display names is sufficient | The obvious implementation | ❌ REJECTED — early bands rename constantly, and a renamed band is invisible to name-only detection, so it gets re-created and the split identity happens anyway. Detection must match **name history and release aliases** (D-06). Pleasing corollary: D-03 (never delete) is what guarantees the history is still there to match against — the no-deletion rule pays for itself in a place nobody expected. |
| DT-06 | "Closure is blocked by live obligations" is a complete rule | Inherited from this file's own surface pass | ❌ REJECTED — it contains a latent bug that would kill exactly the orgs that matter most. A label's royalty streams (10) run for decades and never "resolve". If open royalty streams count as live obligations, **no label can ever close**, and neither can a band with a catalogue. The fix is a definition, not an exception: only **finite, resolvable** obligations block; perpetual entitlements never block and always survive (D-10). Nobody in the sweep or the surface pass caught this. |
| DT-07 | A counterparty can hold an org open forever by refusing to settle | Adversarial read of the closure block | ✅ CONFIRMED — and it is a hostage surface. "You have an unsettled show" is unfalsifiable by the party that wants out if the other side simply never signs off. Closure blocked must not mean closure denied. The `closing` intent state (D-09) resolves it: it stops new obligations accruing immediately, needs nobody's cooperation, and completes automatically when the last item clears. Same shape applies to 01.02.03's type-removal block — flagged in Cross-Cut Notes. |
| DT-08 | The lifecycle model works because owners declare their state | Implicit in D-04's dormancy design | ❌ REJECTED — 01.04.04 already states the truth: "the band just quietly stopped… nobody initiates anything." A declared model is wrong most of the time. But the obvious fix is worse than the problem: inferring "this band has broken up" and telling fans is a serious harm and often false. The resolution is a distinction: **infer quietness (a fact), never intent (a state)** (D-11). The system may ask, and may withhold from supply search, and may **never** publish an inferred terminal state. This is the failure mode nobody designs for — every directory has ghost listings, and every attempted fix has libelled a working business. |
| DT-09 | "Fan: None" in the Role Lens is an enforceable gate on org creation | The Role Matrix reads like a permission table | ❌ REJECTED as an enforcement claim, ✅ retained as a surface claim. `personas.md` is explicit that personas are **lenses, not account types** — there is no `is_fan` flag to check, and the boundary is porous by design (D-11 global: "may be a hobbyist musician too"). A fan who creates a band has, by that act, behaved as a Musician. So the row means *the fan surface offers no entry point*, and the real defence must be structural: **make spam worthless rather than making creation hard** (D-14). This reinforces 01.05.01's stance ("rate limiting and creator accountability") rather than contradicting it — but the enforcement mechanism is a permission cross-cut question, not a persona check, and saying so now prevents a downstream spec writing a role guard that cannot exist. |
| DT-10 | Require verification (or any proof) before an org can be created | The intuitive anti-abuse answer | ❌ REJECTED — it kills the thesis at its narrowest point. The Producer creates a band at 2am inside a credit flow to get the fact recorded while it is true (`problem-statement.md`; `personas.md`'s named accidental failure). Any proof step there means the credit is not captured, and "we'll do it later" wins again. D-01/D-02 already made creation weak-and-cheap on purpose. Verification belongs on **consequence** — taking money, being bookable, ranking — never on existence. |
| DT-11 | A manager creating their artist's band is an exception to "creator becomes owner", requiring a special case | The old Q-02's framing | ❌ REJECTED as an exception — and the reframe is the value. It is not a special case, it is **shadow-party creation** (01.05.01), which the domain already models. Three modes fall out cleanly (D-07): for-myself ⇒ membership + owning mandate; for-a-party-I-represent ⇒ representation edge + **custodial** mandate; by-reference ⇒ attribution only. The custodial mandate's limits are *derived* from 01.03.03 rule 1 (a mandate cannot exceed what the granting party granted — an unclaimed org granted nothing), not invented. Resolves the old Q-02 without a new mechanism. |
| DT-12 | When a user creates an org while acting as their band, the band owns the new org | The natural reading of the acting-context switcher (01.01.03) | ❌ REJECTED — a mandate is authority a *human* exercises, and org↔org hierarchy is explicitly folded into 01.03.02 as a party↔party relationship (parent index D-03). Letting an acting context take ownership would smuggle org-owns-org back in through the creation flow, contradicting a ratified sub-domain decision. The human takes the mandate; the org↔org link is an affiliation (D-12). |
| DT-13 | Detection should enforce name uniqueness to protect trademark holders | The plausible-sounding legal argument | ❌ REJECTED — the platform cannot adjudicate trademark (jurisdiction, class, use in commerce, priority), and enforcing uniqueness would hand a contested name to whoever typed it first: DT-02's land-grab wearing a lawyer's coat. **Creating a page is not a claim to a name.** Name conflicts route to 24 and 01.05.03, where adjudication is what the flow is *for*. |
| DT-14 | Org creation is a destination flow reached from a profile | How the surface pass's Happy Path reads ("taps Create a band from their profile") | ❌ REJECTED as *sufficient* — it must also be **invocable inline from any flow that needs to name a party** (D-13): credit capture (02), lineups (01.03.01), bookings (17). This falls straight out of the thesis — consolidation exists to put the platform *in the room*, and any detour out of the room to a creation destination is where the fact is lost. 01.05.01 already requires exactly this for shadow parties; the same rule must hold for orgs the creator *is* in, or the flows diverge for no reason a user could perceive. |
| DT-15 | A multi-type entity needs a per-type lifecycle state | The sub-domain CX file's own framing: "A multi-type entity with divergent terminal states per type is unmodelled — the sharpest open question in the sub-domain" | ❌ REJECTED, and the question dissolves. Per-type lifecycle forks the party identity — the exact thing 01.02.03 D-03 forbids ("followers, reviews, credits attach to the party, never the type"). Lifecycle is **one state on the party** (D-17). A band+label that stops being a band **removes the `band` type** (01.02.03) and stays `active` as a label; terminal states are only available when they are terminal for the whole party. The apparent gap was a category error: ending a capability is a type operation, not a lifecycle operation. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | Creation is cheap and weak; claiming is the proof | DT-02 — otherwise first-to-type owns the venue |
| D-02 | Duplicate detection runs before commit, and offers claim/join instead of create | DT-01 — the cheapest possible point to prevent a split identity |
| D-03 | Orgs are never deleted; lifecycle terminates in dormant/closed/dissolved | DT-03 — deletion would evaporate other people's proof of work. Second payoff: it preserves the name history detection matches against (DT-05) |
| D-04 | Dormancy is a first-class, unstigmatised, reversible state | Seasonal venues and paused bands are normal; treating pause as failure makes users abandon the record instead of updating it |
| D-05 | Detection aggressiveness is **per-type**, never global; and detection **never blocks**, only interrupts | DT-04 — a venue is unique by address, a band name is not unique at all. One threshold is wrong on the domain. Blocking would be DT-02's land-grab by another route |
| D-06 | Detection matches name history + aliases + locality + member overlap + the creator's own entity set — never the current display name alone | DT-05 + sub-domain CX-02 — the split-identity cases that matter are invisible to name-only matching |
| D-07 | Creating an org you are not in is not an exception — it is one of three creation modes, and modes 2/3 are shadow-org creation (01.05.01) with a **custodial** mandate, not ownership | DT-11 — resolves old Q-02 with a mechanism the domain already has. Custodial limits derive from 01.03.03 rule 1 |
| D-08 | Ownership status (`unclaimed`/`owned`/`ownerless`) is **orthogonal** to lifecycle state | An unclaimed venue can be seasonally dormant. One enum for both is a bug that is cheap now and unaffordable later |
| D-09 | A `closing` intent state exists, entered unilaterally, completing automatically when the last obligation clears | DT-07 — otherwise a counterparty who won't settle holds the org open forever |
| D-10 | Only **finite, resolvable** obligations block closure. Perpetual entitlements (royalties, credits, catalogue, followers) never block and always survive | DT-06 — otherwise no label with a catalogue can ever close |
| D-11 | The platform infers **quietness** (a fact) and never **intent** (a state). No inferred terminal state is ever published | DT-08 — nobody declares dormancy, but inferring death and telling fans is a real harm and often false |
| D-12 | The first owning mandate always lands on a human, never on the acting-context org; org↔org links are affiliations (01.03.02) | DT-12 — parent D-03 folded org↔org hierarchy into 01.03.02; the creation flow must not smuggle it back |
| D-13 | Org creation is invocable inline from any flow that needs to name a party, not only from a profile | DT-14 — a detour out of the room is where the fact is lost. Same rule 01.05.01 already applies to shadow parties |
| D-14 | Anti-abuse makes spam **worthless** (unclaimed orgs are inert, unranked, unindexed, permanently attributed), not creation **hard** | DT-09 + DT-10 — hard creation kills the Producer's capture moment, which is the thesis. Rate limits are friction, never denial |

| D-17 | A multi-type entity has **one** lifecycle state, on the party.
