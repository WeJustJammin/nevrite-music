# Feature: Organization Creation & Lifecycle

> **Number**: 01.02.02
> **Parent**: [Organizations & Entity Model](./01.02-organizations-entity-model-index.md)
> **Status**: [SURFACE]
> **Last updated**: 2026-07-16

## Overview

How an entity comes into existence and how it stops — creation, duplicate detection at the moment of creation, dormancy, and closure. The lifecycle matters because an org accumulates the things the platform exists to protect (credits, bookings, reviews, royalty lines), so no lifecycle state may ever destroy them. An org is never deleted; it becomes dormant, closed, or dissolved, and its record of work survives all three.

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Full | Creates a band in seconds from their own profile. Later marks it inactive when it stops gigging — which must not read as failure, and must not remove the catalogue, credits or the fans following it. |
| Producer | Full | Creates a studio org. Their lifecycle risk is different: a studio that closes still holds the credits for everything tracked there, and those credits are other people's careers. Closure cannot cascade. |
| Operator | Full | Creates a venue — commonly by **claiming** a seeded one (01.05) rather than creating from scratch, because their venue is likely already listed. Seasonal dormancy is normal (a festival site, a winter closure) and must not look like closure to bookers. |
| Fan | None | Cannot create orgs. Sees only the *consequences*: a band's page marked inactive, a venue marked permanently closed. Explicit absence — a fan creating a venue page is how directories get polluted. |

> **Access levels**: Full · Config · Read-only · Reports · None

## Behavior

Creation is deliberately cheap: name + type + (for a band) who else is in it. The expensive parts (attributes, verification, payability) accrue later from the flows that need them (01.02.01 D-02).

The creator becomes the first member with an owning mandate (01.03.03) — but **creating an org does not prove you have the right to it**. A person creating "The Lexington" is asserting, not proving; the venue's real operator claims it through 01.05. Creation and ownership are different facts, and the duplicate-detection step at creation is where they meet.

Lifecycle states: `active` → `dormant` (reversible, seasonal, no signal of failure) → `closed` (org stopped trading) / `dissolved` (band-specific, governed by 01.04.04). All are read-preserving.

### Happy Path

1. Musician taps "Create a band" from their profile.
2. System asks for the name and runs duplicate detection *before* creating anything.
3. No match. Band is created; the creator is the first member with an owning mandate.
4. Band is immediately usable: it has a page, an actable context, and can be invited to a gig.
5. Attributes fill in later, from the flows that need them.

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Creating an org that already exists (seeded venue, or another member already made the band) | Duplicate detection intercepts at creation. This is the highest-leverage moment on the platform to prevent a split identity — after creation, it is a merge problem, and merge is expensive (see domain CX-02) | "The Lexington already exists — is this yours? [Claim it] [It's a different one]" — claim routes to 01.05, not to a second entity |
| Two band members each create the band on the same day | Both are legitimate attempts. Detection catches the second; the second person is offered to *join* rather than create | "Someone already created {band}. Ask to join?" |
| Creator leaves the band they created | Ownership must transfer before or on departure. An org with no owning member is unadministrable | Blocked until a successor mandate exists (01.03.03) — see domain CX-06 |
| Org is closed while it has live obligations (open bookings, unsettled money, pending payouts) | Closure blocked, not cascaded | "You have 2 confirmed bookings and an unsettled show. Resolve these before closing." |
| Fan-created spam orgs / vanity venue pages | Fans cannot create orgs (Role Lens). Musicians can — so abuse routes to 24 | Report path |
| Org is closed but its credits are load-bearing for other people | Closure never removes credits. The org page persists read-only | "Closed" state; credits intact and still citable |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Loading | Creation submitted / org fetch | Progress; duplicate check runs before commit |
| Empty | N/A — an org never exists without a name and a member | — |
| Populated | `active` | Normal org page |
| Error | Creation failed | Error with retry; no partial org is ever committed |
| Partial | `dormant` | Page renders with an explicit dormancy note; not discoverable in booking search; owner can reactivate in one tap |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | Duplicate detection belongs to the Canonical Data / Entity Merge cross-cut, so this file should not mention it | The boundary narrowing recorded in the domain overview did move entity merge out | ⏳ SPLIT — merge (reconciling two records that already exist) is the cross-cut's. **Prevention at the creation moment is a product flow that lives here**, and it is worth far more: the entity-merge cross-cut is the expensive cleanup for the case this step prevents. Handing the whole problem to the cross-cut would delete the cheap fix and keep only the dear one. |
| DT-02 | Creating an org proves you own it | Implicit in every "create your band" flow | ❌ REJECTED — and the distinction is load-bearing. Creation is an assertion; claiming (01.05) is a proof. Conflating them means whoever types the name first owns the venue, which is a land-grab surface. It also means the seeded-venue case (01.05.01) has no home. Creation must be cheap *and* weak. |
| DT-03 | An org can be deleted | Standard CRUD assumption | ❌ REJECTED — an org accumulates other people's careers. Deleting a studio would evaporate the credits of everyone who ever tracked there, which is the precise failure in `problem-statement.md` ("the proof of it evaporates"), delivered by the platform itself. Lifecycle terminates in states, never in deletion. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | Creation is cheap and weak; claiming is the proof | DT-02 — otherwise first-to-type owns the venue |
| D-02 | Duplicate detection runs before commit, and offers claim/join instead of create | DT-01 — the cheapest possible point to prevent a split identity |
| D-03 | Orgs are never deleted; lifecycle terminates in dormant/closed/dissolved | DT-03 — deletion would evaporate other people's proof of work |
| D-04 | Dormancy is a first-class, unstigmatised, reversible state | Seasonal venues and paused bands are normal; treating pause as failure makes users abandon the record instead of updating it |
