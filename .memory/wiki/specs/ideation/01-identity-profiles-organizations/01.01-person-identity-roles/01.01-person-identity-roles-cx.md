## Cross-Cut Details

### CX-01: Person Record ↔ Acting Context Switcher

**Relationship**: The person record is the root context and the source of the role facets that decide which surfaces any context exposes. The switcher never stores a list — it computes one, and the person record is always its first entry. This is what makes the switcher impossible to leave stale.

**Role scoping**:
- **Musician**: adds a `seller` facet, and selling surfaces appear within whichever contexts can sell — no per-context configuration.
- **Producer**: their facet set is what makes their studio context able to offer services in 05.
- **Operator**: personal facets are distinct from the org context's capabilities — the venue's PA is not a fact about them.
- **Fan**: one context, zero facets, switcher absent.

**Synthesis questions answered**:
1. **Shared state conflict**: The person record owns facets outright. The switcher holds no state, so there is nothing to merge.
2. **Trigger chain**: Facet added → surfaces revealed in the active context. Synchronous. If facet write fails, no context changes — the switcher reads through, so there is nothing to roll back.
3. **Permission intersection**: No. A facet is a claim, not an authorisation (01.01.01 DT-02). It reveals surfaces; the Roles & Permissions cross-cut still decides every action.
4. **Notification fan-out**: None. Facet changes are private.
5. **State transition conflict**: Facet removal with live dependencies is blocked at the record (01.01.01 Edge Cases), so the switcher can never present a context whose facet vanished mid-session.

### CX-02: Aliases ↔ Acting Context Switcher

**Relationship**: Every alias is an actable context. This is the mechanism by which a producer replies to a client as their producer alias, then posts a release as their artist alias, without two accounts. Alias creation and context availability are the same event.

**Role scoping**:
- **Musician**: switches to an alias to post, release, or reply as that project.
- **Producer**: switches between producer alias and artist alias — the industry-normal case.
- **Operator**: not affected — no aliases (01.01.02 Role Lens).
- **Fan**: not affected — no aliases, therefore one context, therefore no switcher.

**Synthesis questions answered**:
1. **Shared state conflict**: Alias record owns the alias. The switcher reads it. No conflict.
2. **Trigger chain**: Alias created → context appears. Alias retired → context disappears, but work done in it persists (01.01.02 D-03). Retirement must not orphan drafts authored in that context — `[PENDING — Step 5]`.
3. **Permission intersection**: Yes, for shared aliases (Q-01 on 01.01.02) — a co-owned alias is a context two people can act in, which is a mandate question this sub-domain has not yet resolved.
4. **Notification fan-out**: Alias-scoped notifications route to the owning person(s); a shared alias fans out to all co-owners.
5. **State transition conflict**: Two co-owners acting as one alias simultaneously can race. Unresolved — this is the strongest evidence for Q-01 (shared alias may be an org).

### CX-03: Aliases ↔ Legal vs Public Identity

**Relationship**: The most consequential intersection in the sub-domain. Because credits reference the alias (01.01.02 D-02) rather than the human, a person can change their legal name and their entire public credit history follows automatically — no rewrite, no contract tampering, no residue. If credits had referenced the human's name, a name change would either falsify history or leave the old name in public forever. One ontology decision made a whole class of harm unreachable.

**Role scoping**:
- **Musician**: changes their name; public credits follow; signed contracts keep the historic name as evidence.
- **Producer**: same, plus they hold others' legal identities from capture moments — those are disclosures, not profile data.
- **Operator**: mostly unaffected personally; org trading name is 01.02.01's.
- **Fan**: no alias, so no separation — their exposure is transactional only.

**Synthesis questions answered**:
1. **Shared state conflict**: Distinct records. The alias is public identity; the legal surface is separate and separately authorised. No overlap by construction — that is D-01's whole purpose.
2. **Trigger chain**: Legal name change → future agreements use the new name; public surfaces untouched (they were never reading the legal name). Alias change → public surfaces update; contracts untouched.
3. **Permission intersection**: Yes, and it is the important one — no path from "view alias" to "view legal name" may exist at any read site.
4. **Notification fan-out**: A legal name change notifies nobody publicly. Counterparties with an active disclosure `[PENDING — Step 5: do they get told?]`.
5. **State transition conflict**: Historic contract vs current public identity intentionally diverge and must never be reconciled. Divergence is correct here.

### CX-04: Person Record ↔ Aliases

**Relationship**: Alias creation is an implicit professional assertion. There is no state where someone holds an alias but no professional facet — creating one crosses the Fan/Musician boundary by definition.

**Role scoping**: Musician/Producer — routine. Operator — n/a. Fan — this is the boundary crossing itself; it must be non-destructive per 01.01.01 DT-03.

**Synthesis questions answered**: 1, 3, 5 deferred. (2) **RESOLVED — DQ-01.A/DQ-01.B.** Alias created → the `performer` facet (always and only `performer`) is **auto-added, disclosed pre-write inside the single Create action**: one line — *"Creating this name adds Performing to your account. Nothing you already have changes."* — then alias and facet are written together. Not prompted (01.01.01 D-12), not silent (01.01.02 D-10), and with **no decline branch**, because a refusal has nowhere to sit against 01.01.02's all-or-nothing creation contract (E-14/E-15) or this cross-cut's own rule that there is no state where someone holds an alias but no professional facet. The two files no longer disagree: prompting and silence are different axes, and the ratified shape avoids both. (4) No fan-out.

### CX-05: Legal vs Public Identity ↔ Acting Context Switcher

**Relationship**: The acting context selects *which party* a disclosure moment discloses. Signing a split as yourself discloses your legal name; signing as your band discloses the band's registered details and the mandate that let you sign. Getting this wrong means either over-disclosing a person or producing an unenforceable signature.

**Role scoping**: Musician/Producer — both cases occur. Operator — signs as the org almost always. Fan — single context, no ambiguity.

**Synthesis questions answered**: Medium confidence — 1, 4, 5 deferred to Step 5. (2) Context switch → disclosure target changes. (3) Yes — acting for an org requires a mandate (01.03.03) that permits binding it; without it, the signature is void and the disclosure was pointless.
