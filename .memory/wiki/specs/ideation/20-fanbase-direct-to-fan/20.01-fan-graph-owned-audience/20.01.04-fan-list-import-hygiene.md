# Feature: Fan List Import & Hygiene

> **Number**: 20.01.04
> **Parent**: [Fan Graph & Owned Audience](./20.01-fan-graph-owned-audience-index.md)
> **Status**: [SURFACE]
> **Last updated**: 2026-07-16

## Overview

The migration path in — CSV from a gig signup sheet, an export from Mailchimp or Bandcamp, a decade of
addresses in a spreadsheet — and the ongoing hygiene that keeps the resulting list sendable: bounce handling,
suppression, dedupe, and role-address stripping. It is simultaneously the domain's **adoption gate** (an
artist will not move here if their list cannot come with them) and its **largest liability** (imported records
carry consent nobody witnessed, and on a shared sending domain their complaints are everyone's problem).

## Role Lens

| Role | Access | What They See/Do |
|------|--------|-------------------|
| Musician | Full | Uploads a CSV or connects an existing ESP/Bandcamp export; maps columns; **asserts the source and consent basis** of what they are uploading; sees exactly what was created, what was skipped, and why. Sees ongoing hygiene: hard bounces removed, complaints suppressed, list health per segment. |
| Producer | None | No visibility — no list to import. |
| Operator | Full | Identical, for a venue list — typically a long-lived and messy one (box-office exports going back years, often the room's most valuable asset). |
| Fan | None | Invisible to them, which is precisely the hazard: the fan's first knowledge of an import is an unexpected email. The mitigation is not fan-facing UI here — it is throttling and consent provenance ([20.01.02](./20.01.02-consent-legal-basis.md)). |

## Behavior

Import is modelled as a **source of observations**, identical in kind to a ticket scan or a store purchase
(`-cx.md` R-02) — with one difference that governs everything: the platform did not witness the consent. The
artist asserts it. That assertion is recorded as provenance strength on the consent event, never converted
into equivalence with a witnessed grant.

Import may **never** override suppression (`-cx.md` CX-06) and may never downgrade a stronger existing record.
It writes only where it strictly adds.

Hygiene runs continuously afterwards: hard bounces suppress permanently, soft bounces retry then suppress,
complaints suppress permanently and count against the artist's [sender reputation](../20.03-broadcast-fan-messaging/20.03.04-deliverability-sender-reputation.md).
Role addresses (`info@`, `booking@`, `noreply@`) are flagged — they are not fans and they are complaint magnets.

### Happy Path

1. Musician uploads `mailchimp-export-2026.csv` (4,812 rows)
2. System previews the mapping — email, first name, signup date, signup source — and asks the question that matters: **where did these people agree to hear from you, and when?**
3. Musician selects "Mailchimp double opt-in list, 2019–2025" and confirms
4. System processes: 4,812 rows → 312 already known (untouched), 47 previously unsubscribed (**skipped, not creatable**), 96 hard-bounced/invalid syntax, 22 role addresses flagged, 4,335 created with provenance `artist-asserted: prior ESP double opt-in`
5. Musician sees the breakdown and the consequence stated plainly: the new records enter a warm-up tier — first sends are throttled ([20.03.03](../20.03-broadcast-fan-messaging/20.03.03-send-scheduling-throttling.md)) because a cold blast to 4,335 unwitnessed addresses is how a sending domain gets blocklisted

### Edge Cases / Failure Modes

| Scenario | What Happens | User Sees |
|----------|-------------|-----------|
| Artist cannot answer the provenance question | Import **completes** and records land in an unmarketable tier. Data is never lost because a compliance question was unanswerable. | "Imported, but not yet sendable — tell us where these came from, or run a re-permission campaign." |
| Artist asserts a false provenance ("double opt-in") for a bought list | The platform cannot detect this at import. It surfaces later as complaint rate, and is handled by [20.03.04](../20.03-broadcast-fan-messaging/20.03.04-deliverability-sender-reputation.md) throttling and 24. **This is the domain's most serious unsolved abuse vector.** See DT-02. | Nothing at import; consequences at send. |
| Re-import of a stale CSV containing since-unsubscribed fans | Skipped, unconditionally, with no override — not for admin, not for support. | "47 records skipped — these people unsubscribed." |
| CSV with no consent column at all (a gig signup sheet photographed and typed up) | The common real case. Provenance = artist assertion + a date range they give. | Same flow; warm-up tier. |
| Encoding/format mess (Excel mangling, BOM, semicolon delimiters, `Name <email>` in one column) | Parser tolerates and previews. Import never silently drops rows. | Row-level preview with per-row errors before commit. |
| Import of 200k rows from a venue's decade-old box office | Volume is fine; the consent age is not. `[PENDING — /ideate-discover Step 5 deepening]` on whether stale consent (Q-02 on [20.01.02](./20.01.02-consent-legal-basis.md)) blocks. | `[PENDING]` |

### States

| State | Trigger | What User Sees |
|-------|---------|---------------|
| Loading | File uploaded | Parse + preview progress; row count and detected columns |
| Empty | No imports yet | Empty state offering CSV, ESP connect, Bandcamp/Bandsintown export paths |
| Populated | Import complete | Breakdown: created / already known / skipped-suppressed / invalid / flagged, each expandable to rows |

## Deep Think Annotations

| # | Hypothesis | Source | Outcome |
|---|-----------|--------|---------|
| DT-01 | Import is a low-value utility feature — table stakes, safe to defer | Initial read of the candidate list, where it sat as an unremarkable child | ❌ REJECTED — it is the **adoption gate for the entire domain**. An artist with 5,000 Mailchimp subscribers will not run their fanbase here if the list must be rebuilt from zero; without the list, segmentation ([20.02](../20.02-segmentation-superfan-intelligence/20.02-segmentation-superfan-intelligence-index.md)) has nothing to segment and broadcast has nobody to send to. The whole sub-tree is dead on arrival without it. Proposed `must` on that basis alone. |
| DT-02 | The dangerous import is the honest artist with a messy list | Reasonable-seeming assumption | ❌ REJECTED — the dangerous import is the artist who **asserts consent they do not have**, and the platform has no way to detect it at import time. Worse, the cost is **externalised**: their complaints degrade the shared sending reputation for every other artist ([20.03.04](../20.03-broadcast-fan-messaging/20.03.04-deliverability-sender-reputation.md)). This makes it a *platform* risk, not a per-artist one, and it means enforcement cannot be optional or purely legal — it has to be mechanical (warm-up tiers, complaint-rate circuit breakers). Flagged to `/create-prd-security` and 24. |
| DT-03 | Two-way sync with an existing ESP would ease migration | Product instinct — "meet them where they are" | ❌ REJECTED for this domain — sync implies the artist keeps Mailchimp, which means consent state has two masters and the "owned audience" claim is false. One-way import (with re-import) is honest; sync manufactures a consent split-brain in which neither system can answer who unsubscribed first. Bulk sync tooling generally is CX-M29 — if the owner wants sync, it belongs there, and the consent hazard must go with it. |

## Decisions

| # | Decision | Context |
|---|----------|---------|
| D-01 | Import asserts provenance; it never manufactures witnessed consent | The platform's whole thesis is that reconstructed facts are worth less than captured ones. Applying that honestly to our own import path means admitting an imported list is weaker evidence — and pricing that in with throttling rather than pretending otherwise. |
| D-02 | Import never overrides suppression, for any role | No admin override. The re-import resurrection bug is common, unlawful, and entirely preventable. |
| D-03 | Unanswered provenance imports data anyway, into an unmarketable tier | Losing an artist's list because they could not answer a compliance question is a worse failure than holding unsendable rows. |
| D-04 | One-way import only; no two-way ESP sync | See DT-03. Sync creates consent split-brain and contradicts the owned-audience claim. |
