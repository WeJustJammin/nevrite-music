## Cross-Cut Details

### CX-01: Rig Definition ↔ Compatibility Oracle

**Relationship**: The oracle is a pure function of two inputs — this rig, that target — and it can
only check what the definition actually states. Real rigs are full of holes: gear the user doesn't
own, placeholders for backline, and specs (voltage, current draw, connector type) that nobody
records because they've never needed to. The oracle's real-world coverage is therefore much lower
than it looks, and it must report what it *couldn't* check as prominently as what it did.

**Role scoping**:
- **Musician**: defines a rig once and expects the check to be complete. It won't be, and the gap must be visible rather than silently passing.
- **Producer**: defines studio signal paths where the specs are better known but the gear is older and less documented.
- **Operator**: read-only — they are the target, not the author.

**Synthesis questions answered**:
1. **Shared state conflict**: The oracle is a reader; the definition owns the rig. No conflict.
2. **Trigger chain**: The check runs on demand and when a target's data changes. An unchecked item must never render as compatible.
3. **Permission intersection**: Checking against a venue's published backline requires that data to be published (15.07.03) — the oracle can see only what the Operator chose to expose.
4. **Notification fan-out**: A target's spec changing after a check should re-notify — the room that had a 230V supply last month may not this month.
5. **State transition conflict**: A check run against a target's data that changes before the show. The check is a snapshot; the show is later.

### CX-02: Rig Definition ↔ Rig Spec Sheet

**Relationship**: The sheet is a projection of the definition at a different resolution. The
signal chain a guitarist maintains for themselves and the tech spec a venue's crew reads contain
the same objects, but the crew needs power draw, connector types and physical dimensions while the
player needs order and routing. One store, several renders — and the definition must therefore
carry the crew's fields even though the player has no personal use for them, which is why the
spec sheet's data will always be incomplete unless something else motivates its capture.

**Role scoping**:
- **Musician / Producer**: author the definition, export the sheet.
- **Operator**: receives the sheet through domain 18's advancing flow; never authors it.

**Synthesis questions answered**:
1. **Shared state conflict**: None — the sheet stores nothing.
2. **Trigger chain**: Export on demand. A sheet exported and sent is a snapshot; if the rig changes afterwards, the venue holds a stale document. `[PENDING — /ideate-discover Step 5 deepening]`
3. **Permission intersection**: Exporting a rig containing gear the user doesn't own (15.08) discloses someone else's asset.
4. **Notification fan-out**: None inherent; domain 18 owns the advancing conversation.
5. **State transition conflict**: Rig edited after the sheet was sent — the venue's copy and the platform's diverge silently.

### CX-03: Compatibility Oracle ↔ Rig Spec Sheet

**Relationship**: The oracle's finding is often not actionable by the person who receives it. "Your
amp is 120V and the venue is 230V" tells the band something they cannot fix from a tour bus — but
"this band needs a 230V step-down at position 3" tells the venue something they *can* fix, and
often already have in a cupboard. Routing the oracle's output into the outgoing spec sheet
converts a warning into a request, which is the only form that prevents the failure.

**Role scoping**:
- **Musician / Producer**: see the mismatch and want it solved, not reported.
- **Operator**: receives it as a requirement they can act on — which is the whole value.

**Synthesis questions answered**:
1. **Shared state conflict**: None.
2. **Trigger chain**: Oracle finding → requirement line on the sheet. Medium confidence because the sheet's delivery is domain 18's advancing flow, and a requirement that arrives the day of the show is not a requirement, it is a complaint.
3. **Permission intersection**: A requirement reveals something about the band's rig to the venue — which is the intent, and is fine.
4. **Notification fan-out**: Belongs to domain 18.
5. **State transition conflict**: `[PENDING — /ideate-discover Step 5 deepening]`
