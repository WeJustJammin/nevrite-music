## Overview

Shard 10 owns asserted/consented ownership records for works and recordings, split capture, transfers and encumbrances, chain of title, rights conflicts, consent for AI/voice/likeness uses, identifiers and publication-safe evidence. It records evidence and agreement; it does not turn credits into ownership, adjudicate legal merits, promise clearance, hold funds, collect royalties, register automatically or provide legal advice.

## Features

- **09.01 Rights Registry** — work/recording duality, exact-rational ownership ledgers, master control/encumbrances, publishing structures, performer facts and sample provenance.
- **09.02 Split Capture & Agreements** — creation-time split proposals, producer points, work-for-hire/buyout designation and superseding re-consent.
- **09.03 Chain of Title & Rights Lifecycle** — attributed title events, term/territory/reversion, termination windows, succession, term/public-domain and moral-right status.
- **09.04 Rights Conflicts & Disputes** — deterministic/probabilistic conflict detection, scoped evidence cases and rights-side freeze instructions.
- **09.05 AI, Voice & Likeness Consent** — scoped AI-training consent, person-held NIL positions and orthogonal AI declarations without detection.
- **09.06 Rights Evidence & Public Record** — identifier allocation/reconciliation, universal possession timestamping, registration preparation and publication-safe lookup.

## Acceptance Criteria

- **AC-RGT-01 — Assert work/recording:** Given Authenticated actor holds assertion authority for the acting party — a Producer or master administrator may assert a recording or master draft and a named owner or writer may assert either — an explicit kind of `work` or `recording` is supplied, and any source project or version reference is readable to that actor; no project artifact is ever auto-promoted into a rights object, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Authorized actor creates separate composition/recording records; names parties without assigning shares; link optional until release, and (6) return Immutable assertion and possession timestamp commit; if the flow cannot complete, `VALIDATION_FAILED` for a missing or ambiguous object kind, `FORBIDDEN` for an actor without assertion authority for the acting party, `ACTING_CONTEXT_STALE` or `IDEMPOTENCY_MISMATCH` on a replayed request carrying different content; a creation-proof anchor outage never loses the object — the record commits with a failed proof state, raises a loud retryable task and re-anchors the same source hash — and a non-empty, consented or earning record can never be deleted.
- **AC-RGT-02 — Link recording/work:** Given Actor holds authority over the recording, every referenced work exists and is readable to that actor, each link carries its type and a positive reduced exact-rational weight whose values sum to exactly one, and the current link-set version is supplied, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Actor creates weighted typed links whose positive exact-rational weights sum to 100%; concurrent stale edits reject, and (6) return New link-set version and validation result commit; if the flow cannot complete, `VALIDATION_FAILED` for a non-positive weight or a set that does not sum to exactly one — displayed decimals never round back into stored weights — `FORBIDDEN` for an actor without recording authority and `VERSION_CONFLICT` when a concurrent stale link-set edit loses the race, which rejects outright rather than merging; recording lineage edges are untouched by a refused link edit because work links and recording lineage are separate facts.
- **AC-RGT-03 — Draft/propose ownership ledger:** Given Editor holds authority on the object and right type being drafted, every row names a resolvable party with a reduced positive exact rational and a recorded row author, and the territory profile is stated; a draft may persist unbalanced, but proposing additionally requires the structural and arithmetic invariants to hold — writer rows sum exactly one per territory, publisher rows anchor to writer rows and sum exactly to each anchor share, master ownership rows sum exactly one, encumbrances stay outside the ownership sum, and no zero-percent ownership row exists, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Editor enters exact-rational rows, party/type/territory and row authorship; draft may be unbalanced, proposal may not, and (6) return Frozen whole-ledger version and consent requests created; if the flow cannot complete, `LEDGER_UNBALANCED` on proposal with the exact deficit or excess named and no auto-remainder row created — the draft still persists as `unallocated` — `TERRITORY_INCOMPLETE` when the territory profile does not cover the right, `VALIDATION_FAILED` for a zero-percent or unreduced row, `FORBIDDEN` for an actor without authority on the object and `VERSION_CONFLICT` when the ledger moved first; a refused proposal leaves the current governing ledger version and every existing consent untouched.
- **AC-RGT-04 — Consent/refuse ledger:** Given The acting party appears in the frozen proposed ledger's consent set as a row party or an anchored publisher holder, the exact frozen ledger version and row hash the action references still match the current proposal, the complete ledger and its exact values were presented before the action, and a signed-link action additionally binds its intended recipient, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Named party sees complete ledger and exact values, then consents/refuses; stale link or version cannot apply, and (6) return Row consent evidence plus aggregate ledger state commits; if the flow cannot complete, `CONSENT_STALE` when the referenced ledger version or row hash has been superseded, because any row change resets every consent and the stale action cannot apply, `FORBIDDEN` when a party acts on a row it is not authorized for and `VALIDATION_FAILED` for a malformed decision; refusal leaves the ledger `refused` rather than advancing it, an unreachable party leaves the proposal pending and blocked indefinitely, and silence, opening a link or a read receipt never counts as consent while the current consented ledger keeps governing.
- **AC-RGT-05 — Capture split at close:** Given A Shard 09 session close moment has fired for a work the acting party may draft splits on and supplies participants and claim references only — never percentages — each participant's designation is captured as the explicit ternary `share`, `fee` or `present-not-party`, and an ensemble contractor binds other players only under recorded Shard 01 agency, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Shard 09 moment pre-fills parties/designations, never percentages; share/fee/present-not-party remain explicit and skippable, and (6) return Draft/proposal/debt stored without blocking session; if the flow cannot complete, `VALIDATION_FAILED` for a designation outside the ternary, `FORBIDDEN` when the actor may not draft splits for the work and `ACTING_CONTEXT_STALE` when the capture moment's acting context has expired; an empty, skipped or open designation is not an error and persists as first-class capture debt, no failure here blocks or reopens the session close, and individual extinguishment consents that no recorded agency covers remain pending rather than inferred.
- **AC-RGT-06 — Record producer points:** Given Actor holds master-administration authority on the recording, the entry names its base, exact rate, tier, term, payee and recoupment terms, the base tier's existing encumbrance sum leaves room so that the tier stays at or below 100%, and the same contribution carries no work-for-hire fee because points and a WFH fee are mutually exclusive per contribution, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Parties specify named base, exact rate, payee and recoupment terms as master encumbrance, not ownership share, and (6) return Consented encumbrance version and title event commit; if the flow cannot complete, `VALIDATION_FAILED` for a missing named base, an unnamed payee, or a tier that would exceed 100%, `FORBIDDEN` for an actor without master administration on the recording, `CONSENT_REQUIRED` until the consenting parties have accepted the encumbrance and `VERSION_CONFLICT` on a competing encumbrance edit; a refused entry never lands as an ownership ledger row because points are an assignable encumbrance and never an ownership share, so the recording's ownership sum is unaffected.
- **AC-RGT-07 — Record work-for-hire/buyout:** Given Actor is the payer or holds standing to record the designation, the buyout is scoped to an exact contribution rather than to a person, designation and consideration are supplied atomically with the beneficiary explicitly named or explicitly none, and both designee and payer consents are collected unless approved engagement evidence waives the payer action, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Contribution-scoped designation, consideration, beneficiary and required consents captured without asserting legal effectiveness, and (6) return Agreement/evidence state and ledger gap consequences commit; if the flow cannot complete, `CONSENT_REQUIRED` until every required consent is recorded, `VALIDATION_FAILED` when the designation is not contribution-scoped or the consideration is absent and `FORBIDDEN` for an actor with no standing to record it; the platform never asserts the designation's legal effectiveness, a bought-out contributor is absent from the ownership ledger rather than carried as a zero row, and credit, performer fact, neighbouring-right potential and NIL positions all survive the buyout.
- **AC-RGT-08 — Amend split/ledger:** Given Proposer has standing on some ledger version in the object's chain, the per-party before-and-after delta and the downstream impact manifest covering licences, registrations, accounting runs and releases are produced, any share decrease carries the affected party's explicit consent to the exact decreased value, and a cross-ledger proposal is packaged so master and publishing advance together or not at all, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Authorized prior/current party proposes delta; one open proposal, all affected consents reset, current version governs until unanimous required consent, and (6) return Successor version or blocked/disputed proposal; if the flow cannot complete, `VALIDATION_FAILED` when the proposer has no standing on any version in the chain or a share decrease lacks its exact acknowledged value, and `CONSENT_STALE` because any change resets the whole consent set; a second proposal raised while one is already `open` is not rejected but queues with its source snapshot and must rebase rather than merge, an unreachable party leaves the proposal blocked indefinitely with at most three resends per rolling seven days while saving stays unlimited, the current ledger keeps governing until the successor is fully consented, and there is no admin override.
- **AC-RGT-09 — Record transfer/grant/reversion:** Given Actor holds standing to record the event for the named party, the event supplies right type, exact share, territory, period, from and to parties, evidence and a `TrustLevel`, any grant states both its territory and its term explicitly, a fixed reversion executes only under a versioned approved rule, and a succession event is recorded under verified Shard 01 representation, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Actor selects right, share, territory, term, parties, evidence and trust level; fixed reversion may execute only under approved rule, and (6) return Chain event and current registry projection update atomically; if the flow cannot complete, `VALIDATION_FAILED` for a grant with a missing term — incomplete is never read as perpetual — `TERRITORY_INCOMPLETE` when the territory or right scope does not resolve, `FORBIDDEN` for an actor without standing and `COUNSEL_GATE_DISABLED` for an automated legal action outside the fixed approved rules; conflicting transfers both remain visible with no silent winner while control stays blocked or uncertain pending a case, a conditional reversion only notifies rather than executing, and a compelled court-ordered action records as `court_ordered` and never as consent.
- **AC-RGT-10 — Resolve control summary:** Given The requesting actor may read the object's rights state and the derivation reads only consented ledgers, the consented joint-owner rule, recorded grants, encumbrances, covenants and custody — asserted or merely proposed records are never folded in — with jurisdiction, source, inputs and unknowns available for labelling, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) System derives ownership/control/encumbrance/covenant outcome from consented records and labels uncertainty honestly, and (6) return Verdict `authorized`, `blocked` or `no_recorded_obstacle` with evidence links; `no_recorded_obstacle` never asserts clear title; if the flow cannot complete, `FORBIDDEN` when the actor may not read the object's rights state and `CONTROL_BLOCKED` when a recorded obstacle or an active conflict prevents an authorized verdict; where inputs are missing or contradictory the summary preserves the gap and returns uncertainty with its jurisdiction, source, input and unknown labels plus the non-advice disclaimer rather than a bare verdict, and it never upgrades `no_recorded_obstacle` into a clearance claim.
- **AC-RGT-11 — Detect rights conflict:** Given A claim or write against rights state has been submitted, because detection runs synchronously at claim and write time and is never opt-in; the deterministic classes `arithmetic_overlap`, `double_assignment`, `territory_collision`, `external_conflict` and `public_domain_contradiction` evaluate against readable current records, and a `duplicate_candidate` additionally requires a corroborating writer, identifier or fingerprint signal because a matching title alone never flags, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) At claim time deterministic overlaps and precision-first duplicate signals notify parties; no case/freeze auto-opens, and (6) return Conflict record/dismissibility and evidence snapshot commit; if the flow cannot complete, `VALIDATION_FAILED` when the triggering claim is itself malformed, in which case the write is refused and no detection result is recorded; a detection input that cannot be read leaves the conflict unresolved and visible rather than silently passing, deterministic conflicts can never be suppressed, a `duplicate_candidate` dismissed by either party remembers the exact pair and version so it is not re-raised, and no outcome here auto-opens a Shard 06 case or freezes money.
- **AC-RGT-12 — Open rights dispute:** Given The opening party has standing on the contested right, the case scope names exactly one right, share, territory and period because a broader scope is not accepted, and the Shard 06 case service is reachable to create the linked case, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Standing party opens Shard 06 case scoped to right/share/territory/period; platform evidence remains unweighted, and (6) return Case link, contest state and optional freeze request; if the flow cannot complete, `FORBIDDEN` for a party without standing on the contested right and `VALIDATION_FAILED` for a scope that is not exactly one right, share, territory and period; a Shard 06 outage leaves the contest unopened and retryable rather than half-created, the platform's own evidence stays unweighted and its merits unadjudicated, and any attached freeze remains a request until independently authorized.
- **AC-RGT-13 — Freeze disputed share:** Given An authorized legal or payment workflow outcome exists on a linked case, the instruction targets the exact contested share, territory and period because a whole-work freeze is prohibited, a downstream adapter is named to acknowledge the hold, and any release names a release authority independent of the share's beneficiary, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Authorized legal/payment workflow targets exact share/territory/period; rights state instructs downstream hold but never holds funds itself, and (6) return Freeze instruction/version; distribution fails closed if required hold fails; if the flow cannot complete, `FORBIDDEN` when the requester is not the authorized case workflow or when a party attempts to release its own disputed hold, and `VALIDATION_FAILED` for a scope wider than the contested share; if the downstream adapter cannot acknowledge the required hold the distribution or payment operation fails closed, Shard 10 never claims custody of funds or pretends they are held, and the instruction stays visibly unacknowledged and retryable.
- **AC-RGT-14 — Record AI-training consent:** Given The acting holder holds the right the position covers and the position states its scope, grantee, use or model, term, territory and compensation; evaluating an actual grant additionally requires a stated position from every relevant holder because the most restrictive position governs and unanimity is required, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) All relevant holders state scoped grantee/use/term/territory/compensation positions; most restrictive controls and no-position stays distinct, and (6) return Consent registry version and grant eligibility result; if the flow cannot complete, `VALIDATION_FAILED` for a position missing scope, grantee, use, term, territory or compensation, `FORBIDDEN` when the actor does not hold the right the position covers and `CONSENT_REQUIRED` when evaluation runs before every relevant holder has stated a position; a holder with no position stays distinctly no-position — unknown, never refusal and never consent — so evaluation returns ineligible-pending rather than defaulting either way.
- **AC-RGT-15 — Record NIL position:** Given The actor is the person the position belongs to or that person's authorized representative under recorded Shard 01 authority, and the position states the voice, name or likeness right kind with its use scope, territory, term and compensation; master ownership, credit, a work-for-hire designation or a representation mandate confers no NIL authority on its own, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Person or authorized representative records voice/name/likeness scope; master/WFH ownership grants no implied NIL authority, and (6) return Person-scoped position/evidence version commits; if the flow cannot complete, `FORBIDDEN` when the actor is neither the person nor its recorded representative — a master owner, credited party or WFH beneficiary is denied here even while holding the recording — `VALIDATION_FAILED` for a position missing its right kind, scope, territory or term and `VERSION_CONFLICT` on a competing position edit; a refused position leaves the person's prior position governing and never lets a downstream voice or likeness use proceed on an inferred grant.
- **AC-RGT-16 — Record AI declaration:** Given The declarant is the contributor or an authorized declarant for the content being annotated, and the declaration is structured with its kind and details and linked to an exact content reference the declarant may read; the platform performs no AI detection, so a declaration exists only where a human asserts it, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Contributor/authorized declarant links structured declaration to content; platform never detects AI or converts absence into human claim, and (6) return Declaration version and downstream disclosure event; if the flow cannot complete, `FORBIDDEN` for an actor who is neither the contributor nor an authorized declarant and `VALIDATION_FAILED` when the declaration's kind, details or content reference does not resolve; a refused or absent declaration renders as undeclared and is never converted into a no-AI or human-origin claim, and a corrected declaration supersedes by appending rather than overwriting the prior one.
- **AC-RGT-17 — Allocate/reconcile identifier:** Given The scheme is served by an approved adapter under a registrant profile — identifier registrant allocation is a later-activation capability rather than consumer launch — the actor holds identifier-operator standing for the object, the request carries a stable request key, and the preflight over existing external and internal identifiers has completed before any allocation is reserved, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Approved adapter checks existing identifiers before allocation; retries are idempotent; conflicts rank but owners confirm canonical, and (6) return Identifier assertion/allocation/reconciliation version; if the flow cannot complete, `IDENTIFIER_PROVIDER_FAILED` when the external scheme is unreachable or rejects the request, `VALIDATION_FAILED` for an allocation attempted without its preflight and `FORBIDDEN` for an actor without operator standing; a retried request returns the same allocation under the same request key and never consumes a second code, two valid identifiers produce a ranked recommendation only so owners confirm the canonical value or open a dispute, and no conflict may be hidden and no identifier asserts legal ownership.
- **AC-RGT-18 — Prepare registration:** Given The actor may read every object in the registration group, the jurisdiction and form version are selected, the source ledger and title versions are pinned into the draft, and the group, source values, gaps and deadline have been presented for review; filing itself is a separately gated later-activation capability, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) User reviews registration group, source values, gaps and deadline; platform never auto-registers or says filing creates copyright, and (6) return Draft artifact and source-version manifest; if the flow cannot complete, `FORBIDDEN` when the actor may not read an object in the group, `VALIDATION_FAILED` for an unsupported jurisdiction or form version and `VERSION_CONFLICT` when a pinned source version moved during preparation; gaps are reported as gaps and never filled by inference, the platform never auto-files and never states that filing creates copyright, and a refused preparation leaves no partial submission evidence behind.
- **AC-RGT-19 — View private/public rights evidence:** Given For the private view the requester is a named party on the ledger or is otherwise authorized to read the object's rights state; for the public view no authentication is required and the request resolves against the dedicated allowlisted publication-safe projection only, which carries holders, contact, one-stop and provenance and never percentages, disputes, private economics or evidence, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Authorized party sees full ledger; public sees separate publication-safe projection without default percentages/disputes, and (6) return Viewer-scoped, provenance-labelled response; if the flow cannot complete, `FORBIDDEN` for an unauthorized private read, returned without disclosing whether a private ledger, dispute or percentage exists; a publication-safe projection that cannot be read returns an explicit unavailable state rather than falling back to the private ledger, and every response carries its viewer scope and provenance labels so an asserted record is never served as consented.
- **AC-RGT-20 — Export signed agreement/title chain:** Given The actor is authorized to read every record the export covers, the export pins an exact right, territory and period together with the current evidence and source versions, and short-lived authorized download delivery is available for the resulting artifact, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) User pins right/territory/period and current evidence; output names its scope, gaps, trust and source versions, and (6) return Immutable artifact/checksum/receipt created; if the flow cannot complete, `FORBIDDEN` when the actor may not read a record inside the pinned scope, `VALIDATION_FAILED` when the right, territory or period is not fully pinned and `VERSION_CONFLICT` when a pinned source version changes during generation, which forces regeneration rather than a mixed-version artifact; the output always names its scope, gaps, trust levels and source versions and never claims clearance or legal effect, and a failed export produces no artifact, checksum or receipt.

### Global Interaction Rules

- Commands carry `actor_person_id`, `acting_party_id?`, `acting_context_version`, `idempotency_key`, `expected_version?`, `request_id` and exact right/territory scope.
- Credit, contribution, ownership, control, custody, collection, registration and payment are distinct facts.
- Exact rationals are canonical; displayed decimals are derived and never round back into stored shares.
- Consent binds the whole frozen ledger version and exact values. Silence, opening a link, being named, credit or representation mandate never means consent.
- Draft capture never blocks creative work; release/payment/licensing gates may later refuse incomplete/conflicted rights.
- Legal-status computations expose jurisdiction, source, inputs, unknowns and disclaimer; no bare verdict or clearance claim.

## Edge Cases

| Case | Required result |
|---|---|
| Unbalanced draft | Persist as unallocated; proposal blocked with exact deficit/excess, no auto-remainder. |
| Ledger edited after one consent | New version resets all consents; stale action rejected. |
| Two concurrent amendments | First opens; second queues with snapshot and must rebase, never merges. |
| Unreachable party | Proposal remains blocked indefinitely; silence never consent and current ledger governs. |
| Bought-out contributor | Absent from ownership ledger, not zero row; credit/performance/NIL records remain. |
| Lineage child diverges | Inherited ledger reference forks to independent copy on first divergence. |
| Conflicting transfers | Both title events visible; control remains blocked/uncertain pending case. |
| Payment freeze adapter fails | Distribution/payment operation fails closed; rights service never pretends funds held. |
| Public-domain declaration conflicts with computed term | Persistent non-dismissible conflict; neither state silently overwrites other. |
| Identifier allocation retries | Same request returns same allocation; never consumes second code. |
| Two valid identifiers | Ranked recommendation only; owners confirm canonical or open dispute. |
| Timestamp anchor outage | Source record commits with failed proof state, loud task and idempotent retry. |
| Public lookup request | Separate safe projection; no hidden percentage/dispute existence leak. |
| AI declaration absent | Render undeclared, never no-AI/human-origin claim. |
