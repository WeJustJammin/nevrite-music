# Shard 20 — Licensing core and instrument lifecycle

**Status:** Complete
**Surface:** Web/PWA, asynchronous projections and provider-reconciled single-payee consideration
**Source:** [Architecture design](../2026-08-02-architecture-design.md) · [Decomposition plan](decomposition-plan.md)

## Overview

Shard 20 owns sync catalogue eligibility, briefs/pitches, bilateral holds, dual-right coordination, scope-specific clearance, completeness/encumbrance evidence, consent routing, pricing/negotiation/MFN, share-scoped owner policy, veto/conflict folding, structured licence instruments, verification and lifecycle. It consumes rights truth from Shard 10 and cannot override missing consent, contested title, encumbrance, payment/counsel gates or post-issue licence history.

### Scope Reconciliation

| Item | Result |
|---|---|
| In-scope source documents | 29 |
| Child capabilities | 19 |
| Core chains | Search/pitch/hold; clearance/attestation/encumbrance/consent; price/quote/MFN; policy/veto/fold; scope/instrument/lifecycle |
| Phase | Phase-2 licensing train after rights, projects, safety and single-payee payment prerequisites |
| Money boundary | Single-payee or £0 consideration only under current architecture; paid multi-counterparty routing/escrow remains B3-disabled |

### Licensing Decisions

| Area | Locked decision |
|---|---|
| Clearance | Computed per `(work, scope)` from fresh consent graph, rights sides, attestations, encumbrances and policy; fail closed and owner cannot override. |
| One-stop | Displayed only when exactly one transacting counterparty controls every required side; otherwise state counterparty count. |
| Catalogue evidence | Human-committed tags/attestations/declarations only. Machine output may propose but never creates clearance. |
| Consent | Route all required parties simultaneously; silence never improves status; buyer blocker detail is privacy-scoped. |
| Policy | Share-scoped, opt-in auto-approval; refusals first, permissions conjunctive, AI training refused by default, exclusivity never auto-approved. |
| Scope | Structured versioned grammar; unset is non-permissive, data use is separate, territory resolves to explicit countries and instruments pin versions. |
| Issuance | Gate issues immutable instrument(s), not owner UI. Required sides issue atomically or not at all; consideration commitment and issuance reconcile as one saga. |
| Lifecycle | Amendments supersede; widening is new consent/policy/price; later regret/veto/encumbrance cannot rewrite an issued licence. |

## Acceptance Criteria

- **AC-LIC-01 — Owner prepares sync catalogue entry:** Given Share owner or licensing administrator for the work; the work, master and assets exist upstream and every catalogue tag is human-confirmed, with each asset-backed flag supported by governed asset evidence, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Bind work/master/assets; human confirms tags; asset-backed flags require governed asset evidence, and (6) return Searchable eligible projection or blocked reasons; if the flow cannot complete, machine-generated tags may propose but never commit, so an unconfirmed tag blocks publication rather than being accepted; missing governed asset evidence blocks the asset-backed flag; blocked reasons return to the owner and the projection carries no rights authority of its own.
- **AC-LIC-02 — Professional buyer searches:** Given Authenticated professional buyer; the query carries a scope snapshot, and only publication-approved catalogue projections with an advisory clearance snapshot are searchable, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Apply metadata/reference candidates and scope snapshot; render clearance status/time basis inline, and (6) return Results with advisory “as of” verdicts; if the flow cannot complete, `SCOPE_REQUIRED` where no scope is supplied, since no verdict is rendered against a default scope; every verdict is advisory and carries its snapshot age, so a stale or unavailable snapshot renders as `unknown` rather than as clear and no cached verdict creates a right.
- **AC-LIC-03 — Buyer creates brief and pitch request:** Given Authenticated buyer, or a buyer representative acting under a declared mandate with the licensee named; hard constraints, target scope, deadline and clearance requirement supplied, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Freeze hard constraints, target scope/deadline and clearance requirement; prefilter pitches, and (6) return Bounded candidate set and eventual terminal statuses; if the flow cannot complete, an undisclosed end client or an inferred corporate affiliate is refused rather than assumed; where no candidate satisfies the frozen hard constraints the brief returns an empty bounded set with the binding constraint named, and every pitch reaches a terminal status rather than lapsing silently.
- **AC-LIC-04 — Buyer requests hold:** Given Authenticated buyer supplying an exact scope and window, with a fresh conflict and clearance check over every required rights side evaluated at request time rather than read from a cached search verdict, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Fresh conflict/clearance check; reserve both required sides for exact scope/window, and (6) return Active bilateral hold or no hold; if the flow cannot complete, `HOLD_CONFLICT` for an overlapping grant or hold, `EXCLUSIVITY_CONFLICT` for a competing exclusive, and `CLEARANCE_UNKNOWN` where conflict cannot be determined, because unknown means no hold; a partial reservation is never created, holds expire automatically, and a refused request is not queued behind the winner.
- **AC-LIC-05 — Owner/participant attests catalogue completeness:** Given Verified attestor with an authority basis for the named rights side, referencing an immutable party-list version and stating knowledge basis, identity, presence, listing and evidence grade, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Reference immutable party-list version, side, knowledge basis, identity/presence/listing and grade, and (6) return Valid, corroborated, contested or superseded evidence; if the flow cannot complete, a contest by a listed party invalidates the attestation immediately and a credible unlisted claim marks it contested and blocks new issuance; a superseding attestation never deletes its predecessor; grade and corroboration disclose quality and never silently convert into consent authority.
- **AC-LIC-06 — Contributor declares encumbrance:** Given Credited contributor declaring against their OWN work or material, supplying source, scope condition and evidence grade; fingerprint output may prompt privately but can never itself declare, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Record own-work sample/material/source/scope condition and evidence grade; no accusation/notification, and (6) return Encumbered/declared state pending owner resolution; if the flow cannot complete, no accusation is raised and no third party is notified; a retraction supersedes and remains attributable rather than deleting history; the scope ceiling is the intersection of upstream clearance instruments and downstream scope can never exceed it, so the work stays `ENCUMBRANCE_ACTIVE` pending owner resolution.
- **AC-LIC-07 — Buyer requests clearance:** Given A complete `LicenceScope` under a pinned supported grammar version with buyer and end client named, territory resolved to explicit countries and unset axes treated as non-permissive; fresh bitemporal rights, consent graph, attestations, encumbrances, holds and policy versions are loadable, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Freeze grammar/scope/buyer/end-client; derive required sides/consent parties and evaluate precedence, and (6) return Clearable, consent-needed, incomplete, encumbered, contested, blocked or unknown; if the flow cannot complete, `SCOPE_REQUIRED` without a scope and `GRAMMAR_UNSUPPORTED` for an unrecognized grammar value; evaluation fails closed along `unknown > blocked > contested > encumbered > incomplete > consent_needed > clearable_now`, so any load failure returns `CLEARANCE_UNKNOWN` rather than a permissive verdict; the buyer sees verdict, snapshot age and remedy class only, never blocker identity, and no owner may override the verdict.
- **AC-LIC-08 — System routes consent:** Given Clearance evaluation has derived the required consent parties — standing parties, not merely share holders — each a verified person with a reachable route, and scope, price and deadline are expressible in plain language alongside the exact legal appendix, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Send one plain-language request per verified person naming all stakes, simultaneously, and (6) return Approve/decline/counter/expired; non-response stays pending; if the flow cannot complete, non-response, an expired identity or an unavailable party never improves clearance and never auto-approves; an unreachable person leaves the request `pending` with its stake named; an erased party's pseudonymous share survives and its fresh-consent scope stays blocked; a partial approval set produces no deal.
- **AC-LIC-09 — Owner configures licensing policy:** Given Share owner or their administrator acting on their OWN share, expressing defaults, per-work overrides, exclusions, thresholds and any opt-in auto-approve under the pinned scope-grammar version, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Save share-scoped defaults/overrides, exclusions, thresholds and opt-in auto-approve under grammar version, and (6) return Versioned policy; no work-wide authority; if the flow cannot complete, `POLICY_BLOCKED` on any attempt to bind another share or assert work-wide authority; a newly added grammar value stays inert until affirmatively adopted rather than being covered by an existing policy; AI training remains refused by default and exclusivity is never auto-approvable; a share transfer ends the prior policy rather than transferring it.
- **AC-LIC-10 — Co-owner creates veto/block:** Given Co-owner with standing on the named rights side, scoping the block by category or by declared buyer/end client, with a term and a reason-disclosure level, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Validate standing side/category/buyer scope; atomically affect future/in-flight requests, not issued licences, and (6) return Active/lapsed/superseded block; if the flow cannot complete, the block is refused where its author lacks standing on that side; it applies atomically to future and in-flight requests only, so an issued instrument is never rewritten and a block arriving during a quote withdraws the affected in-flight quote and consent rather than revoking a licence; lapsed and superseded blocks remain visible in history.
- **AC-LIC-11 — System folds owner policies:** Given A clearance request with every affected owner's share-scoped `licensing_policy_version` resolvable, evaluated in the fixed refusal → eligibility → per-owner threshold → fall-through → pricing order independently of input order, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Apply refusal→eligibility→per-owner threshold→fall-through→pricing order independently of input order, and (6) return Derived attributed verdict; failure blocks/falls through safely; if the flow cannot complete, `POLICY_EVALUATION_FAILED` or an exceeded budget falls through to a human decision, never to approval; silence is non-permissive; the verdict is attributed per owner with its binding owner named, and any evaluation failure blocks rather than defaulting open.
- **AC-LIC-12 — Buyer requests quote:** Given Policy fold has passed for the frozen scope, a `rate_card_version` covers that scope, and the quote pins card, policy, read version, grammar and TTL with the deadline set, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Evaluate policy first, pin rate-card version, scope and deadline; route ask/consent separately, and (6) return Complete quote, partial/pending or expired; if the flow cannot complete, `POLICY_BLOCKED` where the fold refuses, before any price is shown; `QUOTE_EXPIRED` once the TTL elapses, requiring a fresh quote rather than an extension; a partial or pending quote is labelled as such and never presented as complete; the money ask travels separately from consent, so a priced quote implies no consent.
- **AC-LIC-13 — Parties negotiate:** Given A live quote or ask within its TTL, with each counterparty acting on their own share and consent tracked separately from money, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Record money asks/counters/consents until TTL; partial agreement never appears as deal, and (6) return Settled set or no deal; if the flow cannot complete, partial agreement never appears as a deal, so an unsettled counterparty leaves the set at no deal; TTL expiry closes the negotiation rather than implying acceptance; offers and counters are recorded immutably, so a withdrawn ask remains in history.
- **AC-LIC-14 — System evaluates MFN:** Given A complete settled set of eligible distinct counterparties at the fixed settlement point, with self-comparison excluded and agreed price recorded separately from owed price, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) At fixed settlement point compare eligible distinct counterparties; separate agreed and owed price, and (6) return Final owed prices or provisional hold; if the flow cannot complete, `MFN_PROVISIONAL` where the evaluator fails or the settled set is incomplete — the owed price stays provisional and issuance does not proceed, and a later comparison never rewrites an issued instrument's price.
- **AC-LIC-15 — Gate issues licence:** Given Inside a protected transaction with expected versions: buyer, licensee, purchaser authority, end client, scope, required sides, quotes, consents and idempotency key are frozen, clearance, blocks, holds, exclusivity and policy are re-evaluated fresh rather than read from a cached verdict, and the payee topology is single-payee or £0, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Re-evaluate fresh clearance/exclusivity/policy/payment/B3; atomically persist required instruments and commitment record, and (6) return Issued pair/single instrument or no issuance; if the flow cannot complete, `MULTIPAYEE_DISABLED_B3` for a paid multi-counterparty topology, returned before any provider side effect; `CLEARANCE_BLOCKED`, `CONSENT_REQUIRED`, `POLICY_BLOCKED` or `EXCLUSIVITY_CONFLICT` aborts with no partial issuance; `CONSIDERATION_UNCOMMITTED` or an ambiguous provider outcome leaves the transaction pending for reconciliation and never claims charged or issued; a failed transaction voids or refunds the provider commitment; `ISSUANCE_CONFLICT` where a concurrent exclusive commits first, and the required-side instrument pair issues atomically or not at all.
- **AC-LIC-16 — User downloads certificate:** Given An issued canonical `licence_instrument` the actor is party to, plus a resolvable render of that instrument version carrying its unguessable verification reference, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Render PDF/file projection from canonical instrument with prominent unguessable verification reference, and (6) return Reproducible certificate, not authority source; if the flow cannot complete, a failed render leaves the instrument issued and retries the projection, never reissuing the instrument; the certificate is a disposable projection and is never the authority source, so a stale certificate defers to live verification.
- **AC-LIC-17 — Third party verifies:** Given An unguessable live verification reference, with the pinned grammar version, instrument and lifecycle state resolvable at check time, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Live lookup pinned grammar/instrument/lifecycle and timestamped validity window, and (6) return Valid/superseded/terminated/expired/cannot-verify; if the flow cannot complete, `CANNOT_VERIFY` on outage — an outage is reported as cannot-verify and never as invalid; a superseded or terminated instrument returns the safe current status without exposing private terms; the response carries checked-at and the validity window, so an unresolved term trigger reads as `expiry_indeterminate` rather than as an absent or fabricated date.
- **AC-LIC-18 — Parties amend licence:** Given An issued instrument plus the authority of every affected party, with the requested change classified as narrowing, administrative or widening before anything is written, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Classify narrowing/administrative/widening; widening runs new request, consent, price and consideration, and (6) return Superseding instrument or original unchanged; if the flow cannot complete, `AMENDMENT_REQUIRES_NEW_GRANT` for any widening, which runs a fresh scope, clearance, consent, quote and consideration cycle and leaves the original instrument untouched on refusal; issued scope never expands because policy, grammar or ownership later changed; a superseding amendment records rather than edits the original.
- **AC-LIC-19 — System processes term/termination:** Given An issued instrument whose commencement trigger and duration are resolvable, or a breach-termination request carrying instrument-authorized remedy plus Shard 06 evidence or case, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Resolve commencement/duration; warn both sides; breach termination only through authorized evidence/case, and (6) return Active, expiry-indeterminate, expired, superseded or terminated; if the flow cannot complete, a non-computable term stays `expiry_indeterminate` under active lifecycle monitoring rather than receiving a fabricated date; breach termination without instrument-authorized remedy and Shard 06 evidence is refused, since regret is not breach; expiry warns both buyer and owners before it lands, and a later veto, policy or ownership change cannot terminate an issued licence.

### Global Interaction Rules

- Search verdict is advisory; issuance gate always re-evaluates current canonical state.
- Consent graph, share graph, credit graph and payment payees are distinct and may contain different parties.
- Buyer never sees blocker identity/category detail; co-owners receive attributed reasons within their side.
- No licence without valid consideration state; no finalized charge without issued instrument. Ambiguous provider outcomes remain pending reconciliation.
- Paid issuance involving more than one payee/counterparty is denied until B3; consent/quote preparation may proceed without implying payment availability.
- Issued scope never expands because policies, grammar or ownership later changes.

### Types and Errors

## Accessibility

- Search, briefs, consent, policy, quote, hold, issue, certificate and lifecycle flows are keyboard operable with visible focus and stable headings.
- Clearance displays dominant state plus all user-actionable blockers in text; audience filtering never creates unexplained empty UI.
- Structured scope has plain-language summary before legal appendix, with explicit unspecified/refused axes and country-list access.
- Consent/quote deadlines warn before expiry and preserve work after reauthentication; no action depends only on countdown/color.
- Multi-owner tables identify the current user's share/standing and expose derived fold reasoning in linearized text.
- Verification gives timestamp, validity window and cannot-verify state without treating outage as invalid.

## Edge Cases

| Scenario | Required behavior |
|---|---|
| No scope supplied | No verdict or quote; never default scope. |
| Search says clear, owner changes policy | Issuance fresh gate aborts; cached verdict creates no right. |
| One person controls both sides | Two approval/instrument-side records remain; one counterparty may qualify one-stop. |
| One side approves, other declines | No partial deal/licence/hold. |
| Silence/erased party | Never auto-consent; pseudonymous share survives and fresh-consent scope remains blocked. |
| New grammar value | Existing policies do not cover it; affirmative adoption required. |
| AI training omitted | Means none/refused, never implied by broad media rights. |
| Encumbrance retracted | Superseding history remains; downstream scope cannot exceed upstream clearance. |
| Veto arrives during quote | Withdraw affected in-flight quote/consent; issued licence unaffected. |
| Concurrent exclusive attempts | Database exclusion permits at most one; loser refused, not queued. |
| MFN evaluator fails | Owed price stays provisional; no issuance. |
| Provider payment ambiguous | Transaction remains pending; reconcile to issue or void/refund, never charge-only success. |
| Multiple paid counterparties | Consent may complete; issuance denied `MULTIPAYEE_DISABLED_B3`. |
| Certificate render fails | Instrument remains issued; retry projection, never reissue. |
| Verifier outage | `cannot verify`, not invalid. |
| Amendment widens scope | New request/consent/policy/price; original remains if refused. |
| Life-of-copyright/trigger unknown | `expiry_indeterminate` with active lifecycle monitoring, no fabricated date. |
