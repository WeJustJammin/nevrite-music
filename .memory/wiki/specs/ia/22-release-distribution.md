# Shard 22 — Release and distribution lifecycle

**Status:** Complete
**Surface:** Web/PWA, governed media jobs and Phase-2 partner delivery adapters
**Source:** [Architecture design](../2026-08-02-architecture-design.md) · [Decomposition plan](decomposition-plan.md)

## Overview

Shard 22 owns release composition, per-partner validation/readiness, asset conformance, DDEX-style message generation/choreography, store/territory selection and status, release scheduling, catalogue updates/takedowns, UGC fingerprint/claim coordination, delivery-time identifiers and migration/exit. It projects canonical identity, rights, credits and assets; it never rewrites them to satisfy a partner or claims live status without store-side evidence.

### Scope Reconciliation

| Item | Result |
|---|---|
| In-scope source documents | 37 |
| Child capabilities | 25 |
| Build chain | Composition, metadata, readiness, asset conformance, label copy |
| Delivery chain | Partner profile, ERN/projection, choreography, store/territory status and remediation |
| Schedule/lifecycle | Lead-time windows, links/deadlines, updates, voluntary/involuntary takedown |
| Claims/exit | Fingerprint/whitelist/disputes, identifiers and catalogue migration/export |

### Distribution Decisions

| Area | Locked decision |
|---|---|
| Release | Contains recordings, not files; membership/order are release facts, recording facts remain canonical upstream. |
| Validation | Per-partner versioned knowledge/rule/spec packs; no global valid/live flag and no canonical-value mutation. |
| Readiness | Continuously re-evaluated chase list of people/actions; rights consent/conflict/third-party restrictions gate delivery. |
| Delivery | Deterministic per-partner projection with retained message/snapshot/profile/thread; partner deliveries are independent. |
| Status | Acknowledged, accepted and live are distinct; live requires store-side confirmation and store-local clock. |
| Territory | Derived from complete rights records and exact destination/model; unresolved rights never default worldwide. |
| Dates | Delivery/release/live/original-release/first-live are distinct; platform never moves announced date automatically. |
| Lifecycle | Updates/redelivery/takedown are versioned commands; provenance survives and redelivery after takedown is new release. |
| Claims | Fingerprint registration is stricter than delivery; unresolved ownership/uncleared samples block and no dispute auto-response occurs. |
| Identifiers | One ISRC per recording forever; UPC release-scoped; assignment idempotent and survives failed delivery. |
| Label copy | (P)/(C) lines derive from the Shard 10 ownership record; divergence requires a recorded justification visible to co-owners, because the platform must not publish a claim its own records refute. Distributor of record carries a mandatory plain-language consequence statement at the moment it is set. OPEN UPSTREAM, not an IA gap: which party may be named as distributor of record, and whether an owner may deliver through the platform under their own label, is ideation `12.01.05` Q-01, with the label-services question at Q-02 — both owner-owned and deferred to `/create-prd`. |
| Enrichment | MEAD is an independently sequenced, never-blocking delivery generated from one descriptor record that the editorial pitch also reads; inferred values are marked and never delivered as artist assertions. The MEAD field list is partner-knowledge-version data exactly as the ERN field list already is, so this shard enumerates neither — that is not missing information. OPEN UPSTREAM, not an IA gap: whether partners meaningfully consume MEAD is ideation `12.02.04` Q-01 (Agent-owned, deferred to `/create-prd`, never answered), and whether an inferred-value correction propagates to the Shard 09 version-scoped record is `12.02.04` Q-02 (deferred to `/create-prd-security`, blocked on the permission model). The feature ledger still carries MEAD as `Could` assigned to this shard, so the IA layer represents it; a later drop to `wont` is a ledger change that cascades here. |
| Exit | Export always available; imported catalogue marked asserted/not witnessed; lock-in never depends on withholding data. |

## Acceptance Criteria

- **AC-DST-01 — Owner composes release:** Given Release owner or admin holds authority on a release version that is still editable, every added recording is eligible at add time through its own right or a Shard 20 licensed inclusion, each recording's immutable origin is recorded, and the current release version is supplied, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Add eligible recordings/licensed inclusions; set order/type/volume/focus/gapless and schedule licence-expiry obligations, and (6) return Versioned draft composition; if the flow cannot complete, `RECORDING_INELIGIBLE` when a recording carries neither its own right nor a valid licensed inclusion, `RIGHTS_UNRESOLVED` when its rights basis cannot be resolved at add time, `FORBIDDEN` for an actor without release authority — a co-owner or contributor raises a change request instead — and a typed revision conflict to the loser of a competing composition edit; the add-time eligibility snapshot is re-checked at delivery time, a refusal never mutates the canonical recording, and licence-expiry obligations stay scheduled against the membership.
- **AC-DST-02 — System validates metadata:** Given The release resolves to a canonical snapshot, at least one destination is selected, and each selected destination resolves to one immutable pinned partner-knowledge version carrying its rule pack and asset spec, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Evaluate canonical snapshot against selected destination knowledge version; derive per-store renderings/findings, and (6) return Blocking/advisory findings with examples; if the flow cannot complete, `PARTNER_RULE_BLOCKED` for each blocking finding, recorded against its item, field and destination with an example and a remedy rather than as a global invalid flag, `PROFILE_UNCERTIFIED` when the destination's knowledge version has not been admitted, and a typed refusal when no canonical snapshot or destination resolves; no finding mutates a canonical value to satisfy a partner, advisories return separately from blockers, and a profile or model gap is attributed as a platform failure that suspends new delivery for repair rather than being blamed on the artist.
- **AC-DST-03 — Producer supplies assets:** Given A Producer or release owner supplies or selects an immutable source object, confirms its mapping to the release item, and every target destination resolves to an asset spec version so analysis is keyed by `(asset version × spec version)`, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Upload/choose immutable source, confirm mapping; analyze against asset spec and generate non-artistic renditions, and (6) return Conformant/unverified/blocked per target; if the flow cannot complete, `ASSET_UNANALYSABLE` after three failed analysis attempts, leaving that target `unverified` with manual retry available and never a false pass, `PARTNER_RULE_BLOCKED` for a target whose spec the source cannot satisfy, and `FORBIDDEN` for an actor without asset standing on the release; a derived rendition is never an artistic alteration of the source, the immutable source object is retained on every failure path, and target uncertainty is stated per target rather than collapsed into one global verdict.
- **AC-DST-04 — Owner opens readiness gate:** Given The release has a target set whose machine preconditions are evaluable — complete canonical facts, partner profile and rules, asset analysis, artist links, identifiers and destination rights — and the social chase list is built only for items that already pass that machine gate, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Resolve machine preconditions then rights/consent/conflict/third-party chase list and named actors, and (6) return Ready, blocked, exhausted or explicit override path; if the flow cannot complete, `RIGHTS_UNRESOLVED`, `RELEASE_CONSENT_REQUIRED` for absent master consent and `THIRD_PARTY_CLEARANCE_REQUIRED` each hold the target at `machine_blocked` or `social_blocked` with the named actor and action rather than a bare failure; an unreachable or unresponsive party ends at `exhausted`, and only an explicit disclosed `overridden` state proceeds, which changes the delivery decision and never the source record; no stale readiness result authorizes delivery, because any drift re-runs the gate.
- **AC-DST-05 — Owner selects destinations/territories:** Given Every recording on the release resolves to a complete rights record with its encumbrances stated, the exact destination, commercial model and territory set are supplied, and the destination's profile capabilities are readable from its pinned knowledge version, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Derive per recording×territory×model×destination availability and costs from rights/profile, and (6) return Exact footprint or blocked/unknown; if the flow cannot complete, `TERRITORY_UNKNOWN` and `RIGHTS_UNRESOLVED` when a recording's rights record is missing or unresolved for a requested territory, which blocks that territory and never defaults to worldwide, `PARTNER_RULE_BLOCKED` where the destination profile cannot carry the requested commercial model, and `FORBIDDEN` for an actor without destination authority; a complete no-encumbrance record may derive worldwide only with its basis shown, and every blocked or unknown cell states the exact basis for its state.
- **AC-DST-06 — Owner chooses release dates:** Given The destination footprint is derived, each selected partner's lead-time window and business-day evidence are readable from its pinned knowledge version, and the user supplies the chosen date; the system computes and costs the options but never preselects or moves a date, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Compute per-partner earliest deliverable/all-windows-open and costed forfeits; user chooses date, and (6) return Versioned territory-scoped date plan; if the flow cannot complete, `TERRITORY_UNKNOWN` when the footprint the plan depends on is unresolved, a typed refusal when a chosen date precedes a partner's earliest deliverable window, returned with the exact forfeited windows costed rather than silently accepted, and a typed revision conflict on a competing date-plan edit; a store that stays silent into the date triggers a T−24h forced choice in which the announced date stands by default, and the platform never moves an announced date or redelivers automatically.
- **AC-DST-07 — System assigns identifiers:** Given Message generation has been reached for a release whose recordings each resolve to exactly one identity, and the registrant-and-year allocation batch is available so ISRC assignment is recording-idempotent and atomic; a supplied third-party identifier is accepted as a well-formed assertion, not as a globally verified fact, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) At generation, reuse/safely assign ISRCs and UPC policy; reconcile ambiguous allocation by lookup, and (6) return Immutable identifier records independent of delivery success; if the flow cannot complete, `IDENTIFIER_CONFLICT` when a lookup or import finds the same ISRC under a conflicting holder, which blocks and routes to Shard 06 and Shard 10 rather than merging, and an allocation timeout that resolves by lookup and reconciliation rather than a second blind allocation; an assigned identifier is immutable, survives a failed delivery and is never rolled back, one ISRC binds to its recording forever, and a redelivery after takedown takes a new UPC while retaining its ISRCs.
- **AC-DST-08 — System generates partner message:** Given A readiness-passed release pins its canonical snapshot versions, its validation and partner profile version, its identifier set and its message thread for the requested `DeliveryMessageKind`, and the rights and destination basis has been re-resolved at handoff so no stale snapshot enters the generator, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Pin canonical snapshot, validation/profile version, identifier set/thread and deterministic projection; diff prior, and (6) return Retained message and plain receipt; if the flow cannot complete, `DELIVERY_SNAPSHOT_STALE` when rights or destination facts drift after the snapshot was pinned, which halts and shows the diff instead of delivering, `MESSAGE_SEQUENCE_CONFLICT` when the thread for that kind has already advanced, and `PROFILE_UNCERTIFIED` for an uncertified knowledge version; an artist-unrequested delta found by diffing the prior message requires explicit acknowledgement before handoff, and the generator never re-authors or defaults a missing canonical fact to make its own output valid.
- **AC-DST-09 — Delivery operator dispatches:** Given A retained message exists for a certified and runtime-admitted partner profile, the delivery operator holds that assigned profile and queue scope, the dispatch is keyed idempotently by `(message, step)`, and the partner's business-day response window is evidenced, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Verify profile certification/runtime admission; execute idempotent partner choreography per release/partner, and (6) return Sent/received/accepted/rejected/overdue/unknown; if the flow cannot complete, `PROFILE_UNCERTIFIED` when the partner profile is uncertified or its runtime admission is suspended — a suspension blocks new deliveries while still permitting updates and takedowns against pinned versions — `MESSAGE_SEQUENCE_CONFLICT` on an out-of-sequence step, and `FORBIDDEN` when the operator reaches a profile, partner or canonical edit outside its assignment; an overdue window triggers a human chase and never a blind resend, and any retry reuses the same idempotency key so no duplicate release reaches the partner.
- **AC-DST-10 — System reconciles store status:** Given Every acknowledgement carries a partner timestamp for ordering, and any live, preorder, territory or item claim is backed by independent store-side evidence read in the store's local time; a partner acknowledgement alone never satisfies this precondition, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Order acks by partner timestamp and separately verify store-local live/preorder/territory/items, and (6) return Exception-first destination board; if the flow cannot complete, `ACK_QUARANTINED` for an unrecognized or out-of-order acknowledgement, which is retained by partner timestamp and never regresses the recorded state, and a typed `unknown` destination state rather than an inferred one where store-side evidence is unavailable; a partner that accepts while the store is not yet live holds at accepted with a live-wait and no live claim, and a mixed item outcome records a `partial` row whose rejected items stay structured for scoped redelivery.
- **AC-DST-11 — Owner remediates rejection:** Given A rejection finding exists that translates to a concrete item, action and owning actor, the corrected source or approved rendering is supplied, the redelivery scope is limited to the rejecting partner under a persisted per-store plan, and owner Full approval is held wherever the effect is destructive, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Translate to item/action/owner; update source or approved rendering; redeliver only rejecting partner, and (6) return New superseding message/thread step; if the flow cannot complete, `PARTNER_RULE_BLOCKED` when the correction still fails the pinned rule pack, `DELIVERY_SNAPSHOT_STALE` when the release moved under the remediation, and `FORBIDDEN` when a destructive redelivery lacks owner Full approval; recovery is idempotent so a repeated attempt never duplicates a delivery, a non-rejecting partner is never redelivered to as a side effect, and a superseding message opens a new thread step rather than editing the retained prior message.
- **AC-DST-12 — Owner links artist profile:** Given The release names a Shard 01 artist party, the destination's store artist ID resolves to that party, and the link reaches verified Tier-A before that destination's first delivery; landing is separately verified rather than assumed from submission, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Resolve Shard 01 store artist ID, require verified Tier-A before first delivery and verify landing, and (6) return Linked/merge-chase/block; if the flow cannot complete, `ARTIST_LINK_REQUIRED` when the store artist ID is asserted but not verified, which blocks the first delivery and routes to the Trust & Safety merge chase rather than delivering to a guessed profile, and a typed refusal when the destination ID does not resolve to the named party; the state stays honest as linked, merge-chase or blocked, and no failure path fabricates a landing confirmation.
- **AC-DST-13 — Owner manages editorial/pre-save/timeline:** Given The release has a share claim source and a one-use OAuth grant for the destination's editorial surface, hard and soft deadlines derive from the pinned partner windows, and the editorial pitch reads the single `release_enrichment` record rather than holding claims of its own, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Share claim source, one-use OAuth, derive hard/soft deadlines and person-owned critical path. The editorial pitch READS `release_enrichment` rather than holding its own claims — one record, two projections, so the two surfaces cannot tell one partner two different stories, and (6) return Honest submitted/link/deadline states; if the flow cannot complete, `FORBIDDEN` when a co-owner or contributor without a release mandate attempts the pitch, share-claim or deadline action, a typed refusal when the one-use OAuth grant is missing, expired or already spent, and an honest submitted, link or deadline state — never an implied success — where the partner surface does not confirm; a missed hard deadline is stated with its owning person on the critical path rather than silently reassigned, distribution never messages fans directly on any recovery path, and the pitch surface can never author a claim that diverges from the shared descriptor record.
- **AC-DST-14 — Owner changes release date:** Given An announced date plan exists, the acting owner holds the release mandate and supplies the new date, and the forfeits, broken-promise consequences and pre-save partner continuity effects are stated before the change is accepted, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) State broken promise/forfeits, update plan and pre-save partner continuity; emit event only, and (6) return New announced date; no direct fan message; if the flow cannot complete, `FORBIDDEN` when the acting party holds no release mandate over the date plan, a typed refusal when the new date precedes a partner's earliest deliverable window or the required consequence statement was not presented, and a typed revision conflict on a competing date-plan edit; the change emits an event only and never a direct fan message, and a refused change leaves the previously announced date standing rather than partially applying a new plan.
- **AC-DST-15 — Owner updates live metadata/audio:** Given The release version is delivered or live, every requested field or asset change is classified by its per-store effect into metadata update, redelivery, takedown or new release before authorization, and any destructive plan carries owner Full approval with its per-destination steps persisted, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Classify field/store effect and approval; persist per-store plan; credit updates land canonically regardless of store, and (6) return Update/redelivery/new-version path; if the flow cannot complete, `FORBIDDEN` when a destructive plan lacks owner Full approval and `DELIVERY_SNAPSHOT_STALE` when the release moved under the change plan; a metadata update that would replace the master asks explicitly whether this is the same recording or a new version and never silently reuses the identity, label copy or distributor of record on a delivered version routes through the update or redelivery path rather than an in-place edit, and credit updates land canonically whether or not any store accepts them.
- **AC-DST-16 — Owner requests voluntary takedown:** Given The requesting party holds takedown authority on the release, the concrete irreversible losses and their counts have been shown and confirmed, the destination scope is explicit, and an accepted delivery exists at every destination a takedown message would be issued to, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Show irreversible losses/counts, authority and destination scope; issue takedown messages only where accepted delivery exists, and (6) return Withdrawn evidence with provenance retained; if the flow cannot complete, `TAKEDOWN_NOT_DELIVERED` where no accepted delivery exists at a destination, in which case a queued thread is cancelled rather than issuing an invalid takedown message, and `FORBIDDEN` for a party without takedown authority; provenance is retained on every path so a takedown never erases the release's history or its identifiers, and re-entry after takedown is a new release taking a new UPC while retaining its ISRCs.
- **AC-DST-17 — Platform processes involuntary removal:** Given An assigned rights or safety reviewer acts on evidence held under Shard 06, the scope is narrowed to exactly what that evidence supports, and the affected party is reachable so the basis and the contest route can be notified, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Apply legal/rights/safety evidence and narrow scope; notify basis/contest; preserve append-only claim path, and (6) return Suspended/removed with post-mortem; if the flow cannot complete, `FORBIDDEN` for a reviewer acting outside the assigned case or browsing the general catalogue, and a typed refusal when the evidence does not support the requested scope, which narrows the action rather than broadening it; the claim path stays append-only so contest evidence can always be added, the affected party is notified of the basis and contest route on every path, and a post-mortem record is retained with the suspension or removal.
- **AC-DST-18 — Owner registers fingerprint/whitelist:** Given The recording passes the stricter fingerprint gate — resolved ownership, cleared samples and a complete rights record, which is stricter than the delivery gate — the derived whitelist has been reviewed before provider registration, and the provider operation is confirmed rather than assumed, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Apply stricter rights/sample/ownership gate; review derived whitelist and confirmed provider operation, and (6) return Registered/blocked/withdrawn/reconciling; if the flow cannot complete, `CLAIM_REGISTRATION_BLOCKED` when ownership is unresolved or a sample is uncleared, which blocks registration across every supported platform, and `RIGHTS_UNRESOLVED` when the underlying rights record is incomplete; an unconfirmed provider write holds at `reconciling` rather than reporting registered, an unresolved UGC conflict blocks any new registration, and a withdrawal is recorded explicitly rather than inferred from provider silence.
- **AC-DST-19 — Artist handles UGC claim:** Given A claim case exists whose people, videos and held evidence are available to the acting artist or owner, and the response is an explicit user decision; the platform holds no standing to respond on the user's behalf, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Show people/videos/evidence; user chooses response; unresolved conflict blocks new registration, and (6) return Release/whitelist/dispute action, never auto-response; if the flow cannot complete, `CLAIM_REGISTRATION_BLOCKED` while an unresolved conflict on the recording bars any new registration, and `FORBIDDEN` when reaching a case or evidence outside the acting party's standing; no failure or timeout path produces an automatic response, release or dispute on the user's behalf, and an undecided case stays open with its evidence retained rather than resolving by default.
- **AC-DST-20 — Owner migrates/exports catalogue:** Given The requesting owner holds export standing on the requested scope; export is always available and never withheld for commercial reasons, and an import states its origin and its witnessed-data losses rather than fabricating attestations, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Export canonical/partner/message/identifier/assets/evidence; import marks origin/losses and reconciles IDs, and (6) return Portable package and honest witnessed boundary; if the flow cannot complete, `IDENTIFIER_CONFLICT` when an import carries the same ISRC under a conflicting holder, which blocks and routes to Shard 06 and Shard 10 rather than merging, and a resumable typed failure on a long export job stating its exact scope and safe retry rather than implying success; imported catalogue is marked asserted and not witnessed on every path, and neither partner access revocation nor account exit can erase canonical provenance or make the export unavailable.
- **AC-DST-21 — Owner enriches release descriptors:** Given The release exists and enrichment is advisory rather than gating: the Shard 09 project record and Shard 07 credits supply the `witnessed` pre-fill where they exist, audio analysis supplies `inferred` tempo and key, the Producer is prompted only for the gaps they are uniquely authoritative for, and the record is retained even where no selected partner currently supports MEAD, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Pre-fill mood/tempo/key/instrumentation/personnel/live-vs-programmed from the Shard 09 project record and Shard 07 credits, stamping each value `witnessed`; add audio-derived tempo/key stamped `inferred`; prompt the Producer only for gaps they are uniquely authoritative for. Descriptors are ONE source shared with the editorial pitch surface (DST-13), projected twice, never authored twice, and (6) return Versioned enrichment record; delivery is never blocked by its absence or incompleteness; if the flow cannot complete, `FORBIDDEN` for a delivery operator or any actor without Config standing on `release_enrichment`, a typed refusal for a malformed descriptor and a typed revision conflict on a competing enrichment edit, none of which blocks or fails the release delivery, because enrichment is never a gate; an off-platform master with no project record has nothing to pre-fill and falls to full manual entry, a partner without MEAD support is skipped silently with no error, no failure event and no user-visible failure state, an `inferred` value is never delivered as an artist assertion and is always correctable, and a retained record becomes retroactively deliverable when a partner's capability flag flips.
- **AC-DST-22 — Owner sets label copy and distributor of record:** Given The release owner or admin acts on a release version that has not yet been delivered, since a delivered version's label copy is frozen; the Shard 10 ownership record and the release year both resolve so the (P) and (C) lines derive; any divergence from a derived value carries a recorded justification; the current label-copy version is supplied; and the distributor-of-record consequence statement is presented at the moment the value is set, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Derive the (P)/(C) lines from the Shard 10 ownership record and the release year; require a recorded justification, visible to co-owners, for any divergence; warn without blocking where the (C) line names a party absent from the rights record; state the distributor-of-record consequences in plain language at the moment the value is set, and (6) return Versioned label-copy record with per-field provenance, frozen once delivered; if the flow cannot complete, `LABEL_COPY_JUSTIFICATION_REQUIRED` when a derived (P) or (C) value is diverged from without a recorded justification, `OWNERSHIP_RECORD_ABSENT` which routes to the readiness gate rather than accepting free text, `RELEASE_YEAR_UNSET` which leaves the year empty and flags it at the readiness gate rather than guessing, and `LABEL_COPY_CONCURRENT_EDIT` when a co-owner edited first, so the second editor sees that change before saving and last-write-wins never applies to an ownership assertion; a (C) line naming a party absent from the rights record warns and never blocks, a change on a delivered release routes to the update or redelivery path, and naming a label or distributor the owner does not control is not mechanically detectable at this layer and routes to Shard 06 as a trust concern.

### Global Interaction Rules

- Partner profile, validation rule pack and asset spec resolve from one immutable partner-knowledge version pinned at handoff.
- Partner facts are data, not hardcoded logic; no profile may require a knowingly false canonical assertion.
- Generation does not re-author or default missing facts. Readiness owns eligibility; generator validates only its output/profile.
- Delivery/contact notifications are purpose-scoped; distribution never directly messages fans.
- No external provider is considered successful without signed/verified acknowledgement or independent store-side evidence.

### Typed Field and Cardinality Registry

Field typing is deterministic: `*_id: uuid`, `*_at: timestamptz`, `*_date: date`, `*_minor: bigint`, `*_count: integer`, `currency: char(3)`, `is_*|has_*: boolean`, `state|status|type|kind|class: closed enum`, `version: bigint`, ratios `numeric(9,6)`, checksums `text`, and URLs `text`. Every named contract field uses this registry unless its contract declares a stricter type.

These named fields are additionally `closed enum` even though their names do not match the `state|status|type|kind|class` suffix rule: `descriptor_provenance` (resolving to `DescriptorProvenance`) and `label_copy_provenance` (resolving to `LabelCopyProvenance`). `delivery_message.kind` and `delivery_snapshot.kind` resolve to `DeliveryMessageKind`.

- **`release`:** required core fields `id: uuid`, `owner_id: uuid`, `state: closed enum`, `version: bigint`, `created_at: timestamptz`, `updated_at: timestamptz`; domain fields are the named keys in Contracts and the model row above using the deterministic registry; cardinality is N:1 to its owner/aggregate and 1:N to additive events, revisions or evidence unless the row declares uniqueness. Constraints/relationships: Owner, type, label copy, distributor statement, dates/state; immutable published versions..
- **`release_version`:** required core fields `id: uuid`, `owner_id: uuid`, `state: closed enum`, `version: bigint`, `created_at: timestamptz`, `updated_at: timestamptz`; domain fields are the named keys in Contracts and the model row above using the deterministic registry; cardinality is N:1 to its owner/aggregate and 1:N to additive events, revisions or evidence unless the row declares uniqueness. Constraints/relationships: Owner, type, label copy, distributor statement, dates/state; immutable published versions..

## Access Control

| Role | Allowed | Denied |
|---|---|---|
| Release owner/admin | Compose, destination/date choice, delivery/update/takedown/export under authority; Config on `release_enrichment` descriptors; sets `release_label_copy` including the (P)/(C) override justification and the distributor-of-record declaration | Rewrite recording rights/credits or force partner state |
| Co-owner/contributor | Own readiness/consent item, footprint notice and change request; sees every label-copy divergence and its recorded justification | Release edit/delivery/takedown without mandate, and editing the (P)/(C) lines, which are the rights holder's assertion |
| Producer | Asset conformance/replacement request and recording identity question; Config on `release_enrichment` for the technical descriptors they are uniquely authoritative for | Owner approval or rights overrides, and editing label copy — a disagreement with the (P) line is a Shard 10/06 rights dispute, not a metadata correction |
| Delivery operator | Assigned profile, queue, acknowledgement, triage and recovery operations | Canonical content edits, false live state, owner override, and any access to `release_enrichment` descriptors or `release_label_copy` |
| Partner adapter principal | One destination/message/thread callback scope | Other partners/releases, party authority |
| Rights/safety reviewer | Assigned suspension/claim evidence and narrow command | General catalogue/media browsing |
| Support | Minimum status/request-ID projection and named recovery | Raw messages/media/legal evidence by default |

## Accessibility

- Builder, findings, chase list, destination map/list, date plan, delivery board, remediation, takedown, claims and export are keyboard operable.
- Findings expose partner/item/severity/evidence/remedy in text; advisories collapse separately from blockers.
- Store status distinguishes requested/received/accepted/preorder/live/unknown/withdrawn/removed without color-only meaning.
- Timelines provide tables and person-owned critical path; dates include destination timezone and evidence basis.
- Irreversible takedown/change confirmation lists concrete losses before action and preserves focus after step-up.
- Long jobs expose resumable status, exact scope and safe retry; no spinner implies success.

## Edge Cases

| Scenario | Required behavior |
|---|---|
| Rights drift before dispatch | Halt, diff and re-run gate; never deliver stale snapshot. |
| Partner rule differs from canonical | Derive per-store rendering; never mutate canonical fact. |
| Profile gap/model gap | Attribute platform failure, suspend new delivery and repair/certify; do not blame artist. |
| Asset analysis fails three times | `unanalysable`, manual retry and target uncertainty; never false pass. |
| Message regenerated unexpectedly | Diff and require acknowledgement before handoff. |
| Ack out of order | Retain history by partner timestamp; never regress state. |
| Partner accepts but store not live | Accepted/live-wait; no live claim. |
| Store silent into date | T−24h forced choice; default announced date stands, no automatic move/redelivery. |
| Mixed item outcome | Partial row with structured rejected items; scoped redelivery only. |
| Artist ID asserted but not verified | First delivery blocked; Trust & Safety/merge chase. |
| Voluntary takedown before accepted delivery | Cancel queued thread; no invalid takedown message. |
| Metadata update replaces master | Ask same recording/new version; never silently reuse identity. |
| Unresolved ownership conflict | Block fingerprint registration across supported platforms. |
| Identifier allocation timeout | Lookup/reconcile, never second blind allocation. |
| Import has same ISRC with conflicting holder | Block and route Shard 06/10; do not merge. |
| User exits | Export remains available; partner access revocation cannot erase canonical provenance. |
| Partner does not consume MEAD | Skip silently; never an error path; user sees honest reach ("sent to N of M stores that use it"), never an implied failure. |
| Partner adds MEAD support later | Retained enrichment becomes retroactively deliverable; deliver the backlog. |
| Inferred tempo/key is wrong | Correctable; the correction is attributed, and whether it propagates to the Shard 09 version-scoped record or stays release-local is OPEN (ideation `12.02.04` Q-02, Agent-owned, deferred to `/create-prd-security`, blocked on the permission model). |
| Owner skips enrichment entirely | Delivery proceeds unchanged; advisory only, never a gate. |
| MEAD delivered after ERN acceptance | Normal; independently sequenced. |
| Off-platform master with no project record | Nothing to pre-fill; full manual entry, correctly scoped to the case that earns it. |
| (P) line contradicts the Shard 10 ownership record | Warn, require the recorded justification and notify the co-owners named on the ownership record; never publish the divergence silently. |
| (C) line names a party absent from the rights record | Warn only; never block. Publishing splits are the society's business, not the store's. |
| Label copy or distributor of record changes on a live release | Route through the update/redelivery path, never an in-place edit of a delivered version. |
| Two co-owners edit label copy at once | Edits serialize; the second editor sees the first's change before saving. Last-write-wins is unacceptable on an ownership assertion. |
| No release year available yet | (P)/(C) year cannot derive; leave the field empty and flag it at the readiness gate rather than guessing. |
| Owner names a label or distributor they do not control | Not mechanically detectable at this layer; route to Shard 06 as a trust concern, never a builder validation rule. Ideation `12.01.05` defers the rule to `/create-prd-security`. |
