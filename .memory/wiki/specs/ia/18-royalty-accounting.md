# Shard 18 — Royalty registration, ingestion, calculation and payout

**Status:** Complete
**Surface:** Web/PWA and asynchronous import/export jobs
**Source:** [Architecture design](../2026-08-02-architecture-design.md) · [Decomposition plan](decomposition-plan.md)

## Overview

Shard 18 owns society affiliation facts, registration payload projection/delivery status, immutable statement ingestion, deterministic parsing, catalogue matching, exact bitemporal calculation, recoupment position, restatements, payee statements, recovery findings and statement disputes. It does not interpret contracts, promise society acceptance, infer ownership, hide residuals or move multi-party royalty money before counsel/provider gate B3.

### Accounting Decisions

| Area           | Locked decision                                                                                                                                      |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| Registration   | Payload projects immutable Shard 10/09 rights data; user corrects source records, never edits delivery payload.                                      |
| Source files   | Original bytes and custody remain immutable even when unparseable; duplicate and restatement are distinct.                                           |
| Parsing        | Source/version/date adapter is deterministic data. No runtime LLM parsing and no user column mapping.                                                |
| Reconciliation | Every row classified and source-currency lines reconcile to the declared total/tolerance; no-total is explicitly `unoracled`.                        |
| Matching       | Probabilistic matches never move money. Human-confirmed, catalogue/source-scoped mappings are reversible and replay deterministically.               |
| Calculation    | Exact decimal, bitemporal, right/territory/source scoped, versioned and fully derived; unknown terms produce no fabricated amount.                   |
| Residuals      | Unmatched, underallocated, unpayable and converted residuals travel with every affected total. Nothing is dropped or redistributed.                  |
| Payout         | Statements/calculated balances may exist, but provider payout execution and disputed-money escrow remain disabled until B3 evolves the architecture. |
| Disputes       | Restatements version facts; disputes attach beside them and absorb concurrent versions rather than racing.                                           |

## Acceptance Criteria

- **AC-ROY-01 — Rights administrator records society affiliation:** Given Rights administrator acting under a current mandate for the party; body, territory, role, identifier, status and effective dates supplied with provenance, plus the expected version of any existing `society_affiliation` record, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Save body/territory/role/identifier/status/dates with provenance; conflicts block payload only, and (6) return Asserted/acknowledged affiliation or named conflict; if the flow cannot complete, `NOT_AUTHORIZED` outside the mandate; a competing affiliation for the same body and territory returns `SOURCE_CONFLICT`, names both actors, blocks only the affected registration payload and chooses no precedence, leaving the actor to correct the conflicting affiliation at source.
- **AC-ROY-02 — User validates work registration:** Given Actor may read the target work's Shard 10 rights, split and party-identifier records; a target society, territory and as-of date are supplied; validation is a read-only projection, so no delivery payload is editable here, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Project rights/title/party identifiers as-of target; run structural/arithmetic checks and assign blockers to actors, and (6) return Registration-ready belief or actionable blockers; if the flow cannot complete, `PAYLOAD_NOT_READY` or `RIGHTS_INCOMPLETE` returns every structural and arithmetic blocker named and assigned to the actor who owns the source record; the user corrects the Shard 10/09 source record and re-runs validation, and the delivery payload is never edited directly.
- **AC-ROY-03 — Administrator delivers registration:** Given Rights administrator holding a mandate over the work; a registration-ready payload from `ProjectRegistrationPayload` with no open blocker; a versioned society profile carrying dialect, channel and cadence for the target body and territory; prior submissions in the same work × society × territory sequence resolved, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Select versioned society profile/channel/cadence; sequence-aware file/API/manual task with expected-by, and (6) return Submitted state with immutable payload/receipt; if the flow cannot complete, `PAYLOAD_NOT_READY` where blockers remain, `DELIVERY_SEQUENCE_CONFLICT` where an earlier submission for the same work × society × territory is unresolved, `NOT_AUTHORIZED` outside the mandate; nothing is submitted and no receipt is created, and the actor clears the blocker or the sequence and retries under the same idempotency key.
- **AC-ROY-04 — User receives acknowledgement/rejection:** Given An `in_flight` submission exists for that work × society × territory, and either a society response arrives on the registered channel or its expected-by date is breached, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Parse response; update work×society×territory belief, reason/action/owner and age, and (6) return Known outcome (`registered` | `registered_unmatched` | `matched` | `rejected`), conflict route (`conflicted`) or overdue alarm (`overdue`); if the flow cannot complete, an untranslatable society rejection code is recorded as an explicit untranslatable state and never paraphrased into a guess; silence past expected-by synthesises an `overdue` observation and alarm rather than indefinite pending or assumed acceptance; a late acknowledgement resolves that alarm and updates the same belief instead of creating a second contradictory one; a competing claim becomes `conflicted` and routes to Shard 10, never collapsing into `rejected`.
- **AC-ROY-05 — Authorized party registers statement source:** Given Actor is the payee/rightsholder or a mandated administrator for that payee; counterparty/payer relationship, remittee, cadence, correction window and custody channels supplied, with the expected version of any prior registry entry, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Bind counterparty/payee/reporting relationship, remittee, cadence/correction window and custody channels, and (6) return Versioned source registry entry; if the flow cannot complete, `NOT_AUTHORIZED` where the actor holds no reporting relationship with that counterparty; schema and policy validation fail before mutation so no partial registry entry exists, and the actor supplies the missing relationship facts and retries.
- **AC-ROY-06 — User uploads/forwards/fetches statement:** Given A versioned `statement_source` entry exists and binds this actor to that counterparty/payee relationship; bytes arrive complete with a checksum over a supported custody channel — upload, DKIM-witnessed forward or platform fetch, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Verify complete transfer/checksum/custody; certain-byte dedupe; retain private original, and (6) return Ingest, duplicate, notification-only or loud failure; if the flow cannot complete, `TRANSFER_INCOMPLETE` on byte-length or checksum mismatch fails loudly and never half-ingests; `DUPLICATE_STATEMENT` where the same checksum recurs for the same counterparty/payee, with no second parse or calculation; original bytes and custody are retained immutably even when unparseable, and the actor re-transfers or supplies a semantically distinct file.
- **AC-ROY-07 — System parses statement:** Given A `received` `statement_ingest` with immutable original bytes, a declared source, an in-file fingerprint, and an `adapter_version` effective for that statement date, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Select declared source + fingerprint adapter version by statement date; deterministic whole-file parse and classification, and (6) return Reconciled, unoracled or blocked parse; if the flow cannot complete, `ADAPTER_MISMATCH` blocks and names the mismatch rather than sniffing content or guessing a parser; `PARSE_UNRECONCILED` where a row is unclassified or the source-currency sum falls outside the file-derived tolerance, blocking all downstream matching and calculation; a file with no declared total resolves to `unoracled` and travels downstream labelled; the adapter maintainer reviews and activates a corrected deterministic adapter version while the original and prior adapter output remain immutable.
- **AC-ROY-08 — User resolves catalogue identities:** Given A `reconciled` or `unoracled` parse whose repeated lines are collapsed to source identities; the actor may act on that payee's catalogue; a fuzzy candidate is offered only where at least two independent signal classes support it, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Apply identifier cascade; show multi-signal candidates; confirm/reject reversible source identity mapping, and (6) return Deterministic attribution or value-ranked exception; if the flow cannot complete, `MAPPING_CONFIRMATION_REQUIRED` — no probability threshold auto-confirms and a probabilistic match never moves money; a title-only candidate returns to the exception queue carrying its open value; contradicting facts are shown once and both retained; a reversal after statements or payouts preserves rejection history and opens a restatement cascade over every attributed line.
- **AC-ROY-09 — User works exception queue:** Given One or more open `royalty_exception` rows within the actor's authorized payee and catalogue scope, each carrying a closed-taxonomy reason, open amount, age and any correction-window deadline, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Rank source identities by open value/age/reason; resolve not-mine, mapping, missing period/rights or escalation, and (6) return Open decreases; closed history never disappears; if the flow cannot complete, a resolution outside the closed reason taxonomy is refused and no materiality threshold may drop an item; closed history is immutable and never disappears; an exception this actor cannot resolve escalates on a named route with its open amount preserved and continues to age as a money-sized alarm.
- **AC-ROY-10 — System normalizes periods/currency:** Given A parsed `normalized_line` carrying its source amount, currency and precision, with usage, distribution, receipt and payout dates held distinct, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Preserve source amount; pin period basis, source FX facts and optional reporting-rate provenance, and (6) return Source-native fact plus labelled derived view/residual; if the flow cannot complete, `PERIOD_UNKNOWN` where no usable period can be derived and no bounded window proves a single split version — the line becomes an exception rather than receiving a guessed period; `FX_UNAVAILABLE` where no rate on or before the date exists within seven days, returning the source-native result plus a named converted residual and never an invented rate.
- **AC-ROY-11 — Administrator records executable deal terms:** Given Rights administrator with a mandate over the deal; terms authored by a human in the closed taxonomy with scope, application order and effective/recorded times, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Store authored closed-taxonomy terms/order/scope/effective/recorded time; flag unrepresentable/contradictory, and (6) return Versioned term set or calculation hold; if the flow cannot complete, `TERMS_CONTRADICTORY` or an unrepresentable term flags the set and returns `CALCULATION_HELD`; the platform never interprets contract text and never substitutes a standard or default term, so the deal stays held until the administrator authors an expressible term.
- **AC-ROY-12 — System calculates royalties:** Given A normalized reconciled line attributed through a human-confirmed identity mapping, never a probabilistic one, plus a fully resolvable bitemporal parameter set of rights, splits, allocation and authored deal terms as of both usage and knowledge time, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Resolve bitemporal right/split/allocation/deal inputs; exact arithmetic; itemized deductions and residual, and (6) return Immutable derivation and scoped party results; if the flow cannot complete, `TERMS_UNKNOWN` for a known deal with missing terms yields no amount — not zero, not a standard rate, not the raw split; `RIGHTS_INCOMPLETE` and `ALLOCATION_INVALID` hold rather than estimate; parts above the whole hard-block with `ALLOCATION_INVALID`; an entity or deal cycle is refused with the cycle named; parts below the whole create a visible residual routed to exceptions and rights, never redistribution; `CALCULATION_HELD` persists until the missing fact is authored upstream.
- **AC-ROY-13 — User views recoupment:** Given Actor may read that payee's calculations; advance amount, application order, reserve timing and cross-collateral scope exist as explicit recorded terms, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Derive advance/recoupable applications/cross-collateralization separately from earnings, and (6) return Payability position or explicit unknown; if the flow cannot complete, a missing advance or application term returns an explicit unknown position rather than an assumed zero or a netted balance, and earnings remain readable independently of payability.
- **AC-ROY-14 — New fact triggers restatement:** Given A source correction, mapping reversal, or rights, allocation or deal-term change lands against an existing calculation or issued statement version, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Recompute transitive dependent calculations/statements; retain prior version and causation, and (6) return New version/delta; no overwrite; if the flow cannot complete, the prior version, its cause and its dependency manifest are always retained, so no overwrite is possible; a restatement racing an open dispute is absorbed by that dispute with its exact delta and a stale dispute resolution cannot win the race; a partially applied cascade leaves the prior version authoritative and re-queues dependent recomputation idempotently.
- **AC-ROY-15 — Administrator issues payee statement:** Given Calculations for that payee and period exist in `calculated` or `restated` state, and display FX rates and coverage are resolvable for freezing, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Freeze display FX, coverage and earned/deducted/applied/payable lines with drill-through/breaks, and (6) return Immutable zero-or-nonzero statement version; if the flow cannot complete, zero-paid and broken-chain statements still issue rather than being suppressed; where drill-through cannot reach source or session the first honest break is shown; coverage and open, unattributed or held residuals appear on every applicable view and export; an unresolvable display rate leaves a source-native line with a named residual.
- **AC-ROY-16 — Finance operator requests payout:** Given Finance operator with MFA and a stated reason, and a calculated balance for the payee; the B3 counsel/provider gate is a hard precondition that no role overrides, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Gate on B3/provider/KYC/tax/holds/reconciliation; launch/ungated system refuses execution, and (6) return Disabled or future idempotent provider run; if the flow cannot complete, `PAYOUT_DISABLED_B3` returns before any provider side effect; the calculated statement and balance remain and are never described as platform custody, escrow, float or guaranteed money; no threshold, dormancy, erasure or account closure converts a balance into revenue, forfeiture or redistribution; execution becomes reachable only after `/evolve-feature` clears gate B3.
- **AC-ROY-17 — User reviews recovery candidate:** Given Actor holds a mandate covering the party and right; the search is bounded to approved corpora and every candidate carries evidence, since self-asserted credit alone cannot rank a claim, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Search approved corpora with evidence/mandate; never promise amount; assemble filing or handoff pack, and (6) return Dismissed, submitted or expected-by monitored claim; if the flow cannot complete, a candidate amount the source does not prove stays unknown and is never presented as promised money; where no filing API exists the claim becomes an explicit manual handoff pack with an expected-by; dismissed candidates persist across re-sweeps rather than resurfacing as new; platform-caused leakage is attributed to the platform.
- **AC-ROY-18 — Party opens statement dispute:** Given Actor is a party to the named calculation and statement versions being disputed, and supplies the scoped amount, reason, evidence and any deadline, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Freeze amount scope, attach evidence/reason/deadline, incorporate restatements and route Shard 06 process, and (6) return Open/resolved dispute; no hidden payment; if the flow cannot complete, `DISPUTE_SCOPE_CONFLICT` where the scope cannot be frozen against a named calculation or statement version; a concurrent restatement is absorbed with its exact delta rather than racing; the disputed amount may be marked held in calculation, but no escrow release exists before B3 and no payment is hidden; the process routes to the Shard 06 case path.
- **AC-ROY-19 — System derives performer registration eligibility:** Given Acting party has readable Shard 07 credit records and the recording carries a Shard 22 `recording_identifier` ISRC, with a body and territory in scope; no ownership share, split or agreement is required or consulted, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Project Shard 07 credit records for the acting party against Shard 22 `recording_identifier` ISRC; emit one eligibility row per (performer party, recording ISRC, body, territory); eligibility derives from the credit graph alone — never from an ownership share, split or 100% arithmetic; imported credits are eligible on identical terms to captured ones; attestation tier scales the platform's own suggestion strength ONLY and has no standing with a society, and (6) return Eligible-unregistered set, or named blocker (`ISRC_ABSENT`, `MEMBERSHIP_ABSENT`); if the flow cannot complete, `ISRC_ABSENT` names the Shard 22 gap instead of a silent dead end; `MEMBERSHIP_ABSENT` surfaces as a leakage finding — the platform points at the missing membership and never joins on the performer's behalf; an unclaimed shell performer is recorded, not suppressed.
- **AC-ROY-20 — Performer or authorized filer asserts featured role:** Given An eligibility row exists for that (performer party, recording ISRC, body, territory) and the actor is either the named performer or an administrator with a mandate over that performer; the assertion is `featured` or `non_featured`, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Record `featured` or `non_featured` as an ATTRIBUTED assertion with asserting party and timestamp, the platform never computing it, and where the asserter is not the named performer emit a confirmation request to that performer and set `role_confirmation: unconfirmed`, and (6) return Usable assertion carrying its confirmation state; if the flow cannot complete, the platform never computes a role, so a refusal is returned rather than a platform verdict; an administrator may not confirm on the performer's behalf; a contested featured/non-featured assertion routes to the same Shard 06/07 credit-dispute evidence path; a performer who never answers leaves the assertion permanently `unconfirmed` with periodic nudges and no hold; assertions are append-only, so a refused write leaves prior assertions intact.
- **AC-ROY-21 — Administrator files performer registration:** Given Rights administrator with a mandate over the performer; an eligibility row carrying an ISRC; the performer's OWN `society_affiliation` membership for that body and territory; a versioned society profile with channel and expected-by; platform accreditation is explicitly NOT a precondition, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Bind to the performer's OWN society membership, platform accreditation not being a precondition unlike the work-registration path, and deliver via the same versioned society profile/channel/expected-by machinery as `DeliverRegistration`, including the manual-task channel, and (6) return Submitted state with immutable payload/receipt, or handoff pack; if the flow cannot complete, `MEMBERSHIP_ABSENT` blocks and surfaces as a leakage finding; `ISRC_ABSENT` names the Shard 22 gap; `PERFORMER_SLOT_CONFLICT` where two parties claim the same performer slot holds money at source and routes to Shard 10; where no API channel exists the filing becomes an explicit manual task and handoff pack with an expected-by; a repeat filing on the same (performer_party, recording_isrc, body, territory) key returns the existing record rather than a duplicate.

### Global Interaction Rules

- Source fact, platform derivation, registration belief, calculated entitlement, payability, provider transfer and actual receipt are separate states.
- Every number names source currency, coverage, right type, territory, usage period, calculation version and residual where applicable.
- Work/catalogue matching never asserts ownership; Shard 10/09 owns rights and split truth.
- Calculated/held balances are not described as platform custody or escrow while B3 is disabled.
- Financial commands require MFA where policy demands, expected version, idempotency, immutable audit and exact reconciliation.

#### `RegistrationBeliefState` member semantics

- `unregistered` — never submitted. Renders the reason (blocked, or never attempted); never an unexplained absence.
- `in_flight` — delivered, still within expected-by. Always carries the expected-by date.
- `registered` — acknowledgement received for that body and territory, dated, with retained evidence.
- `registered_unmatched` — registered, but the body's usage is still sitting in its unmatched pool. FIRST-CLASS, not a variant of `registered` (ideation `10.01.05` D-02): at the MLC it is the modal outcome for weak metadata and it is publicly observable. This is the member that distinguishes a successful registration from money still in the black box, and collapsing it into `registered` destroys the shard's only signal for that condition. The platform observes the pool; it never claims to drive matching.
- `matched` — the body has attributed usage to the registration. Income is expected on that body's calendar; hand off to Shard 19 forecasting.
- `rejected` — a rejection code was returned. Translated to an action and a named owner, or an explicit untranslatable state; never a paraphrased guess at a society code.
- `conflicted` — the society reports a competing claim. Routes to Shard 10 as a rights dispute; money held at source. A conflict is NOT a rejection and must not collapse into one.
- `overdue` — expected-by breached with silence. Synthesises an observation and an alarm. Indefinite pending and assumed acceptance are both forbidden.
- `stale` — registered, but the underlying splits have since changed, so the society now holds a record the platform knows is wrong. Re-registration is required.

A late acknowledgement arriving AFTER an `overdue` alarm resolves that alarm and updates the same belief; it never creates a second, contradictory belief, and a retry racing a late acknowledgement must not produce a duplicate registration.

`active registration`, as consumed by [Deep Dive 19](deep-dives/19-royalty-reporting-forecasting.md) § Forecast step 2, resolves against this enum: `registered`, `registered_unmatched` and `matched` are active; every other member — `unregistered`, `in_flight`, `rejected`, `conflicted`, `overdue` and `stale` — is not.

## Edge Cases

| Scenario                                            | Required behavior                                                                                                                                          |
| --------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Conflicting society affiliations                    | Block affected payload and name actors; do not choose precedence.                                                                                          |
| Society silent past expected-by                     | Create overdue observation/alarm; never indefinite pending or assumed acceptance.                                                                          |
| Same bytes uploaded twice                           | Certain duplicate, no second parse/calculation; restatement requires parsed semantic distinction.                                                          |
| Adapter fingerprint mismatch                        | Block and name mismatch; never guess parser.                                                                                                               |
| No declared statement total                         | `unoracled` travels downstream; never silently reconciled.                                                                                                 |
| Parse total differs within precision                | Use file-derived tolerance only; outside blocks all downstream calculation.                                                                                |
| Fuzzy title-only candidate                          | Exception with value; not confirmable candidate and never auto-match.                                                                                      |
| Mapping reversed after payouts/statements           | New restatement cascade; historical cause and affected versions preserved.                                                                                 |
| Usage period spans split change                     | Allocate only at source-supplied granularity; overlap without valid weights blocks.                                                                        |
| FX unavailable within seven days                    | Source-native result plus named converted residual; never invent rate.                                                                                     |
| Known deal but terms absent                         | No calculated amount, not zero/standard/raw split.                                                                                                         |
| Calculation parts exceed whole                      | Hard block; below whole creates visible residual, never redistribution.                                                                                    |
| Circular entity/deal resolution                     | Refuse and name cycle.                                                                                                                                     |
| Restatement races dispute                           | Dispute absorbs new version and exact delta; no parallel stale resolution.                                                                                 |
| Payout requested before B3                          | Deny; calculated statement remains and never claims custody/escrow.                                                                                        |
| Payee unpayable/erased                              | Balance remains attributable under legal policy, never float, revenue, forfeiture or redistribution.                                                       |
| Original contains third-party rows                  | Parse whole file privately; do not notify/expose/aggregate third parties.                                                                                  |
| Splits change after a successful registration       | Move the belief to `stale` and require re-registration; never silently leave `registered`, because the society holds a record the platform knows is wrong. |
| Performer has no society membership                 | Surface as a leakage finding; the platform points, it never joins on their behalf.                                                                         |
| Featured/non-featured contested                     | Route to the same evidence path as a credit dispute (Shard 06/07); never a platform verdict.                                                               |
| Performer never responds to the confirmation prompt | No blocking; the assertion stands permanently tagged `unconfirmed`. Periodic nudge, never a hold.                                                          |
| Performer credit exists with no ISRC                | Block with the ISRC gap named against Shard 22; never a silent dead end.                                                                                   |
| Performer is an unclaimed shell party               | Money is visible to the platform for a person it cannot contact; record it, do not suppress it.                                                            |
| Two parties claim the same performer slot           | Society-side conflict; money held and routed to Shard 10.                                                                                                  |
