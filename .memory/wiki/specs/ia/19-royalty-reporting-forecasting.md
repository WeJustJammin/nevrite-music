# Shard 19 — Performance reporting, money-in-flight and forecasting

**Status:** Complete
**Surface:** Web/PWA and scheduled reference-data jobs
**Source:** [Architecture design](../2026-08-02-architecture-design.md) · [Decomposition plan](decomposition-plan.md)

## Overview

Shard 19 owns live-performance PRO returns, cue-sheet expectations, curated distribution calendars, money-in-flight expectations and conservative royalty forecasts. It consumes immutable Shard 18 accounting facts; it never edits them, promises money, files another party's cue sheet, blends deterministic dates with statistical estimates or emits a forecast when evidence is too thin.

### Scope Reconciliation

|---|---|
| In-scope source documents | 4 |

| Reporting | Live setlist→PRO return and cue-sheet expectation/chase |
| Timing | Society/territory/income-type distribution calendar and overdue tolerance |
| Forecasting | Registration-gated range with public calibration; silence on thin data |

## Acceptance Criteria

- **AC-RRF-01 — Performer reports completed show:** Given A completed Shard 09/booking show with act, date, venue, territory and an immutable setlist version readable by the actor, who is the performer or reporter for that act; a manually entered show is admitted but explicitly lower-provenance, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Load Shard 09/booking show and setlist; match registered works; explain covers/unmatched entries, and (6) return Draft return or honest no-route state; if the flow cannot complete, `WORK_UNREGISTERED` preserves the setlist entry, omits the return line and creates a registration/leakage action rather than filing an unregistered work; a cover matches the writer's work and states plainly that the performer may earn nothing; `REPORTING_ROUTE_UNAVAILABLE` for the territory returns an honest no-route state rather than an empty draft return.
- **AC-RRF-02 — Performer/operator submits PRO return:** Given A draft return exists for that show; the reporter holds their OWN PRO membership, or an operator holds an explicitly permitted reporting role for that territory; a versioned society delivery profile with sequence and expected-by is available, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Resolve own membership/reporting role/territory; freeze return version and expected-by; prevent blind duplicate, and (6) return Submitted/manual task or typed block; if the flow cannot complete, `MEMBERSHIP_REQUIRED` where the reporter has no membership of their own, because the platform never borrows another party's accreditation; `REPORTING_ROUTE_UNAVAILABLE` becomes an explicit manual task rather than a silent success; `RETURN_DUPLICATE` where reporter-role and sequence checks find an existing filing for the same show, with the society remaining the final deduper; submission never implies guaranteed income.
- **AC-RRF-03 — Performer amends setlist:** Given A submitted `live_performance_return` exists for that show and the amending actor is its original reporter or an authorized operator holding the same reporting role, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Create superseding return against same show; retain prior filing and restart expected-by, and (6) return Amended version, never duplicate history loss; if the flow cannot complete, the prior filing is retained and superseded, never deleted or overwritten, and the expected-by clock restarts on the superseding version; `RETURN_DUPLICATE` refuses an amendment attempting to file as a second independent return.
- **AC-RRF-04 — Rights holder tracks cue sheet:** Given Rights holder or mandated administrator with a licensed placement, plus the production, territory and cue-sheet obligation evidence that gives rise to the expectation, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Create expectation from licensed placement, production/territory and obligation evidence, and (6) return Expected, confirmed, missing or unverifiable; if the flow cannot complete, `NOT_AUTHORIZED` where the actor holds no mandate over the placement; where the obligation cannot be evidenced for a territory the expectation is `unverifiable` — never assumed filed and never assumed missing, and per-territory unverifiability is never collapsed into `confirmed` or `missing`.
- **AC-RRF-05 — User chases missing cue sheet:** Given A `missing` or `unverifiable` `cue_sheet_expectation` within the actor's mandate, with a contact route or a recorded absence of one, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Create off-platform task/contact evidence; platform never files for production, and (6) return Follow-up history and honest dead end; if the flow cannot complete, the platform never files a cue sheet for the production, so an unreachable or defunct production returns an honest dead end with the expectation retained and the follow-up history preserved, never a fabricated escalation or an implied filing.
- **AC-RRF-06 — Curator updates calendar:** Given Calendar curator with a reviewed source; the candidate names body, territory, income type, usage-period mapping, distribution schedule, tolerance, provenance and effective dates, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Version body/territory/income type/usage period/distribution/tolerance with source provenance, and (6) return Reviewed active calendar version; if the flow cannot complete, activation without review is refused, since silent activation is denied to the curator role; a correction supersedes rather than edits, and its manifest identifies every affected expectation while prior expectations retain the source version they were computed under.
- **AC-RRF-07 — System projects money-in-flight:** Given An active Shard 18 registration belief — `registered`, `registered_unmatched` or `matched` — for that work, society and territory, and an active `distribution_calendar_version` covering that body, territory and income type, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Join registration state to applicable calendar; state body/period/due date and amount unknown, and (6) return Dated expectation, never fabricated amount; if the flow cannot complete, `REGISTRATION_REQUIRED` where the registration is not active and `CALENDAR_UNKNOWN` where no reviewed calendar covers that body, territory and income type; both render an honest absence or finding rather than a default cadence, and no amount is fabricated where no independently sourced amount fact exists.
- **AC-RRF-08 — Statement arrives:** Given A Shard 18 statement fact with resolvable source, right and period evidence; a matching `money_in_flight_expectation` may or may not exist, since the calendar is not an income gate, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Match Shard 18 source/period/right to expectation and mark arrival independent of expected amount, and (6) return Arrived/reconciled or unexplained arrival; if the flow cannot complete, an arrival with no matching expectation reconciles normally as an unexplained arrival and is never rejected; matching rests on source, right and period evidence and never on the expected amount, so an amount mismatch does not suppress the arrival.
- **AC-RRF-09 — Expected distribution is late:** Given A `money_in_flight_expectation` whose due date has passed, plus the tolerance carried by the calendar version it was computed under and the counterparty-wide delay signal, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Apply versioned tolerance and counterparty-wide delay signal before finding, and (6) return Overdue observation, not automatic leakage accusation; if the flow cannot complete, `EXPECTATION_NOT_DUE` until the versioned tolerance elapses; a market-wide slip visible in the counterparty-wide delay signal suppresses the finding, so lateness produces an overdue observation and never an automatic leakage accusation.
- **AC-RRF-10 — User requests forecast:** Given Actor may read that party's catalogue; `forecast_eligibility` passes the governed minimum-history, coverage, active-registration and stable-rights-basis policy version, and deterministic in-flight expectations have already been separated out, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Verify registrations, rights stability, coverage and sufficient history; separate in-flight facts, and (6) return Range or explicit insufficient-data silence; if the flow cannot complete, `INSUFFICIENT_HISTORY` or `REGISTRATION_REQUIRED` returns explicit insufficient-data silence with the failing check named, never a chart over thin or lumpy data; a disclosed one-off event is excluded or robustly isolated rather than silently establishing a baseline; no forecast may feed a payable balance, payout, credit decision or guaranteed-income language.
- **AC-RRF-11 — Model recalibrates:** Given An immutable `royalty_forecast_version` whose horizon has elapsed, and the actual Shard 18 accounting versions covering that horizon, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Compare immutable forecast version to actual Shard 18 outcomes; publish error/coverage, and (6) return Calibrated/stale/withdrawn version; if the flow cannot complete, a model replacement never rewrites historical forecasts, and error and coverage are published rather than suppressed; where actuals do not yet cover the horizon the calibration is withheld rather than reported against partial data.
- **AC-RRF-12 — Catalogue/rights change:** Given A Shard 10 rights, registration or catalogue change lands against the basis of an existing active forecast version, when the actor invokes this flow, then the system MUST (1) validate inputs, (2) authenticate and resolve acting context, (3) authorize, (4) enforce revision and idempotency, (5) Invalidate affected forecast basis and recompute only when still eligible, and (6) return No stale confident chart; if the flow cannot complete, `FORECAST_BASIS_STALE` marks the forecast stale or withdrawn before any recompute, so no stale confident chart survives the change; where the party no longer passes eligibility no replacement forecast is emitted.

### Types and Errors

`ReturnState = draft|submitted|amended|overdue|distributed|not_filed`; `CueSheetState = expected|confirmed|missing|unverifiable|collecting`; `InFlightState = scheduled|due|arrived|overdue|unknown`; `ForecastState = insufficient_data|active|stale|withdrawn|calibrated`.

Errors: `NOT_AUTHORIZED`, `MEMBERSHIP_REQUIRED`, `WORK_UNREGISTERED`, `RETURN_DUPLICATE`, `REPORTING_ROUTE_UNAVAILABLE`, `CALENDAR_UNKNOWN`, `EXPECTATION_NOT_DUE`, `REGISTRATION_REQUIRED`, `INSUFFICIENT_HISTORY`, `FORECAST_BASIS_STALE`.

## Accessibility

- Setlist matching, return status, calendar, in-flight, forecast and calibration views are keyboard operable with visible focus and persistent text states.
- Dates always include timezone/period context; ranges expose lower/upper/confidence/basis in text.
- Known dates, unknown amounts, estimates, actuals, overdue and unverifiable states never rely on color alone.
- Charts have equivalent tables; insufficient data renders explanation rather than an empty misleading axis.
- Submission/amendment jobs preserve input and announce terminal state without time-limited-only feedback.

## Edge Cases

| Scenario | Required behavior |
|---|---|
| Cover song | File writer's work correctly; explain performer may earn nothing. |
| Unregistered original | Preserve setlist; omit return line and create registration/leakage action. |
| Venue and performer may both report | Reporter-role/sequence checks prevent platform blind duplicate; society remains final deduper. |
| Cue sheet cannot be verified | `unverifiable`, never assumed filed/missing. |
| Production is defunct/no contact | Honest dead end and retained expectation, no fake escalation. |
| Calendar changes | New version affects future projection; prior expectation retains source version and correction history. |
| Distribution slips market-wide | Tolerance/delay signal prevents premature leakage label. |
| Unexpected statement arrives | Reconcile normally; calendar is not an income gate. |
| Thin/lumpy history | No forecast; in-flight facts remain separate. |
| One-off sync distorts history | Exclude/robustly model with disclosed basis; never silently establish baseline. |
| Rights/registration changes | Mark forecast stale/withdrawn before recompute. |
| Forecast used as guaranteed cash | UI/API labels range, basis and calibration; no payable/payout contract accepts forecast. |
